# RocketMQ 消息可靠性（防丢失）

> "消息会丢吗？" —— MQ 面试 100% 必问。
> 本篇要解决：
> ① 一条消息从 Producer 到 Consumer 全程，三个阶段各有什么丢失场景？
> ② "消息绝对不丢"是不可能的——RocketMQ 提供的是哪几档可靠性？
> ③ 防丢失方案的代价：吞吐降多少？延迟增多少？什么场景才值得？
> ④ 业务侧补偿（事务消息、幂等、对账）和 MQ 侧防丢的关系是什么？

---

## 一、消息丢失的三个阶段

```
┌─────────────────────────────────────────────────────────────┐
│   阶段 1: 生产                                              │
│   Producer ──网络──► Broker                                  │
│   ❌ 网络抖动、Broker 拒绝、Producer 进程挂                 │
└─────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────┐
│   阶段 2: 存储                                              │
│   Broker 内存 ──刷盘──► 磁盘 ──复制──► Slave                │
│   ❌ Broker 崩溃、OS 崩溃、磁盘损坏、主从切换数据丢失       │
└─────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────┐
│   阶段 3: 消费                                              │
│   Broker ──Pull──► Consumer ──ACK──► Broker                 │
│   ❌ 消费抛异常、Consumer 进程挂、提交早于业务完成          │
└─────────────────────────────────────────────────────────────┘
```

每一阶段都需要单独防御。**任意阶段失防 → 整体不可靠**。

## 二、阶段 1：生产端防丢

### 2.1 三件套

```
① 同步发送
② 重试机制
③ 多 Master 部署
```

### 2.2 为什么不用异步/Oneway？

| 发送方式 | 失败感知 | 是否丢消息 |
| --- | --- | --- |
| **Sync** | 同步抛异常 | ✅ 不丢（业务层捕获重试） |
| **Async** | 回调通知 | ⚠️ 容易丢（业务忘了回调里处理失败） |
| **Oneway** | 完全不感知 | ❌ 会丢（OS 错误也察觉不到） |

**结论**：可靠性要求高的场景**只能用 Sync**。Async 适合"丢了能补偿"的场景（如发邮件、通知）。Oneway 只适合日志埋点。

### 2.3 重试配置

```java
// 同步发送默认重试 2 次（共 3 次发送），换 Broker
producer.setRetryTimesWhenSendFailed(2);
producer.setRetryAnotherBrokerWhenNotStoreOK(true);  // 失败换 Broker

// 异步发送默认重试 2 次（同 Broker）
producer.setRetryTimesWhenSendAsyncFailed(2);
```

**关键**：业务层最终捕获到 `MQClientException` / `RemotingException` 后，**必须有补偿**——本地落库 + 重试任务，否则重试 N 次仍是丢。

### 2.4 多 Master 容灾

```
Topic 分布在 3 个 Broker Group：
  Broker-A (Master) ─┐
  Broker-B (Master) ─├─► 同 Topic 的 Queue 分散在 3 个 Master
  Broker-C (Master) ─┘
  
任 1 个挂了，Producer 自动切换到其他 Master（故障规避机制）
```

单 Master 模式下 Master 挂 = Topic 不可写，必丢。

### 2.5 业务层补偿：消息发送本地表

```java
// 步骤 1: 业务表 + 消息发送状态表 在同一个事务中插入
@Transactional
public void createOrder(Order order) {
  orderDao.insert(order);
  messageDao.insert(new MsgRecord(order.getId(), "PENDING"));
}

// 步骤 2: 发送 MQ
SendResult result = producer.send(buildMsg(order));

// 步骤 3: 更新发送状态
if (result.getSendStatus() == SEND_OK) {
  messageDao.updateStatus(order.getId(), "SENT");
} else {
  messageDao.updateStatus(order.getId(), "FAILED");
}

// 步骤 4: 定时任务扫描 PENDING/FAILED，重发
```

这就是 **本地消息表 + 定时重试** 模式——即使 MQ 完全挂了，业务也能在恢复后补发。但要配合幂等。

## 三、阶段 2：存储端防丢

### 3.1 三档可靠性

| 配置组合 | 单机崩溃 | 进程挂 | OS 崩溃 | 磁盘损坏 |
| --- | --- | --- | --- | --- |
| ASYNC_FLUSH + ASYNC_MASTER | ❌ 丢 | ✅ 不丢 | ❌ 丢 ≤ 500ms | ❌ 全丢 |
| ASYNC_FLUSH + SYNC_MASTER | ✅ 不丢 | ✅ 不丢 | ✅ 不丢（Slave 也有 PageCache）| ❌ 丢 |
| SYNC_FLUSH + SYNC_MASTER | ✅ 不丢 | ✅ 不丢 | ✅ 不丢 | ⚠️ 单台坏不丢 |
| Dledger（Raft） | ✅ 不丢 | ✅ 不丢 | ✅ 不丢 | ⚠️ 多数派坏才丢 |

> 详见 [刷盘与复制](./刷盘与复制.md)。

### 3.2 推荐配置（互联网业务）

```properties
# Master
brokerRole=SYNC_MASTER
flushDiskType=ASYNC_FLUSH

# Slave
brokerRole=SLAVE
flushDiskType=ASYNC_FLUSH
```

**承诺**：单机宕机不丢；OS 崩溃不丢（Slave 也有 PageCache 副本）。

吞吐相比"全异步"下降 ~30%（多了一次主从复制等待），但避免了金融级 SYNC_FLUSH 的 50% 性能损失。

### 3.3 推荐配置（金融级）

```properties
# 同步刷盘 + 同步复制
brokerRole=SYNC_MASTER
flushDiskType=SYNC_FLUSH
```

或：

```properties
# Dledger（自动主备切换）
enableDLegerCommitLog=true
flushDiskType=SYNC_FLUSH
```

### 3.4 监控指标

```
- haSlaveFallbehindMax  Slave 落后 Master 字节数（生产 < 1MB，> 100MB 报警）
- putMessageTimes        写入次数
- putMessageFailedTimes  写入失败次数
- pageCacheLockTimeMills 写 PageCache 阻塞时长（> 100ms 即异常）
- diskMaxUsedSpaceRatio  磁盘使用率（> 85% 触发拒绝写）
```

## 四、阶段 3：消费端防丢

### 4.1 关键原则

```
"消费成功"的定义 = 业务逻辑已完成 ＋ Listener 返回 CONSUME_SUCCESS
而不是 = 消息从 Broker 拉到 Consumer
```

错误示范：
```java
// ❌ 错：异步线程处理，Listener 直接返回成功
public ConsumeConcurrentlyStatus consumeMessage(List<MessageExt> msgs, ...) {
  asyncExecutor.submit(() -> {
    processBusiness(msgs);  // 异步处理，可能失败
  });
  return CONSUME_SUCCESS;  // ❌ 但这里立即返回了
}
```

正确示范：
```java
// ✅ 同步处理，业务完成才返回
public ConsumeConcurrentlyStatus consumeMessage(List<MessageExt> msgs, ...) {
  try {
    for (MessageExt msg : msgs) {
      processBusiness(msg);
    }
    return CONSUME_SUCCESS;  // 业务全部成功
  } catch (Exception e) {
    log.error("consume failed", e);
    return RECONSUME_LATER;  // 触发重试
  }
}
```

### 4.2 重试机制保底

消费抛异常或返回 `RECONSUME_LATER` → 自动进入重试 Topic，按延迟级别重试 16 次，最终进 DLQ。

```
失败次数 → 延迟时间
   1     →  10s
   2     →  30s
   3     →  1min
   ...
   16    →  2h
   17    →  死信队列（%DLQ%ConsumerGroup）
```

详见 [消费者 - 消费失败重试](./消费者.md#五消费失败重试)。

### 4.3 死信队列处理

```java
// 单独消费 DLQ
@RocketMQMessageListener(
    topic = "%DLQ%my-consumer-group",
    consumerGroup = "dlq-handler-group"
)
public class DlqHandler implements RocketMQListener<MessageExt> {
  public void onMessage(MessageExt msg) {
    // 1. 落库（业务方人工查看）
    dlqLogDao.insert(...);
    // 2. 告警通知（钉钉/短信）
    alertService.notifyOps("DLQ message", msg);
  }
}
```

### 4.4 业务幂等（必须）

不论防丢做得多好，**重复消费是必然存在的**：
- 重试机制本身导致重复
- offset 异步提交（每 5s）→ 重启会重复
- 网络抖动 ACK 丢失 → 重复推送

→ 详见 [重复消费与幂等](./重复消费与幂等.md)。

## 五、端到端可靠性矩阵

| 防御层 | 投入 | 防御什么 |
| --- | --- | --- |
| **Sync 发送 + 重试** | 业务侧编码 | 网络抖动、Broker 临时不可用 |
| **本地消息表 + 定时重发** | 数据库一张表 | MQ 整体不可用 |
| **SYNC_MASTER（同步复制）** | 吞吐 -20% | Broker 单机崩溃 |
| **SYNC_FLUSH（同步刷盘）** | 吞吐 -50% | OS 崩溃、断电 |
| **Dledger / Raft** | 3 节点起步 | 单节点故障自动切换 |
| **多 Topic 分布在多 Broker Group** | 部署成本 | 单 Broker Group 整体故障 |
| **消费者业务逻辑完成才 ACK** | 业务侧编码 | 消费阶段消息丢失 |
| **业务幂等** | 业务侧编码 | 重复消费 |
| **死信队列监控** | 监控成本 | 消费 16 次后未处理消息可见 |
| **业务对账（终极兜底）** | 离线作业 | 上述所有方案的漏网之鱼 |

## 六、典型业务场景的可靠性方案

### 6.1 订单创建 → 库存扣减

```
方案：事务消息（half message）

[订单系统]                            [库存系统]
   │                                     │
   ├─ 1. 发送 half 消息                  │
   │                                     │
   ├─ 2. 本地事务：创建订单              │
   │                                     │
   ├─ 3. commit / rollback              │
   │                                     │
   │   broker：4. half → 真消息          │
   │   broker 回查兜底 ───────────────►  │
   │                                     │
   │                                     ├─ 5. 消费消息，扣库存
   │                                     ├─ 6. 业务幂等（订单 ID 唯一）
   │                                     └─ 7. 失败重试 / DLQ 报警
```

详见 [事务消息](./事务消息.md)。

### 6.2 通知类消息（短信/邮件）

```
方案：异步发送 + 失败回调入库 + 定时重发

[业务系统] ──► MQ ──► [通知系统]
   │
   └─ Async 发送
        ├─ onSuccess: 不做任何事
        └─ onException: 落库 PENDING 状态
        
   定时任务：扫描 PENDING 重发（带最大重试次数限制）
   
通知系统：业务幂等（同一通知 ID 只处理一次）
```

### 6.3 日志/埋点

```
方案：Oneway + 接受少量丢失

性能 >> 可靠性
单机 50w+ TPS，丢 0.1% 业务可接受
```

## 七、生产踩坑

### 7.1 Sync 发送配置成 Async 引发丢消息

**现象**：发布后业务方反馈大量订单消息丢失。

**根因**：开发误用 `producer.send(msg, callback)` 异步 API，回调里没处理 `onException`。

**修复**：
```java
// 改回 Sync
SendResult result = producer.send(msg);
if (result.getSendStatus() != SEND_OK) {
  throw new BusinessException("send failed");
}
```
代码 review 必查"重要场景禁用 Async"。

### 7.2 同步刷盘配置错位置

**现象**：申请同步刷盘但发现性能没下降，重启 Broker 验证发现仍丢消息。

**根因**：在 Slave 节点改了 flushDiskType=SYNC_FLUSH，Master 仍是 ASYNC_FLUSH——Slave 同步是没用的，关键是 Master。

**修复**：所有 Broker Master 配置一致。

### 7.3 异步消费假装成功

**现象**：消费回调里直接返回 SUCCESS，业务异步处理失败也不会重试。

**根因**：开发不理解"成功 = 业务完成"。

**修复**：业务必须同步在 Listener 里完成；如果一定要异步，用 LitePullConsumer 手动管理 offset。

### 7.4 MQ 整体宕机业务受影响

**现象**：MQ 集群全挂 30min，订单系统全部失败。

**根因**：业务直接同步 send，没本地兜底。

**修复**：
- 重要场景必须有**本地消息表**
- 业务下单 + 落 MQ 状态表在同一事务
- 异步重试 / 异步发送

### 7.5 死信队列堆积无人发现

**现象**：DLQ 堆了 5 万条，业务一无所知。

**修复**：监控所有 ConsumerGroup 的 DLQ 堆积量，> 阈值告警。

## 八、面试高频追问

**Q1：消息一定不丢能做到吗？**

理论上**不能**，因为防御链上任何一环都可能失效。所以工程上的目标是 "**99.999% 不丢 + 业务对账兜底**"——把概率压到极低，最后用业务对账（订单未到账等）发现极少数漏网的。

**Q2：Sync 发送收到 SEND_OK 但业务最终发现消息丢了，可能吗？**

可能。两种情况：
1. **响应回包丢失**：Broker 写入成功，但响应在网络上丢了 → Producer 重试 → 消息存了两份。这不是"丢"是"重"——靠幂等解决
2. **Broker 异步刷盘 + OS 崩溃**：Broker 把消息写入 PageCache 就返回 OK，OS 在刷盘前崩溃 → 数据丢失

只有同步刷盘 + 同步复制 + Dledger 才能完全消除第 2 种情况。

**Q3：异步发送怎么保证可靠？**

```
producer.send(msg, new SendCallback() {
  public void onSuccess(SendResult r) { /* 不需要做啥 */ }
  public void onException(Throwable e) {
    // ① 落库 PENDING
    // ② 加入业务重试队列
    // ③ 触发告警
  }
});
```
**onException 必须写**——很多事故就是因为这块为空导致丢消息。

**Q4：消费端为什么必须做幂等？**

因为重复消费是**必然**的（不是"可能"）：
- offset 异步提交 → 重启重复
- 失败重试 → 第一次部分成功 + 第二次完整 = 部分逻辑执行多次
- Rebalance → 老 Consumer 已拉但未提交 → 新 Consumer 重新拉
- 网络抖动 → ACK 丢失 → Broker 重投

不做幂等就是事故等着发生。

**Q5：本地消息表 vs 事务消息怎么选？**

| | 本地消息表 | RocketMQ 事务消息 |
| --- | --- | --- |
| 实现复杂度 | 高（要建表 + 定时任务） | 中（实现 TransactionListener） |
| 业务侵入性 | 高（每个业务独立做） | 低（封装在 Producer） |
| 可靠性 | 依赖业务方质量 | 依赖 Broker（更可靠） |
| 性能 | 业务表多一次 IO | 多一次 half 消息 |
| 适用 | 不用 RocketMQ 也行 | 强依赖 RocketMQ |

互联网中小项目用事务消息；大型业务通常本地消息表 + 事务消息双重保障。

**Q6：Master 宕机时 Producer 收到什么？**

- ASYNC_MASTER：Master 在写之后未复制到 Slave 时挂 → Producer 已经收到 SEND_OK，但消息其实丢了
- SYNC_MASTER：Master 在写之后未复制时挂 → 可能复制超时（FLUSH_SLAVE_TIMEOUT），Producer 选择重试 → 不丢
- 完全宕机：Producer 触发故障规避，下次发到其他 Broker → 不丢（只要有其他 Master）

**Q7：消息从写入 Broker 到 Consumer 拉到的延迟有多大？**

```
正常情况：
- ConsumeQueue 异步生成：< 1ms
- Consumer 长轮询拉取：< 5ms
- 端到端：5~10ms
```

异常情况下（CommitLog 写入压力大、PageCache 抖动）可能到几百 ms。监控 `dispatchBehindBytes`（CommitLog 与 ConsumeQueue 的差距）。

## 九、答题模板（60 秒话术）

> 消息可靠性是**端到端三段防御**：
>
> **生产端**用同步发送 + 默认 3 次重试 + 多 Master 部署。重要场景配本地消息表，业务下单和发送状态在同一事务，定时任务扫描重发兜底 MQ 整体不可用。
>
> **存储端**两个旋钮：刷盘和复制。互联网默认 ASYNC_FLUSH + ASYNC_MASTER，性价比最高但 OS 崩溃丢 ≤ 500ms 数据；订单/支付推荐 **ASYNC_FLUSH + SYNC_MASTER**——同步复制让 Slave 也有 PageCache 副本，OS 崩溃也不丢，吞吐只降 30%；金融级用 SYNC_FLUSH + SYNC_MASTER 或 Dledger Raft 自动切换。
>
> **消费端**最关键的是"消费成功 = 业务完成"——业务在 Listener 内同步处理，抛异常返回 RECONSUME_LATER 触发重试 Topic 16 次，第 17 次进 DLQ。配合**业务幂等**（重复消费是必然）和**死信队列监控告警**。
>
> 终极兜底：**业务对账**——离线作业核对订单表 vs MQ 消费记录，发现漏网之鱼。
