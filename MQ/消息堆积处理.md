# RocketMQ 消息堆积处理

> "线上 MQ 堆积了 500 万消息，怎么处理？" —— 互联网大厂面试必考的故障应对题。
> 本篇要解决：
> ① 堆积的本质是什么？怎么快速判断是生产快了还是消费慢了？
> ② 5 分钟内的临时方案、当天的修复方案、长期的预防方案分别是什么？
> ③ 经典的"扩 Topic Queue + 临时 Consumer 转发"方案到底怎么做？
> ④ 哪些堆积是正常的（如延迟消息），不要瞎处理。

---

## 一、堆积的本质

### 1.1 一句话定义

```
堆积 = 生产速度 > 消费速度 持续一段时间
```

### 1.2 三种堆积模式

| 模式 | 现象 | 原因 |
| --- | --- | --- |
| **突发型** | 短时间堆积百万，几小时内消化 | 流量峰值（双 11 / 大促） |
| **持续型** | 缓慢增长但不消化 | 消费者代码 bug / 消费速度跟不上业务增长 |
| **永久卡死** | 部分 Queue 完全不消费 | 顺序消费卡死 / Consumer 异常 |

不同模式应对方式不同——先**判断类型**再处方。

## 二、监控与诊断

### 2.1 核心指标

```
brokerInfo:
- diffTotal       消费者落后总条数（最关键指标）
- maxDiff         最大落后 Queue 的差值
- consumeLag      消费延迟时间（最早未消费消息的时间戳差）

producerInfo:
- putTps          生产 TPS
- consumeTps      消费 TPS
- 差值 = 持续堆积速度
```

### 2.2 命令排查

```bash
# 查看消费者堆积情况
mqadmin consumerProgress -n localhost:9876 -g your_consumer_group

# 输出
#Topic              #BrokerName    #QueueId   #Broker_Offset  #Consumer_Offset   #Diff
order_topic         broker-a       0          1000000         900000             100000   ← 这个 Queue 堆积 10 万
order_topic         broker-a       1          1000000         999999             1
...
```

### 2.3 判断生产快还是消费慢

```
看 putTps 和 consumeTps：

case 1: putTps 突增（10000 → 50000）+ consumeTps 不变（10000）
        → 生产端突增（流量峰值）
        
case 2: putTps 不变 + consumeTps 骤降（10000 → 1000）
        → 消费端故障（代码异常 / 下游 DB 慢 / Consumer 实例挂）
        
case 3: putTps 平稳上涨 + consumeTps 跟不上
        → 业务增长 / 容量规划问题
```

### 2.4 看哪些 Queue 堆了

```
- 全部 Queue 都堆 → 整体消费能力不足，扩 Consumer
- 部分 Queue 堆 → 该 Queue 对应的 Consumer 实例异常
- 单个 Queue 永远卡 → 顺序消费卡死，特定消息处理失败
```

## 三、应对策略：分时段方案

### 3.1 5 分钟内（止血）

**目标**：快速降低堆积速度，避免雪崩。

```
1. 快速扩 Consumer 实例（K8s 一键 scale）
   - 但要保证 Consumer 实例数 ≤ Queue 数（否则新加的没用）
   
2. 调大 Consumer 线程数
   consumer.setConsumeThreadMax(50);  // 默认 20
   
3. 限流上游（如果是 Producer 突增）
   - 网关层限流
   - 临时拒绝低优先级流量
```

### 3.2 1 小时内（消化）

**目标**：处理已堆积的消息，恢复正常消费速度。

**方案 A：扩 Queue + 临时 Consumer 转发**（经典方案）

适用：堆积百万级，单 Topic Queue 数严重不足。

```
[现状]
  Topic-A: 4 个 Queue
  Consumer Group: 4 实例
  堆积 500 万

[操作步骤]
1. 扩容 Topic Queue
   mqadmin updateTopic -t Topic-A -r 32 -w 32
   → Queue 从 4 个变成 32 个

2. 临时关闭原 Consumer Group（避免争抢）

3. 启动临时转发 Consumer：
   - 8 个实例（每个负责 4 个新 Queue）
   - 不做业务，只把消息转发到一个新 Topic（Topic-A-Backup）
   - 新 Topic 也建 32 个 Queue

4. 启动消化 Consumer：
   - 16~32 个实例消费 Topic-A-Backup
   - 真正执行业务逻辑

5. 待堆积消化完，关闭临时方案，恢复原架构
```

**方案 B：直接扩 Consumer 实例**

适用：Topic Queue 数本来就够（如 32 个），只是 Consumer 实例不够。

```
原 Consumer Group: 4 实例 / 32 Queue → 每实例 8 Queue 压力大
扩容到: 32 实例 / 32 Queue → 每实例 1 Queue 完美

K8s scale: kubectl scale deployment consumer-app --replicas=32
```

**方案 C：消息丢弃（极端场景）**

适用：业务允许丢失（日志、低优先级通知）。

```
1. 备份：把堆积消息消费到一个备份 Topic 或 OSS
2. 重置 offset 到最新：
   mqadmin resetOffsetByTime -t Topic-A -g consumer_group -s now
3. 业务恢复正常消费
4. 离线分析备份的消息，决定是否需要补偿
```

### 3.3 长期方案（预防）

```
1. 容量规划：
   - Topic Queue 数 = 平时 Consumer 实例数 × 2~3 倍（留扩容空间）
   - 默认 Queue 数 4 个太少，业务 Topic 至少 16 个
   
2. 监控告警：
   - 堆积 > 10000 → 普通告警
   - 堆积 > 100000 → 严重告警 P1
   - consumeLag > 5min → P1
   - 单 Queue 堆积无变化 30min → P0（可能卡死）
   
3. 消费者预案：
   - 提前压测最大消费 TPS
   - 准备弹性扩容预案
   - DLQ 监控覆盖
   
4. 流控：
   - 业务限流（网关层）
   - Producer 限流（避免 MQ 被打爆）
   - 消费侧反向施压机制
```

## 四、特殊场景处理

### 4.1 顺序消费卡死

**现象**：单个 Queue 堆积上涨且不消化。

**排查**：
```bash
# 查看卡住的消息
mqadmin queryMsgByOffset -t topic -b broker-a -i 0 -o <stuck_offset>
```

**修复**：
1. 看消息内容，找到失败原因（DB 死锁 / 业务异常）
2. 修复业务代码 / 临时跳过该消息
3. **不要直接 reset offset**——会让该消息永远丢失

详见 [顺序消息](./顺序消息.md)。

### 4.2 重试队列堆积

**现象**：`%RETRY%consumer_group` Topic 堆积。

**根因**：消费失败率高 → 大量消息在重试队列等待延迟级别后重投。

**排查**：
- 看 Consumer 错误日志，找到主要异常类型
- 修复业务代码后，问题会逐渐自愈（重试到期消化）

### 4.3 死信队列堆积

**现象**：`%DLQ%consumer_group` Topic 堆积。

**根因**：消费失败超过 16 次的消息进入 DLQ。

**处理**：
1. **业务方必须订阅 DLQ Topic** 单独处理
2. 监控 DLQ 堆积量，超阈值告警
3. 定期 review DLQ 消息，找出系统性问题

```java
@RocketMQMessageListener(
    topic = "%DLQ%order_consumer_group",
    consumerGroup = "dlq_handler"
)
public class DlqHandler {
    public void onMessage(MessageExt msg) {
        // 1. 落库（人工分析）
        dlqLogDao.insert(msg);
        // 2. 告警（钉钉/短信）
        alertService.notify("DLQ message: " + msg.getMsgId());
    }
}
```

### 4.4 延迟消息"堆积"

**现象**：SCHEDULE_TOPIC_XXXX 看到大量消息。

**判断**：这是**正常现象**——延迟消息就是要"暂存"在这里直到到期。不要瞎处理。

**真有问题的特征**：到期了还没投递，监控应该看 `consumeLag` 而不是延迟 Queue 的总数。

### 4.5 广播消费"堆积"

**现象**：广播消费的 Consumer 重启后看到大量"堆积"。

**根因**：广播消费 offset 存本地文件，删本地或换机器导致从 `CONSUME_FROM_FIRST_OFFSET` 开始。

**修复**：
- 启动时显式指定 `CONSUME_FROM_LAST_OFFSET`
- 或忽略这次"堆积"——业务上本来就不重要

## 五、堆积治理的反模式

### 5.1 ❌ 直接 resetOffset 跳过堆积消息

```bash
mqadmin resetOffsetByTime -t topic -g group -s now  # 跳到最新
```

**后果**：堆积的消息**永久丢失**。除非业务允许（日志类），否则严禁。

### 5.2 ❌ 关掉 Consumer 等堆积"自愈"

**问题**：Broker 默认保留 72h 消息，超过会被删除——堆积越久丢失越多。

### 5.3 ❌ 加 Consumer 实例但 Queue 数不够

```
原 Topic 4 个 Queue，加到 32 个 Consumer 实例
→ 28 个实例完全空闲（一个 Queue 只能被一个 Consumer 消费）
```

**先扩 Queue 再扩 Consumer**——顺序不能反。

### 5.4 ❌ 在堆积期间频繁滚动重启 Consumer

每次重启触发 Rebalance，Rebalance 期间消费暂停 + 重复消费——加剧堆积。

**应该**：等堆积稳定后再重启。

## 六、生产踩坑

### 6.1 大促前没扩 Queue

**现象**：双 11 0 点流量到，Producer 写入正常，但 Consumer 跟不上 → 堆积秒级 100w+。

**根因**：Topic Queue 4 个，Consumer 实例 4 个——已是天花板，加 Consumer 也没用。

**修复**（事中）：
- 紧急扩 Queue 到 32 个
- 启动 32 个临时 Consumer
- 1 小时内消化完毕

**修复**（事后）：
- 大促前压测、扩 Queue 数
- 容量规划留 2~3 倍冗余

### 6.2 下游 DB 抖动导致雪崩

**现象**：DB 某主库抖动 30s，Consumer 全部抛 SQLException 走重试 → 重试 Topic 瞬间堆积百万。

**根因**：消费者没限流，所有消息都往 DB 打。

**修复**：
- Consumer 接入熔断器（Sentinel / Hystrix）
- DB 异常时短暂返回 RECONSUME_LATER 让消息延迟重试
- 不要立即重试，给下游恢复时间

### 6.3 慢消费者拖累全 Queue

**现象**：单个消息处理时间 30s+（默认 30s 超时），Queue 内其他消息全部等待。

**根因**：消费 Listener 里有 RPC 调用 + 没设超时。

**修复**：
- 业务调用必须设超时（通常 < 1s）
- 同步阻塞的 IO 操作改异步
- 拆分长任务为多步

### 6.4 临时方案做完没清理

**现象**：堆积消化完了，临时 Consumer / 临时 Topic 还在跑，每月多花几千。

**修复**：建立"临时资源清单 + Owner"制度，事故复盘必查。

## 七、面试高频追问

**Q1：堆积 500 万消息怎么处理？**

```
分时段：
- 5 分钟内：扩 Consumer 实例 + 调大线程数 + 限流上游
- 1 小时内：扩 Queue（如 4→32）+ 临时 Consumer 转发到新 Topic + 多实例消化
- 长期：容量规划、监控告警、DLQ 监控

判断步骤：
1. 看监控：putTps vs consumeTps 差距
2. 看 Queue 分布：全部堆还是局部堆？
3. 看下游：DB / 缓存 / 第三方接口是否慢？
4. 看消费日志：是否有大量异常？
```

**Q2：为什么扩 Consumer 必须先扩 Queue？**

因为**一个 Queue 同组只能被一个 Consumer 消费**。Topic 4 个 Queue，加再多 Consumer 也只有 4 个能干活，其他空闲。

**Q3：Topic 扩 Queue 会有什么影响？**

- 顺序消息会乱序（业务键 hash 取模结果变了）
- 不影响普通消息
- Producer 拉到新路由后会写入新 Queue
- 消费侧重新分配（轻微抖动）

所以**业务低峰期扩**，避开顺序消息场景或停 Producer 后扩。

**Q4：Broker 默认保留 72h，堆积超过 72h 怎么办？**

老消息会被**自动删除**，丢消息。所以：
- 监控堆积时长（不光看数量）
- 接近 72h 之前必须处理（要么消化、要么备份）
- 临时调大 `fileReservedTime` 争取时间

**Q5：堆积期间能滚动发布 Consumer 吗？**

**不能**。Rebalance 会触发：
- 老 Consumer 已拉未提交的消息被新 Consumer 重新拉 → 重复
- Rebalance 期间消费暂停 → 堆积加剧
- 应该堆积稳定后再发布

紧急修复 bug 必须重启时：滚动间隔 ≥ 30s，避免同时大量 Rebalance。

**Q6：怎么避免堆积？**

```
1. 容量规划：Queue 数 = Consumer 实例数 × 2~3
2. 监控告警：堆积条数、堆积时长、单 Queue 卡死
3. 消费降级：DB 异常时熔断，避免雪崩
4. 业务限流：网关 / Producer 端限流
5. 弹性扩容：K8s + HPA 基于堆积量自动扩 Consumer
```

**Q7：怎么判断堆积是不是正常的？**

```
正常：
- 延迟消息（SCHEDULE_TOPIC_XXXX）
- 重试队列正在消化中（%RETRY%）
- 业务高峰短期堆积（10 分钟内消化）
- 死信队列（业务方主动接收）

不正常：
- consumeLag > 1 分钟且持续上涨
- 单 Queue 堆积长期不变
- 全 Queue 一起堆
```

**Q8：消息堆积会影响 Producer 吗？**

通常不会——CommitLog 顺序写，消息只要能写入 Broker 就成功。

但极端情况：
- 磁盘满了 → Broker 拒写（diskMaxUsedSpaceRatio 超 88%）
- PageCache 抖动 → 写入延迟增加

所以堆积也是磁盘容量管理的问题。

## 八、答题模板（60 秒话术）

> 消息堆积是大厂故障应对必考题。**本质是生产速度 > 消费速度**，处理思路分**判断 + 止血 + 消化 + 预防**四步。
>
> **判断**：看监控 putTps 和 consumeTps，是上游突增还是下游变慢；看 Queue 分布，是全部堆还是局部堆；看 Consumer 日志找异常。
>
> **5 分钟内止血**：扩 Consumer 实例 + 调大消费线程 + 限流上游。
>
> **1 小时内消化**：经典方案是"**扩 Queue + 临时 Consumer 转发**"——把 Topic Queue 从 4 个扩到 32 个，启动 8 个临时 Consumer 把消息原样转发到新 Topic，再用 32 个真正的 Consumer 消化新 Topic。这是因为**一个 Queue 同组只能被一个 Consumer 消费**，扩 Consumer 必须先扩 Queue。
>
> **长期预防**：容量规划留 2~3 倍冗余、监控堆积条数 + 时长 + DLQ、消费侧加熔断防雪崩、业务侧限流。
>
> **反模式不要犯**：不要 reset offset 跳过堆积（丢消息）、不要在堆积期间频繁重启（加剧 Rebalance）、不要忘了 Broker 默认 72h 保留期。
