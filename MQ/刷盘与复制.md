# RocketMQ 刷盘与复制

> 这是 RocketMQ "可靠性 vs 性能"权衡最直接的两个旋钮。
> 本篇要解决：
> ① 异步刷盘 + 异步复制为什么是默认推荐？什么场景必须升级？
> ② SYNC_MASTER 和 Dledger 都是同步复制，区别在哪？
> ③ 主从异步复制下 Master 挂了为什么消息可能丢，但消费不影响？
> ④ 为什么 RocketMQ 4.x 主从挂了不会自动切换？

---

## 一、两个独立的旋钮

```
┌────────────────────────────────────────────────────────┐
│              单条消息写入的时间线                       │
└────────────────────────────────────────────────────────┘

Producer ──► Broker-Master ─┬─► PageCache (mmap)
                             │
                  ┌──────────┴──────────┐
                  ▼                     ▼
           [1] 刷盘            [2] 复制到 Slave
           SYNC / ASYNC         SYNC / ASYNC

         决定单机持久化           决定主从冗余
```

| 旋钮 | 取值 | 影响 |
| --- | --- | --- |
| `flushDiskType` | `ASYNC_FLUSH` / `SYNC_FLUSH` | **单 Broker 内**消息是否落盘才返回 |
| `brokerRole` | `ASYNC_MASTER` / `SYNC_MASTER` / `SLAVE` | **主从之间**是否同步复制才返回 |

**两者正交**——可以任意组合：

| 组合 | 适用场景 | 单机 TPS |
| --- | --- | --- |
| ASYNC_FLUSH + ASYNC_MASTER | **互联网默认** | 10w |
| ASYNC_FLUSH + SYNC_MASTER | 高可靠 + 高吞吐 | 7~8w |
| SYNC_FLUSH + ASYNC_MASTER | 不常见 | 5~6w |
| SYNC_FLUSH + SYNC_MASTER | **金融级** | 3~5w |
| Dledger（Raft） | 自动主备切换 | 5~7w |

## 二、刷盘机制（FlushDiskType）

### 2.1 异步刷盘（ASYNC_FLUSH，默认）

```
Producer ──► Broker
                │
                │ writeToPageCache (mmap)
                ▼
          [立即返回 SendResult.OK]
                ▲
                │
              FlushRealTimeService（后台线程）
                │ 每 500ms 或累计 ≥ 4 page (16KB)
                ▼
              fsync 到磁盘
```

**特点**：
- 写完 PageCache 就返回成功 → ~1ms 延迟
- 后台线程 `FlushRealTimeService` 默认每 500ms 批量刷盘
- **Broker 进程挂了不丢**（PageCache 由 OS 管理）
- **OS 崩溃/断电会丢**（PageCache 里未刷盘的数据）

**核心源码**（伪代码）：
```java
class FlushRealTimeService {
  void run() {
    while (running) {
      waitForRunning(500);  // 默认 500ms
      // 或 dirtyPages >= 4 时立即刷
      mappedFileQueue.flush(flushCommitLogLeastPages);
    }
  }
}
```

### 2.2 同步刷盘（SYNC_FLUSH）

```
Producer ──► Broker
                │
                │ writeToPageCache
                │
                │ 提交 GroupCommitRequest
                │ countDownLatch.await(timeout)
                ▼
        GroupCommitService 批量 fsync ──► 磁盘
                │
                │ countDown()
                ▼
        [返回 SendResult.OK]
```

**特点**：
- 等 fsync 完成才返回 → ~5~10ms 延迟
- **批量提交**：1ms 内的多个写请求合并一次 fsync（GroupCommit），平摊系统调用开销
- **Broker 单机层面不丢消息**（除非磁盘物理损坏）

**为什么是 GroupCommit 而不是每条 fsync？**

```
不批量：1000 条 × 5ms fsync = 5000ms
批量（每 ms 一组）：1000 条 / 100 条每组 × 5ms = 50ms
```

把 N 条请求的 fsync 合并成 1 次，吞吐提升 ~100 倍。代价是单条延迟略增（要等组内其他请求）。

### 2.3 关键参数

```properties
# 异步刷盘
flushIntervalCommitLog=500            # 刷盘线程间隔 ms
flushCommitLogLeastPages=4            # 累计页数才触发（4 页 = 16KB）
flushCommitLogThoroughInterval=10000  # 强制刷盘间隔 ms

# 同步刷盘
syncFlushTimeout=5000                 # 单次 fsync 超时
```

## 三、复制机制（BrokerRole）

### 3.1 异步复制（ASYNC_MASTER，默认）

```
Producer ──► Master (写 PageCache)
                │
                │ 立即返回成功
                ▼
              Producer 收到 OK
                
              （独立线程）
              HAService ──► Slave 拉取增量 CommitLog
```

**特点**：
- Master 写完就返回 → 不等 Slave
- Slave 通过 HAClient 主动从 Master 拉取增量数据（类似 Kafka 的 follower fetch）
- **Master 挂了未同步的部分会丢**（恢复后 Master 重新启动时会自动追上 Slave 的进度，但客户端已经认为消息成功）

### 3.2 同步复制（SYNC_MASTER）

```
Producer ──► Master (写 PageCache)
                │
                │ 等待 ≥ 1 个 Slave 同步成功
                ▼
              返回 SendResult.OK
```

**特点**：
- 至少 1 个 Slave 同步完成才返回 → 多 ~3~5ms 延迟
- 单个 Slave 同步阻塞 Master 写入（多 Slave 时只等最快的一个）
- Master + Slave 任一挂了都不丢（要 2 个同时坏才丢）

**坑**：
- 4.x SYNC_MASTER 下 Slave 挂了会**阻塞 Master 写入**（要等同步超时），导致整体不可用
- 配合 `haSlaveFallbehindMax` 监控 Slave 滞后字节数

### 3.3 Slave 不能写、不能升 Master

**重点**：传统 RocketMQ 4.x（非 Dledger）下：
- Slave **只能读，不能写**（Producer 只能往 Master 发）
- Master 挂了 **不会自动选举 Slave**——需要运维介入
- 期间 Producer 该 Topic 的发送会失败（其他 Master 的 Topic 不影响）
- Consumer 仍可从 Slave 拉消息（保证消费不中断）

**为什么不自动切换？**

> 因为 RocketMQ 4.x 没有共识协议——多个 Slave 时无法保证选出"数据最新"的那个。错选会导致数据回退。如果业务允许"短暂不可写"，就接受运维介入；如果业务要求自动切换，必须用 Dledger（Raft 共识）。

## 四、Dledger 模式（4.5+ 自动主备切换）

### 4.1 拓扑

```
Broker-Group 必须 ≥ 3 节点（奇数）

      [Leader] ←── Raft 心跳 ──► [Follower-1]
          ▲                          │
          │                          │
          └──── Raft 心跳 ──► [Follower-2]
```

### 4.2 写入流程

```
Producer ──► Leader
                │
                │ AppendEntries 复制到 N/2+1 节点
                │（3 节点至少 2 个 ACK）
                ▼
              返回成功
```

**关键差异 vs SYNC_MASTER**：
- SYNC_MASTER：等"≥ 1 个" Slave，配置上一般 1 主 1 从，**单个 Slave 挂了主就阻塞**
- Dledger：等"多数派"，3 节点容忍 1 个挂、5 节点容忍 2 个挂，**少数派挂了不影响**

### 4.3 故障切换

```
Leader 挂 ──► 剩余节点选举 (~10s) ──► 新 Leader ──► 客户端自动重连
```

**代价**：
- 选举期间（一般 < 10s）该 Broker Group 不可写
- 至少 3 节点 → 资源成本增加 50%
- 复制延迟比 ASYNC_MASTER 高 ~30%（要等多数派 ACK）

### 4.4 配置示例

```properties
# 启用 Dledger
enableDLegerCommitLog=true
dLegerGroup=broker-group-1
dLegerPeers=n0-192.168.1.1:40911;n1-192.168.1.2:40911;n2-192.168.1.3:40911
dLegerSelfId=n0
storePathRootDir=/data/rocketmq/dlegerStore
```

## 五、生产推荐配置

### 5.1 互联网典型业务（默认）

```properties
# Master
brokerRole=ASYNC_MASTER
flushDiskType=ASYNC_FLUSH

# Slave
brokerRole=SLAVE
flushDiskType=ASYNC_FLUSH
```

**承诺**：99.99% 不丢；Master 进程挂不丢；OS 崩溃丢 < 1s 数据。

### 5.2 高可靠业务（订单/支付）

```properties
# Master
brokerRole=SYNC_MASTER       # 同步复制
flushDiskType=ASYNC_FLUSH    # 但仍异步刷盘

# Slave
brokerRole=SLAVE
flushDiskType=ASYNC_FLUSH
```

**理由**：
- 同步复制保证 Master 单机宕机不丢（数据已在 Slave）
- 异步刷盘保证性能（PageCache 在 OS 层不会因进程挂而丢）
- **OS 同时崩溃 + Slave 同时崩溃 才会丢**——概率极低

### 5.3 金融级（钱相关）

```properties
brokerRole=SYNC_MASTER
flushDiskType=SYNC_FLUSH
```

**或者用 Dledger**：

```properties
enableDLegerCommitLog=true
flushDiskType=SYNC_FLUSH
```

## 六、对比表

### 6.1 单机刷盘对比

| 维度 | ASYNC_FLUSH | SYNC_FLUSH |
| --- | --- | --- |
| 写入延迟 | ~1ms | ~5~10ms |
| 单机 TPS | 10w+ | 5~6w |
| Broker 进程挂 | ✅ 不丢 | ✅ 不丢 |
| OS 崩溃 | ❌ 丢 ≤ 500ms 数据 | ✅ 不丢 |
| 磁盘损坏 | ❌ 全丢 | ❌ 全丢 |

### 6.2 主从复制对比

| 维度 | ASYNC_MASTER | SYNC_MASTER | Dledger |
| --- | --- | --- | --- |
| 写延迟增加 | 0 | +3~5ms | +5~10ms |
| Master 单点宕机 | ❌ 可能丢 | ✅ 不丢 | ✅ 不丢 |
| Master 挂可用性 | ❌ 不可写 | ❌ 不可写 | ✅ 自动切（10s 内）|
| 资源成本 | 1 主 1 从 | 1 主 1 从 | 3 节点起步 |

## 七、生产踩坑

### 7.1 同步复制 Slave 挂导致写入阻塞

**现象**：SYNC_MASTER 模式下，Slave 网络抖动 30s，Producer 全部超时。

**根因**：4.x 老版本 SYNC_MASTER 没有 Slave 故障降级，Slave 挂就阻塞 Master。

**修复**：升级到 4.5+，或改用 Dledger，或用 ASYNC_MASTER + 业务重试兜底。

### 7.2 异步刷盘 + 强制重启导致少量消息丢失

**现象**：运维粗暴 `kill -9` 之后查日志发现少了几百条消息。

**根因**：`kill -9` 让 OS 强制终止进程，但 PageCache 在内核态不会丢；真正丢消息是因为后续机器重启导致 OS 重启 = PageCache 清空。

**修复**：
- 关机操作必须用 `mqshutdown broker` 优雅停机（触发 final flush）
- 或开同步刷盘
- 监控 `lastFlushTimestamp`，发现长时间未刷盘报警

### 7.3 主从异步复制下 Master 宕机消息回退

**现象**：异步复制下，Master 故障后被踢，Master 恢复后重新接入，发现消息时间戳出现倒退。

**根因**：Master 写入了一批数据没来得及同步到 Slave 就挂了；这批数据在 Master 重启后仍在它的 CommitLog 里，但 Slave 上没有；如果客户端先消费了 Slave 的数据，再切回 Master，就会看到"过去的"消息。

**修复**：
- 业务侧用幂等 + 时间戳校验
- 高可靠场景升级到 SYNC_MASTER 或 Dledger

### 7.4 Dledger 选举期间消息发送全部失败

**现象**：滚动重启 Dledger 集群时，10s 内大量发送失败。

**根因**：Leader 节点重启触发重新选举，期间该 Broker Group 不可写。

**修复**：
- 同 Topic 多 Broker Group → 一个 Group 不可写还有别的 Group 接管
- Producer 端开启 `retryAnotherBrokerWhenNotStoreOK=true`，单次失败自动换 Broker
- 滚动重启间隔 ≥ 30s，避免同时多节点离线

## 八、面试高频追问

**Q1：为什么 RocketMQ 默认是异步刷盘 + 异步复制？**

因为业务场景**对吞吐的需求 >> 对零丢失的需求**：异步刷盘 + 异步复制下单机 10w+ TPS，几乎不会丢消息（Broker 进程挂不丢，OS 崩溃才丢 < 500ms 的数据）。同步配置吞吐降到 3~5w，对大多数业务"过度设计"。

**Q2：异步复制下 Master 挂了，消息一定丢吗？**

不一定。看 Master 是不是已经把数据同步给了 Slave。
- 如果挂的瞬间最新写入还没复制到 Slave：丢
- 如果已经复制了：不丢（Slave 可继续提供消费）

可观测指标：`haSlaveFallbehindMax`（Slave 落后字节数），生产正常应 < 1MB；> 100MB 就是异常。

**Q3：SYNC_MASTER + ASYNC_FLUSH 这个组合有意义吗？**

**有，而且常用**。逻辑是：
- 数据"在 Master 内存 + Slave 内存"两份了，单台挂掉另一台 PageCache 还在
- 比 SYNC_FLUSH 快 5 倍，比 ASYNC_MASTER 多一份冗余
- **能容忍 OS 崩溃**（Slave 仍有 PageCache 数据；Slave OS 也崩溃才会丢）

这是高可靠业务的"性价比之选"。

**Q4：为什么不能让 Slave 自动升级为 Master？**

因为非 Dledger 模式下没有共识协议，无法保证：
1. 多个 Slave 中哪个数据最新？
2. 网络分区时不会同时选出多个 Master？

错误的自动切换可能导致数据丢失或脑裂。所以 RocketMQ 4.x 选择"手动切"，要自动切必须上 Dledger。

**Q5：Dledger 比 SYNC_MASTER 多什么？**

| | SYNC_MASTER | Dledger |
| --- | --- | --- |
| 写入"等几个节点"？ | 等 1 个 Slave | 等多数派（N/2+1） |
| Master 挂了 | 手动切 | 自动选主 |
| 节点数 | 1 主 1+ 从 | 至少 3 个 |
| 选主期间 | 不影响（无选主） | 短暂不可写 |

**Q6：fsync 真的能让数据安全落盘吗？**

绝大多数 SSD 支持 `fsync` 落盘，但有些消费级 SSD 用 **Write Cache**（DRAM）回应 fsync 但其实没真正写到 NAND。**生产必须用企业级 SSD（带掉电保护电容）**——掉电时电容供电完成 cache 刷写。

**Q7：CommitLog 同步刷盘了，但 ConsumeQueue 还没生成怎么办？**

正常情况下不会有问题——CommitLog 刷盘成功就返回 Producer。Consumer 会持续轮询 ConsumeQueue，**短暂的延迟（< 1ms）等 ReputMessageService 异步生成完即可消费**。Broker 异常重启时：
- 如果 CommitLog 完整，ConsumeQueue 损坏 → 自动从 checkpoint 重建
- 重建期间 Consumer 拉取可能为空，但不会丢消息（CommitLog 是 single source of truth）

## 九、答题模板（60 秒话术）

> RocketMQ 的可靠性靠**两个独立旋钮**：刷盘策略和主从复制策略。
>
> **刷盘**有同步异步两档：异步刷盘写完 PageCache 就返回，~1ms 延迟，进程挂不丢、OS 崩溃丢 ≤ 500ms 数据；同步刷盘等 fsync 完成才返回，~5ms 延迟，单机层面不丢——但批量提交（GroupCommit）让吞吐没塌，1ms 内的写请求合并一次 fsync。
>
> **复制**也是同步异步两档：异步复制 Master 写完即返回，性能最高但 Master 挂可能丢未复制的数据；同步复制至少 1 个 Slave 同步完才返回，单机宕机不丢；自动主备切换必须用 **Dledger**，基于 Raft，至少 3 节点容忍 1 个挂。
>
> 生产推荐组合：互联网业务用 ASYNC + ASYNC（默认）；订单支付用 **SYNC_MASTER + ASYNC_FLUSH**（性价比之选——两台机器内存做冗余）；金融级用 SYNC + SYNC 或 Dledger。
