# RocketMQ 延迟消息

> "30 分钟未支付订单自动关闭" —— 这种典型场景背后的实现，**4.x 和 5.x 完全不一样**。
> 本篇要解决：
> ① 4.x 的 18 个固定延迟级别为什么是这套？怎么实现的？
> ② 5.x 任意时间延迟的时间轮算法，槽位 / TimerLog 怎么配合？
> ③ 延迟消息超过 7 天怎么处理？
> ④ Broker 重启延迟消息会丢吗？怎么恢复？
> ⑤ 业务侧的"延时队列"还有哪些方案？

---

## 一、为什么需要延迟消息？

### 1.1 典型场景

| 场景 | 延迟时间 |
| --- | --- |
| 订单 30 分钟未支付自动关闭 | 30 分钟 |
| 用户注册后 7 天未活跃发送召回邮件 | 7 天 |
| 优惠券领取 24 小时未使用提醒 | 24 小时 |
| 限时活动到期清理 | 任意时间 |
| 重试延迟 / 失败补偿 | 几秒到几分钟 |

### 1.2 不用 MQ 怎么做？

```
方案 A：定时扫表
  - 每分钟扫 order 表 WHERE status = 'PENDING' AND created_at < NOW() - 30min
  - 问题：① 扫描压力大 ② 不够实时 ③ 多个业务都扫，DB 受不了

方案 B：Redis ZSet（score = 触发时间戳）
  - 定时拉 ZRANGEBYSCORE 0, NOW
  - 问题：① 单点 ② 无持久化保障 ③ 不能直接触发业务逻辑

方案 C：MQ 延迟消息
  - 业务下单时发一条"30 分钟后投递"的消息
  - 时间到了 Consumer 自动收到
  - 优势：异步解耦、可靠、可水平扩展
```

## 二、RocketMQ 4.x：18 个固定延迟级别

### 2.1 配置

```properties
# Broker 端
messageDelayLevel=1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h
```

**注意**：只能选这 18 个固定值。要 1.5 小时？没有，最多 1h 或 2h。

### 2.2 用法

```java
Message msg = new Message("topic", "tag", body);
msg.setDelayTimeLevel(3);  // 第 3 级 = 10s
producer.send(msg);
```

`setDelayTimeLevel(3)` 表示按上面配置的第 3 个延迟（10s）。

### 2.3 实现原理

```
① 普通消息发送，Broker 收到后检查 delayTimeLevel
② 如果 > 0：
   - 备份原 topic 到消息属性
   - 改 topic 为 SCHEDULE_TOPIC_XXXX（系统内部 topic）
   - queueId = delayLevel - 1（每个级别一个 Queue）
   - 写入 CommitLog
③ Broker 后台线程 ScheduleMessageService：
   - 每秒扫描每个延迟级别的 Queue
   - 检查队首消息的"投递时间"是否已到
   - 到了就把消息**重新投递**到原 topic
   - Consumer 才能看到
```

### 2.4 为什么用"级别"而不是任意时间？

```
任意时间需要：
  - 按时间排序（消息插入时找到正确位置）
  - 每次取出都要扫描整个堆
  - 性能差
  
固定级别 + 每级一个 Queue：
  - 同 Queue 内消息**天然按时间有序**（因为同级别延迟一样长，按发送顺序就是按到期时间顺序）
  - 检查队首即可，O(1)
  - 牺牲灵活性换性能
```

### 2.5 SCHEDULE_TOPIC_XXXX 的结构

```
SCHEDULE_TOPIC_XXXX
├─ Queue-0  ← 延迟级别 1 (1s) 的消息
├─ Queue-1  ← 延迟级别 2 (5s) 的消息
├─ Queue-2  ← 延迟级别 3 (10s) 的消息
├─ ...
└─ Queue-17 ← 延迟级别 18 (2h) 的消息
```

每个 Queue 内消息按发送时间有序 → 按到期时间也有序。

### 2.6 4.x 的局限

| 局限 | 影响 |
| --- | --- |
| 只能用预定义的 18 个级别 | "30 分钟"可以，"35 分钟"不行 |
| 不支持任意时间 | 需要业务侧二次延迟（multiple-step） |
| 改 messageDelayLevel 要重启 Broker | 不灵活 |
| 单 Queue 处理压力 | 高峰期某级别 Queue 大量消息时延迟生效 |

## 三、RocketMQ 5.x：任意时间延迟（时间轮）

### 3.1 用法

```java
Message msg = new Message("topic", "tag", body);
// 设置在指定时间投递（毫秒级时间戳）
msg.setDeliverTimeMs(System.currentTimeMillis() + 3600 * 1000);  // 1 小时后
producer.send(msg);
```

不再受 18 个级别限制，**任意未来时间**都可以（默认上限 7 天）。

### 3.2 时间轮算法

```
时间轮 = 一个循环数组，每个槽位（slot）代表一个时间精度（默认 1 秒）

时间精度 1s × 7 × 24 × 3600 = 7 天的槽位（604800 个）

  ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
  │ 0│ 1│ 2│ 3│..│..│..│..│..│N │
  └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘
                           ▲
                           │ 当前时间
                           
每个槽位 = 该时刻要投递的消息列表（指向 TimerLog）
```

**循环复用**：N 秒后从槽 0 重新开始（因为已过去的槽位用完了），无需新建文件。

### 3.3 三个核心文件

```
TimerWheel：时间轮（循环数组）
  每个槽位存：first_pos / last_pos （指向 TimerLog 的物理偏移）
  
TimerLog：定时消息索引文件
  Append-only Log，结构类似 CommitLog
  每条记录：消息在 CommitLog 中的物理偏移 + 前一条索引的位置
  形成链表，与 TimerWheel 槽位组成"该时刻所有定时消息的列表"
  
Checkpoint：恢复点
  记录 TimerLog 中已被 TimerWheel 处理的位置
  Broker 重启时从此处恢复
```

```
TimerWheel 槽位 ──first_pos──► TimerLog 链表头
                                   │
                                   ├─► msg-A（CommitLog offset = X）── prev ─►
                                   │
                                   ├─► msg-B（CommitLog offset = Y）── prev ─►
                                   │
                                   └─► msg-C（CommitLog offset = Z）── prev ─► null
```

### 3.4 入轮流程

```
[Producer]
   │ Producer 发送带 deliverTimeMs 的消息
   ▼
[Broker]
   │ 写入 CommitLog（topic 改为 rmq_sys_wheel_timer，原 topic 备份在属性中）
   ▼
[TimerEnqueueGetService] 后台线程
   │ 扫描 rmq_sys_wheel_timer topic 的 ConsumeQueue
   │ 把定时消息封装成 TimerRequest
   ▼
[BlockingQueue: enqueuePutQueue]  生产-消费缓冲
   ▼
[TimerEnqueuePutService] 后台线程
   │ 批量取出 TimerRequest
   │ 按 deliverTimeMs 计算槽位 = (deliverTime / precision) % wheelSize
   │ 把 TimerRequest 写入 TimerLog
   │ 更新 TimerWheel 对应槽位的 first_pos / last_pos
   ▼
[等待时间到达]
```

### 3.5 出轮投递流程

```
[TimerDequeueGetService] 后台线程，每 50ms 推进一个槽位
   │ 当前时间到了，遍历该槽位的 TimerLog 链表
   │ 把每条记录封装成 TimerRequest
   ▼
[BlockingQueue: dequeueGetQueue]
   ▼
[TimerDequeueGetMessageService]
   │ 根据 TimerRequest 中的 CommitLog offset 读出原始消息
   ▼
[BlockingQueue: dequeuePutQueue]
   ▼
[TimerDequeuePutMessageService]
   │ 取出 TimerRequest 中的原始消息
   │ 把 topic 还原成业务 topic
   │ 重新写入 CommitLog
   │ → Consumer 即可消费
```

**生产-消费模式的好处**：流量控制（队列满则阻塞），避免单步 OOM。

### 3.6 防止延迟消息被老化删除

RocketMQ 默认消息保留 72 小时（`fileReservedTime=72`），延迟超过 72h 的消息会被删除。

5.x 的方案：
- 入轮前判断：如果延迟时间超过时间轮窗口（默认 2 天），**重新写入 CommitLog 滚动一遍**
- 等到接近投递时间（在窗口内）再放入时间轮

代价：多次 CommitLog 写入；好处：避免存储膨胀。

### 3.7 关键参数

```properties
# 启用定时消息（5.x）
timerEnable=true

# 时间轮精度（默认 1s）
timerPrecisionMs=1000

# 时间轮窗口（默认 7 天 = 604800s）
TIMER_WHEEL_TTL_DAY=7

# 时间轮文件路径
storePathTimerLog=${storePathRootDir}/timerlog
storePathTimerWheel=${storePathRootDir}/timerwheel
```

## 四、4.x vs 5.x 对比

| 维度 | 4.x（延迟级别） | 5.x（时间轮） |
| --- | --- | --- |
| 灵活性 | ❌ 仅 18 个固定级别 | ✅ 任意时间 |
| 精度 | ✅ 准确（按级别定时器）| 默认 1s |
| 实现复杂度 | 低（每级别一个 Queue） | 高（时间轮 + TimerLog + 多线程协作） |
| 性能 | 高（O(1) 检查队首）| 中（多次写入 + 链表遍历） |
| 最大延迟 | 2h（受配置限制） | 默认 7 天 |
| 生产成熟度 | 久经考验 | 较新，业务稳定但需要观察 |

**升级建议**：业务大部分需求 4.x 已能覆盖；只有强需求"任意延迟时间"的场景才上 5.x。

## 五、其他延时方案对比

### 5.1 Redis ZSet 延时队列

```python
# 入队
ZADD delay_queue <trigger_time> <message_id>

# 消费
loop:
  msgs = ZRANGEBYSCORE delay_queue 0 NOW LIMIT 0 100
  for msg in msgs:
    if ZREM delay_queue msg == 1:  # 抢占
      handle(msg)
```

**优势**：实现简单，Redis 即可。
**劣势**：单实例性能瓶颈、无持久保障、Cluster 下分片困难。

### 5.2 数据库轮询

```sql
SELECT * FROM order WHERE status='PENDING' AND created_at < NOW()-INTERVAL 30 MINUTE
```

**优势**：可靠、易理解。
**劣势**：DB 压力大、不实时、扩展性差。

### 5.3 Kafka 没有延迟消息

Kafka 不原生支持延迟消息，需要外部实现：
- 多个延迟级别 Topic（30s、1min、5min...），到期投递业务 Topic
- 或用 KSQL / Stream API 自定义

### 5.4 RabbitMQ：DLX + TTL

利用死信交换机：
1. 消息发到一个**没有 Consumer**的队列，设置 TTL
2. TTL 到期后消息进入 DLX（死信交换机）
3. 业务 Consumer 订阅 DLX 消费

**坑**：RabbitMQ 的 TTL 是基于消息**进入队列的时刻**，并发消费时容易乱序。

| 方案 | 精度 | 最大延迟 | 持久化 | 适用 |
| --- | --- | --- | --- | --- |
| **RocketMQ 4.x** | 准确（18 级） | 2h | ✅ | 主流业务 |
| **RocketMQ 5.x** | 1s | 7 天 | ✅ | 任意延迟需求 |
| Redis ZSet | 取决于轮询 | 任意 | ⚠️ | 中小规模 |
| DB 轮询 | 取决于扫描 | 任意 | ✅ | 简单业务 |
| RabbitMQ TTL+DLX | 队列级 | 任意 | ✅ | RabbitMQ 用户 |
| Kafka | 不支持 | - | - | - |

## 六、生产踩坑

### 6.1 4.x 升级后业务延迟时间不对

**现象**：从 4.6 升到 4.9 后，部分延迟消息变成了 1s 级别。

**根因**：`messageDelayLevel` 配置改了或 Broker 重启时配置丢失。

**修复**：
```properties
# 在所有 Master Broker 的 broker.conf 中显式配置
messageDelayLevel=1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h
```

### 6.2 延迟消息高峰期延迟生效

**现象**：业务下单 30 分钟后才触发关单，但实际触发时延迟了 5 分钟。

**根因**：4.x 中所有"30 分钟级"消息都堆在一个 Queue（SCHEDULE_TOPIC_XXXX 的 Queue-15），高峰期单个 Queue 处理不过来。

**修复**：
- 业务侧错峰发送（同一秒发的消息分到不同 trigger time）
- 或用 5.x 时间轮（多线程并发处理）

### 6.3 5.x 时间轮重启后消息丢失

**现象**：Broker 异常 kill 后，部分定时消息没有按时投递。

**根因**：TimerWheel 的内存状态丢失，CheckPoint 没及时刷盘。

**修复**：
- 启用 `flushDiskType=SYNC_FLUSH`（Checkpoint 文件也同步刷）
- 或开 Dledger 防止单机故障

### 6.4 大量延迟消息导致存储膨胀

**现象**：业务用 5 天延迟，Broker 磁盘 1 周翻一倍。

**根因**：5.x 时间轮窗口外的消息会**重新写入 CommitLog**滚动 → 同一条消息可能写多次。

**修复**：
- 调大时间轮窗口（默认 7 天可以撑住绝大多数场景）
- 业务上避免大量长延迟消息（改用 DB 定时任务）

### 6.5 延迟消息使用了消息属性导致序列化错误

**现象**：消息体包含特殊字符，延迟到期后 Consumer 解析失败。

**根因**：4.x SCHEDULE_TOPIC_XXXX 转发时**消息属性被覆盖**——某些版本 bug 会丢失自定义 properties。

**修复**：
- 关键属性放消息体不放 properties
- 或升级到稳定版本

## 七、面试高频追问

**Q1：4.x 的延迟消息怎么实现"按时间到期投递"？**

每个延迟级别一个内部 Queue（SCHEDULE_TOPIC_XXXX 下的 Queue-N）。同 Queue 内消息**天然按发送时间有序 → 也按到期时间有序**（因为同级别延迟相同）。Broker 后台 ScheduleMessageService 每秒扫一次队首，到期了就把消息重新投递到原 topic。

**Q2：4.x 为什么不支持任意延迟时间？**

任意时间会破坏"同 Queue 内有序"的优势——消息插入要找正确位置，每次扫描要全 Queue 排序，性能急剧下降。RocketMQ 4.x 选择**牺牲灵活性换性能**：18 个级别覆盖 95% 的业务场景。

**Q3：5.x 时间轮怎么处理超过窗口的消息（比如 8 天延迟）？**

入轮前判断：如果延迟时间 > 时间轮窗口（默认 7 天），**不入轮，重新写入 CommitLog 让它"滚一圈"**——等到 1 天后再次扫描，此时距投递时间还有 7 天，可以入轮了。代价是多次写入 CommitLog（占用存储），好处是避免时间轮文件无限膨胀。

**Q4：5.x 的时间轮槽位是 1 秒精度，能做毫秒级延迟吗？**

不能。`timerPrecisionMs` 默认 1000，最小精度就是 1s。要毫秒级延迟用 ScheduledExecutorService 在业务侧实现。

**Q5：4.x 修改 messageDelayLevel 配置要重启 Broker 吗？**

**要**。配置在 Broker 启动时加载，运行时修改不会生效。改完要滚动重启所有 Master。

**Q6：延迟消息和事务消息能一起用吗？**

可以。事务消息 COMMIT 后变成普通消息，可以再带上 delayTimeLevel——业务上常见场景"创建订单 + 30 分钟后检查支付状态"就是这个组合。

**Q7：延迟消息的吞吐和普通消息一样吗？**

略低。多了一次"先写 SCHEDULE_TOPIC_XXXX → 到期再写业务 topic"的过程，所以吞吐降低 ~20%。

**Q8：消息已经在延迟队列里了，能取消吗？**

4.x **不能**——消息已写入 CommitLog 不可改。业务侧只能在 Consumer 收到时判断"是否还需要执行"。

5.x **支持取消**——可以发送一条带 `cancelMsgId` 的消息到时间轮，TimerDequeueGetMessageService 处理时会跳过被标记取消的消息。

**Q9：延迟消息上限是多少？**

- 4.x：取决于 messageDelayLevel 最大值，默认 2h
- 5.x：取决于 timerWheelTTL，默认 7 天，可调

## 八、答题模板（60 秒话术）

> RocketMQ 延迟消息 4.x 和 5.x 实现完全不同：
>
> **4.x 是 18 个固定延迟级别**（1s ~ 2h）。Producer 发消息时设 `setDelayTimeLevel(N)`，Broker 收到后把 topic 改成 SCHEDULE_TOPIC_XXXX，每个级别对应一个 Queue。同 Queue 内消息天然按到期时间有序，后台线程每秒扫队首是否到期，到期就还原 topic 重新投递。优点是简单高性能，缺点是不能用 35 分钟这种自定义延迟。
>
> **5.x 用时间轮**支持任意时间延迟。基于三个文件：TimerWheel（循环数组，每槽 1 秒）、TimerLog（追加日志，每条指向 CommitLog 物理偏移）、Checkpoint（恢复点）。入轮和出轮各分多个步骤，用 BlockingQueue 串起来形成生产-消费流水线。超过 7 天的延迟会**重新写入 CommitLog 滚动**避免时间轮膨胀。
>
> **典型场景**：30 分钟未支付关单。生产建议：① 关键属性放消息体不放 properties（避免转发丢失） ② 业务侧错峰发送，避免单 Queue 高峰堆积 ③ Broker 用 SYNC_FLUSH 防止重启丢消息。
