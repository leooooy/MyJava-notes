# RocketMQ 重复消费与幂等

> "MQ 怎么保证消息不被重复消费？" —— **永远是错误问法**。MQ 不能保证不重复，**必须由业务侧做幂等**。
> 本篇要解决：
> ① 为什么重复消费是必然的而不是偶然？哪些环节会导致重复？
> ② 几种幂等实现方式的取舍：DB 唯一约束 / 状态机 / Token / Redis SETNX？
> ③ 幂等设计的边界——什么时候可以放弃幂等？
> ④ 幂等表/去重表怎么避免无限膨胀？

---

## 一、重复消费是必然，不是可能

### 1.1 五大重复来源

```
① Producer 重试
   - 同步发送收到超时（其实 Broker 已写入），重试 → 消息存了两份

② Broker 异步刷盘 + OS 崩溃
   - 极少数情况：消息写入但响应丢失 + Producer 重试 → 重复

③ Consumer offset 异步提交（每 5s）
   - 消费完 100 条还没提交 offset 就重启 → 这 100 条全部重新消费

④ Rebalance（最常见）
   - Consumer 上线/下线/扩容 → Queue 重新分配
   - 老 Consumer 已拉但未提交 offset 的消息 → 新 Consumer 重新拉

⑤ 消费失败重试
   - Listener 抛异常 → 进入 retry topic → 16 次重试
   - 业务可能"部分成功"——重试时已成功的部分重复执行
```

### 1.2 RocketMQ 的语义承诺

```
At Least Once（至少一次）
  保证消息不丢失，但可能重复
  
不是 Exactly Once（仅一次）
  代价太高（要分布式事务），业务上靠幂等等价实现
```

**所以 MQ 只承诺"At Least Once"**——是否变成 "Exactly Once" 由消费方靠幂等保证。

## 二、什么是幂等

### 2.1 定义

```
幂等：任意多次执行所产生的影响均与一次执行的影响相同

幂等：     "把账户余额设置为 100"     执行 N 次结果都是 100
不幂等：   "把账户余额加 100"         执行 N 次结果是 100N
```

### 2.2 业务设计原则

> **能改成幂等的接口尽量改**——不光是 MQ 消费，HTTP 接口、RPC 调用、定时任务、回调通知都该幂等。

## 三、幂等实现方式

### 3.1 方式 1：DB 唯一约束

**核心思路**：用业务键 + 唯一索引，重复插入会报错，业务捕获并跳过。

```sql
CREATE TABLE order_msg_log (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  msg_id VARCHAR(64) NOT NULL,
  order_id BIGINT NOT NULL,
  status VARCHAR(20) NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_msg_id (msg_id)  -- 关键：唯一约束
);
```

```java
public void onMessage(MessageExt msg) {
    try {
        msgLogDao.insert(new MsgLog(msg.getMsgId(), ...));  // 唯一约束
    } catch (DuplicateKeyException e) {
        return;  // 已处理过，直接跳过
    }
    
    // 业务逻辑（幂等保护已生效）
    orderService.handle(...);
}
```

**优势**：简单、可靠（DB 强一致）。
**劣势**：每条消息一次 DB IO；表会持续增长（要定期清理）。

### 3.2 方式 2：业务状态机

**核心思路**：业务本身有状态（如订单 PENDING → PAID → SHIPPED），更新时检查"前置状态"。

```java
public void handlePaidEvent(Long orderId) {
    int updated = orderDao.updateStatus(
        orderId, 
        OrderStatus.PENDING,    // 期望前置状态
        OrderStatus.PAID        // 目标状态
    );
    if (updated == 0) {
        // 不在期望状态——已经被处理过了
        return;
    }
    // 业务逻辑
}
```

```sql
UPDATE order
SET status = 'PAID'
WHERE id = ? AND status = 'PENDING';  -- 状态校验
```

**优势**：无需额外的去重表；天然契合业务。
**劣势**：要求业务有清晰的状态机；不适合"无状态"场景。

### 3.3 方式 3：乐观锁（版本号）

```java
public void updateBalance(Long userId, BigDecimal delta, int version) {
    int updated = userDao.updateBalanceWithVersion(userId, delta, version);
    if (updated == 0) {
        return;  // 版本号已变，可能已处理过
    }
}
```

```sql
UPDATE user
SET balance = balance + ?, version = version + 1
WHERE id = ? AND version = ?;
```

**优势**：可处理并发更新。
**劣势**：要求消息中携带 version，且业务端有版本号字段。

### 3.4 方式 4：Redis SETNX（Token 机制）

**核心思路**：用 Redis 做"去重表"，比 DB 性能高。

```java
public void onMessage(MessageExt msg) {
    String key = "msg_dedup:" + msg.getMsgId();
    Boolean ok = redisTemplate.opsForValue().setIfAbsent(key, "1", 7, TimeUnit.DAYS);
    if (Boolean.FALSE.equals(ok)) {
        return;  // 已处理过
    }
    
    try {
        // 业务逻辑
        bizService.handle(...);
    } catch (Exception e) {
        redisTemplate.delete(key);  // 失败回滚 Redis 标记，允许下次重试
        throw e;
    }
}
```

**优势**：性能高（Redis 单机 10w+ TPS）。
**劣势**：
- Redis 故障 → 幂等失效（必须降级到 DB）
- 业务执行 + Redis 操作不在同事务，**有"窗口期"**：写 Redis 成功 → 业务执行失败 → Redis 回滚——这中间崩溃就会丢消息处理

### 3.5 方式 5：DB 去重表 + 业务表（同事务）

```java
@Transactional
public void onMessage(MessageExt msg) {
    // 同一事务，原子性保证
    msgLogDao.insertWithUniqueCheck(msg.getMsgId());  // 唯一约束
    bizDao.update(...);                                 // 业务操作
}
```

**优势**：强一致，不依赖外部组件。
**劣势**：每条消息至少 2 次 DB IO；幂等表膨胀。

### 3.6 五种方式对比

| 方式 | 性能 | 一致性 | 实现复杂度 | 适用场景 |
| --- | --- | --- | --- | --- |
| DB 唯一约束 | ⭐⭐⭐ | 强 | 简单 | 通用 |
| 业务状态机 | ⭐⭐⭐⭐ | 强 | 中 | 状态机场景 |
| 乐观锁版本号 | ⭐⭐⭐⭐ | 强 | 中 | 并发更新场景 |
| Redis SETNX | ⭐⭐⭐⭐⭐ | 弱（Redis 故障会失效）| 简单 | 高吞吐 |
| 去重表 + 业务表（事务）| ⭐⭐⭐ | 强 | 简单 | 不允许丢失 |

## 四、幂等键怎么选？

### 4.1 候选

| 幂等键 | 优势 | 劣势 |
| --- | --- | --- |
| **msgId**（RocketMQ 消息 ID） | 全局唯一 | 重发新消息时 msgId 变了 |
| **uniqueKey**（消息 keys） | 业务方控制 | 业务要保证唯一 |
| **业务 ID**（订单 ID）| 业务自然键 | 同业务多消息时不够 |

### 4.2 关键考虑：相同业务多次发消息

```
场景：用户支付重试
  - 第一次支付：发消息 (orderId=100, msgId=A)
  - 用户取消又重试：发消息 (orderId=100, msgId=B)
  - 这两条消息都应该被消费！
  - 用 msgId 幂等：✅ 都执行
  - 用 orderId 幂等：❌ 第二条会被丢弃
```

所以 **msgId 是更安全的幂等键**——相同业务重发时 msgId 不同，不会被错误去重。

### 4.3 推荐组合

```java
// 业务 ID + 消息 ID 双重保护
String dedupKey = orderId + ":" + msgId;
```

或

```java
// 用 keys 字段（业务可控）
msg.setKeys(orderId + "_" + UUID.randomUUID());  // Producer 端
String dedupKey = msg.getKeys();                   // Consumer 端
```

## 五、幂等表的运维

### 5.1 表会无限膨胀

**问题**：一个高 TPS 业务每天 1000 万条消息 → 一年 36 亿行去重记录。

### 5.2 解决方案

**方案 1：分表**

```sql
-- 按月分表
CREATE TABLE msg_dedup_202310 (...);
CREATE TABLE msg_dedup_202311 (...);
```

**方案 2：定期清理**

```sql
-- 每天清理 30 天前的记录
DELETE FROM msg_dedup WHERE created_at < NOW() - INTERVAL 30 DAY LIMIT 10000;
```

注意：消息重复的窗口期通常很短（< 24h），保留 7~30 天足够。

**方案 3：Redis + 短 TTL**

```java
String key = "dedup:" + msgId;
redis.setex(key, 7 * 24 * 3600, "1");  // 7 天后自动过期
```

**方案 4：布隆过滤器**

```
适用：千万级 / 亿级业务，DB 撑不住
代价：有误判（极小概率把"未处理"误判为"已处理"）
建议：业务能接受 < 0.01% 漏处理时使用
```

## 六、什么时候不用幂等？

### 6.1 真"幂等的"操作

```
- 简单的 SET（"把 status 设为 PAID"）
- 删除（"删除订单 X"）
- 计算后的覆写（不依赖前值）
```

这些操作天然幂等，不需要额外去重。

### 6.2 业务允许重复

```
- 日志埋点（多写一条没所谓）
- 统计计数（接受 0.1% 误差）
- 推荐内容刷新（多刷一次没事）
```

### 6.3 业务无副作用

```
- 通知类（发推送）—— 即使重复发送一次推送，用户看到同样内容多了一条问题不大
  （但还是建议 Token 去重避免轰炸用户）
```

## 七、生产踩坑

### 7.1 SETNX 后业务异常导致永久丢消息

**现象**：偶发性消息没被处理，但 Redis 里有 dedupKey。

**根因**：
```java
redis.setIfAbsent(key, "1");  // 成功
bizService.handle(...);        // 抛异常
// ❌ Redis 标记没回滚 → 下次重试时被认为已处理 → 真的丢了
```

**修复**：
```java
try {
    bizService.handle(...);
} catch (Exception e) {
    redis.delete(key);  // 业务失败 → 回滚去重标记
    throw e;
}
```

或者用 DB 去重表 + 业务表同事务（更强一致）。

### 7.2 幂等表设计成自增主键

**现象**：插入幂等表偶发主键冲突，重启后正常。

**根因**：自增 ID 跨实例分配可能冲突；应该用业务键（msgId）作主键或唯一约束。

**修复**：
```sql
CREATE TABLE msg_dedup (
    msg_id VARCHAR(64) PRIMARY KEY,  -- 直接用 msg_id 做主键
    ...
);
```

### 7.3 用消息体哈希做幂等键

**现象**：同样内容的两条业务消息（如"支付 100 元"重发）被错误去重。

**根因**：消息内容相同 ≠ 业务相同。

**修复**：用 msgId 或业务 ID + 时间戳作幂等键，不要用消息体哈希。

### 7.4 高并发下 SETNX 之后立即查 DB

**现象**：高并发时偶发"找不到订单"异常。

**根因**：
```java
redis.setIfAbsent("dedup:" + msgId, "1");
Order order = orderDao.find(orderId);  // 可能为 null（订单还没创建完）
```

消息可能比订单创建更快到达消费者（事务消息或 DB 主从延迟）。

**修复**：业务上加重试 + 兜底查从库 + 配合 RocketMQ 重试机制。

### 7.5 状态机幂等漏判后置状态

```java
// ❌ 错：只检查前置状态
UPDATE order SET status='PAID' WHERE id=? AND status='PENDING';

// 边界情况：消息延迟到达，订单已经 SHIPPED 了
// 这时 UPDATE 0 行 → 业务以为重复，实际是迟到——但已经无法回退
```

**修复**：
```java
// 检查"当前状态是否已经 ≥ 目标状态"
Order o = orderDao.find(orderId);
if (o.getStatus().ordinal() >= OrderStatus.PAID.ordinal()) {
    return;  // 已是更后的状态，跳过
}
```

## 八、面试高频追问

**Q1：MQ 怎么保证消息不被重复消费？**

**这是错误问法**。MQ 不保证，必须由业务侧做幂等。重复消费的来源：
- Producer 重试（Broker 已写入但响应丢失）
- Consumer offset 异步提交（每 5s，重启丢失）
- Rebalance（已拉未提交的消息被新 Consumer 重新拉）
- 消费失败重试（部分成功部分失败时，重试导致部分逻辑重复执行）

**Q2：怎么实现幂等？**

主流五种方式：
1. **DB 唯一约束**（推荐通用方案）
2. **业务状态机**（订单 PAID → SHIPPED 这种）
3. **乐观锁版本号**（并发更新场景）
4. **Redis SETNX**（高吞吐，但要注意业务异常时回滚）
5. **DB 去重表 + 业务表同事务**（强一致）

**Q3：用 msgId 还是业务 ID 做幂等键？**

**推荐 msgId**。因为相同业务可能合理地发多次消息（如用户支付重试），用业务 ID 会错误去重；用 msgId 每条消息独立，安全。

如果业务方能保证消息发送的去重（同一业务只发一次消息），可以用业务 ID。

**Q4：Redis 做幂等有什么风险？**

最大风险是 **Redis 故障导致幂等失效**——这时只能让业务降级（拒绝处理 / 队列暂停）或回退到 DB 去重。

其次是 **业务执行 vs Redis 操作不在同事务**：写 Redis 成功 → 业务失败 → Redis 没回滚 → 真的丢消息。要么靠 try/catch 主动 delete，要么用 DB 同事务方案。

**Q5：幂等表无限膨胀怎么办？**

```
- 分表（按月）
- 定期清理（保留 7~30 天，重复消费窗口期通常很短）
- Redis + 短 TTL（自动过期）
- 布隆过滤器（千万级业务，接受极小误判）
```

**Q6：Exactly Once 真的能实现吗？**

工程上 **靠"At Least Once + 幂等"等价实现**。理论上 Exactly Once 需要分布式事务（如 2PC）协调 Producer / Broker / Consumer 三方，性能极差，业内基本不用。

Kafka Streams 的 "Exactly Once" 也是限定在 Kafka 内部（producer + consumer + state store 同事务），跨外部系统仍要业务侧幂等。

**Q7：为什么 RocketMQ 不能直接做 Exactly Once？**

```
要做到 Exactly Once 需要：
① Producer 不能重复发（要事务存储）
② Broker 不能丢
③ Consumer offset 提交和业务执行原子
   - 业务在外部系统（DB / 其他 MQ）→ 跨系统事务
   - 几乎无法实现
```

所以承诺 At Least Once + 业务幂等是工程实现的最佳折中。

**Q8：幂等和重试是矛盾的吗？**

不是，**互补的**。重试保证"消息一定被处理"，幂等保证"重复处理不出问题"。两者必须同时存在：
- 只重试不幂等 → 重复执行业务（扣 200 元而不是 100 元）
- 只幂等不重试 → 失败时消息丢失

## 九、答题模板（60 秒话术）

> MQ 不保证不重复消费——RocketMQ 承诺的是 **At Least Once**。重复来源主要 5 个：Producer 重试、offset 异步提交、Rebalance、消费失败重试、网络抖动 ACK 丢失。
>
> **解法是业务侧幂等**——能改成幂等的接口尽量改。主流五种方式：
>
> ① **DB 唯一约束**：用 msgId 做唯一索引，重复插入 catch 异常。简单可靠，通用首选。
>
> ② **业务状态机**：UPDATE WHERE 检查前置状态（PAID ← PENDING），无需额外去重表。
>
> ③ **乐观锁**：用版本号 / 时间戳，并发更新场景。
>
> ④ **Redis SETNX**：高吞吐，但业务异常时必须 catch 后 delete 回滚去重标记。
>
> ⑤ **DB 去重表 + 业务表同事务**：强一致兜底方案。
>
> **幂等键选 msgId** 不是业务 ID——同一业务可能合理地发多次消息（用户支付重试），用业务 ID 会错误去重。**幂等表会膨胀**，按月分表 + 定期清理 7~30 天前数据 + Redis 短 TTL 三种方式选其一。
