# RocketMQ 存储机制

> RocketMQ 单机能跑到 10w+ TPS，**核心就在这一篇里讲的存储设计**。
> 本篇要解决：
> ① 为什么用一个 CommitLog 共用所有 Topic，而 Kafka 反着来按 Partition 分文件？
> ② mmap、PageCache、零拷贝到底怎么配合？为什么 sendfile 用不上？
> ③ ConsumeQueue 和 IndexFile 各解决什么问题？
> 这是面试最深一层的题——能讲明白这一篇，"高吞吐为什么"就过关了。

---

## 一、整体架构：三个文件三件事

```
+---------------------------------------------------------------+
|                       Broker 文件系统                          |
+---------------------------------------------------------------+
|                                                               |
|  CommitLog（消息主体，所有 Topic 共用）                        |
|   00000000000000000000        ← 1G，文件名=起始 offset         |
|   00000000001073741824                                        |
|                                                               |
|  ConsumeQueue（消费索引，按 Topic/Queue 拆）                   |
|   topic-A/                                                    |
|     queue-0/                                                  |
|       00000000000000000000   ← 5.72M，每条 20 字节定长        |
|     queue-1/                                                  |
|   topic-B/                                                    |
|                                                               |
|  IndexFile（key/时间索引，可选）                               |
|   20231011120000             ← 哈希索引，按 msgKey 查找       |
|                                                               |
+---------------------------------------------------------------+
```

**职责划分**：

| 文件 | 存什么 | 写入方式 | 用途 |
| --- | --- | --- | --- |
| **CommitLog** | 全量消息（topic、tag、body 都在里面） | **顺序追加**，所有 Topic 共用 | 唯一持久化源 |
| **ConsumeQueue** | offset (8B) + size (4B) + tagHash (8B) = 20B | 异步生成（ReputMessageService） | 消费时定位 |
| **IndexFile** | key 哈希 → offset | 可选 | 按 msgKey/时间查询消息 |

## 二、CommitLog：所有 Topic 共用一个文件

### 2.1 文件结构

```
单文件 1G（commitLog.fileSize = 1073741824），文件名 = 起始物理偏移量

00000000000000000000   ← 第 1 个文件，起始 offset = 0
00000000001073741824   ← 第 2 个文件，起始 offset = 1G
00000000002147483648   ← 第 3 个文件
...
```

写满 1G 自动生成下一个，**永远顺序追加**——这是高吞吐的物理基础。

### 2.2 单条消息格式

```
┌────────────┬───────┬────────┬──────┬─────┬──────┬─────────┬─────────┬──────┐
│ totalSize  │ magic │ bodyCRC│ qid  │ flag│ qOff │ phyOff  │ ... body│ ...  │
│   4B       │  4B   │   4B   │  4B  │  4B │  8B  │   8B    │   xB    │      │
└────────────┴───────┴────────┴──────┴─────┴──────┴─────────┴─────────┴──────┘
```

**变长**——所以 CommitLog 不能像 ConsumeQueue 一样用偏移量直接定位第 N 条；需要先读 4 字节 totalSize。

### 2.3 关键设计：为什么所有 Topic 共用？

**Kafka 的反例**：每个 Topic-Partition 一个独立文件目录。

```
topic-a/
  partition-0/
  partition-1/
topic-b/
  partition-0/
```

| 场景 | RocketMQ（共用 CommitLog） | Kafka（每分区独立） |
| --- | --- | --- |
| 单 Topic 写入 | ⚠️ 与其他 Topic 抢一个文件锁 | ✅ 各 Partition 独立顺序写 |
| **N 个 Topic 同时写** | ✅ **依然顺序追加 1 个文件**，磁盘磁头不来回跳 | ❌ N 个 Partition = N 路写，本质退化为随机写 |
| 单 Topic 极限 TPS | ~10w | ~17w |
| **数百 Topic 并发** | ✅ 不掉性能 | ❌ 每多一个 Topic 性能下降 |

**结论**：
- Kafka 优化的是**少量大 Topic 的极限吞吐**（日志场景，1~10 个 Topic）
- RocketMQ 优化的是**大量小 Topic 的稳定吞吐**（业务场景，几百~上千 Topic）

**代价**：CommitLog 不区分 Topic，按 Topic 查消息要遍历整个 1G 文件——性能不可接受。所以引入 **ConsumeQueue 索引**。

## 三、ConsumeQueue：消费索引（关键）

### 3.1 文件结构

```
$HOME/store/consumequeue/{topic}/{queueId}/{fileName}

每条记录定长 20 字节：
┌────────────────────┬────────────┬────────────────────┐
│  CommitLog 物理偏移 │  消息长度  │  Tag 哈希值        │
│       8 B          │     4 B    │       8 B          │
└────────────────────┴────────────┴────────────────────┘

单文件 30W 条 × 20B = 5.72MB
```

### 3.2 为什么定长？

```java
// 直接根据 queueOffset 计算物理位置，O(1) 随机读
long phyOffset = queueOffset * 20;
// 读 20 字节
ByteBuffer buf = mappedFile.read(phyOffset, 20);
```

定长 → 像数组一样可以随机访问 → Consumer 拉消息无需顺序遍历。

### 3.3 怎么生成？

```
[Producer] ─────► CommitLog（同步）
                       │
                       ▼
              ReputMessageService（后台线程）
                       │
                       │ 每 1ms 扫描 CommitLog 新增
                       ▼
              生成 ConsumeQueue 索引 + IndexFile
```

**关键点**：
- ConsumeQueue 是 **异步构建** 的，写 CommitLog 立即返回成功
- ReputMessageService 默认 1ms 一轮，所以从写成功到可被消费 **延迟通常 < 1ms**
- 极端情况下（Broker 重启）会从 checkpoint 文件恢复，**先重建 ConsumeQueue 才对外提供消费**

### 3.4 Tag 过滤怎么工作？

```
Consumer 订阅 topic-A, tag=ORDER_PAY

(1) Broker 收到 Pull 请求，先用 tag 的 hashCode 在 ConsumeQueue 上过滤
    ─→ 命中的 record 才去 CommitLog 读完整消息
(2) Consumer 收到消息后，对原始 tag 字符串再做一次精确比对
    ─→ 因为 hashCode 可能冲突
```

为什么不在 ConsumeQueue 存原始 tag？因为定长 20 字节是**前提**——存原始 tag 就退化成变长，丢了 O(1) 随机访问。

## 四、IndexFile：按 Key/时间查消息

### 4.1 用途

不是消费时用的，**是运维和业务排查用**：
- 按 msgKey 查消息（业务下单时给消息打 keys = orderId）
- 按时间区间查消息（回溯消费）

### 4.2 结构

```
┌─────────────┬───────────────────┬───────────────────────────┐
│  Header     │  HashSlot 数组    │  Index 链表节点           │
│  40B        │  500W × 4B = 20M  │  2000W × 20B = 380M       │
└─────────────┴───────────────────┴───────────────────────────┘

总大小 ≈ 400MB（参数 hashSlotNum=500W, indexNum=2000W）
```

哈希冲突用 **拉链法**：每个 slot 指向链表头，链表节点存 keyHash + phyOffset + timestamp + prev。

### 4.3 查询流程

```java
slotIndex = (keyHash % 5000000)
slotPhyPos = HEADER_SIZE + slotIndex * 4
indexHeadPos = mappedFile.getInt(slotPhyPos)  // 读 slot 链表头位置

while (indexHeadPos > 0) {
    Index node = readIndex(indexHeadPos);
    if (node.keyHash == keyHash && time in [begin, end]) {
        result.add(node.phyOffset);  // 命中
    }
    indexHeadPos = node.prev;  // 沿链表前推
}
```

## 五、mmap + PageCache：高吞吐的核心

### 5.1 mmap 是什么？

```
传统 read/write：
  应用 buffer ←── 内核 PageCache ←── 磁盘
  3 次拷贝（磁盘 → PageCache → 内核 socket buffer → 用户态）

mmap（内存映射）：
  应用直接操作"看似在内存的文件"
  实际数据在 PageCache，OS 按需缺页加载
  零拷贝（用户态/内核态共享同一物理内存页）
```

```java
// RocketMQ 的 MappedFile
FileChannel fc = new RandomAccessFile(file, "rw").getChannel();
MappedByteBuffer buf = fc.map(MapMode.READ_WRITE, 0, fileSize);
buf.put(messageBytes);  // 实际是写到 PageCache，不立即落盘
```

### 5.2 PageCache 的角色

```
                  写入                      读取
                   │                          │
                   ▼                          ▼
            ┌─────────────────────────────────────┐
            │       PageCache（内核）             │
            │   - 按 4KB 页缓存                    │
            │   - LRU 淘汰                         │
            └─────────────────────────────────────┘
                   │                          ▲
                   │ pdflush / fsync          │ 缺页中断
                   ▼                          │
            ┌──────────────────────────────────┐
            │            磁盘                   │
            └──────────────────────────────────┘
```

**Broker 进程挂了 PageCache 不会丢**（OS 接管），只有**断电或 OS 崩溃**才会丢——这是异步刷盘"安全"的核心理由。

### 5.3 文件预热（warmMappedFile）

冷启动时第一次访问会**频繁缺页中断**，导致延迟尖峰。RocketMQ 在创建新 MappedFile 时主动预热：

```java
// 每 4KB 写一个 0，触发 OS 把所有 page 加载进 PageCache
for (int i = 0, j = 0; i < this.fileSize; i += pageSize, j++) {
    byteBuffer.put(i, (byte) 0);
    if (j % 1000 == 0) Thread.sleep(0);  // 让出 CPU
}
mlock();  // 锁定不被 swap
```

### 5.4 为什么 RocketMQ 用 mmap，不用 sendfile？

| 方案 | 用法 | 优势 | 劣势 |
| --- | --- | --- | --- |
| **mmap** | 内存映射，应用可见数据 | 读写都行；可在用户态做 tag 过滤、CRC 校验 | 需要应用主动管理（mlock、unmap） |
| **sendfile** | 内核直接磁盘 → socket | 最少拷贝（DMA 到 socket buffer）| 应用看不到数据，**无法做 tag 过滤**、消息预处理 |

**RocketMQ 必须能在 Broker 端做 tag/sql 过滤**（否则推无效消息浪费带宽），所以选 mmap。Kafka 不做服务端过滤、直接转发，可以用 sendfile 把性能压到极致。

**单文件 1G 也是 mmap 的限制**：MappedByteBuffer 在 32 位系统上单次最多映射 2G，1G 是兼容性 + 文件切换粒度的折中。

## 六、刷盘策略（FlushDiskType）

> 详见 [刷盘与复制](./刷盘与复制.md)，这里只列要点。

| 模式 | 行为 | 延迟 | 安全性 |
| --- | --- | --- | --- |
| **ASYNC_FLUSH**（默认） | 写完 PageCache 即返回，后台线程每 500ms 批量 fsync | ~1ms | OS 崩溃丢数据 |
| **SYNC_FLUSH** | 写完 PageCache 后等 fsync 完成才返回 | ~5~10ms | 不丢（Broker 单机层面） |

代码层面：

```java
// org.apache.rocketmq.store.config.MessageStoreConfig
flushDiskType = ASYNC_FLUSH;  // 默认
// 或
flushDiskType = SYNC_FLUSH;
```

## 七、关键参数与配置

### 7.1 文件大小

```properties
# CommitLog 单文件大小（默认 1G）
mappedFileSizeCommitLog=1073741824

# ConsumeQueue 单文件条数（默认 30W 条）
mappedFileSizeConsumeQueue=6000000   # = 30W × 20

# 文件保留时长（默认 72h）
fileReservedTime=72

# 删除文件的时间窗口（默认凌晨 4 点）
deleteWhen=04
```

### 7.2 PageCache & 刷盘

```properties
# 异步刷盘间隔
flushIntervalCommitLog=500           # 默认 500ms
flushCommitLogLeastPages=4           # 累计 4 页（16KB）才触发
flushCommitLogThoroughInterval=10000 # 强制 10s 触发一次

# 文件预热
warmMapedFileEnable=true             # 推荐生产开启
```

### 7.3 容量估算

```
日均 1 亿消息，平均消息 1KB
─→ 日写入量 = 100GB
─→ 默认保留 72h = 300GB CommitLog 空间

ConsumeQueue 每条 20B
─→ 1 亿条 × 20B = 2GB/天
─→ 72h ≈ 6GB（基本忽略不计）

预留 50% 余量 ─→ 单 Broker 至少 500GB SSD
```

## 八、生产踩坑

### 8.1 PageCache 抖动导致写入抖动

**现象**：`storePutOK` TP99 偶发飙到 500ms+。

**根因**：异步刷盘的 fsync 在某些时刻批量触发（dirty_ratio 达到阈值），导致大量脏页一次性下刷，期间 PageCache 阻塞写入。

**修复**：
```bash
# 调小 dirty_ratio，减少单次 fsync 量
echo 5 > /proc/sys/vm/dirty_ratio          # 默认 20
echo 1 > /proc/sys/vm/dirty_background_ratio  # 默认 10
```

### 8.2 大消息（>4MB）导致写入失败

**现象**：发送 5MB 消息抛 `MessageBodySize > maxMessageSize`。

**根因**：默认 `maxMessageSize=4MB`，超过会被拒绝。

**修复**：
```properties
# Broker 端
maxMessageSize=8388608   # 提到 8MB

# Producer 端
producer.setMaxMessageSize(8388608);
```

> 推荐做法：消息体超 1MB 就改用对象存储（OSS/S3）+ 消息只传 URL。

### 8.3 ConsumeQueue 损坏导致消费回退

**现象**：Broker 异常重启后，部分消费者从很老的 offset 开始消费。

**根因**：异常宕机时 ConsumeQueue 来不及刷盘，重启后从 checkpoint 重建——但重建过程中消费者已开始拉消息，看到的是部分 ConsumeQueue。

**修复**：
- 启动参数加 `enableCleanIndex=true`，确保 ConsumeQueue 重建完成才对外提供服务
- 监控 `dispatchBehindBytes`（CommitLog 与 ConsumeQueue 的差距）

### 8.4 删除老文件触发磁盘 IO 风暴

**现象**：每天凌晨 4 点（默认 `deleteWhen=04`），磁盘 IOPS 飙升、写入抖动。

**根因**：72h 前的所有 CommitLog + ConsumeQueue 在凌晨 4 点一次性删除，触发文件系统 metadata 操作风暴。

**修复**：
```properties
deleteCommitLogFilesInterval=100   # 删除文件之间间隔 100ms（默认 100ms）
diskMaxUsedSpaceRatio=88           # 磁盘使用率超过 88% 才删（避免空闲时狂删）
```

## 九、面试高频追问

**Q1：为什么 RocketMQ 选择"所有 Topic 共用一个 CommitLog"，Kafka 反着来？**

RocketMQ 优化的是**业务场景下的多 Topic 稳定吞吐**——大厂业务可能有几百上千个 Topic，Kafka 那种"每 Topic 一个文件"在 Topic 多了之后会退化成随机写（磁盘磁头来回跳）。共用一个 CommitLog 保证**永远顺序写**，靠后台异步生成 ConsumeQueue 索引来弥补"按 Topic 读"的麻烦。代价是 ConsumeQueue 引入约 1ms 延迟（异步生成）+ 额外存储（每条 20B）。

Kafka 优化的是**少量大 Topic 的极限吞吐**（日志埋点几个 Topic 打天下），每 Partition 独立顺序写，单 Topic 能压到 17w TPS。

**Q2：mmap 和 sendfile 有什么区别？为什么 RocketMQ 不用 sendfile？**

mmap 是把文件映射到进程地址空间，应用可以直接读写"看似内存"的数据，OS 用 PageCache 缓存；sendfile 是内核直接把文件数据通过 DMA 送到 socket，应用看不到数据。

RocketMQ 必须在 Broker 端做 **tag 过滤、SQL92 过滤、CRC 校验**——这些都需要应用层访问消息内容，sendfile 做不到。Kafka 不做服务端过滤直接转发，所以可以用 sendfile 把性能压到极致。

**Q3：消息写到 PageCache 还没刷盘就返回成功，Broker 进程挂了会丢吗？**

**不会。** PageCache 是内核管理的，进程崩溃 PageCache 不受影响，OS 后台仍会把脏页刷到磁盘。**只有断电或 OS 崩溃**（kernel panic）才会丢失 PageCache 里未刷盘的数据——这就是为什么金融场景要开同步刷盘 + UPS 双重保护。

**Q4：CommitLog 文件名为什么用偏移量命名？**

为了 **O(1) 定位**：给定一个消息的物理偏移量（比如 1500000000），直接计算 `1500000000 / 1073741824 = 1`，找到第 2 个文件 `00000000001073741824`，读取相对偏移 `1500000000 - 1073741824 = 426258176`。无需维护文件元数据。

**Q5：ConsumeQueue 异步生成的话，会不会出现"消息写入成功但拉不到"？**

短暂会出现（通常 < 1ms）。`ReputMessageService` 默认每 1ms 轮询 CommitLog 新增。RocketMQ 的设计哲学是"业务消息允许 ms 级最终可见"，而不是 Kafka 那种"写完立即可读"。生产中这个延迟监控指标叫 `putMessageDistributeTime`，正常应该 < 10ms。

**Q6：IndexFile 删除会丢消息吗？**

**不会**。IndexFile 只是辅助查询索引，删除后只是无法按 key 查消息，**消息本身还在 CommitLog 里**。这也是 RocketMQ 设计上的解耦——CommitLog 是 single source of truth。

**Q7：单台 Broker 的极限 TPS 怎么估算？**

```
顺序写 SSD ≈ 500MB/s
单条消息平均 1KB
─→ 理论极限 50w TPS

但要扣除：
- mmap 系统调用开销
- 主从复制同步等待
- CRC 校验
- ConsumeQueue 异步生成的内存占用

实际 ≈ 10~17w TPS（异步刷盘异步复制）
       ≈ 5~8w TPS（同步刷盘同步双写）
```

## 十、答题模板（60 秒话术）

> RocketMQ 存储的核心是**三个文件 + 一项技术**：
>
> ① **CommitLog** 是消息真正的存储地——所有 Topic 共用一个 1G 的顺序追加文件，这是 RocketMQ 高吞吐的根基；和 Kafka 反着来的设计动机是优化多 Topic 场景，避免 Topic 多了退化成随机写。
>
> ② **ConsumeQueue** 是 CommitLog 的索引文件——按 Topic/Queue 拆，每条 20 字节定长（offset + size + tagHash），让消费时可以 O(1) 随机读。它是异步生成的，由后台 ReputMessageService 每 1ms 扫一次 CommitLog。
>
> ③ **IndexFile** 是按 key/时间的辅助索引——用哈希拉链法存 key→offset，主要用于业务排查。
>
> ④ 整套架构靠 **mmap + PageCache** 实现零拷贝写入：写消息直接写到 PageCache，进程挂了不丢、断电才丢；启动时主动 warmup（每 4KB 写一个 0）避免首次访问的缺页抖动。**为什么用 mmap 不用 sendfile**——因为 Broker 要做 tag 过滤、CRC 校验，需要应用层访问消息内容。
