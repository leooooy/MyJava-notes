# RocketMQ 生产者

> Producer 看似简单（建连、选 Queue、发消息），但**面试问深一层就是体力题**。
> 本篇要解决：
> ① 三种发送方式（Sync/Async/Oneway）怎么选？同步发送的"假同步"是怎么实现的？
> ② Producer 怎么做负载均衡 + 故障规避？为什么 Master 挂了客户端能立即绕开？
> ③ 重试机制有哪些细节？同步和异步的重试策略不一样？
> ④ Producer 的几个高频生产坑（OOM / 路由更新延迟 / 大消息）。

## 一、Producer 启动流程

```
DefaultMQProducer.start()
       │
       ▼
DefaultMQProducerImpl.start()
       │
       ├─► [1] 参数校验（producerGroup 不能用默认值 DEFAULT_PRODUCER）
       ├─► [2] changeInstanceNameToPID（默认 instanceName 改为 PID）
       ├─► [3] 获取/创建 MQClientInstance（一个 JVM 一个实例）
       ├─► [4] 注册 Producer 到 MQClientInstance
       ├─► [5] mQClientFactory.start()（核心）
       │       │
       │       ├─ Netty Client 启动
       │       ├─ 启动定时任务：
       │       │   - 每 30s 拉路由
       │       │   - 每 30s 发心跳到所有 Broker
       │       │   - 每 30s 清理失联 Broker
       │       │   - 每 5s 持久化 offset（共用 Consumer 的逻辑）
       │       └─ pullMessageService / rebalanceService 启动（共用 Consumer）
       │
       └─► serviceState = RUNNING
```

**关键点**：
- 一个 JVM **共享一个 MQClientInstance**——Producer 和 Consumer 共用 Netty 连接、心跳线程等
- `instanceName=PID` 是默认行为，**多个 Producer 同进程不会冲突**

## 二、消息发送的核心流程

### 2.1 端到端时序

```
[Producer]                                                  [Broker]
   │
   │ 1. 校验消息（topic 长度、body 大小）
   │
   │ 2. tryToFindTopicPublishInfo(topic)
   │    └─► 命中本地缓存？是 → 跳过 / 否 → 拉路由
   │
   │ 3. 选 Queue：mqFaultStrategy.selectOneMessageQueue()
   │    └─► 默认轮询 + 故障规避
   │
   │ 4. sendKernelImpl()
   │    │
   │    ├─ buildMessage（带上 topic / queueId / properties）
   │    ├─ 构造 RemotingCommand (opaque = 自增 id)
   │    └─ ────── Netty writeAndFlush ──────────────────────►
   │                                                              ▼
   │                                                       Broker 处理
   │                                                       │
   │                                                       ├─ checkMessage
   │                                                       ├─ putMessage
   │                                                       │   ├─ 写 CommitLog（mmap）
   │                                                       │   ├─ 同步/异步刷盘
   │                                                       │   └─ 同步/异步复制
   │                                                       └─ 返回 SendResult
   │                                                              │
   │ 5. 收到响应 ◄────── Netty channelRead ──────────────────────┘
   │    └─► responseTable.get(opaque).complete(result)
   │
   │ 6. 返回 SendResult { sendStatus, msgId, queueOffset, ... }
```

### 2.2 同步发送的"假同步"——opaque + ResponseFuture

```java
class NettyRemotingClient {
  // key = opaque（自增 ID），value = 等待响应的 Future
  ConcurrentMap<Integer, ResponseFuture> responseTable;
  
  RemotingCommand invokeSync(channel, request, timeout) {
    int opaque = request.getOpaque();
    ResponseFuture rf = new ResponseFuture(opaque, timeout);
    responseTable.put(opaque, rf);
    
    channel.writeAndFlush(request).addListener(f -> {
      if (!f.isSuccess()) {
        rf.setSendRequestOK(false);
        responseTable.remove(opaque);
      }
    });
    
    return rf.waitResponse(timeout);  // CountDownLatch.await
  }
  
  void channelRead(RemotingCommand response) {
    ResponseFuture rf = responseTable.remove(response.getOpaque());
    rf.putResponse(response);  // 解阻塞调用方
  }
}
```

**精髓**：
- 底层永远是 **Netty 异步**（writeAndFlush 不阻塞）
- 通过 `opaque` 把请求和响应关联起来
- 用 `CountDownLatch` 让调用方"看起来"是阻塞的

**好处**：单线程能并发处理大量同步请求（不需要 N 个线程对应 N 个同步请求）。

## 三、三种发送方式对比

### 3.1 三种 API

```java
// ① 同步：阻塞等响应（最可靠）
SendResult result = producer.send(msg);

// ② 异步：通过回调拿结果
producer.send(msg, new SendCallback() {
  public void onSuccess(SendResult result) { ... }
  public void onException(Throwable e) { ... }
});

// ③ 单向：发完就走，不等响应（最快，最不可靠）
producer.sendOneway(msg);
```

### 3.2 对比表

| 维度 | Sync | Async | Oneway |
| --- | --- | --- | --- |
| 调用线程是否阻塞 | ✅ 阻塞 | ❌ 不阻塞 | ❌ 不阻塞 |
| 是否能拿到 SendResult | ✅ 直接返回 | ✅ 回调 | ❌ 拿不到 |
| 是否自动重试 | ✅ 默认 2 次 | ✅ 默认 2 次（同 broker） | ❌ 无 |
| 失败是否能感知 | ✅ 异常 | ✅ 回调 | ❌ 无（OS 错误才能感知） |
| 单线程吞吐 | 受 RTT 限制 | 高 | 极高 |
| 典型场景 | 订单/支付（必达） | 通知类（容忍丢失但要可观测） | 日志/埋点（性能 > 一切） |

### 3.3 选型决策

```
能丢 1 条消息吗？
├─ 不能 → Sync
└─ 能丢 →
     是否需要异步处理？
     ├─ 是 → Async
     └─ 否（吞吐压满） → Oneway
```

## 四、负载均衡：选哪个 Queue？

### 4.1 默认策略：轮询 + 故障规避

```java
// MessageQueueSelector 默认实现（伪代码）
class SelectMessageQueueByRandom {
  int sendWhichQueue;  // ThreadLocal 自增
  
  MessageQueue select(List<MessageQueue> mqs, ...) {
    // 1. 简单轮询
    int index = sendWhichQueue++ % mqs.size();
    MessageQueue mq = mqs.get(index);
    
    // 2. 故障规避：检查这个 Broker 是不是"近期出过问题"
    if (latencyFaultTolerance.isAvailable(mq.getBrokerName())) {
      return mq;  // 可用，使用
    }
    
    // 3. 都不可用，退化为轮询
    return mqs.get(sendWhichQueue++ % mqs.size());
  }
}
```

### 4.2 故障规避（MQFaultStrategy）

每次发送完记录 latency，下次选 Queue 时根据 latency 决定"规避时长"：

| 单次 Latency | 规避时长 |
| --- | --- |
| < 100ms | 0ms（不规避） |
| 100~550ms | 30s |
| 550~1000ms | 60s |
| 1000~2000ms | 2min |
| 2000~3000ms | 3min |
| ≥ 15000ms 或异常 | **30min** |

**效果**：
- Broker 短暂网络抖动 → 30s 规避后再尝试
- Broker 进程挂掉 → 30 分钟内不会再选它
- 无需等 NameServer 的 120s 心跳超时
- **客户端层面的"快速故障转移"**

### 4.3 自定义 Queue 选择（顺序消息场景）

```java
producer.send(msg, new MessageQueueSelector() {
  @Override
  public MessageQueue select(List<MessageQueue> mqs, Message msg, Object arg) {
    int orderId = (int) arg;
    return mqs.get(orderId % mqs.size());  // hash 路由
  }
}, orderId);
```

**典型场景**：同一订单的所有消息发到同一个 Queue，保证顺序性。

## 五、重试机制

### 5.1 同步发送重试

```java
// DefaultMQProducerImpl.sendDefaultImpl
int timesTotal = 1 + retryTimesWhenSendFailed;  // 默认 1 + 2 = 3 次
String lastBrokerName = null;

for (int times = 0; times < timesTotal; times++) {
    MessageQueue mq = selectOneMessageQueue(topicPublishInfo, lastBrokerName);
    // 关键：lastBrokerName 让下次选 Queue 时绕开上次失败的 Broker
    lastBrokerName = mq.getBrokerName();
    
    try {
      sendResult = sendKernelImpl(msg, mq, ...);
      if (sendResult.getSendStatus() == SEND_OK) return sendResult;
      // 写入失败（如 FLUSH_DISK_TIMEOUT），continue 重试
    } catch (RemotingException | MQClientException e) {
      continue;  // 网络异常重试
    } catch (MQBrokerException e) {
      // Broker 业务异常（如 Topic 不存在）不重试
      throw e;
    }
}
```

**重试要点**：
- **默认 3 次**（首次 + 2 次重试）
- **每次换 Broker**（`retryAnotherBrokerWhenNotStoreOK=true`）
- **业务异常不重试**（避免无意义的重试）

### 5.2 异步发送重试

```properties
retryTimesWhenSendAsyncFailed=2  # 异步重试次数
```

**与同步的差异**：异步重试**只在同一 Broker** 上重试（因为换 Broker 涉及 selectQueue，而异步回调线程上下文不便操作）。

### 5.3 Oneway 不重试

发完就忘，无法感知失败，自然没有重试。

### 5.4 不该重试的场景

| 异常 | 是否应重试 | 原因 |
| --- | --- | --- |
| RemotingException（网络错误） | ✅ | 可能临时抖动 |
| FLUSH_DISK_TIMEOUT | ✅ | 重试到其他 Broker 可能成功 |
| FLUSH_SLAVE_TIMEOUT | ✅ | 同上 |
| MQBrokerException（Topic 不存在） | ❌ | 重试也没用 |
| 消息格式错误 | ❌ | 客户端 bug |

## 六、关键参数与配置

```properties
# 重试
retryTimesWhenSendFailed=2          # 同步重试次数
retryTimesWhenSendAsyncFailed=2     # 异步重试次数
retryAnotherBrokerWhenNotStoreOK=true  # 失败时切换 Broker

# 发送超时
sendMsgTimeout=3000                 # 默认 3 秒，建议 5 秒

# 消息大小
maxMessageSize=4194304              # 默认 4MB

# 路由
pollNameServerInterval=30000        # 拉路由间隔（默认 30s）

# 故障规避
sendLatencyFaultEnable=true         # 默认 true，建议保留

# 单 Producer 线程模型
asyncSenderExecutor                 # 异步发送的线程池，默认 cpuCores 大小
```

## 七、生产踩坑

### 7.1 Producer 启动慢、首次发送 RT 高

**现象**：服务启动后第一次 `send` 耗时 200ms+，之后正常 < 5ms。

**根因**：
1. 第一次拉 Topic 路由（NameServer 网络往返）
2. 第一次和 Broker 建立 TCP 长连接 + TLS 握手
3. JIT 还没编译热点方法

**修复**：服务启动时主动预热：
```java
producer.start();
// 主动拉一次路由
producer.fetchPublishMessageQueues("YOUR_TOPIC");
// 发一条预热消息
producer.send(new Message("YOUR_TOPIC", "warmup".getBytes()));
```

### 7.2 大消息引发 OOM

**现象**：日志类业务发 50MB 消息，Broker `OutOfMemoryError`。

**根因**：
- 默认 `maxMessageSize=4MB`，但有人改大到 50MB
- mmap 写大消息会一次性占满 PageCache，导致其他写入饥饿

**修复**：
- 业务遵守 1MB 上限
- 大文件传 OSS/S3，消息只传 URL
- 极端场景考虑用专门的"大消息 Broker 集群"隔离

### 7.3 路由缓存过期导致雪崩

**现象**：NameServer 重启后，1 分钟内大量 Producer 报"No route info"。

**根因**：Producer 默认 30s 拉一次路由，NameServer 启动后路由表为空（要等 Broker 上报，30s 才有完整路由）。

**修复**：
- NameServer 集群部署（≥ 3 台），滚动重启
- Broker 启动时立即上报路由
- Producer 增加路由拉取重试（`fetchNameServerAddr` 失败兜底）

### 7.4 同步发送在事件循环线程上调用导致死锁

**现象**：业务在 `SendCallback#onSuccess` 中又调用 `producer.send()` 同步等响应，整个 Producer 卡死。

**根因**：异步回调跑在 Netty 的 IO 线程上，同步发送也用同一个 Netty 客户端——同一线程等待自己的响应 = 死锁。

**修复**：永远不要在 SendCallback 里做同步发送；如果要发，提交到业务线程池。

### 7.5 ProducerGroup 重复导致冲突

**现象**：同 JVM 启了两个 Producer 用相同 group，第二个启动报错。

**根因**：MQClientInstance 用 producerGroup 做唯一性校验。

**修复**：每个 Producer 实例的 group 必须不同，或共享同一个 Producer 实例（推荐）。

## 八、面试高频追问

**Q1：Producer 是怎么知道 Topic 在哪些 Broker 上的？**

启动时连一台 NameServer，发 `GET_ROUTEINFO_BY_TOPIC` 请求，拉到 `TopicRouteData`，里面包含该 Topic 的 Queue 列表（broker + queueId）。**本地缓存 30s**，过期后从 NameServer 重新拉。

如果 Topic 不存在，会触发 **自动创建**（前提是 Broker 配置了 `autoCreateTopicEnable=true`）——生产强烈建议关闭，避免一个错别字导致建一堆垃圾 Topic。

**Q2：同步发送的 send() 为什么不阻塞所有 Netty 线程？**

因为底层是 **Netty 异步 + opaque + ResponseFuture**：调用方 `await` 在 CountDownLatch 上，Netty IO 线程只负责读响应、找到对应的 Future、`countDown` 解阻塞。一万个并发 send 只需要 N 个 IO 线程（默认 cpuCores 个）+ 一万个业务线程在等待。

**Q3：故障规避机制和 NameServer 心跳是什么关系？**

互补：
- NameServer 心跳：**Broker 角度**，120s 才能从注册中心剔除挂掉的 Broker
- 故障规避：**Producer 客户端角度**，单次发送失败立即生效（30 分钟规避）

故障规避补足了 120s 心跳超时的"反应迟钝"。

**Q4：异步发送的回调线程能做耗时操作吗？**

**不能**。回调跑在 `defaultAsyncSenderExecutor`（默认大小 = cpuCores），耗时操作会阻塞后续回调，导致超时增加。耗时逻辑应该再 submit 到业务线程池。

**Q5：消息发送失败的 SendStatus 有哪些？**

```java
public enum SendStatus {
  SEND_OK,              // 写入成功
  FLUSH_DISK_TIMEOUT,   // 同步刷盘超时（消息已写 PageCache）
  FLUSH_SLAVE_TIMEOUT,  // 同步复制超时（Master 已写）
  SLAVE_NOT_AVAILABLE,  // SYNC_MASTER 但没 Slave 可用
}
```

**注意**：这四种**都不是异常**——消息已经在 Master 的 PageCache 里了，只是没满足"完整可靠"承诺。后三种状态下，业务侧通常仍**算发送成功**，靠重试和幂等兜底。

**Q6：同步发送怎么处理超时？**

`sendMsgTimeout` 默认 3000ms，超时抛 `RemotingTimeoutException`，触发重试。**易错点**：超时不一定意味着 Broker 没收到——可能只是响应回包丢了，所以**消费侧必须做幂等**。

**Q7：发送 100w 条消息怎么提速？**

```
排查瓶颈：
- 单线程同步发送 ≈ 1000 TPS（受 RTT 限制）
- 多线程同步发送 → 每个线程独立 TPS，CPU/网卡打满
- 异步发送 → 单线程几万 TPS（Netty 流水线）
- Oneway → 极致性能，但失去可靠性

最优组合：
- 业务允许丢 → Oneway + 批量发送（List<Message>）
- 业务不允许丢 → 多线程 Sync + 业务幂等
```

批量发送：`producer.send(List<Message>)`——一次 RPC 发多条，吞吐提升 5~10 倍。

## 九、答题模板（60 秒话术）

> RocketMQ Producer 启动时拉一次 Topic 路由缓存到本地，每 30s 刷新，每 30s 给所有相关 Broker 发心跳。
>
> 发送时分三步：**选 Queue → 选 Broker → 写入**。负载均衡默认轮询，配合 **MQFaultStrategy 故障规避**——根据上次发送的 latency 动态规避 30s ~ 30min，比 NameServer 的 120s 心跳超时反应快得多。
>
> 三种发送模式：**Sync 是底层 Netty 异步 + opaque 假同步**，靠 CountDownLatch 阻塞调用线程；Async 是真正的回调；Oneway 发完就走。Sync 默认重试 3 次且换 Broker，Async 重试 2 次但只在同 Broker，Oneway 无重试。
>
> 几个高频坑：① 业务异常（Topic 不存在）不要重试；② SendCallback 里别同步发送会死锁；③ 大消息走对象存储；④ NameServer 重启避免空缓存雪崩。
