# RocketMQ 事务消息

> "下单 + 扣库存"跨服务，怎么保证一致？这道题十有八九用 RocketMQ 事务消息。
> 本篇要解决：
> ① 为什么 2PC / TCC 不够用，要用事务消息？事务消息解决的是哪一类一致性？
> ② Half 消息怎么实现"对消费者不可见"的？Broker 内部到底怎么处理？
> ③ 事务回查机制是干嘛的？什么情况下会触发？
> ④ 事务消息能保证强一致吗？局限是什么？

---

## 一、问题背景：分布式事务难在哪

### 1.1 一个典型的跨服务场景

```
[订单服务]              [库存服务]
   │                        │
   ├─ 1. 创建订单            │
   │   (DB.insert)           │
   │                        │
   ├─ 2. 通知扣库存 ─────────►│
   │                        ├─ 3. 减库存 (DB.update)
   │                        │
```

**4 种失败组合**：

| 场景 | 订单 | MQ 通知 | 库存 | 结果 |
| --- | --- | --- | --- | --- |
| ✅ 全成功 | OK | OK | OK | 一致 |
| ❌ 1 后挂 | OK | 没发 | 不变 | 用户付了款没库存扣 |
| ❌ 2 后挂 | OK | OK | 没收到 | 库存系统漏处理 |
| ❌ 3 后挂 | OK | OK | OK | 库存扣了但订单没创建 |

**核心矛盾**：订单 DB 操作 和 MQ 发送 **不能放在同一个事务** 里——一个是 MySQL，一个是 MQ，没有跨系统的本地事务。

### 1.2 已有方案的不足

| 方案 | 一致性 | 性能 | 复杂度 | 局限 |
| --- | --- | --- | --- | --- |
| **2PC（XA）** | 强一致 | 极差 | 高 | 协调器单点；阻塞 |
| **TCC** | 最终一致 | 中 | 极高 | 业务侧实现 try/confirm/cancel 三套接口 |
| **本地消息表** | 最终一致 | 中 | 中 | 业务表多一张表 |
| **RocketMQ 事务消息** | 最终一致 | 高 | 中 | 强依赖 RocketMQ |
| **Saga** | 最终一致 | 中 | 高 | 跨多个服务的补偿链复杂 |

**RocketMQ 事务消息**对应"业务事务 + 一条 MQ 消息"的最简单场景，是工程性价比最高的方案。

## 二、核心设计：half 消息 + 事务回查

### 2.1 整体流程（6 步）

```
[Producer]                          [Broker]                      [Consumer]
    │                                  │                               │
    ├─ 1. 发送 half 消息 ──────────────►│                               │
    │                                  │ 写入 RMQ_SYS_TRANS_HALF_TOPIC │
    │◄────── 2. 发送结果 ───────────────┤                               │
    │                                  │                               │
    ├─ 3. 执行本地事务                  │                               │
    │   (DB insert order)              │                               │
    │                                  │                               │
    ├─ 4. 发送二次确认 ─────────────────►│                               │
    │   (COMMIT / ROLLBACK)            │                               │
    │                                  │ COMMIT → 投递到目标 Topic     │
    │                                  │ ROLLBACK → 删除 half          │
    │                                  │                               │
    │                                  │       消息可见 ──────────────►│
    │                                  │                               ├─ 6. 消费
    │                                  │                               │
    │   （如果 4 没发出去？）           │                               │
    │   ◄──── 5. 事务回查 ─────────────│                               │
    ├─ 反查本地事务状态                 │                               │
    │   返回 COMMIT / ROLLBACK          │                               │
```

### 2.2 关键阶段拆解

**阶段 ①：half 消息（半消息）**

```java
TransactionMQProducer producer = new TransactionMQProducer("group");
producer.setTransactionListener(new MyListener());

// 发送 half 消息
TransactionSendResult result = producer.sendMessageInTransaction(msg, null);
// result.getLocalTransactionState() = COMMIT_MESSAGE / ROLLBACK_MESSAGE / UNKNOWN
```

half 消息的本质：**Broker 收到消息但对消费者不可见**。怎么实现？

```
Broker 收到消息后：
1. 备份原消息的 topic 和 queueId（存到消息属性里）
2. 把 topic 改成 RMQ_SYS_TRANS_HALF_TOPIC
3. 写入 CommitLog（和普通消息一样）
4. ConsumeQueue 索引也建在 RMQ_SYS_TRANS_HALF_TOPIC 下
```

由于 Consumer 没订阅 `RMQ_SYS_TRANS_HALF_TOPIC`，自然消费不到——**这就是"对消费者不可见"的实现**。

**阶段 ②：本地事务**

```java
class MyListener implements TransactionListener {
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try {
            orderService.createOrder(arg);  // 业务事务
            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }
    
    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        // 事务回查时调用
        Order order = orderDao.findByMsgKey(msg.getKeys());
        return order != null ? COMMIT_MESSAGE : ROLLBACK_MESSAGE;
    }
}
```

**阶段 ③：二次确认**

Producer 调用 `endTransaction(...)` 发送二次确认（COMMIT 或 ROLLBACK）：

```
COMMIT：Broker 把 half 消息从 RMQ_SYS_TRANS_HALF_TOPIC 还原回原 topic，写入并刷新 ConsumeQueue
        → Consumer 可见

ROLLBACK：Broker 在 OP_HALF_TOPIC 标记为已取消（half 消息本身仍在 CommitLog，但永远不投递）
```

**阶段 ④：事务回查（兜底）**

如果二次确认没发出去（Producer 进程挂、网络抖动），Broker 看到 half 消息一直没收到 COMMIT/ROLLBACK，会**主动回查**：

```
TransactionalMessageCheckService（Broker 后台线程）
   每 60s 扫一次 RMQ_SYS_TRANS_HALF_TOPIC：
   - 找到超时未确认的 half 消息
   - 通过 producerGroup 找到一个活跃的 Producer
   - 发送 CHECK_TRANSACTION_STATE 请求
   - Producer 调用 checkLocalTransaction 反查本地事务状态
   - 返回 COMMIT / ROLLBACK / UNKNOWN
   
默认最多回查 15 次（transactionCheckMax），仍 UNKNOWN 则丢弃
```

## 三、Broker 内部细节

### 3.1 关键 Topic

| Topic | 用途 |
| --- | --- |
| `RMQ_SYS_TRANS_HALF_TOPIC` | half 消息存放处（消费者看不到）|
| `RMQ_SYS_TRANS_OP_HALF_TOPIC` | 已确认（COMMIT/ROLLBACK）的 half 消息标记 |
| 业务原 topic | COMMIT 后真正的消息所在地 |

### 3.2 怎么判断 half 是否已确认？

Broker 不会原地修改 half 消息（CommitLog 不可变），而是：
1. 收到 COMMIT → 在 OP_HALF_TOPIC 写一条标记（含原 half 的 offset）
2. 后台扫描 HALF_TOPIC 时，与 OP_HALF_TOPIC 对账，跳过已确认的

### 3.3 COMMIT 怎么"还原"消息？

```java
// Broker 端伪代码
void endTransactionCommit(halfMessage) {
    // 从 half 消息属性中读出原始 topic 和 queueId
    String realTopic = halfMessage.getProperty(REAL_TOPIC);
    int realQueueId = Integer.parseInt(halfMessage.getProperty(REAL_QUEUE_ID));
    
    // 构造一条新消息（同 body，同 properties，但 topic 还原）
    MessageExtBrokerInner realMsg = buildRealMessage(halfMessage, realTopic, realQueueId);
    
    // 写入 CommitLog
    putMessageResult = messageStore.putMessage(realMsg);
    
    // 在 OP_HALF_TOPIC 标记 half 已确认
    putHalfConfirmMessage(halfMessage.getQueueOffset());
}
```

注意：COMMIT 后 **CommitLog 里其实有两条消息**——原 half 消息（topic = RMQ_SYS_TRANS_HALF_TOPIC）+ 重新投递的真消息（topic = 业务 topic）。这是 RocketMQ 用追加日志实现"事务"的取舍。

## 四、为什么是最终一致而不是强一致？

### 4.1 强一致 vs 最终一致

```
强一致：所有节点同时看到同样的数据状态（订单创建 = 库存扣减 同时发生）

最终一致：经过一段时间（通常秒级），所有节点达到一致
```

### 4.2 RocketMQ 事务消息的语义

```
Producer 端事务（订单 DB）─── 强一致 ───┐
                                         ├─── 解耦
Consumer 端事务（库存 DB）─── 最终一致 ───┘
```

**Producer 保证**：只要本地事务成功 + COMMIT 发出去，**消息一定送达 Consumer**。
**Consumer 不保证**：消费失败可能重试 16 次，仍失败进 DLQ——库存可能没扣成功。

所以业务侧需要：
- Consumer 必须**幂等**（订单 ID 唯一约束）
- 消费失败要有补偿（重试 + DLQ 监控）
- 极端场景做**对账**（订单表 vs 库存日志，T+1 修正）

### 4.3 局限性

| 局限 | 说明 |
| --- | --- |
| 不支持 Producer 端跨多个数据库的强一致 | 本地事务只是 ProducerListener 里的一段代码，Producer 自己保证 |
| 不支持多消息原子 | 一次只能事务一条消息 |
| 回查依赖 Producer 在线 | Producer 集群必须有人在世 |
| 性能比普通消息差 | 多了一次 half 写入 + 二次确认 RPC |

## 五、对比其他方案

### 5.1 vs 本地消息表

| 维度 | RocketMQ 事务消息 | 本地消息表 |
| --- | --- | --- |
| **业务侵入** | 低（封装在 Producer） | 高（要建表 + 定时任务） |
| **依赖** | 强依赖 RocketMQ | 不依赖 MQ |
| **Producer 挂时** | 回查机制等到 Producer 重启 | 重启后定时任务继续扫 |
| **消息可靠性** | Broker 保障 | 业务侧保障 |
| **典型场景** | 订单创建发消息 | 跨技术栈、有遗留系统 |

### 5.2 vs TCC

```
TCC：Try → Confirm / Cancel
  - 必须改造业务为 3 阶段接口
  - 强一致级别更高
  - 适合金融、支付等场景
  
RocketMQ 事务消息：
  - 业务接口不变
  - 最终一致
  - 适合一般业务
```

### 5.3 vs 2PC（XA）

```
2PC：协调器 + 资源管理器，所有参与者锁定到事务结束
  - 强一致
  - 阻塞 → 性能差
  - 协调器是单点
  - 几乎没人在生产用
  
RocketMQ 事务消息：
  - 异步、不阻塞
  - 最终一致
  - 高性能
```

## 六、Consumer 端的幂等是必须的

```java
@RocketMQMessageListener(topic = "order_created", consumerGroup = "stock_group")
public class StockConsumer implements RocketMQListener<OrderCreatedEvent> {
    
    @Override
    public void onMessage(OrderCreatedEvent event) {
        // ① 幂等：检查是否已处理
        if (stockLogDao.exists(event.getOrderId())) {
            return;  // 已处理，跳过
        }
        
        // ② 业务：扣库存
        stockService.deduct(event.getProductId(), event.getQty());
        
        // ③ 落库：记录处理过
        stockLogDao.insert(new StockLog(event.getOrderId(), ...));
    }
}
```

**幂等手段**：
- 唯一约束（DB unique key）
- Redis SETNX
- 状态机（PENDING → PAID，PAID 状态不能再变 PAID）
- 业务表关联表（去重表）

详见 [重复消费与幂等](./重复消费与幂等.md)。

## 八、生产踩坑

### 8.1 回查接口异常导致消息全部 ROLLBACK

**现象**：上线后所有事务消息都 ROLLBACK，业务下游收不到任何消息。

**根因**：`checkLocalTransaction` 实现里查 DB 抛异常，被框架兜底返回 ROLLBACK。

**修复**：
```java
public LocalTransactionState checkLocalTransaction(MessageExt msg) {
    try {
        return orderDao.exists(msg.getKeys()) ? COMMIT_MESSAGE : ROLLBACK_MESSAGE;
    } catch (Exception e) {
        // ❌ 错：return ROLLBACK_MESSAGE
        // ✅ 对：返回 UNKNOWN，下次回查再判断
        return LocalTransactionState.UNKNOWN;
    }
}
```

### 8.2 Producer 重启导致回查找不到 Producer

**现象**：half 消息超时后 Broker 回查失败，最终被丢弃。

**根因**：Producer 进程重启了，原来的 producerGroup 没有活跃实例。

**修复**：
- Producer 集群部署（多个实例同 group）
- 重启间隔 < 回查超时（默认 10 分钟）

### 8.3 业务事务执行时间过长

**现象**：half 消息回查触发了，但业务事务还在跑，导致 ROLLBACK 然后业务事务又成功了 → 消息丢失。

**根因**：默认 6s 超时太短。

**修复**：
```properties
# Broker 端调大
transactionTimeOut=30000   # 30 秒
```

或者业务侧避免长事务。

### 8.4 没考虑回查时业务还没开始

**现象**：half 消息发出后业务事务还没开始执行，回查时查不到数据 → ROLLBACK。但实际后面业务事务又成功了。

**根因**：half 发送 vs 本地事务执行 之间的窗口期过长。

**修复**：
- half 发送之后**立即同步执行本地事务**（不要异步、不要先做其他事）
- 业务事务必须在 6s 内完成

### 8.5 多消息事务

**现象**：一个业务想发多条消息，希望全部成功或全部失败。

**根因**：RocketMQ 事务消息**只支持单消息事务**。

**修复**：
- 改造业务为单消息（合并 payload）
- 或一条消息触发下游分发到多个 Topic
- 或用 Saga 模式手动补偿

## 九、面试高频追问

**Q1：half 消息为什么"对消费者不可见"？**

Broker 收到 half 消息后，**把 topic 改成 RMQ_SYS_TRANS_HALF_TOPIC**，原始 topic 备份在消息属性里。Consumer 没订阅这个特殊 topic，自然消费不到。COMMIT 后 Broker 把 topic 还原成原 topic，重新写入 CommitLog → 才对消费者可见。

**Q2：为什么需要事务回查？正常情况不是有 COMMIT/ROLLBACK 吗？**

兜底机制。考虑这种情况：
1. Producer 发 half 成功
2. Producer 执行本地事务成功
3. Producer 发 COMMIT 时**进程挂了** ← 关键

此时 half 消息"悬空"——既不能直接 COMMIT（万一本地事务失败了？）也不能 ROLLBACK（万一本地事务成功了？）。所以 Broker 必须主动回查 Producer：你那边的本地事务到底成功了没？

**Q3：事务消息能保证消费成功吗？**

不能。事务消息只保证 Producer 端"本地事务成功 → 消息一定到 Broker"，**Consumer 端的成功不归 Producer 管**。Consumer 消费失败会进重试 Topic，16 次后进 DLQ。所以业务侧必须：
- Consumer 幂等
- 消费失败要补偿
- 监控 DLQ

**Q4：RocketMQ 事务消息和 Kafka 事务消息有什么区别？**

```
Kafka 事务消息：
  - Producer 端事务（多 Topic 多消息原子写入）
  - 消费侧 read_committed 隔离级别
  - 用于 Kafka Streams 的 exactly-once 处理
  - 不解决"业务事务 + MQ 一致性"问题
  
RocketMQ 事务消息：
  - Producer 本地事务 + MQ 消息 一致性
  - 单消息事务
  - 用于业务"下单 + 通知"场景
```

**Q5：half 消息会持久化吗？Broker 重启会怎样？**

会持久化（写在 CommitLog 里，只是 topic 是特殊 topic）。Broker 重启后，TransactionalMessageCheckService 会继续扫描 RMQ_SYS_TRANS_HALF_TOPIC，对超时未确认的 half 触发回查——所以**重启不影响事务消息的可靠性**。

**Q6：Producer 调用 sendMessageInTransaction 之后立即返回了 COMMIT_MESSAGE，但本地事务还没开始执行，可能吗？**

不会。`sendMessageInTransaction` 内部流程是：
1. 同步发送 half 消息
2. 收到 SendResult.OK 后**立即同步调用** `executeLocalTransaction(msg, arg)`
3. 拿到返回值后发送 endTransaction 请求

这三步是同步的。如果 step 2 抛异常，框架自动发 ROLLBACK；如果 step 2 返回了状态，按状态发对应的 endTransaction。

**Q7：如果 ROLLBACK 之前，Consumer 已经"看到"了消息怎么办？**

不会。ROLLBACK 之前消息还在 RMQ_SYS_TRANS_HALF_TOPIC，Consumer 看不到。只有 COMMIT 后才会还原到业务 Topic 让 Consumer 可见。

**Q8：事务消息的吞吐比普通消息差多少？**

差 ~30~50%：
- 多了 half 消息的写入
- 多了二次确认 RPC
- COMMIT 时多了一次"还原 + 重新写入"

所以事务消息不适合极致高吞吐场景，普通消息（或本地消息表）更合适。

## 十、答题模板（60 秒话术）

> RocketMQ 事务消息解决的是 **"业务事务（如下单）+ 发送 MQ 消息"两件事的最终一致性**——比 2PC 性能高、比 TCC 业务侵入低。
>
> 核心是 **half 消息 + 事务回查** 两阶段：
>
> ① 第一阶段 Producer 发 half 消息，Broker 把它的 topic 改成 RMQ_SYS_TRANS_HALF_TOPIC——消费者订阅不到所以看不见。
>
> ② Producer 执行本地事务，成功就发 COMMIT、失败就发 ROLLBACK。COMMIT 时 Broker 还原 topic 写入业务 Topic，消费者可见；ROLLBACK 时 Broker 在 OP_HALF_TOPIC 标记取消。
>
> ③ 如果二次确认丢失（Producer 进程挂、网络抖动），Broker 后台 TransactionalMessageCheckService 每 60s 扫一次 half topic，对超时未确认的消息**主动回查 Producer**——调用 `checkLocalTransaction` 反查本地事务状态，最多回查 15 次。
>
> 注意事项：① Consumer 必须幂等（事务消息不保证 Consumer 端成功） ② 业务事务要快（默认 6s 超时） ③ Producer 集群部署避免回查找不到接收方 ④ checkLocalTransaction 出错应返回 UNKNOWN 而不是 ROLLBACK。
