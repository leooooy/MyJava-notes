# RocketMQ 顺序消息

> 顺序消息是面试"区分背书 vs 真懂"的题。
> 本篇要解决：
> ① 全局顺序为什么实际不可用？为什么大家都用部分顺序？
> ② 生产端怎么把"同语义消息"路由到同一个 Queue？
> ③ 顺序消费用了三把锁，每把锁解决什么问题？
> ④ 顺序消费失败会怎样？为什么会"卡住整个队列"？
> ⑤ Broker 主从切换时顺序性怎么受影响？

---

## 一、什么是顺序消息

### 1.1 定义

| 类型 | 定义 | 实现代价 |
| --- | --- | --- |
| **全局顺序** | 整个 Topic 所有消息严格按发送顺序消费 | **极大**（单 Queue + 单生产者 + 单消费者） |
| **部分顺序** | 同一组业务 ID 的消息按发送顺序消费，不同 ID 之间无序 | 可控 |

### 1.2 为什么全局顺序几乎没人用

```
全局顺序的代价：
① Topic 只能有 1 个 Queue → 失去并发，TPS = 单 Queue 极限 ≈ 几千
② Producer 只能 1 个实例 + Sync 发送 → 单点
③ Consumer 只能 1 个 + 单线程 → 消费速度 = 单线程速度
④ 任意一个 Broker 挂掉，全局停摆
```

实际能撑住的吞吐 < 1000 TPS，**且无任何高可用**。除了 binlog 同步等极少数场景，**业务上全局顺序基本等同"不可用"**。

### 1.3 部分顺序的典型场景

```
订单 ID = 100
  ├─ 创建订单 (100, CREATE)  
  ├─ 支付 (100, PAID)        ◄── 必须按这个顺序消费
  └─ 发货 (100, SHIPPED)

订单 ID = 200
  ├─ 创建订单 (200, CREATE)
  ├─ 支付 (200, PAID)
  └─ 发货 (200, SHIPPED)

→ 100 和 200 之间无所谓顺序，但同一订单内必须有序
```

## 二、生产端：把消息路由到同一 Queue

### 2.1 默认轮询会破坏顺序

```
Topic 有 4 个 Queue，Producer 默认轮询：

(100, CREATE) → Queue-0
(100, PAID)   → Queue-1   ❌ 跑到不同 Queue 了
(100, SHIPPED)→ Queue-2

Consumer 多线程消费 → 顺序无法保证
```

### 2.2 用 MessageQueueSelector 路由

```java
producer.send(msg, new MessageQueueSelector() {
    @Override
    public MessageQueue select(List<MessageQueue> mqs, Message msg, Object arg) {
        Long orderId = (Long) arg;
        int index = (int) (orderId % mqs.size());
        return mqs.get(index);
    }
}, orderId);
```

**关键**：用业务键（orderId）hash 取模 → 同一订单永远到同一 Queue。

### 2.3 必须同步发送

```java
producer.send(msg, selector, orderId);  // ✅ Sync
```

**为什么不能异步？**
- 异步发送的回调时机不确定 → 网络抖动时第二条可能比第一条先到 Broker
- 内部线程池调度也会破坏顺序

### 2.4 集群扩容/缩容会破坏顺序

```
扩容前：4 个 Queue
  orderId 100 → 100 % 4 = Queue-0

扩容后：8 个 Queue（原 4 + 新增 4）
  orderId 100 → 100 % 8 = Queue-4   ❌ 落到了不同 Queue
```

期间发的消息 100, CREATE 在 Queue-0，PAID 在 Queue-4——顺序破坏。

**解法**：
- 缩容/扩容选业务低峰期
- 用一致性哈希 selector（变动小）
- 业务侧补偿（消费时检查 status 是否合理）

### 2.5 Broker 故障会破坏顺序

```
原始：Queue-0 (在 broker-a), Queue-1 (在 broker-b)
broker-a 挂了：
  orderId 100 % 1 = Queue-0   但 Queue-0 不可用！
  fallback：发到 Queue-1
  
但之前在 Queue-0 排队的消息怎么办？
  Slave 还能消费（如果是 SYNC_MASTER），但新消息已经分到 Queue-1
  → 同一订单的旧消息在 Queue-0 老消息在 Queue-1，乱序
```

**这是顺序消息最大的坑**：**严格的顺序性 + 高可用 是矛盾的**。所以"顺序消息"在生产中往往是"**99.9% 顺序 + 业务侧容忍少量短暂乱序**"。

## 三、消费端：MessageListenerOrderly + 三把锁

### 3.1 两种 Listener

```java
// 并发消费（不保证顺序）
consumer.registerMessageListener(new MessageListenerConcurrently() {
    public ConsumeConcurrentlyStatus consumeMessage(...) { ... }
});

// 顺序消费
consumer.registerMessageListener(new MessageListenerOrderly() {
    public ConsumeOrderlyStatus consumeMessage(...) { ... }
});
```

只用 `MessageListenerOrderly` 才能保证顺序消费。

### 3.2 顺序消费仍是多线程

很多人以为"顺序消费 = 单线程"。**错。**

```
顺序消费实际是：消费线程池 + 加锁串行化
- 仍是 20 线程的线程池（默认）
- 但同一时刻同一 Queue 只能有一个线程在处理
- 不同 Queue 的消息可以并发处理
```

→ 多 Queue 仍能并发，但单 Queue 内串行。

### 3.3 三把锁详解

**锁 1：Broker 端的分布式锁**

```
作用：保证同一 ConsumerGroup 内同一 Queue 只被一个 Consumer 客户端持有
实现：Broker 端 ConcurrentMap<group, ConcurrentMap<MessageQueue, LockEntry>>
申请：消费者负载均衡时（updateProcessQueueTableInRebalance）
过期：Broker 端 60s 过期，Client 端每 20s 续锁
```

为什么需要？因为 Rebalance 时如果两个 Consumer 同时认为自己负责某 Queue，会同时消费 → 乱序。Broker 锁强制只有一个客户端能拿到。

**锁 2：MessageQueue 本地 synchronized 锁**

```java
// ConsumeMessageOrderlyService 消费任务
ConsumeRequest run() {
  Object lock = MessageQueueLock.fetchLockObject(messageQueue);
  synchronized (lock) {
    // 同一 MessageQueue 同一时刻只有一个线程进入
    messageListener.consumeMessage(msgs, ctx);
  }
}
```

为什么需要？因为消费用线程池（默认 20 线程），同一 Queue 可能被多个线程拉取消费——这把锁强制同 Queue 串行。

**锁 3：ProcessQueue 的 ReentrantLock（consumeLock）**

```
作用：防止"消费过程中" Queue 被 Rebalance 解绑给其他客户端
场景：
  - C1 正在消费 Queue-0 的一批消息（已拉取 32 条）
  - 此时新 Consumer C2 加入，Rebalance 后 Queue-0 被分给 C2
  - 如果 C1 立刻释放 Broker 锁，C2 立刻拿到 Queue-0 开始消费
  - 但 C1 还没提交 offset，C2 会从老的 offset 重新拉 → 重复 + 乱序
  
解法：C1 释放 Broker 锁前，必须先获取 ProcessQueue.consumeLock
      consumeLock 在消费业务逻辑期间是被持有的
      → C1 释放失败（锁住了）→ 本次不释放，等下次 Rebalance 周期再尝试
      → 期间 C1 必须把当前批次消费完 + 提交 offset
```

### 3.4 三把锁的协作

```
┌────────────────────────────────────────────────────┐
│ Rebalance 周期到达                                 │
│   ↓                                                │
│ Consumer A 检查负载分配                            │
│   ↓                                                │
│ ┌──────────── 锁 1: Broker 端分布式锁 ───────────┐│
│ │ 申请 Queue-0 的锁                              ││
│ │   成功 → 创建 ProcessQueue 启动消费             ││
│ │   失败 → 跳过这个 Queue                        ││
│ └────────────────────────────────────────────────┘│
│                                                    │
│ ┌──────────── 锁 2: MessageQueue synchronized ───┐│
│ │ 拉取消息 → 提交到线程池                         ││
│ │ 多个线程争 messageQueue 锁                      ││
│ │   一个线程拿到 → 进入消费业务                   ││
│ └────────────────────────────────────────────────┘│
│                                                    │
│ ┌──────────── 锁 3: ProcessQueue.consumeLock ────┐│
│ │ 业务消费期间持有                               ││
│ │   保护 Rebalance 不会强行解绑                   ││
│ └────────────────────────────────────────────────┘│
└────────────────────────────────────────────────────┘
```

## 四、顺序消费的失败处理

### 4.1 失败原地重试

```java
public ConsumeOrderlyStatus consumeMessage(List<MessageExt> msgs, ConsumeOrderlyContext ctx) {
    try {
        process(msgs);
        return ConsumeOrderlyStatus.SUCCESS;
    } catch (Exception e) {
        // 不能像并发消费那样进入 retry topic（破坏顺序）
        return ConsumeOrderlyStatus.SUSPEND_CURRENT_QUEUE_A_MOMENT;
    }
}
```

返回 `SUSPEND_CURRENT_QUEUE_A_MOMENT` 后：
- 当前消息**不进重试 Topic**（因为重试会乱序）
- 在原 Queue **原地重试**（每秒一次）
- 默认重试 `Integer.MAX_VALUE` 次（直到成功）

### 4.2 这会卡住整个 Queue

```
[Queue-0 内容]
  msg-1 (orderId=100, CREATE)  ← 正在重试，永远失败
  msg-2 (orderId=100, PAID)    ← 阻塞中
  msg-3 (orderId=200, CREATE)  ← 阻塞中（虽然 200 跟 100 无关）
  msg-4 (orderId=200, PAID)    ← 阻塞中
  ...
```

因为顺序消费同 Queue 内必须严格按 offset 顺序，前面的不消费完后面的不能跳过。**任何一条永久失败 = 整个 Queue 卡死**。

### 4.3 防卡死方案

```java
consumer.setMaxReconsumeTimes(5);  // 显式限制
```

超过限制后：
- 消息丢弃（业务可能已经卡了 5 秒不可恢复）
- 或进入 DLQ
- 同时业务必须监控告警（卡 Queue 必须 P0 级别响应）

**关键**：业务代码本身要做好异常分类——
- **可重试错误**（DB 连接断开、第三方接口 5xx）→ 返回 SUSPEND
- **不可重试错误**（参数错误、业务规则不满足）→ 记录日志 + 返回 SUCCESS（跳过）

绝对不能让代码 bug 卡死整条 Queue。

## 五、其他 MQ 的顺序消息对比

| MQ | 顺序粒度 | 实现方式 | 故障容忍 |
| --- | --- | --- | --- |
| **RocketMQ** | Queue 内严格 | 三把锁 + 同步发送 | Broker 主从切换可能短暂乱序 |
| **Kafka** | Partition 内 | 单 Partition + 单 Consumer | Broker 宕机 + 副本切换可能乱序 |
| **RabbitMQ** | Queue 内 | 单 Queue 单 Consumer 单线程（性能极差）| - |

**共同点**：都靠"分区内有序 + 业务侧路由"实现部分顺序。

## 七、生产踩坑

### 7.1 Producer 用了异步发送破坏顺序

**现象**：同一订单的消息偶尔乱序消费。

**根因**：开发用了 `producer.send(msg, callback)` 异步——内部线程池可能让第二条比第一条先到。

**修复**：顺序消息**必须 Sync 发送**：
```java
SendResult result = producer.send(msg, selector, orderId);  // 不要 callback
```

### 7.2 顺序消费里抛异常没处理

**现象**：某条消息因为 NullPointerException 失败，整个 Queue 卡死，消息堆积百万。

**根因**：业务代码没 catch，默认行为返回 SUSPEND，原地重试 Integer.MAX_VALUE 次。

**修复**：
```java
public ConsumeOrderlyStatus consumeMessage(List<MessageExt> msgs, ConsumeOrderlyContext ctx) {
    for (MessageExt msg : msgs) {
        try {
            process(msg);
        } catch (BusinessException e) {
            // 业务错误：跳过，继续后续消息
            log.error("biz error, skip", e);
        } catch (Exception e) {
            // 系统错误：重试有限次数
            if (msg.getReconsumeTimes() < 5) {
                return SUSPEND_CURRENT_QUEUE_A_MOMENT;
            }
            // 超过 5 次：丢入 DLQ + 告警
            sendToDlq(msg);
        }
    }
    return SUCCESS;
}
```

### 7.3 Topic 扩容 Queue 数后乱序

**现象**：扩容当天大量订单状态错乱。

**根因**：`orderId % oldQueueCount` ≠ `orderId % newQueueCount`，部分订单的消息分到了新旧两个 Queue。

**修复**：
- 不要在业务高峰期扩容
- 扩容前停 Producer，让现有消息消费完，再扩容，再启动 Producer
- 或用一致性哈希策略减少影响范围

### 7.4 Broker Master 挂消息乱序

**现象**：Broker-A 故障，订单状态不一致。

**根因**：Broker-A 上的 Queue-0 写入暂停，Producer 自动 fallback 到 Queue-1（其他 Broker），同一订单的新消息发到 Queue-1，旧消息还在 Queue-0 上等 Slave 消费。

**修复**：
- 业务接受短暂乱序（恢复后由业务对账兜底）
- 或用 Dledger（自动选主，主从一致）

### 7.5 Rebalance 期间重复消费

**现象**：发布期间订单"支付"状态被处理了 2 次。

**根因**：发布触发 Rebalance，老 Consumer 已拉但未提交 offset 的消息被新 Consumer 重新拉取。

**修复**：业务端必须幂等（订单状态机：PAID 状态不能再次变 PAID）。

## 八、面试高频追问

**Q1：为什么 RocketMQ 用三把锁，不能简化？**

每把锁解决一个独立问题：
- 锁 1（Broker 分布式锁）：解决"多个 Consumer 客户端"竞争同一 Queue
- 锁 2（MessageQueue synchronized）：解决"单 Consumer 内多个线程"消费同一 Queue
- 锁 3（ProcessQueue consumeLock）：解决"消费过程中" Queue 被 Rebalance 解绑

少任一把都会出问题。

**Q2：顺序消费失败为什么不能用重试 Topic？**

重试 Topic 是延迟 Topic（10s/30s/1min...），消息会**晚于后续消息**到达——后续消息已经被消费过去了，重试消息再来就乱序了。所以顺序消费只能**原地阻塞重试**。

**Q3：单 Queue 单消费者还要锁吗？**

要。即使单 Queue 单 Consumer，**消费用的是线程池**（20 线程默认），同一 Queue 拉到的多批消息可能被分到不同线程并行处理 → 仍需要锁 2 串行化。

**Q4：顺序消息能保证 ms 级延迟吗？**

不能。三把锁 + 同步发送 + 单 Queue 串行消费 → 通常延迟 10~50ms，业务高峰期可能上升到秒级。极致低延迟和严格顺序是矛盾的。

**Q5：怎么定 Queue 数量？**

```
Queue 数 ≥ 并发业务 ID 基数 / 单 Queue 处理能力

例：日均 100w 订单，单 Queue 能处理 1000 TPS
   → 至少 100w / 86400 / 1000 ≈ 12 个 Queue
   → 但要考虑峰值，建议 32 个

太少：单 Queue 压力大、横向扩展受限
太多：分布到多 Broker，Broker 故障影响范围大
```

**Q6：Kafka 和 RocketMQ 顺序消息的差异？**

```
Kafka：
  - Partition 内有序
  - Producer 用 key 路由到 Partition
  - 但 Broker 切换 Leader 时可能丢消息 → 乱序更严重
  - Consumer 单 Partition 单线程消费

RocketMQ：
  - Queue 内有序
  - Producer 用 MessageQueueSelector 路由
  - 三把锁保证消费端同 Queue 串行
  - SYNC_MASTER 配置下主从一致，故障切换不丢
```

**Q7：业务侧怎么补偿短暂乱序？**

订单状态机 + 时间戳校验：
```java
public void handlePaidEvent(Order order) {
    Order existing = dao.findById(order.getId());
    if (existing.getStatus().ordinal() >= Order.PAID.ordinal()) {
        return;  // 后到的消息发现已是更后的状态，跳过
    }
    if (existing.getUpdatedAt() > order.getUpdatedAt()) {
        return;  // 时间戳更新，跳过
    }
    dao.updateStatus(order.getId(), PAID);
}
```

## 九、答题模板（60 秒话术）

> 顺序消息分**全局顺序**和**部分顺序**。全局顺序需要单 Queue + 单 Producer + 单 Consumer，性能极差，业务上几乎不用；部分顺序是常用方案——同一业务键路由到同一 Queue。
>
> **生产端**用 `MessageQueueSelector` 按业务键 hash 取模选 Queue，**必须用同步发送**。Topic 扩缩容、Broker 故障会短暂破坏顺序，业务侧靠状态机 + 时间戳兜底。
>
> **消费端**用 `MessageListenerOrderly` 启用顺序消费，**底层是三把锁**：Broker 分布式锁保证同 Queue 同组只一个客户端持有；MessageQueue 本地 synchronized 让多线程串行；ProcessQueue 的 consumeLock 保护消费过程中不被 Rebalance 解绑。
>
> **关键风险**：顺序消费失败默认原地重试 Integer.MAX_VALUE 次，会**卡死整个 Queue**。生产必须显式 `setMaxReconsumeTimes`，并对业务异常分类处理——业务错误 catch 跳过，系统错误有限重试。
