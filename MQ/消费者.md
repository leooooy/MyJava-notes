# RocketMQ 消费者

> Consumer 是 RocketMQ 整个体系最复杂的部分——拉模式、长轮询、Rebalance、消费进度、重试、死信，全都在这边。
> 本篇要解决：
> ① Push 模式底层是 Pull，长轮询到底怎么实现？
> ② Rebalance 是什么？什么时候触发？怎么避免抖动？
> ③ 消费失败重试 16 次，时间间隔为什么是这套？什么是死信队列？
> ④ 消费 offset 是 Client 持久化还是 Broker 持久化？
> ⑤ 集群消费 vs 广播消费具体差异是什么？

---

## 一、消费者启动流程

```
DefaultMQPushConsumer.start()
       │
       ▼
DefaultMQPushConsumerImpl.start()
       │
       ├─► [1] copySubscription（订阅关系，包含重试 Topic）
       ├─► [2] changeInstanceNameToPID
       ├─► [3] 获取 MQClientInstance（与 Producer 共用）
       ├─► [4] 注册 Consumer 到 Instance
       ├─► [5] 启动 OffsetStore
       │       - 集群消费：RemoteBrokerOffsetStore（offset 存 Broker）
       │       - 广播消费：LocalFileOffsetStore（offset 存本地文件）
       ├─► [6] 启动 ConsumeMessageService
       │       - 并发消费：ConsumeMessageConcurrentlyService
       │       - 顺序消费：ConsumeMessageOrderlyService
       ├─► [7] mQClientFactory.start()
       │       │
       │       ├─ 启动 PullMessageService（拉消息线程，全局唯一）
       │       ├─ 启动 RebalanceService（每 20s 一次重平衡）
       │       ├─ 定时任务：拉路由、心跳、清理失联 Broker
       │
       └─► sendHeartbeatToAllBrokerWithLock（首次心跳）
```

**关键点**：
- `PullMessageService` **全 JVM 一个**——一个线程负责所有 Consumer 的消息拉取
- `ConsumeMessageService` 是**消费线程池**，每个 Consumer 独立（默认 20 线程）
- 拉与消费完全异步——拉到就丢线程池，立即去拉下一批

## 二、Push 模式：长轮询的真相

### 2.1 表面上是 Push，底层是 Pull

```
Consumer                              Broker
   │
   │── Pull Request ──────────────────►
   │                                  │
   │                                  ├─ 有新消息？
   │                                  │   是 → 立即返回
   │                                  │   否 → hold 住 15s
   │                                  │
   │                                  │   期间新消息到达 → 立即唤醒
   │                                  │   超时（15s） → 返回 EMPTY
   │                                  │
   │◄────── Pull Response ────────────│
   │
   │── 立即下一次 Pull Request ────────►
```

### 2.2 服务端 hold 机制

```java
// PullMessageProcessor 处理 Pull 请求（伪代码）
GetMessageResult result = messageStore.getMessage(...);

if (result.getStatus() == NO_MESSAGE_IN_QUEUE) {
  // 没消息，hold 住请求
  PullRequest pullRequest = new PullRequest(channel, request, ...);
  pullRequestHoldService.suspendPullRequest(topic, queueId, pullRequest);
  return null;  // 不立即响应
}

// 后台线程
class PullRequestHoldService {
  void notifyMessageArriving(topic, queueId, maxOffset) {
    // 新消息到达，找出所有 hold 的 Pull 请求，立即响应
    List<PullRequest> requests = pullRequestTable.get(topic + "@" + queueId);
    for (PullRequest req : requests) {
      executePullRequestImmediately(req);  // 唤醒
    }
  }
}
```

**核心参数**：
```properties
# Broker 端
longPollingEnable=true             # 默认 true
shortPollingTimeMills=1000         # 关闭长轮询时的轮询间隔
```

### 2.3 为什么不真正实现 Push？

| 真 Push | 长轮询模拟 Push |
| --- | --- |
| 服务端主动推送 | 客户端定期拉取 |
| 推太快压垮客户端（无流控） | ✅ 客户端自主控速 |
| 实现复杂（要维护客户端状态） | ✅ 服务端无状态 |
| 客户端必须暴露端口接收推送 | ✅ 单向 TCP 长连接 |
| 客户端断网重连复杂 | ✅ 重新发起 Pull 即可 |

**真 Push 的核心问题是流控**——一旦消息生产远快于消费速度，客户端会被打爆。长轮询把"什么时候要消息"的控制权交给客户端，反而更稳。

## 三、Rebalance：消费者重平衡

### 3.1 什么时候触发？

```
- 消费者启动 / 停止
- 消费者上下线（心跳超时被剔除）
- Topic 增加 / 减少 Queue
- 订阅关系变更
- 周期性重试（默认 20s 一次，确保最终一致）
```

### 3.2 分配策略（AllocateMessageQueueStrategy）

**默认：平均分配（AllocateMessageQueueAveragely）**

```
8 个 Queue，3 个 Consumer：
  C1 → Q0, Q1, Q2
  C2 → Q3, Q4, Q5
  C3 → Q6, Q7
```

**其他策略**：
- `AllocateMessageQueueAveragelyByCircle` — 轮询分配（C1→Q0,Q3,Q6；C2→Q1,Q4,Q7...）
- `AllocateMessageQueueByMachineRoom` — 按机房就近
- `AllocateMessageQueueConsistentHash` — 一致性哈希（变动小）
- `AllocateMessageQueueByConfig` — 配置文件指定

### 3.3 Rebalance 时序

```
[Consumer A]                    [Broker]                    [Consumer B 新加入]
     │                              │                                │
     │ 心跳带消费者列表              │                                │
     ├─ HEART_BEAT ────────────────►│                                │
     │                              │◄────── HEART_BEAT ─────────────┤
     │                              │ （现在知道有 A 和 B）          │
     │                              │                                │
     │ 20s 后触发 Rebalance（本地） │                                │
     │ getConsumerList(group)       │                                │
     ├─ GET_CONSUMER_LIST_BY_GROUP ►│                                │
     │◄── 返回 [A, B] ──────────────┤                                │
     │                              │                                │
     │ 用 AllocateMessageQueue 算法 │                                │
     │ 重新分配                      │                                │
     │                              │                                │
     │ 释放老的 Queue（停止 Pull）  │                                │
     │ 启动新的 Queue 的 Pull       │                                │
```

**注意**：Rebalance 是**消费者本地决策**——每个 Consumer 自己算自己应该负责哪些 Queue（同样的算法 + 同样的输入 → 同样的结果）。Broker 只提供 Consumer 列表。

### 3.4 Rebalance 代价

| 维度 | 影响 |
| --- | --- |
| 消费暂停 | Queue 切换瞬间该 Queue 暂停拉消息 |
| 重复消费 | 老 Consumer 已拉但未提交 offset 的消息会被新 Consumer 再消费 |
| 抖动 | 频繁变动（如 Consumer 频繁重启）→ 频繁 Rebalance → 吞吐抖动 |

**优化**：
- Consumer 数量 = Queue 数量的 **整除关系**（避免分配不均）
- 不要频繁滚动重启（间隔 ≥ 30s）
- 用一致性哈希策略减少变动影响

## 四、消费模式：集群 vs 广播

### 4.1 集群消费（CLUSTERING，默认）

```
Topic[Q0,Q1,Q2,Q3]  ──►  ConsumerGroup-A
                          ├─ C1: 消费 Q0, Q1
                          ├─ C2: 消费 Q2
                          └─ C3: 消费 Q3
                          
每条消息只被组内 1 个 Consumer 消费
offset 由 Broker 持久化
```

### 4.2 广播消费（BROADCASTING）

```
Topic[Q0,Q1,Q2,Q3]  ──►  ConsumerGroup-A
                          ├─ C1: 消费 Q0, Q1, Q2, Q3 (全量)
                          ├─ C2: 消费 Q0, Q1, Q2, Q3 (全量)
                          └─ C3: 消费 Q0, Q1, Q2, Q3 (全量)
                          
每条消息所有 Consumer 都收到
offset 存本地文件（${user.home}/.rocketmq_offsets/...）
```

### 4.3 对比

| 维度 | 集群 | 广播 |
| --- | --- | --- |
| 一条消息消费几次 | 1 次（组内任 1 个） | N 次（每个 Consumer 一次）|
| offset 存哪 | Broker 端 | Consumer 本地文件 |
| 失败重试 | ✅ 支持（消息回 Broker） | ❌ 不支持 |
| 典型场景 | 业务消息 | 本地缓存刷新、多副本通知 |

**广播消费坑**：offset 存本地，**Consumer 重启 + 删除本地文件 = 从最新位置消费**，老消息全丢。

## 五、消费失败重试

### 5.1 集群消费的重试机制

消费返回 `RECONSUME_LATER` 时，Broker 把消息重新投递到 **重试队列**（`%RETRY%ConsumerGroup`），按延迟级别消费：

```
消费失败次数 → 延迟时间
   1 次  →  10 秒
   2 次  →  30 秒
   3 次  →  1 分钟
   4 次  →  2 分钟
   5 次  →  3 分钟
   ...
   16 次 →  2 小时
   17 次 →  进入死信队列（%DLQ%ConsumerGroup）
```

**注意**：第 1~16 次共 ~46 小时，超过 16 次后消息进入 DLQ，**死信队列默认不被消费**——业务方需要订阅 DLQ Topic 单独处理。

### 5.2 重试 Topic 的实现

```
1. Consumer 返回 RECONSUME_LATER
2. Broker 把消息原始 Topic 改成 %RETRY%MyConsumerGroup
3. 按 delayLevel 投递到延迟队列（SCHEDULE_TOPIC_XXXX）
4. 时间到了，从延迟队列移到 %RETRY%MyConsumerGroup
5. Consumer 自动订阅了这个 retry topic，消费
6. 消费成功 → ACK；继续失败 → 累计 reconsumeTimes，下一档延迟
```

### 5.3 自定义重试次数

```java
consumer.setMaxReconsumeTimes(5);  // 最多重试 5 次（默认 16）
```

### 5.4 顺序消费的重试不一样

顺序消费失败不进入 retry topic，而是**原地阻塞重试**（避免乱序）：
- 每秒重试一次
- 默认重试 `Integer.MAX_VALUE` 次（直到成功）
- **会卡住整个 Queue**——必须做好异常处理 + 监控告警

## 六、消费 offset 管理

### 6.1 集群消费：远程持久化

```java
// RemoteBrokerOffsetStore
class RemoteBrokerOffsetStore {
  ConcurrentMap<MessageQueue, AtomicLong> offsetTable;  // 本地缓存
  
  void persistAll(Set<MessageQueue> mqs) {
    // 每 5s 把缓存的 offset 上报到 Broker
    for (MessageQueue mq : mqs) {
      updateConsumeOffsetToBroker(mq, offsetTable.get(mq).get());
    }
  }
}
```

**关键**：
- offset **本地缓存 + 异步上报**（每 5s）
- Broker 持久化到 `consumerOffset.json`
- Consumer 重启时从 Broker 拉最新 offset

### 6.2 提交时机

```
[拉到 32 条消息]
     │
     ▼
[ProcessQueue 缓存这 32 条]
     │
     ▼
[消费线程池处理]
     │
     │ 处理完成（成功）→ ProcessQueue.removeMessage
     │
     ▼
[ProcessQueue.commit() 返回最小 offset]
     │
     ▼
[updateOffset 到本地缓存]
     │
     ▼
[每 5s 异步上报 Broker]
```

**注意**：commit 的是 **ProcessQueue 中已消费消息的最小 offset**——保证了"提交的 offset 之前的消息全部消费完"。

### 6.3 重启后会重复消费吗？

可能。因为 offset 是异步上报（每 5s），重启时可能丢失最近 5s 的 offset 更新——这部分消息会被重复消费。

**所以消费必须幂等。**

## 八、生产踩坑

### 8.1 消息消费很慢，吞吐上不去

**排查路径**：
1. **Consumer 数量 < Queue 数量？** → 加 Consumer
2. **单条消息处理慢？** → 看业务代码，加 `consumeThreadMax`
3. **消费线程池满？** → JStack 看是否锁/IO 阻塞
4. **拉的批量太小？** → 调大 `pullBatchSize`
5. **Broker 还没生成 ConsumeQueue？** → 看 `dispatchBehindBytes` 监控

### 8.2 Rebalance 抖动导致重复消费

**现象**：发布期间业务收到大量重复消息。

**根因**：滚动重启 → 多次 Rebalance → 老 Consumer 已拉但未提交 offset → 新 Consumer 重新拉 = 重复。

**修复**：
- 业务幂等（必须）
- 优雅停机：`consumer.shutdown()` 会主动同步 offset
- 滚动间隔 ≥ Rebalance 周期（20s）

### 8.3 死信队列堆积无人处理

**现象**：DLQ Topic 堆积几万条，业务一无所知。

**根因**：DLQ 不会自动通知，需要业务方主动订阅。

**修复**：
- 监控所有 ConsumerGroup 的 DLQ 堆积量
- 创建专门的 DLQ 消费者打告警 + 入库分析
- 超过阈值（如 100 条/天）触发人工介入

### 8.4 顺序消费一直卡住

**现象**：某个 Queue 完全不消费，监控发现一直在重试同一条消息。

**根因**：顺序消费默认重试 `Integer.MAX_VALUE` 次，遇到代码 bug 永远卡住。

**修复**：
```java
consumer.setMaxReconsumeTimes(5);  // 显式限制
// 在 ConsumeOrderlyContext 中也可以 setSuspendCurrentQueueTimeMillis
```
失败次数超过限制后丢弃 / 进入 DLQ。

### 8.5 Push Consumer 内存暴涨

**现象**：Consumer 内存持续增长，最终 OOM。

**根因**：消费速度跟不上拉取速度，ProcessQueue 缓存的消息越积越多。

**修复**：
```java
consumer.setPullThresholdForQueue(500);     // 默认 1000，调小
consumer.setPullThresholdSizeForQueue(50);  // 默认 100MB
```
触发流控后 Consumer 暂停 Pull 50ms。

### 8.6 拉模式 Consumer 卡死不消费

**现象**：使用 `DefaultMQPullConsumer`（5.0 已 deprecated），偶尔不消费。

**根因**：拉模式需要业务自己维护 offset、自己拉、自己处理。容易写错。

**修复**：除非有特殊需求，**永远用 Push 模式**（或 `LitePullConsumer`），把 offset 管理交给框架。

## 九、面试高频追问

**Q1：Push 模式真的是服务端推吗？**

不是。底层是**长轮询的 Pull**：Consumer 发起 Pull 请求，Broker 没新消息时 hold 住请求最多 15s 不返回；新消息到达立即唤醒推送。

为什么不真 Push？因为 Push 没有流控——Broker 推太快客户端会被打爆。长轮询把控制权交给客户端，更稳。

**Q2：Rebalance 是 Broker 协调还是 Client 自己算？**

**Client 自己算**。Broker 只负责告诉每个 Consumer "组内有哪些活跃 Consumer"。每个 Consumer 拿到列表后用相同的 `AllocateMessageQueueStrategy` 算法算自己的负责区间——只要算法和输入一致，结果就一致。

这个设计的好处是 **Broker 完全无状态**，不需要维护 Consumer 的分配关系。

**Q3：消费完成是怎么通知 Broker 的？是每条消息都 ACK 吗？**

不是每条 ACK。流程是：
1. Consumer 消费成功 → 在 ProcessQueue 中移除该消息
2. ProcessQueue 取出当前最小未消费 offset
3. 更新到本地 offsetTable（内存）
4. 每 5s 异步上报 Broker（批量提交）
5. Broker 持久化到 `consumerOffset.json`

所以**最近 5s 的 offset 是不持久的**，Consumer 异常重启会重复消费这部分——必须靠业务幂等。

**Q4：消费失败重试 16 次的逻辑是怎么实现的？**

Broker 把失败消息改 Topic 为 `%RETRY%ConsumerGroup`，再投递到延迟队列（按 delayLevel）。延迟时间到了再投递回 retry topic，Consumer 自动订阅了 retry topic 所以会再次拉到。重试次数累计在消息属性 `RECONSUME_TIMES` 里。

第 17 次失败 → 投递到 `%DLQ%ConsumerGroup`（死信队列），不会再尝试。

**Q5：顺序消费的重试和并发消费一样吗？**

**完全不一样**。
- 并发消费：失败的消息进 retry topic，按延迟级别后续重投，**不阻塞队列**
- 顺序消费：失败**原地重试**（每秒一次），**阻塞整个 Queue**——因为如果跳过当前消息处理后面的，就违反顺序性了

所以顺序消费遇到不可恢复的错误（代码 bug）会卡死，必须设置 `maxReconsumeTimes`。

**Q6：广播消费的 offset 为什么存本地？**

因为广播消费是 N 个 Consumer 各自消费全量——每个 Consumer 都是独立的"游标"，没法在 Broker 上统一存。所以 offset 存在 `${user.home}/.rocketmq_offsets/...`。

**坑**：换机器或删本地文件 → 从 `CONSUME_FROM_LAST_OFFSET` 开始 → 老消息全丢。

**Q7：怎么防止消费抖动（频繁 Rebalance）？**

```
1. Consumer 数量稳定，不要短时间频繁启停
2. 用 AllocateMessageQueueConsistentHash（一致性哈希）减少变动影响
3. Topic Queue 数量 = Consumer 实例数的整数倍
4. 优雅停机（consumer.shutdown 触发主动 offset 提交）
5. 监控 RebalanceImpl 的 changed 日志频率
```

**Q8：DefaultMQPushConsumer 和 DefaultLitePullConsumer 区别？**

- `DefaultMQPushConsumer`：推模式（长轮询），框架自动管理 Pull/消费/offset，最常用
- `DefaultLitePullConsumer`：4.6+ 引入的拉模式简化版，**业务自己 poll() 拿消息**，类似 Kafka Consumer，offset 仍由框架自动提交（也可手动）
- `DefaultMQPullConsumer`：5.0 已 deprecated，要业务管理 offset，麻烦不推荐

## 十、答题模板（60 秒话术）

> RocketMQ Consumer 启动后会做几件事：① 注册 Listener（并发或顺序）② 启动 OffsetStore（集群消费存 Broker、广播消费存本地文件）③ 启动 PullMessageService 和 RebalanceService。
>
> **Push 模式底层是长轮询的 Pull**——Consumer 发请求，Broker 没消息就 hold 住请求最多 15s，新消息到了立即唤醒；这样既有 Push 的实时性又能客户端流控。
>
> **Rebalance 是客户端自己算**：每 20s 一次，用相同算法（默认平均分配）算自己负责哪些 Queue。Consumer 数量 = Queue 数量的整数倍最理想，避免分配不均。
>
> **offset 是异步提交**：每 5s 上报 Broker，所以消费必须幂等——重启会重复消费最近 5s。
>
> **消费失败的重试**：并发消费走重试 Topic 按延迟级别 16 次重试，第 17 次进死信队列；顺序消费原地阻塞重试默认 Integer.MAX_VALUE 次，必须设上限避免卡死。
