# 循环依赖

> Spring 三大经典面试题之一。这道题的"区分度"在两个地方：
> ① 能不能讲清 **三级缓存为什么要三级，二级缓存解决不了什么**
> ② 能不能讲清 **构造器循环依赖、prototype 循环依赖、`@Async` 循环依赖** 各自为什么解不了
> 答得出第①和第②的，基本就稳了。

---

## 一、什么是循环依赖

```
A 依赖 B，B 又依赖 A          → 二者循环
A → B → C → A                → 三者循环
A 依赖自身                    → 自循环
```

代码层面：

```java
@Service
public class A {
    @Autowired private B b;          // A 要 B
}

@Service
public class B {
    @Autowired private A a;          // B 要 A
}
```

**为什么这是个问题**：Spring 创建 A 时发现要先创建 B；创建 B 时发现要先创建 A。如果没有任何机制，无限递归，栈溢出。

> **为什么单元测试 `new A()` 没问题**：因为 `new` 出来的是空对象，Java 的对象引用只要拿得到就能传递，**字段是 null 或半成品都不影响传递**。Spring 解循环依赖正是利用这一点：先把"半成品"暴露出去。

---

## 二、Spring 在啥前提下才能解

不是所有循环依赖都解得了，必须同时满足：

| 条件 | 为什么 |
| --- | --- |
| 单例 scope（`singleton`） | prototype 不缓存，没法提前曝光 |
| **属性注入** 或 **setter 注入** | 构造器注入时对象都还没 new 出来 |
| 没有被 `@Async` 等"二次代理" | 否则代理对象与曝光的早期对象不一致 |
| `allowCircularReferences = true` | Spring Boot 2.6+ 默认改为 false |

## 三、三级缓存

```java
public class DefaultSingletonBeanRegistry {
    /** 一级：完全初始化好的 bean */
    private final Map<String, Object> singletonObjects 
        = new ConcurrentHashMap<>(256);
    
    /** 二级：提前曝光的"早期引用"（可能是原始对象，也可能是代理对象） */
    private final Map<String, Object> earlySingletonObjects 
        = new ConcurrentHashMap<>(16);
    
    /** 三级：ObjectFactory，调 getObject() 才会按需生成早期引用（含 AOP 代理决策） */
    private final Map<String, ObjectFactory<?>> singletonFactories 
        = new HashMap<>(16);
}
```

### 3.1 三个缓存的"分工"

```
        【三级】singletonFactories               【二级】earlySingletonObjects        【一级】singletonObjects
        ─────────────────────────                ─────────────────────────             ──────────────────────
         存：ObjectFactory                        存：早期引用（原始 / 代理）           存：完整 bean
         作用：延迟决策"是否要代理"                 作用：缓存早期引用避免重复代理         作用：最终成品
         填入时机：实例化后立即                     填入时机：第一次调 getObject 后        填入时机：完整生命周期完成后
         移除时机：进二级时                         移除时机：进一级时                     移除时机：bean 被销毁
```

### 3.2 `getSingleton` 流程（解循环依赖入口）

```java
protected Object getSingleton(String beanName, boolean allowEarlyReference) {
    // 1. 先看一级缓存（成品）
    Object singletonObject = this.singletonObjects.get(beanName);
    if (singletonObject == null && isSingletonCurrentlyInCreation(beanName)) {
        // 2. 看二级缓存（早期引用）
        singletonObject = this.earlySingletonObjects.get(beanName);
        if (singletonObject == null && allowEarlyReference) {
            synchronized (this.singletonObjects) {
                // double-check
                singletonObject = this.singletonObjects.get(beanName);
                if (singletonObject == null) {
                    singletonObject = this.earlySingletonObjects.get(beanName);
                    if (singletonObject == null) {
                        // 3. 看三级缓存（ObjectFactory）
                        ObjectFactory<?> singletonFactory = this.singletonFactories.get(beanName);
                        if (singletonFactory != null) {
                            singletonObject = singletonFactory.getObject();   // 决策是否代理
                            this.earlySingletonObjects.put(beanName, singletonObject);
                            this.singletonFactories.remove(beanName);          // 三级 → 二级
                        }
                    }
                }
            }
        }
    }
    return singletonObject;
}
```

### 3.3 完整剧本：A ↔ B 循环依赖

```
1. getBean(A)
   └─ singletonObjects.get(A) → null
   └─ 走创建流程：
      ① createBeanInstance(A) → new A()         // A 是空壳
      ② addSingletonFactory(A, ObjectFactory)   // 写入三级缓存
      ③ populateBean(A)
         └─ 注入 b 字段 → getBean(B)
            └─ singletonObjects.get(B) → null
            └─ 走创建流程：
               ① createBeanInstance(B) → new B()
               ② addSingletonFactory(B, ObjectFactory)
               ③ populateBean(B)
                  └─ 注入 a 字段 → getBean(A)
                     └─ singletonObjects.get(A) → null
                     └─ earlySingletonObjects.get(A) → null
                     └─ singletonFactories.get(A) → 调 getObject()
                        └─ 返回 A 的早期引用（裸对象 or AOP 代理）
                        └─ 写入二级缓存，移出三级缓存
                     └─ 返回早期 A
                  └─ B.a = 早期 A
               ④ initializeBean(B) → B 完整初始化（含 AOP 代理决策）
               └─ 写入一级缓存
            └─ 返回完整 B
         └─ A.b = 完整 B
      ④ initializeBean(A) → A 完整初始化
      └─ 写入一级缓存
   └─ 返回完整 A
```

**A 拿到的 B 是完整对象，B 拿到的 A 是"半成品早期引用"**——但因为 Java 是引用传递，A 完成初始化后，B.a 引用指向的对象自动变成完整 A。这正是循环依赖能解开的根本原因。

## 四、为什么必须三级缓存？二级不够吗？

这是高级面试官的杀手锏问题。

### 4.1 没有 AOP 时：二级足够

如果系统里没有 AOP，bean 永远是原始对象。曝光时直接把 `bean` 放二级缓存就行——不需要三级。

### 4.2 有 AOP 时：必须三级才能"按需代理"

AOP 代理在 `BeanPostProcessor.postProcessAfterInitialization`（生命周期最后一步）才生成。但循环依赖时，**B 必须提前拿到 A 的引用**——这时还没到代理生成那一步。

设计选择：

**方案 1（粗暴）**：循环依赖时直接生成代理 → 放二级缓存
- ❌ 哪怕没循环依赖也提前生成代理（无意义开销）
- ❌ 与"AOP 在生命周期最后一步织入"的设计原则冲突

**方案 2（Spring 选这个）**：放三级缓存（ObjectFactory），**当真有人来要早期引用时，才决定要不要代理**
- ✅ 没循环依赖时，三级缓存里的 factory 永远不会被调，AOP 还是在生命周期最后做
- ✅ 有循环依赖时，触发 `getEarlyBeanReference`，按需生成代理放二级
- ✅ 设计上"按需付费"，不为不存在的问题买单

```java
// SmartInstantiationAwareBeanPostProcessor 的接口
default Object getEarlyBeanReference(Object bean, String beanName) {
    return bean;        // 默认返回原始对象
}

// AbstractAutoProxyCreator 重写
public Object getEarlyBeanReference(Object bean, String beanName) {
    Object cacheKey = getCacheKey(bean.getClass(), beanName);
    this.earlyProxyReferences.put(cacheKey, bean);  // 标记：已提前代理
    return wrapIfNecessary(bean, beanName, cacheKey);  // 生成代理
}

// 后续 postProcessAfterInitialization 检查标记，避免重复代理
public Object postProcessAfterInitialization(Object bean, String beanName) {
    Object cacheKey = getCacheKey(bean.getClass(), beanName);
    if (this.earlyProxyReferences.remove(cacheKey) != bean) {
        return wrapIfNecessary(bean, beanName, cacheKey);
    }
    return bean;
}
```

> **总结**：三级 = 延迟生成 + 防止重复代理。没有第三级，只有"全员提前代理"或"无法解决 AOP 循环依赖"两个糟糕选择。

### 4.3 数据结构选型为什么这样

```java
singletonObjects        = ConcurrentHashMap   // 高频读，需要并发安全
earlySingletonObjects   = ConcurrentHashMap   // 6.0 后改 CHM，之前是 HashMap+synchronized
singletonFactories      = HashMap             // 写入/读取都在 synchronized 块内，普通 HashMap 即可
```

**追问点**：为什么三级用 HashMap？因为对它的所有访问都在 `synchronized(singletonObjects)` 块里，外层锁已经保证了线程安全。

## 五、解不了的循环依赖

### 5.1 构造器循环依赖

```java
@Service
public class A {
    public A(B b) { ... }
}
@Service
public class B {
    public B(A a) { ... }
}
```

启动报错：`BeanCurrentlyInCreationException: Error creating bean with name 'a': Requested bean is currently in creation`。

**根因**：曝光到三级缓存的前提是 **对象已经 new 出来**。构造器循环依赖时，A 的构造器卡在等 B，B 的构造器卡在等 A——**两边都没 new 出来**，三级缓存里啥都没有。

**怎么解**：
1. 改成字段注入或 setter 注入
2. 用 `@Lazy` 标在构造器参数上：`public A(@Lazy B b)`，注入的是代理对象，第一次用时才解析
3. 重新设计——**循环依赖往往是设计问题**，能不解就不解

### 5.2 prototype 循环依赖

```java
@Scope("prototype")
@Service
public class A { @Autowired B b; }
```

报错。**根因**：prototype 不缓存，每次 `getBean` 都新建——三级缓存压根用不上。

**怎么解**：改 singleton。如果业务必须 prototype，重新设计依赖关系。

### 5.3 `@Async` 循环依赖

报错（Spring 5+）：

```
The bean 'a' could not be injected as a 'com.foo.A' because it is a JDK 
dynamic proxy that implements: ... Consider injecting the bean as one of 
its interfaces or forcing the use of CGLib-based proxies (e.g. via 
@EnableAsync(proxyTargetClass=true)).
```

**根因**：
- `@Async` 通过单独的 BPP 在 `postProcessAfterInitialization` 生成代理
- 循环依赖时 A 已经把"早期引用"（不含 `@Async` 代理）注入给 B 了
- 等 A 走完初始化，A 的最终对象（含 `@Async` 代理）和 B 持有的引用不是同一个
- Spring 检测到不一致，直接报错

**怎么解**：
1. 强制 CGLIB 代理：`@EnableAsync(proxyTargetClass = true)` —— 让 A 提前用 CGLIB 代理曝光
2. 改 `@Async` 方法到独立的 bean，避免循环

### 5.4 多级循环（A→B→C→A）

**能解**——三级缓存是按 bean 维度工作的，链路上每个 bean 都能被早期曝光。但**链路越长越难调试**——这本身就是设计警报。

## 六、Spring Boot 2.6+ 默认禁止循环依赖

从 Spring Boot 2.6.0 起，`spring.main.allow-circular-references` 默认 `false`。启动时检测到循环依赖直接抛异常：

```
The dependencies of some of the beans in the application context form a cycle:
   ┌─────┐
|  a defined in file [...]
↑     ↓
|  b defined in file [...]
   └─────┘
```

**为什么 Spring 团队这样做**：
1. 循环依赖往往是设计问题，应该在编译/启动期暴露
2. AOP / `@Async` / `@Transactional` 与循环依赖叠加时坑非常多
3. 强制开发者重新设计或显式 opt-in

**应急开关**（不推荐长期保留）：

```yaml
spring:
  main:
    allow-circular-references: true
```

**根治**：
- 拆 bean，把共同依赖抽出来
- 用接口隔离
- 事件驱动（`ApplicationEventPublisher` 解耦）
- `@Lazy` 注入

## 七、生产踩坑

### 坑 1：升级 Spring Boot 2.6 后启动失败

线上业务跑了好多年，升级时一片 `BeanCurrentlyInCreationException`。

**根因**：业务里隐藏的循环依赖以前靠三级缓存"自动解决"，2.6 默认禁止后暴露。
**修法**：先开 `allow-circular-references=true` 救急，逐步重构去掉循环依赖（用 `@Lazy` 是过渡，不是终点）。

### 坑 2：`@Async` + 循环依赖导致 NPE

```java
@Service
public class OrderService {
    @Autowired private NotifyService notifyService;
    @Async public void send() { ... }
}

@Service
public class NotifyService {
    @Autowired private OrderService orderService;
    public void notify() { orderService.send(); }   // 期待异步
}
```

线上现象：`send()` 不是异步执行的（同步执行了）。

**根因**：循环依赖时 `NotifyService` 持有的是 `OrderService` 的早期引用（无 `@Async` 代理），`@Async` 代理失效。
**修法**：拆出独立的 `AsyncNotifySender` bean。

### 坑 3：构造器注入误以为能循环

新人代码：

```java
@Service
@RequiredArgsConstructor   // Lombok 生成构造器
public class A {
    private final B b;
}

@Service
@RequiredArgsConstructor
public class B {
    private final A a;
}
```

启动直接挂。**根因**：`@RequiredArgsConstructor` 生成构造器注入，构造器循环依赖无解。
**修法**：拆掉一边，或换 setter，或用 `@Lazy`：

```java
@Service
public class A {
    private final B b;
    public A(@Lazy B b) { this.b = b; }
}
```

### 坑 4：`@Bean` 方法之间的循环依赖

```java
@Configuration
public class AppConfig {
    @Bean
    public A a(B b) { return new A(b); }
    
    @Bean
    public B b(A a) { return new B(a); }
}
```

**这就是构造器循环依赖**——`@Bean` 方法的参数等价于构造器参数。同样无解。

## 八、面试高频追问

**Q1：Spring 解决了哪种循环依赖？**
A：**单例 scope + 字段/setter 注入** 这一类。其他场景都解不了：构造器循环（对象都没 new 出来）、prototype（不缓存）、`@Async` 这类二次代理（早期引用与最终对象不一致）。

**Q2：为什么用三级缓存？二级不够吗？**
A：二级缓存解决"找早期引用"的问题，但解决不了"AOP 代理什么时候生成"的设计冲突。
- AOP 应该在生命周期最后一步织入
- 但循环依赖时必须提前曝光带不带代理的引用
- 第三级 `ObjectFactory` **延迟决策**：没人要就一直不调，按需生成代理放二级。这样 90% 没循环依赖的场景 AOP 还是最后做。

**Q3：三级缓存能否换成"代码里加个标记位"？**
A：理论可以，但 ObjectFactory 是更优雅的封装——把"何时生成代理"作为可插拔的策略，由 `SmartInstantiationAwareBeanPostProcessor.getEarlyBeanReference` 决定。Spring 团队用最少的改动给了 AOP 一个接管点。

**Q4：构造器循环依赖一定无解吗？**
A：可以用 `@Lazy` 强行解——给参数加 `@Lazy`，Spring 注入代理对象，真正调方法时才解析。但这是兜底，不是最佳实践。**真正的修法是改设计**——循环依赖往往意味着两个 bean 应该合一或拆三。

**Q5：prototype 循环依赖为什么不能解？**
A：`prototypesCurrentlyInCreation`（ThreadLocal）检测当前线程是否正在创建该 bean，发现重入直接抛异常。根因：prototype 不缓存，每次新建，没有"提前曝光"的概念——容器都不打算保留它，谈何让别人引用。

**Q6：单例 + 构造器注入 + 循环依赖会怎样？**
A：启动失败。`createBeanInstance` 之前 `singletonsCurrentlyInCreation` 标记 A 在创建中；构造器要 B，递归到 B；B 构造器要 A，发现 A 在创建中且二、三级缓存都没东西（A 还没 new 出来）→ 抛 `BeanCurrentlyInCreationException`。

**Q7：`@Lazy` 解决循环依赖的原理？**
A：`@Lazy` 标在依赖上时，Spring 注入的是 **代理对象**（`ContextAnnotationAutowireCandidateResolver` 生成）——代理内部持有一个 `ObjectFactory`，第一次调方法时才走 `getBean`。这样构造器执行时只是注入了"占位代理"，不会真正触发依赖创建——绕过了循环。

**Q8：循环依赖在 Spring 6 / Spring Boot 3 有什么变化？**
A：行为没变，三级缓存仍然存在。但 Spring 官方在文档里更明确地推荐 **构造器注入 + 不要循环依赖**。Spring Boot 3.x 仍默认 `allow-circular-references=false`。

## 九、答题模板（60 秒）

> Spring 用 **三级缓存** 解决 **单例 scope、setter / 字段注入** 的循环依赖。
>
> 三级缓存：① `singletonObjects` 存成品；② `earlySingletonObjects` 存早期引用（原始或代理）；③ `singletonFactories` 存 `ObjectFactory`，按需生成早期引用。
>
> 流程：A 实例化后立即把生产 A 早期引用的 ObjectFactory 放入三级缓存；A 注入属性时发现要 B，递归创建 B；B 注入属性时发现要 A，从三级缓存调 `getObject` 拿到 A 的早期引用（**这一步可能触发 AOP 提前生成代理**），把早期引用放二级缓存；B 完成全部初始化后写入一级缓存；A 拿到完整 B 后完成自己初始化，也写入一级缓存。
>
> **为什么必须三级**：AOP 代理本应在生命周期最后一步织入，三级缓存的 `ObjectFactory` 让"按需代理"成为可能——没循环依赖时三级缓存里的工厂从不被调用，AOP 仍在最后做；有循环依赖时才被迫提前。
>
> **解不了的场景**：① 构造器循环依赖（对象没 new 出来），② prototype（不缓存），③ `@Async` 等二次代理（代理对象与早期引用不一致）。
>
> **生产取舍**：Spring Boot 2.6+ 默认禁止循环依赖，强制重构。临时救急用 `allow-circular-references=true` 或 `@Lazy`，但根治是**改设计**。
