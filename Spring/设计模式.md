# Spring 中的设计模式

> 这道题面试经常问，但 90% 的人只会列"工厂、单例、代理、模板方法、观察者……"——干巴巴 5 个名词。
> 资深答法的关键：**每个模式举一个 Spring 真实代码 + 解释为什么这里用它而不是别的**。
> 本篇就是这个版本的笔记。

---

## 一、Spring 用到的核心设计模式

| 模式 | Spring 中的体现 | 解决什么问题 |
| --- | --- | --- |
| **工厂模式** | `BeanFactory` / `FactoryBean` | 把对象创建集中管理 |
| **单例模式** | bean 默认 singleton | 资源复用、状态共享 |
| **代理模式** | AOP / 事务 / `@Async` | 在不修改原对象的前提下增强行为 |
| **模板方法** | `JdbcTemplate` / `RedisTemplate` / `AbstractApplicationContext.refresh()` | 流程骨架 + 可变填空 |
| **观察者** | `ApplicationEvent` + `ApplicationListener` | 解耦发布方和订阅方 |
| **策略模式** | `HandlerMethodArgumentResolver` / `Resource` 各实现 | 同一接口，多实现按需切换 |
| **责任链** | `HandlerExecutionChain` / Servlet `Filter` chain | 多个处理器串行处理一个请求 |
| **适配器** | `HandlerAdapter` / AOP `AdvisorAdapter` | 统一不同来源接口的调用方式 |
| **装饰器** | `BeanPostProcessor` / `BufferedReader` 风格的 wrapper | 在不改原类的情况下叠加能力 |
| **建造者** | `RestTemplateBuilder` / `BeanDefinitionBuilder` / `MockMvcBuilders` | 复杂对象构造分步走 |
| **门面（Facade）** | `ApplicationContext` 整合多个子接口 | 用一个对外接口屏蔽内部复杂度 |

## 二、工厂模式

### 2.1 简单工厂 / 工厂方法：`BeanFactory`

**职责**：根据 bean name 生产对应的对象，调用方不关心怎么生产。

```java
public interface BeanFactory {
    Object getBean(String name);
    <T> T getBean(String name, Class<T> requiredType);
    ...
}
```

调用方代码：

```java
UserService svc = (UserService) ctx.getBean("userService");
```

调用方完全不知道 `UserService` 是怎么 new 出来的——可能反射、可能工厂方法、可能 FactoryBean 生产。

### 2.2 抽象工厂：`FactoryBean`

**职责**：让"生产对象的过程"本身也成为容器里的一个 bean。

```java
public interface FactoryBean<T> {
    T getObject() throws Exception;          // 生产真实对象
    Class<?> getObjectType();                // 真实对象的类型
    boolean isSingleton();
}
```

经典案例：`MapperFactoryBean`（MyBatis）

```java
public class MapperFactoryBean<T> extends SqlSessionDaoSupport implements FactoryBean<T> {
    private Class<T> mapperInterface;
    
    @Override
    public T getObject() throws Exception {
        return getSqlSession().getMapper(mapperInterface);   // JDK 动态代理生成 Mapper 实现
    }
    
    @Override
    public Class<?> getObjectType() { return mapperInterface; }
}
```

业务方注入 `UserMapper`，拿到的是 `getObject()` 返回的代理对象，**不是 `MapperFactoryBean` 自身**。

> **追问**：怎么拿到 FactoryBean 自身？前缀 `&`：`getBean("&userMapper")`。

## 三、单例模式

Spring bean **默认 singleton**——但实现的不是 GoF 经典单例（私有构造 + 静态字段），而是**容器维护**：

```java
// DefaultSingletonBeanRegistry
private final Map<String, Object> singletonObjects = new ConcurrentHashMap<>(256);

public Object getSingleton(String beanName) {
    return singletonObjects.get(beanName);
}
```

**和 GoF 单例的差异**：
- GoF 单例：JVM 全局唯一，绑定在类上
- Spring 单例：**容器内**唯一，可以多容器持有不同实例

> **生产追问**：Spring 单例是线程安全的吗？**Spring 不保证**——只保证容器内只有一个实例。是否线程安全取决于 bean 自身有没有可变状态。无状态 Service 天然安全，有状态需要业务自己处理。

## 四、代理模式

### 4.1 应用：AOP / 事务 / 缓存 / `@Async`

```
调用方  →  代理对象  →  目标对象
              │
              └─ 织入：开事务 / 打日志 / 缓存查找 / 异步分发 / ...
```

### 4.2 Spring 的两种实现

| 实现 | 适用 | 原理 |
| --- | --- | --- |
| **JDK 动态代理** | 目标类实现接口 | `Proxy.newProxyInstance` 反射 |
| **CGLIB** | 任意类（非 final） | ASM 生成子类 |

详见 [AOP.md](AOP.md)。

### 4.3 代理模式 vs 装饰器模式

很多人混淆。区别：

| 维度 | 代理 | 装饰器 |
| --- | --- | --- |
| **意图** | 控制访问（鉴权、远程、惰性、日志） | 动态扩展行为 |
| **是否对调用方透明** | 是（看起来就是原对象） | 是 |
| **构造方式** | 一般在内部创建目标对象 | 调用方主动包一层 |
| **典型** | Spring AOP、RMI Stub | `BufferedInputStream`、`BeanPostProcessor` |

> **简言之**：意图不同。代理强调**控制**，装饰器强调**叠加能力**。

## 五、模板方法模式

### 5.1 定义

定义一个算法的**骨架**（template），把其中**可变的步骤**延迟到子类去实现。父类把流程定死，子类只填空。

> 一句话：**父类调子类**（钩子方法），是 IoC 思想的雏形（"不要找我，我会调你"）。

### 5.2 角色

- **AbstractClass**：抽象类，定义模板方法（一般用 `final` 防止被子类覆盖整体流程）和若干抽象/钩子方法
- **ConcreteClass**：具体子类，实现抽象方法，决定可变步骤的具体行为

### 5.3 通用结构

```java
public abstract class AbstractTask {
    // 模板方法：流程骨架，final 锁死
    public final void execute() {
        before();
        doExecute();      // 关键步骤交给子类
        after();
        if (needLog()) {  // 钩子，可选覆盖
            log();
        }
    }

    protected void before() { /* 默认实现 */ }
    protected abstract void doExecute();
    protected void after()  { /* 默认实现 */ }
    protected boolean needLog() { return false; }   // hook
    private void log() { /* ... */ }
}
```

### 5.4 Spring / 业界中的真实案例

| 来源 | 类 | 模板方法 | 子类填什么 |
| --- | --- | --- | --- |
| Spring JDBC | `JdbcTemplate.execute()` | 获取连接 → 执行 SQL → 处理结果 → 释放连接 | `StatementCallback` 实现 SQL 执行细节 |
| Spring Tx | `TransactionTemplate.execute()` | 开启事务 → 业务回调 → commit/rollback | `TransactionCallback` 写业务 |
| Spring | `AbstractApplicationContext.refresh()` | 12 步初始化骨架 | 子类 override 各阶段（如 `loadBeanDefinitions`、`onRefresh`） |
| Servlet | `HttpServlet.service()` | 根据 method 分发 | 子类实现 `doGet/doPost` |
| JDK | `AbstractList`、`AbstractMap` | 提供模板（contains, indexOf 等） | 子类实现 `get(int)`、`size()` |
| MyBatis | `BaseExecutor` | 缓存 + 委托 | 子类实现 `doQuery`、`doUpdate` |
| Netty | `AbstractBootstrap` | 配置 + 启动骨架 | 子类实现具体绑定逻辑 |

### 5.5 示例：JdbcTemplate

```java
public abstract class JdbcTemplate {
    public final <T> T execute(StatementCallback<T> action) {
        Connection con = getConnection();
        Statement stmt = null;
        try {
            stmt = con.createStatement();
            return action.doInStatement(stmt);   // ← 钩子，由用户实现
        } catch (SQLException ex) {
            throw translateException(ex);
        } finally {
            close(stmt);
            release(con);
        }
    }
}

// 调用方
List<User> users = jdbcTemplate.execute(stmt ->
    parseRows(stmt.executeQuery("select * from user"))
);
```

固定的资源管理、异常处理、连接释放 → 在父类。变化的"具体执行什么 SQL" → 用户定。

### 5.6 模板方法 vs 策略模式

| 维度 | 模板方法 | 策略 |
| --- | --- | --- |
| 实现 | 继承（is-a） | 组合（has-a） |
| 关系 | 父类调子类 | 上下文调策略对象 |
| 扩展点 | 抽象方法 / 钩子 | 整个算法替换 |
| 灵活度 | 固定骨架，只能改填空部分 | 可整体替换 |

> 实际项目中，**有共享流程骨架**用模板方法；**算法整体可换**用策略。两者经常组合使用。

## 六、观察者模式（事件机制）

### 6.1 Spring 实现

```java
// 1. 定义事件
public class OrderCreatedEvent extends ApplicationEvent {
    private final Long orderId;
    public OrderCreatedEvent(Object source, Long orderId) {
        super(source); this.orderId = orderId;
    }
    public Long getOrderId() { return orderId; }
}

// 2. 发布事件
@Service
public class OrderService {
    @Resource private ApplicationEventPublisher publisher;
    
    public void createOrder(Long userId) {
        Long orderId = ...;
        publisher.publishEvent(new OrderCreatedEvent(this, orderId));
    }
}

// 3. 监听事件（两种方式）
@Component
public class OrderEventListener {
    @EventListener
    public void onOrderCreated(OrderCreatedEvent event) {
        log.info("order created: {}", event.getOrderId());
    }
}
```

### 6.2 异步事件

```java
@EnableAsync                  // 启动类
@Component
public class AsyncOrderListener {
    @EventListener
    @Async
    public void onOrderCreated(OrderCreatedEvent event) { ... }   // 异步执行
}
```

### 6.3 事务事件

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onOrderCreated(OrderCreatedEvent event) { ... }
```

事务提交后才触发，避免事务回滚时事件已发出导致数据不一致。

### 6.4 经典 Spring 事件

| 事件 | 触发时机 |
| --- | --- |
| `ContextRefreshedEvent` | 容器 refresh 完成 |
| `ContextStartedEvent` | `start()` 调用 |
| `ContextStoppedEvent` | `stop()` 调用 |
| `ContextClosedEvent` | `close()` 调用 |
| `ApplicationStartedEvent` | Spring Boot 启动后期 |
| `ApplicationReadyEvent` | Spring Boot 完全就绪 |

## 七、策略模式

### 7.1 Spring 中的体现

**`HandlerMethodArgumentResolver`**：把请求参数解析成方法参数。

```java
public interface HandlerMethodArgumentResolver {
    boolean supportsParameter(MethodParameter parameter);   // 我能解析这种参数吗
    Object resolveArgument(MethodParameter parameter, ...) throws Exception;   // 怎么解析
}

// 各种实现：
// RequestParamMethodArgumentResolver       → @RequestParam
// PathVariableMethodArgumentResolver       → @PathVariable
// RequestResponseBodyMethodProcessor       → @RequestBody
// ServletRequestMethodArgumentResolver     → HttpServletRequest 类型
// ...
```

`HandlerMethodArgumentResolverComposite` 持有所有 resolver，按 `supportsParameter` 选用——典型的策略模式 + 注册表。

**`Resource`**：

```java
public interface Resource extends InputStreamSource {
    boolean exists();
    InputStream getInputStream() throws IOException;
    ...
}

// 实现：
// ClassPathResource     → classpath 资源
// FileSystemResource    → 文件系统
// UrlResource           → URL
// ByteArrayResource     → 内存 byte[]
// ServletContextResource→ Servlet 上下文
```

业务用 `@Value("classpath:foo.txt") Resource res`，Spring 按 URL 协议自动选实现。

## 八、责任链模式

### 8.1 `HandlerExecutionChain`

```
请求 →  Interceptor1.preHandle  → Interceptor2.preHandle  → Controller  
       ← Interceptor1.postHandle  ← Interceptor2.postHandle  ←
```

`HandlerExecutionChain` 持有 Handler 和 Interceptor 数组，`DispatcherServlet` 按顺序遍历调用。**每个拦截器可以决定是否中断后续**（`preHandle` 返回 false）。

### 8.2 Servlet `Filter` 链

```java
public class MyFilter implements Filter {
    @Override
    public void doFilter(ServletRequest req, ServletResponse resp, FilterChain chain) {
        // 前置
        chain.doFilter(req, resp);   // ← 把控制权交给下一个 Filter / Servlet
        // 后置
    }
}
```

经典的"洋葱皮"模型，每个 Filter 都可以决定是否继续。

### 8.3 Spring Security FilterChain

更复杂的责任链——`SecurityFilterChain` 由 N 个 `Filter` 组成，每个 Filter 处理一类安全关注点（认证、授权、CSRF、CORS、Session 等）。

## 九、适配器模式

### 9.1 `HandlerAdapter`

DispatcherServlet 想统一调用 Controller，但 Controller 有多种类型：
- `@RequestMapping` 注解的方法（`HandlerMethod`）
- 实现 `Controller` 接口的类（旧式）
- 实现 `HttpRequestHandler` 接口的类（处理静态资源）
- WebSocket / Servlet API ……

`HandlerAdapter` 接口屏蔽差异：

```java
public interface HandlerAdapter {
    boolean supports(Object handler);
    ModelAndView handle(HttpServletRequest req, HttpServletResponse resp, Object handler) throws Exception;
}
```

`RequestMappingHandlerAdapter` / `HttpRequestHandlerAdapter` / `SimpleControllerHandlerAdapter` 各对应一种。

### 9.2 AOP `AdvisorAdapter`

把不同类型的 Advice（`MethodBeforeAdvice` / `AfterReturningAdvice` / `ThrowsAdvice`）统一适配成 `MethodInterceptor`。

## 十、装饰器模式

### 10.1 `BeanPostProcessor`

每个 BPP 都可以把 bean 包装一层（典型：AOP 包代理）：

```java
Object bean = new UserService();
bean = bpp1.postProcessAfterInitialization(bean);   // 可能包一层 logging proxy
bean = bpp2.postProcessAfterInitialization(bean);   // 又包一层 transaction proxy
bean = bpp3.postProcessAfterInitialization(bean);   // 又包一层 cache proxy
return bean;                                        // 最终的 bean 是层层装饰过的
```

### 10.2 `HttpServletRequestWrapper`

Servlet 标准提供，业务可以继承它做"修改 request body / header"等装饰：

```java
public class CachedBodyRequestWrapper extends HttpServletRequestWrapper {
    private final byte[] cachedBody;
    
    public CachedBodyRequestWrapper(HttpServletRequest req) throws IOException {
        super(req);
        cachedBody = StreamUtils.copyToByteArray(req.getInputStream());   // 把 body 读到内存
    }
    
    @Override
    public ServletInputStream getInputStream() {
        return new CachedBodyInputStream(cachedBody);   // 装饰：可以反复读
    }
}
```

## 十二、门面模式

`ApplicationContext` 自身就是门面——它聚合了：
- `BeanFactory`（IoC）
- `MessageSource`（i18n）
- `ResourceLoader`（资源访问）
- `ApplicationEventPublisher`（事件）
- `Environment`（环境）

业务代码只依赖一个 `ApplicationContext`，背后五个能力都能用——这就是门面的意义。

## 十三、面试高频追问

**Q1：Spring 用了哪些设计模式？**
A：见第一章表格。回答时**每个模式都要带 Spring 真实代码举例**——这是和初级的差距。

**Q2：`BeanFactory` 和 `FactoryBean` 区别？**
A：完全是两个东西。`BeanFactory` 是容器，管所有 bean；`FactoryBean` 是放在容器里、用来生产某种复杂对象的特殊 bean。`getBean("xx")` 拿到的是 `FactoryBean.getObject()` 产出的对象，`getBean("&xx")` 才能拿到 `FactoryBean` 自身。MyBatis `MapperFactoryBean` 是经典案例。

**Q3：Spring AOP 是哪种模式？代理还是装饰器？**
A：**代理**。差异：意图。AOP 的意图是"控制对原对象的访问，织入横切关注点"——典型代理；装饰器的意图是"动态扩展对象本身的能力"。两者结构相似，意图不同。

**Q4：`JdbcTemplate` 是什么模式？**
A：**模板方法**——固定流程（拿连接 → 执行 → 处理结果 → 释放）在父类，可变部分（具体 SQL 怎么执行）通过 `StatementCallback` 钩子让用户填。Spring 一系列 `XxxTemplate`（`RestTemplate`、`RedisTemplate`、`TransactionTemplate`）都是这个模式。

**Q5：观察者模式在 Spring 哪里？**
A：`ApplicationEvent` + `ApplicationListener` + `ApplicationEventPublisher`。事件本身是 `ApplicationEvent` 子类；发布方调 `publisher.publishEvent`；订阅方实现 `ApplicationListener<XxxEvent>` 或在方法上加 `@EventListener`。Spring Boot 启动期间的 `ApplicationStartedEvent` / `ApplicationReadyEvent` 等都是这套机制。

**Q6：`HandlerInterceptor` 是责任链吗？**
A：是。`HandlerExecutionChain` 持有 N 个拦截器，按顺序调 `preHandle`，任意一个返回 false 就中断；后续按反序调 `postHandle` / `afterCompletion`。"洋葱皮"结构。

**Q7：Spring 的单例和 GoF 单例有什么不同？**
A：GoF 单例是 JVM 全局唯一（私有构造 + 静态字段）；Spring 单例是**容器内**唯一，由容器管理（`ConcurrentHashMap` 缓存）。多容器场景下 Spring 单例不止一个实例。Spring 选这个方案因为：① 测试友好（容器隔离）；② 父子容器；③ 单例语义可配（`scope`）。

**Q8：装饰器模式在 Spring 哪里？**
A：`BeanPostProcessor` 是最典型的——每个 BPP 都可以在 `postProcessAfterInitialization` 把 bean 包一层。AOP 代理本身既是代理也算装饰。`HttpServletRequestWrapper`（Spring MVC 用它包装 request）也是装饰器。

## 十四、答题模板（60 秒）

> Spring 是设计模式的"教科书代码库"——核心模式都能找到至少一个真实应用：
>
> **工厂**：`BeanFactory.getBean()` 把对象创建集中管理；`FactoryBean` 让"生产对象的过程"也成为容器里的 bean（MyBatis `MapperFactoryBean`）。
>
> **单例**：bean 默认 singleton，但**容器内**唯一（不是 GoF 全局唯一），由 `ConcurrentHashMap` 缓存。
>
> **代理**：AOP / 事务 / `@Async` 全靠它——JDK 动态代理（接口）和 CGLIB（继承）。
>
> **模板方法**：所有 `XxxTemplate`（`JdbcTemplate` / `RedisTemplate` / `TransactionTemplate`）和 `AbstractApplicationContext.refresh()`——固定骨架 + 钩子填空。
>
> **观察者**：`ApplicationEvent` + `@EventListener`，Spring Boot 启动期的 8 个事件都是这套机制。
>
> **策略**：`HandlerMethodArgumentResolver` 选用不同的参数解析器；`Resource` 不同协议的实现。
>
> **责任链**：`HandlerExecutionChain`（拦截器）、Servlet `Filter` 链、Spring Security FilterChain。
>
> **适配器**：`HandlerAdapter` 屏蔽不同类型 Controller 的调用差异；AOP `AdvisorAdapter` 适配不同类型的 Advice。
>
> **装饰器**：`BeanPostProcessor` 层层包装 bean；`HttpServletRequestWrapper` 包装 request。
>
> **建造者**：`RestTemplateBuilder` / `BeanDefinitionBuilder` 链式构造复杂对象。
>
> **门面**：`ApplicationContext` 聚合 BeanFactory / MessageSource / Resource / Event / Environment。
