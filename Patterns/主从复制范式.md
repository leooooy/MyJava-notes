# 主从复制范式 — MySQL binlog / Redis PSYNC / Kafka ISR / RocketMQ HA / Raft 同构设计

> 引子：
> ① **是什么**：一个写入节点（Master / Leader）把变更同步给多个读节点（Slave / Follower），换取**高可用 + 读扩展 + 容灾**。所有有状态系统都得做这件事——MySQL binlog 复制、Redis PSYNC、Kafka ISR、RocketMQ HA、Raft/ZAB 共识本质上是同一个范式的不同强度。
> ② **面试为什么必考**：上一篇《WAL 预写日志》已经说过"WAL 即天然复制源"——这一篇就是 WAL 的下游。主从延迟、半同步、ISR、脑裂、数据回退、Failover、读写分离一致性，每个都是面试常驻点。讲清这套范式，等于一次性解决十几道高频题。
> ③ **本篇要解决**：① 异步 / 半同步 / 全同步的本质差别是什么 ② Kafka 的 ISR 为什么比 Raft 灵活 ③ Master 挂了怎么选新 Master，数据回退是怎么发生的 ④ "写后立即读到旧值"在每个系统里怎么破解。

---

## 一、为什么需要主从复制

### 1.1 原始问题

单点的三个痛：

| 痛点 | 单机表现 | 影响 |
| --- | --- | --- |
| **故障即停摆** | 机器挂 / 进程挂 / 磁盘坏 → 数据不可访问 | 业务全断 |
| **读写都压一台** | 读 QPS 上不去 | 容量天花板 |
| **数据无备份** | 磁盘损坏数据归零 | 不可接受 |

主从复制一次性解决三件事：① **高可用**（Master 挂可切到 Slave）；② **读扩展**（读分散到多个 Slave）；③ **容灾**（Slave 在异地机房）。

### 1.2 核心问题：复制源是什么

**复制 = 把 Master 上的变更搬到 Slave 上重做**。变更怎么表达？

答案：**WAL**。所有主从复制系统的复制源都是某种 WAL（呼应上一篇《WAL 预写日志》）：

| 系统 | 复制源 |
| --- | --- |
| MySQL | binlog（逻辑日志）|
| Redis | replication stream + repl_backlog（命令流）|
| Kafka | partition log（消息日志）|
| RocketMQ | CommitLog（消息日志）|
| Raft / ZAB | Raft log / txn log（状态机命令）|

**复制源 = 系统已有的 WAL 文件**——不需要额外设计一个"复制专用的格式"，直接拷贝/传输 WAL 给 Slave 重放就够了。这就是 WAL 范式的"天然红利"。

## 二、共性骨架

### 2.1 通用流程

```
[Client] ──写入──► [Master]
                       │
                       ├─ ① 本地写 WAL（顺序追加 + fsync）
                       │
                       ├─ ② 应用到内存数据结构
                       │
                       ├─ ③ 复制 WAL 给 Slave
                       │   ┌───────────────────────┐
                       │   │ 异步：发完不等        │
                       │   │ 半同步：等部分 Slave  │
                       │   │ 同步/共识：等多数派   │
                       │   └───────────────────────┘
                       │
                       ▼
                  向 Client 返回成功
                       │
                       ▼
                       │
                  [Slave1]  [Slave2]  [Slave3]
                       │
                  各自重放 WAL 到本地数据结构
```

### 2.2 三个关键 trade-off

**①  Master 什么时候向 Client 回 ACK** —— 决定一致性级别

```
            写 Master 本地 → 复制给 Slave → Slave 也持久化
                  ↑                ↑                ↑
              ① 异步        ② 半同步            ③ 同步/共识
              "我自己有了就行"  "至少 1 个从有"   "多数派都有"
```

**②  谁主动复制** —— 决定网络模型

| 推（Push） | 拉（Pull） |
| --- | --- |
| Master 主动把 WAL 发给 Slave | Slave 主动从 Master 拉 |
| 实时性强 | Master 无状态、扩展性强 |
| Slave 慢会阻塞 Master | Slave 自己控速 |
| MySQL（dump thread）、Redis | Kafka、RocketMQ（HAClient）|

**③  Master 挂了怎么处理** —— 决定可用性

| 方案 | 自动 | 数据安全 | 复杂度 |
| --- | --- | --- | --- |
| 人工切换 | ❌ | 取决于半同步 | 低（运维介入）|
| Sentinel / 哨兵选主 | ✅ | 异步可能丢 | 中 |
| Raft / ZAB 共识 | ✅ | 多数派承诺即不丢 | 高 |
| Kafka Controller + ISR | ✅ | acks=all + min.insync 控制 | 中 |

## 三、五种实现的横向对比

### 3.1 全维度对比表

| 维度 | **MySQL binlog** | **Redis PSYNC** | **Kafka ISR** | **RocketMQ HA** | **Raft / ZAB** |
| --- | --- | --- | --- | --- | --- |
| **复制源** | binlog（逻辑日志）| repl_backlog + 命令流 | partition log | CommitLog | Raft log / txn log |
| **传输方式** | Push（Master dump thread 推）| Push（命令实时写 socket）| **Pull**（follower fetch）| **Pull**（HAClient）| Push（AppendEntries）|
| **同步级别** | 异步 / 半同步 / 全同步可选 | 异步默认；WAIT 命令做半同步 | 通过 acks=0/1/all + min.insync.replicas 控制 | ASYNC_MASTER / SYNC_MASTER / DLedger | 共识级（多数派同步）|
| **默认级别** | 异步（5.7+ 半同步常用）| 异步 | acks=1（等 Leader 落盘）| ASYNC_MASTER | 同步（多数派）|
| **多数派语义** | ❌ | ❌ | ✅（动态 ISR）| DLedger 有 | ✅（固定多数派）|
| **故障切换** | 人工 / MHA / Orchestrator | Sentinel（异步选主）| Controller 自动选 ISR 中的 Leader | 4.x 人工；DLedger 自动 | 自动（Term 选举）|
| **能从 Slave 读** | ✅（读写分离）| ✅ | ❌（Kafka 一直只读 Leader）| ✅（Consumer 可拉 Slave） | 默认从 Leader；ZAB 可读 Follower |
| **复制延迟典型值** | 同机房 1~10ms，跨机房 50~200ms | 同机房 < 1ms | 同机房 ms 级 | 同机房 ms 级 | 同机房 < 5ms |
| **数据回退风险** | 半同步 OK / 异步会丢 | 异步会丢 | Unclean leader 会丢 | 4.x 错切 Slave 会丢 | 多数派承诺即不丢 |
| **典型用法** | 主从 + 读写分离 + 容灾 | 主从 + 哨兵 + Cluster | 多副本（默认 3）| 主备 + DLedger 高可用 | etcd / ZK / Nacos 配置中心 |

### 3.2 一张图理解"为什么差别这么大"

```
              一致性强度 ───────────────────────────►
              异步              半同步           共识（多数派）
                │                  │                  │
        ┌───────┴──────┐    ┌──────┴──────┐    ┌──────┴──────┐
   MySQL 异步         MySQL 半同步      Raft / ZAB
   Redis 默认         Redis WAIT        Kafka acks=all+min.insync
   RocketMQ ASYNC     RocketMQ SYNC     RocketMQ DLedger
                │                          │
        高 TPS / 可能丢                 低 TPS / 不丢
        可用性高                       可用性受多数派限制
```

**所有系统都在这条轴上滑动**，没有"无脑选谁"——本质都是 **CAP 中 C 和 A 的取舍**。

## 四、关键机制详解

### 4.1 异步复制：最快也最危险

**怎么工作**：Master 写完本地 WAL 就立即返回成功，复制丢给后台线程。

```
[Client] ──写──► [Master] ──返回成功──► [Client]
                    │
                    │ 后台异步
                    ▼
                 [Slave]
```

**致命问题**：Master 写完成功了，但还没来得及发给 Slave 就崩了 → Slave 永远不会有这条数据 → 切换到 Slave 后数据丢失。

**适用**：① 业务对一致性要求弱（如缓存、点击日志、监控指标）；② 跨机房高延迟场景（半同步太贵）；③ 已经有更可靠的兜底（如配合本地消息表 + 对账）。

**代表**：Redis 主从默认、MySQL 默认（5.6 前）、RocketMQ ASYNC_MASTER、Kafka acks=1。

### 4.2 半同步：等"至少 1 个"Slave

**怎么工作**：Master 写完本地，等至少一个 Slave 回 ACK 才向 Client 返回。

```
[Client] ──写──► [Master] ─── 复制 ──► [Slave1]
                    │   ◄── ACK ─────┘
                    │   （收到至少 1 个 ACK）
                    ▼
              返回成功 [Client]
```

**好处**：Master 挂了，数据已经在至少一个 Slave 上 → 不丢。

**典型实现**：

| 系统 | 实现 |
| --- | --- |
| MySQL | `rpl_semi_sync_master_enabled = ON` + 超时 1s 退化异步 |
| Redis | `WAIT numreplicas timeout` 命令（业务侧主动调）|
| RocketMQ | SYNC_MASTER（4.x 等"至少 1 个" Slave）|

**坑 1：超时退化**。MySQL 半同步如果 Slave 全挂 / 网络抖动超 1s，会**自动退化为异步**——退化期间发生主挂还是会丢。要监控 `Rpl_semi_sync_master_status` 和 `Rpl_semi_sync_master_no_tx`。

**坑 2：Slave 挂了 Master 阻塞**。RocketMQ 4.x SYNC_MASTER 模式下如果唯一的 Slave 挂了，Master 写入会卡住等同步超时（没有降级机制）。这是 4.x 的硬伤，DLedger 解决了。

### 4.3 Kafka ISR：动态多数派的优雅

Kafka 没有"半同步"或"全同步"的开关，而是用 **ISR（In-Sync Replicas）** 机制。

```
分区 Replicas = [Broker1(Leader), Broker2, Broker3]
ISR = "跟得上 Leader 的副本集合"  例如 [Broker1, Broker2]（Broker3 暂时落后被剔除）

Producer 配置：
  acks=0    → 不等任何 ACK（不丢就靠运气）
  acks=1    → 等 Leader 写完 ✅
  acks=all  → 等 ISR 中所有副本写完 ✅✅
  
配合：min.insync.replicas=2   → ISR 数量 < 2 时拒绝写入
```

**ISR 是动态的**：
- Follower 落后超过 `replica.lag.time.max.ms`（默认 30s）→ 踢出 ISR
- 追上后自动加回 ISR

**vs Raft 固定多数派的优势**：

| 维度 | Raft 多数派 | Kafka ISR |
| --- | --- | --- |
| 副本数 N=3 | 2/3 必须同步 | 配置 min.insync=2 时等价；其他时候更灵活 |
| 1 个副本慢 | 等它 / 选举 | 直接踢出 ISR，不影响 |
| 业务调优 | 不能 | 可改 `acks` 在性能/可靠之间动态切换 |
| 一致性证明 | 数学严格 | 工程经验，但实际很稳 |

**Kafka 的本质：把"多数派"从固定数变成可配置的最低水位**。这是非常工程化的简化——不追求 Raft 那种数学严格，但解决了 99% 的业务需求。

### 4.4 共识复制（Raft / ZAB / DLedger）

**最强的复制**：Master 写完本地，发给所有 Slave，等到**多数派承诺持久化**才返回。

```
[Client] ──写──► [Leader]
                    │
                    ├─ ① 本地写 log（fsync）
                    │
                    ├─ ② AppendEntries 给所有 Follower
                    │
                    ├─ ③ 等多数派（N/2+1）返回 ACK
                    │
                    └─ ④ 推进 commitIndex，应用到状态机
                          ▼
                       返回 Client
                          │
                          └─► 心跳告知 Follower commit
```

**为什么共识 = "强半同步"**：把"等至少 1 个 Slave"升级成"等多数派 Slave"——任何少数派故障都不影响写入，任何多数派的写入都不会因为切主丢失。

**代价**：
- 写延迟取决于"最慢的多数派"中的最慢者
- 一旦多数派挂掉 → 完全不可写（CP 而非 AP）
- 实现复杂度高

**代表**：etcd / TiKV（Raft）、ZooKeeper（ZAB）、RocketMQ DLedger、Nacos 配置中心（Raft）。

### 4.5 PSYNC：增量同步的精妙

Redis 主从断线重连不需要重新全量同步，靠 `repl_backlog`（环形缓冲区）：

```
Master 维护：
  replid       = "abc123"（Master 自身的运行 ID）
  master_offset = 当前累计字节数（如 10000）
  repl_backlog  = 最近 1MB 的命令流（环形缓冲）

Slave 断线后重连：
  发 PSYNC abc123 9500   ← "我上次同步到 9500，replid 是 abc123"
  
Master 判断：
  ① replid 不匹配 → FULLRESYNC（全量同步）
  ② offset 在 backlog 范围内（9500 ≥ 10000-1MB） → CONTINUE + 增量
  ③ offset 太老（不在 backlog 内） → FULLRESYNC
```

**为什么精妙**：用"客户端持有版本号 + Server 端环形缓冲"实现增量同步——这和《长轮询》里"客户端持有版本"是同一个范式。

**核心参数**：`repl_backlog_size`。默认 1MB 太小，生产建议 100MB+（按业务写入速率算：1Gbps 写入下 1MB 只够缓冲 8ms 网络抖动）。

→ 细节见 [Redis/主从一致性.md](../Redis/主从一致性.md)

## 五、Master 挂了：选主与数据回退

### 5.1 选主的核心问题：选谁？

主挂之后选一个 Slave 升级。**选错就丢数据**。

```
原始状态：
  Master:  ...写了到 offset 1000...
  Slave A: 同步到 offset 990（落后 10）
  Slave B: 同步到 offset 800（落后 200）

Master 挂掉。Sentinel 错选了 B 升级为新 Master：
  → B 当 Master，写 offset 801, 802, ...
  → A 重新挂到 B 下面，发现自己的 990 比 B 的小，全量重置
  → 原本在 990 那段（offset 800~990）的数据全部丢失！
```

**这就是数据回退（Data Loss after Failover）**。

### 5.2 各系统怎么避免

| 系统 | 防数据回退机制 |
| --- | --- |
| MySQL + Orchestrator | 选主前比较各 Slave 的 binlog 位点，选最新的 |
| Redis Sentinel | 选 `replica-priority` 最高 + offset 最大的 Slave |
| Kafka | 默认只在 ISR 内选 Leader（OSR 不选）；除非开 `unclean.leader.election.enable=true` |
| RocketMQ 4.x | **不自动选主**（无共识协议无法保证数据最新）|
| RocketMQ DLedger / Raft / ZAB | 共识协议天然保证：新 Leader 必须有最完整的日志（Raft 选举安全性约束）|

### 5.3 Kafka 的 unclean.leader.election

```
ISR = [Leader, F1]      OSR = [F2]
Leader 挂了，F1 也挂了

unclean.leader.election.enable=false（默认）
  → 拒绝选举，整个 partition 不可写 → 可用性差，但不丢数据
  
unclean.leader.election.enable=true
  → 强行选 F2 当 Leader → 可用性恢复，但 F2 落后的那段数据全丢
```

**这是 CAP 在 Kafka 上的具体落地**：开 = 选 A（可用性），关 = 选 C（一致性）。金融场景必关，互联网日志类可开。

### 5.4 脑裂与 fencing

**脑裂**：Master 没真挂（只是网络隔离），Sentinel 选出新 Master → 两个 Master 同时接受写入 → 数据冲突。

**通用 fencing 机制**：
- **MySQL**：MHA 在切换时 SSH 到老 Master 强制 kill mysqld
- **Redis Sentinel**：`min-slaves-to-write` + `min-slaves-max-lag` 强制老 Master 在没足够 Slave 时拒绝写
- **Kafka**：Leader epoch（每次选举 epoch +1，老 Leader 用旧 epoch 写入会被拒绝）
- **Raft**：term + commit index 双重保证，老 Leader 看到更大 term 立即降级 Follower

**Leader epoch / Raft term 本质相同**：用一个单调递增的数字标识"哪一任 Leader"，所有副本拒绝来自旧任的请求——是分布式系统防脑裂的通用招式。

## 六、主从延迟：写后立即读读到旧值

### 6.1 这个问题的本质

异步 / 半同步下 Master 写完返回成功的瞬间，Slave 还没收到。Client 立即去 Slave 读 → 读到旧值。

```
T0: Client write Master → "OK"
T0+1ms: Client read Slave → 旧值
T0+5ms: Slave 同步完成
T0+10ms: Client read Slave → 新值
```

### 6.2 各系统的破解方案

| 方案 | MySQL | Redis | Kafka | RocketMQ |
| --- | --- | --- | --- | --- |
| **强制走主**（关键场景）| ✅ 业务标记走主库 | ✅ 业务标记走主 | N/A（消费总是 Leader）| ✅ 业务配置 |
| **写后等同步**（半同步）| `rpl_semi_sync` | `WAIT` 命令 | acks=all + min.insync=2 | SYNC_MASTER / DLedger |
| **业务侧 read-after-write** | 写完直接返回数据，不再读 | 同左 | N/A | N/A |
| **延迟感知路由** | Sharding-JDBC 检测复制延迟 | 客户端记录 master_offset | N/A | N/A |
| **会话一致性** | GTID + WAIT_FOR_EXECUTED_GTID_SET | replid+offset | N/A | N/A |

**最实用的两招**：① **关键场景强制走主**（最简单，代价是主库压力大）；② **写后返回的接口直接带新数据**给前端（连读都省了）。

### 6.3 不同系统的延迟根因对比

| 系统 | 主要延迟根因 |
| --- | --- |
| MySQL | 从库 SQL 线程回放慢（大事务、长更新、单线程回放）|
| Redis | 网络 RTT（命令流极小，几乎不会卡）|
| Kafka | Follower fetch 间隔 + 网络 |
| RocketMQ | Slave HAClient 拉取间隔 + 刷盘 |
| Raft / ZAB | 多数派中最慢节点的网络 + fsync |

**MySQL 主从延迟是最难治理的**——大事务一来从库延迟动辄几分钟。解法：① 拆大事务；② 5.7+ 开并行复制（`slave_parallel_workers`）；③ 控制单 SQL 影响行数。

→ 细节见 [MySQL/主从复制.md](../MySQL/主从复制.md)

## 七、生产踩坑

### 踩坑 1：Redis repl_backlog 默认 1MB，断网 10s 就触发全量同步

**现象**：Slave 偶发卡顿数十秒 + 主库 CPU 飙到 100%。

**根因**：`repl_backlog_size` 默认 1MB，业务写入 100MB/s 时 10ms 就转一圈。一旦网络抖动 1s，offset 已经被覆盖 → 触发 FULLRESYNC（BGSAVE 出 RDB + 全量传输 + 加载）。

**修复**：
```ini
repl_backlog_size 100mb     # 按写入速率 × 容忍断线时间算
repl-timeout 60             # 默认 60s 复制超时
```

**判断公式**：`repl_backlog_size ≥ 写入字节速率 × 平均断线时间`。同机房断线 30s 是常态，100MB+ 才安全。

### 踩坑 2：MySQL 半同步因 Slave 全挂退化为异步，主库挂数据丢

**现象**：金融业务半夜大促，主库挂掉切到从库后发现少了几千笔交易。

**根因**：半同步配 `rpl_semi_sync_master_timeout=1000` ms。大促压力下从库 fsync 卡住超过 1s → 半同步**自动退化为异步**。退化期间主库继续吃写入但 Slave 没收到，主库挂了这段就丢。

**修复**：① 监控 `Rpl_semi_sync_master_status`（1 = 同步状态，0 = 异步）+ `Rpl_semi_sync_master_no_tx` 计数；② 金融场景上 MGR / Group Replication（多副本写都要多数派 ACK）；③ 提前演练 Slave 异常的降级行为。

### 踩坑 3：RocketMQ 4.x SYNC_MASTER 下 Slave 挂了主也卡死

**现象**：Slave 宕机后 Producer 写入直接超时，整个 MQ 不可写。

**根因**：4.x SYNC_MASTER 必须等 Slave ACK；Slave 挂了没有降级机制，所有写入阻塞到超时。

**修复**：① 升级到 4.5+ 用 DLedger 模式（基于 Raft，多数派承诺即可）；② 临时切回 ASYNC_MASTER（接受丢失）；③ 主备双 Slave 部署，提高单 Slave 故障容忍。

### 踩坑 4：Kafka 开了 unclean.leader.election 选错副本丢消息

**现象**：监控显示某 partition 末尾几千条消息消失了。

**根因**：Leader 挂了，ISR 同时挂了，`unclean.leader.election.enable=true` → 选 OSR 中的 F2 当 Leader → F2 落后的几千条数据被覆盖。

**修复**：① 关键 topic 设 `unclean.leader.election.enable=false` + `min.insync.replicas=2` + `acks=all`，宁可不可写也不丢数据；② 容忍丢失的日志类 topic 可以开，但要明白代价。

### 踩坑 5：MySQL 主从延迟 30 分钟，应用层读到 30 分钟前数据

**现象**：业务投诉"刚下的订单查不到"。

**根因**：主库一个 ALTER TABLE 影响 1 亿行，binlog 几个 GB；从库 SQL 线程单线程回放，回放速度跟不上主库写入速度，延迟越拉越大。

**修复**：① 大表 DDL 用 gh-ost / pt-online-schema-change 在线 DDL 避开复制延迟；② 5.7+ 开并行复制 `slave_parallel_type=LOGICAL_CLOCK`，按事务并行；③ 拆大事务，单 SQL 影响行数限制；④ 业务侧关键查询走主库。

## 八、面试高频追问

### Q1：主从复制为啥都用 WAL 做复制源？

WAL 是已有的"系统所有变更的完整记录"——直接复用，零额外成本。如果不用 WAL，要么自己再造一份"复制日志"（双倍写入开销），要么传输内存数据结构（顺序难定、增量难做）。WAL 顺序、自描述、可截断，天然适合做复制源——这是 WAL 范式的连带红利。

### Q2：异步 / 半同步 / 同步的本质差别？

差别只在 **"Master 何时向 Client 返回成功"**：

- 异步：本地 WAL 写完 → 立即返回（Slave 没收到都不影响）
- 半同步：等"至少 1 个" Slave 收到 → 返回
- 同步：等"所有 / 多数派" Slave 收到 → 返回

性能：异步 > 半同步 > 同步。安全：同步 > 半同步 > 异步。

工程主流是**异步性能 + 半同步兜底**：互联网开半同步（同机房 RTT 1ms 可忽略），金融上多数派共识（Raft / ZAB / MGR）。

### Q3：Kafka 的 ISR 和 Raft 多数派一回事吗？

**思路相同，灵活度不同**。

Raft：副本数 N 固定，必须 N/2+1 ACK 才 commit——数学严格但僵硬。

Kafka ISR：副本集合**动态变化**——慢的 Follower 自动踢出 ISR，不拖累 Leader；恢复后自动加回。配 `min.insync.replicas=2` + `acks=all` 时实现"动态多数派"。

ISR 比 Raft 更工程化——容忍部分副本慢，且 `acks` 可让业务在性能/可靠间灵活切换。

### Q4：Master 挂了选 Slave 升级，怎么避免数据回退？

核心：**选 offset 最大的 Slave**。

- MySQL：MHA / Orchestrator 比对 binlog 位点
- Redis Sentinel：比 `master_repl_offset`
- Kafka：只在 ISR 内选（OSR 数据可能落后）
- Raft：选举投票时比较 lastLogIndex/lastLogTerm，必须比自己新才投

**Raft 的选举安全性约束** 是这套范式的标准答案——"新 Leader 必须包含所有已 commit 的日志"是数学证明过的。

### Q5：脑裂怎么解决？

脑裂 = 老 Master 没真挂（网络隔离），新 Master 选出后两者都写。

通用招式 **fencing + epoch / term**：
- 每次选举生成单调递增的 `epoch / term`
- 所有副本只接受当前 epoch 的写入
- 老 Master 用旧 epoch 写会被拒绝
- 老 Master 自己看到更大 epoch 时主动降级 Follower

例子：Kafka leader epoch、Raft term、ZooKeeper zxid 高 32 位。

附加 fencing：MHA 切换时 SSH 老 Master kill 进程；Redis `min-slaves-to-write` 让老 Master 在没足够 Slave 时拒绝写。

### Q6：写后立即读读到旧值怎么破？

按"简单到复杂"四级：
1. **写完返回数据**：前端直接展示，不再读
2. **关键场景强制走主**：业务标记走 Master
3. **半同步**：MySQL `rpl_semi_sync` / Redis `WAIT`
4. **会话一致性**：客户端记录写入的 GTID/offset，读时等从库追到该位点（`WAIT_FOR_EXECUTED_GTID_SET`）

互联网 99% 用 1 或 2；金融用 3 或 4 + 多数派共识。

### Q7：为什么 RocketMQ 4.x 主从不自动切换？

因为**没有共识协议**，多副本时无法保证"哪个 Slave 数据最新"。错切会数据回退。

设计权衡：4.x 选 **"宁可短暂不可写也不丢"**——人工介入选数据最新的 Slave 手动切。DLedger 模式（基于 Raft）解决了这个问题，所以现代 RocketMQ 集群推荐 DLedger。

### Q8：MySQL 半同步退化为异步的风险？

`rpl_semi_sync_master_timeout=1000ms` 默认。如果 Slave 全挂或网络卡顿超 1s，自动退化为异步。**退化期间发生主挂还是会丢**。

防御：① 监控 `Rpl_semi_sync_master_status`；② 高可靠场景用 5.7+ 的 `AFTER_SYNC` 模式（先复制再 commit，退化期不丢已提交事务）；③ MGR 多副本规避。

### Q9：主从延迟根因都有哪些？

按发生频率：
1. **大事务**：主库瞬间产生几 GB binlog，从库单线程回放慢
2. **DDL**：ALTER TABLE 影响百万行
3. **从库性能差**：磁盘 IO / 内存配置不如主库
4. **网络抖动**：跨机房 RTT 突增
5. **从库被读爆**：读 QPS 太高挤掉回放线程

修复：① 5.7+ 开并行复制 `LOGICAL_CLOCK`；② 大表 DDL 用 gh-ost；③ 从库配置不能比主库差；④ 控制读 QPS 不超过从库一半。

## 九、答题模板（60 秒话术）

> **主从复制 = 把 Master 上的 WAL 同步给 Slave 重做**，换取高可用 + 读扩展 + 容灾。所有有状态系统都有这个范式，差别只在 **Master 何时向 Client 回 ACK**：
>
> ① **异步**：写完本地 WAL 立即返回，Master 挂可能丢——Redis 默认、MySQL 5.6-、RocketMQ ASYNC_MASTER、Kafka acks=1。
>
> ② **半同步**：等"至少 1 个" Slave ACK 才返回——MySQL `rpl_semi_sync`（超时退化异步）、Redis `WAIT` 命令、RocketMQ SYNC_MASTER。性能略降但 Master 挂数据已到至少一从。
>
> ③ **共识 / 多数派**：等多数派 ACK——Raft / ZAB / MGR / RocketMQ DLedger / Kafka acks=all+min.insync=2。任何少数派故障不影响写，多数派承诺即不丢。代价是延迟取决于最慢的多数派、多数派挂掉就不可写。
>
> **Kafka ISR 是动态多数派**——慢的 Follower 自动踢出，不拖累 Leader；配 acks=all+min.insync.replicas 实现可调一致性。比 Raft 灵活，工程化更强。
>
> **Master 挂了选主的核心是选 offset 最大的 Slave 防数据回退**——MySQL 用 binlog 位点比对、Redis 用 master_repl_offset、Kafka 只在 ISR 内选、Raft/ZAB 用日志比较投票。脑裂用 epoch/term 防御。
>
> **写后立即读读到旧值** 四级方案：写完直接返回数据 → 关键场景走主 → 半同步等同步完成 → GTID/offset 会话一致性。
>
> **生产经验**：Redis repl_backlog 必须 100MB+（不是默认 1MB）；MySQL 半同步监控退化；RocketMQ 4.x 用 DLedger 替代手工切换；Kafka 关键 topic 关 unclean.leader.election；主从延迟用并行复制 + 拆大事务治理。
