# 一致性哈希的应用 — Memcached / Dubbo / Nginx / CDN / Redis Cluster 同构与对比

> 引子：
> ① **是什么**：把节点和 key 都哈希到 0~2³² 的环上，**key 顺时针找最近的节点**——节点增减时只影响相邻区段，**绝大多数 key 不需要重映射**。这是 Memcached 客户端、Dubbo 负载均衡、Nginx 一致性哈希、CDN 边缘节点路由的核心算法。
> ② **面试为什么必考**：上一篇《分片+副本》讲了分片范式的整体，本篇深挖"分片规则"那一招——为什么哈希取模在扩容时几乎要重映射所有 key、一致性哈希怎么解决这个、为什么 Redis Cluster **没用**一致性哈希而是 slot。讲清这套对比，立刻显出"懂工程"而非"背算法"。
> ③ **本篇要解决**：① 普通哈希 / 一致性哈希 / Redis slot 的关系 ② 虚拟节点为什么是 150 个 ③ 哪些场景该用一致性哈希、哪些不该 ④ Dubbo / Nginx / Ketama 各自怎么实现。

## 一、为什么需要一致性哈希

### 1.1 普通哈希取模的死穴

最朴素的分片：

```java
node = hash(key) % N
```

工作完美——直到 N 变化的那一刻：

```
N=4 时：
  key="foo"  → hash=12345 → 12345%4 = 1 → 节点 1
  key="bar"  → hash=67890 → 67890%4 = 2 → 节点 2

加一个节点变 N=5：
  key="foo"  → 12345%5 = 0 → 节点 0  ❌ 变了
  key="bar"  → 67890%5 = 0 → 节点 0  ❌ 变了

实验：1000 个 key 在 N: 4→5 时
  几乎 100% 的 key 都映射到不同节点
```

**N 变化时几乎所有 key 都要重映射**——意味着：
- 缓存场景：缓存几乎全部失效 → 雪崩
- 分片存储：几乎全部数据要迁移 → 不可接受

### 1.2 一致性哈希的核心 idea

把节点和 key 都映射到同一个**哈希环**（0~2³²-1）上，**key 顺时针找最近的节点**：

```
哈希环（0 ~ 2^32-1）

                      [Node A] (hash=1000)
                       /
        ┌───────────┐
        │           │
key  ─► │           │ ─► 顺时针找下一个节点
        │           │
        │           │
        │  Node C   │
        │ (hash=    │
        │  3000000) │
        └───────────┘
                       \
                      [Node B] (hash=2000000)

新加节点 D (hash=1500000)：
  原本 hash 在 1000~2000000 区间的 key 归 B
  现在 1000~1500000 归 D，1500000~2000000 还归 B
  ─► 只有 0.05% 的 key 重映射（D 接管的部分）
```

**节点变动时只影响"被接管的环段"上的 key**——这是和普通哈希的根本差别。

## 三、关键机制详解

### 3.1 哈希环不均匀的问题

```
理想：N 个节点均匀分布在环上，每节点接 1/N 的 key
现实：节点 hash 完全随机，环上分布很不均

例：3 个节点的哈希值
  Node A = 1,000,000
  Node B = 1,500,000
  Node C = 4,200,000,000

A 接 (C, A] 这一段，环宽 ≈ 0.094 × 2^32
B 接 (A, B] 这一段，环宽 ≈ 0.012 × 2^32
C 接 (B, C] 这一段，环宽 ≈ 0.894 × 2^32 ← 接了 89% 的 key
```

3 个节点时，C 可能接 89% 的负载——单节点扛爆。这就是为什么需要**虚拟节点**。

### 3.2 虚拟节点：把"一个大节点"打散成 N 个小节点

```
物理节点 A → 虚拟节点 A#1, A#2, ..., A#150
物理节点 B → 虚拟节点 B#1, B#2, ..., B#150
物理节点 C → 虚拟节点 C#1, C#2, ..., C#150

每个虚拟节点 hash 算法不同（如 `hash("A#1")`、`hash("A#2")`）
→ 共 450 个虚拟节点散布在环上 → 接近均匀分布

key 顺时针找虚拟节点 → 反查虚拟节点对应哪个物理节点
```

**150 这个数字怎么来的**：Ketama（Memcached 一致性哈希实现）的经验值。实验：

| 虚拟节点数 / 物理节点 | 负载偏差 |
| --- | --- |
| 1 | 30%+（极不均）|
| 10 | 15% |
| 50 | 8% |
| **150~160** | **< 5%**（工程甜点）|
| 1000 | < 2%（边际收益递减）|

**Ketama 选 160 是工程经验值**——再多内存和环搜索开销不值得。Dubbo 默认 160 也是同一来源。

### 3.3 单节点挂掉的影响

```
3 个物理节点 × 150 虚拟 = 450 个虚拟节点散布

物理节点 B 挂了：
  B 的 150 个虚拟节点全部从环上摘除
  每个虚拟节点接的 key 找下一个虚拟节点（必然是 A 或 C 的）
  
统计学结果：B 的 1/3 流量均匀分摊给 A 和 C
A 接收 1/6 增量，C 接收 1/6 增量
─► 任何其它节点最多多接 1/N 的流量
```

**对比 Redis Cluster**：一个 master 挂了，它的 slave 升 master 接所有 slot——其他节点不受影响。两种方案的"故障接管"语义完全不同。

### 3.4 客户端怎么实现：环 + 二分查找

```java
public class ConsistentHash<T> {
    private final TreeMap<Long, T> circle = new TreeMap<>();
    private final int virtualNodes;
    
    public ConsistentHash(int virtualNodes, Collection<T> nodes) {
        this.virtualNodes = virtualNodes;
        for (T node : nodes) {
            addNode(node);
        }
    }
    
    public void addNode(T node) {
        for (int i = 0; i < virtualNodes; i++) {
            long hash = murmur3(node.toString() + "#" + i);
            circle.put(hash, node);
        }
    }
    
    public T getNode(Object key) {
        long hash = murmur3(key.toString());
        // 顺时针找第一个 >= hash 的节点
        Map.Entry<Long, T> entry = circle.ceilingEntry(hash);
        if (entry == null) {
            // 超过最大 hash，回到环起点
            entry = circle.firstEntry();
        }
        return entry.getValue();
    }
}
```

**关键数据结构是 TreeMap（红黑树）**——O(log N) 查找。N 是虚拟节点总数（如 3 节点 × 160 = 480），查找 ~ 9 步比对就够了。

## 四、为什么 Redis Cluster 不用一致性哈希

这是面试高频深度题。Redis 作者 Salvatore 明确说过 Cluster **没用**一致性哈希，而是用 **16384 个固定 slot**。

### 4.1 两种方案的本质对比

| 维度 | 一致性哈希 | Redis Cluster slot |
| --- | --- | --- |
| **key 怎么定位** | hash(key) → 环 → 顺时针找节点 | CRC16(key) % 16384 → slot → 查 slot 表找节点 |
| **节点数能变** | 任意（每加节点自动分担相邻段）| 节点数不限，但 slot 数永远 16384 |
| **数据迁移粒度** | 相邻环段（精确到 key 哈希值范围）| 单个 slot（约 N/16384 的数据）|
| **节点 → 数据的映射** | 通过哈希环位置间接计算 | slot → node 显式映射表 |
| **均衡性** | 靠虚拟节点（< 5% 偏差）| 显式分配（可手工精确均衡）|
| **支持人工干预** | 不支持（环位置由 hash 决定）| 支持（手动 `cluster setslot` 迁指定 slot）|
| **协调成本** | 客户端 / 控制面感知节点变动 | 节点间 Gossip 同步 slot 表 |

### 4.2 Redis 为什么不选一致性哈希

Salvatore 的设计理由：

**① 可控性**：硬件不均衡时（如 16C 机器 vs 8C 机器），slot 方案可以**手工把更多 slot 分给强机器**——一致性哈希做不到（环上位置由 hash 决定）。

**② 迁移粒度**：slot 是显式概念，**迁一个 slot 一次性迁完，运维清晰**；一致性哈希迁的是"环上 hash 范围"，业务感觉不到。

**③ 哈希标签（HashTag）**：`{user:123}:profile` 和 `{user:123}:cart` 用 `{user:123}` 算 hash 同 slot——多 key 操作可原子。一致性哈希很难支持这种"显式分组"。

**④ 心跳消息**：Gossip 带的是"我负责的 slot 位图"。16384 bit = 2KB，恰好够用且不爆带宽。一致性哈希要带"我覆盖的环段"，描述更复杂。

### 4.3 一句话总结

**一致性哈希是客户端方案、slot 是服务端协调方案**——前者适合无中心场景（Memcached / Dubbo 客户端 / CDN），后者适合有控制面的 Cluster。

## 五、五种应用场景深入

### 5.1 Memcached + Ketama：客户端分片的鼻祖

Memcached 服务端是**多个独立的 KV 实例**，没有"集群"概念。分片由客户端做：

```
客户端配置：memcached-1:11211, memcached-2:11211, memcached-3:11211
客户端用 Ketama 算法：每个节点 160 个虚拟节点散布到环
SET key1 → Ketama 算出归 memcached-2 → 直接连 -2
GET key1 → 同上
```

**精妙之处**：Memcached 服务端零改造——分片全在客户端。但代价是**节点变动要靠配置变更通知所有客户端**。

### 5.2 Dubbo ConsistentHashLoadBalance

```
@Reference(loadbalance = "consistenthash")
private UserService userService;

调用 userService.getUser(userId)：
  Dubbo 把方法参数（如 userId）做一致性哈希
  → 同一个 userId 总是路由到同一个 Provider 实例
```

**为什么有这种需求**：
- 本地缓存命中——同 userId 落到同 Provider，Provider 本地缓存能复用
- 并发安全——同 key 的请求串行处理在同一实例（用本地锁）
- 灰度发布——按 userId 哈希分流量到新版本

**坑**：Provider 上下线时部分 userId 会迁移——业务必须接受"会话粘性偶发漂移"。

### 5.3 Nginx hash consistent

```nginx
upstream backend {
    hash $request_uri consistent;     # 一致性哈希
    server backend1.example.com;
    server backend2.example.com;
    server backend3.example.com;
}
```

**关键 `consistent` 关键字**——加了用 ketama 一致性哈希，不加是普通 hash 取模。

**应用场景**：
- 反代缓存：同 URL 永远到同后端，最大化缓存命中
- 灰度：`hash $cookie_userid consistent` 让同用户固定走同后端
- 会话粘性：`ip_hash` 是另一种实现（但它**不是真·一致性哈希**，是普通取模）

**`ip_hash` 不是一致性哈希——这是一个常见误解**。`ip_hash` 用的是普通 hash，加节点就会大面积重映射。`hash $remote_addr consistent` 才是真正的一致性哈希。

→ 细节见 [Middleware/Nginx.md](../Middleware/Nginx.md)

### 5.4 CDN 边缘节点路由

```
用户请求 https://cdn.example.com/video.mp4
  ↓
DNS 解析到最近的 PoP 节点
  ↓
PoP 节点内部多个缓存服务器 → 一致性哈希(URL) → 选具体服务器
  ↓
同一个 URL 永远在同一服务器上 → 最大化缓存命中
```

**CDN 是一致性哈希的"教科书"应用**：
- 节点数大（一个 PoP 几十台缓存）
- 缓存命中率至关重要（重映射 = 缓存失效 = 回源压力暴涨）
- 节点上下线频繁

加节点时只迁移环上的一段，老缓存大部分还能命中——这是 CDN 经济性的核心。

### 5.5 MySQL 分库分表——一般不用一致性哈希

**反直觉**：分库分表场景一般用 **取模 + 双倍扩容** 而非一致性哈希：

```
4 库分片：user_id % 4 → 0~3 号库
扩容到 8 库：user_id % 8 → 0~7 号库
迁移方式：每个老库的数据分一半到对应新库
  老库 0 → 新库 0 + 4
  老库 1 → 新库 1 + 5
  ...
```

为什么不用一致性哈希：
- DB 扩容次数极少（一年 1~2 次），不需要"加节点只迁移 1/N"
- 取模方案数据迁移粒度清晰、可预测
- DB 分库分表的核心痛点是 **跨库 JOIN / 事务**，不是节点变动

**所以一致性哈希主要用于"节点频繁变动"的场景**——缓存、负载均衡、CDN 都符合；DB 分片几乎不用。

## 六、生产踩坑

### 踩坑 1：客户端配置不一致，缓存大面积穿透

**现象**：Memcached 集群 5 节点，加一台到 6 节点。当晚 CDN 缓存命中率从 95% 跌到 60%，后端 QPS 翻倍。

**根因**：客户端配置变更**没有同时滚动重启**所有应用——有的客户端看到 5 节点、有的看到 6 节点，Ketama 算出的归属节点不一致——大量 key 在两种配置下落到不同节点。

**修复**：① 改 Memcached 服务端的元数据中心化（如 Mcrouter）；② 客户端配置变更必须严格"一次性切换"；③ 加节点时做"流量预热"——新节点上线后先 dual-write 让缓存预热再切流量。

### 踩坑 2：虚拟节点数太少，3 节点时一台扛 60%

**现象**：自研一致性哈希客户端，3 节点压测时发现单节点 QPS 是其他两台的 3 倍。

**根因**：虚拟节点数配了 32，对 3 个物理节点来说太少——环上分布严重不均。Ketama 默认 160 也是有道理的。

**修复**：虚拟节点数提到 150~200。**永远不要少于 150**。

### 踩坑 3：Nginx ip_hash 在 NAT 后所有用户都到同一后端

**现象**：用 `ip_hash` 做 session 粘性，但发现公司内网用户都被路由到同一后端。

**根因**：办公网 NAT 后所有内部用户共享一个出口 IP——`ip_hash` 看到的都是同 IP，全部去同一后端。

**修复**：① 用 `hash $cookie_session consistent`——按 cookie 而不是 IP；② 业务侧迁移到无状态：把 session 存 Redis，所有后端共享；③ 生产基本不推荐 `ip_hash`——它是 10 年前的方案。

### 踩坑 4：Dubbo 一致性哈希看似均衡但热点用户打爆 Provider

**现象**：Dubbo 用一致性哈希后某 Provider CPU 100%，其它 50%。

**根因**：一致性哈希均衡的是"key 分布"，但**热点 key 仍然集中到一个节点**。某大客户 userId 单独占 30% 流量——全压在一台 Provider 上。

**修复**：① 一致性哈希适合"key 分布均匀"的场景，热点场景反而不适合；② 热点 key 单独走"加权随机"而不是一致性哈希；③ 接受"一致性哈希不解决业务热点"的局限。

### 踩坑 5：迁移过程中读到旧节点的数据

**现象**：缓存节点扩容期间业务报错"数据不一致"——某些请求拿到的还是老数据。

**根因**：一致性哈希迁移是**逐 key 迁**，迁移期间同一个 key 可能在老节点（旧值）和新节点（新值）都有副本。客户端按新环路由去新节点，但新节点可能还没拿到老数据。

**修复**：① 类似 Redis Cluster 的 MOVED/ASK 双重定向（但 Memcached 客户端方案通常没有）；② 迁移期间"穿透回源"——找不到的 key 从 DB 读重建缓存；③ 灰度切换流量（先 1% 客户端用新环，验证后全量）。

### 踩坑 6：CDN 节点维护时一段时间 5% 用户命中率为零

**现象**：CDN 单节点维护 30 分钟，监控显示这 30 分钟约 5% 用户的命中率为零。

**根因**：节点下线 → 它负责的 5% URL 范围迁移到相邻节点 → 相邻节点没有这 5% URL 的缓存 → 回源——这 30 分钟正常。

**修复**：本来就是正常现象——一致性哈希的"故障接管"代价就是接管段的临时缓存失效。运维侧：① 维护安排在低峰；② 节点下线前先 drain（流量逐步切走 + 邻居节点预热）；③ 多副本一致性哈希（每 key 写多个节点，主节点挂还能命中副本）。

## 七、面试高频追问

### Q1：一致性哈希怎么解决普通哈希取模的扩容问题？

普通哈希 `hash(key) % N`：N 变化时几乎所有 key 都映射到新节点——大量数据迁移 / 缓存失效。

一致性哈希：节点和 key 都映射到 0~2³² 的环上，key 顺时针找最近节点。**加一个节点只影响环上相邻一段**——只有 1/N 的 key 需要重映射。

### Q2：为什么需要虚拟节点？多少合适？

**节点 hash 完全随机**，N 个节点 hash 后不一定均匀落环——可能一个节点接 80% 流量。

虚拟节点：每个物理节点对应 N 个虚拟节点（不同 hash），散布到环——大数定律下分布趋于均匀。

经验值：**150~160 个虚拟节点**（Ketama / Dubbo 默认），实测分布偏差 < 5%。再多收益递减且内存/查找开销大。

### Q3：Redis Cluster 为什么不用一致性哈希？

四个理由：① **可控性**——slot 可手工分配，硬件不均衡时强机器多分 slot；② **迁移粒度**——slot 是显式概念，运维清晰；③ **HashTag 支持**——`{user}:profile` 和 `{user}:cart` 同 slot 可原子操作；④ **心跳消息**——16384 bit slot 位图 = 2KB 刚好。

**本质区别**：一致性哈希是客户端方案、slot 是有控制面的服务端协调方案。Redis Cluster 有 Gossip 协调，所以能用 slot。

### Q4：Memcached 和 Redis Cluster 分片方案为什么不同？

Memcached 服务端**没有集群概念**，每个实例是独立的——必须客户端分片。一致性哈希是天然选择。

Redis Cluster 有节点间 Gossip 协议**协调元数据**——能维护 slot → node 的映射表，所以可以用 slot 方案。

总结：**有协调能力用 slot，无协调能力用一致性哈希**。

### Q5：一致性哈希迁移时数据怎么处理？

两种思路：
1. **客户端缓存方案**（Memcached）：扩容后**老缓存失效**，业务读穿透到 DB 重建——能容忍是因为缓存本身就是"有损"的
2. **服务端协调方案**（Redis Cluster slot）：MOVED / ASK 双重定向 + slot 显式 setslot——能保证迁移过程中数据可访问

一致性哈希客户端方案没有内置的"迁移协议"——扩容代价是缓存命中率短暂下降。

### Q6：Nginx 的 `ip_hash` 是一致性哈希吗？

**不是**。`ip_hash` 是普通哈希取模——加节点会大面积重映射。

真正的一致性哈希是 `hash $key consistent`——加 `consistent` 关键字才用 ketama 一致性哈希。

`ip_hash` 还有更严重的问题：办公网 NAT 后所有用户共享 IP——全部路由到同一后端，session 粘性变热点。生产基本不推荐 `ip_hash`，用 `sticky cookie` 或无状态服务 + Redis session。

### Q7：一致性哈希能解决热点问题吗？

**不能**。一致性哈希均衡的是"key 分布"，但**热点 key 仍集中到一个节点**。

例：1000 个 key 中 999 个均匀分布、1 个 key 占 50% 流量——一致性哈希让这 1 个 key 完全压到一台节点。

热点的真正解法：① key 拆分（如 `hotkey:1`、`hotkey:2`...）；② 多副本读（hot key 写多个节点客户端随机读）；③ 本地缓存。一致性哈希解决不了。

### Q8：节点挂了的时候哈希环怎么变？

物理节点 B 挂掉：B 的 150 个虚拟节点全部从环上摘除。B 原本接的 key 顺时针找下一个节点——必然是 A 或 C 的某个虚拟节点。

**统计学结果**：B 的流量被**均匀分摊**给 A 和 C，每个节点最多多接 1/N。这是虚拟节点的关键价值——单节点故障不会把流量打集中。

**vs Redis Cluster**：单 master 挂 slave 顶上接走 master 的所有 slot——其他 master 不受影响。两种方案的"故障接管"语义完全不同。

### Q9：Dubbo 一致性哈希什么场景用？

三种场景：
1. **Provider 本地缓存**：同 key 总路由到同实例，缓存命中
2. **并发安全**：同 key 串行处理在同一实例
3. **灰度发布**：按用户哈希分流

**坑**：① 不解决热点；② Provider 上下线时部分 key 会漂移——业务必须能容忍。

### Q10：一致性哈希算法本身的时间复杂度？

虚拟节点用 TreeMap（红黑树）存——O(log N) 查找，N 是虚拟节点总数。

3 物理节点 × 160 虚拟 = 480 个，查找 ~ 9 步——纳秒级。完全不是性能瓶颈。

## 八、答题模板（60 秒话术）

> **一致性哈希解决普通哈希取模的"扩容大迁移"问题**：把节点和 key 都映射到 0~2³² 的环上，key 顺时针找最近节点——加节点只影响环上相邻一段，**只有 1/N 的 key 需要重映射**，对比普通哈希几乎全部重映射。
>
> **核心配套是虚拟节点**：每物理节点对应 150~160 个虚拟节点散布到环——大数定律下分布偏差 < 5%。Ketama / Dubbo 默认 160 是工程经验值。
>
> **五种典型应用**：① **Memcached + Ketama**：客户端分片鼻祖；② **Dubbo ConsistentHashLoadBalance**：本地缓存命中 + 灰度；③ **Nginx hash $key consistent**：反代缓存命中（注意 `ip_hash` 不是一致性哈希）；④ **CDN 边缘路由**：最大化缓存命中；⑤ **MySQL 分库分表**：一般用取模而不用一致性哈希（扩容罕见，运维清晰更重要）。
>
> **Redis Cluster 不用一致性哈希**——用 16384 个固定 slot 二级路由。理由：① slot 可手工分配（强机器多分）；② 迁移粒度清晰（一个 slot 一次性迁完）；③ 支持 HashTag 显式分组；④ 心跳带 slot 位图 2KB 合适。**本质区别**：一致性哈希是客户端方案、slot 是服务端协调方案——Redis 有 Gossip 协调，所以能选 slot。
>
> **关键局限**：① 不解决热点 key（均衡是按 key 分布、不按访问量）；② 客户端方案迁移时缓存命中率短暂下降；③ ip_hash 在 NAT 后全部集中到一节点。
>
> **生产坑**：① 客户端配置不一致导致 key 归属节点不同；② 虚拟节点 < 150 时分布严重不均；③ Nginx ip_hash 是普通哈希不是一致性哈希；④ Dubbo 一致性哈希热点用户打爆单 Provider；⑤ CDN 节点维护时接管段命中率为零。
