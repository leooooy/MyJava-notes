# 幂等与重试 — 接口防重 / 重试退避 / MQ 去重 / RPC 重试同构设计

> 引子：
> ① **是什么**：分布式世界里**网络一定会丢、调用一定会重试、消息一定会重复**——任何会被重试的接口都必须幂等。"重试"和"幂等"是一对孪生兄弟：前者解决"调用方不知道对方是否成功"，后者解决"对方收到多次重复请求时业务不出错"。
> ② **面试为什么必考**：每个会做支付 / 下单 / MQ 消费的人都被问过——重复扣款怎么防？MQ 至少一次怎么去重？POST 接口能不能重试？前端连点两下提交怎么挡？这是大厂 P6+ 业务面试的"高频必考压舱石"。
> ③ **本篇要解决**：① 幂等键怎么选才不踩坑 ② 6 种主流幂等方案的取舍 ③ 重试为什么要带退避 + 熔断 ④ 重试 + 幂等的边界在哪、什么场景不需要幂等。

---

## 一、为什么需要幂等

### 1.1 原始问题：网络的不可靠

任何分布式调用都面临**"三态问题"**：

```
Client → Server
  │
  │  调用请求
  ▼
Server 处理 → 写 DB
  │
  ▼
返回响应（这一步可能丢）
  │
  ├─ Client 收到：✅ 成功
  ├─ Client 收到错误：❌ 失败
  └─ Client 超时 / 网络断：❓ 未知 ← 关键
```

**第三态是分布式系统所有麻烦的源头**：Server 到底成没成？Client 不知道。

```
Client 处理"未知"的两条路：
① 不重试 → 万一 Server 没成功，业务丢数据
② 重试   → 万一 Server 之前成功了，业务执行两次
```

绝大多数业务选 ② —— **重试 + 让 Server 端幂等**。这是分布式系统的工程妥协。

### 1.2 重试和幂等的关系

```
重试解决"调用方不知道对方是否成功"
  ─► 让 Client 重发请求

幂等解决"对方收到多次相同请求时业务不出错"
  ─► 让 Server 第二次以后的请求识别为"已处理"

两者必须配对——只重试不幂等会重复扣款，只幂等不重试会丢数据。
```

### 1.3 哪些操作天然幂等

| 操作 | 幂等？ | 说明 |
| --- | --- | --- |
| `SELECT *` | ✅ | 查询不改状态 |
| `DELETE WHERE id=1` | ✅ | 删多次结果一样 |
| `UPDATE x SET status='paid' WHERE id=1` | ✅ | 状态机幂等（值已经是目标态）|
| `UPDATE x SET counter=counter+1` | ❌ | 重复执行结果不同 |
| `INSERT INTO t VALUES(...)` | ❌ | 重复 insert 多条记录 |
| `INSERT INTO t(id, ...) VALUES(1, ...)` | ✅ | 有唯一约束 + 主键冲突报错可以视为成功 |

**RESTful 语义**：GET / PUT / DELETE 天然幂等，POST 不幂等（要业务设计）。

## 二、共性骨架：幂等的核心三件套

### 2.1 通用流程

```
请求来 ──► [服务端处理]
            │
            ├─ ① 找到"幂等键"（识别这次操作）
            │
            ├─ ② 原子地"占位 + 判重"
            │   ├─ 第一次：占位成功 → 继续业务
            │   └─ 重复：占位失败 → 返回上一次的结果（或视为成功）
            │
            ├─ ③ 执行业务
            │
            └─ ④ 记录"幂等键 → 业务结果"
```

**三件套**：① 幂等键 ② 占位 + 判重的原子操作 ③ 结果记录。

### 2.2 幂等键怎么选

| 来源 | 适用 | 案例 |
| --- | --- | --- |
| **业务自带 ID** | 创建类（订单/交易）| 订单号、交易流水号 |
| **客户端生成 UUID** | 前端发起 | 每次请求带一个唯一 nonce |
| **服务端预发 token** | 强幂等场景 | 表单提交前 GET 一个 token，提交时带 token |
| **MQ 消息 ID** | 消费幂等 | RocketMQ msgId / 业务 messageKey |
| **业务键组合** | 必须自然唯一 | "用户 ID + 商品 ID + 业务日期" |

**反面教材**：用"用户 ID + 商品 ID"做幂等键——同一用户买同一商品两次都被当成重复，第二次买就吃了。**幂等键必须能区分"两次合理操作"和"一次操作的重试"**。

### 2.3 幂等的窗口和颗粒度

**窗口 TTL**：幂等不是永久的，要明确多久内防重——
- 接口防重提交：5~10 分钟（覆盖前端重试 + 用户连点）
- 支付幂等：T+1 或更长（覆盖对账周期）
- MQ 消费幂等：3~7 天（覆盖最长重试窗口）

**颗粒度**：接口级 ≠ 业务级。下单接口幂等了，但库存扣减接口没幂等 → 整体仍然超扣。**幂等必须在每一段会被重试的边界上都做**。

## 三、六种主流幂等方案

### 3.1 全表对比

| 方案 | 性能 | 强度 | 业务侵入 | 典型场景 |
| --- | --- | --- | --- | --- |
| **数据库唯一约束** | 中 | ⭐⭐⭐⭐⭐ | 低 | 创建类接口兜底 |
| **乐观锁（version）** | 高 | ⭐⭐⭐⭐ | 中 | 更新类操作 |
| **业务状态机** | 高 | ⭐⭐⭐⭐ | 中 | 订单 / 支付状态流转 |
| **Token / 防重 Token** | 中 | ⭐⭐⭐ | 高 | 表单提交、前端连点 |
| **分布式锁** | 低 | ⭐⭐⭐ | 中 | 高并发临时去重 |
| **DB 去重表 + 业务表同事务** | 低 | ⭐⭐⭐⭐⭐ | 中 | 强一致场景（金融）|

### 3.2 数据库唯一约束（最便宜的兜底）

```sql
CREATE TABLE order_t (
    id BIGINT PRIMARY KEY,
    biz_order_no VARCHAR(64) UNIQUE,    -- 业务幂等键
    ...
);

INSERT INTO order_t(id, biz_order_no, ...) VALUES(...);
-- 第二次 insert 报 Duplicate entry → 视为成功（或返回已存在的订单）
```

**优势**：
- 几乎零成本（加唯一索引就完事）
- 强一致（DB 保证）
- 无任何业务侵入

**生产建议**：**所有创建类接口都加唯一键兜底**——哪怕业务层已经有别的幂等机制。

### 3.3 乐观锁（更新类的标准方案）

```sql
UPDATE balance SET amount = amount - 100, version = version + 1
WHERE user_id = 123 AND version = 5;
-- 影响行数 = 1 → 成功；= 0 → 已被改过，重复请求被挡
```

**核心**：上一篇《版本号与 CAS》里讲过的范式——读时拿版本、写时带版本、版本匹配才写。

### 3.4 业务状态机（最优雅）

```sql
-- 订单从 PENDING 变成 PAID
UPDATE order_t SET status = 'PAID' WHERE id = 123 AND status = 'PENDING';
-- 重复支付请求：第二次 status 已经是 PAID → WHERE 不命中 → 影响行数 0 → 视为重复
```

**优势**：
- 无需额外去重表 / token
- 天然契合业务（状态本身就有意义）
- 即使去重表挂了，状态机仍然防重

**前提**：业务有清晰的状态机。"状态从 A 只能到 B"这种约束本身就是天然的幂等。

### 3.5 Token / 防重 Token（前端防连点）

```
1. 用户进入页面：GET /api/order/token → 返回 token=abc123
2. 用户提交表单：POST /api/order { token: "abc123", ... }
3. 服务端：SETNX redis "token:abc123" 1 EX 600
   ├─ 成功 → 处理订单
   └─ 失败 → 重复提交，返回上次结果
```

**适用**：表单提交、防止前端连点 / 用户网络重连重发。

**坑**：
- token 一旦使用立即失效——但如果业务处理失败，用户无法重试（要业务侧 token 复用机制）
- 跨进程必须用 Redis 而不是本地 map

### 3.6 分布式锁（临时去重）

```
String key = "idempotent:" + bizKey;
if (redisLock.tryLock(key, 5, TimeUnit.MINUTES)) {
    try { 
        // 检查业务是否已经处理
        if (alreadyDone()) return prevResult();
        process();
    } finally {
        // 不主动释放——靠 TTL 自然过期才能挡后续重试
    }
} else {
    return prevResult();  // 别人正在处理或刚处理完
}
```

**缺点**：① 锁本身有成本（Redis RTT）；② 处理失败后续重试要等锁过期；③ 集中式存储依赖。

**适用**：高并发临时去重，作为前置过滤。**通常和"DB 唯一约束"配合使用**——锁是高性能前置过滤、唯一约束是兜底强保证。

### 3.7 DB 去重表 + 业务表（同事务，最强一致）

```sql
BEGIN;
INSERT INTO dedup_log(biz_key) VALUES('order-123');  -- 唯一约束
INSERT INTO order_t(...) VALUES(...);
COMMIT;
```

**核心**：去重和业务在**同一个本地事务**——要么都成功要么都失败，绝不会出现"去重记录了但业务没执行"或"业务执行了但去重没记录"。

**金融场景**：扣款 / 转账这种"绝对不能丢、绝对不能重"的场景，几乎都用这种。

→ 细节见 [Distributed/幂等.md](../Distributed/幂等.md)

## 四、重试：什么时候重试、怎么重试

### 4.1 三种失败语义

调用方收到错误时要先识别**失败类型**：

| 类型 | 例子 | 该不该重试 |
| --- | --- | --- |
| **业务失败** | 余额不足 / 参数错 | ❌ 不重试（重多少次都失败）|
| **明确未执行** | 网络拒接 / 503 / 限流 | ✅ 可以重试（对方没收到）|
| **未知** | 超时 / 连接断 | ⚠️ 重试要求对方幂等 |

**错误的做法**：所有失败一律重试 N 次——可能业务参数错误重试 5 次还失败，浪费资源 + 拖累 RT。

### 4.2 重试的"退避"为什么必须做

```
错误做法：失败立即重试
  T=0    请求失败
  T=0.01 重试 1 失败
  T=0.02 重试 2 失败
  T=0.03 重试 3 失败
  → 0.03 秒内打了 4 倍流量，本来下游就慢更卡死

正确做法：指数退避 + jitter
  T=0     失败
  T=1s    重试 1（基础间隔 1s）
  T=3s    重试 2（×2 + 抖动）
  T=7s    重试 3
  T=15s   重试 4 → 给下游恢复时间
```

**指数退避公式**：`delay = base × 2^retry + random(0, jitter)`
- base：基础间隔（如 1s）
- 2^retry：指数增长（防雪崩）
- random jitter：随机抖动（**防重试风暴对齐**）

**为什么 jitter 必须有**：100 个 client 同时失败，全部 1s 后重试——下游瞬间 100 倍流量。加随机抖动让重试时间分散，下游平滑接 traffic。

### 4.3 重试风暴 / 雪崩

```
A 调 B 超时 → A 重试 3 次 → 实际向 B 发了 4 次请求
B 调 C 超时 → B 重试 3 次 → 4 次

如果 B 调 C 出问题：
  A 一次请求 → B 实际处理 1 次成功 / 4 次失败
  A 重试 → B 又 1 + 4
  → A 一次失败给 C 放大成 16 次请求
  
3 层调用链 + 每层重试 4 次 → 放大 64 倍
```

**生产防御**：
- 重试预算：调用链上**只有一层做重试**（通常是边缘 / 最外层），中间层不重试
- 熔断器：错误率超阈值直接熔断不再重试
- 限流：自我保护防止重试打爆自己

### 4.4 哪些请求可以重试

| 操作 | 可重试？ |
| --- | --- |
| 读（GET 类）| ✅ 天然安全 |
| 写但幂等（PUT / 已设计幂等的 POST）| ✅ |
| 写但不幂等的 POST | ❌ 除非业务能容忍偶尔重复 |
| 已经收到业务级错误（如余额不足）| ❌ 重试也是失败 |
| 超时但不确定对方状态 | ⚠️ 要求对方幂等才能重 |

**Feign 默认不重试**——就是因为不知道业务接口是否幂等，不敢替业务做决定。

### 4.5 重试 + 幂等的边界

```
重试位置                  幂等责任
───────────────────────────────────────
浏览器自动重试           ── 不可控，前端 + 后端都要防
HTTP 客户端重试          ── 调用方决定开关
Feign / RPC 重试         ── 配置开关
MQ 消费重试              ── 必然发生（at-least-once）
网关层重试               ── 通常关，避免重试风暴
分布式事务回查           ── 必然发生（RocketMQ 事务消息）
```

**核心原则**：**只要存在重试，被调用方必须幂等**。无论你信不信对方"配了重试"，**所有写接口都应该幂等**——这是分布式系统的基本卫生。

## 五、五种场景的具体应用

### 5.1 RPC 调用（Feign / Dubbo）

```yaml
feign:
  client:
    config:
      default:
        connect-timeout: 2000
        read-timeout: 5000

# 重试只对 GET 类开（业务级写接口必须设计幂等才能开）
spring:
  retry:
    initial-interval: 1000
    max-attempts: 3
    multiplier: 2.0
```

**关键**：Feign 默认不重试。**写接口要重试必须先设计幂等**。

### 5.2 MQ 消费（必然重复）

RocketMQ / Kafka 是 **at-least-once 语义**——消息一定会被消费，但可能消费多次。

消费方必须幂等：

```java
@RocketMQMessageListener(topic = "order-paid")
public class OrderPaidConsumer implements RocketMQListener<OrderMsg> {
    @Override
    public void onMessage(OrderMsg msg) {
        // 用 messageKey 或业务 ID 做幂等键
        String key = "msg_dedup:" + msg.getMsgId();
        if (!redis.setIfAbsent(key, "1", 7, DAYS)) {
            return;  // 已消费过
        }
        process(msg);
    }
}
```

**坑**：① Redis 挂了去重表失效——配合 DB 唯一约束兜底；② 业务异常时 redis key 已设但业务没成功——要 Lua 原子（业务成功才标记）或异常回滚。

→ 细节见 [MQ/重复消费与幂等.md](../MQ/重复消费与幂等.md)

### 5.3 接口防重提交（前端连点）

```
前端：用户点击"提交订单"按钮
  ├─ 立即 disable 按钮（前端兜底）
  ├─ 调用 POST /api/order
  
后端：
  1. Token 机制：进入页面时 GET token，提交时校验 + 删除
  2. 唯一键：业务键（订单号）+ DB 唯一约束
  3. 限流：单用户限频
```

**生产组合**：**前端 disable + 后端 token + DB 唯一约束**三层防御——前端兜底用户体验，后端保证最终正确。

### 5.4 支付场景（最严的幂等）

```
支付场景的特殊性：
- 重复扣款 = 资金损失（不可逆）
- 漏扣款 = 业务损失（用户没付钱拿到货）

通常做法：
  ① 前端：disable + 防连点
  ② 接口层：业务订单号唯一约束
  ③ 业务层：状态机（PENDING → PAID 不可逆）
  ④ 资金层：流水表唯一约束 + 同事务
  ⑤ 第三方支付：对账平台兜底（T+1 校验）
```

5 层防御——任何一层出问题其他层都能挡。**支付场景的幂等是"过度设计"也不为过**。

### 5.5 分布式事务回查（必然重复）

RocketMQ 事务消息回查、Seata 重试、TCC Confirm/Cancel——**所有"协调者重试"的场景都要参与方幂等**。

```java
public LocalTransactionState checkLocalTransaction(MessageExt msg) {
    // 多次回查必须返回相同结果（基于业务真实状态）
    Order order = orderDao.findByMsgKey(msg.getKeys());
    return order != null ? COMMIT_MESSAGE : ROLLBACK_MESSAGE;
}
```

回查的"自然幂等"靠业务查询——查到就 COMMIT、没查到就 ROLLBACK，多次查询结果一致。

## 六、生产踩坑

### 踩坑 1：幂等键选错，同一用户买同一商品被去重

**现象**：电商业务上线后，"用户连买两个同款商品"只成单一个。

**根因**：幂等键用了 "user_id + product_id"——同一用户两次购买的幂等键相同，第二次被识别为重复请求挡掉。

**修复**：用客户端生成的唯一 nonce 或业务订单号作为幂等键——**幂等键必须能区分"两次合理操作"和"一次操作的重试"**。

### 踩坑 2：MQ 消费业务异常时 Redis 去重已写入，导致丢消息

**现象**：MQ 消费日志显示某些订单"已消费但业务无记录"。

**根因**：消费者先 `redis.set(key, 1)` 标记已消费，再处理业务——业务报错时 Redis 已经记了，重试又被 Redis 挡掉——消息被吞。

**修复**：① 调换顺序：业务成功后再标记 Redis；② 用 DB 去重表 + 业务表同事务（强一致）；③ Redis 标记 + Lua 原子（业务报错时回滚 Redis 标记）。

**通用原则**：**"标记幂等"和"执行业务"要在同一原子操作里**——不能分开做。

### 踩坑 3：Feign 默认开重试，POST 接口重复扣款

**现象**：客户反馈某笔订单被扣了两次款。

**根因**：项目 Feign 配了 `Retryer.Default()`——所有失败请求重试 5 次。某次 POST 请求成功执行但响应超时 → Feign 重试 → 服务端二次扣款。

**修复**：① Feign 默认就别开重试（除非确认接口幂等）；② 业务侧加幂等设计（订单号唯一约束）；③ 区分读 / 写——读接口允许重试，写接口默认禁用。

### 踩坑 4：重试风暴打爆下游

**现象**：下游 API 单次故障期间被打了平时 50 倍流量。

**根因**：调用链 5 层，每层都配了"失败重试 3 次"——一次根本失败被放大成 3^5 = 243 倍。

**修复**：① **重试预算**——调用链只有最外层做重试，中间层不重试；② 重试指数退避 + jitter；③ 熔断器在错误率超阈值时直接快速失败不再重试。

### 踩坑 5：Token 用了一次就失效，业务失败用户重试不了

**现象**：用户提交订单失败，再点提交报"重复提交"。

**根因**：Token 用了一次（无论业务成功失败）就被删了——用户重试无 token。

**修复**：① 业务成功才删 token（失败时保留让用户重试）；② 失败页面引导用户重新进入下单页（重新发 token）；③ Token 设短 TTL（5 分钟），失败后让用户自然过期重发。

### 踩坑 6：去重表无限膨胀

**现象**：MQ 消费去重表跑了半年涨到 50 亿行，查询慢、磁盘满。

**根因**：去重表只增不减，从来不清理。

**修复**：① 按业务窗口清理（如 MQ 7 天前的数据删）；② 用 Redis 替代 DB 做去重（自带 TTL）；③ 分区表 + drop 老分区（比 delete 快）；④ 业务允许的话用状态机替代去重表（无额外存储）。

## 七、面试高频追问

### Q1：幂等和重试什么关系？

**孪生兄弟**：
- 重试解决"调用方不知道对方是否成功" → 让 Client 重发
- 幂等解决"对方收到多次相同请求时业务不出错" → 让 Server 识别重复

两者必须配对——只重试不幂等会重复扣款，只幂等不重试会丢数据。

### Q2：哪些操作天然幂等？

- 读（SELECT）天然幂等
- 删（DELETE WHERE）天然幂等
- 状态机式 UPDATE（如 `SET status='PAID' WHERE status='PENDING'`）幂等
- 带唯一约束的 INSERT 幂等（重复报错视为成功）

不幂等：自增 UPDATE（counter+=1）、不带唯一约束的 INSERT。

RESTful 语义：GET / PUT / DELETE 幂等，POST 不幂等。

### Q3：幂等键怎么选？

| 来源 | 适用 |
| --- | --- |
| 业务自带 ID（订单号 / 交易流水）| 创建类 |
| 客户端 UUID / nonce | 任何客户端发起场景 |
| 服务端预发 token | 表单提交 |
| MQ 消息 ID | 消费幂等 |

**铁律**：幂等键必须**唯一标识这次操作**，不能和"业务上下文"混用——拿 "user_id + product_id" 当幂等键会把"同一用户买两次"误认为重复。

### Q4：六种幂等方案怎么选？

按场景：
- **创建类**：业务 ID + DB 唯一约束（最便宜）
- **更新类**：乐观锁 version 字段
- **状态流转**：业务状态机（最优雅）
- **表单提交**：服务端预发 token
- **高并发临时去重**：Redis 分布式锁
- **强一致金融场景**：DB 去重表 + 业务表同事务

实际生产**多层叠加**——前端 disable + token + 唯一约束 + 状态机，任何一层挂了其他层兜底。

### Q5：重试为什么要带退避和 jitter？

**退避**：失败立即重试会**加重下游负担**——本来下游就快炸了，你还放大流量。指数退避（1s → 3s → 7s）给下游恢复时间。

**Jitter（随机抖动）**：100 个 client 同时失败、整齐 1s 后重试 → 下游瞬间 100 倍流量。加随机抖动让重试时间分散，平滑接 traffic。

### Q6：怎么防止重试风暴？

四招组合：
1. **重试预算**：调用链上只有最外层做重试，中间层一律不重试
2. **指数退避 + jitter**：基础间隔指数增长 + 随机抖动
3. **熔断器**：错误率超阈值（如 50%）直接快速失败不再重试
4. **限流**：自我保护防止重试爆量打爆自己

调用链 5 层各重试 3 次 → 放大 3^5 = 243 倍；用了重试预算 → 只有最外层重试 → 最多 3 倍。

### Q7：MQ 消费幂等怎么做？

**消息一定会重复消费**（at-least-once）——必须在消费方做幂等：

1. **Redis 去重表**：性能高，配合 TTL 自动清理；缺点是 Redis 挂了去重失效
2. **DB 唯一约束**：强一致；性能较低；表会膨胀要定期清
3. **业务状态机**：UPDATE WHERE 检查前置状态，无需额外去重表（最优雅）
4. **DB 去重表 + 业务表同事务**：金融级强一致

生产组合：业务状态机为主 + DB 唯一约束兜底。

### Q8：Feign / Dubbo 重试默认开不开？

**Feign 默认不重试**——因为不知道业务接口是否幂等，不敢替业务做决定。开重试要先确认接口幂等。

**Dubbo 默认重试 2 次**——历史遗留，**生产建议明确改成 0 或只对读接口开**。

### Q9：哪些场景"不需要"幂等？

理论上**任何会被重试的接口都必须幂等**。但有些场景退而求其次：
- 重复操作的代价可接受（如日志 / 监控写入，多写一条无所谓）
- 业务已经在更高层保证不会重试（如完全同步的内部调用）
- 业务能容忍幂等失败（如某些"宽松一致"的统计）

**金融 / 库存 / 支付场景永远要幂等**——任何接口都可能被网络层无感知地重试。

### Q10：怎么解决去重表无限膨胀？

四招：
1. **TTL 清理**：按业务窗口（如 7 天）定期删
2. **Redis 替代**：Redis 自带 TTL，到期自动清
3. **分区表 + drop 老分区**：比 DELETE 快得多
4. **业务状态机替代**：能用状态机就不用去重表

设计阶段就要考虑去重表的生命周期，不能等出问题再补。

## 八、答题模板（60 秒话术）

> **幂等和重试是分布式系统的孪生兄弟**：网络一定会丢、调用一定要重试、消息一定会重复——所以任何会被重试的接口都必须幂等。
>
> **幂等的核心三件套**：① **幂等键**（订单号 / 客户端 UUID / token / 消息 ID）；② **原子的占位 + 判重**（DB 唯一约束 / Redis SETNX / 同事务去重）；③ **结果记录**（让重复请求返回上次结果）。
>
> **六种主流方案**：
>
> ① **DB 唯一约束**——最便宜的兜底，所有创建类接口都该加；
>
> ② **乐观锁 version**——更新类标准方案（《版本号与 CAS》的应用）；
>
> ③ **业务状态机**——`UPDATE WHERE status='PENDING'` 最优雅，无需额外去重表；
>
> ④ **Token / 防重 Token**——表单提交、前端连点；
>
> ⑤ **分布式锁 + Redis**——高并发临时去重；
>
> ⑥ **DB 去重表 + 业务表同事务**——金融场景强一致兜底。
>
> **重试三件套**：① **退避 + jitter**——指数 + 随机抖动防止重试风暴对齐；② **重试预算**——调用链只有最外层重试（中间层不重试）防止放大；③ **熔断器**——错误率超阈值快速失败不再重试。
>
> **铁律**：① 不幂等的写接口不能开重试（Feign 默认不重试就是这个原因）；② 幂等键必须能区分"两次合理操作"和"一次操作的重试"（拿业务字段当键是经典坑）；③ "标记幂等"和"执行业务"必须同一原子操作（避免 Redis 已写但业务失败的丢消息）；④ 金融场景多层防御——前端 disable + token + 唯一约束 + 状态机 + 对账。
>
> **生产坑**：① 幂等键选错（user_id + product_id 误伤同一用户两次合理购买）；② MQ 消费先标 Redis 再执行业务导致丢消息；③ Feign 重试 POST 重复扣款；④ 5 层调用链都重试放大 243 倍打爆下游；⑤ token 一次失效用户重试不了；⑥ 去重表无限膨胀。
