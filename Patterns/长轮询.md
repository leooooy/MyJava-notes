# 长轮询 Long Polling — Nacos Config / RocketMQ Pull 同构设计

> 引子：
> ① **是什么**：客户端发请求，服务端没数据时**挂起请求**（不立即响应），有数据时立即返回，超时则空响应；客户端拿到响应立刻发下一次。本质是用一次 HTTP/TCP 请求换"准实时通知"的能力。
> ② **面试为什么必考**：Nacos 配置中心、RocketMQ Push（实为 Pull）、Apollo、Kafka Consumer.poll 全用它——能不能讲清这套机制，是判断候选人"只会调 API"还是"懂中间件内部"的分水岭。
> ③ **本篇要解决**：① 长轮询 vs 短轮询 vs WebSocket/gRPC 怎么选 ② Nacos 和 RocketMQ 的实现差别在哪 ③ 为什么 hold 时长是 29.5s / 15s 这种"诡异"数字 ④ 大量客户端同时挂起会不会把服务端打爆。

---

## 一、为什么需要长轮询

需求场景：**客户端要"及时"知道服务端的变化**（配置变了、有新消息了、状态改了），但不希望客户端轮询太频繁。

### 1.1 三个最朴素的方案

| 方案 | 工作方式 | 致命缺陷 |
| --- | --- | --- |
| **短轮询（Short Polling）** | 客户端每 N 秒发一次请求，问"变了没？" | 99% 请求是空返回，浪费 QPS；N 太小服务端扛不住，N 太大延迟高 |
| **服务端推送（真 Push）** | 服务端有变化主动 push | 客户端要暴露端口/保活；客户端被推爆没流控；NAT/防火墙环境难穿透 |
| **长轮询（Long Polling）** | 客户端请求挂起在服务端，有事立即返回，超时空返回 | hold 占连接、有"伪心跳"开销，但综合最优 |

### 1.2 长轮询的核心 idea

```
短轮询：客户端忙问 "变了吗？变了吗？变了吗？..." （服务端 99% 答"没变"）
长轮询：客户端问一次 "变了告诉我，没变你先憋着"   （服务端要么立即答，要么 hold 30s 答"没变"）
真 Push：服务端追着客户端喊 "变了！变了！变了！" （客户端可能被打爆）
```

**关键洞察**：服务端**不主动推**，而是**延迟应答**——把推送的实时性接近做出来，又不需要客户端可达、又有客户端自主流控。

## 二、核心原理：一次长轮询的完整流程

### 2.1 通用流程图（去具体实现）

```
   Client                                  Server
     │                                        │
     │── Request（带版本/offset/MD5）─────────►│
     │                                        │
     │                                        ├─ ① 立即检查：有变化吗？
     │                                        │     是 → 立即返回
     │                                        │
     │                                        ├─ ② 没变化 → 把请求对象塞入挂起表
     │                                        │     ┌──────────────────────┐
     │                                        │     │ holdMap[key] = Req+  │
     │                                        │     │   截止时间戳 deadline │
     │                                        │     └──────────────────────┘
     │                                        │
     │                                        ├─ ③ 后台两条触发路径：
     │           （hold 在这里...）            │
     │                                        │   路径 A：变化事件到达
     │                                        │       → notifyMessageArriving(key)
     │                                        │       → 从挂起表取出请求立即响应
     │                                        │
     │                                        │   路径 B：定时扫描 hold 表
     │                                        │       → 到 deadline 的请求返回空
     │                                        │
     │◄──────── Response（变了/没变） ────────│
     │                                        │
     │── 立即下一次 Request ──────────────────►│
```

### 2.2 服务端核心数据结构

无论 Nacos 还是 RocketMQ，本质都是这两份结构：

```java
// 挂起请求表：key → 等待这个 key 变化的请求列表
Map<String, List<HeldRequest>> holdMap;

// 单个挂起请求
class HeldRequest {
    HttpServletResponse response;   // 或 Channel（Netty）
    long deadline;                   // 到期时间戳
    String clientVersion;            // 客户端持有的版本 / offset / MD5
}
```

**两条线程**：
- **业务线程**：处理请求时，如果 key 没变化 → 把请求塞进 `holdMap`，**不响应**（关键：Servlet 容器的请求不立即返回不算关闭）
- **唤醒线程**：① 定时器扫到期请求；② 业务变化时回调 `notifyArriving(key)` 找出对应挂起请求立即响应

## 三、Nacos Config vs RocketMQ Pull：同构而不同样

这两个是面试最常对比的"同构典型"。

### 3.1 同构骨架

| 抽象维度 | Nacos Config 1.x | RocketMQ Push（实为 Pull） |
| --- | --- | --- |
| **挂起的"key"** | dataId + group + tenant | topic + queueId |
| **"变化"事件** | 配置发布 → MD5 改变 | 新消息写入 CommitLog |
| **唤醒方** | Server 端 `LongPollingService` | Broker 端 `PullRequestHoldService` |
| **挂起载体** | HttpServletRequest（异步 Servlet 3.0） | Netty Channel |
| **客户端表态版本** | 客户端发**所有关心配置的 MD5** | 客户端发**下次要拉的 offset** |
| **本质** | "我手里 MD5 是 X，变了告诉我" | "我下次想从 offset=Y 开始拿" |

### 3.2 关键参数对比

| 参数 | Nacos Config | RocketMQ |
| --- | --- | --- |
| Server hold 时长 | **29.5s**（30s - 500ms 安全垫） | **15s**（`longPollingTimeOutMillis`） |
| 客户端超时 | **30s** | **30s** |
| 关闭长轮询时退化为 | 短轮询，间隔由客户端控制 | 短轮询，`shortPollingTimeMills=1000ms` |
| 唤醒触发 | 配置发布 RPC 调用本机 `LongPollingService.notify()` | Broker 写完 CommitLog 后回调 `notifyMessageArriving()` |
| 客户端发的版本 | 一批 dataId 的 MD5 列表（一次问多个） | 单个 queue 的 offset |

### 3.3 为什么 Nacos 是 **29.5s** 而不是 30s

```
客户端 timeout = 30s
Server hold = 29.5s
         ↑
       500ms 安全垫
```

如果 Server 也是 30s，那客户端在网络抖动下经常出现 "请求都没回呢客户端先超时了"——客户端会发一个**新的长轮询请求**，而 Server **老请求还挂着**。两次请求堆积，可能引发挂起队列翻倍、连接泄漏。

**Server 比客户端早 500ms 返回**——保证客户端一定先拿到响应再决定要不要发下一次。这是一条**生产经验淬炼出的细节**。

### 3.4 为什么 RocketMQ 是 **15s** 而不是 30s

RocketMQ 的 Pull 是**消息流模式**——hold 太久不利于 Consumer 端及时感知 Rebalance、心跳异常。15s 是经验值：
- 太短（如 1s）→ 退化成短轮询，CPU 浪费
- 太长（如 60s）→ Rebalance 触发后客户端要等老请求超时才发新请求，消息消费会卡一下

而 Nacos 配置变化频率远低于消息，hold 久一点没成本，所以选 30s。

## 四、关键机制详解：怎么避免常见坑

### 4.1 怎么实现"挂起"而不阻塞业务线程

**错误做法**：

```java
// 反例：用 Thread.sleep + while 循环检查
while (!hasChange(key)) {
    Thread.sleep(100);   // ❌ 占着业务线程 30s，连接数瞬间爆掉
}
return response;
```

**正确做法（两种）**：

| 实现 | 适用 | 代表 |
| --- | --- | --- |
| **Servlet 3.0 异步请求** | HTTP 协议、SpringMVC | `request.startAsync()`，业务线程立即归还，请求对象塞 holdMap |
| **Netty Channel 挂起** | RPC、TCP | Channel 不写回响应即可，Channel 与业务线程本就分离 |

两者共同点：**业务线程处理完判断后立即归还**，请求对象只是"等待被唤醒"——没占用任何线程。

### 4.2 变化事件怎么唤醒挂起请求

**Nacos**：

```
配置发布 (POST /v1/cs/configs)
  └─ ConfigController.publishConfig()
     └─ 写库
     └─ dump 到本地文件
     └─ 通知集群其它节点（HTTP RPC）
     └─ 本节点：LongPollingService.notify(dataId, group, tenant)
        └─ 遍历 holdMap 中订阅该 key 的请求
        └─ 异步 Servlet response.write() + complete()
```

**RocketMQ**：

```
Producer 发送消息
  └─ Broker SendMessageProcessor.sendMessage()
     └─ MessageStore.putMessage() 写 CommitLog
     └─ ReputMessageService 后台异步分发到 ConsumeQueue
     └─ ConsumeQueue 写入时回调 NotifyMessageArrivingListener
        └─ PullRequestHoldService.notifyMessageArriving(topic, queueId, maxOffset)
        └─ 找出 holdMap[topic@queueId] 所有 Pull 请求
        └─ 立即返回消息
```

**共性**：写入路径上**埋一个 hook**，写完同步/异步触发挂起表的唤醒。这是 WAL/CommitLog 类设计天然能复用的——反正都要写日志，写日志的最后一步加个 notify 就完了。

### 4.3 防"惊群"——大量挂起请求同时到期

10 万客户端同时连接，假设它们大致同时启动，那 30s 后会**几乎同时**到期，30s 后又来 10 万新请求——服务端会经历周期性 CPU 抖动。

**解法（两个系统都用）**：
- **挂起时间加随机抖动**：客户端 timeout 取 `30s + random(-500ms, +500ms)`，把齐截切分变成连续分布
- **挂起表分桶**：按 key hash 分到多个 holdMap，每个桶独立扫描线程

Nacos 1.x 源码里能看到一个 `clientPollingService` 每 10ms 扫一次过期请求——粒度细，配合 timeout 抖动，避免脉冲式响应。

### 4.4 客户端怎么"持有状态"

| 设计 | 持有的状态 | 含义 |
| --- | --- | --- |
| Nacos Config | dataId 的 MD5 | "我手里这版的指纹，你比对一下变没变" |
| RocketMQ Pull | queueOffset | "我消费到这了，给我后面的" |
| Apollo | release key（版本号） | 同 MD5，但用版本号 |
| Kafka Consumer.poll | offset | 同 RocketMQ |

**关键设计**：客户端发请求时**自带版本信息**，Server 才能立即判断"有没有变化"——不用查客户端内存里持有什么。这让 Server 完全无状态（除了挂起表），任意节点都能响应。

## 五、与其它通信方案的横向对比

### 5.1 通信方案选型矩阵

| 方案 | 实时性 | 服务端开销 | 客户端复杂度 | 典型场景 |
| --- | --- | --- | --- | --- |
| **短轮询** | 取决于间隔（秒级） | 高（空响应率 99%）| 低 | 简单状态查询 |
| **长轮询** | 准实时（< 1s）| 中（hold 连接） | 中 | Nacos 1.x、RocketMQ、Apollo |
| **WebSocket** | 实时（毫秒级）| 中（保活连接） | 中（要管重连）| 聊天、协作编辑 |
| **gRPC Stream** | 实时（毫秒级）| 低（HTTP/2 多路复用） | 中 | Nacos 2.x、Dubbo3、内部 RPC |
| **SSE（Server-Sent Events）** | 实时 | 中 | 低（HTTP 标准）| 浏览器单向推送 |

### 5.2 为什么 Nacos 2.x 从长轮询切到 gRPC

Nacos 1.x：

```
10 万客户端 × 平均 5 个配置 = 50 万挂起的 HTTP 请求
每个请求占一个 Tomcat 线程槽（即使是异步 Servlet，依然要管理大量 Connection）
30s 一个周期 → 服务端连接抖动剧烈
```

切到 gRPC（HTTP/2 多路复用）：

```
10 万客户端 = 10 万 TCP 连接
单连接复用：一个 Stream 推所有订阅，配置变化在 Stream 上发包
连接稳定（应用层心跳保活），不存在 30s 周期重建
```

**核心收益**：连接数从 50 万降到 10 万；Server 不再需要挂起表，变成事件驱动推送。

**为什么 RocketMQ 没切**：RocketMQ 自己用 Netty 长连接 + 拉模型，本来就是 TCP 长连接复用，长轮询只是"在长连接上 hold 一个请求"，没有 Nacos 那种 HTTP 短连接重建的压力。

### 5.3 真正切到推送之前长轮询的优势

- **协议简单**：标准 HTTP，任何客户端能调（包括浏览器、命令行 curl 调试）
- **无状态**：Server 重启后客户端重连，状态全在客户端持有的版本号里
- **NAT/防火墙友好**：客户端发起的请求，企业网络默认放行
- **故障隔离**：单个客户端 hang 不影响其它，比 WebSocket 长连接干净

## 六、生产踩坑（真实案例级别）

### 踩坑 1：Tomcat maxConnections 打满

**现象**：Nacos Server 监控 `tomcat.connections.current` 飙到上限（默认 10000），新客户端连接失败 `Connection refused`。

**根因**：业务线上 6 万客户端，每个客户端订阅 1 个配置 = 6 万挂起请求；但 Tomcat 默认 maxConnections=10000。

**修复**：
```properties
server.tomcat.max-connections=200000
server.tomcat.accept-count=10000
```
+ 升级到 2.x 用 gRPC（推荐）。

**监控**：`tomcat.connections.current` / `tomcat.threads.busy`，阈值告警 80%。

### 踩坑 2：MD5 计算 CPU 飙高

**现象**：Nacos Server CPU 持续 70%+，火焰图显示 MD5 计算占 40%。

**根因**：客户端每次长轮询要带**所有订阅配置的 MD5 拼接串**，Server 端要逐个比对——客户端订阅 100 个配置 + 6 万客户端 + 30s 一个周期 = **每秒 20 万次 MD5 计算**。

**修复**：① 减少订阅粒度（按 group 聚合）；② Server 端缓存 MD5（配置不变时不重算）；③ 切 2.x（用 release key 数值比较）。

### 踩坑 3：客户端 timeout 比 Server hold 短，连接泄漏

**现象**：Server 端挂起表持续增长，挂起请求数远大于客户端连接数。

**根因**：客户端某框架默认 HTTP timeout 配成 20s，Server hold 30s——客户端 20s 后超时关闭连接发新请求，**Server 端老挂起请求还没到期，半死状态占着挂起槽**。

**修复**：客户端 timeout 必须 **大于** Server hold + 网络往返时间（Nacos 推荐 30s+ 配合 Server 的 29.5s）。

**类似坑**：RocketMQ Consumer 的 `consumerTimeoutMillisWhenSuspend` 必须 ≥ Broker 的 `longPollingTimeOutMillis`。

### 踩坑 4：配置发布瞬间 Server 雪崩

**现象**：发布一个被 5 万客户端订阅的配置，瞬间 Server CPU 100%，QPS 飙到 5 万。

**根因**：5 万挂起请求**同一时刻**被唤醒，每个都要构造响应、写回 HTTP——同步唤醒打成尖刺。

**修复**：① 唤醒走线程池异步（Nacos 1.4+ 已优化）；② 大客户端量配置发布走灰度（按客户端 IP 分批通知）；③ 切 2.x 用 gRPC stream，单连接顺序发包不堆积。

### 踩坑 5：RocketMQ 关闭长轮询导致消费延迟

**现象**：某新人把 `longPollingEnable=false`，结果 Consumer 端 P99 消费延迟从 50ms 飙到 1s。

**根因**：长轮询关掉后变成短轮询，`shortPollingTimeMills=1000`，平均要等 500ms 才能拿到下一批消息。

**修复**：长轮询**默认开**，几乎没有关闭的合理理由——除非诊断特定 Broker 卡死才临时关。

## 七、面试高频追问

### Q1：长轮询和 WebSocket 区别？什么时候不能用 WebSocket 替代？

长轮询是 HTTP 请求-响应模型（每次有 TCP 握手或连接复用开销），WebSocket 是双向长连接。

**WebSocket 替代不了长轮询的场景**：
- 协议层简单性要求高（如配置中心要被各种语言客户端调用）
- 客户端无法持有长连接（如 Serverless / 短生命周期容器）
- 需要标准 HTTP 网关、代理、负载均衡的运维能力（WebSocket 在很多反代后面有兼容坑）

实际：Nacos 2.x 选 gRPC 而不是 WebSocket，因为 gRPC 内置流控、Stream 复用、Protobuf，比裸 WebSocket 更适合 RPC。

### Q2：为什么 Nacos 长轮询是 29.5s，RocketMQ 是 15s？

见 3.3 / 3.4。本质是：① 客户端 timeout 与 Server hold 之间要有"安全垫"防交叉超时；② hold 时长跟业务变更频率、Rebalance 节奏匹配。这种问题答出"29.5s"和"500ms 安全垫"，面试官立即知道你看过源码。

### Q3：100 万客户端长轮询，服务端怎么扛？

按四个方向答：
1. **连接层**：调大 Tomcat / Netty maxConnections；用 epoll；Linux 调 `ulimit -n` 和 `net.core.somaxconn`。
2. **挂起表**：分桶（hash 分多个 holdMap），每桶独立扫描线程，避免单大表竞争。
3. **唤醒**：异步线程池唤醒，避免发布瞬间打成尖刺；大客户端量灰度通知。
4. **架构升级**：超过单机能扛的规模就该上 gRPC stream / WebSocket / Kafka 风格的拉模型，长轮询本身不是无限扩展的方案。

### Q4：长轮询挂起期间，TCP 连接是什么状态？

ESTABLISHED 状态，但 socket 缓冲区无数据流动——只是应用层不写响应。期间靠 TCP keepalive 或应用层心跳保活防中间代理（如 NAT、网关）断连。

**坑**：很多默认 NAT/防火墙 TCP 会话保活时间是 5 分钟，长轮询 30s 远低于这个值所以没事；但如果设计成 hold 几分钟，就一定要应用层心跳。

### Q5：Push 模式（真 Push）为什么这么少见？长轮询为什么压倒性占优？

真 Push 的核心问题：
- **客户端必须可达**（公网 IP、暴露端口、NAT 穿透）→ 在云原生/微服务场景几乎不可能
- **没有流控**（服务端不知道客户端处理能力）→ 推太快客户端崩
- **复杂度高**（要管客户端在线状态、订阅关系、ACK 机制）

长轮询把控制权交回客户端：**客户端决定什么时候要数据、要多少、能消化多少**——天然有流控、对客户端环境零要求。这就是为什么 Kafka、RocketMQ 都选 Pull 而不是 Push 即使前者实时性略低。

### Q6：长轮询和 SSE 区别？

SSE（Server-Sent Events）是 HTML5 的标准，本质是 **一个长连接 + 服务端在连接上多次写 data**。和长轮询比：
- SSE 一次连接可以推多个事件，长轮询一次请求只推一次
- SSE 是浏览器标准 API（`EventSource`），长轮询要自己实现
- SSE 是真推（连接已建立，服务端有数据立即写），长轮询是延迟响应

Server 端复杂度上 SSE > 长轮询（要维护持续输出流），但实时性更好。中间件几乎不用 SSE 是因为它是浏览器场景设计的。

### Q7：长轮询会不会读到旧数据？怎么保证拿到最新版本？

**风险点**：Server 端 hold 期间，配置已经变了但 notify 还没触发；或者 Server 集群多节点间数据没同步完。

**Nacos 的解法**：客户端发请求时携带的 **MD5 是绝对真理**——只要 MD5 和 Server 当前 MD5 不一样，立即返回（无论是不是刚 hold 上）。Server 注册挂起请求**前**会做一次 MD5 比对，避免"刚挂起就错过通知"。

**RocketMQ 的解法**：客户端发请求时携带 offset，Broker 注册挂起前做一次"消息已写入但比 offset 大"的检查。

**通用范式**：挂起前的"门口检查"——这是长轮询能不丢消息/通知的关键。

### Q8：长轮询和"反应式 I/O"是一回事吗？

不是。长轮询是**应用协议层**的设计（请求 hold 多久），反应式 I/O（Reactor 模型、epoll）是**网络 I/O 层**的设计（一个线程怎么管多个连接）。

两者关系：长轮询挂起 N 个请求，**服务端必须用 Reactor/epoll 才能管得起 N 个连接**——长轮询规模化的前提是底层 I/O 多路复用。Nacos / RocketMQ 都是 Reactor 模型 + 长轮询的组合。

→ Reactor 模型详见 [反应式 I/O](./反应式IO.md) / [Network/多路复用](../Network/多路复用.md)

## 八、答题模板（60 秒话术）

> **长轮询是一种"延迟响应"的 HTTP 通信模式**——客户端发请求，服务端没数据时**把请求挂在挂起表里不立即响应**，有变化时立即返回，超时则空响应；客户端拿到响应立刻发下一次。
>
> **核心数据结构**是服务端的 `holdMap[key] → List<HeldRequest>`，业务变化触发 `notify(key)` 唤醒挂起请求，定时器扫超时请求。客户端发请求时**自带版本信息**（MD5 / offset），让服务端保持无状态。
>
> **典型应用**：① **Nacos Config 1.x**——客户端发 dataId+MD5 列表，Server hold **29.5s**（比客户端 30s 少 500ms 安全垫，防交叉超时）；② **RocketMQ Push 实为 Pull**——Consumer 发 offset，Broker hold **15s**，新消息到 CommitLog 触发 `notifyMessageArriving` 唤醒。
>
> **vs 真 Push**：长轮询客户端不需要可达、自带流控、协议简单；**vs 短轮询**：消除空请求浪费、实时性接近推送；**vs gRPC Stream**：Nacos 2.x 已切到 gRPC，因为 10 万客户端长轮询的连接数和 MD5 计算压力扛不住，stream 单连接复用更省资源。
>
> **生产坑**：① 客户端 timeout 必须 > Server hold；② 唤醒要异步线程池防尖刺；③ 大量客户端启动同步要加 timeout 抖动防惊群；④ 升级到 2.x 后单机能稳定扛 10 万+ 客户端，1.x 长轮询通常 2~3 万就要分集群了。
