# 心跳与租约 — ZK 临时节点 / Nacos 心跳 / Redisson 看门狗 / Raft 心跳 / K8s 探针同构设计

> 引子：
> ① **是什么**：把"我还活着 / 我还想持有这个资源"压缩成一个**定期信号**，对端在窗口期内没收到就认定你死了，自动接管/释放/转移。所有"分布式存活检测 + 资源占有期限"的场景都用这套——服务注册、分布式锁、Leader 任期、Pod 生命周期、连接池保活、长连接维持。
> ② **面试为什么必考**：能问出"看门狗怎么触发"、"Nacos 临时实例 30s 才剔除合不合理"、"K8s liveness 误杀怎么办"、"Raft 心跳为什么是 150ms"——讲清这套范式，就能用一套语言回答这十几道散在不同模块里的高频题。
> ③ **本篇要解决**：① 心跳和租约是不是一回事 ② TTL / 心跳间隔 / 容忍丢失次数 该怎么选 ③ 客户端 hang 住但 JVM 还活着，心跳还在送——怎么破 ④ 网络抖动一秒就把好节点剔除，怎么稳。

## 一、为什么需要心跳与租约

### 1.1 原始问题：分布式系统里"对方是不是还活着"

经典分布式难题：**没法 100% 确定对方是死了还是只是慢了**。

```
A 给 B 发请求 → B 一直不回
原因可能是：
  ① B 进程死了
  ② B 卡在 GC
  ③ B 处理慢
  ④ 网络丢包
  ⑤ 网络分区（B 还活着，但 A 看不到）
```

唯一能用的工程手段：**让 B 定期"自报家门"——若窗口期没收到就当死了**。这就是心跳。

但心跳只解决"还活着吗"，没解决"我占用的资源啥时候释放"。所以引出**租约（Lease）**：
- 心跳本身是"我活着"
- 心跳的副作用是"延长我的资源持有期限"
- 心跳停 → 租约到期 → 资源自动释放给别人

**心跳是机制，租约是语义**——两者几乎总是一起出现。

### 1.2 核心 idea

```
持有方                          中心方
  │                                │
  │ 申请资源（拿到 TTL）            │
  ├─────────────────────────────►│
  │                                │  记录：owner=A, expires_at=now+30s
  │                                │
  │ 周期心跳（间隔 < TTL）          │
  ├──── beat (每 10s) ────────────►│  expires_at = now + 30s
  │                                │
  │ ... 业务进行 ...                │
  │                                │
  │ X  网络断 / 进程死  X          │
  │                                │
  │                                │  时钟走到 expires_at → 释放
  │                                │   broadcast：A 死了，资源可被 B 接管
```

**关键三件套**：
1. **TTL（Time-To-Live）**：资源的"过期时间"，没续就死
2. **心跳频率 < TTL / N**：留足重试余地，通常 N=3
3. **接管机制**：TTL 到期后资源去哪（被谁接管 / 触发什么）

## 二、共性骨架：六种场景在做同一件事

### 2.1 通用流程

```
[申请资源] ──► 拿到 (resourceId, TTL)
   │
   ▼
[启动后台心跳线程] 周期 = TTL / 3
   │
   ├──► 每周期：发 beat → 重置 expires_at
   │
   │   失败重试 + 退避
   │
   ▼
[资源使用完毕]
   │
   ├──► 主动释放（推荐，立即释放）
   │
   └──► 心跳停 → TTL 到期 → 中心方自动释放

[中心方]
   │
   ├──► 定时扫所有资源的 expires_at
   ├──► 已过期 → 触发回调（移除 / 通知 watcher / 选新 Leader）
   └──► 期间收到 beat → 续约
```

### 2.2 六种系统的同构对照

| 维度 | **ZK 临时节点 + session** | **Nacos 临时实例** | **Redisson 看门狗** | **Raft / ZAB 心跳** | **K8s liveness/readiness** | **数据库连接池保活** |
| --- | --- | --- | --- | --- | --- | --- |
| **持有方** | 客户端 | 微服务实例 | 加锁的 JVM | Leader | Pod | 应用 |
| **中心方** | ZK Server | Nacos Server | Redis | 所有 Follower | kubelet | 数据库 |
| **资源** | 临时节点（session）| 注册条目 | 分布式锁 key | Leader 任期 | Pod 调度位 | 连接 |
| **TTL 默认值** | session timeout（典型 30s）| 30s | 30s | election timeout（150~300ms）| 取决于探针配置 | 取决于驱动 |
| **心跳间隔** | tickTime × 2~20（默认 2~4s）| 5s | TTL / 3 ≈ 10s | 50ms（约 election timeout / 3）| 取决于 periodSeconds（10s）| 通常 30s 一次 ping |
| **心跳载体** | TCP ping（应用层）| HTTP PUT beat（1.x）/ gRPC 流（2.x）| Lua 续期脚本 | AppendEntries（空 entries）| HTTP GET / Exec / TCP | SELECT 1 |
| **TTL 到期后** | 删除 session 关联的临时节点 + 触发 watcher | 标记不健康 → 30s 后剔除 | Redis key 过期，被其他客户端抢 | Follower 选举新 Leader | 重启容器 / 摘流量 | 关闭连接 |
| **客户端 hang 但 JVM 活的处理** | 无解（session 一直在）| 无解（心跳一直送）| 无解（看门狗一直续）| 无解（同上） | livenessProbe 兜底（应用层 hang 仍会失败）| 无解 |
| **代表场景** | 分布式锁、Leader 选举 | 微服务注册 | Redisson 分布式锁 | 共识协议 | Pod 健康管理 | 防 connection idle 被网关切 |

### 2.3 一张图看清"为什么都是同一套"

```
                  共性骨架：TTL + 定期续约 + 到期接管
                                    │
        ┌───────────────────────────┼─────────────────────────┐
        │                           │                         │
   存活检测 + 资源占用         共识协议任期            连接保活
        │                           │                         │
   ┌────┴────┐                  ┌───┴────┐               ┌────┴────┐
ZK session              Raft / ZAB heartbeat          数据库 ping
Nacos 临时实例                                          长连接 keep-alive
Redisson 看门狗
K8s probe
```

**全是一种东西**：用"定期信号 + 超时窗口"代替"实时判断"——分布式系统里没有"实时"，只有"我多久没听到你的声音了"。

## 三、关键机制详解

### 3.1 ZK session：临时节点的生命周期

ZK 的"心跳 + 租约"是**最经典的实现**，几乎所有现代注册中心/分布式锁都受它启发。

```
客户端连 ZK：
  ① 建立 TCP 连接 + 协商 session timeout（如 30s）
  ② 创建 EPHEMERAL 节点 /locks/lock_xxx → 关联到 session
  ③ 启动心跳线程：每 tickTime × N（默认 4s）发一次 ping
     ├─ ZK 收到 ping → 重置 session 过期时间
     └─ 30s 内没收到 → 关闭 session → 删除所有关联的临时节点 → 通知 watcher

客户端断网：
  ZK 那边过期了
  其它客户端通过 watcher 立即知道（也是临时节点的副作用）
```

**核心精妙**：临时节点的生命周期**与 session 绑定**——这是"心跳就是租约副作用"的最完美表达。**注册 + 续约 + 接管**统一在 session 机制里，外部应用感觉不到底层有什么。

→ ZK 分布式锁、ZK Leader 选举都基于这个机制。

### 3.2 Nacos 临时实例：客户端心跳的工程版

```
客户端                              Nacos Server
   │                                    │
   │ POST /v1/ns/instance              │
   │ {ephemeral: true}                 │  注册 → 内存 + Distro 同步副本
   ├──────────────────────────────────►│
   │                                    │
   │ PUT /v1/ns/instance/beat（5s）   │  收到 → 续约
   ├──────────────────────────────────►│  expires_at = now + 30s
   │                                    │
   │ ... 业务运行 ...                   │
   │                                    │
   │ X 客户端挂了 X                     │
   │                                    │
   │                                    │  15s 没心跳 → 标记不健康（推送给订阅方）
   │                                    │  30s 没心跳 → 从注册表删除
```

**两段式剔除**：

| 阶段 | 时间 | 动作 |
| --- | --- | --- |
| 不健康 | 15s | 标记 healthy=false，订阅方收到推送停止路由 |
| 删除 | 30s | 注册表完全移除 |

**为什么分两段**：网络抖动 < 15s 是常态，立即剔除会引发服务列表震荡。先标记不健康让流量绕开，给真死服务再 15s 缓冲——一种典型的**"先降级再剔除"**保守设计。

**对比 ZK**：ZK 没有"不健康"中间态——session 过期就是没了，没缓冲。Nacos 用两段是因为微服务场景下"短暂不可用"很常见，ZK 的"硬剔除"对微服务不友好。

→ 细节见 [Microservice/Nacos.md](../Microservice/Nacos.md)

### 3.3 Redisson 看门狗：客户端主动续约

Redis 没有 session 概念，分布式锁只是普通 key 加 TTL：

```java
lock.lock();   // 默认 30s TTL，不传 leaseTime 才触发看门狗

// 后台线程：每 TTL/3 = 10s 续期一次
class WatchdogTask implements Runnable {
    public void run() {
        // 用 Lua 原子续期（仍然持有锁才续）
        evalLua("if redis.call('hexists', KEY, THREAD_ID) == 1 then "
              + "  redis.call('pexpire', KEY, 30000); end");
    }
}

lock.unlock();   // 删除 key + 停止看门狗
```

**vs ZK / Nacos 的关键差别**：
- ZK / Nacos：**心跳是协议级行为**——发的是"我还活着"，Server 端识别 session 并续约
- Redisson 看门狗：**心跳是客户端主动操作**——客户端定期写 Redis"延长这个 key 的 TTL"

**精妙之处**：Redis 本身没设计"session"，Redisson 用 watchdog 在客户端层"模拟"出了 session 语义。**任何 KV 存储 + TTL 都能这么改造成"租约"**——这是 Redisson 设计的核心洞察。

**面试坑**：被问"看门狗怎么触发"时，必须答 **"`leaseTime` 缺省才会触发"**。显式传了 `lock.lock(10, SECONDS)` 就是固定 TTL，到点必死，不续。

→ 细节见 [Redis/分布式锁.md](../Redis/分布式锁.md)

### 3.4 Raft / ZAB 心跳：共识协议的任期续约

Raft 的 Leader 必须**持续刷存在感**，否则 Follower 觉得 Leader 死了发起选举：

```
Leader 状态：
  每 50ms 给所有 Follower 发 AppendEntries（即使没新日志，发空的）
  
Follower 状态：
  收到 AppendEntries → 重置 election timer（150~300ms 随机）
  election timer 到期 → 变 Candidate，发起选举
```

**为什么 50ms / 150~300ms 这两个数字**：
- 心跳间隔 50ms：网络 RTT 跨机房 1~10ms，留 5~10 倍余地
- election timeout 150~300ms：足够让心跳过 3 次（150/50=3）才超时
- 随机化（150~300ms 而不是固定值）：防止多个 Follower 同时超时同时选举导致投票分裂

**vs 服务注册的心跳**：
- 微服务心跳：5s 一次，30s 超时 — 优先**容忍抖动**
- Raft 心跳：50ms 一次，150~300ms 超时 — 优先**故障快速感知**

**根本原因**：Raft Leader 挂了集群不可写，所以要快；微服务实例挂了其他实例还能扛，可以慢。**TTL 选多大**完全取决于"假死的代价 vs 误杀的代价"。

→ 细节见 [Distributed/一致性算法.md](../Distributed/一致性算法.md)

### 3.5 K8s 探针：三种探针的分工

K8s 没用"心跳"这个词，但本质就是 kubelet 周期性"check 容器还活着吗"。

```yaml
livenessProbe:        # 活检：失败 → 重启容器
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10
  failureThreshold: 3   # 连续 3 次失败才算挂

readinessProbe:       # 就绪：失败 → 摘流量（不重启）
  httpGet:
    path: /ready
  periodSeconds: 5

startupProbe:         # 启动：成功前不跑 liveness（K8s 1.16+）
  httpGet:
    path: /health
  failureThreshold: 30   # 给 5 分钟启动时间
```

**与传统心跳的差别**：心跳是"持有方主动报告"，K8s 探针是 **"中心方主动探测"**——kubelet 周期性 GET 应用接口。

**为什么是"探"而不是"报"**：
- 应用代码不需要写心跳逻辑（业务代码不耦合）
- 可以探到应用层是否真的健康（业务接口真的能响应）而不仅是"进程没死"
- 缺点：探测频率太密对应用有 QPS 压力

**三探针分工**：
- liveness 解决"卡死"——重启可恢复的故障
- readiness 解决"暂时不可用"——重新加载缓存、依赖慢启动
- startup 解决"启动慢"——避免应用启动期间被 liveness 误杀

### 3.6 数据库连接池保活：被忽视的"心跳"

| 场景 | 不保活的后果 |
| --- | --- |
| HikariCP / Druid 连接池 | 连接被 LB / 防火墙 idle 切断 → 拿到死连接业务报错 |
| MySQL `wait_timeout`（8h）| 闲置 8h 被服务端关 → 下次用报 "MySQL gone away" |
| 云数据库网关 | 通常 5 分钟切空闲连接 |

**保活机制**：
- HikariCP：`keepaliveTime` 配置（如 30s），定期发 `SELECT 1`
- Druid：`testWhileIdle=true` + `timeBetweenEvictionRunsMillis`

**心跳 ≠ 续约**：数据库连接保活的目的是**防 LB/网关切连接**，没有"租约"概念。所以不是所有心跳都是租约——但所有租约都靠心跳维系。

## 四、参数怎么选：TTL / 心跳间隔 / 失败阈值

### 4.1 三大参数的关系

```
TTL：资源最长能"假活"多久
心跳间隔 = TTL / N（N 通常 3）
失败阈值 = 多少次心跳丢了才算死（K8s liveness 默认 3）

总判死时间 ≈ 心跳间隔 × 失败阈值
```

### 4.2 各系统的默认值对比

| 系统 | TTL | 心跳间隔 | 失败容忍 | 总判死时间 |
| --- | --- | --- | --- | --- |
| ZK session | 30s | 2~4s | — | 30s |
| Nacos 临时实例 | 30s | 5s | — | 15s 不健康 / 30s 剔除 |
| Redisson 看门狗 | 30s | 10s | — | 30s |
| Raft 心跳 | — | 50ms | — | election timeout 150~300ms |
| K8s liveness | — | 10s（periodSeconds）| 3 次 | ~30s |
| MySQL wait_timeout | 8h | — | — | 8h（被动断）|

### 4.3 选型口诀

| 场景诉求 | 心跳频率 | 总判死时间 |
| --- | --- | --- |
| **故障快速感知**（共识协议）| 50ms~1s | < 1s |
| **微服务注册**（容忍抖动）| 5s~10s | 15~30s |
| **分布式锁**（防误抢）| TTL/3 | TTL |
| **K8s 容器探测** | 5~10s | 30~60s |
| **数据库保活** | 30s | 不存在判死，纯防切 |

**核心矛盾**：心跳越密 → 故障感知越快 + 资源开销越大 + 误判（网络抖动判死）越多；心跳越稀 → 容忍抖动 + 故障感知慢。

## 五、生产踩坑

### 踩坑 1：JVM Full GC 把 ZK session 搞断了

**现象**：业务系统跑得好好的，突然分布式锁全部丢失，所有线程报 `KeeperException.SessionExpiredException`。

**根因**：JVM Full GC 卡了 35 秒，超过 ZK session timeout 30s → ZK 主动关闭 session 删除所有临时节点 → 应用恢复后所有锁/选举状态全没。

**修复**：① 调大 session timeout 到 60s+（但代价是故障感知慢）；② 治理 GC（用 G1 / ZGC，避免 Full GC）；③ 业务侧捕获 `SessionExpiredException` 主动重建状态而不是裸抛错。

**通用教训**：**心跳的 TTL 必须大于业务最长停顿时间**——GC、IO 卡死、网络抖动都算停顿。

### 踩坑 2：Nacos 临时实例下线后流量还路由过去 15s

**现象**：发布期间用户报错"超时"，但服务实例已经下线了。

**根因**：发布脚本 SIGTERM 后实例立即关，但 Nacos 默认心跳超时 15s 才标记不健康。这 15s 内消费方还往老实例打请求。

**修复**：① 优雅下线——实例关闭前先**主动调 Nacos API 注销自己**，立即从注册表移除（Spring Cloud Alibaba 默认有这个 ShutdownHook）；② 配合 K8s preStop hook 给应用 30s 排空连接；③ 消费方加重试 + 短超时（5s 内能拿到正确路由）。

### 踩坑 3：Redisson 看门狗续了一晚上锁没释放

**现象**：业务跑了一整夜，分布式锁一直被持着，其它服务全部拿不到。

**根因**：业务代码 `lock.lock()` 后线程死循环 / hang 住，watchdog 还在 10s 续一次——锁永远不过期。

**修复**：① 业务必须有超时机制（`lock.tryLock(waitTime, leaseTime)` 显式设上限）；② 监控关键锁的持有时长，超过 N 分钟告警；③ 接受"理论永远无法完美防御 JVM hang"——这是分布式锁的固有局限。

**通用教训**：**心跳只能证明心跳线程还活着，不能证明业务线程还在干活**。这是所有心跳机制的共同盲点。

### 踩坑 4：K8s liveness 把还在加载缓存的应用误杀

**现象**：应用启动期间被 K8s 反复重启，永远进不了 Ready 状态。

**根因**：应用启动需要从 Redis 加载 5GB 缓存（耗时 2 分钟），liveness 30s 探测开始，应用还没加载完不响应 /health → 被判死 → kill 重启 → 循环。

**修复**：① 用 `startupProbe`（K8s 1.16+）覆盖启动期，failureThreshold × periodSeconds 设大于启动时间；② 老版本 K8s 用 `initialDelaySeconds: 300` 延后开始检查；③ /health 区分"启动中"和"运行中"语义（启动期间也返回 200，只是不接流量）。

### 踩坑 5：Raft 心跳 50ms 跨机房不够用

**现象**：跨机房 etcd 集群频繁发生 leader 选举抖动。

**根因**：跨机房 RTT 30~80ms，原配置 `heartbeat-interval=100ms` + `election-timeout=1000ms`，但偶尔单次心跳因网络抖动延迟到 200~300ms，连续 3 次累计接近 election timeout。

**修复**：① 调大 `heartbeat-interval=500ms` + `election-timeout=5000ms`（跨机房推荐）；② etcd 部署最好同城多机房（≤ 5ms 抖动），异地多活用其它方案（如 TiKV Multi-Raft + 异步复制）；③ 监控 `etcd_server_leader_changes_seen_total`，频繁变更说明配置不合理。

### 踩坑 6：连接池没保活，凌晨 4 点报"MySQL gone away"

**现象**：每天凌晨低峰时段批量报错"Communications link failure"，业务高峰恢复正常。

**根因**：HikariCP 没开 keepalive，连接池闲置 5+ 分钟被云数据库 LB 切断；业务来请求时拿到死连接报错。

**修复**：
```properties
spring.datasource.hikari.keepalive-time=30000     # 30s 一次保活
spring.datasource.hikari.max-lifetime=1800000     # 30 分钟回收连接
```

云数据库环境下 keepalive 是**必开项**——不是可选优化。

## 六、面试高频追问

### Q1：心跳和租约是一回事吗？

**机制相同，关注点不同**。

- 心跳：解决"对方还活着吗"的存活检测
- 租约：解决"资源占用期限"的语义

实际系统里几乎总是一起出现——心跳就是租约的"续约信号"。但也有例外：纯心跳不带租约（如数据库连接保活 SELECT 1，只防切断，无资源期限）；纯租约不靠心跳（如 Redis SET EX 30，到点必死，不续）。

### Q2：为什么 Nacos 临时实例 30s 才剔除，不能立即？

避免**网络抖动误剔除**。微服务环境下 1~10s 的网络分区是常态，立即剔除会引发：
- 服务列表频繁震荡
- 大量缓存失效
- 雪崩式重连

Nacos 用**两段式**：15s 标记不健康（让流量先绕开）→ 30s 删除（确认真死）。是"容忍抖动 vs 故障感知慢"的工程平衡。

注意：实例**主动注销**会立即移除——优雅下线就是用这个 API。

### Q3：Redisson 看门狗在什么场景下不会续期？

**只有 `lock.lock()` 不传 `leaseTime` 才触发看门狗**。

```java
lock.lock();                       // ✅ 触发看门狗
lock.lock(10, SECONDS);            // ❌ 固定 10s TTL，不续期
lock.tryLock(5, 10, SECONDS);      // ❌ 固定 10s，不续期
lock.tryLock(5, -1, SECONDS);      // ✅ leaseTime = -1 触发看门狗
```

设计意图：**显式 leaseTime = "我自己知道这次操作多久，到点必死"**；缺省 = "我不知道要多久，请保护我"。

→ 细节见 [Redis/分布式锁.md](../Redis/分布式锁.md)

### Q4：客户端 hang 住但 JVM 还活着，心跳一直在送——怎么破？

**这是所有心跳机制的共同盲点，没有完美解**。

部分缓解：
- K8s liveness 探测应用层接口（/health 走业务线程，业务 hang 探针就会失败）
- 业务层超时（任务最大执行时间）
- 监控关键锁/资源的持有时长，异常长时间告警
- Redisson 看门狗最多续 `lockWatchdogTimeout` 上限（默认无限，可改）

**正确的认知**：分布式锁/注册不是为了对抗"业务 bug"，是为了对抗"机器故障"。业务死循环属于代码 bug，应该用单元测试 / 压测 / 监控解决，不是分布式锁能保护的。

### Q5：Raft 心跳 50ms 为什么这么密？跟微服务心跳 5s 比？

**核心区别在"故障的代价"**：

- Raft Leader 挂了 → 集群不可写 → 必须秒级感知 → 50ms 心跳 + 150~300ms 选举超时
- 微服务实例挂了 → 还有其它实例扛 → 可以慢一点 → 5s 心跳 + 30s 剔除

通用原则：**心跳频率 = 故障代价 ÷ 容忍延迟**。共识协议是"集群最关键单点"，所以最密；微服务是"水平扩展节点"，可以稀。

### Q6：K8s 三种探针有什么区别？

| 探针 | 失败后果 | 用途 |
| --- | --- | --- |
| livenessProbe | **重启容器** | 检测"卡死"——重启能恢复的故障 |
| readinessProbe | **摘流量**（不重启） | 检测"暂时不可用"——加载缓存、依赖慢 |
| startupProbe | 重启容器 + **阻止 liveness 启动** | 给慢启动应用宽限期 |

**最常见的误用**：把 readiness 当 liveness 写——业务依赖一挂直接重启容器，反而把好实例打挂。

### Q7：分布式锁的 TTL 和看门狗能不能彻底防"锁过期 + 业务还没结束"？

**不能 100%**。Redlock 的作者 Martin Kleppmann 有篇著名争论文章，核心论点：
- 看门狗不能续期网络分区中的客户端（消息发不出去）
- JVM 暂停（GC、虚拟化迁移）期间锁可能过期被别人拿走，自己醒来不知道
- 时钟跳变也会破坏 TTL 语义

工程上的现实做法：① 业务接口必须**幂等**（即使锁失效重复执行也安全）；② 关键资源用 **fencing token**（每次拿锁带递增 token，写存储时校验 token 单调）；③ 接受锁不是"绝对互斥"而是"大概率互斥 + 业务幂等"。

### Q8：为什么 K8s 没用"持有方主动心跳"而用 kubelet 主动探测？

**让业务无感知**。如果用"应用主动报心跳"：
- 应用要嵌入 K8s SDK
- 应用要起心跳线程
- 应用代码和编排系统耦合

kubelet 主动探测的优势：
- 应用只要起一个 `/health` HTTP 接口，谁都能写
- 探针检查"业务层是否健康"（业务接口真能响应）而非"进程在不在"
- 探针逻辑完全在编排层，应用不感知

**代价**：探测有 QPS 压力，频率不能太密；探针接口写错（永远返回 200）会失效。

### Q9：临时实例和永久实例怎么选？

| 维度 | 临时实例 | 永久实例 |
| --- | --- | --- |
| 谁注册 | 应用启动时自注册 | 运维手动注册（脚本/控制台）|
| 谁报心跳 | 应用 SDK 内置 | 没人报，靠 Server 探测 |
| 心跳超时后果 | 剔除 | 标记不健康，**永不剔除** |
| 适合 | 微服务实例 | DB / Redis / Kafka 等基础设施 |

设计意图：基础设施是"长期资产"，不能因为运维忘记重启个进程就从注册表消失；微服务是"瞬态资产"，挂了就该走。

→ 细节见 [Microservice/Nacos.md](../Microservice/Nacos.md)

### Q10：心跳频率定多大合适？

按"故障代价 ÷ 容忍延迟"算，参考表：

| 业务场景 | 推荐心跳 | TTL/判死 |
| --- | --- | --- |
| 共识协议（Raft/ZAB）| 50~500ms | 150~1500ms |
| 分布式锁 | TTL/3（10s）| 30s |
| 微服务注册 | 5~10s | 15~60s |
| K8s 探针 | 5~10s | 30~60s |
| 数据库保活 | 30~60s | 防 LB 切（无判死）|

**通用原则**：心跳间隔 = TTL / 3（留两次重试余地）。TTL 设多大取决于业务能容忍的"误判 + 恢复延迟"。

## 七、答题模板（60 秒话术）

> **心跳与租约是分布式系统"存活检测 + 资源占用期限"的通用范式**：持有方周期发送"我还活着"信号，中心方在 TTL 内没收到就判死，自动释放/接管资源。三大参数 **TTL、心跳间隔（TTL/3）、失败容忍** 决定故障感知速度。
>
> **六种同构实现**：
>
> ① **ZK 临时节点 + session**：session 到期自动删临时节点 + 触发 watcher——分布式锁、Leader 选举的鼻祖；
>
> ② **Nacos 临时实例**：5s 心跳，15s 不健康（停流量），30s 剔除——两段式应对网络抖动；
>
> ③ **Redisson 看门狗**：客户端定期 Lua 续期 TTL，**只有 leaseTime 缺省才触发**；
>
> ④ **Raft / ZAB 心跳**：Leader 每 50ms 发 AppendEntries，Follower 150~300ms 没收到选举——共识协议要秒级感知；
>
> ⑤ **K8s 三探针**：kubelet 主动探测——liveness 重启 / readiness 摘流量 / startup 宽限启动；
>
> ⑥ **数据库连接池保活**：定期 SELECT 1 防 LB 切空闲连接——纯心跳无租约。
>
> **频率选择按"故障代价 ÷ 容忍延迟"**：共识协议要快（50ms）、微服务可慢（5s）、连接池更稀（30s）。
>
> **共同盲点**：心跳证明不了业务线程没卡死。生产兜底靠业务接口幂等 + fencing token + 长持有时间告警。
>
> **生产坑**：① GC 卡 35s 把 ZK session 搞断了 → TTL 必须大于最长 GC 暂停；② Nacos 实例下线后流量还路由 15s → 优雅下线主动注销；③ 看门狗续了一晚上 → 业务必须有最大执行时间；④ K8s startupProbe 防慢启动应用误杀；⑤ 连接池开 keepalive 防云数据库切连接。
