# 分片 + 副本 — Redis Cluster / Kafka / ES / MongoDB / 分库分表同构设计

> 引子：
> ① **是什么**：用**分片（Sharding）**水平拆分数据 + 每片配 **副本（Replica）**做高可用——一套范式同时解决"单机容量 / 写吞吐扛不住 + 单点故障"两个核心扩展性问题。Redis Cluster slot、Kafka partition、ES shard、MongoDB chunk、MySQL 分库分表全是这套。
> ② **面试为什么必考**：上一篇《主从复制范式》讲的是"副本"——只解决可用性和读扩展；这一篇补上"分片"——解决写扩展和容量。两者合起来才是"系统怎么从单机扛 1w 走到分布式扛 100w" 的完整答案，大厂系统设计题的核心范式。
> ③ **本篇要解决**：① 分片键怎么选才不踩"热点 / 大 chunk / 跨片查询"三大坑 ② 哈希分片 vs 范围分片 vs 一致性哈希怎么取舍 ③ 路由信息存哪里、客户端怎么知道走哪片 ④ 扩容时数据怎么平滑迁移。

---

## 一、为什么需要分片 + 副本

### 1.1 上一篇没解决的问题

《主从复制》解决了**单点故障 + 读扩展**：

```
[Master] ──同步──► [Slave1] [Slave2] [Slave3]
   ↑                  ↑        ↑        ↑
  写                  读       读       读
```

但还有两个痛没解决：
1. **写吞吐天花板**：所有写都打 Master，Master 是单点上限——MySQL 单机 1w TPS、Redis 单实例 10w QPS，再多就扛不住
2. **容量天花板**：所有数据都要装在 Master 的内存/磁盘里——Redis 单实例几十 GB、MySQL 单表 5000 万行就要分

### 1.2 分片的核心 idea

把数据按某种规则拆成 N 份，分散到 N 台机器：

```
原来：
  [单 Master: 100GB / 10w TPS]
  
分片后：
  [Shard1: 25GB / 2.5w TPS]   ← 一部分数据
  [Shard2: 25GB / 2.5w TPS]   ← 另一部分
  [Shard3: 25GB / 2.5w TPS]
  [Shard4: 25GB / 2.5w TPS]
  
  写吞吐 = 4 × 2.5w = 10w TPS（理想情况线性扩展）
  容量 = 4 × 25 = 100GB（任意扩）
```

### 1.3 但每个分片还会单点挂——所以每片再配副本

```
[Shard1 Master]──同步──►[Shard1 Slave]
[Shard2 Master]──同步──►[Shard2 Slave]
[Shard3 Master]──同步──►[Shard3 Slave]
[Shard4 Master]──同步──►[Shard4 Slave]
```

**分片解决水平扩展，副本解决高可用，两件事正交**——一起做才是完整的分布式存储。

## 二、共性骨架：五种系统在做同一件事

### 2.1 通用结构

```
                  ┌────────────────────────┐
                  │   元数据 / 路由层       │
                  │   "哪个 key 在哪片"      │
                  └───────────┬────────────┘
                              │
              ┌───────────────┼───────────────┐
              │               │               │
              ▼               ▼               ▼
         ┌─────────┐     ┌─────────┐     ┌─────────┐
         │ Shard 1 │     │ Shard 2 │     │ Shard 3 │
         │  M+R+R  │     │  M+R+R  │     │  M+R+R  │
         │ 副本组   │     │ 副本组   │     │ 副本组   │
         └─────────┘     └─────────┘     └─────────┘
              │
              └─ Shard 内部是个独立的主从复制单元
                 （上一篇《主从复制范式》解决）
```

**三件事缺一不可**：
1. **分片规则**：key → 哪个 shard
2. **路由信息**：客户端怎么知道 shard 在哪
3. **副本机制**：每个 shard 内部的高可用（直接复用上一篇）

### 2.2 五种系统的同构对照

| 维度 | **Redis Cluster** | **Kafka** | **Elasticsearch** | **MongoDB** | **MySQL 分库分表** |
| --- | --- | --- | --- | --- | --- |
| **分片单位叫什么** | slot（16384 个固定）| partition | shard | chunk | 物理库 / 物理表 |
| **分片规则** | CRC16(key) % 16384 | hash(key) % partitionCount | hash(_routing) % shardCount | shard key 范围 or hash | sharding-key 取模 / 一致性哈希 |
| **分片数能改吗** | ❌ 16384 永远不变 | ⚠️ 可加分片但 hash 会重映射 | ❌ Primary 数创建时定死 | ✅ 可加 shard（chunk 自动迁移）| 改了要重新分库分表 |
| **副本叫什么** | master + slave | ISR（in-sync replicas）| primary + replica | replica set（每个 shard）| 每库的主从 |
| **路由信息存哪里** | 各节点 gossip 同步 slot 表 | Zookeeper / Controller 维护 | Master node 维护 routing table | Config Server（独立副本集）| 应用代码 / 中间件（如 ShardingSphere）|
| **客户端如何路由** | Smart Client 缓存 slot 表 + MOVED 重定向 | 客户端从 metadata 拉 partition leader 信息 | Coordinator 节点路由 | mongos 路由层 | 中间件透明路由 / 应用手动 |
| **跨片操作** | 不支持（HashTag 强制同片）| 不支持事务跨分区（除非 Kafka 事务）| 不支持跨片 join | 4.2+ 跨分片事务（极慢）| 不支持跨库 JOIN（除非 ShardingSphere 联邦）|
| **扩容方式** | reshard：手动迁 slot | 加分区（不重平衡历史数据）| 几乎不能（重建索引）| chunk 自动 balance | 双写迁移 + 流量切换 |
| **典型规模** | 1000 节点 / 16384 slot | 单 topic 几百分区 | 数千分片 | 上百 shard | 上百分库分表 |

### 2.3 一张图看清"为啥都长一样"

```
                          共性骨架：路由层 + 多分片 + 每片副本组
                                          │
        ┌─────────────────────────────────┼─────────────────────────────────┐
        │                                 │                                 │
   去中心化 Gossip               中心化元数据                  应用层
   分片信息                       分片信息                      分片信息
        │                                 │                                 │
   ┌────┴────┐                       ┌────┴────┐                       ┌────┴────┐
 Redis Cluster                     Kafka / ES / MongoDB               MySQL 分库分表
   16384 slot                       Controller / Master /              ShardingSphere
                                    Config Server                       MyCAT
                                                                        手写代码
```

**全是一种东西**：把"单点数据"切成"N 份数据 + 每份再做副本"——差别只在 ① 路由信息怎么管 ② 分片规则用哈希还是范围 ③ 扩容怎么迁数据。

## 三、关键机制详解

### 3.1 分片规则：哈希 vs 范围 vs 一致性哈希

**核心权衡：均衡 vs 范围查询**。

| 维度 | 哈希分片 | 范围分片 | 一致性哈希 |
| --- | --- | --- | --- |
| 路由方式 | `hash(key) % N` | 按 key 区间映射 | hash 落到环上最近节点 |
| 均衡性 | ✅ 几乎完美 | ❌ 容易热点 | ⚠️ 需虚拟节点 |
| 范围查询 | ❌ 必须广播所有分片（scatter-gather）| ✅ 单分片定位 | ❌ |
| 扩容 | ❌ N 变化几乎全部 key 要重映射 | ⚠️ 只动相关区间 | ✅ 只动相邻节点 |
| 代表 | Kafka partition / ES shard 默认 | MongoDB 默认 / TiDB region | Redis Cluster slot / Dubbo LB |

**注意 Redis Cluster slot ≠ 一致性哈希**：

```
真·一致性哈希：哈希环（2^32 个点），动态加节点环上找邻居
Redis Cluster：固定 16384 个 slot 槽，槽到节点的映射可调整
```

Redis 用 16384 个 slot 是**"二级路由"**——key → slot 是固定哈希、slot → node 是可调映射。**比一致性哈希更可控**（手动迁指定 slot），代价是 slot 数量固定。

### 3.2 为什么 Redis Cluster 是 16384 个 slot

经典面试题。答案在 Redis 作者的设计权衡里：

```
Cluster 节点之间用 Gossip 心跳同步 slot 分布信息
心跳消息要带 "我负责的 slot 位图"

16384 bit = 2KB
65536 bit = 8KB（节省 75% 网络流量）
```

16384 是平衡 **"分配粒度足够细"（千节点级集群够分）** 和 **"心跳消息足够小"（2KB 一条不爆带宽）** 的工程数。

→ 细节见 [Redis/集群部署.md](../Redis/集群部署.md)

### 3.3 路由信息：去中心化 vs 中心化

| 模式 | 代表 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **去中心化（Gossip）** | Redis Cluster | 无元数据单点；节点对等 | 集群感知慢；元数据可能短暂不一致 |
| **中心化元数据（独立组件）** | Kafka（Controller）、ES（Master node）、MongoDB（Config Server）| 元数据强一致；运维清晰 | 元数据组件挂了部分功能不可用 |
| **应用层 / 中间件** | MySQL 分库分表 + ShardingSphere | 完全可控；可结合业务定制 | 应用要侵入 / 多一层中间件 |

**为什么 Kafka 选中心化**：Kafka 的分片（partition）数量多、变动少、读写性能要求极高——中心化的 Controller 维护 metadata 让客户端能精准命中 Leader，省去 Gossip 的不一致风险。

**为什么 Redis 选去中心化**：Redis 集群规模不大（一般几十到几百节点）、扩缩容频率低——Gossip 的"最终一致"够用，没必要为元数据搞个独立组件。

### 3.4 客户端路由：MOVED / metadata 拉取

**Redis Cluster 的 MOVED**：

```
1. Client 连 NodeA，发 GET key
2. NodeA 算 hash(key) → slot 5000
   slot 5000 不在 NodeA → 在 NodeB
   返回 MOVED 5000 NodeB:6379
3. Smart Client 更新本地 slot 表
4. 重发请求到 NodeB
```

**Kafka 的 metadata 拉取**：

```
1. Client 连任一 broker，发 metadata 请求
2. broker 返回完整 partition → leader 映射
3. Client 缓存映射，发消息时直接命中正确的 Leader broker
4. Leader 切换 → 下次请求拿到错误（NOT_LEADER）→ 重新拉 metadata
```

**两种模式骨架相同**：客户端持有本地缓存 + 失效后从服务端拉新版本。**这是上一篇《版本号与 CAS》的"客户端持有版本"在路由场景的应用**。

→ 细节见 [Patterns/版本号与CAS.md](./版本号与CAS.md)

### 3.5 分片键怎么选：三大死亡陷阱

| 陷阱 | 表现 | 案例 |
| --- | --- | --- |
| **热点（hotspot）** | 单分片承担 90% 流量 | 用"国家"分片 → 中国分片占 70% |
| **大 chunk（Jumbo chunk）** | 单分片数据量爆炸不能迁移 | 用"create_at 月份"分片 → 双 11 那个月几十 GB |
| **跨片查询（scatter-gather）** | 查询要广播所有分片 | 用 hash(user_id) 分片但常按 user_id 范围扫——全广播 |

**通用选键准则**：
1. **基数足够大**：避免单值占太多数据（如"性别"基数只有 2，绝不能做分片键）
2. **写入均匀**：均匀分布到所有分片，避免热点
3. **查询带键**：80% 的查询能带上分片键（targeted query），避免广播

**典型选择**：
- 业务 ID（用户 ID、订单 ID）+ 哈希 → 均匀分布 + 主查询天然带键
- 时间字段 + 范围 → 适合时间序列（日志、监控），但要做归档/分桶防大 chunk

### 3.6 扩容时数据怎么迁

**最难的工程问题**：扩容期间业务不能停。

| 系统 | 迁移方式 |
| --- | --- |
| Redis Cluster | 手动 `cluster reshard`：源节点 MIGRATING → 目标 IMPORTING → 逐 key 迁 → 完成后 setslot 切归属 |
| MongoDB | Balancer 后台自动迁 chunk；chunk size 默认 128MB；按集合 chunk 数差异触发 |
| Kafka | **不自动迁** —— 新加 partition 后旧数据留在老 partition，新写按新 partition 数路由 |
| ES | 加新 shard 几乎不可能（要重建索引）—— 用 reindex 工具新建索引重导数据 |
| MySQL 分库分表 | 双写 + 增量同步 + 校验 + 流量切换 + 老库下线（全套工程）|

**核心难点**：迁移期间客户端可能去老分片找数据找不到，或者去新分片找时迁移还没完——靠 **MOVED + ASK 双重定向**（Redis）、**version 比对 + 重路由**（Kafka）、**chunk 锁 + 路由 metadata 更新**（MongoDB）等机制解决。

## 四、副本怎么和分片配合

每个分片内部就是一个独立的"主从复制单元"——直接复用上一篇《主从复制范式》的所有机制。

### 4.1 副本机制对照

| 系统 | 每片副本组叫什么 | 副本同步级别 | Failover 机制 |
| --- | --- | --- | --- |
| Redis Cluster | master + slave | 异步复制 | 集群内 Gossip 选举（半数派 master 投票） |
| Kafka | ISR (动态多数派) | 可配 acks=0/1/all + min.insync.replicas | Controller 选 ISR 中的 Leader |
| ES | primary + replica | 同步复制（写要等所有 in-sync replica）| Master node 选 in-sync 的副本 |
| MongoDB | 副本集（Replica Set）| 可配 writeConcern w:majority | 副本集内 Raft-like 选举 |
| MySQL 分库分表 | 每库的主从 | 异步 / 半同步 | 由具体方案（MHA / Orchestrator）决定 |

### 4.2 分片数 × 副本数 = 集群规模

```
ES 配置：
  number_of_shards: 5      # 5 个 primary shard
  number_of_replicas: 1    # 每片 1 个副本
总分片数 = 5 × (1+1) = 10 个 shard 实例

集群机器数：≥ 副本数 + 1 = 2 台（保证 primary 和 replica 不在同一节点）
```

**通用公式**：`总分片实例数 = 分片数 × (1 + 副本数)`；**最少机器数 ≥ 副本数 + 1**（保证可用性）。

### 4.3 副本拓扑：分片副本放哪台机器

简单做法：随机分配。**生产做法：副本拓扑感知**，副本必须放在不同：
- 物理机（防硬件挂同时影响主从）
- 机架（防机架断电）
- 机房（容灾）

ES 用 `cluster.routing.allocation.awareness.attributes` 配置；MongoDB / Kafka 都有类似的 rack-awareness 机制；Redis Cluster 默认尽量分散但需要手动 validate。

## 五、生产踩坑

### 踩坑 1：MongoDB 选错分片键，只能重建集群

**现象**：上线一年后发现 99% 流量集中在一个 shard，其它 shard 闲置。

**根因**：用了 `{create_at: 1}` 做分片键——新数据全往时间最大的 chunk 写，其它历史 chunk 没新写入。MongoDB 4.4 之前**不能改分片键**。

**修复**：① 4.4+ 用 `reshardCollection`（代价极大，全集合数据迁移）；② 4.4- 只能新建集合 + 双写迁移 + 切流量。最佳：**上线前压测分片均衡性**——分片键选错的代价是天文级的运维工作量。

### 踩坑 2：Redis Cluster HashTag 把所有 key 集中到一个 slot

**现象**：Redis Cluster 16 节点，但 95% 流量打到 1 个节点。

**根因**：业务用 `{user:123}:profile`、`{user:123}:order`、`{user:123}:cart`——HashTag `{user:123}` 让这三个 key 强制同 slot。看似实现了"同用户 multi-key 操作"，但**热点用户成为 slot 杀手**。

**修复**：① HashTag 只用在"必须跨 key 原子操作"的场景，不要为方便用；② 大流量用户拆 key（`profile:123`、`order:123:001`）；③ 监控 slot 流量分布，热点 slot 拆分。

### 踩坑 3：Kafka 加 partition 后旧数据顺序乱了

**现象**：加 partition 后发现按 key 顺序消费的业务串了。

**根因**：Kafka 用 `hash(key) % partitionCount` 路由——partitionCount 变了，同一个 key 算出的 partition 也变。**老消息在 partition3，新消息可能去了 partition7**——同 key 的消息不再有序。

**修复**：① **顺序敏感的 topic 创建时就给足 partition 数**，不要后期扩；② 必须扩时：① 双 topic 过渡 ② 业务侧改路由策略（如保留映射表）；③ 用 RocketMQ 这种支持顺序消息的（按 MessageQueue 而非 partition 数）。

**通用教训**：**hash mod 分片规则下，分片数变化几乎等于"全量重映射"**——一致性哈希和 slot 设计就是为了避免这个。

### 踩坑 4：ES 单 shard 过大导致查询慢

**现象**：ES 单个 shard 200GB，查询 P99 飙到 30s。

**根因**：ES 设计经验是单 shard 控制在 30~50GB（最多 100GB），超过这个值 Lucene segment 合并代价大、查询响应慢。

**修复**：① 上线时按"总数据 / 50GB"算 primary shard 数；② 已经过大：用 reindex 工具新建索引重导（无法在线扩 shard 数）；③ 时序数据用 ILM（Index Lifecycle Management）按日 / 按月滚动新索引。

### 踩坑 5：MySQL 分库分表后没法跨库 JOIN

**现象**：业务想做"按用户查所有订单 + 商品信息"——但订单按 user_id 分库，商品按 product_id 分库。

**根因**：分库分表后**跨库 JOIN 失效**——SQL 引擎只能扫单库。要么应用层拼接（两次查询），要么用中间件联邦查询（ShardingSphere 支持但性能差）。

**修复**：① 业务层拆 SQL，先查订单再查商品（应用内 JOIN）；② 冗余字段：订单表冗余 product_name 等常用字段（牺牲规范化换查询性能）；③ 用 ES / OLAP 引擎做"宽表"，分析查询走那边。

**通用教训**：**分库分表的代价不是"分"，是"分完之后做不了 JOIN"**。要在设计阶段就接受这个代价。

### 踩坑 6：MongoDB Jumbo Chunk 拖死 balancer

**现象**：MongoDB 集群一个 shard 越来越胖，balancer 显示"无法迁移"。

**根因**：单条记录的 shard key 值聚集太多 chunk > 128MB → **Jumbo Chunk 不能被切分迁移**——balancer 跳过，单 shard 持续膨胀。

**修复**：① **片键粒度要够细**（如 user_id 而非 country）；② 已经形成 Jumbo：手动 `splitChunk` 切分（如果 key 还能切的话）；③ 实在不行：换片键 + reshardCollection（4.4+）。

→ 细节见 [Middleware/MongoDB.md](../Middleware/MongoDB.md)

## 六、面试高频追问

### Q1：分片和副本是一回事吗？

**正交关系**：
- 分片（Sharding）：解决**水平扩展**（容量 + 写吞吐）—— 把数据分散到多台
- 副本（Replica）：解决**高可用 + 读扩展**——同一份数据多副本

生产系统几乎都是**分片 + 每片副本**的二维结构。Redis Cluster、Kafka、ES、MongoDB 全都是。

### Q2：为什么 Redis Cluster 是 16384 个 slot？

权衡两件事：① **足够细**（千节点级集群够分）；② **心跳消息足够小**（节点心跳带 slot 位图，16384 bit = 2KB vs 65536 bit = 8KB）。

Redis 设计目标是几十到几百节点集群——16384 完全够；如果要支持上万节点，slot 数得加大（代价是心跳带宽涨）。

### Q3：分片键怎么选？

三条铁律：① 基数大（避免单值聚集）；② 写入均匀（避免热点）；③ 查询带键（80% 查询能精准路由）。

**典型坑**：用"状态字段"（如订单状态）做分片键——基数只有几个状态，绝对热点；用"时间"做分片键——新数据集中在最新 chunk，旧数据闲。

**推荐**：业务 ID + 哈希（user_id / order_id）——基数大、均匀、主查询天然带键。

### Q4：扩容时怎么平滑迁移数据？

按系统：
- Redis：源 MIGRATING + 目标 IMPORTING + 逐 key 迁移 + MOVED/ASK 双重定向兜底
- MongoDB：Balancer 自动迁 chunk + 路由 metadata 更新
- Kafka：实际上**不重平衡历史数据**——新加 partition 只影响新数据
- MySQL 分库分表：双写 + 增量同步 + 校验 + 流量切换 + 老库下线

**核心难点**：迁移期间客户端可能拿到旧路由——通用解法是 **"客户端缓存路由 + 服务端校验 + 错误重定向"**。

### Q5：Redis Cluster slot 算不算一致性哈希？

**思想接近但不是同一个东西**：

- 真·一致性哈希：哈希环（2^32 个点），节点哈希落环上，key 找环上下一个节点
- Redis slot：固定 16384 槽，key 二次路由（key → slot 固定、slot → node 可调）

Redis 的设计更可控——能手动把热点 slot 迁到强机器，扩容时精确控制迁移粒度。一致性哈希的"自动均衡"换来"不可精细控制"。

→ 详见 [Distributed/一致性哈希.md](../Distributed/一致性哈希.md)

### Q6：分库分表的代价是什么？

最大代价：**跨库操作做不了**——
- 跨库 JOIN：不支持，要应用层拆
- 跨库事务：要走分布式事务（Seata / 事务消息）
- 跨库分页：极度复杂（要从所有库取 N 条再汇总排序）
- 跨库 COUNT / SUM：每库算然后汇总

工程上的应对：
- 冗余字段（牺牲范式换 JOIN 替代）
- 业务侧拆 SQL
- 复杂分析查询走 ES / OLAP 引擎
- 全局唯一 ID 用雪花算法 / Leaf

### Q7：Kafka 加 partition 为什么不能保证顺序？

`partition = hash(key) % partitionCount`。

partitionCount 从 4 加到 8 时，同一个 key 算出的 partition 几乎一定变——老消息在 partition3、新消息可能去 partition7——**同 key 消息分散到不同 partition**，消费时不再有序。

解法：① 顺序敏感的 topic 创建时就给足 partition 数；② RocketMQ 的顺序消息是按 MessageQueue 而非 hash mod。

### Q8：每片副本数怎么选？

经验：
- Redis Cluster：1 主 1 从够用，要求高的 1 主 2 从
- Kafka：默认 replication factor = 3（min.insync.replicas = 2）
- ES：1 个 replica（要求高的 2 个）
- MongoDB：副本集 3 节点（1 primary + 2 secondary）

**3 副本是金融场景甜点**——任意 1 节点挂仍是多数派（2/3），任意 1 节点维护不影响可用。互联网 2 副本足够。

### Q9：跨片操作怎么办？

按重要度分级：
1. **能避免就避免**：分片键选好，让 80% 操作天然单片
2. **不可避免时，scatter-gather**：广播到所有分片，coordinator 汇总（ES / MongoDB 都支持但慢）
3. **跨片事务**：MongoDB 4.2+ / Kafka 事务 / Seata 跨库——性能极差
4. **物化视图**：定期 / 实时算好结果存别处

**核心原则**：分片设计是**为了让操作不跨片**——如果业务大量需要跨片操作，说明分片键选错了。

### Q10：分片 + 副本和共识协议（Raft）什么关系？

正交：
- 分片：把数据切成 N 份
- 副本：每份的高可用
- 共识：副本之间怎么保证强一致

Kafka / Redis Cluster：分片 + 副本，但副本同步是异步/半同步（非强一致）
TiKV / CockroachDB：**Multi-Raft**——分片 + 每片用 Raft 保证强一致——同时拿到水平扩展 + 强一致
ES / MongoDB：分片 + 副本，副本写要等 in-sync（接近半同步）

**Multi-Raft 是分片范式 + 共识协议的现代终极组合**——但代价是写延迟和复杂度。

## 七、答题模板（60 秒话术）

> **分片 + 副本是分布式存储的核心扩展性范式**：分片（Sharding）水平拆分数据解决**容量和写吞吐**，副本（Replica）每片做高可用解决**故障和读扩展**——两者正交，合起来才是完整方案。
>
> **五种同构实现**：① **Redis Cluster**：16384 个固定 slot + Gossip 去中心化路由 + 每片主从异步复制；② **Kafka**：partition + ISR 动态多数派副本 + 中心化 Controller 维护 metadata；③ **ES**：shard + primary/replica + Master node 维护 routing table；④ **MongoDB**：chunk + 副本集 + Config Server 存元数据；⑤ **MySQL 分库分表**：物理库 / 表 + 每库主从 + 应用层 / ShardingSphere 路由。
>
> **分片规则三选一**：哈希均衡但范围查询广播、范围适合时序但容易热点、一致性哈希扩容友好但需虚拟节点。Redis 16384 slot 是**"二级路由"**——key → slot 固定 + slot → node 可调，比一致性哈希更可控。
>
> **分片键三铁律**：基数大、写入均衡、80% 查询带键。选错代价天文级——MongoDB 4.4 之前甚至不能改片键，只能重建集群。
>
> **路由信息两路线**：Redis Cluster 去中心化 Gossip 同步（无元数据单点）vs Kafka/ES/MongoDB 中心化元数据组件（强一致但有依赖）。客户端都是"缓存路由 + 失效重拉"——是《版本号与 CAS》在路由场景的应用。
>
> **生产坑**：① MongoDB 分片键选错——只能重建；② Redis HashTag 集中到一个 slot 形成热点；③ Kafka 加 partition 后顺序乱；④ ES 单 shard > 100GB 查询慢；⑤ 分库分表后跨库 JOIN 做不了，要冗余字段或走 ES。
>
> **扩容核心**：客户端缓存路由 + 服务端校验 + 错误重定向（MOVED/ASK）—— 这是迁移期间不丢请求的通用兜底机制。
