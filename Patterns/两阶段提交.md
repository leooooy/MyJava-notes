# 两阶段提交与事务消息 — redo+binlog / 事务消息 / TCC / Seata 同构设计

> 引子：
> ① **是什么**：把一个事务分成 **"准备阶段（Prepare）+ 提交阶段（Commit）"** 两步，第一阶段每个参与者把"想做的事"持久化但不暴露，第二阶段协调者根据投票统一 Commit 或 Rollback。是分布式/跨子系统一致性的鼻祖范式。
> ② **面试为什么必考**：MySQL 内部 redo+binlog 是 2PC、跨库 XA 是 2PC、RocketMQ 事务消息是变体 2PC、TCC 是 2PC、Seata AT 也是 2PC——讲不清这套范式，就讲不清"为什么 redo 要先 prepare 再 commit"、"事务消息的 half 消息为什么消费者看不到"、"TCC 为什么要写 Try"这一连串题。
> ③ **本篇要解决**：① 这 5 种实现是不是真的"同一个东西" ② Prepare 阶段的"持久化但不暴露"在每种系统里怎么做的 ③ 协调者挂了/网络断了各自怎么兜底 ④ 强一致和最终一致的边界在哪。

---

## 一、为什么有这么多 2PC 变体

### 1.1 原始问题

**一个事务的副作用要落到多个"独立持久化系统"**，而这些系统没有共享锁、没有共享时钟、没有 ACID 保证。例子：

| 多系统场景 | 系统 A | 系统 B |
| --- | --- | --- |
| MySQL 单机内部 | InnoDB 引擎（redo log） | Server 层（binlog） |
| MySQL 跨实例 | DB1 | DB2 |
| 订单 + MQ 通知 | 订单 MySQL | RocketMQ |
| 跨服务业务事务 | 订单服务 | 库存服务 / 账户服务 |
| 跨库的 Seata 接入 | DB1 + 业务代码 | DB2 + 业务代码 |

**核心矛盾**：A 写成功了 B 失败怎么回滚？B 写成功了 A 失败怎么回滚？没法一把锁住，那就先**"预定"**——这就是 Prepare 阶段的来历。

### 1.2 共性骨架（所有变体共享）

```
                            ① Prepare 阶段
[协调者] ────── prepare ──────► [参与者 A] ──► 写"准备好但未生效"的持久化记录
              │                              ──► 投票 YES / NO
              │
              ├─────── prepare ─────────────► [参与者 B] ──► 同上
              │
              ▼
        收齐所有投票
              │
              ├─ 全 YES → 进入 ②
              └─ 任一 NO → ③
                            ② Commit 阶段
[协调者] ────── commit ───────► [参与者 A] ──► 把"准备好"的记录暴露/生效
              ├─────── commit ─────────────► [参与者 B] ──► 同上
              ▼
           事务结束

                            ③ Rollback 阶段
[协调者] ────── rollback ─────► [参与者 A] ──► 把"准备好"的记录清除/反做
              ├─────── rollback ───────────► [参与者 B] ──► 同上
```

**关键三件套**：
1. **Prepare 持久化但不暴露**：A 已经写到磁盘，但读者看不到、消费者收不到。
2. **协调者持久化决定**：协调者本身要持久化"已经决定 commit/rollback"，否则它挂了就乱套。
3. **崩溃恢复能继续**：任何节点挂了重启后，扫日志能继续走完未完成的 2PC。

下面 5 种系统都是这套骨架的实例化。

## 二、五种 2PC 的横向对比

### 2.1 全表对比

| 维度 | **MySQL 内部 XA**（redo+binlog） | **MySQL 跨实例 XA** | **RocketMQ 事务消息** | **TCC** | **Seata AT** |
| --- | --- | --- | --- | --- | --- |
| **协调者** | MySQL Server 层 | 应用代码 / 中间件 | RocketMQ Broker | TM（事务管理器）| TC（Seata Server）|
| **参与者** | InnoDB / binlog | 多个 MySQL 实例 | Producer 的本地事务 / MQ | 业务服务的 Try/Confirm/Cancel | 多个业务 DB（通过 Seata Client）|
| **Prepare 持久化方式** | redo log 写 prepare 状态 | XA START + XA PREPARE | half 消息（topic 改名隐藏）| Try 接口冻结资源 | 改业务表 + 写 undo_log 表 |
| **"持久化但不暴露"靠什么** | redo prepare 状态对 SELECT 不可见 | XA 锁保持，行锁不释放 | 改 topic 为 `RMQ_SYS_TRANS_HALF_TOPIC`，消费者不订阅 | 资源被冻结，Confirm 前不可用 | 本地行锁 + 全局行锁（Seata 注册）|
| **Commit 怎么"生效"** | redo 状态置 COMMIT | XA COMMIT 各实例 | 把 half 改回原 topic，写 ConsumeQueue | 调 Confirm 真正扣 | 删 undo_log，释放全局锁 |
| **协调者挂了怎么办** | 重启扫 redo + binlog 恢复 | RM 锁挂死（2PC 致命缺陷）| Broker 主动回查 Producer（回查机制） | TM 必须高可用，挂了 RM 卡 | TC 集群部署 + DB 持久化 |
| **参与者挂了怎么办** | redo 提供崩溃恢复 | 阻塞、靠人工介入 | 回查时 Producer 不在线 → 重试 15 次后丢弃 | 超时回滚 + 幂等 Cancel | TC 重发 commit/rollback |
| **一致性级别** | 强一致 | 强一致 | 最终一致（Producer 端强一致，Consumer 端最终一致）| 强一致 | 最终一致（默认 AT 模式）|
| **性能** | 高（group commit 优化）| 极差（3~5 倍损耗）| 高 | 中（业务侧 3 倍接口开销）| 中（多一次 TC 通信）|
| **业务侵入** | 无 | 中（要写 XA SQL）| 低（Producer Listener）| **极高**（业务拆 Try/Confirm/Cancel）| 几乎无（@GlobalTransactional 注解）|
| **典型场景** | 所有 MySQL 写入 | 几乎不用（性能差）| 订单+MQ通知（互联网主流）| 金融支付强一致 | 中小团队微服务首选 |

### 2.2 看一张图理解"为什么都是 2PC"

```
                      共性骨架：Prepare-Commit 两阶段
                                  │
        ┌─────────────────────────┼──────────────────────────┐
        │                         │                          │
   单机系统内部                跨进程协调                跨业务服务
        │                         │                          │
   ┌────┴────┐                ┌───┴────┐                ┌────┴────┐
redo+binlog              MySQL XA               TCC      Seata AT
（InnoDB+Server                              事务消息
 双系统）                                  （业务+MQ）
        │                         │                          │
   "持久化但不暴露"            "持久化但不暴露"             "持久化但不暴露"
    = redo prepare 状态        = half 消息改 topic         = Try 冻结资源 / undo_log
```

5 种都在做同一件事：**先把"想做的事"安全地落到日志/中间状态，再统一切换到"对外可见"**。差异只在"持久化"的载体（redo prepare / half topic / Try 接口 / undo_log）和"协调者"的形态（Server 层 / Broker / TM / TC）。

## 三、关键机制详解：Prepare 阶段的"持久化但不暴露"

这是 2PC 最微妙的地方。每个系统都解决得不一样，但思想完全一致。

### 3.1 MySQL 内部 XA：redo 状态字段

```
事务 COMMIT
    │
    ├─ Phase 1: redo log 写入 + 状态置 PREPARE  ← 持久化，但事务尚未"完成"
    │           binlog 还没写
    │
    ├─ Phase 2: binlog 写入磁盘                  ← 协调者"决定提交"的标志
    │
    └─ Phase 3: redo log 状态置 COMMIT           ← 对外生效
```

**"不暴露"是怎么做到的**：
- redo 是页修改的物理日志，记录"页 X 偏移 Y 改成 Z"
- 状态 = PREPARE 时，崩溃恢复扫到这条 redo，要回查 **binlog 是否完整**
  - binlog 完整 → 提交（认为决定已经下达）
  - binlog 不完整 → 回滚（认为还没决定就崩了）
- 状态 = COMMIT 时，正常重放
- 在内存 buffer pool 层面，事务未 COMMIT 前的修改对 SELECT 不可见（MVCC 保证）

**协调者**：MySQL Server 层。**参与者**：InnoDB 引擎（写 redo）+ Server 层自己（写 binlog）。这就是为什么 redo+binlog 被叫做"**内部 XA**"——同一个进程里两个子系统的 2PC。

→ 细节见 [MySQL/日志.md - 两阶段提交](../MySQL/日志.md#六两阶段提交重要)

### 3.2 RocketMQ 事务消息：half topic 改名

```
[Producer]                          [Broker]                      [Consumer]
    │                                  │                               │
    ├─ 1. 发 half 消息 ────────────────►│                               │
    │                                  │ 改 topic 为                   │
    │                                  │ RMQ_SYS_TRANS_HALF_TOPIC      │
    │                                  │ 写入 CommitLog                │
    │                                  │                               │
    │   （消费者订阅的是原 topic，看不到 half）                          │
    │                                  │                               │
    ├─ 2. 执行本地事务（写订单表）      │                               │
    │                                  │                               │
    ├─ 3. 发 COMMIT/ROLLBACK ──────────►│                               │
    │                                  │ COMMIT → 把 half 改回原 topic │
    │                                  │ 写 ConsumeQueue ──────────────►│
    │                                  │                               ├─ 消费
    │                                  │ ROLLBACK → OP 表标记取消      │
```

**"不暴露"是怎么做到的**：
- Broker 收到 half 消息后**把 topic 改成 `RMQ_SYS_TRANS_HALF_TOPIC`**（保存原 topic 到消息属性里）
- 消费者订阅的是原 topic（如 `OrderTopic`），ConsumeQueue 索引也没建在原 topic 下 → **物理上写了，但消费者扫不到**
- COMMIT 时，Broker 拿出 half 消息，按属性里的原 topic 重新投递（写一条新消息到 CommitLog + 建 ConsumeQueue 索引）→ 消费者立即可见

**协调者**：Broker。**参与者**：Producer 的本地事务（DB）+ Broker 自己（消息可见性）。

**精妙之处**：CommitLog 是追加写的不可修改日志，Broker 不能"原地修改 half 让它生效"——所以选择**重新投递一条新消息**。代价是 CommitLog 里会有两条消息（half + 真消息），但换来 CommitLog 设计的简洁性，是经典的"用空间换设计简单"。

→ 细节见 [MQ/事务消息.md](../MQ/事务消息.md)

### 3.3 TCC：Try 阶段冻结资源

```
转账：A 账户扣 100 → B 账户加 100

Try 阶段：
  A: balance=900, frozen=100      ← 钱"冻结"，A 看自己只有 900 可用
  B: balance=500, in_transit=100  ← 钱"在途"，B 看自己还是 500
  
Confirm 阶段：
  A: balance=900, frozen=0        ← 真正扣掉
  B: balance=600, in_transit=0    ← 真正到账

Cancel 阶段：
  A: balance=1000, frozen=0       ← 解冻
  B: balance=500, in_transit=0    ← 取消在途
```

**"不暴露"是怎么做到的**：
- Try 阶段不真正扣钱，而是**冻结**——业务上 A 已经看不到这 100（不可再用），但财务报表上"实际余额"还没变
- Confirm 才真正变更资产
- Cancel 解冻，业务上等于没发生过

**协调者**：TM（事务管理器）。**参与者**：所有业务服务（订单、库存、账户……）的 Try/Confirm/Cancel 接口。

**最大的代价**：业务侵入极深——每个原本的"扣库存"接口都要拆成 Try、Confirm、Cancel 三个，且每个都要幂等、防空回滚、防悬挂。

→ 细节见 [Distributed/分布式事务.md - TCC](../Distributed/分布式事务.md)

### 3.4 Seata AT：undo_log 自动记录

Seata AT 模式的精妙：**业务代码不感知 2PC**，但底层自动两阶段。

```
@GlobalTransactional
void placeOrder() {
    orderDao.insert(order);     // 业务代码无感
    inventoryClient.deduct();   // RPC 调用，会自动传 XID
}
```

底层执行：

```
Phase 1（每个 RM 本地）：
  ① 解析 SQL，查询修改前数据 → 存到 undo_log 表（前镜像）
  ② 执行业务 SQL → 改业务表（前镜像 + 后镜像都有了）
  ③ 注册分支事务到 TC，申请全局锁
  ④ 提交本地事务（业务表改动 + undo_log 一起 commit）

Phase 2 ─ Commit：
  ⑤ TC 通知所有 RM commit → 删 undo_log + 释放全局锁（异步，对业务无感）

Phase 2 ─ Rollback：
  ⑤ TC 通知所有 RM rollback → 用 undo_log 反向执行 SQL → 恢复数据 + 释放锁
```

**"不暴露"是怎么做到的**：
- 业务表实际上**已经被改了**，并不像 TCC 那样"冻结"——这才是 AT 的特别之处
- 但有 **全局锁**（在 TC 中心化保存）：在 commit/rollback 前，其它要修改这一行的事务必须等
- 也就是说，"不暴露"靠的是**全局锁机制**，而不是"中间状态字段"
- 如果有人**绕过 Seata 直接改表**，AT 模式的隔离性就破了——这是 AT 的一个公认缺陷

**协调者**：TC（Seata Server）。**参与者**：业务 DB（通过 Seata Java Client 代理 JDBC 行为）。

→ 细节见 [Distributed/Seata分布式事务.md](../Distributed/Seata分布式事务.md)

### 3.5 五种实现的"不暴露"机制对比

| 系统 | "不暴露"的真正机制 | 强度 |
| --- | --- | --- |
| MySQL 内部 XA | redo 状态字段 + MVCC 可见性 | 强（数据不暴露）|
| MySQL XA | XA 协议下行锁不释放 | 强（数据不暴露）|
| RocketMQ 事务消息 | 改 topic 名让消费者订阅不到 | 强（消费者收不到）|
| TCC | 业务侧"冻结"字段 | 强（业务层不可用）|
| Seata AT | 业务表实际已改 + 全局锁 | 弱（绕过 Seata 就破）|

→ 这也是 TCC 一致性级别高于 AT 的根本原因。

## 四、协调者持久化决定：另一个"两阶段"的隐藏关键

新人讲 2PC 容易只讲参与者两阶段，忽略协调者本身要**持久化它的决定**——否则协调者一挂，参与者收到不一致的指令。

| 系统 | 协调者怎么持久化决定 |
| --- | --- |
| MySQL 内部 XA | **binlog 写完 = 决定提交**。崩溃后扫 redo，PREPARE 状态的事务看 binlog 完整不完整 |
| MySQL XA | `XA COMMIT` SQL 写到 TC 的日志（应用层自己保证）|
| RocketMQ 事务消息 | Producer 发出的 COMMIT/ROLLBACK 写到 OP_HALF_TOPIC（一条普通消息） |
| TCC | TM 把全局事务状态持久化到 DB（TM 必须有自己的存储）|
| Seata AT | TC 把全局事务状态写到 `global_table` / `branch_table` / `lock_table` |

**面试一句话**：协调者的"决定"必须落盘，否则 2PC 退化成"碰运气"。

## 五、超时、回查、悬挂：故障兜底机制

### 5.1 三种故障与各自兜底

| 故障 | MySQL 内部 XA | RocketMQ 事务消息 | TCC | Seata AT |
| --- | --- | --- | --- | --- |
| **参与者 Prepare 后挂** | 重启扫 redo + binlog | half 消息留在 Broker，Producer 重启后被回查 | RM 重启后被 TM 通知 Confirm/Cancel | RM 重启后被 TC 通知 |
| **协调者 Commit 前挂** | binlog 是否完整决定走向 | Broker 主动回查 Producer | TM 集群高可用兜底；不行则人工 | TC 集群高可用兜底 |
| **网络断开 Commit 没到** | 内部场景不存在 | 回查机制每 60s 一次最多 15 次 | TM 重试，超时回滚 | TC 重试，重发 commit/rollback |

### 5.2 RocketMQ 的回查（不可不知）

```java
class MyListener implements TransactionListener {
    // 二次确认时调用
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) { ... }
    
    // 回查时调用（关键）
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        Order order = orderDao.findByMsgKey(msg.getKeys());
        return order != null ? COMMIT_MESSAGE : ROLLBACK_MESSAGE;
    }
}
```

**回查触发条件**：half 消息超过 6 秒没收到 COMMIT/ROLLBACK → Broker 后台线程 `TransactionalMessageCheckService` 找一个活跃 Producer 反查；默认最多 15 次，仍 UNKNOWN 则放弃。

这就是为什么**事务消息要求 Producer 集群存活**——回查必须有人接。

### 5.3 TCC 的三大经典坑

| 坑 | 描述 | 解法 |
| --- | --- | --- |
| **幂等** | 网络重试导致 Confirm 调两次 | 每个事务 ID 在业务表里查"已 Confirm？" |
| **空回滚** | Try 还没到，Cancel 先到（如 Try 网络超时但成功） | Cancel 先检查 Try 记录是否存在 |
| **悬挂** | Cancel 比 Try 先成功，之后 Try 才到 → 凭空冻结 | Cancel 时写"已 Cancel"标记，Try 看到标记直接返回 |

→ 细节见 [Distributed/分布式事务.md - TCC](../Distributed/分布式事务.md)

## 六、一致性级别的真相

### 6.1 同样叫 2PC，一致性差别巨大

| 系统 | 一致性 | 原因 |
| --- | --- | --- |
| MySQL 内部 XA | **强一致** | 单进程协调，崩溃恢复确定性 |
| MySQL XA | **强一致** | 但代价是阻塞 + 性能差 |
| TCC | **强一致** | 业务侧"冻结"保证中间态正确 |
| RocketMQ 事务消息 | **半强一致**（Producer 强、Consumer 最终）| Consumer 端消费失败靠重试 + DLQ |
| Seata AT | **最终一致**（带读隔离）| 全局锁保证写隔离，但回滚是"反向 SQL" |

### 6.2 为什么事务消息只能做"半强一致"

```
Producer 端：本地事务 + half 消息确认 → 强一致（要么都做要么都不做）
              │
              │ 消息到达 Broker 之后……
              ▼
Consumer 端：消费失败 → 重试 16 次 → 进 DLQ → 业务侧补偿
                            ↑
                       这一步不是事务的一部分
```

事务消息只解决了 **Producer 端业务事务 + 消息发送的一致性**，Consumer 端的消费是独立的——所以 Consumer 必须**幂等 + 重试 + 监控 DLQ + 极端兜底对账**。这是事务消息的天然局限。

### 6.3 选型口诀

```
强一致、能容忍性能差              → MySQL XA / TCC
强一致、强业务侧改造能力         → TCC
高性能、最终一致、Producer+1条MQ → RocketMQ 事务消息
高性能、最终一致、跨多库         → Seata AT
不依赖 MQ                       → 本地消息表
长流程业务                       → Saga
```

## 七、生产踩坑

### 踩坑 1：MySQL XA 把数据库压死

**现象**：跨实例 XA 上线后 QPS 从 5000 直接掉到 800，主库 CPU iowait 飙到 70%。

**根因**：XA 的 PREPARE 阶段每个参与者**fsync 3 次以上**（redo prepare + binlog + 协调者日志），且行锁/表锁要持有到 XA COMMIT；一旦有慢的参与者，整个 XA 链阻塞。

**修复**：弃用 XA，改用 RocketMQ 事务消息或 Seata AT。**MySQL XA 在互联网公司几乎没人用**——这条踩坑就是给"想用 XA 救场的新架构师"看的。

### 踩坑 2：事务消息 Producer 上线了新版本，老版本 checkLocalTransaction 没实现

**现象**：发布后 Broker `transaction_check_*.log` 日志爆量，每秒上千条回查。

**根因**：新代码用 `sendMessageInTransaction` 发了大量 half 消息，但 `checkLocalTransaction` 方法返回 `UNKNOWN`（没实现订单状态查询），Broker 每 60s 回查一次，15 次后放弃。

**修复**：① `checkLocalTransaction` 必须真实查业务状态返回 COMMIT/ROLLBACK；② Broker 端调小 `transactionTimeOut`（默认 6s，可调 30s 给业务更长执行窗口）；③ 监控 `transactionCheckMax` 触发率。

### 踩坑 3：TCC 没做幂等，Confirm 重复扣款

**现象**：客户投诉一笔订单扣了两次钱。

**根因**：TM 触发 Confirm 后网络超时重发，业务方 Confirm 接口没有事务 ID 的幂等校验，扣了两次。

**修复**：每个 TCC 接口必须有"事务 ID + 业务键"的唯一记录表，进入 Confirm/Cancel 时先 `SELECT FOR UPDATE` 检查是否已处理。

### 踩坑 4：Seata AT 没排查脏写，回滚失败

**现象**：全局事务回滚时报错"脏写"——Seata 比对当前数据 vs undo_log 后镜像，发现不一致。

**根因**：业务 A 用 Seata 改了行 X，业务 B **没接 Seata** 也改了行 X → A 回滚时发现行 X 已不是它改完后的样子。

**修复**：① 所有访问业务表的代码必须接 Seata（统一 DataSource 代理）；② 不接的场景（如 BI 报表、运维脚本）走读副本，不写主库；③ 关键表加监控，统计"非 Seata 客户端"的写入。

> MySQL 内部 XA 的性能优化（group commit）属于单系统话题，详见 [MySQL/日志.md - group commit](../MySQL/日志.md#63-group-commit组提交性能优化)。

## 八、面试高频追问

### Q1：MySQL 的 redo+binlog 为什么要两阶段提交？

保证 **redo 与 binlog 的一致性**——任一日志写完后崩溃，都不能出现"主库有 / 从库没"或"主库没 / 从库有"。具体：

- 反例 A（先 redo 再 binlog）：redo 完崩溃 → 主库重启回放有数据，binlog 没写 → 从库永远收不到 → 主从不一致
- 反例 B（先 binlog 再 redo）：binlog 完崩溃 → 从库执行了，主库没有 → 主从不一致

两阶段+崩溃恢复扫 binlog 完整性，是唯一能解决的方案。

### Q2：RocketMQ 事务消息和 2PC 是同一个东西吗？

**骨架同构，细节不同**。

同：① Prepare（half 消息持久化）→ Commit/Rollback（暴露/删除）两阶段；② 协调者持久化决定（OP_HALF_TOPIC）；③ 失败重试机制（回查）。

不同：① RocketMQ 只协调"Producer 本地事务 + MQ 消息"两个参与者，而经典 2PC 协调任意多个；② RocketMQ Consumer 端不在事务范围内（最终一致），经典 2PC 全链路强一致；③ RocketMQ 协调者主动回查 Producer，经典 2PC 是协调者发送 commit。

### Q3：为什么 RocketMQ 事务消息的 half 消息消费者看不到？

**Broker 收到 half 消息后把 topic 改成 `RMQ_SYS_TRANS_HALF_TOPIC` 写入 CommitLog**，且 ConsumeQueue 索引只建在这个内部 topic 下。消费者订阅的是业务原 topic，ConsumeQueue 扫不到这条 → 物理上写了，但消费链路里不存在。COMMIT 时 Broker 取出 half，按消息属性里保存的原 topic **重新写一条新消息**到 CommitLog，消费者就能看到了。

### Q4：TCC 的 Try / Confirm / Cancel 必须做什么？

- **Try**：资源预留（冻结余额、占库存），不真正扣减；要支持幂等（同一事务 ID 重试不重复冻结）
- **Confirm**：真正扣减；要幂等；建议不要再失败（因为已经在 Confirm 阶段意味着所有 Try 都通过了）
- **Cancel**：释放预留；要幂等；要防空回滚（Cancel 比 Try 先到）；要防悬挂（Cancel 后 Try 才到）

### Q5：Seata AT 和 TCC 的根本区别？

**关键看 Prepare 阶段做了什么**：

- TCC 的 Prepare（Try）阶段**业务表的真实数据没改**，只是冻结 → 一致性强（中间状态对外不可见），但业务侵入极高
- Seata AT 的 Prepare 阶段**业务表已经改了**，只是 undo_log 记录前镜像 + 全局锁防其它人改 → 业务无侵入，但隔离性靠"所有人都用 Seata"才能保证

总结：**TCC 一致性强、业务侵入大；AT 业务无感、一致性弱**。

### Q6：协调者挂了怎么办？这是 2PC 的死穴吗？

是。**经典 2PC 协调者挂了，所有参与者锁等到天荒地老**——这是 2PC 被叫做"悲观、阻塞、单点"的根源。

现代变体的应对：
- MySQL 内部 XA：协调者就是 Server 自己，挂了重启扫 redo+binlog 恢复——没有单点问题
- RocketMQ：Broker 集群部署，主挂从顶
- TCC / Seata：TM/TC 集群部署 + DB 持久化状态

**所以现代分布式事务很少用经典 2PC**——要么内部化（MySQL 那种），要么放弃强一致换最终一致（事务消息）。

### Q7：为什么 Saga 不是 2PC？

Saga 没有 Prepare 阶段——它的思路是"**每一步立即提交，失败靠补偿事务回退**"。例子：

```
T1（订单创建）→ T2（扣库存）→ T3（扣账户）

如果 T3 失败：
执行 C2（库存补回）→ C1（订单删除）
```

每一步都已经真实提交了，没有"冻结/不可见"的中间态。所以 Saga **不是 2PC 范式**，而是另一种最终一致方案，适合长流程业务（旅游、订单履约这种十几步的链路）。

### Q8：本地消息表为什么不是 2PC？

**本地消息表 = 业务事务和"发消息这件事"放在同一个本地数据库事务里**。

```
@Transactional
public void placeOrder() {
    orderDao.insert(order);              // 业务
    messageDao.insert(messageRecord);    // 把"待发消息"插到本地消息表，同事务
}

// 定时任务：扫描 message 表，发到 MQ，发成功后删除
```

本质是用**本地事务的 ACID** 保证两件事一致，靠定时任务把消息最终送达 MQ。没有 Prepare 阶段，不是 2PC，是另一种思路（业务方自己实现 outbox 模式）。

### Q9：什么场景下应该用 XA 而不是 TCC 或事务消息？

几乎只有：**银行核心系统、保险核心系统、传统行业的老业务**。互联网公司几乎不用。

XA 的优势：业务零改造、强一致；劣势：性能差 3~5 倍、协调者单点、跨实例锁阻塞。所以：**只有"业务变更代价 > 性能损失"且能扛住低 QPS 的场景才选 XA**。

## 九、答题模板（60 秒话术）

> **两阶段提交是一类通用范式**：把事务分成 **Prepare（持久化但不暴露）+ Commit（暴露生效）** 两阶段，协调者根据所有参与者的投票决定提交还是回滚，并把决定本身**持久化**以应对崩溃。这套骨架在五个地方都出现：
>
> ① **MySQL 内部 XA**：协调者是 Server 层，参与者是 InnoDB（redo）和 binlog——Prepare = redo 写"PREPARE 状态" + binlog 写盘 = 决定提交标志；崩溃恢复扫 binlog 完整性决定 PREPARE 事务的命运。
>
> ② **RocketMQ 事务消息**：协调者是 Broker，参与者是 Producer 本地事务 + MQ；Prepare = half 消息（topic 改名让消费者订阅不到）；Commit = 把 half 改回原 topic 重新投递；Broker 主动回查 Producer 兜底网络异常。
>
> ③ **TCC**：协调者是 TM，参与者是各业务服务；Prepare = Try（冻结资源，业务上不可用但财务上没扣）；Confirm = 真正扣；Cancel = 释放冻结。强一致但业务侵入极大，要做幂等、空回滚、悬挂。
>
> ④ **Seata AT**：协调者是 TC，参与者是业务 DB；Prepare = 业务表已改 + undo_log + 全局锁；Commit = 删 undo_log + 释放锁；Rollback = 用 undo_log 反向 SQL。业务零侵入，但隔离性靠"所有人都用 Seata"。
>
> ⑤ **MySQL 跨实例 XA**：经典 2PC，强一致但性能差 3~5 倍、协调者单点，互联网几乎不用。
>
> **选型口诀**：跨库 + 极致强一致 → XA；金融支付强一致 + 能改业务 → TCC；订单 + 一条 MQ 通知 → 事务消息；中小团队微服务无侵入 → Seata AT。
