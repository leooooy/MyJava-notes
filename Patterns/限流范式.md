# 限流范式 — 计数器 / 滑动窗口 / 漏桶 / 令牌桶同构设计

> 引子：
> ① **是什么**：在系统入口判定"这一次请求该过还是该拒"，把超过容量的流量挡在外面，避免系统被打爆。看似"加个 if 计数器"，实际工程里有四种算法 + 单机/集群两种部署 + 网关/服务/接口三层应用——每一层选错就是事故现场。
> ② **面试为什么必考**：Sentinel / Spring Cloud Gateway / Nginx / Guava RateLimiter / Redis Lua 几乎每场都问，且和上一篇《分片+副本》、《主从复制》一样是大厂"系统设计题"的常驻配套——能讲清"为什么 Sentinel 默认用滑动窗口不用令牌桶"，立刻显出深度。
> ③ **本篇要解决**：① 四种算法的本质差别和"突刺"问题 ② 令牌桶 vs 漏桶到底怎么选 ③ 单机限流和集群限流为什么是两套不同问题 ④ Nginx / Sentinel / Guava 各自实现了哪种、为什么。

## 一、为什么需要限流

### 1.1 原始问题：流量来时谁都扛不住

系统的处理能力是有上限的——CPU、内存、连接数、下游依赖都有瓶颈。一旦请求超过上限：

```
QPS 1000：响应时间 10ms ✅
QPS 5000：响应时间 100ms ⚠️
QPS 10000：响应时间 5s + 大量超时
QPS 15000：雪崩，服务彻底卡死
```

**核心矛盾**：在某个 QPS 阈值之上，系统不是"慢点处理"而是"直接挂"。所以**宁可拒绝一部分请求让另一部分活下来，也不要全部死在一起**——这就是限流的工程价值。

### 1.2 限流和别的"流控"机制的边界

| 机制 | 解决问题 | 触发方式 |
| --- | --- | --- |
| **限流（Rate Limit）** | 超过容量的请求直接拒 | 主动定阈值 |
| **熔断（Circuit Breaker）** | 下游不可用时不再调 | 错误率/慢调用率触发 |
| **降级（Degrade）** | 非核心业务关掉 | 手动开关 / 自动触发 |
| **隔离（Bulkhead）** | 一个业务挂不影响其它 | 线程池 / 信号量隔离 |

四件套配合使用——限流挡在外面、熔断快速失败、降级保核心、隔离防扩散。

### 1.3 限流的核心 idea

```
请求 ──► [限流器]
            │
            ├─ 当前流量 < 阈值 → 放行
            ├─ 当前流量 = 阈值 → ① 立即拒（fail-fast）
            │                    ② 排队等待
            │                    ③ 降级到备用接口
            └─ 持续超过 → 触发告警/扩容
```

**两个核心决策**：
1. **算法**：怎么"判断当前流量是否超阈值"——四种算法
2. **拒绝策略**：超了之后怎么办——直接 503、排队、降级

## 二、四种算法的共性骨架

### 2.1 通用结构

```
请求来 → 读"当前流量状态" → 判断能否通过 → 修改状态
            │
            ├─ 计数器：counter ++ 比阈值
            ├─ 滑动窗口：N 个小格累加比阈值
            ├─ 漏桶：水位 ++ 比容量；后台匀速漏
            └─ 令牌桶：取一个 token；后台匀速生成
```

**所有限流算法都在做"状态读 + 状态改"的原子操作**——单机用本地原子变量，集群用 Redis Lua。

### 2.2 四种算法的横向对比

| 维度 | **固定窗口** | **滑动窗口** | **漏桶** | **令牌桶** |
| --- | --- | --- | --- | --- |
| **状态** | (counter, windowStart) | N 个小窗口的 counter 数组 | (water, capacity) | (tokens, capacity) |
| **请求来时** | counter++ if 超阈值拒 | 累加最近 N 格 counter 比阈值 | water++ if 满拒 | 取 1 token if 0 拒 |
| **状态怎么变化** | 跨窗口清零 | 后台滚动新格丢老格 | 后台匀速漏水 | 后台匀速产 token |
| **流出节奏** | 窗口内不限 | 窗口内不限 | **强制匀速** | 突发允许（最多桶满）|
| **窗口边界突刺** | ❌ 最高 2x | ✅ 几乎消除 | ❌ 无概念 | ❌ 无概念 |
| **突发流量** | 突刺通过 | 突刺被压平 | 强制平滑（吞吐稳定）| 允许（桶有 token 全放）|
| **典型实现** | 早期接口限流 | **Sentinel 默认** | **Nginx limit_req** | **Guava RateLimiter / Sentinel 排队** |

### 2.3 一张图理解"为啥这么多算法"

```
                       核心维度：① 是否允许突发  ② 是否强制平滑
                                          │
        ┌─────────────────────────────────┼─────────────────────────────────┐
        │                                 │                                 │
   计数器范式                       漏桶范式                          令牌桶范式
   （时间窗内累加）                 （水位 + 匀速漏）                 （token + 匀速产）
        │                                 │                                 │
   固定窗口 / 滑动窗口             不允许突发                          允许突发
   计数好理解但有突刺              强制匀速整形                        平时无流量时可攒
   滑动窗口压平突刺               适合保护下游                          适合业务限流
```

**全是一种东西**：用"状态变量 + 时间维度"判断"现在这一刻能不能放"——差别只在状态怎么衰减、突发怎么处理。

## 三、四种算法详解

### 3.1 固定窗口（Fixed Window）：最简单但有突刺

```python
class FixedWindow:
    def __init__(self, limit, window_size_ms):
        self.limit = limit
        self.window_size = window_size_ms
        self.counter = 0
        self.window_start = now()
    
    def allow(self):
        if now() - self.window_start > self.window_size:
            self.counter = 0
            self.window_start = now()
        
        if self.counter < self.limit:
            self.counter += 1
            return True
        return False
```

**致命缺陷：窗口边界突刺**

```
配置：1 秒允许 100 个请求

T=0.0s ─────────── T=1.0s ─────────── T=2.0s
            │ 100 个 │ 100 个 │
            T=0.99s  T=1.01s
                ↑       ↑
        2 个窗口的边界附近 200 个请求挤在 20ms 内通过
        瞬时 QPS = 100 / 0.02s = 5000，5 倍超阈值
```

**适用场景**：要求宽松、易实现的简单业务限流（如非核心接口）。生产级几乎都改用滑动窗口。

### 3.2 滑动窗口（Sliding Window）：消除突刺

把固定窗口切成 N 个小格，每次累加最近 N 格：

```
配置：1 秒 100 个，切 10 格 = 每格 100ms

T=0.0  T=0.1  T=0.2  T=0.3  ...  T=0.9  T=1.0
[ 10 ][ 10 ][ 10 ][ 10 ][ 10 ][ 10 ][ 10 ][ 10 ][ 10 ][ 10 ]
                                                          ↑
                                                  当前累加 = 100

每个新请求：累加最近 10 格 → 比阈值 100
N 越大，突刺越小：N=10 时最高 1.1x，N=100 时几乎无突刺
```

**代表实现：Sentinel LeapArray**——固定数量的 bucket 数组，环形复用，老 bucket 自动被覆盖。

**为什么不无限细分**：每格都要存 counter，N 越大内存越多 + CAS 操作越频繁。10~100 是工程甜点。

→ 细节见 [Microservice/限流算法.md](../Microservice/限流算法.md)

### 3.3 漏桶（Leaky Bucket）：强制平滑

```
请求 ─►[ 入桶 ]─► 桶中排队 ─►[ 匀速漏 ]─► 处理
                  ↑
              满了就拒绝

class LeakyBucket:
    def __init__(self, capacity, leak_rate):
        self.capacity = capacity      # 桶容量
        self.leak_rate = leak_rate    # 漏速 req/s
        self.water = 0
        self.last_leak = now()
    
    def allow(self):
        # 先漏掉应该漏掉的水
        elapsed = now() - self.last_leak
        leaked = elapsed * self.leak_rate
        self.water = max(0, self.water - leaked)
        self.last_leak = now()
        
        # 再判能不能入桶
        if self.water < self.capacity:
            self.water += 1
            return True
        return False
```

**核心特性**：**不论入桶多快，出桶速率恒定**——这是它和令牌桶最关键的差别。

**适用场景**：
- 调用下游（DB / 第三方 API）——保护下游不被突发流量打爆
- 网络层流量整形（TCP shaping）

**代表实现：Nginx `limit_req`**——`nodelay` 关时就是经典漏桶。

### 3.4 令牌桶（Token Bucket）：允许突发

```
[后台 token 生成器]─► 桶（最多 capacity 个 token）
                                │
请求来 ─► 取 1 token ──► 成功通过 / 失败拒绝

class TokenBucket:
    def __init__(self, capacity, refill_rate):
        self.capacity = capacity
        self.refill_rate = refill_rate
        self.tokens = capacity     # 初始满
        self.last_refill = now()
    
    def allow(self):
        elapsed = now() - self.last_refill
        new_tokens = elapsed * self.refill_rate
        self.tokens = min(self.capacity, self.tokens + new_tokens)
        self.last_refill = now()
        
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False
```

**核心特性**：**允许突发**——桶里攒了 100 个 token，瞬时 100 个请求都能通过。但长期 QPS 仍受 refill_rate 限制。

**适用场景**：
- 业务限流（接口 QPS）——平时空闲时段，偶发突发是正常业务
- 用户限流（用户 N 次/分钟）——允许用户突发操作但限制总量

**代表实现：Guava RateLimiter / Sentinel 排队模式 / Redis Lua**。

### 3.5 漏桶 vs 令牌桶：核心区别

```
漏桶：
  入桶 100 req（突发）
  出桶 1 req/s（匀速）
  ─► 100 秒才处理完，下游永远只承受 1 QPS

令牌桶：
  桶满 100 token
  100 req 同时到 ─► 全部立即通过
  ─► 下游瞬间 100 QPS
  之后 token 用完，长期受 refill rate 限制
```

**一句话**：**漏桶保护下游、令牌桶保护自己**。

## 四、六种系统的横向对比

### 4.1 五种代表实现

| 维度 | **固定窗口（早期）** | **Sentinel 默认** | **Guava RateLimiter** | **Nginx limit_req** | **Redis Lua（集群）** |
| --- | --- | --- | --- | --- | --- |
| **算法** | 计数器 | 滑动窗口（LeapArray） | 令牌桶 | 漏桶（nodelay 关）/ 允许突发（burst） | 令牌桶 / 滑动窗口都可 |

## 五、单机 vs 集群限流

### 5.1 两个不同问题

**单机限流**：JVM 内 AtomicLong / Sentinel LeapArray 控制本进程 QPS——本地操作，纳秒级。

**集群限流**：N 台机器共享一个限流阈值（如"所有实例总 QPS 1000"）——必须有中心化状态存储（通常 Redis）。

### 5.2 Redis + Lua 实现令牌桶

```lua
-- KEYS[1] = limiter key
-- ARGV[1] = capacity, ARGV[2] = refill_rate, ARGV[3] = now, ARGV[4] = requested

local capacity = tonumber(ARGV[1])
local refill_rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local requested = tonumber(ARGV[4])

local last_tokens = tonumber(redis.call('hget', KEYS[1], 'tokens') or capacity)
local last_refill = tonumber(redis.call('hget', KEYS[1], 'ts') or now)

local elapsed = math.max(0, now - last_refill)
local new_tokens = math.min(capacity, last_tokens + elapsed * refill_rate)

if new_tokens >= requested then
    new_tokens = new_tokens - requested
    redis.call('hset', KEYS[1], 'tokens', new_tokens)
    redis.call('hset', KEYS[1], 'ts', now)
    return 1
else
    return 0
end
```

**为什么必须用 Lua**：① 读 + 计算 + 写要原子（避免并发覆盖）；② 一次 RTT 完成（不是 GET → 算 → SET 三次往返）。**集群限流的成本核心是 Redis 的额外 RTT**——每次限流判断 ≈ 1ms。

→ 这是上一篇《WAL 预写日志》、《长轮询》里都用过的"Lua 原子操作 + 客户端少 RTT"思路。

### 5.3 集群限流的精度问题

```
集群限流配置：总 QPS 1000，5 台实例
理想：每台 200 QPS

但实际：某台机器收到突发 500 QPS，Redis 限流允许了 200 token，剩 300 拒绝
       另外 4 台只用了 100 QPS 各自
       
全集群实际通过 = 200 + 100 × 4 = 600 QPS（远低于 1000）
```

**核心问题**：流量不均衡时，集群限流的"总配额"很难全用完。两种缓解：
- **平均分配 + 单机限流**：每台限 200 QPS，简单但不灵活
- **预申请配额**：每台向中心申请一批 token 本地用完再申请——减少 Redis RTT

## 六、生产踩坑

### 踩坑 1：固定窗口边界 5 倍突刺压垮下游

**现象**：限流明明配的 100 QPS，下游 DB 偶发被打到 500 QPS 报错。

**根因**：用了固定窗口算法。0.99s 通过 100 个 + 1.01s 通过 100 个 → 20ms 内 200 个 → 瞬时 10000 QPS。

**修复**：切到滑动窗口（Sentinel 默认）或令牌桶。

**通用教训**：**不要用固定窗口做核心限流**——它的"窗口对齐突刺"是已知缺陷不是 bug。

### 踩坑 2：Nginx limit_req 配 nodelay 后 burst 全通过没限住

**现象**：配 `limit_req zone=req burst=200 nodelay`，但发现 200 个请求瞬间全过。

**根因**：`nodelay` = 桶里有空位就立即通过不排队。`burst=200` 是桶容量——意味着允许瞬时 200 个突发。

**修复**：理解 Nginx 限流语义：
- 不加 burst：严格漏桶，超了立即拒
- 加 burst 不加 nodelay：经典漏桶（多余的排队等）
- 加 burst 加 nodelay：令牌桶（允许突发 burst 个）

**选择**：保护下游用前两种（强制匀速）；业务限流允许突发用第三种。

### 踩坑 3：Sentinel 集群限流没生效，每台都按总阈值跑

**现象**：配集群限流总 QPS 1000，但 10 台实例都允许 1000 QPS，实际通过 10000。

**根因**：Sentinel 集群限流需要 token server（独立或嵌入），客户端配置没指向 server 或 server 挂了——降级到单机限流。

**修复**：① 部署 token server（生产推荐独立部署）；② 配置客户端 `clusterMode=true` + server 地址；③ 监控 token server 健康；④ 接受"server 挂了降级单机"的兜底语义。

### 踩坑 4：Guava RateLimiter 单机限流，扩容到 10 实例后被打爆

**现象**：单实例阶段 RateLimiter 配 100 QPS 跑得好好的；扩到 10 个实例，下游被打到 1000 QPS。

**根因**：Guava RateLimiter 是**单 JVM 内**的限流——每个实例独立 100 QPS，10 个实例 = 1000 总 QPS。

**修复**：① 多实例必须用集群限流（Sentinel 集群 / Redis Lua）；② 单机限流只用于"接口级保护本机"而非"总流量控制"；③ 阈值按"总目标 / 实例数"算，但扩缩容时要同步调整。

### 踩坑 5：限流挡了重要业务的高峰但放过了爬虫

**现象**：限流配 100 QPS，正常用户在高峰被拒；爬虫低速持续撸过限流毫无压力。

**根因**：只配了总流量限流没区分维度。**限流维度选错比没限流更糟**。

**修复**：多维度限流——
- IP 维度：防爬虫单 IP 高频
- 用户 ID 维度：防单用户滥用
- 接口 + 用户：核心接口单用户严格
- 网关 + 接入层 + 应用层 + 接口：四层组合

### 踩坑 6：Redis 限流脚本性能成为瓶颈

**现象**：业务 QPS 5w，但 Redis Lua 限流脚本 CPU 占了 Redis 50%。

**根因**：每个请求一次 Redis RTT + Lua 执行 ≈ 0.5ms——5w QPS 时 Redis 单线程被限流脚本独占。

**修复**：① 本地令牌桶预申请（每次申请 100 个 token 本地慢慢用）；② 限流粒度上移（接入层 Nginx 限流代替应用层 Redis 限流）；③ 限流分桶（多个 limiter key 分散热点）；④ 接受"集群限流不精准但更高性能"的取舍。

→ 高 QPS 场景集群限流的成本会反噬业务——这是工程上必须意识到的代价。

## 七、面试高频追问

### Q1：四种算法本质区别？

按"窗口语义 vs 桶语义"：

- **计数器（固定窗口）**：硬切时间窗，最简单也最有突刺（边界 2x）
- **滑动窗口**：把窗口切细，N 格累加，N 越大越平滑——Sentinel 默认
- **漏桶**：水位 + 匀速漏，**强制平滑下游**
- **令牌桶**：token + 匀速产，**允许突发**

记忆口诀：**两窗口看时间累加、两桶看流量出入**。

### Q2：漏桶和令牌桶选哪个？

**核心问法：你要保护谁？**

- **保护下游**（DB / 第三方 API 不能被突发打爆）→ 漏桶（强制匀速）
- **保护自己 + 允许突发**（业务接口正常有突发流量）→ 令牌桶

或者：
- 网络流量整形（TCP shaping）→ 漏桶
- 业务限流（接口 QPS / 用户 QPS）→ 令牌桶

### Q3：Sentinel 为什么默认用滑动窗口不用令牌桶？

Sentinel 的核心场景是"统计 + 流控全链路"——滑动窗口的 LeapArray **既能限流又能统计**（每个 bucket 同时记 pass / block / RT / 异常数），令牌桶纯限流没法做统计。

Sentinel 的排队模式才用令牌桶——专门为"允许突发 + 排队等待"场景。

### Q4：固定窗口为什么不能用？

**窗口边界突刺**：1s 100 QPS 配置下，0.99s 和 1.01s 各通过 100 个，20ms 内瞬时 10000 QPS——5 倍超阈值。

修复方案：切滑动窗口（N 越大越平滑），或者直接上令牌桶（无时间窗概念）。

工程现实：除了非核心场景，几乎不用固定窗口。

### Q5：单机限流 vs 集群限流怎么选？

| 维度 | 单机 | 集群 |
| --- | --- | --- |
| **本地状态** | AtomicLong | Redis |
| **延迟** | ns 级 | ms 级（Redis RTT）|
| **精度** | 精确 | 不精确（流量不均衡时配额浪费）|
| **典型工具** | Guava / Sentinel 单机 | Redis Lua / Sentinel 集群 |
| **适合** | 接口级保护本机 | 跨实例总流量控制 |

**生产经验**：底层用单机限流保护单实例，上层用集群限流控总量——**两层都要**。

### Q6：集群限流为什么不精准？

流量不均衡 + Redis RTT 延迟 + 配额预申请误差——三层不精准叠加。

```
配总 QPS 1000，5 实例
某实例突发 → 抢到 800
其它实例只用了 50 × 4 = 200
全集群实际 1000 = 800 + 200 ✓ 总量对了
但单实例 800 已经把它打爆了 ✗
```

工程上接受"集群限流不严格精确"——它只是兜底，不是单点保护。

### Q7：Nginx limit_req 的 burst 和 nodelay 怎么配？

```nginx
# 严格漏桶：超阈值立即拒
limit_req zone=req;

# 经典漏桶：允许排队
limit_req zone=req burst=20;

# 令牌桶：允许 burst 个突发
limit_req zone=req burst=20 nodelay;
```

- 保护下游（不允许突发）→ 不加 nodelay
- 允许业务突发 → 加 nodelay

### Q8：限流维度怎么选？

按"被攻击面"分层：
- **接入层（Nginx）**：IP / 全局 QPS——防 DDoS
- **网关层（Spring Cloud Gateway / APISIX）**：接口 / 应用 QPS——业务粗粒度限流
- **应用层（Sentinel）**：方法 / 线程数 / RT——细粒度链路保护
- **接口层（业务代码）**：用户 / 业务键 QPS——防滥用

**生产标准**：四层都要有，每层挡掉对应的攻击面，单层防御不可能完整。

### Q9：限流后如何处理被拒的请求？

按重要性分级：
1. **直接拒（503）**：非核心、可重试——网关默认
2. **排队等待**（带超时）：核心、能容忍延迟——Sentinel 排队模式
3. **降级**：调备用接口 / 返回缓存数据 / 返回默认值
4. **削峰填谷**：丢到 MQ 异步处理（如秒杀场景）

### Q10：限流和熔断的区别？

| 维度 | 限流 | 熔断 |
| --- | --- | --- |
| **触发条件** | 主动定阈值 | 错误率 / 慢调用率超阈值 |
| **防护对象** | 防自己被打爆 | 防自己被慢下游拖垮 |
| **恢复方式** | 阈值下立即恢复 | 半开试探探活 |
| **典型工具** | Sentinel 流控 | Sentinel 熔断 / Hystrix |

通常一起用：限流挡外面 + 熔断挡里面调用。

## 八、答题模板（60 秒话术）

> **限流是把超过容量的流量挡在外面的工程手段**，避免系统被打爆雪崩。四种经典算法：
>
> ① **固定窗口**——计数器 + 时间窗，简单但有窗口边界 2x 突刺，几乎不用；
>
> ② **滑动窗口**——把窗口切 N 格累加，N=10 时突刺降到 1.1x，**Sentinel 默认**（同时能做统计）；
>
> ③ **漏桶**——水位 + 匀速漏，**强制平滑下游**，适合保护 DB / 第三方 API；
>
> ④ **令牌桶**——token + 匀速产，**允许突发**，适合业务限流——Guava RateLimiter / Sentinel 排队 / Redis Lua 都是。
>
> **核心选型口诀**：保护下游用漏桶（强制匀速），保护自己用令牌桶（允许突发）。
>
> **单机 vs 集群限流是两个问题**：单机用 JVM 内 AtomicLong / LeapArray，纳秒级精确；集群用 Redis Lua 原子脚本，毫秒级 RTT 且不精准（流量不均衡时配额浪费）。生产实践是**两层都要**——底层单机保护、上层集群控总量。
>
> **限流维度选错比没限流更糟**——爬虫低速过限流但挡了正常用户。四层组合：接入层 IP（防 DDoS）+ 网关层接口（业务粗粒度）+ 应用层方法（链路保护）+ 接口层用户键（防滥用）。
>
> **生产坑**：① 固定窗口边界 5 倍突刺压垮下游；② Nginx burst+nodelay 实际是令牌桶不是漏桶；③ Sentinel 集群限流 token server 挂了悄悄降级单机；④ Guava 单机限流扩容后总流量翻 N 倍打爆下游；⑤ Redis Lua 限流自己成为 Redis 瓶颈——本地令牌预申请缓解。
>
> **限流和熔断、降级、隔离合起来是完整的稳定性四件套**——限流挡外面、熔断挡下游、降级保核心、隔离防扩散。
