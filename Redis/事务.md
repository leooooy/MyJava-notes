# Redis 事务

> 八股必考。一句话点破：**Redis 事务不是真正的事务**——它只保证"批量命令一起执行 + 不被打断"，但**不支持回滚**。
> 答这道题的关键是讲清楚和 MySQL 事务的本质区别，以及为什么 Redis 没有回滚机制。

---

## 一、Redis 事务能做什么、不能做什么

### 1.1 能做的（"事务"提供的保证）

| 保证 | 含义 |
| --- | --- |
| **打包执行** | 多个命令排队，到 EXEC 时一起执行 |
| **顺序性** | 队列里的命令按顺序执行，没人能插队 |
| **不被中断** | 主线程串行执行队列，单个事务中间没有其他客户端的命令插入 |

### 1.2 不能做的（很多人误解）

| 不保证 | 说明 |
| --- | --- |
| **原子性（部分意义）** | 命令出错时**不回滚已执行的**——和 MySQL 事务最大的区别 |
| **隔离级别** | 没有"读已提交/可重复读"概念 |
| **持久性** | 取决于 RDB/AOF 配置，事务本身不保证 |
| **支持回滚** | **完全不支持**，没有 ROLLBACK 命令 |

> 所以严格说 Redis 事务只满足 **C（一致性）+ I（隔离性，强）**，不满足 **A（原子性）+ D（持久性）**。

## 二、命令速查

```bash
MULTI                # 开启事务（命令开始入队）
SET k1 v1            # 入队（不立即执行，返回 QUEUED）
INCR counter         # 入队
EXEC                 # 执行队列里所有命令，返回结果数组
DISCARD              # 放弃事务，清空命令队列

WATCH key [key...]   # 监视 key（乐观锁）
UNWATCH              # 取消所有监视
```

### 2.1 基础示例

```bash
> MULTI
OK
> SET balance 100
QUEUED
> INCR counter
QUEUED
> EXEC
1) OK
2) (integer) 1
```

### 2.2 入队就报错的命令

如果命令**语法错误**（如参数数量不对），整个事务会被拒绝执行：

```bash
> MULTI
> SET k                        # 语法错误（缺 value）
(error) ERR wrong number of arguments
> INCR counter
QUEUED
> EXEC
(error) EXECABORT Transaction discarded because of previous errors.
```

### 2.3 执行时才报错的命令（关键差异）

如果命令是**类型错误**（运行时才能发现），Redis **继续执行后续命令，不回滚**：

```bash
> SET k1 "abc"
> MULTI
> INCR k1                      # 入队成功（语法对）
QUEUED
> SET k2 "ok"
QUEUED
> EXEC
1) (error) ERR value is not an integer or out of range   # ← 这条失败
2) OK                                                    # ← 但这条仍然执行了
```

→ 这就是"不支持回滚"的具体表现。

## 三、为什么 Redis 不支持回滚？

antirez（Redis 作者）的理由：

### 1. 命令出错只可能是**程序员 bug**

- 类型错误（INCR 一个字符串）
- 参数错误（少传/多传）

这些都是**开发阶段**该发现的 bug，**不是运行时业务异常**（如银行转账失败）。生产代码里如果还有类型错误，根本问题在代码而不在事务。

### 2. 不支持回滚让 Redis 更简单

- 内核更小
- 没有 undo log 维护开销
- 性能更好

### 3. 业务异常（钱不够、库存不够）应该用业务逻辑判断

```bash
> WATCH balance
> MULTI
> 业务层先查 balance
> 如果余额够：DECRBY balance 100
> EXEC
```

不应该依赖"事务回滚"来处理业务条件。

> 这是一种**哲学差异**——Redis 把"业务正确性"的责任全部交给开发者，用乐观锁（WATCH）来配合，而不是用事务回滚。

## 四、WATCH（乐观锁）

事务最强大的部分。配合 MULTI/EXEC 实现 **CAS** 语义。

### 4.1 工作机制

```
1. WATCH key1 key2          # 监视这些 key
2. MULTI                    # 开启事务
3. ... 一系列命令入队
4. EXEC                     # 提交
   ↓
   如果 watch 的任一 key 在 WATCH ~ EXEC 期间被改 → EXEC 返回 nil（事务取消）
   否则 → 正常执行
```

### 4.2 经典场景：余额扣减（防超扣）

```python
while True:
    redis.watch("balance")
    balance = redis.get("balance")
    if balance < 100:
        redis.unwatch()
        return False
    
    pipe = redis.pipeline()
    pipe.multi()
    pipe.decrby("balance", 100)
    result = pipe.execute()
    
    if result is None:           # 被别的客户端改了
        continue                 # 重试
    return True
```

### 4.3 WATCH 的特性

| 特性 | 说明 |
| --- | --- |
| **是乐观锁** | 不锁住资源，事务提交时检查版本 |
| **EXEC 后自动 UNWATCH** | 不需要手动清理 |
| **事务取消也自动 UNWATCH** | DISCARD / 连接断开都会清理 |
| **多 key 支持** | WATCH key1 key2 key3，任一被改都取消 |
| **不支持嵌套** | 一个连接同时只能有一组 WATCH |

### 4.4 WATCH 是怎么实现的

每个 key 有一个 watcher 列表。客户端 WATCH 时把自己加入列表。任何写命令修改这个 key 时，会把列表里所有客户端标记为 dirty。EXEC 时检查自己是否 dirty——是就拒绝执行。

## 五、Redis 事务 vs MySQL 事务

| 维度 | Redis 事务 | MySQL 事务 |
| --- | --- | --- |
| **原子性** | 部分（运行时错误不回滚） | **完全**（全部成功或全部回滚） |
| **隔离性** | 强（单线程串行） | 4 个隔离级别可选 |
| **持久性** | 取决于 RDB/AOF | redo log 保证 |
| **一致性** | 业务逻辑保证 | 引擎 + 业务保证 |
| **回滚** | ✗ | ✓（undo log） |
| **嵌套** | ✗ | ✗（标准 SQL） |
| **保存点** | ✗ | ✓（SAVEPOINT） |
| **典型用途** | CAS（WATCH + MULTI） | 复杂业务的原子操作 |

## 六、Redis 事务 vs Lua 脚本

| 维度 | 事务（MULTI/EXEC） | Lua 脚本 |
| --- | --- | --- |
| **原子性** | 全部命令一起执行（中间不被打断） | 同 |
| **错误处理** | 运行时错误不影响其他命令 | 异常直接抛出，未执行的命令不会执行 |
| **逻辑** | 只能执行命令序列 | 可写条件判断、循环 |
| **网络往返** | MULTI + 多个命令 + EXEC = N+2 次 | 1 次 |
| **可读性** | 直观 | 需要 Lua 知识 |
| **CAS 支持** | WATCH + MULTI/EXEC | 直接在脚本里判断 |
| **Cluster 限制** | 必须同一节点 | 必须同一 slot |
| **典型用途** | 简单批量 + WATCH 乐观锁 | 复杂原子逻辑（限流、扣库存） |

> 现代 Redis 编程中 **Lua 脚本几乎完全替代了 MULTI/EXEC**——更原子、更高效、更灵活。详见 [Lua 脚本](./Lua%20脚本.md)。

## 七、面试高频追问

### Q1：Redis 事务保证原子性吗？

**部分保证**：
- 入队语法错误 → 整个事务拒绝
- 运行时类型错误 → 后续命令仍执行，**不回滚**

严格说不满足 ACID 的 A（原子性）。

### Q2：Redis 为什么不实现回滚？

作者认为：
1. 运行时错误几乎都是程序员 bug，应该开发阶段发现
2. 业务异常应该用业务逻辑判断（WATCH + 重试）
3. 简化内核，性能更高

### Q3：MULTI/EXEC 期间能 GET 当前数据吗？

不能。MULTI 后所有命令都入队，**返回 QUEUED 而不是真实结果**。要先读再决定写，必须用：
- WATCH + MULTI/EXEC（乐观锁重试）
- Lua 脚本（更优雅）

### Q4：WATCH 是悲观锁还是乐观锁？

**乐观锁**。不锁资源，提交时检查 key 是否被修改。被改 → EXEC 返回 nil → 客户端重试。
对应数据库的 CAS 或 MVCC 思路。

### Q5：MULTI 嵌套会怎样？

报错 `MULTI calls can not be nested`。一个连接只能有一组 MULTI。

### Q6：DISCARD 后 WATCH 还生效吗？

不生效。DISCARD 会自动 UNWATCH。

### Q7：在 Redis Cluster 下 MULTI/EXEC 有什么限制？

事务里所有 key **必须在同一个 slot**——否则报错 `CROSSSLOT`。
解决：用 Hash Tag `{tag}` 让多 key 落到同 slot。详见 [Redis 集群部署](./集群部署.md#47-多-key-操作的限制)。

### Q8：MULTI 队列里的命令是序列化执行还是并发？

**严格串行**。Redis 主线程单线程，整个事务执行期间不处理其他客户端的命令。

### Q9：Redis 事务和管道（Pipeline）有什么区别？

| 维度 | MULTI/EXEC | Pipeline |
| --- | --- | --- |
| **原子性** | 是（中间不被打断） | 否（其他客户端命令可能插入） |
| **网络优化** | 一定程度优化（一次 EXEC 触发） | 主要目的就是减少 RTT |
| **错误隔离** | 入队错误整个拒绝 | 每条命令独立 |
| **典型用途** | 一组必须一起做的命令 | 批量加速（但不要求原子） |

详见 [管道与批量优化](./管道与批量优化.md)。

### Q10：现代 Redis 编程还推荐 MULTI/EXEC 吗？

**多数场景推荐 Lua 脚本替代**：
- 更强的原子性（条件判断也是原子）
- 一次网络往返
- 写复杂逻辑更自然

只有这两种场景考虑 MULTI/EXEC：
- 简单批量 + 不需要逻辑判断
- 配合 WATCH 做乐观锁，且业务模型清晰

### Q11：连接断开时事务怎么处理？

未 EXEC 的事务会被自动 DISCARD（连接里的命令队列清空）。
**但要注意**：如果 EXEC 已经发出去但响应丢失，**Redis 已经执行了**——客户端要做幂等保护。

### Q12：为什么 INCR 执行成功后续命令仍执行？

Redis 设计选择：把每条命令视为独立单元。一条命令的失败**不影响**事务里其他命令的执行——这正是"不回滚"的体现。

## 八、生产真实踩坑

### Case 1：依赖 Redis 事务的"原子性"导致数据不一致

代码用 MULTI 一次扣库存 + 写订单：
```
MULTI
DECR stock
LPUSH orders $orderId
EXEC
```

某天 `stock` 被人误改成字符串，DECR 报类型错误，但 LPUSH 仍然执行 → 订单写了但库存没扣 → 超卖。

**修复**：改用 Lua 脚本（`redis.call` 出错会中止脚本）；或业务侧检查 EXEC 返回值的每一项。

### Case 2：WATCH 重试饥饿

热点 key 在高并发下持续被改，WATCH 总是失败，客户端无限重试，CPU 飙升。
**修复**：
- 加最大重试次数 + 退避
- 改用 Lua 脚本（不需要重试）
- 改用 Redis 分布式锁

### Case 3：MULTI 没 EXEC，连接被复用

某客户端 MULTI 后忘了 EXEC，连接放回连接池被下一个用户拿到 → 它的命令全部入队，没真正执行。
**修复**：连接归还前强制 DISCARD 兜底；或客户端 SDK 自动检测。

### Case 4：Cluster 下 MULTI 命中 CROSSSLOT

事务里 key 没用 Hash Tag，散到不同节点 → 报错。
**修复**：业务规划好 Hash Tag；或拆事务到多个节点单独执行。

### Case 5：以为 MULTI/EXEC 是隔离的

```
MULTI
GET x         # 期望读出当前值
SET x ${value+1}
EXEC
```
但 GET 在 MULTI 内**不返回真实值**（返回 QUEUED），所以 `${value+1}` 拿不到。
**修复**：必须用 WATCH + 应用层判断，或 Lua 脚本。

## 九、答题模板（60 秒话术）

> Redis 事务**不是真事务**。它能保证：MULTI / EXEC 之间的命令**批量入队、顺序执行、不被打断**（强隔离性）。
>
> 它**不能保证**的是：运行时错误**不回滚**——Redis 设计上认为业务原子性由开发者保证；语法错误整批拒绝，运行时错误（如对 String 用 LPUSH）只该条失败、其它仍执行。
>
> **WATCH** 实现乐观锁——监视的 key 被改则 EXEC 返回 nil，配合 MULTI 做 CAS。
>
> 和 MySQL 完整 ACID 比，Redis 事务弱很多；和 **Lua 脚本**比，Lua 更原子、能写逻辑、一次 RTT——**现代 Redis 编程推荐 Lua 替代 MULTI/EXEC**。
>
> 生产经验：Cluster 下事务有跨槽限制（所有 key 必须同 slot）、连接复用注意 WATCH/MULTI 状态、避免 WATCH 饥饿。
