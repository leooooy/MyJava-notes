# Redis 分布式锁

> 大厂高频题。回答的关键是 **演进式回答**：从最简单的 `SETNX` 一路推到 Redisson + Redlock，每一步都讲清"上一版有什么问题，这一版怎么解决"。
> 这种讲法 = 你真做过、真踩过坑，比直接背"用 Redisson"高出一个段位。

---

## 一、为什么要分布式锁

单机锁（`synchronized` / `ReentrantLock`）只在一个 JVM 进程里有效。分布式系统下：

```
        [应用 A 实例 1]      [应用 A 实例 2]      [应用 A 实例 3]
              │                    │                    │
              └────────────────────┴────────────────────┘
                              ↓ 都来抢同一份资源
                            [DB / 缓存]
```

JVM 锁锁不住跨进程的并发。需要一个**所有进程都能访问的"中心仲裁者"**：
- **Redis**：性能最高，最常用
- **ZooKeeper**：可靠性最高，CP
- **etcd**：云原生场景

> **取舍**：性能优先选 Redis，可靠性优先选 ZK。互联网业务 95% 用 Redis。

## 二、演进史：从 SETNX 到 Redisson

### 版本 1：SETNX（最朴素）

```bash
SETNX lock:order:1001 1
# 1 → 拿锁成功
# 0 → 拿锁失败
```

**问题**：拿到锁的客户端**崩了**或**网络断了**，锁永远不释放 → **死锁**。

### 版本 2：SETNX + EXPIRE（加超时）

```bash
SETNX lock:order:1001 1
EXPIRE lock:order:1001 30
```

**问题**：两条命令**不是原子**的。SETNX 成功后客户端崩了，EXPIRE 没执行 → 还是死锁。

### 版本 3：SET NX EX（合并成原子命令）

Redis 2.6.12+ 提供：

```bash
SET lock:order:1001 1 NX EX 30
# OK   → 拿锁成功
# nil  → 拿锁失败
```

原子操作，解决了 V2 的问题。**但还有新问题**：

**问题 A：误删别人的锁**
```
1. 客户端 A 拿到锁，TTL 30s
2. A 业务执行 35s（GC / 慢 SQL / IO 抖动）
3. 锁到期自动释放
4. 客户端 B 拿到锁
5. A 业务终于执行完，DEL lock → 把 B 的锁删了
6. 客户端 C 又拿到锁 → 此时 B 和 C 都觉得自己有锁
```

**问题 B：锁过期时业务还没结束**
锁的 TTL 设短了误删，设长了死锁久。无解。

### 版本 4：UUID + Lua 释放（解决误删）

加锁时存 **唯一标识**，释放时校验：

```bash
# 加锁
SET lock:order:1001 ${uuid} NX EX 30

# 释放锁（必须 Lua 保证 GET + DEL 原子）
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

```java
String uuid = UUID.randomUUID().toString();
boolean locked = redis.set("lock:order:1001", uuid, "NX", "EX", 30);

if (locked) {
    try {
        // 业务逻辑
    } finally {
        // 用 Lua 校验+删除原子
        String script = "if redis.call('GET', KEYS[1]) == ARGV[1] " +
                        "then return redis.call('DEL', KEYS[1]) else return 0 end";
        redis.eval(script, Collections.singletonList("lock:order:1001"), 
                   Collections.singletonList(uuid));
    }
}
```

**还剩一个问题**：业务超时怎么办？

### 版本 5：Redisson + 看门狗（生产推荐）

Redisson 在 V4 基础上加了 **WatchDog 续期机制**。

```java
RLock lock = redisson.getLock("lock:order:1001");
lock.lock();                    // 默认 30s TTL，自动续期
try {
    // 业务逻辑
} finally {
    lock.unlock();
}
```

#### 看门狗工作原理

```
1. 客户端调 lock.lock()，默认 leaseTime = -1
2. Redis 写入：SET key uuid:threadId NX EX 30
3. 后台启动 watchdog 定时任务（10s 一次）
4. 每次检查锁是否还在自己手上：
   - 在 → PEXPIRE 续到 30s
   - 不在 → 退出
5. 业务结束 unlock，watchdog 停止
```

**默认参数**：
- `lockWatchdogTimeout = 30s`（锁 TTL）
- 续期间隔 = TTL / 3 ≈ 10s

#### 看门狗触发条件（很多人答错的点）

```java
// ✓ 触发看门狗：不传 leaseTime
lock.lock();
lock.tryLock();
lock.tryLock(100, TimeUnit.SECONDS);     // 等待时间 100s，但 leaseTime 用默认 -1

// ✗ 不触发看门狗：显式传了 leaseTime
lock.lock(10, TimeUnit.SECONDS);          // 锁 10s 后自动释放，不续期
lock.tryLock(100, 10, TimeUnit.SECONDS); // 等 100s，最多锁 10s
```

> **面试坑**：被问"看门狗怎么触发"答"自动触发"是错的，必须 `leaseTime` 缺省才会触发。

## 三、Redisson 的关键能力

### 3.1 可重入

同一线程多次 lock 不会死锁。底层用 Redis Hash：
```
HSET lock:key uuid:threadId 1     # 第一次 lock
HINCRBY lock:key uuid:threadId 1  # 重入计数 +1
unlock 时 HINCRBY -1，归 0 才 DEL
```

### 3.2 公平锁

```java
RLock fairLock = redisson.getFairLock("key");
```

按"申请顺序"获取锁（用 Redis ZSet 排队），避免饥饿。
**代价**：性能比非公平锁差，公平锁的 Redis 操作多 3 倍。

### 3.3 读写锁

```java
RReadWriteLock rwLock = redisson.getReadWriteLock("key");
rwLock.readLock().lock();    // 共享
rwLock.writeLock().lock();   // 互斥
```

读多写少场景，读锁可并发，写锁互斥。

### 3.4 联锁（MultiLock）

需要同时锁住多个资源时：
```java
RLock multi = redisson.getMultiLock(lock1, lock2, lock3);
multi.lock();    // 全部成功才算成功，全部释放才算释放
```

### 3.5 信号量

```java
RSemaphore semaphore = redisson.getSemaphore("limit");
semaphore.acquire();   // 减 1，没了就阻塞
```

可用于分布式限流（限制 N 个并发处理）。

## 四、Redlock：跨实例的强一致方案

### 为什么有 Redlock

Redisson 默认基于**单 master**：
```
master 拿到锁 → 还没同步给 slave → master 挂 → slave 升主
新主上没有这把锁 → 第二个客户端拿到锁 → 两个客户端同时持锁
```

**主从异步复制 + 故障转移 = 锁不可靠**。

### Redlock 算法（Redis 作者 antirez 提出）

要求 **N 个独立的 Redis master**（推荐 5 个，无主从）：

```
1. 客户端获取当前时间戳 T1
2. 用相同 key/value，依次向 5 个 master 申请锁，每次都设很短的超时（如 50ms）
3. 至少 (N/2 + 1) = 3 个成功，且总耗时 < TTL，才算获锁成功
4. 锁的有效时间 = 原始 TTL - (T2 - T1)
5. 失败时（3 个没拿到 / 总耗时超 TTL），向所有节点发释放命令
```

```java
RedissonClient r1 = ...;     // 5 个独立 Redis 实例
RedissonClient r2 = ...;
RedissonClient r3 = ...;

RLock lock1 = r1.getLock("key");
RLock lock2 = r2.getLock("key");
RLock lock3 = r3.getLock("key");

RedissonRedLock redLock = new RedissonRedLock(lock1, lock2, lock3);
redLock.lock();
```

### Redlock 的争议

**Martin Kleppmann（《DDIA》作者）反对 Redlock**：
- 时钟漂移（GC、NTP 跳变）会破坏算法假设
- 网络延迟下"3 个节点拿到"也可能不安全
- 进程暂停（GC stop-the-world、磁盘 IO 阻塞）期间锁可能被另一个客户端拿到

**antirez 反驳**：Redlock 假设的是"无界限 STW 不存在 / 时钟单调递增"，工程上够用。

**实际选型**：
- 一般业务：Redisson 单 master 够用，**绝对正确性不必要**
- 极端正确：用 ZooKeeper（CP，强一致）
- Redlock：成本高（5 个 Redis）+ 复杂度高 + 仍有争议，**实战中很少用**

## 五、与 ZooKeeper 锁对比

| 维度 | Redis（Redisson） | ZooKeeper |
| --- | --- | --- |
| **CAP** | AP | CP |
| **性能** | 高（10 万 QPS） | 中（1-2 万 QPS） |
| **可靠性** | 主从切换可能丢锁 | 强一致，不会丢 |
| **实现** | Hash + Lua + watchdog | 临时顺序节点 + Watcher |
| **羊群效应** | 无 | 有（顺序节点缓解） |
| **适用** | 互联网业务，秒杀、订单 | 金融、配置中心、领导选举 |

## 六、面试高频追问

### Q1：为什么要用 Lua 释放锁？

`GET + 判断 + DEL` 三步操作不是原子的：
```
1. GET key → 拿到自己的 uuid
2. 此时锁过期了，B 拿到锁
3. DEL key → 删了 B 的锁
```
Lua 在 Redis 单线程里执行是原子的，避免这个时序问题。

### Q2：看门狗续期会一直续下去吗？

不会。两种停止条件：
1. **正常 unlock**：客户端调用 `unlock()`，watchdog 停止
2. **客户端断连/挂掉**：JVM 死了，watchdog 线程也死了，30s 后锁自然过期

> **极端情况**：JVM 还活着但应用 hang 住（GC、死循环），watchdog 还在续期 → 锁一直被持着。这种情况无解，需要业务层超时判断。

### Q3：业务执行时间不可预测，TTL 设多少？

- 默认 30s 够大多数场景（watchdog 自动续期）
- 业务明确知道短（比如 1 秒），可以 `lock.lock(2, TimeUnit.SECONDS)` 显式短锁，不用 watchdog
- **不要设很长的固定 TTL**（如 10 分钟）：客户端崩了就锁 10 分钟，影响并发

### Q4：Redisson 在主从切换时会丢锁吗？

会。这就是 Redlock 要解决的问题。
**实战做法**：
- 大部分业务接受这个风险（概率很低，主从切换的几秒内）
- 业务自带幂等（详见 [幂等](../Distributed/幂等.md)），即使锁丢了执行两次也无害
- 强一致场景才用 ZooKeeper

### Q5：可以用本地锁 + 分布式锁吗？

可以，叫**双重锁**。先抢本地 `synchronized`，再抢分布式锁：

```java
synchronized (LOCAL_LOCK) {
    RLock dist = redisson.getLock(key);
    dist.lock();
    try { /* 业务 */ } finally { dist.unlock(); }
}
```

减少分布式锁竞争（同一 JVM 内本地锁先收敛），适合单机并发量极高的场景（如秒杀）。

### Q6：分布式锁加了之后并发还是高吗？

**取决于锁的粒度**：
- **粗粒度**（`lock:order`）：所有订单串行，性能差
- **细粒度**（`lock:order:${userId}`）：只锁单个用户，并发不受影响

**优化技巧**：
- key 拆分：`lock:order:${shardId}`，按业务维度散列
- 锁段（segment）：仿 ConcurrentHashMap，锁住一段
- 无锁化：能用 Lua 原子操作（INCR / SETNX）就不要用锁

### Q7：怎么实现"获取不到锁就放弃"？

```java
// tryLock 第一个参数是等待时间
boolean got = lock.tryLock(0, 30, TimeUnit.SECONDS);
if (!got) {
    return Result.fail("正在处理中，请稍后");
}
```

秒杀场景必备：抢不到锁就立刻返回，不要堆积线程。

### Q8：分布式锁怎么实现可重入？

Redisson 用 **Hash 数据结构**：
```
HASH lock:key {
   "uuid:threadId" -> 重入次数
}
```
加锁时 `HINCRBY` +1，解锁时 -1，归 0 才 DEL key。
关键是要用 **Hash + Lua** 保证操作原子。

### Q9：Redis 单线程如何保证多个分布式锁请求的顺序？

Redis 命令串行执行，先到先处理。但**网络到达顺序不可靠**——客户端 A、B 几乎同时发请求，谁先到 Redis 谁拿锁。这不叫"先到先得"，叫"先到 Redis 先得"。
要严格 FIFO 用 **公平锁**（Redisson `getFairLock`）。

### Q10：Redis 挂了怎么办？

详见 [秒杀场景-Redis故障应对](./秒杀场景-Redis故障应对.md)。
分布式锁场景下：
- **熔断 + 兜底**：拿不到 Redis 直接降级（拒绝请求 / 走单机锁）
- **不要 fallback 到 DB 锁**：DB 性能更差，会被打挂
- **多级**：本地锁 + Redis 锁，Redis 挂了至少本地锁还能扛单机并发

## 七、生产真实踩坑

### Case 1：误删别人的锁

V3 写法（没用 UUID 校验），业务执行超过锁 TTL → DEL 删了下一个客户端的锁 → 双客户端持锁 → 库存超卖。
**修复**：升级到 V4，UUID + Lua 校验。

### Case 2：watchdog 没生效

代码：
```java
lock.lock(30, TimeUnit.SECONDS);    // 显式传了 leaseTime！
```
误以为 watchdog 会续期，结果业务执行 35 秒，锁过期了被别人抢了。
**修复**：去掉 leaseTime 参数 → `lock.lock()`。

### Case 3：unlock 抛异常导致锁泄漏

```java
lock.lock();
try { ... } finally {
    lock.unlock();    // 当前线程没持有锁会抛 IllegalMonitorStateException
}
```
锁过期了再 unlock 就抛异常，线程没处理 → 锁残留（虽然有 TTL 兜底）。
**修复**：
```java
finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

### Case 4：粒度太粗导致并发崩

商品库存锁写成 `lock:stock`，所有商品共用一把锁，QPS 100 直接卡死。
**修复**：改成 `lock:stock:${goodsId}`，按商品 ID 分散。

### Case 5：嵌套锁死锁

业务 A 锁了资源 X 后再锁 Y，业务 B 锁了 Y 后再锁 X → 死锁，watchdog 还续期，永远不释放。
**修复**：
- 强制锁顺序（小 ID 先锁）
- 用 `tryLock` 带超时，拿不到就回滚
- 联锁 `MultiLock` 一次性锁全

### Case 6：超时时间太短，业务被频繁打断

`lock.lock(2, SECONDS)`，业务慢的时候经常 2 秒还没跑完，锁过期被抢，导致业务异常重试。
**修复**：要么用默认 TTL + watchdog，要么把超时设到 P99 业务耗时的 3 倍以上。

### Case 7：跨服务持锁不释放

服务 A 拿了锁，调服务 B 等待响应，B 卡住 5 分钟。锁早过期，但 A 一直认为自己持锁，处理完后 unlock 抛异常。
**修复**：
- 跨服务调用前，重新检查锁是否还在
- 或者根本不要"长锁 + 跨服务"，把跨服务调用移出锁的临界区

## 八、答题模板（60 秒话术）

> 单机锁锁不住跨进程业务——分布式锁解决多实例间的互斥。
>
> 演进路径：**SETNX**（原始）→ **SET key value NX EX**（合并原子）→ **UUID + Lua 释放**（防误删）→ **Redisson + 看门狗**（生产标配）。每一步解决：死锁（加超时）、原子性（NX+EX 合一）、误删（带 owner 标识 + Lua 校验）、业务超时锁失效（看门狗每 1/3 leaseTime 续期）。
>
> 生产用 **Redisson** 默认 watchdog（30s 自动续）；可重入用 Hash 结构（owner + count）；**长业务别显式传 leaseTime**——会关掉看门狗，让锁可能在业务跑一半时失效。
>
> 极端可靠性场景考虑 **Redlock**（争议大，多数派算法但有时钟漂移问题）或干脆用 **ZooKeeper**（CP 系统天然适合锁）。
>
> 关键配套：**业务幂等 + 限流 + 监控锁等待时长 P99**——不要把分布式锁当万能。
