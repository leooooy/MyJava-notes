# Redis 消息队列方案

> 面试高频："Redis 怎么做消息队列？"
> 答得 senior 的关键是说清 **三种方式（List / Pub-Sub / Stream）的演进与取舍**，再给出生产选型。
> 别只会说 "用 LPUSH/BRPOP" —— 这是初级答案。

---

## 一、Redis 做 MQ 的三种方式（演进史）

| 方式 | 引入版本 | 一句话定位 | 评价 |
| --- | --- | --- | --- |
| **List + BRPOP** | 1.0 | 最朴素的阻塞队列 | 简单但功能单薄 |
| **Pub/Sub** | 2.0 | 发布订阅广播模型 | **不可靠**，订阅者下线消息丢失 |
| **Stream** | **5.0** | 完整 MQ（消费者组 + ACK + 持久化 + 回放） | **2024 年生产首选** |

→ Redis 5.0 之前用 List 凑合，2.0~5.0 偶尔用 Pub/Sub，**5.0+ 应直接用 Stream**。

---

## 二、方式 1：List + BRPOP

### 2.1 基本用法

```bash
# 生产者
LPUSH mq:order '{"orderId":1001,"userId":2001}'

# 消费者（阻塞拉取）
BRPOP mq:order 30      # 30 秒超时，无消息时阻塞
```

### 2.2 优点

- **极简**：两条命令
- **持久化**：List 的数据进 RDB/AOF
- **顺序**：先进先出
- **多生产者支持**：N 个生产者 LPUSH 到同一 key

### 2.3 致命缺点

| 缺点 | 后果 |
| --- | --- |
| **无 ACK 机制** | 消费者拿到消息后崩溃，**消息永久丢失** |
| **不支持消费者组** | 同一消息只能被一个消费者拿到，无法广播给多个独立服务 |
| **不支持重放** | 消费过的消息无法再读 |
| **没有消息 ID** | 无法去重、无法按 ID 跳转 |
| **没有延时** | 想做延时队列要用 ZSet（详见 ZSet 文档） |

### 2.4 改进方案：BRPOPLPUSH（"备份"模式）

```bash
# 消费者拿消息时同时备份到"处理中"队列
BRPOPLPUSH mq:order mq:order:processing 30

# 处理成功后删除备份
LREM mq:order:processing 1 ${msg}

# 处理失败：消息留在 processing 队列，定时任务可以拣回
```

→ 弥补"无 ACK"的缺陷，但仍很简陋（无超时识别、无重试计数等）。

### 2.5 适用场景

- 简单的内部任务队列（如发邮件、写日志）
- 容忍偶尔丢消息
- 不需要复杂消费语义

→ **生产新项目不建议用 List 当 MQ**。

## 三、方式 2：Pub/Sub（发布订阅）

### 3.1 基本用法

```bash
# 订阅（消费者，必须先订阅）
SUBSCRIBE channel:order

# 发布（生产者）
PUBLISH channel:order '{"orderId":1001}'
# → 返回收到消息的订阅者数量

# 模式订阅（通配符）
PSUBSCRIBE channel:*
```

### 3.2 工作机制

```
[Publisher] ──PUBLISH──→ [Redis Server]
                              │
                  ┌───────────┼───────────┐
                  ▼           ▼           ▼
             [Sub A]      [Sub B]      [Sub C]
```

- 广播模型：消息发给**所有当前订阅者**
- 订阅者**离线时发的消息全丢**
- Redis 不存储消息，**没有持久化**

### 3.3 致命缺点（比 List 还差）

| 缺点 | 后果 |
| --- | --- |
| **完全不持久化** | Redis 重启 / 订阅者重连 → 消息全丢 |
| **离线消息丢失** | 订阅者掉线那一刻起的消息再也收不到 |
| **没有 ACK** | 没法确认 |
| **慢消费者拖累 Redis** | 消息堆在订阅者输出缓冲区，可能被强断连接 |
| **没有消息 ID** | 无法回溯 |

### 3.4 实际可用的场景

不是 MQ！是"实时广播通知"：
- **服务间事件广播**（缓存失效通知、配置变更广播）
- **Sentinel 哨兵通信**（Redis 内部用 Pub/Sub）
- **Redis 自身的 keyspace 通知**

→ **不要把 Pub/Sub 当 MQ 用**——这是典型的初级误解。

## 四、方式 3：Stream（5.0+ 推荐）

### 4.1 是什么

5.0 引入的**完整 MQ 类型**，弥补 List 和 Pub/Sub 的全部缺点：

| 特性 | List | Pub/Sub | Stream |
| --- | --- | --- | --- |
| 持久化 | ✓ | ✗ | ✓ |
| ACK 机制 | ✗ | ✗ | ✓ |
| 消费者组 | ✗ | 类似（广播） | ✓ |
| 历史消息回放 | ✗ | ✗ | ✓ |
| 消息 ID | ✗ | ✗ | ✓（自增） |
| 阻塞读取 | ✓ | 隐式 | ✓ |
| 多生产/多消费 | ✓ | ✓ | ✓ |

### 4.2 核心命令

```bash
# 生产
XADD mq:order * orderId 1001 userId 2001
# *  = 自动生成 ID（毫秒时间戳-序号）
# 返回 ID 如 "1735200000000-0"

# 消费（无消费者组，简单读）
XREAD COUNT 10 BLOCK 30000 STREAMS mq:order $
# $ = 只读新消息；0 = 从头读

# 消费（有消费者组，完整 MQ 模式）
XGROUP CREATE mq:order group1 $ MKSTREAM         # 创建组
XREADGROUP GROUP group1 consumer1 COUNT 10 BLOCK 30000 STREAMS mq:order >
XACK mq:order group1 1735200000000-0             # 确认消费

# 待处理列表（PEL = Pending Entries List）
XPENDING mq:order group1                         # 查未 ACK 的
XPENDING mq:order group1 IDLE 60000 - + 10       # 查空闲超 60s 的
XCLAIM mq:order group1 consumer2 60000 1735200000000-0   # 把消息认领给别人

# 长度控制
XADD mq:order MAXLEN 10000 * field value         # 队列最多 10000 条
XADD mq:order MAXLEN ~ 10000 * field value       # 近似（更高效）
XLEN mq:order
XDEL mq:order 1735200000000-0
```

### 4.3 消费者组模型

```
                       ┌── consumer1
                       │
[Producer] ─→ [Stream] ┼── consumer2  ←── group1（消息只发给组内一个）
                       │
                       └── consumer3

                       ┌── consumer4 ←── group2（独立组，所有消息也发到这里）
                       │
                       └── consumer5
```

**核心特点**：
- 同一消息**在一个组内只发给一个消费者**（横向扩展处理）
- 不同组之间**互相独立**（每组都能拿到全部消息）

→ 类似 Kafka 的 Consumer Group。

### 4.4 PEL（Pending Entries List）—— 关键面试点

每个消费者组维护一个 PEL：**已发出但未 ACK 的消息列表**。

```
消息流转：
  XADD → 消息进入 stream
  XREADGROUP → 从组里读消息，**进入该组的 PEL**
  XACK → 从 PEL 移除
```

**消费者崩溃恢复**：
- 重启后用 `XREADGROUP GROUP g c COUNT 10 STREAMS k 0` 读 PEL（不是 `>`），先处理未确认的
- 用 `XPENDING` 查空闲太久的消息
- 用 `XCLAIM` 把"挂掉消费者"的消息转移给其他消费者（防止单点消费失败）

### 4.5 完整生产/消费示例（Java）

```java
// 生产
StreamEntryID id = jedis.xadd("mq:order", StreamEntryID.NEW_ENTRY,
    Map.of("orderId", "1001", "userId", "2001"));

// 消费者组初始化（一次）
try {
    jedis.xgroupCreate("mq:order", "group1", new StreamEntryID("0-0"), true);
} catch (JedisDataException e) { /* group already exists */ }

// 消费循环
while (true) {
    Map<String, StreamEntryID> streams = Map.of("mq:order", StreamEntryID.UNRECEIVED_ENTRY);
    List<Map.Entry<String, List<StreamEntry>>> result = 
        jedis.xreadGroup("group1", "consumer1",
            XReadGroupParams.xReadGroupParams().count(10).block(30000),
            streams);
    
    for (Map.Entry<String, List<StreamEntry>> entry : result) {
        for (StreamEntry msg : entry.getValue()) {
            try {
                process(msg.getFields());
                jedis.xack("mq:order", "group1", msg.getID());
            } catch (Exception e) {
                // 不 ACK，下次读 PEL 时还会再来
            }
        }
    }
}
```

### 4.6 长度控制（防内存溢出）

```bash
# 严格上限
XADD mq:order MAXLEN 10000 * ...
# Stream 最多保留 10000 条，超过自动删除最老的

# 近似上限（推荐，性能高）
XADD mq:order MAXLEN ~ 10000 * ...
# 实际可能略多于 10000，但操作 O(1)

# 按 ID 修剪
XTRIM mq:order MINID 1735100000000     # 删 ID 早于此的
```

## 五、Stream vs RocketMQ / Kafka

| 维度 | Redis Stream | RocketMQ | Kafka |
| --- | --- | --- | --- |
| **吞吐** | 10 万 / 秒（单实例） | 10 万 / 秒 | **百万 / 秒** |
| **持久化** | RDB/AOF | 磁盘文件 | 磁盘文件（顺序 IO） |
| **消息保留** | 有限（内存） | 长期（磁盘） | 长期（磁盘） |
| **延迟** | 微秒 | 毫秒 | 毫秒 |
| **顺序** | Stream 内有序 | Topic-Queue 内有序 | Partition 内有序 |
| **事务** | Lua 脚本可做 | 原生事务消息 | 事务（2.0+） |
| **死信** | 自己实现 | 原生 DLQ | 自己实现 |
| **运维** | 简单（Redis 已有） | 中（专业 MQ 集群） | 高（依赖 ZK/KRaft） |
| **典型场景** | 中小流量、内部任务 | 业务消息（订单、支付） | 日志、事件流 |

### 5.1 选 Stream 的合理场景

- **已经在用 Redis**，不想多引入 MQ 基础设施
- **流量中等**（< 10 万 QPS）
- **消息保留时间短**（小时~天级）
- **需要消费者组 + ACK** 但不需要专业 MQ 的全套功能

### 5.2 不要用 Stream 的场景

- **海量日志 / 事件流**（Kafka）
- **金融级业务消息**（RocketMQ 事务消息）
- **跨数据中心**（专业 MQ 有完善的镜像方案）
- **消息需要保留几个月**（磁盘存储 MQ）

## 六、Redis MQ 的常见辅助场景

### 6.1 延时队列（用 ZSet）

详见 [有序集合 ZSet](./有序集合-ZSet.md#82-延时队列)。

```bash
# 生产：30 秒后执行
ZADD delay:queue ${execTime} ${task}

# 消费：定时拉取已到期任务
ZRANGEBYSCORE delay:queue 0 ${now} LIMIT 0 10
```

Stream **不直接支持延时**，要靠 ZSet + 定时任务转发到 Stream。

### 6.2 优先级队列（用 ZSet）

```bash
# score = 优先级
ZADD priority:queue 1 highTask
ZADD priority:queue 5 midTask
ZPOPMIN priority:queue
```

详见 [有序集合 ZSet](./有序集合-ZSet.md#84-优先级队列)。

### 6.3 简单 Pub-Sub 替代

如果只需要"广播事件"（不要求可靠），用 Pub/Sub。
如果要可靠广播，用 Stream（多个消费者组）。

## 七、面试高频追问

### Q1：List、Pub/Sub、Stream 三者怎么选？

| 业务需求 | 推荐 |
| --- | --- |
| 简单内部任务队列，能容忍丢消息 | List + BRPOP |
| 实时广播事件（缓存失效、配置推送） | Pub/Sub |
| **正经业务消息队列**（订单、库存、支付前置） | **Stream** |
| 高并发 / 海量日志 | RocketMQ / Kafka |

### Q2：Pub/Sub 为什么不能当 MQ？

3 个致命问题：
1. **完全不持久化**——Redis 重启全丢
2. **订阅者掉线丢消息**——重连后从那一刻开始算
3. **没有 ACK**——无法确认消费成功

只能做"实时广播"，不是 MQ。

### Q3：List 当 MQ 怎么防丢消息？

用 `BRPOPLPUSH` 模式：取消息时同时备份到"处理中"队列，处理成功才删除。
处理失败 / 消费者崩溃 → 消息留在 processing 队列，定时任务拣回。

### Q4：Stream 的 PEL 是什么？

**Pending Entries List（待确认列表）**，每个消费者组维护一份。
- 消费者 XREADGROUP 读出消息 → 进入 PEL
- 消费者 XACK 确认 → 从 PEL 移除
- 消费者崩溃 → 消息留在 PEL，重启后可重读

PEL 解决了"消息至少消费一次"的可靠性。

### Q5：Stream 的消息会丢吗？

正常情况不会：
- XADD 写入 → 持久化（RDB/AOF）
- XREADGROUP 读出 → 进入 PEL
- 消费者崩溃 → 重启后从 PEL 重读
- 消费者完全失联 → XCLAIM 转给其他消费者

但极端场景仍可能丢：
- XADD 后主库挂、未同步给从库 → 主从切换丢
- AOF 配置 always 才彻底不丢

### Q6：Stream 和 Kafka 的本质区别是什么？

**存储介质**：Stream 在内存（受限），Kafka 在磁盘（无限）。
**吞吐**：Kafka 百万级，Stream 十万级。
**生态**：Kafka 流处理生态完善（Streams、Connect），Stream 仅基础 MQ 功能。
**复杂度**：Redis 单进程已有，Kafka 需要 ZK/KRaft 集群。

### Q7：消费者组和广播怎么共存？

**广播 = 多个消费者组**：
- 订单服务订阅 stream，组名 `order-svc`
- 通知服务订阅同 stream，组名 `notify-svc`
- 同一条消息，每组各拿到一份

→ 完美支持"一份消息多个独立消费者"。

### Q8：Stream 怎么实现延时？

**不直接支持**。变通方案：
- 用 ZSet 做延时存储，score = 执行时间
- 定时任务扫到期的，迁移到 Stream
- 见 [ZSet 延时队列](./有序集合-ZSet.md#82-延时队列)

### Q9：Stream 的消息 ID 是什么格式？

`<毫秒时间戳>-<序号>`，如 `1735200000000-0`。
- 同一毫秒内的多条消息序号递增
- ID 全局有序、可比较
- XRANGE 按 ID 范围查询

### Q10：Stream 怎么防止内存爆？

`XADD MAXLEN 10000` 或 `MAXLEN ~ 10000`（近似，性能更好）。
超过后自动删除最老的消息。
**注意**：被裁剪的消息如果还在 PEL 里没 ACK，PEL 里仍保留引用，但 stream 本体没了。

### Q11：怎么处理"卡住"的消费者？

```bash
# 找空闲超 60s 的消息
XPENDING mq:order group1 IDLE 60000 - + 10

# 把消息转给其他消费者
XCLAIM mq:order group1 healthyConsumer 60000 ${msgId}
```

定时任务跑这个逻辑，自动转移挂掉消费者的未完成消息。

### Q12：Pub/Sub 在 Cluster 下能正常工作吗？

可以，但有特点：消息会在所有节点广播（用 Cluster Bus）。
**Sharded Pub/Sub（7.0+）**：用 `SSUBSCRIBE` / `SPUBLISH`，按 channel hash 路由到固定节点，性能更好但只在该节点订阅可见。

## 八、生产真实踩坑

### Case 1：把 Pub/Sub 当 MQ 用，重启全丢

老项目用 Pub/Sub 做订单通知，Redis 重启后丢了 5 分钟的订单 → 客服爆炸。
**修复**：迁移到 Stream + 消费者组 + ACK。

### Case 2：List 当 MQ，消费者崩溃丢消息

消费者用 BRPOP 拿到消息后处理时 OOM 重启，消息再也找不回来。
**修复**：改 BRPOPLPUSH 备份模式；或迁 Stream。

### Case 3：Stream 没设 MAXLEN，内存爆

业务上线没设上限，跑了一周 Stream 涨到 10GB，Redis OOM。
**修复**：设 `MAXLEN ~ 100万` 或定期 XTRIM。

### Case 4：Stream 消费者组未消费消息累积

某个消费者组的所有消费者全挂了，没人 XACK，PEL 持续增长，消息保留在 stream 里 → 内存暴涨。
**修复**：监控 XPENDING 数量；XCLAIM 转移到其他组；最坏情况 XGROUP DESTROY 重建组。

### Case 5：单 Stream 成为热点

所有订单都进同一个 Stream，分片 master 100% CPU。
**修复**：按 hash 分多个 Stream（mq:order:0、mq:order:1、...）；客户端按 orderId hash 路由。

### Case 6：消费者组消费太慢，PEL 越来越大

业务高峰期生产 10 万/秒，消费者只能跑 1 万/秒 → PEL 累积百万。
**修复**：增加消费者实例（Stream 支持横向扩展）；优化消费逻辑。

### Case 7：Stream 在 Cluster 下没考虑分片

业务以为 Stream 是分布式的，实际 Stream 是单 key —— 整个 stream 在一个 slot 上，性能受单 master 限制。
**修复**：业务层做分片（多个 Stream key）；或上专业 MQ。

## 九、答题模板（60 秒话术）

> Redis 做 MQ 走过三代：**List**（朴素）→ **Pub/Sub**（不可靠）→ **Stream**（5.0+ 完整 MQ）。
>
> **List** 缺点是无 ACK、无消费者组、消费者拉取后崩溃就丢消息——可以用 BRPOPLPUSH 备份模式改进。**Pub/Sub** 完全不持久化、订阅者离线就丢、没 ACK，**根本不是 MQ**，只适合实时广播（行情推送、即时通知）。
>
> **Stream 是 5.0+ 首选**，对标 Kafka 小型版本——支持**消费者组**（多消费者负载均衡）、**ACK 机制**、**PEL（Pending Entry List 跟踪未 ACK 消息）**、历史回放。PEL 是关键：消费者拉到消息后未 ACK 就停留在组的 PEL，崩溃重启可重读；XCLAIM 把挂掉消费者的消息转移给其它消费者。
>
> 和专业 MQ 比，吞吐、持久化、生态都不及 Kafka / RocketMQ；但流量中等且已部署 Redis 时是合适的轻量选择。
>
> **延时队列** Stream 不支持，要用 **ZSet**（score = 执行时间）+ 定时扫描迁移到正常队列。
