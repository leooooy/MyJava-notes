# Redis 数据结构总览

> Redis 之所以强，本质就两件事：**精心选择的数据结构** + **单线程 + IO 多路复用**。
> 这一篇是上层数据类型 + 底层编码的全景图，**面试被问"Redis 有几种数据结构" 必答**。
> 单类型的细节进各自子页，这页只讲全局取舍和决策树。

## 二、5 种高级数据类型

| 类型 | 应用 | 底层 |
| --- | --- | --- |
| **Bitmap** | 大规模布尔状态（签到、活跃用户） | String 的位操作 |
| **HyperLogLog** | 海量去重计数（UV，误差 0.81%） | 12KB 固定大小 |
| **Geo** | 地理位置（附近的人） | ZSet（GeoHash 作 score） |
| **Stream** | 完整消息队列（5.0+） | rax tree + listpack |
| **Bitfield** | 多字段位操作 | String 位操作扩展 |

> **Bitmap、Geo、HLL 都是"复合类型"**——底层借用基础类型实现，只是命令封装不同。

## 五、底层结构详解

### 5.1 SDS（Simple Dynamic String）

C 字符串的"加强版"。详见 [字符串-String.md](./字符串-String.md#四sdssimple-dynamic-string深度解析)。

**解决了 C 字符串四个问题**：
- 长度 O(1)（vs C 是 O(n)）
- 二进制安全（vs C 以 \0 结尾）
- 自动扩容（vs C 缓冲区溢出）
- 空间预分配 + 惰性释放（减少 realloc 次数）

### 5.2 dict（哈希表）

Hash 和 Set 的底层。详见 [哈希-Hash.md](./哈希-Hash.md#四hashtable-数据结构详解)。

**核心点**：
- 数组 + 拉链法（头插）
- 位运算取模（size 必须 2 的幂）
- **两张表 + 渐进式 rehash**：扩容时分摊到每次 CRUD，避免阻塞主线程
- 负载因子 ≥ 1（普通）/ ≥ 5（BGSAVE 期间）触发扩容

### 5.3 ziplist（压缩列表，旧）

Hash/List/ZSet/Set 小集合的旧实现。

**特点**：紧凑数组，节省内存。
**致命问题**：连锁更新（O(N²)）—— 每个节点存"前一个节点的长度"，长度变化触发级联升级。

### 5.4 listpack（替代 ziplist，7.0+）

7.0 起逐步取代 ziplist，**核心改进**：每个节点不存"前一个的长度"，只存"自己的长度"，反向遍历靠末尾长度字段。彻底无连锁更新。

### 5.5 quicklist（List 专属，3.2+）

双向链表 + 多段小 ziplist/listpack。

**目的**：平衡 ziplist 紧凑（小数据省内存）和 linkedlist 高性能（大数据 O(1) 头尾插入）。
**节点压缩**：中间节点可 LZF 压缩（`list-compress-depth`）。

### 5.6 intset（整数集合）

Set 全整数小集合的实现。

**特点**：
- 有序数组（升序）
- 二分查找 O(log N)
- 统一编码（所有元素同一字节宽度，按最大值升级）
- 只升不降

### 5.7 skiplist（跳表）

ZSet 大集合的核心。详见 [有序集合-ZSet.md](./有序集合-ZSet.md#五跳表skiplist深度解析)。

**核心特性**：
- 有序链表 + 多层稀疏索引
- 平均 O(log N)，最坏 O(N)
- 节点层数随机决定（P = 0.25，期望 1.33 层）
- 配合 dict 实现 ZSet 的 O(1) 查 score + O(log N) 范围查询
- 比红黑树简单 + 范围查询友好

### 5.8 rax（基数树）

Stream 的索引结构。压缩前缀树（Radix Tree）的变种。
不在常规面试范围。

## 六、选型决策树

### 6.1 按"操作模式"选

```
要不要排序？
├─ 要 → ZSet
└─ 不要
   │
   要不要去重？
   ├─ 要 → Set / Bitmap / HyperLogLog（看精度和数据规模）
   └─ 不要
      │
      要不要按字段访问？
      ├─ 要 → Hash
      └─ 不要
         │
         要不要按位置访问 / 队列语义？
         ├─ 要 → List / Stream
         └─ 不要 → String
```

### 6.2 按"数据特征"选

| 数据特征 | 推荐类型 |
| --- | --- |
| 单值 / 序列化对象 / 整数计数 | String |
| 多字段对象（频繁单字段访问） | Hash |
| 用户在线状态（亿级用户） | Bitmap |
| 海量去重计数（亿级 UV） | HyperLogLog |
| 排序集合（榜单 / 延时） | ZSet |
| 集合运算（交并差） | Set |
| 消息队列 | Stream（5.0+，旧版用 List） |
| 地理位置 | Geo |

### 6.3 按"内存敏感度"选

10 亿用户的"是否注册"判断：

| 方案 | 内存 | 精度 |
| --- | --- | --- |
| Set 存 UID | ~20 GB | 精确 |
| Bitmap | 125 MB | 精确（前提 ID 连续） |
| HyperLogLog | 12 KB | ~99.2% |
| 布隆过滤器 | ~1.2 GB | ~99% |

→ 选哪个看**精度要求 + ID 形态 + 内存预算**。

## 七、面试高频追问

### Q1：Redis 有几种数据结构？

**5 种基础类型**：String / Hash / List / Set / ZSet
**+ 5 种高级类型**：Bitmap / HyperLogLog / Geo / Stream / Bitfield

很多面试官把"数据类型"和"底层编码"混着问，要分清楚。

### Q2：底层有哪些数据结构？

7-8 种：
- **SDS**（简单动态字符串）
- **dict**（哈希表）
- **ziplist**（压缩列表，旧）
- **listpack**（替代 ziplist，7.0+）
- **quicklist**（双向链表 + ziplist/listpack）
- **intset**（整数集合）
- **skiplist**（跳表）
- **rax**（基数树，Stream 用）

### Q3：String 的内部编码？

三种：int / embstr / raw。
- 数字 → int
- 字符串 ≤ 44B → embstr（与 redisObject 内存连续）
- 字符串 > 44B → raw

### Q4：Hash 什么时候用 listpack 什么时候用 hashtable？

7.0+：
- 字段数 ≤ 128 且每个字段名/值 ≤ 64 字节 → listpack
- 否则 → hashtable

`hash-max-listpack-entries`、`hash-max-listpack-value` 控制。

### Q5：List 为什么用 quicklist？

**单一 ziplist**：大集合插入慢（要复制整个内存块）+ 连锁更新风险
**单一 linkedlist**：每节点单独分配内存 + 指针开销大

quicklist 取中：链表 + 节点是小段 ziplist/listpack，平衡内存和性能。

### Q6：ZSet 为什么用 skiplist + dict 两个结构？

各负其责：
- **dict**：O(1) 通过 member 查 score（ZSCORE）
- **skiplist**：O(log N) 排名 + 范围查询（ZRANK / ZRANGE）

省时间、舍空间（多 30% 内存）。

### Q7：跳表 vs 红黑树？

详见 [有序集合-ZSet.md - 为什么用跳表](./有序集合-ZSet.md#六为什么用跳表而不是红黑树)。
跳表实现简单、范围查询友好、调试方便、排名 O(log N)。Redis 选它正确。

### Q8：7.0 的 listpack 解决了什么？

ziplist 的**连锁更新问题**（O(N²)）。
listpack 不再存"前一个节点的长度"，每个节点自描述长度，反向遍历靠末尾字段算位置。

### Q9：怎么查看一个 key 的内部编码？

```bash
OBJECT ENCODING key
```

返回 `int / embstr / raw / listpack / hashtable / quicklist / intset / skiplist`。

### Q10：编码会自动降级吗？

**不会**。所有类型的编码切换都是"只升不降"。
原因：降级判断成本高（要扫全集合），而升级是被动触发（插入时自然发现）。

### Q11：Bitmap 和 Set 怎么选？

| 场景 | 选 |
| --- | --- |
| 用户 ID 连续整数 + 大量布尔 | Bitmap（节省 95% 内存） |
| 用户 ID 是 UUID / 字符串 | Set |
| 需要原始元素值 | Set（Bitmap 只能存 0/1） |

### Q12：HyperLogLog 怎么实现"12KB 估计 1 亿基数"？

基于伯努利试验 + 调和平均值 + 概率密度估算。
核心：把 hash 值的"前缀 0 的个数"作为基数信息，用桶（默认 16384）平均化。
**不能用来精确计数 / 列出元素**，只能估计基数。

### Q13：Stream 和 List 当 MQ 比？

详见 [列表-List.md - List vs Stream](./列表-List.md#六list-vs-stream面试常问)。
Stream 完胜：消费者组、ACK、历史回放、阻塞 + 多消费、消息 ID 严格有序。

## 八、底层数据结构 vs Java 集合对照表

帮 Java 同学建立直觉：

| Redis | Java 类比 | 关键差异 |
| --- | --- | --- |
| String | `String` / `byte[]` | SDS 是二进制安全 + O(1) 长度 |
| Hash (hashtable) | `HashMap` | 渐进式 rehash + 头插法 + 位运算取模 |
| Hash (listpack) | 无（紧凑数组） | Java 没有这种紧凑结构 |
| List (quicklist) | `LinkedList` 改进版 | 节点是小数组而非单元素 |
| Set (hashtable) | `HashSet` | 同 |
| Set (intset) | 无（紧凑有序数组） | Java 用 `TreeSet<Integer>` 类似但更重 |
| ZSet | `TreeMap<String, Double>` + `HashMap<String, Double>` | dict + skiplist 双结构 |
| skiplist | `ConcurrentSkipListMap` | 思路一致，Redis 单线程无并发逻辑 |

## 十、答题模板（60 秒话术）

> Redis 提供 **5 种基础类型**（String / Hash / List / Set / ZSet）+ **5 种高级类型**（Bitmap / HyperLogLog / Geo / Stream / BitField）。每种类型背后有多种**内部编码**——根据数据规模自动切换且**只升不降**。
>
> 底层数据结构有 SDS、dict、ziplist / **listpack**（7.0+ 用 listpack 替代 ziplist 解决连锁更新）、quicklist、intset、skiplist。
>
> 版本演进：3.2 引入 quicklist 改造 List，5.0 引入 Stream 做 MQ，6.0 网络 IO 多线程，7.0 用 listpack 全面替换 ziplist。
>
> 选型按"是否需要排序 / 去重 / 字段访问 / 队列语义"判断；加分点是讲清 **ziplist 连锁更新缺陷**、**跳表 P=0.25 的取舍**、**ZSet 用 dict + skiplist 双结构并存**的设计动机。
