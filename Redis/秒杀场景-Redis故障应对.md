# 秒杀场景 - Redis 故障应对

> 经典面试题。回答的关键不是背"几条预案"，而是讲清楚 **三层逻辑**：
> 1. **预防**（不让它挂）→ 2. **降级**（挂了能扛）→ 3. **恢复**（挂完能补）。
> 拿出这三层框架，再填具体方案，比直接报"加哨兵、加本地缓存"高一个段位。

---

## 一、为什么秒杀强依赖 Redis

先把秒杀链路画清楚，才能讲清楚"哪里挂了影响哪一段"。

```
[用户]
  │
[CDN/前端]                ← 静态资源、按钮置灰
  │
[网关层 Nginx/Gateway]    ← 限流、签名、防刷
  │
[秒杀服务]
  │
  ├─ ① 库存查询          ← Redis（HOT KEY）
  ├─ ② 用户重复购买校验   ← Redis（用户秒杀标记）
  ├─ ③ 预扣库存（Lua）    ← Redis（核心，原子）
  └─ ④ 发送 MQ           ← MQ
                          │
                          ▼
                       [订单消费者]
                          │
                          ▼
                       [DB 落库]
```

Redis 在秒杀里承担的是**前置筛选层**：靠内存的极速读写，把 **99% 不可能成功的请求**（库存已空、用户已抢过、限流命中）在到达 DB 前过滤掉。

→ 这意味着 **Redis 一旦挂，DB 立刻被打挂**——百万 QPS 直击 MySQL，没有任何系统能扛。所以秒杀里 Redis 的可用性比 DB 更重要。

---

## 二、Redis 挂的几种姿势（先分类）

不是所有"挂"都一样，针对性不同。

| 故障类型 | 表现 | 原因 |
| --- | --- | --- |
| **单节点宕机** | 某 master 进程挂、机器断电 | OOM、硬件、误操作 |
| **主从切换抖动** | 几秒内不可写 | 哨兵/Cluster 选主 |
| **集群分片不可用** | 某 slot 范围全部失败 | 主从同时挂、网络分区 |
| **大 key 阻塞** | 单 key 操作让整个实例卡死 | bigkey、热 key、慢 Lua |
| **网络抖动** | 间歇性超时 | 跨机房、抖网、连接池打满 |
| **缓存击穿/雪崩** | 大量请求同时打 DB | 集中过期、热 key 失效 |
| **整个集群挂** | 全军覆没 | 机房断电、运维误操作 |

> 面试官追问"具体哪种挂"时，能分类回答 = 你真做过线上。

## 三、第一层：预防（高可用建设）

**核心思想**：让 Redis 大概率不挂；少数挂的也要尽量短。

### 1. 部署形态

| 部署 | 可用性 | 适用场景 |
| --- | --- | --- |
| 单实例 | ✗ | 别想，秒杀必死 |
| 主从 + 哨兵 | ★★★ | 中小规模，写不分流 |
| **Redis Cluster** | ★★★★ | 主流秒杀方案，分片+主从 |
| **多机房双活 / 异地多活** | ★★★★★ | 大促、金融级 |

最低要求：**Cluster 至少 3 主 3 从，跨机架部署**。3 个 master 同时挂的概率才能压到可接受。

### 2. 容量与拓扑规划

- **容量预估**：秒杀峰值 QPS × 每个请求消耗的 Redis 操作数 = 集群目标 OPS。例：100 万 QPS × 4 次 Redis 操作 = 400 万 OPS，单分片极限 ~10 万 OPS → **至少 40 个分片**。
- **热点分散**：商品库存 key 不要堆在同一 slot，按商品 ID hash 分散；超热的单个商品要做 **本地缓存 + 多副本 key**（key1, key2, ..., keyN，请求随机选一个）。
- **专享集群**：秒杀活动**独立 Redis 集群**，不和业务公用，避免别人慢查询拖死秒杀。

### 3. 大 key / 热 key 防护

- **大 key**：扫描工具（`redis-cli --bigkeys`）定期巡检，超过阈值（如 10MB / 10000 个元素）的拆分。
- **热 key 自动发现**：抽样监控 + 客户端代理（如 Tair Proxy 自带），命中阈值自动迁移到独立分片或推本地缓存。
- **慢日志监控**：`slowlog-log-slower-than 10000`（10ms），慢 Lua 脚本立刻告警。

### 4. 客户端容错

```java
// Lettuce / Jedis 都要配
- connectionTimeout: 200ms     // 连接超时短
- commandTimeout: 100ms        // 命令超时短，防止单 key 卡死拖垮线程池
- maxRedirects: 3              // Cluster 重定向次数
- retry: 1                     // 失败重试 1 次足矣，多了放大故障
```

> 关键："**快速失败 + 兜底降级**"，比无限重试好。一个长尾请求卡 5 秒，整个线程池就废了。

## 四、第二层：降级（挂了能扛）

预防做得再好，挂了的瞬间还是要救命。降级方案按"故障范围"分级。

### 4.1 局部抖动 / 单分片不可用

#### 方案 A：本地缓存兜底（必备）

```
请求 → Caffeine 本地缓存 → Redis → DB
```

- **库存粗粒度本地缓存**：每个秒杀商品的"是否还有库存"标志位，TTL 1-3 秒
- **用户黑名单本地缓存**：风控命中的用户，本地缓存就足够
- **配置数据本地缓存**：活动配置、商品基础信息，启动时加载

> **取舍**：本地缓存有几秒延迟，但能保证 Redis 抖动期间核心链路不死。秒杀场景"少卖" >> "超卖" >> "完全不可用"。

#### 方案 B：客户端 Hash 降级路由

如果是 Cluster 单分片不可用：
- 客户端识别到该 slot 持续失败，把这部分流量**直接拒绝**（fail-fast 返回"系统繁忙"）
- 不要 fallback 到 DB——这相当于把雪崩从 Redis 转嫁到 DB

### 4.2 整个 Redis 集群不可用

这才是面试官真想问的"Redis 挂了怎么办"。

#### 方案 A：开关降级 + 静态化兜底（推荐）

```java
@GetMapping("/seckill/{id}")
public Result seckill(@PathVariable Long id, HttpServletRequest req) {
    // 配置中心读取降级开关（Nacos/Apollo，本地缓存）
    if (degradeSwitch.isRedisDown()) {
        // 直接返回静态降级页：活动太火爆，请稍后再试
        return Result.fail("系统繁忙，请稍后再试");
    }
    // 正常链路
    return seckillService.doSeckill(id, getUserId(req));
}
```

**核心动作**：
1. 监控发现 Redis 不可用 → 自动或人工拉降级开关
2. 网关层 / 服务层立刻拒绝所有秒杀请求，返回静态页/友好文案
3. **不要让请求落到 DB**，否则 DB 也会挂，整站被拖垮

> "**保大盘**"是核心原则。秒杀这个活动失败用户骂几句没关系，DB 挂了整个商城瘫痪是事故。

#### 方案 B：主备双 Redis（金融级）

- **主集群**：阿里云 Redis Cluster
- **备集群**：自建 Redis Cluster（不同机房）
- 客户端配置主备地址，主集群连续 N 次失败 → 自动切到备集群
- 数据通过双写或异步同步保持一致

成本高，只在大促核心场景用。

#### 方案 C：单机本地分布式协调（极端兜底）

- 业务退化为**单机部署**，每台机器分一份库存（如总 100 个奖品，10 台机器每台 10 个）
- 每台机器用 JVM 内存 + ReentrantLock 处理并发
- 缺点：流量必须严格按机器分发（一致性 hash），否则部分机器卖光部分机器还有

适合**极端兜底**，活动期间 Redis 整个挂的概率极低，但金融场景要预案。

### 4.3 兜底动作三板斧

无论哪种降级，三件事一定要做：

1. **限流**：网关 + 服务双重限流（[限流算法](../Microservice/限流算法.md)），防止降级时把后端打挂
2. **熔断**：Hystrix / Sentinel 熔断 Redis 调用，避免每个请求都要等 Redis 超时（100ms × 10 万并发 = 线程池爆）
3. **异步化**：能异步的全异步，订单写库走 MQ 削峰，让同步链路最短

## 五、第三层：恢复（挂完能补）

故障恢复后，数据一致性怎么补？

### 5.1 库存对账

Redis 重启 → 内存数据可能丢失（取决于持久化策略和故障类型）：

| 场景 | 内存数据 | 处理 |
| --- | --- | --- |
| AOF + everysec | 最多丢 1 秒数据 | 启动后从 AOF 恢复，对账少量差异 |
| RDB only | 丢的数据多 | 必须从 DB 反查重建 |
| 主从切换 | 异步复制可能丢失最近写入 | 对账 |

**对账策略**：
1. 启动后先用 DB 现存库存 reload 到 Redis
2. 检查"已扣库存 = 已生成订单数"是否一致
3. 异常订单回滚（释放库存）或补单

### 5.2 已发出的 MQ 消息处理

降级期间用户拿到"系统繁忙"提示——但**降级前**已经预扣 Redis 库存 + 发了 MQ 的订单怎么办？

- MQ 消费者**幂等**（业务唯一键 + 唯一索引），重启后正常消费
- 已扣 Redis 但 MQ 没发出去的：**事务消息**或**本地消息表**保证最终一致（详见 [分布式事务](../Distributed/分布式事务.md)）

### 5.3 用户体验补偿

- 推送通知"由于系统繁忙，本次抽奖未成功，可参与下一轮"
- 给受影响用户发补偿券
- 公告 + 道歉，避免投诉爆炸

## 六、监控告警（提前发现）

秒杀活动前必须配齐：

| 指标 | 告警阈值 | 触发动作 |
| --- | --- | --- |
| Redis QPS | > 设计容量 80% | 限流加严 |
| Redis 命令耗时 P99 | > 50ms | 排查慢命令 |
| 连接池占用率 | > 80% | 扩容 / 排查泄漏 |
| 集群节点存活 | 任一 master 挂 | 立即告警 |
| 主从复制延迟 | > 1 秒 | 排查网络/写入压力 |
| Big key 检测 | 出现新 big key | 自动拆分 |
| 客户端 Redis 错误率 | > 0.1% | 准备降级 |

**关键**：要有**降级预演**。大促前一周做一次"模拟 Redis 挂"演练，验证降级开关、本地缓存、MQ 流转全链路。没演练的预案 = 没预案。

## 七、典型面试追问

### Q1：本地缓存有数据不一致问题，怎么办？

接受。秒杀场景下 1-3 秒的"看到旧库存"远比 Redis 挂可接受。**本地缓存只用于粗粒度判断**（活动是否在售、商品是否完全卖光），最终扣减一定走 Redis Lua（如果 Redis 挂了，那走降级，不走本地缓存扣减）。

### Q2：为什么不让 Redis 挂了直接打 DB？

DB 写入 TPS 顶天 1-2 万（带索引、带事务），秒杀流量轻则 10 万、重则百万。直接打 DB → 立刻挂，整个商城瘫痪。**降级的核心是保大盘，不是保活动**。

### Q3：怎么判断 Redis 真的挂了，而不是网络抖动？

- **客户端**：滑动窗口统计错误率，连续 N 秒错误率 > 阈值才算"挂"
- **服务端**：监控系统多个探针（不同 AZ）同时报警才确认
- **避免误降级**：单点抖动不要全局降级，用熔断器隔离

### Q4：降级开关怎么做到"秒级生效"？

- **配置中心**：Nacos/Apollo，本地长轮询 + 监听，变更秒级推送
- **预埋开关**：代码里写好 `if (switch.isOn())` 判断，运维一键拉开关
- **多级开关**：分商品、分活动、分用户白名单，避免一刀切

### Q5：Redis Cluster 主从切换期间怎么处理？

主从切换通常 5-15 秒（哨兵）或 10-30 秒（Cluster 选主）。这期间：
- 客户端会收到 `MOVED` / `CLUSTERDOWN` 错误
- **超时配置必须短**（100ms），快速失败
- **熔断 + 限流 + 兜底文案**度过这段窗口

### Q6：怎么预防热点商品把单分片打挂？

- **多副本 key**：同一商品库存 N 个副本（key_0, key_1, ..., key_(N-1)），请求随机选一个，扣减 N 个副本中的一个，**总库存按比例分配**
- **本地缓存**：超热点直接走客户端本地内存计数
- **代理层热点检测**：自动迁移热 key 到独立分片
- **客户端聚合**：批量请求合并，减少 Redis 调用

### Q7：秒杀完成后怎么把 Redis 数据清理掉？

- 设置 TTL（活动结束后 1-2 小时自动过期）
- 不要主动 DEL big key（会阻塞），用 `UNLINK` 异步删除
- 库存对账完成后，标记活动已结束，所有相关 key 批量 unlink

### Q8：异步刷盘的 Redis 数据丢了怎么办？

秒杀场景**不依赖 Redis 持久化**——Redis 挂了就走降级，不指望它能从 RDB 恢复。**真正的真实数据在 DB**，Redis 只是缓存层。所以 RDB/AOF 配置成"性能优先"即可（如 RDB 5 分钟一次或纯 AOF everysec）。

## 八、生产真实踩坑

### Case 1：双 11 大促 Redis Cluster 单分片挂，扩散全集群

某商品库存 key 是热 key（QPS 50 万），单分片 CPU 100% → 心跳超时 → 集群判定该 master 下线 → 触发故障转移 → 该 slot 期间不可用 5 秒 → 客户端疯狂重试 → 把其他分片也打挂。

**修复**：
- 热 key 拆 100 个副本
- 客户端命令超时 50ms（之前是 1 秒），快速失败
- 集群配置 `cluster-node-timeout` 调小到 5 秒，快速选主

### Case 2：本地缓存写错变成"穿透加速器"

预扣库存 Lua 写在 Redis，本地缓存的是"商品基础信息"，但代码写错把"库存数量"也缓存了——本地显示有库存，请求走到 Redis Lua 发现没库存返回失败，但本地缓存还显示有库存，**用户疯狂重试**导致流量翻倍。

**修复**：本地缓存严禁缓存"扣减类数据"，只缓存只读配置。

### Case 3：降级开关推了，但 SDK 没监听

降级配置推到 Nacos，部分应用 SDK 版本太老，配置没生效。运维以为已降级，实际还在打 Redis。后续故障雪崩。

**修复**：所有应用强制接入统一配置 SDK 版本；大促前演练验证。

### Case 4：MQ 堆积导致补偿失败

降级期间预扣 Redis 库存的请求继续发 MQ，但消费者也被风暴影响处理慢，MQ 堆积百万消息。Redis 恢复后流量爆发，MQ 雪崩。

**修复**：消费者扩容 + 限速消费 + 死信队列兜底；降级时关闭"预扣 Redis 后发 MQ"链路。

## 九、答题模板（60 秒话术）

> 秒杀的 Redis 故障应对按**预防 → 降级 → 恢复**三层。先反问场景——单分片挂还是整个集群挂，分类思维很重要。
>
> **预防**：Cluster 跨机房部署 + 热 key 多副本拆分 + 大 key 治理 + 慢日志告警 + 大促前压测。
>
> **降级**：本地缓存粗粒度兜底（Caffeine 存类目级数据，**丢精度保可用**）+ 降级开关静态化页面 + 限流熔断三件套（Sentinel / Hystrix）+ **严禁打 DB**（DB 只有 Redis 5% 的 QPS 能力）。
>
> **恢复**：Redis 恢复后从 DB 反查重建缓存 + 对账校验数据准确性 + MQ 幂等消费补偿期间丢的事件。
>
> 监控告警围绕 QPS、内存使用率、慢日志、连接数、复制延迟，关键指标提前 5 分钟告警。
>
> **大促前必须演练**降级流程——没演练过的方案在故障时基本不可用。
