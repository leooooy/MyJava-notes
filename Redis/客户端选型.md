# Java Redis 客户端选型

> 中频面试题，但**实战必考**：你项目里用的是 Jedis 还是 Lettuce？为什么？
> 答得好的关键是讲清三家（Jedis / Lettuce / Redisson）的**架构差异和适用场景**，不是只罗列特性。

---

## 一、三大客户端速览

| 客户端 | 定位 | IO 模型 | 主导地位 |
| --- | --- | --- | --- |
| **Jedis** | 经典同步客户端 | BIO + 连接池 | 老项目大量使用，新项目逐渐被取代 |
| **Lettuce** | 异步 NIO 客户端 | Netty + 单连接多路复用 | **Spring Boot 2.x 默认**，新项目首选 |
| **Redisson** | 分布式工具集 + 客户端 | 基于 Lettuce | 需要分布式锁/对象/集合时首选 |

> Spring Boot 自动配置在 2.0 之前默认用 Jedis，**2.0+ 默认 Lettuce**。这是一个里程碑式的切换。

---

## 二、Jedis（老牌经典）

### 2.1 架构

```
[Application Thread 1] ──→ [Jedis Connection 1] ──→ [Redis]
[Application Thread 2] ──→ [Jedis Connection 2] ──→ [Redis]
[Application Thread N] ──→ [Jedis Connection N] ──→ [Redis]
                              ↑
                    JedisPool 连接池管理
```

**核心特点**：
- **同步阻塞 IO**（BIO）
- **每个连接同时只能处理一个命令**
- 必须配连接池，否则并发场景会创建大量短连接
- API 直接对应 Redis 命令，简单直观

### 2.2 基础用法

```java
JedisPoolConfig config = new JedisPoolConfig();
config.setMaxTotal(50);
config.setMaxIdle(20);
config.setMinIdle(5);
JedisPool pool = new JedisPool(config, "localhost", 6379);

// 业务代码
try (Jedis jedis = pool.getResource()) {
    jedis.set("k", "v");
    String v = jedis.get("k");
}
```

### 2.3 连接池配置（高频面试点）

```java
JedisPoolConfig config = new JedisPoolConfig();
config.setMaxTotal(50);              // 最大连接数
config.setMaxIdle(20);               // 最大空闲连接
config.setMinIdle(5);                // 最小空闲连接（预热）
config.setMaxWaitMillis(2000);       // 获取连接最大等待 ms

// 健康检查（推荐打开）
config.setTestOnBorrow(false);       // 取连接时校验（影响性能，慎开）
config.setTestOnReturn(false);       // 还连接时校验
config.setTestWhileIdle(true);       // 空闲时校验（推荐）
config.setTimeBetweenEvictionRunsMillis(30000);   // 30s 跑一次空闲扫描
config.setMinEvictableIdleTimeMillis(60000);      // 60s 没用就回收
```

**容量规划**：`maxTotal = 业务峰值 QPS × 单命令耗时(s) × 安全系数`
例：QPS 5000，平均 5ms → 5000 × 0.005 × 1.5 = ~40 个连接。

### 2.4 优点

- API 直接简单，调试方便
- 文档生态最成熟
- 同步语义对程序员最友好

### 2.5 缺点

- **同步阻塞**：每个并发请求要独占一个连接
- **连接池压力**：高并发下连接耗尽 → 业务排队 / 超时
- **不支持响应式**：不适合 Spring WebFlux 等异步栈
- **Cluster 实现简陋**：早期版本路由 bug 多
- **资源占用大**：每个连接 1 个线程上下文

### 2.6 适用场景

- 老项目维护
- 对响应式编程没需求
- 同步业务（一般 Web 应用、定时任务）
- 团队对 Jedis 熟悉、不想引入新东西

## 三、Lettuce（现代异步首选）

### 3.1 架构

```
                        ┌─────────────────────────┐
                        │   Lettuce 单 TCP 连接    │
                        │  (Netty + 多路复用)     │
[Thread 1] ──┐          │                         │
[Thread 2] ──┼──→ async ┤  并发请求交错发送       ├──→ [Redis]
[Thread N] ──┘          │  按响应顺序匹配回调     │
                        └─────────────────────────┘
```

**核心特点**：
- **异步 NIO**（基于 Netty）
- **单连接多路复用**：所有线程共享一个连接，自动 pipelining
- **响应式 API**：支持 Reactive Streams（Mono/Flux）
- **Cluster / Sentinel / 主从原生支持**
- 默认线程安全

### 3.2 三种 API

```java
RedisClient client = RedisClient.create("redis://localhost:6379");
StatefulRedisConnection<String, String> connection = client.connect();

// 1. 同步 API（最像 Jedis，底层仍是异步）
RedisCommands<String, String> sync = connection.sync();
sync.set("k", "v");
String v = sync.get("k");

// 2. 异步 API
RedisAsyncCommands<String, String> async = connection.async();
RedisFuture<String> future = async.get("k");
future.thenAccept(value -> System.out.println(value));

// 3. 响应式 API（Spring WebFlux 用）
RedisReactiveCommands<String, String> reactive = connection.reactive();
reactive.get("k").subscribe(System.out::println);
```

### 3.3 单连接为什么够用

Redis 服务端是**单线程串行**，命令处理是 CPU bound，**单连接已经能跑出 10 万+ QPS**。
Lettuce 在客户端用异步队列把多个并发请求**交错发送**到这一个 TCP 连接，本质就是**自动 Pipeline**。

详见 [管道与批量优化](./管道与批量优化.md)。

### 3.4 还是要不要连接池？

**多数场景不需要**。Lettuce 单连接性能极好。
**需要的场景**：
- 用了**阻塞命令**（BLPOP、BRPOP、SUBSCRIBE）—— 单连接被独占就阻塞别人
- 用了**事务（MULTI/EXEC）** —— 事务期间这个连接被独占
- 单实例 QPS 极高（连接成为瓶颈，但很少见）

```java
// 需要时用 GenericObjectPool 包装
GenericObjectPoolConfig<StatefulRedisConnection<String, String>> poolConfig = ...;
GenericObjectPool<StatefulRedisConnection<String, String>> pool = 
    ConnectionPoolSupport.createGenericObjectPool(client::connect, poolConfig);
```

### 3.5 优点

- **性能强**：异步 NIO + 单连接多路复用
- **响应式原生**：完美适配 Spring WebFlux
- **Cluster / Sentinel 实现质量高**：自动重连、拓扑刷新
- **资源占用小**：单连接，无连接池开销
- **线程安全**

### 3.6 缺点

- **学习曲线**：异步 API、Reactive API 上手较慢
- **调试复杂**：异步堆栈难追
- **阻塞命令场景反而不方便**

### 3.7 适用场景

- **新项目首选**
- Spring Boot 2.0+ 默认
- 响应式应用（WebFlux）
- 高并发场景

## 四、Redisson（分布式工具集）

### 4.1 定位

Redisson **不是单纯的 Redis 客户端**，而是把 Redis 包装成**分布式 Java 对象**：

```java
// 像用本地对象一样用 Redis
RMap<String, Object> map = redisson.getMap("myMap");
RList<String> list = redisson.getList("myList");
RAtomicLong counter = redisson.getAtomicLong("counter");
RLock lock = redisson.getLock("myLock");
RBloomFilter<String> bloom = redisson.getBloomFilter("myBloom");
RSemaphore semaphore = redisson.getSemaphore("mySemaphore");
RDelayedQueue<String> delayQueue = ...;
RScheduledExecutorService scheduler = ...;
```

底层基于 **Lettuce** 通信（实际更早是 Netty 自实现，现已经统一）。

### 4.2 提供的核心能力

| 类型 | 用法 |
| --- | --- |
| **分布式锁** | RLock、RReadWriteLock、RFairLock、RMultiLock、RedLock |
| **分布式集合** | RMap、RSet、RList、RDeque、RBlockingQueue、RDelayedQueue |
| **原子对象** | RAtomicLong、RAtomicDouble、RBoolean |
| **限流器** | RRateLimiter（令牌桶） |
| **分布式工具** | RSemaphore、RCountDownLatch、RBucket、RBitSet |
| **服务** | RTopic（Pub/Sub）、RScheduledExecutorService、RRemoteService |
| **数据结构** | RBloomFilter、RHyperLogLog、RGeo |

### 4.3 杀手级应用：分布式锁

```java
RLock lock = redisson.getLock("order:1001");
lock.lock();         // 默认看门狗 30s 续期
try {
    // 业务逻辑
} finally {
    lock.unlock();
}
```

详见 [Redis 分布式锁](./分布式锁.md)。**99% 的 Java 项目用 Redisson 做分布式锁**——自己写 SETNX + Lua 都没它做得稳。

### 4.4 优点

- **开箱即用的分布式工具**：锁、限流、信号量、布隆过滤器全有
- **看门狗机制**：自动续期、防误删
- **质量高**：阿里巴巴、京东、腾讯都在用
- **响应式 API 支持**

### 4.5 缺点

- **重**：依赖多，jar 包大
- **抽象层多**：性能略损（vs 直接用 Lettuce）
- **学习成本**：API 多、配置项多
- **过度设计风险**：业务场景简单时可能用不到 90% 功能

### 4.6 适用场景

- **需要分布式锁**（最强需求）
- **需要分布式数据结构**（Map、Queue 等）
- **需要分布式限流**（RRateLimiter）
- **复杂场景**：分布式调度、远程服务调用

通常和 Lettuce / Spring Data Redis **共存**：业务读写用 Lettuce，分布式工具用 Redisson。

## 五、Spring Data Redis 整合

Spring 提供 `RedisTemplate` 抽象层，底层可对接 Jedis 或 Lettuce：

```yaml
# application.yml
spring:
  redis:
    host: localhost
    port: 6379
    password: ...
    timeout: 2000
    lettuce:                  # 默认就是 Lettuce
      pool:
        max-active: 8
        max-idle: 8
        min-idle: 0
        max-wait: 2000
    # 切换到 Jedis（需要在 pom 里加 jedis 依赖 + exclude lettuce-core）
```

```java
@Autowired
private RedisTemplate<String, Object> redisTemplate;

@Autowired
private StringRedisTemplate stringRedisTemplate;

redisTemplate.opsForValue().set("k", value);
redisTemplate.opsForHash().put("hash", "field", "value");
```

**Spring Boot 2.0+ 默认 Lettuce**——切到 Jedis 要显式加依赖。

## 六、性能对比（实测参考）

单线程同步：
- Jedis：~5 万 QPS（受限于网络 RTT）
- Lettuce 同步 API：~5 万 QPS（底层异步但 API 等同）

多线程同步：
- Jedis 连接池：~10 万 QPS（多连接并行）
- Lettuce 单连接：~15 万 QPS（自动 pipelining）

异步 / 响应式：
- Lettuce 异步：~30 万 QPS（充分多路复用）
- Redisson：~20 万 QPS（额外抽象层开销）

> 数据仅供参考，实际取决于命令复杂度、网络、value 大小。

## 七、选型决策树

```
项目用 Spring Boot 2.0+？
├─ 是 → 默认 Lettuce（不用改）
└─ 否
    │
    需要响应式编程（WebFlux）？
    ├─ 是 → Lettuce
    └─ 否
        │
        老项目维护，团队熟悉 Jedis？
        ├─ 是 → Jedis
        └─ 否 → Lettuce（新项目首选）

是否需要分布式锁 / 限流 / 复杂分布式工具？
├─ 是 → 加上 Redisson（和 Lettuce/Jedis 共存）
└─ 否 → 不需要
```

## 八、面试高频追问

### Q1：Jedis 和 Lettuce 选哪个？

**新项目用 Lettuce**：异步 NIO + 单连接多路复用，性能更好；Spring Boot 2.0+ 默认。
**老项目用 Jedis 不用换**：同步语义熟悉，连接池稳定。
**Redisson 是补充**：需要分布式锁就加上。

### Q2：Lettuce 单连接为什么够用？

Redis 服务端单线程，命令是 CPU bound，单连接 10 万+ QPS 已经接近极限。
Lettuce 用 Netty 异步队列，多个并发请求自动在同一连接上交错发送（自动 Pipeline）。
**例外**：阻塞命令、事务期间会独占连接，要用连接池。

### Q3：Jedis 必须用连接池吗？

**必须**。Jedis 单连接同步阻塞，每个请求独占一个连接，没有连接池就会：
- 创建大量短连接（连接成本高）
- 高并发下排队 / 超时
- 资源浪费

### Q4：JedisPool maxTotal 设多少？

公式：`maxTotal = 业务 QPS × 单命令耗时(s) × 安全系数(1.5~2)`
例：QPS 5000，平均耗时 5ms → 5000 × 0.005 × 1.5 = 37.5，设 40~50。
不能太大：连接本身有开销，过多反而降效率。

### Q5：Redisson 和 Lettuce 是替代关系吗？

**不是**。Redisson 是分布式工具集，底层基于 Lettuce 通信。
通常**共存**：
- 业务读写用 Lettuce / RedisTemplate
- 分布式锁、限流、布隆过滤器等用 Redisson

### Q6：客户端怎么应对 Redis 故障转移？

- **Jedis Sentinel**：JedisSentinelPool 自动从哨兵拿主库地址
- **Jedis Cluster**：JedisCluster 缓存 slot 表，收到 MOVED 自动更新
- **Lettuce**：拓扑刷新（topologyRefreshOptions）+ 自动重连
- **Redisson**：内置完善的 failover 处理

### Q7：客户端超时怎么配？

```yaml
spring.redis.timeout: 2000           # 命令超时
spring.redis.connect-timeout: 1000   # 连接建立超时
```
**生产经验**：
- 内网命令超时：100~500ms（追求快速失败）
- 大批量操作（Pipeline）单独配长一点的超时

### Q8：Redis 的 BLPOP 在 Lettuce 单连接下会怎样？

**坑点**：BLPOP 会独占连接 → 其他业务请求被阻塞。
**修复**：阻塞命令必须开独立连接（手动 `client.connect()` 一个新连接，或用连接池）。

### Q9：Lettuce 怎么处理 Cluster？

```java
RedisURI uri = RedisURI.builder()
    .withHost("node1").withPort(7001)
    .build();
RedisClusterClient cluster = RedisClusterClient.create(List.of(uri1, uri2, uri3));
StatefulRedisClusterConnection<String, String> conn = cluster.connect();
RedisAdvancedClusterCommands<String, String> sync = conn.sync();
```

特性：
- 自动维护 slot 表
- 周期性刷新拓扑（默认 60s）
- 故障转移自动跟新

### Q10：Pipeline 在三个客户端怎么写？

**Jedis**：
```java
Pipeline pipe = jedis.pipelined();
pipe.set(...); pipe.get(...);
List<Object> results = pipe.syncAndReturnAll();
```

**Lettuce**：
```java
async.setAutoFlushCommands(false);
List<RedisFuture<String>> futures = ...;
async.flushCommands();
```

**Redisson**：
```java
RBatch batch = redisson.createBatch();
batch.getMap("...").putAsync(...);
batch.execute();
```

### Q11：客户端连接 Redis 还可以怎么优化？

- **连接复用**：连接池 / 单连接多路复用
- **Pipeline / 批量命令**：减少 RTT
- **就近部署**：客户端和 Redis 同机房
- **TCP 优化**：keepalive、tcp-no-delay
- **序列化优化**：Protobuf > JSON > Java 原生
- **客户端缓存**（Tracking，6.0+）：本地缓存热点 key

### Q12：Spring Boot 2 切换到 Jedis 怎么做？

```xml
<!-- pom.xml -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
    <exclusions>
        <exclusion>
            <groupId>io.lettuce</groupId>
            <artifactId>lettuce-core</artifactId>
        </exclusion>
    </exclusions>
</dependency>
<dependency>
    <groupId>redis.clients</groupId>
    <artifactId>jedis</artifactId>
</dependency>
```

```yaml
spring:
  redis:
    jedis:
      pool:
        max-active: 50
```

## 九、生产真实踩坑

### Case 1：JedisPool 没设上限，连接爆炸

某老项目用 Jedis 没配 maxTotal（默认 8），高并发下大量请求阻塞等连接 → 业务超时。
**修复**：根据 QPS 公式估算 maxTotal，再加监控告警。

### Case 2：Lettuce 用 BLPOP 阻塞所有请求

业务用单 Lettuce 连接 + BLPOP 拉队列，期间其他业务请求全部排队。
**修复**：阻塞命令用独立连接 / 连接池。

### Case 3：Spring Boot 升级 2.0 后客户端默认变了

老业务依赖 JedisPool 的某个特性，升级后默认换成 Lettuce → 行为差异导致 bug。
**修复**：明确指定客户端依赖；升级前测试核心路径。

### Case 4：Redisson 用错锁类型

业务用普通 RLock + 长业务，没显式 leaseTime，**看门狗自动续期了**——以为锁会自动过期，实际锁一直被持有。
**修复**：理解看门狗触发条件（leaseTime 缺省才生效）。详见 [Redis 分布式锁 - 看门狗](./分布式锁.md#看门狗触发条件很多人答错的点)。

### Case 5：JedisCluster 老版本 MOVED 风暴

JedisCluster 2.x 版本在拓扑变化后没有正确刷新 slot 表 → 大量 MOVED 重定向 → QPS 暴跌。
**修复**：升级到 4.x+；或换 Lettuce。

### Case 6：Lettuce topology refresh 没开

Lettuce 默认不开自动拓扑刷新，故障转移后客户端持续打到旧主库。
**修复**：
```java
ClusterTopologyRefreshOptions topologyRefreshOptions = ClusterTopologyRefreshOptions.builder()
    .enablePeriodicRefresh(Duration.ofSeconds(30))
    .enableAllAdaptiveRefreshTriggers()
    .build();
```

### Case 7：连接超时设太长

业务把 timeout 设成 30s，故障时一个慢请求拖累线程池。
**修复**：内网 Redis 超时 500ms 内，配合熔断快速失败。

### Case 8：序列化选错性能爆

Spring Data Redis 默认 JdkSerializationRedisSerializer（Java 原生），序列化体积大、性能差。
**修复**：改用 Jackson/Protobuf：
```java
template.setValueSerializer(new GenericJackson2JsonRedisSerializer());
```

## 十、答题模板（60 秒话术）

> Java Redis 三大客户端：**Jedis**（同步老牌）、**Lettuce**（异步现代，**Spring Boot 2.0+ 默认**）、**Redisson**（分布式工具集，提供锁 / 限流 / 集合等高级功能）。
>
> **新项目用 Lettuce**：基于 Netty 的异步 NIO + 单连接多路复用 + 自动 pipelining，吞吐高、连接少。**老项目维持 Jedis**：同步语义熟悉、连接池稳定，迁移收益不大。**Redisson 是补充而非替代**——需要分布式锁、限流、布隆过滤器时和 Lettuce 共存于项目中。
>
> **Lettuce 单连接够用**因为多路复用，但**阻塞命令（BLPOP / BRPOP / SUBSCRIBE）必须用单独连接**——否则会堵住所有命令。
>
> 关键配置：连接池上限、命令超时、Cluster 拓扑刷新间隔、序列化方式（**不要用 JDK 原生序列化**，体积大且不跨语言——用 Jackson / Protobuf）。
>
> 生产经验：BLPOP 别共用连接、Redisson 看门狗触发条件（默认开启除非显式 leaseTime）、序列化可读性优先。
