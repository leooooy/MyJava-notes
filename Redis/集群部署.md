# Redis 集群部署

> 高频面试题，但很多人答着答着就把 **哨兵** 和 **Cluster** 混着讲。
> 回答的关键是把 **三种部署形态**讲清楚（主从 / 哨兵 / Cluster），每种解决了什么问题、还剩什么问题，引出下一种。

---

## 一、部署形态演进

| 形态 | 解决问题 | 遗留问题 |
| --- | --- | --- |
| **单机** | 简单 | 单点故障 + 容量受限 + 性能受限 |
| **主从复制** | 读扩展 + 数据冗余 | 主挂了**人工切主**，没解决高可用 |
| **哨兵（Sentinel）** | 主从 + **自动故障转移** | 容量仍受单机限制，写不能扩展 |
| **Cluster** | 主从 + 故障转移 + **分片** | 复杂度高，多 key 操作受限 |

→ 问题是层层叠加的，每代解决上一代的痛点。

---

## 二、形态 1：主从复制（基础）

### 2.1 拓扑

```
       ┌──────────┐
       │  Master  │ (写 + 读)
       └────┬─────┘
            │ 异步复制
   ┌────────┼────────┐
   ▼        ▼        ▼
┌──────┐ ┌──────┐ ┌──────┐
│Slave1│ │Slave2│ │Slave3│  (只读)
└──────┘ └──────┘ └──────┘
```

### 2.2 用途

- **读写分离**：写主，读从
- **数据冗余**：主挂可手动切从
- **数据备份**：在从库上做 BGSAVE，不影响主库

### 2.3 局限

- **主挂了要人工介入**：业务停顿
- **写性能受限**：单点 master 上限 ~10 万 QPS
- **容量受限**：单机内存 ~32GB 上限

→ 详见 [主从一致性](./主从一致性.md)。

## 三、形态 2：哨兵（Sentinel）

### 3.1 它解决什么

主从复制 + **自动故障转移**：监控、通知、自动选主。

### 3.2 拓扑

```
            ┌──────────┐  ┌──────────┐  ┌──────────┐
            │ Sentinel1│  │ Sentinel2│  │ Sentinel3│   (奇数个，建议 3)
            └─────┬────┘  └─────┬────┘  └─────┬────┘
                  └─────────────┼─────────────┘
                                │ 监控
                  ┌─────────────┼─────────────┐
                  ▼             ▼             ▼
              ┌────────┐    ┌────────┐    ┌────────┐
              │ Master │ ←─→│ Slave1 │ ←─→│ Slave2 │
              └────────┘    └────────┘    └────────┘
                                │ 复制
```

### 3.3 哨兵的核心职责

1. **监控**：定时 ping 主从，判断存活
2. **通知**：故障时通知运维和应用
3. **自动故障转移**：选新主、切换从库、更新配置
4. **配置中心**：客户端从哨兵拿到当前主库地址

### 3.4 主观下线 vs 客观下线（必考）

#### 主观下线（SDOWN）

单个哨兵 `down-after-milliseconds`（默认 30 秒）内 ping 不通主库 → 标记为 SDOWN。
**单个哨兵的判断不可信**，可能是网络抖动或哨兵自己有问题。

#### 客观下线（ODOWN）

某哨兵标记主库 SDOWN 后，**问其他哨兵**。
当 **超过 `quorum` 数量** 的哨兵都同意 → 升级为 ODOWN，**才会触发故障转移**。

**配置**：
```ini
sentinel monitor mymaster 192.168.1.10 6379 2    # quorum = 2
sentinel down-after-milliseconds mymaster 30000
sentinel failover-timeout mymaster 180000
```

### 3.5 故障转移流程

```
1. 哨兵 A 发现 master 主观下线（SDOWN）
2. 哨兵 A 询问其他哨兵 → 收集到 ≥ quorum 票 → 标记客观下线（ODOWN）
3. 哨兵之间用 Raft 算法选出"领头哨兵"（leader sentinel）
4. 领头哨兵从所有从库中选新主：
   a. 排除已下线的、连接断的、最近 5×心跳没响应的
   b. 按 slave-priority 优先（值越小优先级越高，0 = 永不被选）
   c. priority 相同看复制偏移量（offset 越大越新）
   d. 还相同选 runid 最小的
5. 把新主从"slave"模式切换到"master"模式（SLAVEOF NO ONE）
6. 让其他从库重新挂到新主：SLAVEOF newMaster
7. 让旧主（如果回来）变成新主的从库
8. 通知所有客户端新主地址
```

整个流程 **几十秒到几分钟**，期间业务不可写。

### 3.6 客户端怎么找主库

哨兵不是代理，**不参与数据流**。

```java
JedisSentinelPool pool = new JedisSentinelPool(
    "mymaster",                                 // master 名称
    Set.of("sentinel1:26379", "sentinel2:26379", "sentinel3:26379"),
    config
);
Jedis jedis = pool.getResource();    // 自动从哨兵获取当前主库地址
```

客户端启动时连接哨兵问"当前 mymaster 是谁"，得到主库地址后**直连主库**。
故障转移后，哨兵会推送新主地址给客户端（订阅 `__sentinel__:hello` 频道），客户端切换连接。

### 3.7 哨兵自身高可用

**至少 3 个哨兵 + 跨机器部署**：
- 1 个会单点
- 2 个无法仲裁（需要奇数）
- 3 个最经济（quorum=2 容忍 1 个挂）

哨兵不需要复杂集群，本身用 gossip 协议互相发现。

### 3.8 哨兵的局限

1. **故障转移时间长**：几十秒 ~ 分钟级业务不可写
2. **写性能仍是单点**：一主多从，写都打 master
3. **容量仍受单机限制**：一个 master 内存有限
4. **脑裂问题**：见后文

→ **要解决写扩展和容量** → 用 Cluster。

## 四、形态 3：Redis Cluster（分片集群）

### 4.1 它解决什么

哨兵 + **数据分片**：写性能和容量也水平扩展。

### 4.2 拓扑

```
          ┌─ Master A ──→ Slave A1 ──→ Slave A2
          │  (slot 0~5460)
          │
Cluster ──┼─ Master B ──→ Slave B1 ──→ Slave B2
          │  (slot 5461~10922)
          │
          └─ Master C ──→ Slave C1 ──→ Slave C2
             (slot 10923~16383)
```

每个分片（shard）= 1 个 master + N 个 slave。
master 之间各自负责一段 slot，**不重复**。
slot 总数固定 **16384** 个。

### 4.3 哈希槽（Slot）

```
key → CRC16(key) % 16384 → slot 编号 → 路由到对应 master
```

例：
- `set my_name Leo` → CRC16("my_name") % 16384 = 2412 → 在 Master A
- `set order:1001 v` → CRC16(...) % 16384 = 7300 → 在 Master B

**为什么 16384 而不是 65536**？
- 心跳消息要带 slot 位图，16384 bit = 2KB；65536 bit = 8KB，节省 75% 网络流量
- Redis 集群一般不会超过 1000 个节点，16384 个 slot 足够分配

### 4.4 客户端路由（智能客户端）

#### MOVED 重定向

客户端请求 `GET key` 到节点 A，A 算出 key 应该在 B：
```
A → 客户端: MOVED 2412 192.168.1.20:6379
客户端 → 重新发到 B
```

**Smart Client**（如 JedisCluster）会**缓存 slot 表**，下次直连正确节点，避免每次重定向。

#### ASK 重定向

slot 迁移过程中，客户端去 A 查不到，A 返回：
```
A → 客户端: ASK 2412 192.168.1.20:6379
客户端 → 先发 ASKING 命令到 B，再发 GET
```

ASK 是**临时**重定向，客户端**不更新 slot 表**（因为迁移完成后 slot 才正式归属 B）。

→ MOVED 是"slot 已经在 B"，ASK 是"slot 正在迁移到 B"。

### 4.5 Gossip 协议（必考）

集群节点之间靠 Gossip 协议交换信息，**没有中心化的 master**。

**消息类型**：
- `PING`：节点定期 ping 其他节点（含自己看到的整个集群状态）
- `PONG`：响应
- `MEET`：邀请新节点加入
- `FAIL`：广播某节点已客观下线

**特点**：
- 异步、最终一致
- 每个节点不需要知道全部状态，只跟邻居交换
- 集群越大，状态传播越慢（百节点级别仍然秒级）

**集群信息字段**：
- `cluster nodes`：所有节点列表
- `cluster slots`：slot 分布
- 每个节点有 `runid`、`flags`（master/slave/fail）、`epoch`（版本号）

### 4.6 故障转移

```
1. 节点 A 多次 ping master B 失败，标记 PFAIL（疑似下线）
2. A 通过 Gossip 把这个判断告诉其他节点
3. 当超过半数 master（包括自己）都标记 PFAIL → 升级为 FAIL（客观下线）
4. B 的 slave（B1, B2）发现自己的 master FAIL → 准备选举
5. slave 用 Raft-like 算法投票（其他 master 投票）
6. 胜出的 slave 升级为新 master，接管 B 的 slot
7. 集群广播新拓扑
```

整个过程 **15-30 秒**（取决于 `cluster-node-timeout`）。

### 4.7 多 key 操作的限制

```
MGET key1 key2 key3
↓
key1 在 A, key2 在 B, key3 在 C
↓
报错（不能跨 slot）
```

**解决方案：哈希标签（Hash Tag）**

```
SET {user:1001}:name "Tom"
SET {user:1001}:age  20
SET {user:1001}:vip  true
```

`{...}` 内的部分参与 CRC16 计算，三个 key 都映射到同一 slot。
**代价**：失去分片均衡（同一用户的所有数据集中在一个分片，可能成为热点）。

**适用**：
- 多 key 事务
- Lua 脚本访问多 key
- MGET/MSET 批量

### 4.8 Cluster 一致性保证

**和单机一样不强一致**：
- 主从异步复制（master 写完立刻返回，没等 slave）
- 网络分区时少数派可能短暂可写，分区恢复时数据被覆盖

**配置写一致性**：
```ini
min-slaves-to-write 1            # 至少 1 个 slave 可用才允许写
min-slaves-max-lag 10            # 复制延迟不超过 10 秒
```

→ 不是真"强一致"，只是"分区时拒写"，避免脑裂数据冲突。

## 五、哈希槽 vs 一致性哈希

经常被对比，主要区别：

| 维度 | 一致性哈希 | 哈希槽 |
| --- | --- | --- |
| 思路 | 圆环 + 虚拟节点 | 固定 16384 个槽，节点认领 |
| 节点增删 | 影响相邻节点的数据 | 手动迁移指定 slot |
| 数据分布 | 自动（虚拟节点平均） | 手动可控 |
| 扩缩容 | 自动重分布 | 显式 slot 迁移 |
| 实现 | Memcached、Cassandra | Redis Cluster |

**为什么 Redis 选哈希槽**：
- **可控性**：硬件不均衡时可以把多 slot 分给强机器
- **简单**：CRC16 % 16384 直接计算，不需要维护虚拟节点
- **运维友好**：扩缩容明确，能监控每个 slot 的位置

→ 详见 [一致性哈希](../Distributed/一致性哈希.md)。

## 六、扩容缩容流程

### 6.1 扩容（加节点）

```
1. cluster meet 192.168.1.40 6379    # 新节点加入集群
2. cluster addslots 0 1 ... 1000     # 给新节点分配 slot
   或用 redis-cli --cluster reshard
3. 启动 slot 迁移：
   - 源节点：cluster setslot N migrating <new>
   - 目标节点：cluster setslot N importing <old>
   - 循环: cluster getkeysinslot N → migrate key
   - 完成后：cluster setslot N node <new>
4. 集群广播新拓扑
```

迁移期间 ASK 重定向工作。

### 6.2 缩容（去节点）

```
1. 把目标节点的 slot 迁移到其他节点
2. cluster forget <target-id>        # 集群忘记这个节点
3. 关闭目标节点
```

**注意**：先迁移 slave 再迁移 master。

### 6.3 工具

```bash
redis-cli --cluster create 1.1.1.1:7000 2.2.2.2:7000 ...     # 创建
redis-cli --cluster add-node 4.4.4.4:7000 1.1.1.1:7000       # 加节点
redis-cli --cluster reshard 1.1.1.1:7000                     # 重分片
redis-cli --cluster del-node 1.1.1.1:7000 <node-id>          # 删节点
redis-cli --cluster check 1.1.1.1:7000                       # 检查
redis-cli --cluster fix 1.1.1.1:7000                         # 修复
```

## 七、脑裂问题

### 7.1 现象

网络分区导致集群被切成两部分，**两边都认为自己是主**：

```
分区前：[Master, Slave1, Slave2] + 客户端连 Master

发生分区：
  分区 A：[Master]                ← 客户端 X 还在写
  分区 B：[Slave1, Slave2]         ← 哨兵选出新主 NewMaster
                                  ← 客户端 Y 写 NewMaster

分区恢复：
  Master 变 slave，同步 NewMaster
  → 客户端 X 在分区期间写的数据被覆盖丢失！
```

### 7.2 解决方案

**Redis 配置**：
```ini
min-slaves-to-write 1            # 主必须有 ≥ 1 个 slave 才允许写
min-slaves-max-lag 10            # slave 复制延迟不超过 10 秒
```

→ 主和所有 slave 失联后，主变只读，避免脑裂数据冲突。
**代价**：可用性降低（极端情况下主拒绝写入）。

**Cluster 配置**：
```ini
cluster-require-full-coverage no    # slot 部分丢失时，其他 slot 仍可服务
```

→ 避免一个分片故障导致整集群拒绝服务。

## 八、跨机房 / 多活方案

### 8.1 同城双活

```
机房 A：[Cluster A]  ←──同步──→  [Cluster B]：机房 B
   ↑                                  ↑
   客户端                              客户端
```

业务双写或同步工具（如 RedisShake、阿里云 Tair）。

**问题**：
- 数据冲突：两边都写同一 key 怎么办（需要业务避免）
- 同步延迟：不是强一致

### 8.2 异地多活

主备机房：
- **主机房**：所有业务读写
- **备机房**：只读 + 同步主机房数据
- 主机房挂了 → 切换流量到备机房

更复杂的：单元化部署，按用户分片到不同机房，每个机房自治。

## 九、面试高频追问

### Q1：哨兵和 Cluster 的区别？

| 维度 | 哨兵 | Cluster |
| --- | --- | --- |
| 数据分布 | 全量复制 | 分片（16384 slot） |
| 写扩展 | 不能（单 master） | 可以（多 master） |
| 容量上限 | 单机内存 | 几乎无限（加节点） |
| 复杂度 | 中 | 高 |
| 多 key 操作 | 全部支持 | 受限（同 slot） |
| 故障转移 | 哨兵选主 | 集群投票选主 |
| 适合规模 | < 100GB 数据 | > 100GB 或需写扩展 |

### Q2：哨兵的 quorum 怎么设置？

`quorum = N/2 + 1`（多数派）。
3 个哨兵 → quorum = 2。
5 个哨兵 → quorum = 3。

**作用**：避免单哨兵误判触发故障转移。

### Q3：Cluster 为什么是 16384 个 slot？

两个原因：
1. **网络流量**：心跳消息要带 slot 位图，16384 bit = 2KB，65536 bit = 8KB。Redis 集群每秒大量心跳，节省 75% 流量很关键
2. **节点上限**：Redis Cluster 推荐节点数 < 1000，16384 个 slot 足够分配（每节点至少 16 个 slot）

### Q4：Cluster 的 master 之间是怎么通信的？

**Gossip 协议**。每个节点定期 ping 其他节点，PING/PONG 消息携带：
- 自己看到的所有节点状态
- slot 归属
- epoch 版本号

异步、最终一致。集群越大，状态传播越慢，但通常秒级即可。

### Q5：Cluster 怎么处理多 key 操作？

跨 slot 的多 key 操作 **直接报错**。
解决：
- **Hash Tag**：`{tag}:key1` 和 `{tag}:key2` 落到同一 slot
- 业务拆分：分别请求不同分片
- Lua 脚本：要求所有 key 同 slot

### Q6：MOVED 和 ASK 的区别？

| 类型 | 含义 | 客户端行为 |
| --- | --- | --- |
| MOVED | slot 已经永久归属新节点 | 更新 slot 缓存 + 重发 |
| ASK | slot 正在迁移中 | 不更新缓存，先发 ASKING + 重发 |

迁移完成后 MOVED 取代 ASK。

### Q7：Cluster 故障转移时业务影响多大？

通常 **15-30 秒**：
- `cluster-node-timeout`（默认 15 秒）：判 PFAIL 的时间
- 选举投票：几秒
- slave 升主 + 通知客户端：几秒

期间该分片不可用，**其他分片仍正常**。

### Q8：脑裂怎么解决？

`min-slaves-to-write 1` + `min-slaves-max-lag 10`：主与至少 1 个从保持同步，否则拒写。
**代价**：网络分区时主变只读，业务可能受影响。
**取舍**：可用性 vs 一致性，要看业务能接受哪一种。

### Q9：哨兵会和 Cluster 一起用吗？

**不会**。两者是不同的高可用方案，互斥。
Cluster 自己有故障转移机制（不需要哨兵）。

### Q10：Cluster 节点上限是多少？

官方推荐 **< 1000 节点**。
更大的集群：
- Gossip 消息开销暴涨
- 故障传播变慢
- 状态收敛时间变长

实际企业里很少超过 100 个 master 节点。

### Q11：Cluster 怎么扩容？

详见第六节。核心：
- 新节点加入 → 分配 slot → slot 迁移
- 迁移期间 ASK 重定向工作
- 不停机扩容

### Q12：单 slot 数据量太大怎么办？

slot 不可拆分，只能：
- **业务侧拆分**：把一个大 key 拆成多个 key（散到多 slot）
- 拆分粒度更细的业务键名

> Hash Tag 用太多反而集中数据到一个 slot，要警惕。

### Q13：Cluster 模式下能用 keys *、scan 吗？

- `KEYS *`：单节点扫，**不会**跨节点。要扫全集群得遍历每个 master 都执行一遍
- `SCAN`：同上，需要客户端遍历所有 master
- `redis-cli --cluster call <node> KEYS '*'` 帮你统一调用

→ 生产严禁用 `KEYS *`，参考 [工作流程 - 慢命令排查](./工作流程.md#六慢命令排查必备技能)。

### Q14：JedisCluster 是怎么工作的？

- 启动时连任一节点，发 `cluster slots` 拿到 slot → 节点映射
- 缓存到客户端本地
- 每次请求按 key 算 slot，直连对应节点
- 收到 MOVED 时更新缓存
- 收到 ASK 时临时跳转

→ "Smart Client"模型，Redis 自身 Cluster 不带 proxy。

### Q15：Codis、Twemproxy 这种代理还有人用吗？

**Codis**（豌豆荚开源）：proxy 层做分片，业务无感，但运维多一层。
**Twemproxy**（Twitter）：早期方案，不支持自动扩缩容。

**现在主流是 Cluster**：原生分片，无需代理，性能更好。
旧系统迁移成本高的还在用 Codis。

## 十、生产真实踩坑

### Case 1：哨兵 quorum 配置错误

3 个哨兵配置 `quorum 1`，单个哨兵就能触发故障转移 → 网络抖动时频繁切主，业务持续抖动。
**修复**：`quorum 2`（多数派）。

### Case 2：Cluster 一个分片热点拖垮整集群

某商品 key 落在分片 B，QPS 50 万 → B 的 master CPU 100% → 心跳超时 → 集群标记 B 下线 → 触发故障转移 → 分片 B 不可用 5 秒 → 客户端疯狂重试 → 其他分片也被打挂。
**修复**：
- 热 key 拆分（多副本 key）
- 客户端命令超时调短（50ms 而不是 1 秒），快速失败
- 集群配置 `cluster-node-timeout 5000`

### Case 3：Hash Tag 滥用导致单分片爆炸

业务为了支持事务，所有 key 都加了 `{user:1001}` tag → 全部 key 落在同一 slot → 单分片内存满，其他分片空闲。
**修复**：只在真正需要事务的 key 上用 Hash Tag。

### Case 4：脑裂数据丢失

跨机房部署主从，机房断网 → 备机房选出新主 → 业务双写 → 网络恢复后旧主变 slave 同步新主 → 旧主上写的数据全部丢失。
**修复**：`min-slaves-to-write 1`；或用 Cluster 多分片避免单点。

### Case 5：迁移 slot 时业务断流

某次扩容 reshard，没用 `redis-cli --cluster reshard` 工具，手动 migrate 速度慢 + 客户端旧版本不支持 ASK → 大量请求失败。
**修复**：用官方工具；客户端升级到支持 ASK 的版本。

### Case 6：哨兵脑裂

3 个哨兵分别在 3 个机房，机房 A 与其他失联 → A 的哨兵自己选出"主" → 客户端连接错误的哨兵集群 → 数据错乱。
**修复**：哨兵跨多机房部署，但要部署 5 个+；或用 Cluster 替代。

### Case 7：节点数过多导致 Gossip 风暴

某业务 Cluster 节点扩到 200 个 → Gossip 消息 + 心跳 + 状态同步占用大量带宽 → 节点偶发心跳超时 → 假阳性故障转移频发。
**修复**：拆分成多个独立 Cluster（按业务垂直切分），单 Cluster 控制在 50-100 个节点。

### Case 8：cluster-require-full-coverage 默认值导致故障扩散

某个分片 master 和 slave 同时挂（主从都在同一物理机），集群默认 `cluster-require-full-coverage yes` → **整个集群拒绝服务**（即使其他分片正常）。
**修复**：设为 `no`，让其他分片继续工作；同时主从必须跨机器/机架部署。

### Case 9：客户端 slot 缓存过期

业务运行 24 小时后，运维做了 reshard，但客户端没收到通知（配置错） → 大量 MOVED 重定向 → QPS 下降 50%。
**修复**：升级 JedisCluster；或定时刷新 slot 缓存。

### Case 10：哨兵的 down-after-milliseconds 太短

设成 5 秒，频繁因 GC 或网络抖动误判主下线 → 一晚上切了 10 次主。
**修复**：调到 30 秒（默认）；排查 GC 和网络问题。

## 十一、答题模板（60 秒话术）

> Redis 集群形态**单机 → 主从 → 哨兵 → Cluster** 一路演进，每代解决上一代痛点：主从加读扩展和数据冗余但要人工切；哨兵加自动故障转移但容量仍是单机；Cluster 是分片 + 自治。
>
> **哨兵**关键概念：监控 + SDOWN（单节点主观下线）/ ODOWN（quorum 多数派客观下线）/ 选主流程；至少 **3 个哨兵**防脑裂。
>
> **Cluster**：**16384 slot** + CRC16 哈希、Gossip 协议传播拓扑、客户端用智能路由（缓存 slot 映射）；**MOVED 是 slot 已迁、ASK 是临时迁移中**。多 key 操作要 **Hash Tag**（`{tag}part1`、`{tag}part2`）让 key 落同 slot，但不能滥用避免热点。
>
> **脑裂**靠 `min-slaves-to-write` + `min-slaves-max-lag` 配合避免——本质是可用性 vs 一致性的取舍。
>
> 生产经验：超时合理配置、热 key 治理、跨机架部署、**不盲目堆大集群**（节点数多 Gossip 开销大）。
