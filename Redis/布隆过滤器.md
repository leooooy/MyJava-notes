# 布隆过滤器

> 一句话：用很小的内存判断"一个元素**一定不在**集合里"或"**可能在**集合里"。
> 经典场景：解决 [缓存穿透](./缓存雪崩，击穿，穿透.md)。

---

## 一、核心原理

### 数据结构

- 一个长度为 m 的 **位数组（bit array）**，初始全 0
- k 个 **不同的哈希函数**（如 MurmurHash、CityHash 取不同 seed）

### 写入元素 x

```
对 x 算 k 个哈希值 h1(x), h2(x), ..., hk(x)
分别对 m 取模得到 k 个下标
把这 k 个下标对应的位置 1
```

### 判断元素 x 是否存在

```
算同样的 k 个下标
全部都是 1 → 可能存在（也可能误判）
有任何一个是 0 → 一定不存在
```

### 关键特性

| 特性 | 说明 |
| --- | --- |
| **不会假阴性** | 说"不存在"就一定不存在 |
| **会假阳性** | 说"存在"可能其实不存在（多个元素哈希撞到同一组位） |
| **不能删除** | 删一个元素的位会误伤其他元素（变种 Counting Bloom 可删，用计数器替代位） |
| **空间极省** | 1 亿元素，1% 误判率，约 114 MB；放 Redis 里完全可接受 |

---

## 二、误判率与参数

### 公式

设：
- n = 预计放入的元素数量
- m = 位数组长度
- k = 哈希函数个数
- p = 误判率

最优哈希函数数：
```
k = (m / n) * ln(2)
```

误判率：
```
p ≈ (1 - e^(-kn/m))^k
```

### 实战常用对照表

| 元素数 n | 误判率 p | 位数组 m | 哈希函数 k |
| --- | --- | --- | --- |
| 1 万 | 1% | ~96 KB | 7 |
| 100 万 | 1% | ~1.14 MB | 7 |
| 1 亿 | 1% | ~114 MB | 7 |
| 1 亿 | 0.1% | ~171 MB | 10 |
| 1 亿 | 0.01% | ~228 MB | 13 |

> **生产经验**：误判率定 **1%~0.1%** 已经够用，再低空间翻倍但收益有限。

## 三、Redis 中的实现

### 方案 A：原生 setbit（小规模）

```bash
> SETBIT bf:user 12345 1
> GETBIT bf:user 12345
```

适合手撸 demo 或者超小规模。生产不推荐——哈希函数得自己写。

### 方案 B：RedisBloom 模块（推荐）

Redis 4.0+ 通过加载 RedisBloom 插件，原生支持：

```bash
# 创建：误判率 0.01，预期容量 1000000
> BF.RESERVE bf:user 0.01 1000000

# 添加
> BF.ADD bf:user 12345
> BF.MADD bf:user 12345 67890

# 判断
> BF.EXISTS bf:user 12345          # 1 = 可能存在
> BF.MEXISTS bf:user 12345 67890
```

### 方案 C：Redisson（Java 客户端，最常用）

```java
RBloomFilter<Long> bloomFilter = redisson.getBloomFilter("bf:user");
// 初始化：预期 100 万元素，误判率 0.01
bloomFilter.tryInit(1_000_000L, 0.01);

bloomFilter.add(12345L);
boolean maybeExists = bloomFilter.contains(12345L);
```

底层就是 Redis bitmap + 客户端做哈希。**初始化只能调一次**，容量定了改不了。

### 方案 D：Guava BloomFilter（单机内存版）

```java
BloomFilter<Long> bf = BloomFilter.create(
    Funnels.longFunnel(),
    1_000_000L,    // 期望元素
    0.01           // 误判率
);
bf.put(123L);
bf.mightContain(123L);
```

只在 JVM 内存里，多实例不共享。秒杀单机限流之类用得到。

## 四、典型应用场景

### 1. 防缓存穿透（最经典）

```
查询 → 布隆过滤器
        ├─ 不存在 → 直接返回 null（拦截攻击）
        └─ 可能存在 → 查 Redis → 查 DB
```

启动时把所有合法 ID 灌入布隆过滤器。

### 2. 防爬虫 / 黑名单

记录已访问过的 URL、已发送过的短信号码、已下过单的用户，避免重复处理。

### 3. 大规模去重

爬虫去重 URL、消息去重（如推送系统避免给同一个人推两次）。

### 4. 推荐系统过滤

用户已读过的内容不再推荐，记录"已读 ID 集合"用布隆过滤器。

### 5. 数据库加速

LevelDB / RocksDB / HBase 内部都用布隆过滤器判断"key 是否在某个 SST 文件里"，避免无效磁盘 IO。

## 五、常见追问

### Q1：误判率 1% 在缓存穿透场景能接受吗？

可以。即使 1% 的请求被误判为"可能存在"穿透到 DB，也比 100% 全部穿透到 DB 强百倍。
而且 DB 查不到的会再走"空值缓存"机制兜底。

### Q2：能删除元素吗？

普通布隆过滤器**不能删**——同一位可能被多个元素都置 1，删一个会误伤别人。

变种：
- **Counting Bloom Filter**：每位用 4 bit 计数器，加减替代置位，可删但空间多 4 倍。
- **Cuckoo Filter**：基于布谷鸟哈希，支持删除，空间效率更高，但实现复杂。

> 实际工程中，"不能删"的影响通常通过**定期重建**解决（每天/每周重建一次）。

### Q3：扩容怎么办？

布隆过滤器创建时容量已定，超过后误判率会飙升。

方案：
- **重建**：用更大容量重新创建，灌入数据
- **多层布隆过滤器**：满了就新建一层，查询时所有层都查
- **可扩展布隆过滤器（SBF）**：每层容量翻倍，自动加层（RedisBloom 支持）

### Q4：哈希函数怎么选？

要求：**速度快 + 分布均匀 + 互相独立**。
常用：MurmurHash3、CityHash、FNV，**不要用** MD5/SHA（慢且没必要加密强度）。
通常用一个哈希函数 + 两个 seed 模拟出 k 个独立哈希（双重哈希技巧）。

### Q5：为什么不用 Redis 的 Set？

Set 存原值，1 亿个 Long 大概要 8 GB；布隆过滤器只要 100 多 MB，差两个数量级。

### Q6：Redisson 布隆过滤器和 RedisBloom 的区别？

| 维度 | Redisson | RedisBloom |
| --- | --- | --- |
| 部署 | 不需要 Redis 装插件，纯客户端 | Redis 必须加载 RedisBloom 模块 |
| 性能 | 客户端做哈希后多次访问 Redis | 服务端原生支持，单次命令 |
| 网络开销 | k 次 GETBIT/SETBIT | 1 次 BF.* 命令 |
| 推荐度 | 一般场景够用 | 高并发场景更优 |

### Q7：高并发下布隆过滤器会成为瓶颈吗？

会。布隆过滤器本身是 Redis 单 key，是热点。
缓解：
- 客户端本地缓存（Caffeine + 短 TTL）
- 多实例分片：按业务 ID hash 到不同的布隆过滤器 key
- 应用启动时把布隆过滤器全量加载到本地内存（小型场景）

## 六、踩过的坑

1. **初始化容量估错**：上线时按"预计 100 万用户"建，半年后涨到 5000 万，误判率从 1% 飙到 30%。教训：估容量时按 3-5 倍预留。
2. **没考虑数据更新**：用户注销了但布隆过滤器删不掉，永远显示"可能存在"。改成定期重建（凌晨低峰期）。
3. **大 key 问题**：100 MB 的布隆过滤器是 Redis 大 key，故障时 migrate 慢。拆成多个分片解决。
4. **应用重启慢**：用 Redisson 时启动需要拉取布隆过滤器结构，1 亿元素的拉了 30 秒。改成本地预热缓存 + 异步加载。
5. **错把布隆过滤器当真理**：DB 还要校验，不能因为布隆过滤器说"在"就直接给用户。

## 七、答题模板（60 秒话术）

> 布隆过滤器是空间 O(M)、查询 O(K) 的**概率数据结构**——bit 数组 + K 个独立哈希函数。判断"**一定不存在**"或"**可能存在**"，**不能删除**（删一个会误伤其它 key 共用的 bit）。
>
> 误判率公式 `(1 - e^(-kn/m))^k`，工程上 1 亿元素 1% 误判率约需 120 MB——比 Redis Set 存原值省两个数量级。
>
> 最经典应用是**防缓存穿透**：DB 中所有 key 灌入布隆，查询前先问布隆"可能存在吗"，过滤掉一定不存在的请求。
>
> 实现选择：**Redisson 客户端实现**（不依赖 Redis 模块，通用性好，但客户端做哈希要多次 GETBIT/SETBIT）vs **RedisBloom 模块**（服务端原生 BF.ADD / BF.EXISTS 命令，单次往返，性能更好）。
>
> 生产坑：容量按 **3-5 倍预留**防误判率飙升、定期重建处理"删不掉"问题、布隆过滤器本身是大 key 要拆分、应用启动时预热。**布隆之后 DB 必须再校验**——它只是过滤，不是真理。
