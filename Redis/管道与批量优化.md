# 管道与批量优化

> 性能优化高频题。回答关键不是讲"Pipeline 怎么用"，而是讲清楚 **为什么 Redis 这么快还需要 Pipeline**——RTT 才是瓶颈。
> 然后能讲清 Pipeline / Multi-key 命令 / Multi/Exec / Lua 四种"批量"方式的取舍，就是 senior。

---

## 一、为什么需要管道

### 1.1 单命令的瓶颈：网络往返时间（RTT）

Redis 处理一条命令的时间 = **网络 RTT + 命令执行时间**

```
客户端 ──[请求]──→ Redis  ── 0.1ms 处理 ──→ ──[响应]──→ 客户端
        ↑──── 0.5~1ms RTT (同机房)─────────────↓
        ↑──── 5~50ms RTT (跨地域)──────────────↓
```

| 场景 | 命令处理 | RTT | 总耗时 |
| --- | --- | --- | --- |
| 同机房 | 0.1 ms | 0.5 ms | **0.6 ms / 命令** |
| 跨地域 | 0.1 ms | 30 ms | **30.1 ms / 命令** |

→ **网络 RTT 占了绝大部分**。Redis 处理快没用，每条命令都要等网络。

### 1.2 例子：写 1 万个 key

| 方式 | 耗时（同机房） |
| --- | --- |
| 1 万次 SET（一次一个） | 1 万 × 0.6ms = **6 秒** |
| Pipeline 打包 | ~50 ms |

差**两个数量级**。这就是为什么 Pipeline 是必须掌握的优化。

## 二、Pipeline 是什么

**核心思想**：客户端把多个命令**一次性发送**给 Redis，再**一次性接收**所有响应。

```
┌──── 普通模式 ────┐         ┌──── Pipeline ────┐
SET k1 v1                    SET k1 v1
  RTT ────→                  SET k2 v2
  ←──── OK                   SET k3 v3
SET k2 v2                    ...
  RTT ────→                  SET k1000 v1000
  ←──── OK                     RTT ────→
SET k3 v3                      ←──── [OK, OK, OK, ..., OK]
  RTT ────→                  
  ←──── OK                   合计 1 次 RTT
... 1000 次 RTT
```

### 2.1 工作机制

1. **客户端**：把命令累加到本地缓冲区，不立即发送
2. **批量发送**：累计到一定数量 / 调用 sync 时，一次性发到 Redis
3. **Redis**：依次处理（仍是单线程串行），把响应缓存到 socket 输出缓冲区
4. **批量接收**：客户端一次性读取所有响应，按顺序匹配

### 2.2 Java 示例（Jedis）

```java
// 普通模式
for (int i = 0; i < 10000; i++) {
    jedis.set("key:" + i, "value:" + i);     // 每次都 RTT
}

// Pipeline 模式
Pipeline pipe = jedis.pipelined();
for (int i = 0; i < 10000; i++) {
    pipe.set("key:" + i, "value:" + i);      // 仅入缓冲，无 RTT
}
List<Object> results = pipe.syncAndReturnAll();   // 一次 RTT
```

### 2.3 Lettuce 异步示例

```java
RedisAsyncCommands<String, String> async = connection.async();
async.setAutoFlushCommands(false);              // 关闭自动 flush

List<RedisFuture<String>> futures = new ArrayList<>();
for (int i = 0; i < 10000; i++) {
    futures.add(async.set("key:" + i, "value:" + i));
}
async.flushCommands();                          // 一次性发送

LettuceFutures.awaitAll(5, TimeUnit.SECONDS, futures.toArray(new RedisFuture[0]));
```

## 三、四种"批量"方式对比（核心面试点）

| 方式 | 原子性 | 网络 RTT | 命令限制 | 典型用途 |
| --- | --- | --- | --- | --- |
| **多 key 命令** | ✓ | 1 次 | 仅特定命令 | MGET/MSET/HMGET |
| **Pipeline** | ✗ | 1 次 | 任意命令 | 大批量加速 |
| **MULTI/EXEC** | ✓（中间不被打断） | ~3 次（MULTI + 命令 + EXEC） | 任意命令 | 事务 + WATCH |
| **Lua 脚本** | ✓（最强） | 1 次 | 任意命令 + 逻辑 | 复杂原子操作 |

### 3.1 多 key 命令（MGET/MSET 等）

Redis 自带的批量命令：
```bash
MSET k1 v1 k2 v2 k3 v3       # 批量写
MGET k1 k2 k3                # 批量读
HMGET h f1 f2 f3             # 批量读字段
SADD set m1 m2 m3            # 批量加成员
```

**优点**：原子（单命令 = Redis 单线程一次执行）+ 1 次 RTT
**缺点**：仅特定命令支持，且不能混用不同操作

### 3.2 Pipeline

任意命令的批量：
```java
pipe.set(...);
pipe.incr(...);
pipe.zadd(...);
pipe.sync();
```

**优点**：任意命令 + 1 次 RTT
**缺点**：**不原子**——批量执行期间，其他客户端的命令可能插入

### 3.3 MULTI/EXEC

详见 [Redis 事务](./事务.md)。
打包 + 不被打断 + 不支持回滚。

### 3.4 Lua 脚本

详见 [Lua 脚本](./Lua%20脚本.md)。
最强原子性 + 能写逻辑 + 1 次 RTT。

## 四、Pipeline vs MULTI/EXEC（高频对比题）

很多人把这两个混着用，必须分清：

| 维度 | Pipeline | MULTI/EXEC |
| --- | --- | --- |
| **核心目的** | 减少 RTT（性能） | 命令打包 + 隔离（事务语义） |
| **原子性** | ✗ 中间其他客户端命令可能插入 | ✓ 整组命令一起执行不被打断 |
| **错误处理** | 每条命令独立，互不影响 | 入队错误整体拒绝；运行时错误不回滚 |
| **客户端缓冲** | 是 | 否（命令立即发到 Redis 服务端缓冲） |
| **服务端处理** | 收到后逐条执行 | MULTI 后命令入队，EXEC 时一起执行 |
| **能否组合** | 可以（Pipeline 里包 MULTI/EXEC） | 通常单独用 |

**关键澄清**：MULTI/EXEC 的"打包"是**服务端排队**，命令入队那一刻已经发到 Redis 了；Pipeline 的"打包"是**客户端缓冲**，整个批次一起发。

### 4.1 二者可以组合使用

```java
Pipeline pipe = jedis.pipelined();
pipe.multi();
pipe.set("k1", "v1");
pipe.incr("counter");
pipe.exec();
pipe.sync();    // ← 整体一次 RTT
```

这样既有事务语义又减少了 RTT。

## 五、Pipeline 的注意事项

### 5.1 单批次大小要控制

太大的 Pipeline 反而拖慢：
- 客户端缓冲区占用内存
- 服务端响应缓冲区占用内存
- 阻塞主线程的命令执行（10 万条命令至少 1 秒）

**实践**：单次 Pipeline 控制在 **100~1000 条**，超过分批。

```java
int batchSize = 500;
for (int batch = 0; batch < total; batch += batchSize) {
    Pipeline pipe = jedis.pipelined();
    for (int i = batch; i < Math.min(batch + batchSize, total); i++) {
        pipe.set("k:" + i, "v:" + i);
    }
    pipe.sync();
}
```

### 5.2 命令顺序敏感

Pipeline 不保证原子，但**响应是按命令顺序返回的**：
```java
List<Object> results = pipe.syncAndReturnAll();
// results[0] 对应第 1 条命令的响应
// results[1] 对应第 2 条
// ...
```

不要乱用 `sync()` 后从 future 中拿（不同客户端 SDK 行为有差异）。

### 5.3 Cluster 下的 Pipeline

Redis Cluster 不支持原生 Pipeline 跨节点。智能客户端（如 JedisCluster）会：
1. 按 slot 分组命令
2. 对每个节点开 Pipeline
3. 等所有节点返回再合并结果

**注意**：客户端 SDK 实现差异大，并不是所有都正确支持 Cluster Pipeline。

### 5.4 错误处理

Pipeline 里某条命令出错，**其他命令仍然执行**：
```java
pipe.set("k1", "v1");
pipe.incr("k1");        // 类型错误（字符串不能 INCR）
pipe.set("k2", "v2");
List<Object> results = pipe.syncAndReturnAll();
// results[0] = "OK"
// results[1] = JedisDataException
// results[2] = "OK"
```

业务必须遍历 results 检查每条的状态。

### 5.5 不要在 Pipeline 里读已发出命令的结果

```java
pipe.set("k1", "v1");
String r = pipe.get("k1").get();   // ✗ 此时还没 sync，无值
pipe.sync();
```

Pipeline 是 **fire and forget then collect** 模式，必须 sync 后才能拿结果。

## 六、什么时候不该用 Pipeline

| 场景 | 原因 |
| --- | --- |
| 单条命令 | 没意义 |
| 后续命令依赖前面结果 | 必须等响应才能决定下一步 |
| 实时性极高，要求每个响应立刻返回 | Pipeline 有延迟 |
| 命令很少（<10 条） | RTT 节省不明显 |
| 极大批次（百万级） | 内存压力大，应分批 |

依赖前面结果的场景应该用 **Lua 脚本**。

## 七、相关性能优化技巧

### 7.1 连接复用

每次建 TCP 连接 + Redis Auth 都有成本。**必须用连接池**（详见 [客户端选型](./客户端选型.md)）。

### 7.2 批量命令优先

能用 MGET 就别用 GET 循环：
```java
// ✗ 慢
for (String key : keys) {
    String v = jedis.get(key);
}

// ✓ 快（1 次 RTT）
List<String> values = jedis.mget(keys.toArray(new String[0]));
```

### 7.3 数据序列化优化

- 序列化用快速方案（Protobuf、Kryo、JSON 都比 Java 原生快）
- value 不要太大（1MB+ 算大，序列化 + 网络都是瓶颈）
- 大对象拆字段用 Hash 而不是 String + JSON

### 7.4 客户端异步化

Lettuce 是 NIO + 异步设计，单连接也能跑高 QPS（命令 pipelining 内置）。
Jedis 是同步 BIO，必须用连接池。

### 7.5 选对网络模式

- 同机房：用最短路径
- 跨机房：考虑用就近 Redis 实例（多副本）
- 长连接 + keepalive

## 八、面试高频追问

### Q1：Pipeline 是 Redis 服务端的特性吗？

**主要在客户端**。Redis 服务端只是"按收到的顺序处理命令，再把响应按顺序发回"——这是它的标准行为。
Pipeline 是**客户端缓冲 + 一次发送**的优化技巧，服务端不需要特殊支持。

### Q2：Pipeline 和 MULTI/EXEC 区别？

详见第四节对比表。一句话：
- **Pipeline 是性能优化**（减少 RTT，不保证原子）
- **MULTI/EXEC 是事务语义**（打包 + 不被打断，但不支持回滚）

### Q3：Pipeline 是原子的吗？

**不是**。Redis 单线程串行执行命令，但 Pipeline 里的命令之间，**其他客户端的命令可能插入**。
要原子用 MULTI/EXEC 或 Lua。

### Q4：Pipeline 一次能放多少命令？

理论无上限（看客户端和服务端缓冲）。**生产建议 100~1000 条**：
- 太少：RTT 节省不显著
- 太多：内存压力 + 服务端阻塞主线程

### Q5：Cluster 模式下 Pipeline 还能用吗？

能，但有坑：
- 命令必须按 key 分组到对应节点
- 智能客户端（JedisCluster、Lettuce）自动处理，但 SDK 实现质量参差
- 强烈推荐用 Hash Tag 把要批量操作的 key 集中到同一 slot

### Q6：Pipeline 是网络层 hack 吗？

不算 hack。是**Redis 协议（RESP）天然支持的**——RESP 是流式协议，多个命令可以拼接发送，多个响应也按顺序返回。Pipeline 只是利用了这个特性。

### Q7：MGET 和 Pipeline 哪个快？

| 方式 | RTT | 服务端处理 | 总耗时（1000 key） |
| --- | --- | --- | --- |
| MGET | 1 次 | 1 条命令多个 key | 最快 |
| Pipeline + GET | 1 次 | 1000 条命令 | 略慢（命令解析多） |

**MGET 略快**——少了 999 次命令解析。但能用 MGET 的场景少（仅同类型同操作）。

### Q8：Pipeline 中某条命令报错怎么办？

不会中断后续命令，每条命令的结果（成功值或异常）都在结果列表里。
**业务必须遍历检查**，否则错误会被吞掉。

### Q9：Lettuce 默认 Pipeline 吗？

**类似自动 Pipeline**。Lettuce 单连接是异步多路复用，多个并发请求自动在同一 TCP 连接上交错发送，效果接近 Pipeline。
Jedis 同步阻塞，必须显式开 Pipeline。

### Q10：跨地域延迟下 Pipeline 收益多大？

跨地域 RTT 30~50ms，1 万次单命令需要 5~8 分钟，Pipeline 可降到秒级——**收益数百倍**。
跨地域批量场景必须用 Pipeline。

### Q11：Pipeline 期间能做读写一致性吗？

不能。Pipeline 不是事务，期间数据可能被其他客户端改。
要原子读写一致：Lua 脚本或 MULTI/EXEC + WATCH。

### Q12：服务端怎么处理 Pipeline？

Redis 主线程从 socket 缓冲区**逐条**读取命令，依次执行，把响应写回到客户端 socket 输出缓冲区。
**对服务端来说就是普通的命令序列**，没有特殊处理。

## 九、生产真实踩坑

### Case 1：Pipeline 太大阻塞主线程

业务图省事，10 万次 SET 全塞一个 Pipeline，Redis 主线程被这 10 万条命令独占 1 秒，期间所有其他客户端请求超时。
**修复**：拆分批次（每批 500 条）+ 批次间短暂 sleep（让主线程喘息）。

### Case 2：Pipeline 错误未检查导致数据异常

```java
List<Object> results = pipe.syncAndReturnAll();
// 业务直接当成功用，没遍历检查
```
某条命令实际报错（类型错误），业务以为成功 → 数据不一致。
**修复**：遍历 results，instanceof Exception 时单独处理。

### Case 3：Cluster 下 Pipeline 命令乱序

JedisCluster 早期版本，跨节点 Pipeline 时不同节点响应到达时间不一，结果乱序。
**修复**：升级 Jedis；或业务用 Hash Tag 让批量命令落同 slot。

### Case 4：Pipeline 超时设置太短

跨地域 30ms RTT + 1 万条命令处理 200ms，总耗时 230ms，但客户端超时设了 100ms → 全部失败。
**修复**：根据批次大小动态调超时；监控 Pipeline P99 耗时。

### Case 5：异步 Pipeline 不 flush 导致命令累积

Lettuce 关了 autoFlush 但忘了调 `flushCommands()`，命令堆在客户端缓冲区一直没发，业务超时。
**修复**：流程末尾必须 flush；或用 try-with-resources 模式管理。

### Case 6：Pipeline 内嵌了 BLPOP 等阻塞命令

```java
pipe.blpop(0, "queue");    // 永久阻塞
pipe.set("k", "v");
pipe.sync();              // ← 卡死
```
Pipeline 里阻塞命令会让整个 Pipeline 等待 → 后续命令永不执行。
**修复**：阻塞命令不要放 Pipeline；用单独连接处理。

## 十、答题模板（60 秒话术）

> Redis 单命令执行只要 0.1ms，但 RTT 通常 0.5ms 以上——**RTT 才是网络瓶颈**。Pipeline 是客户端把多条命令缓冲后**一次发送**，节省 N-1 次 RTT；服务端按 RESP 协议天然支持，不需特殊语法。
>
> 和 **MULTI/EXEC** 比，Pipeline 是**性能优化**（不原子，命令间可被其它客户端命令穿插）；MULTI 是**事务语义**（原子但不回滚）。和 **Lua** 比，Lua 既原子又能写逻辑，是最优解。
>
> 优先用 **MGET / MSET / HMSET** 这类多 key 命令（更快、原子），用不上时再 Pipeline。
>
> 生产上单批 **500~1000 条**防 socket 缓冲爆、检查每条响应、Cluster 下用 **Hash Tag** 让多 key 同 slot。**Lettuce 异步 API 默认就像自动 Pipeline，Jedis 必须显式开**。
