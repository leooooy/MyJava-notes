# 缓存与数据库双写一致性

> 高频面试题。绝大多数人答不到位的根本原因是 **没有先讲清"我们追求什么级别的一致性"**——是强一致？最终一致？秒级一致？
> 没有这个前提，方案选择无从谈起。

---

## 一、先理清问题边界

### 1.1 一致性级别的现实选择

| 级别 | 含义 | 代价 | 互联网常见吗 |
| --- | --- | --- | --- |
| **强一致** | 任何时刻 Cache == DB | 巨大（要分布式事务） | 否 |
| **最终一致** | 短时间窗口内可能不一致，最终趋于一致 | 较低 | **是，主流** |
| **可接受窗口的最终一致** | 比如 1 秒内不一致可接受 | 低 | 是 |

**关键认知**：缓存的本质是**性能换一致性**。要绝对一致 → 别用缓存。
**互联网业务 99% 选最终一致**，只在金融核心系统才追求强一致（且通常不用缓存）。

### 1.2 双写一致性问题的根源

只要"DB 和 Cache 是两个独立系统"，**任何写操作都需要两步**：写 DB + 写 Cache。
- 两步**不能在同一个事务里**（跨系统，无分布式事务支持时）
- 两步**之间可能失败**，可能有并发请求穿插
- 两步**先后顺序**决定了出问题时数据是新还是旧

→ 分析方案就是分析这两步的顺序 + 失败处理。

## 二、四种基础方案对比

| 方案 | 失败一致性 | 并发一致性 | 实战使用 |
| --- | --- | --- | --- |
| 先更 Cache 再更 DB | ✗ | ✗ | 不用 |
| 先更 DB 再更 Cache | ✗ | ✗ | 不用 |
| 先删 Cache 再更 DB | △（延迟双删） | ✗ | 慎用 |
| **先更 DB 再删 Cache** | ✓ | △（极低概率不一致） | **主流（Cache Aside）** |

### 2.1 方案 A：先更 Cache 再更 DB（×）

**问题 1：Cache 成功 DB 失败**
```
1. 更 Cache 成功
2. 更 DB 失败
→ Cache 是新值，DB 是旧值
→ 用户看到的是错的，下次缓存过期后才会回到旧值
```

**问题 2：并发更新**
```
T1: 线程 A 更 Cache = v1
T2: 线程 B 更 Cache = v2
T3: 线程 B 更 DB = v2
T4: 线程 A 更 DB = v1
→ 最终 DB = v1，Cache = v2，永久不一致
```

> **核心问题**：DB 是数据源（source of truth），先动缓存就是把"非权威"数据当成了"权威"。

### 2.2 方案 B：先更 DB 再更 Cache（×）

**问题 1：DB 成功 Cache 失败**
```
1. 更 DB 成功
2. 更 Cache 失败
→ DB 是新值，Cache 是旧值
→ 缓存过期前都不一致
```

**问题 2：并发更新**
```
T1: A 更 DB = v1
T2: B 更 DB = v2
T3: B 更 Cache = v2
T4: A 更 Cache = v1
→ DB = v2 是最新，但 Cache = v1，永久不一致
```

**问题 3：写多读少时浪费**
更新缓存是"基于新数据计算结果"，可能根本没人读。还不如删掉，下次读再算。

### 2.3 方案 C：先删 Cache 再更 DB（△，需要延迟双删）

**问题 1（致命）：并发读穿越**
```
T1: A 删 Cache
T2: B 读 Cache miss → 查 DB（旧值）→ 写 Cache（旧值！）
T3: A 更 DB（新值）
→ 最终 DB = 新值，Cache = 旧值
```

**修复方案：延迟双删**
```
1. 删 Cache
2. 更 DB
3. sleep 一会儿（500ms~1s，覆盖 B 的 "查 DB + 写 Cache" 时间窗口）
4. 再删 Cache
```

```java
public void update(Goods g) {
    redis.del("goods:" + g.getId());      // 第一次删
    db.update(g);                          // 更 DB
    Thread.sleep(500);                     // 等可能的并发读完成
    redis.del("goods:" + g.getId());      // 第二次删，清理被并发读重建的旧值
}
```

**仍然有问题**：
- sleep 时间没有标准答案（500ms？1s？看业务读耗时）
- 第二次删除还是可能失败
- sleep 期间用户读到的是旧值
- 主从架构下，从库还没同步完就被读走 → 旧值

→ 不是首选方案。

### 2.4 方案 D：先更 DB 再删 Cache（√，Cache Aside Pattern）

```
1. 更 DB
2. 删 Cache
```

**优点**：
- DB 失败 → 不删缓存，无影响
- DB 成功 Cache 删除失败 → 重试或异步补偿

**理论上唯一的不一致情况**（概率极低）：
```
T1: A 读 Cache miss
T2: A 查 DB 得到 v0
T3: B 更 DB = v1
T4: B 删 Cache（本来就没有）
T5: A 把 v0 写回 Cache
→ DB = v1，Cache = v0，不一致
```

**为什么概率极低**：要满足 A 的"DB 查询 + 写 Cache"耗时 > B 的"DB 写入 + Cache 删除"耗时。
在写操作有锁、读操作 fast path 的现实里，几乎不可能。

> **这就是 Cache Aside（旁路缓存）模式，互联网主流方案**。

## 三、生产级实现：Cache Aside + 兜底

### 3.1 完整代码

```java
// 读
public Goods getGoods(Long id) {
    String key = "goods:" + id;
    Goods cached = redis.get(key);
    if (cached != null) return cached;
    
    Goods g = db.selectById(id);
    if (g != null) {
        redis.setex(key, 3600 + random(0, 600), g);  // TTL + 随机偏移防雪崩
    } else {
        redis.setex(key, 60, "__NULL__");             // 空值缓存防穿透
    }
    return g;
}

// 写
@Transactional
public void update(Goods g) {
    db.update(g);                       // 1. 先更 DB（事务内）
    // 事务提交后再删缓存
    TransactionSynchronizationManager.registerSynchronization(
        new TransactionSynchronizationAdapter() {
            @Override public void afterCommit() {
                redis.del("goods:" + g.getId());   // 2. 后删缓存
            }
        });
}
```

**关键点**：
- 删缓存放在**事务提交后**，避免事务回滚后缓存被错删（其实没问题，下次读会重建，但减少不必要的 miss）
- 加 TTL 兜底，删除失败也最多不一致一个 TTL 周期

### 3.2 删除失败怎么办？三种兜底

#### 兜底 1：重试 + MQ

```java
@Transactional
public void update(Goods g) {
    db.update(g);
    afterCommit(() -> {
        try {
            redis.del("goods:" + g.getId());
        } catch (Exception e) {
            mq.send("cache_invalidate", g.getId());   // 失败发 MQ，消费者重试
        }
    });
}

@RocketMQMessageListener(topic = "cache_invalidate")
public class CacheInvalidateConsumer {
    public void onMessage(Long id) {
        redis.del("goods:" + id);     // 消费失败 MQ 自带重试
    }
}
```

#### 兜底 2：Binlog + Canal 异步删除（推荐）

```
[业务写 DB]
     ↓
[MySQL Binlog]
     ↓
[Canal 订阅]
     ↓
[Canal 客户端 / MQ]
     ↓
[消费者删 Redis]
```

**优点**：
- **业务代码无侵入**，不用关心删缓存
- **解耦**：DB 是唯一数据源，缓存只是"DB 的影子"
- **跨服务一致**：多个服务写同一张表，缓存都能正确失效

**缺点**：
- 多了一套 Canal 基础设施
- 异步有延迟（毫秒级，可接受）

> **大厂主流做法**。详见下方"基于 Binlog 的方案"小节。

#### 兜底 3：定时任务对账

后台定时扫，对比缓存和 DB（抽样），发现不一致主动刷新。
适合数据量小、对一致性敏感的核心数据。

### 3.3 基于 Binlog 的方案（推荐，工业级）

```java
@Component
public class BinlogConsumer {
    @EventListener  // Canal 投递的 binlog 消息
    public void onUpdate(BinlogEvent event) {
        if ("goods".equals(event.getTable())) {
            Long id = event.getRowData().get("id");
            redis.del("goods:" + id);
        }
    }
}
```

**架构图**：
```
┌──────────┐      ┌────────┐      ┌──────────┐      ┌────────┐
│  Service │ ───→ │  MySQL │ ───→ │  Canal   │ ───→ │  MQ    │
└──────────┘      └────────┘      └──────────┘      └────┬───┘
                                                         │
                                                         ▼
                                                   ┌────────────┐
                                                   │ Cache Cleaner │
                                                   └────────────┘
                                                         │
                                                         ▼
                                                   ┌────────┐
                                                   │ Redis  │
                                                   └────────┘
```

**多实例部署 + Canal 集群**：所有服务的写都通过 Binlog 统一触发缓存失效。

## 四、强一致方案（仅特殊场景）

### 4.1 分布式锁 + 双写

```java
public void update(Goods g) {
    RLock lock = redisson.getLock("lock:goods:" + g.getId());
    lock.lock();
    try {
        db.update(g);
        redis.setex("goods:" + g.getId(), 3600, g);
    } finally {
        lock.unlock();
    }
}

public Goods getGoods(Long id) {
    RLock lock = redisson.getLock("lock:goods:" + id);
    lock.lock();
    try {
        return readWithCache(id);
    } finally {
        lock.unlock();
    }
}
```

**代价**：吞吐量大幅下降（读写都要抢锁），失去了缓存的性能优势。
**适用**：极少场景（金融关键参数）。

### 4.2 读写锁

读用读锁（共享），写用写锁（互斥）。
读多写少场景比互斥锁好，但仍有性能损失。

### 4.3 同步双写（同一事务）

把 Redis 操作放进 DB 事务里——**强烈不推荐**：
- Redis 操作失败 → DB 回滚，性能浪费
- 跨系统事务不可靠（Redis 不支持 XA）

## 五、面试高频追问

### Q1：先更 DB 再删缓存，删缓存失败怎么办？

三个层次的答案：
1. **基础**：靠 TTL 兜底，最多不一致一个 TTL
2. **中级**：删除失败发 MQ 重试，消费失败入死信队列人工补偿
3. **高级**：用 Binlog + Canal，业务代码完全不管删缓存

### Q2：为什么不用"先更 DB 再更 Cache"，明明也能保证一致？

三个理由：
1. **并发不一致**：方案 B 问题 2，两个写并发会让 Cache 永远停留在错误值
2. **写放大**：每次写都计算新缓存值，但**可能根本没人读**——删除是 lazy 加载，读到再算
3. **复杂数据成本高**：缓存的是聚合后的对象（关联多表），更新缓存要重算，删除让下次读重建简单得多

### Q3：延迟双删的 sleep 时间设多久？

没有标准答案，**业务读链路 P99 耗时的 1.5~2 倍**。
但这本身就是一个不优雅的方案，**生产不建议用**，要么 Cache Aside + Binlog，要么用强一致方案。

### Q4：Cache Aside 的极端不一致场景能不能修？

可以加锁，但代价远大于收益。互联网业务接受这个 0.001% 概率的窗口。
**真正在乎一致性的数据不放缓存**——这才是答案。

### Q5：主从延迟下怎么处理一致性？

```
1. 主库写 DB
2. 删 Cache
3. 读请求来 → Cache miss → 查从库（还没同步）→ 拿到旧值 → 写回 Cache
→ 旧值在 Cache，不一致
```

**解决方案**：
- **关键写后强读主**：写完后 N 秒内的读强制走主库
- **读写分离感知**：通过中间件（如 ShardingSphere）配置"写后读主"窗口
- **延迟双删**：等从库同步完再删一次缓存
- **Canal 监听从库 Binlog**（不靠主库写后立即删）

### Q6：分布式情况下多服务写同一份数据怎么办？

每个服务都自己删缓存 → 漏删的概率高。
最佳方案：**Binlog + Canal 统一删除**，所有服务写 DB → Binlog → 一个消费者负责删 Cache。

### Q7：缓存值是聚合多表的怎么处理？

商品详情 = 商品基础 + 库存 + 价格 + 评论数 + ... 来自多张表。
任何一张表更新都要让缓存失效：
- 各表的 Binlog 都监听
- 触发同一个 key 的删除
- 不要尝试"局部更新"——重算成本高且容易出错

### Q8：写多读少场景还要用缓存吗？

不一定。缓存的收益 = 命中率 × (DB 耗时 - Cache 耗时)。
写多读少 → 命中率低 → 收益低 → 维护一致性还要付成本 → **可能不如不用**。
评估方法：日志统计读写比，<10:1 慎用缓存。

### Q9：用 Redis 做缓存的同时还要用本地缓存吗？

可以，叫**多级缓存**（详见 [缓存雪崩，击穿，穿透](./缓存雪崩，击穿，穿透.md)）。
但本地缓存的双写一致性更难做（每个 JVM 都是独立的）：
- 本地缓存 TTL 必须短（10-60 秒）
- 重要变更通过 MQ 广播给所有节点失效
- 强一致数据**不放本地缓存**

## 六、生产真实踩坑

### Case 1：先删 Cache 再更 DB 导致并发不一致

商品价格修改后，前 2 秒并发读还是旧价格。原因：删 Cache 后用户读 miss → 查 DB（旧值）→ 写 Cache → DB 才更新。
**修复**：改为先更 DB 再删 Cache（Cache Aside）。

### Case 2：事务里删缓存，事务回滚导致空 miss 风暴

```java
@Transactional
public void update(Goods g) {
    redis.del(key);     // 先删
    db.update(g);       // DB 失败回滚
}
// 缓存被错删，大量请求穿透 DB 重建
```
**修复**：删缓存放 `afterCommit`，DB 提交成功才删。

### Case 3：Binlog 顺序错乱导致缓存被旧值覆盖

Canal 多消费者并发处理同一行的 binlog，顺序错乱：
- T1: 写 v1，binlog 1
- T2: 写 v2，binlog 2
- 消费者 A 处理 binlog 2 删 cache，B 处理 binlog 1 又写 cache（旧值）
**修复**：相同 row 的 binlog 必须串行（按 PK 哈希分配 partition）。

### Case 4：缓存 key 拼写不一致

读用 `goods:1001`，写用 `goods_1001`，永远不一致。
**修复**：统一封装 Key 生成器，禁止散落字符串。

### Case 5：忘记空值缓存

商品被下架后 DB 删除，缓存还在 → 用户能看到下架商品。
**修复**：删除 DB 也要删 Cache；空值缓存（短 TTL）覆盖"已下架"场景。

### Case 6：缓存粒度太粗，更新成本爆炸

缓存了"商品列表 Top 100"，任何一个商品更新都要重建整个列表 → 缓存命中率暴跌。
**修复**：拆分粒度，每个商品单独缓存；列表只缓存 ID 数组。

## 七、答题模板（60 秒话术）

> 互联网业务追求**最终一致**而不是强一致——强一致代价大且通常不必要。
>
> 四种基础方案分析：**先 Cache 再 DB** 不行（并发场景脏数据），**先 DB 再 Cache** 不行（同样并发问题），**先删 Cache 再更 DB** 要延迟双删（不优雅），**先更 DB 再删 Cache（Cache Aside）是主流方案**。
>
> Cache Aside 也有极端不一致场景（线程 A 读旧值未写时线程 B 完成更新+删除），但触发概率极低，业务能接受。
>
> **删除失败兜底**用 MQ 重试 / Binlog + Canal 异步 / TTL 三件套防御。要强一致就上分布式锁但代价大，慎用。
>
> 最佳实践：**Cache Aside + Binlog 异步删除 + 合理 TTL + 关键写后读路由主库**；同步双写在多数据源场景才考虑。
