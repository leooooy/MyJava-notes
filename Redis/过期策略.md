# Redis 过期策略与内存淘汰

> 高频面试题，但容易答得浮于表面。
> 关键是分清两个独立机制：**过期策略**（处理已设 TTL 的 key）和 **内存淘汰**（内存满了腾空间）。
> 很多人把它们混着讲，面试官一眼看出基础不扎实。

---

## 一、先分清两个独立机制

| 机制 | 触发条件 | 处理对象 | 配置 |
| --- | --- | --- | --- |
| **过期策略** | key 设了 TTL 且到期 | 仅设过期时间的 key | `maxmemory` 无关 |
| **内存淘汰** | 内存达 `maxmemory` 上限 | 视策略而定（可能淘汰未过期 key） | `maxmemory-policy` |

**区别**：
- 一个 key 没设 TTL，不会被"过期策略"处理，但**仍可能被"内存淘汰"干掉**（取决于淘汰策略）
- 内存够用时，过期 key 不一定立刻被删，但访问时会被惰性删除

---

## 二、过期策略（针对设了 TTL 的 key）

理论上有三种策略，**Redis 用了惰性 + 定期组合**。

### 2.1 三种过期策略对比

| 策略 | 实现 | 优点 | 缺点 | Redis 是否使用 |
| --- | --- | --- | --- | --- |
| **定时过期** | 每个 key 创建时设定时器 | 内存友好（到期立删） | CPU 消耗大 | ✗ |
| **惰性过期** | 访问 key 时才检查 | CPU 友好 | 过期 key 长期占内存 | ✓ |
| **定期过期** | 周期性抽样检查 | 折中 | 仍可能漏 | ✓ |

### 2.2 惰性删除（Lazy Expiration）

读写 key 时，先检查是否过期：
```
GET key
  ↓
检查是否过期
  ↓ 过期
DEL key
返回 nil
```

**优点**：CPU 消耗最小（只在访问时检查）
**缺点**：永远不被访问的过期 key 永远占内存

### 2.3 定期删除（Active Expiration）

Redis 每秒执行 10 次（`hz=10`），每次：

```
1. 从过期字典里随机抽 20 个 key
2. 检查这 20 个 key，过期的删除
3. 如果过期比例 > 25%，重复步骤 1
4. 单次执行时间 < 25ms（避免阻塞主线程）
```

> 注：**抽样删除而不是全量扫**，避免百万 key 时 CPU 100%。

### 2.4 两者组合的副作用

仍然有过期 key 可能存活（既没人访问，又没被随机抽中）：
- 占内存
- 主从复制时把过期数据同步到从库（旧版本问题）
- AOF 写入了过期 key 的命令

→ 这就是为什么还需要"内存淘汰"兜底。

### 2.5 主从复制下的过期处理

| 角色 | 过期处理 |
| --- | --- |
| **主库** | 惰性 + 定期，过期时显式发 `DEL` 命令同步给从库 |
| **从库** | **不主动过期**，等待主库的 DEL 命令 |

**为什么从库不主动过期**？避免主从过期时间不同步导致数据不一致。
**坑**：主库 DEL 命令延迟 → 从库可能短暂返回过期值。Redis 3.2+ 修复：从库读取过期 key 时返回 nil（但不删除）。

## 三、内存淘汰策略（针对内存满）

当 `used_memory > maxmemory` 时触发。

### 3.1 8 种淘汰策略（Redis 4.0+）

| 策略 | 范围 | 算法 | 何时用 |
| --- | --- | --- | --- |
| `noeviction` | — | 不淘汰，写入报错 | 不能丢数据的存储场景 |
| `allkeys-lru` | 所有 key | LRU | **缓存场景默认推荐** |
| `allkeys-lfu` | 所有 key | LFU（4.0+） | 热点稳定的缓存 |
| `allkeys-random` | 所有 key | 随机 | 几乎不用 |
| `volatile-lru` | 设了 TTL 的 key | LRU | 既缓存又存储混用 |
| `volatile-lfu` | 设了 TTL 的 key | LFU | 同上，热点稳定 |
| `volatile-random` | 设了 TTL 的 key | 随机 | 几乎不用 |
| `volatile-ttl` | 设了 TTL 的 key | 优先淘汰快过期的 | 临时数据多的场景 |

### 3.2 关键算法详解

#### LRU（Least Recently Used）

**思路**：淘汰最近最少访问的 key。

**Redis 不用标准 LRU**（标准 LRU 需要双向链表 + 哈希表，每个 key 占额外内存）。
**采用近似 LRU**：
1. 每个 key 在 `redisObject` 中存一个 `lru` 字段（24 位的访问时间戳）
2. 淘汰时**随机抽 N 个 key**（默认 5），淘汰其中最久未访问的
3. Redis 3.0+ 引入 **淘汰池**：维护一个候选淘汰池，每次抽样后合并到池中，从池里挑最老的淘汰

**配置**：
```ini
maxmemory-samples 5    # 抽样数，越大越精准但更耗 CPU
```

**精度**：5 个样本时接近真实 LRU 90%，10 个样本接近 99%。

#### LFU（Least Frequently Used）

**思路**：淘汰**访问频率最低**的 key。

LRU 的弱点：偶发的批量访问会污染（如一次性扫表），把真正热点挤出去。
LFU 关注"频率"而不是"最近时间"。

**实现**：`lru` 字段重新解释为：
- 高 16 位：上次访问时间（分钟）
- 低 8 位：计数器（**对数计数**，而不是直接 +1）

**对数计数**：访问 N 次后计数器约为 log(N)，避免计数器很快达到上限（255）。
随时间衰减：长期不访问的 key，计数器逐渐减少。

**配置**：
```ini
lfu-log-factor 10              # 计数器增长速度（越大越慢）
lfu-decay-time 1               # 衰减时间（分钟）
```

#### TTL

按 TTL 排序，越快过期的越先淘汰。
适合"临时数据多"的场景（如会话）。

### 3.3 怎么选

| 业务特征 | 推荐策略 |
| --- | --- |
| 纯缓存，不在乎数据丢失 | `allkeys-lru`（默认推荐） |
| 缓存热点稳定（如商品热度长期不变） | `allkeys-lfu` |
| 部分 key 是缓存（带 TTL）部分是配置（无 TTL） | `volatile-lru` 或 `volatile-lfu` |
| Redis 做存储，绝对不能丢 | `noeviction`（搭配监控告警和扩容） |
| 临时会话场景 | `volatile-ttl` |

> **生产 95% 用 `allkeys-lru`**。LFU 在某些场景下更优但 4.0+ 才支持，而且对突发热点不敏感。

## 四、关键监控指标

```bash
INFO memory
INFO stats
```

| 指标 | 含义 | 警戒线 |
| --- | --- | --- |
| `used_memory` | 已用内存 | <maxmemory × 80% |
| `maxmemory` | 内存上限 | — |
| `mem_fragmentation_ratio` | 内存碎片率 | 1.0~1.5 正常 |
| `evicted_keys` | 累计淘汰 key 数 | 突增告警 |
| `expired_keys` | 累计过期 key 数 | — |
| `keyspace_hits` / `keyspace_misses` | 命中率 | 命中率 < 95% 报警 |

**淘汰频繁**（`evicted_keys` 持续高）说明内存不够，要扩容或调整 TTL。

## 五、面试高频追问

### Q1：过期策略和内存淘汰是一回事吗？

不是。
- **过期策略**：处理"用户设了 TTL 的 key"，TTL 到点删除
- **内存淘汰**：处理"内存满了"，无论 key 有没有 TTL 都可能被淘汰

一个没设 TTL 的 key，永远不会被"过期策略"碰到，但可能被"内存淘汰"干掉。

### Q2：定期删除每次扫所有 key 吗？

不会。每次**随机抽样 20 个 key**，过期比例高就再来一轮，单轮总耗时 < 25ms。
百万级 key 也不会卡 CPU。

### Q3：定期删除会漏吗？怎么办？

会漏。漏掉的 key：
- 等访问时被惰性删除
- 内存满了被淘汰策略干掉

→ 这就是为什么 Redis 既要定期 + 惰性，又要内存淘汰兜底。

### Q4：Redis 的 LRU 和标准 LRU 一样吗？

不一样。Redis 用**近似 LRU**：
- 标准 LRU 需要双向链表，每个 key 多 16 字节左右内存开销
- 近似 LRU 只在 redisObject 里存 24 位时间戳，淘汰时随机抽样找最老的

代价是精度略差（5 样本 ≈ 90% 准确），但内存友好。

### Q5：LRU 和 LFU 选哪个？

- **LRU**：默认选择，简单、对突发热点反应快
- **LFU**：缓存数据访问模式稳定时更优；对偶发的批量扫描更鲁棒

实战中绝大多数业务用 LRU 就够。LFU 在以下场景更优：
- 缓存了大量"几乎不会变热点"的数据
- 经常有批量扫描污染缓存（如离线分析任务跑过一次后把热点都挤掉了）

### Q6：noeviction 策略下内存满了会怎样？

写命令直接报错（`OOM command not allowed when used memory > 'maxmemory'`），读命令正常。
适合**纯存储**场景（不能丢数据），必须配合监控扩容。

### Q7：为什么从库不主动删除过期 key？

避免主从过期时间不同步导致的不一致。
主库统一控制：主库过期后发 `DEL` 命令到从库。
3.2 之前从库读到过期 key 会返回旧值；3.2+ 修复成返回 nil。

### Q8：过期 key 会立即触发持久化吗？

- **AOF**：过期时（无论惰性还是定期）会写一条 DEL 命令到 AOF
- **RDB**：dump 时跳过已过期 key

### Q9：怎么知道一个 key 什么时候过期？

```bash
TTL key       # 剩余秒数（-1=无 TTL，-2=不存在）
PTTL key      # 剩余毫秒
EXPIRETIME key # 过期的绝对时间戳（7.0+）
```

### Q10：为啥设了 TTL 还能在 INFO 里看到内存占用没变？

惰性删除 + 定期删除是**异步**的。即使 TTL 到了，如果没人访问、定期删除没抽中，内存还占用着。
所以 `used_memory` 可能短期内看着没变。要看 `expired_keys` 计数器。

### Q11：能让 Redis 不淘汰某些重要 key 吗？

没有官方"持久标记"，但可以：
- 给重要 key 不设 TTL（`volatile-*` 策略下不会淘汰）
- 把重要 key 放专用 Redis 实例
- 监控 + 告警，发现被淘汰立刻补回

### Q12：内存碎片率 mem_fragmentation_ratio 太高怎么办？

> 1.5：碎片严重，物理内存浪费
< 1.0：被 swap，性能崩

**碎片治理**：
- Redis 4.0+：开启自动碎片整理 `activedefrag yes`
- 重启实例：碎片归零（备库重启 + 故障切换，避免影响业务）

## 六、生产真实踩坑

### Case 1：noeviction + 内存写满 → 业务全报错

误用 `noeviction`，凌晨监控发现写入失败 → 业务大量报错。
**修复**：改为 `allkeys-lru`。同时调高内存上限。

### Case 2：LRU 抽样数太低，淘汰不准

`maxmemory-samples 3`，淘汰时挑出来的不是真正最老的 → 缓存命中率下降 5%。
**修复**：调到默认 5 或 10。

### Case 3：批量扫描污染 LRU

某次离线任务全量扫了一遍冷数据 → LRU 把真正的热点挤出去 → 命中率从 99% 降到 80%。
**修复**：
- 改用 LFU
- 离线任务用单独的 Redis 实例
- 业务侧加白名单，不让扫描全表

### Case 4：从库读到过期数据

老版本 Redis（< 3.2），主库 DEL 命令延迟，从库读到过期值。
**修复**：升级到 3.2+。或业务侧加二次校验。

### Case 5：定期删除卡死主线程

某次内存暴涨，过期字典极大，定期删除每轮都过 25%，连续多轮，单次 hz 阻塞 200ms。
**修复**：
- 调高 `hz` 到 20（更频繁、单次更短）
- 排查为什么大量 key 集中过期（业务批量写入用了相同 TTL）→ TTL 加随机偏移

### Case 6：监控发现 evicted_keys 暴涨

内存够用时基本为 0，某天暴涨 100 万 → 内存满了在频繁淘汰。
**修复**：
- 紧急扩容
- 排查近期是否有大 key 写入
- 长期：拆分集群

### Case 7：误用 maxmemory 0 导致 OOM

`maxmemory 0` 是"无上限"，物理内存被吃完触发 Linux OOM Killer 杀进程。
**修复**：必须设 `maxmemory`，留 50% 余量给 fork。

## 七、答题模板（60 秒话术）

> 先讲清两个独立机制：**过期策略**针对设了 TTL 的 key，**内存淘汰**针对 maxmemory 内存上限——别混为一谈。
>
> 过期策略采用**惰性 + 定期组合**：惰性是 GET 时检查是否过期，定期是每秒 10 次随机抽样删除（不全扫，分摊开销）。
>
> 内存淘汰有 8 种策略，常用 `allkeys-lru`。Redis 实现的是**近似 LRU**——抽样 N 个 key 中淘汰 LRU 的，不维护全量链表，省内存。
>
> **LRU vs LFU**：默认 LRU；批量污染（一次性 import 大量数据冷数据）场景选 LFU，按访问频次淘汰，用对数计数防溢出。
>
> 关键认知：**从库不主动过期**，靠主库 DEL 同步保证一致；监控 `evicted_keys`、命中率、内存碎片率。
