# 缓存雪崩、击穿、穿透

> 三个概念是面试必问。回答时**先对比清三者的本质区别**（很多人答着答着就混了），再分别讲方案，每个方案都说**取舍**——这是 senior 与初级的分水岭。

---

## 一、三者本质区别（先记牢这张表）

| 维度 | 缓存穿透 | 缓存击穿 | 缓存雪崩 |
| --- | --- | --- | --- |
| **数据是否真实存在** | **不存在**（DB 也查不到） | 存在但过期了 | 存在但过期了 |
| **失效范围** | 单点 / 大范围 | **单个热点 key** | **大量 key 同时失效** |
| **流量特征** | 大量请求查不存在的 key | 高并发请求同一个热 key | 海量请求同时打 DB |
| **典型场景** | 黑客攻击、异常 ID | 热门商品缓存到期 | Redis 集体宕机、批量过期 |
| **核心防护** | 布隆过滤器 + 空值缓存 | 互斥锁 + 逻辑过期 | 过期时间打散 + 多级缓存 + 高可用 |
| **DB 危险等级** | 高（持续打 DB） | 中（短时打 DB） | 极高（瞬间打 DB） |

> 一句话区分：
> - **穿透**：查的东西**根本不存在**
> - **击穿**：**单个热点**没了
> - **雪崩**：**一大片**没了

---

## 二、缓存穿透（Cache Penetration）

### 2.1 现象与原理

请求查询的 key **在缓存和 DB 都不存在**，缓存层永远拦截不到，每次都打 DB。

典型攻击场景：
```
攻击者构造大量不存在的用户 ID（id=-1, id=-2, id=99999999...）
缓存层：miss
DB 层：查不到，但已经走完一次 IO
返回结果：null
```

如果 QPS 几万，DB 直接挂。

### 2.2 解决方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| **参数校验** | 实现简单 | 防得了无效格式，防不了构造合法 ID | 边界第一道防线 |
| **空值缓存** | 简单粗暴 | 每个不存在的 key 都占一份内存；攻击者用随机 ID 让缓存失效 | 大部分场景兜底 |
| **布隆过滤器** | 内存极省（1 亿 key ~100MB） | 误判率（说存在可能不存在）、不能删 | 数据量大、ID 离散 |
| **互斥锁** | 无效 key 也只打一次 DB | 吞吐降低 | 配合空值缓存使用 |
| **网关风控** | 治本 | 需要风控基础设施 | 黑客攻击场景 |

### 2.3 方案 1：参数校验（必做的第一道）

```java
public User getUser(Long id) {
    if (id == null || id <= 0) {
        return null;            // 业务上 id 一定是正数
    }
    // 走缓存逻辑
}
```

**别小看这一步**，能挡掉大部分恶意构造的非法参数。

### 2.4 方案 2：空值缓存

```java
public User getUser(Long id) {
    String key = "user:" + id;
    String cached = redis.get(key);
    
    if ("__NULL__".equals(cached)) {     // 命中空值
        return null;
    }
    if (cached != null) {
        return JSON.parseObject(cached, User.class);
    }
    
    User user = userMapper.selectById(id);
    if (user == null) {
        // 缓存空值，TTL 短一些，避免占用内存
        redis.setex(key, 60, "__NULL__");
        return null;
    }
    redis.setex(key, 3600, JSON.toJSONString(user));
    return user;
}
```

**坑**：
1. **TTL 不能太长**：1-5 分钟。否则真用户注册 ID=12345 后还显示不存在。
2. **TTL 不能太短**：1 秒就废了。
3. **攻击者用随机 ID**：每个 ID 占一份缓存内存 → 缓存空间被打爆。配合**布隆过滤器**或**限流**用。

### 2.5 方案 3：布隆过滤器（推荐）

详见 [布隆过滤器](./布隆过滤器.md)。

```java
public User getUser(Long id) {
    // 第一关：布隆过滤器
    if (!bloomFilter.contains(id)) {
        return null;                    // 一定不存在，直接拒绝
    }
    // 第二关：缓存
    User user = (User) redis.get("user:" + id);
    if (user != null) return user;
    
    // 第三关：DB
    user = userMapper.selectById(id);
    if (user != null) {
        redis.setex("user:" + id, 3600, user);
    } else {
        redis.setex("user:" + id, 60, "__NULL__");   // 双保险
    }
    return user;
}
```

**初始化**：应用启动时，把 DB 全量 ID 加载到布隆过滤器（增量数据通过 binlog/canal 同步）。

### 2.6 方案 4：互斥锁（防止并发穿透打 DB）

即使有空值缓存，**第一次缓存还没建立时**，并发请求会同时打 DB。互斥锁可以让无效 key 也只查一次。

```java
public User getUser(Long id) {
    String key = "user:" + id;
    Object cached = redis.get(key);
    if (cached != null) {
        return "__NULL__".equals(cached) ? null : (User) cached;
    }
    
    String lockKey = "lock:user:" + id;
    if (redis.setnx(lockKey, "1", 10, TimeUnit.SECONDS)) {
        try {
            // 双重检查
            cached = redis.get(key);
            if (cached != null) {
                return "__NULL__".equals(cached) ? null : (User) cached;
            }
            User user = userMapper.selectById(id);
            redis.setex(key, user == null ? 60 : 3600, user == null ? "__NULL__" : user);
            return user;
        } finally {
            redis.del(lockKey);
        }
    } else {
        Thread.sleep(50);                // 没拿到锁，短暂等待重试
        return getUser(id);
    }
}
```

## 三、缓存击穿（Hotspot Invalid）

### 3.1 现象与原理

**单个热点 key** 突然过期，瞬间高并发请求全部穿过缓存打到 DB。

典型场景：
- 双 11 主推商品的详情缓存到期
- 微博热搜词的搜索结果缓存到期
- 首页 Banner 配置缓存过期

> 击穿和穿透的关键区别：**击穿的数据是真实存在的**，只是缓存暂时没有。

### 3.2 解决方案

#### 方案 1：互斥锁（同步思路）

只让一个线程去查 DB 重建缓存，其他线程等待。

```java
public Goods getGoods(Long id) {
    String key = "goods:" + id;
    Goods goods = redis.get(key);
    if (goods != null) return goods;
    
    String lockKey = "lock:goods:" + id;
    // 用 Redisson 或 SETNX 实现分布式锁
    if (redis.setnx(lockKey, "1", 10, TimeUnit.SECONDS)) {
        try {
            // double check
            goods = redis.get(key);
            if (goods != null) return goods;
            
            goods = goodsMapper.selectById(id);
            redis.setex(key, 3600, goods);
            return goods;
        } finally {
            redis.del(lockKey);
        }
    } else {
        // 没拿到锁，短暂自旋等待
        Thread.sleep(50);
        return getGoods(id);             // 此时大概率命中刚重建的缓存
    }
}
```

**优点**：实现简单，强一致。
**缺点**：拿不到锁的线程要等待，**响应时间变长**；锁本身可能成为瓶颈。

#### 方案 2：逻辑过期（异步思路，推荐高并发场景）

**核心思想**：缓存**永不过期**，但 value 里带逻辑过期时间，过期后**返回旧值同时异步重建**。

```java
public class CacheValue<T> {
    private T data;
    private long expireAt;       // 逻辑过期时间戳
}

public Goods getGoods(Long id) {
    String key = "goods:" + id;
    CacheValue<Goods> wrapper = redis.get(key);
    if (wrapper == null) {
        // 完全没缓存，走互斥锁兜底
        return loadAndCache(id);
    }
    
    if (wrapper.getExpireAt() > System.currentTimeMillis()) {
        return wrapper.getData();        // 没过期，直接返回
    }
    
    // 逻辑过期：先返回旧值，异步重建
    String lockKey = "lock:goods:" + id;
    if (redis.setnx(lockKey, "1", 10, TimeUnit.SECONDS)) {
        executor.submit(() -> {
            try {
                Goods fresh = goodsMapper.selectById(id);
                CacheValue<Goods> newVal = new CacheValue<>(fresh, 
                    System.currentTimeMillis() + 3600 * 1000);
                redis.set(key, newVal);  // 不设 TTL
            } finally {
                redis.del(lockKey);
            }
        });
    }
    return wrapper.getData();            // 立即返回旧值
}
```

**优点**：用户响应永远很快（不阻塞）。
**缺点**：返回的可能是旧数据；缓存永不过期需要主动维护（被淘汰、容量考虑）。

#### 方案 3：热点 key 永不过期 + 后台定时刷新

最暴力的方案：识别出热点 key，**不设 TTL**，启动定时任务每隔 N 分钟主动刷新。

```java
@Scheduled(fixedRate = 60_000)         // 每 1 分钟刷新
public void refreshHotGoods() {
    List<Long> hotIds = hotKeyDetector.getHotIds();
    for (Long id : hotIds) {
        Goods g = goodsMapper.selectById(id);
        redis.set("goods:" + id, g);
    }
}
```

**适用**：可枚举的少量超热点（如双 11 主推 100 件商品）。配合**热 key 自动检测**就能动态加入。

#### 三种方案对比

| 方案 | 用户响应 | 数据新鲜度 | 实现复杂度 | 适用场景 |
| --- | --- | --- | --- | --- |
| 互斥锁 | 阻塞等待 | 强 | 低 | 普通业务，可接受短暂等待 |
| 逻辑过期 | 立即返回 | 弱（短暂旧值） | 中 | 高并发、容忍短暂不一致 |
| 永不过期+定时 | 立即返回 | 中 | 中 | 已知少量超热点 |

## 四、缓存雪崩（Cache Avalanche）

### 4.1 现象与原理

**大量缓存 key 同时失效**，或 **Redis 集群整体宕机**，瞬间海量请求打 DB → DB 挂 → 拖垮整站。

两种典型场景：

**场景 A：大量 key 同时过期**
```
凌晨 12:00 批量预热 1000 万商品缓存，TTL 都是 24 小时
次日 12:00 → 1000 万 key 同时失效 → DB 死亡
```

**场景 B：Redis 整个集群挂**
```
机房断电 / 运维误操作 / Cluster 故障转移 → 整个 Redis 不可用
所有请求穿透到 DB → DB 立刻被打挂
```

### 4.2 解决方案

#### 方案 1：过期时间打散（防"同时过期"）

```java
// 错误写法：所有商品 TTL 都是 24 小时
redis.setex(key, 24 * 3600, value);

// 正确写法：基础 TTL + 随机偏移
int randomOffset = ThreadLocalRandom.current().nextInt(3600);  // 0~1 小时随机
redis.setex(key, 24 * 3600 + randomOffset, value);
```

**核心原则**：永远不要让大量 key 在同一秒过期。

#### 方案 2：多级缓存（防"Redis 全挂"）

```
[请求] → 本地缓存 Caffeine → Redis → DB
            ↑                  ↑
         L1 缓存             L2 缓存
```

- **本地缓存（Caffeine）**：JVM 内，TTL 30 秒，容量 1 万
- **Redis 集群**：分布式缓存，TTL 1 小时
- **DB**：兜底

Redis 挂了，本地缓存还能扛 30 秒，给运维留出救援时间。

```java
@Cacheable(cacheManager = "caffeineManager", key = "#id")    // L1
public Goods getGoodsL1(Long id) {
    return getGoodsL2(id);                                   // 没命中 L1 → 查 L2
}

public Goods getGoodsL2(Long id) {
    Goods cached = redis.get("goods:" + id);
    if (cached != null) return cached;
    Goods g = goodsMapper.selectById(id);
    redis.setex("goods:" + id, 3600, g);
    return g;
}
```

**坑**：本地缓存和 Redis 一致性不好处理，详见 [双写一致性](./双写一致性.md)。一般 L1 TTL 设短（10-60 秒），容忍短暂不一致。

#### 方案 3：熔断 + 限流 + 降级（防"DB 被打挂"）

无论缓存怎么挂，最后一道防线是**别让 DB 死掉**。

```java
@SentinelResource(value = "getGoods",
    blockHandler = "getGoodsBlocked",
    fallback = "getGoodsFallback")
public Goods getGoods(Long id) {
    // ...
}

// 限流：QPS > 1000 时直接拒绝
public Goods getGoodsBlocked(Long id, BlockException ex) {
    return Goods.EMPTY;                  // 静态降级
}

// 异常熔断：DB 报错时返回兜底
public Goods getGoodsFallback(Long id, Throwable ex) {
    return Goods.EMPTY;
}
```

**三件套缺一不可**：
1. **限流**：保护 DB 不被打挂
2. **熔断**：DB 已经慢了就别再打了
3. **降级**：返回静态数据 / 空数据 / 友好文案

#### 方案 4：Redis 高可用（防"Redis 整体宕机"）

详见 [集群部署](./集群部署.md)、[秒杀场景-Redis故障应对](./秒杀场景-Redis故障应对.md)。

- **主从 + 哨兵**：master 挂了自动切主
- **Cluster 集群**：分片 + 主从，跨机架部署
- **多机房双活**：异地容灾
- **持久化**：AOF everysec，故障重启能快速恢复

#### 方案 5：缓存预热（防"冷启动雪崩"）

应用启动 / 大促前，提前把热点数据加载到缓存：

```java
@PostConstruct
public void preheat() {
    List<Long> hotIds = hotKeyService.getTop1000();
    for (Long id : hotIds) {
        getGoods(id);                    // 触发缓存写入
    }
}
```

避免用户流量进来时缓存全部 miss，瞬间打 DB。

## 五、综合防护体系（生产环境必备）

把三大问题的方案合并起来，一个完整的缓存层应该长这样：

```
┌─────────────────────────────────────────────┐
│  网关层：限流（[限流算法](../Microservice/限流算法.md)） + 风控（IP/设备）│
└─────────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────┐
│  应用层：参数校验 + 布隆过滤器              │
└─────────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────┐
│  L1 本地缓存（Caffeine，TTL 30s）           │
└─────────────────────────────────────────────┘
                    │ miss
                    ▼
┌─────────────────────────────────────────────┐
│  L2 Redis 集群（TTL 1h + 随机偏移）         │
│   - 互斥锁防击穿                            │
│   - 空值缓存防穿透                          │
│   - 多副本 key 防热点                       │
└─────────────────────────────────────────────┘
                    │ miss
                    ▼
┌─────────────────────────────────────────────┐
│  熔断 + 限流 + 降级                         │
│   （Sentinel / Hystrix）                    │
└─────────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────────┐
│  DB（最后兜底，连接池保护）                 │
└─────────────────────────────────────────────┘
```

每一层都是兜底，**单层失效不影响整体**。

## 六、监控告警

提前发现胜过事后救援：

| 指标 | 告警阈值 | 含义 |
| --- | --- | --- |
| 缓存命中率 | < 95% | 可能有穿透或缓存被淘汰 |
| 单 key QPS | > 1 万 | 热点 key，准备处理 |
| Redis miss 数 | 突增 | 雪崩前兆 |
| DB QPS 突增 | > 平时 2 倍 | 缓存出问题了 |
| 慢 SQL 数 | > 平时 3 倍 | DB 已经在被穿透流量打 |
| 接口 P99 | > 阈值 | 缓存重建变慢 |

## 七、面试高频追问

### Q1：穿透和击穿到底有啥区别？我老搞混

**穿透**：查 **DB 也没有**的数据（比如 id=-1）。
**击穿**：查 **DB 有但缓存刚好过期**的数据（比如热点商品）。

判断：**DB 能不能查到** 就是分界线。

### Q2：布隆过滤器有误判，那万一漏过去了怎么办？

误判率 1% 意味着 1% 不存在的 key 会被认为"可能存在" → 走到缓存/DB。
**这是可接受的**——后面还有空值缓存兜底，最多 1% 流量打 DB 一次，不会持续打。
布隆过滤器的价值是把 99% 的攻击流量在第一关挡掉。

### Q3：互斥锁不就是把并发变串行了？性能不就废了？

只在**缓存重建瞬间**串行（毫秒级），重建完成后所有请求都命中缓存。
对于击穿场景：99.99% 时间是命中状态，0.01% 时间是重建状态，串行的影响微乎其微。
高并发场景下，可以用**逻辑过期**代替互斥锁，连这点等待都没有。

### Q4：逻辑过期返回旧值，业务能接受吗？

看场景：
- **商品详情**：旧 1 分钟用户感知不到 → 能接受
- **商品价格**：旧 1 分钟可能下错单 → 不能接受，必须用互斥锁或缩短过期窗口
- **库存**：永远要实时 → 不能用逻辑过期，必须实时

> **取舍**：高并发要逻辑过期，强一致要互斥锁。看你"能容忍多久的旧"。

### Q5：缓存雪崩 + 热点 key 同时发生怎么办？

最坏情况：双 11 凌晨，所有热点商品缓存集体过期。
应对：
1. **过期时间随机**（基础解决"同时过期"）
2. **超热点永不过期**（运营提前标记，定时刷新）
3. **多级缓存**（本地缓存兜底）
4. **限流降级**（最坏情况保 DB）

### Q6：先更新 DB 还是先删缓存？跟雪崩有关吗？

跟雪崩没关系，跟**双写一致性**有关。
详见 [双写一致性](./双写一致性.md)。
一般用 **先更 DB 再删缓存**（Cache Aside），配合 binlog + canal 异步删除兜底。

### Q7：怎么知道哪个 key 是热点？

- **客户端采样**：拦截器统计 key 访问频率，超阈值上报
- **Redis 监控**：`redis-cli --hotkeys`、`MONITOR`（生产慎用）
- **代理层热点检测**：Tair Proxy / Codis 自带
- **离线分析**：日志分析 Top N 高频 key

### Q8：空值缓存被攻击者用随机 ID 打爆怎么办？

组合拳：
1. **布隆过滤器**前置（最有效）
2. **网关限流**：单 IP/秒 100 次以上拒绝
3. **空值缓存 TTL 短**：1-5 分钟，自然淘汰
4. **风控**：异常 ID 模式（连续负数、超大值）打回

### Q9：缓存预热什么时候做？

- **应用启动时**：常驻热点（首页配置、字典数据）
- **大促前**：活动数据，提前 1-2 小时预热
- **定时刷新**：超热点定时主动刷新
- **流量进来后**：通过 access log 监控，发现新热点立刻预热

### Q10：Redis 容量不够，是该淘汰还是过期？

两套机制：
- **过期**：业务设的 TTL，到点删除
- **淘汰**：内存满了被动删除（`maxmemory-policy`）

秒杀场景必配 `allkeys-lru` 或 `allkeys-lfu`，让冷数据让位给热数据。**别用 `noeviction`**，写满直接拒绝写入会触发雪崩。

## 八、生产真实踩坑

### Case 1：批量预热导致集中过期

凌晨 2 点用脚本批量加载 500 万商品到 Redis，TTL 都是 24 小时。次日 2 点整 → 500 万 key 同时过期 → DB QPS 飙升 5 倍 → DB CPU 100%。

**修复**：脚本里给 TTL 加随机偏移 `random.randint(0, 3600)`。

### Case 2：空值缓存被攻击爆 Redis 内存

恶意流量构造大量随机 ID，每个走完链路都缓存一个空值（TTL 5 分钟）。一晚上缓存了 2000 万空 key，Redis 内存暴涨 10G，触发淘汰，热点数据被挤掉，引发二次雪崩。

**修复**：
- 上布隆过滤器前置拦截
- 空值缓存 key 单独走一个 Redis DB，限制最大内存
- 网关层加 IP 限流

### Case 3：互斥锁死锁拖垮服务

击穿防护用了 SETNX 加锁，但忘了设过期时间。某次 DB 慢查询超时，锁没释放 → 后续请求全部等锁 → 线程池打满 → 整个服务雪崩。

**修复**：
- 锁必须设 TTL（如 10 秒）
- 上 Redisson，自带 watchdog 续命
- 等待超时也要降级，不能无限等

### Case 4：本地缓存 + Redis 双写不一致

商品价格改了，更新了 DB 和 Redis，但本地缓存（Caffeine TTL 60 秒）还是旧的。结果 1 分钟内有用户拿到旧价格，下单后系统按新价格扣款，引发投诉。

**修复**：
- 价格类强一致数据**不放本地缓存**
- 关键配置变更通过 MQ 广播，所有实例主动失效本地缓存

### Case 5：Redis 集群挂了，应用全挂

Redis 集群机房断电，应用调用 Redis 全部超时（默认 timeout 5 秒），线程池里每个线程都阻塞 5 秒，瞬间打满，应用对外完全不响应。

**修复**：
- Redis 客户端超时**必须短**（100-200ms）
- Sentinel 熔断 Redis 调用，连续失败立刻 fallback
- 多级缓存：本地缓存兜底

## 九、答题模板（60 秒话术）

> 三个概念先用一句话区分清：**穿透**是数据本身不存在被恶意 ID 攻击，**击穿**是热点 key 突然过期大量请求打 DB，**雪崩**是大量 key 同时失效或 Redis 整挂——判断关键看 DB 能不能查到。
>
> **穿透**三层防：参数校验挡格式错、**布隆过滤器是主力**、空值缓存兜底，再配合网关限流防恶意流量。
>
> **击穿**两个方案：**互斥锁**让只有一个线程查 DB（强一致响应慢）、或**逻辑过期**返回旧值异步刷新（弱一致响应快）；超热点直接永不过期 + 定时刷新。
>
> **雪崩**三个层面：**过期时间打散**防同时失效、**多级缓存**（本地 Caffeine + Redis）防 Redis 整挂、**熔断限流降级**保 DB；再加 Redis 高可用部署和缓存预热。
>
> 综合防护按"网关 → 布隆 → 本地缓存 → Redis 集群 → 熔断降级"**五层叠加**——任一层失效都有下一层兜底。
