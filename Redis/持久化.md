# Redis 持久化

> 高频面试题。回答时不要只罗列 RDB/AOF 是什么，要讲清楚 **三件事**：
> 1. **为什么 Redis 需要持久化**（不是所有场景都需要）
> 2. **每种方案的取舍**（CPU、内存、磁盘 IO、数据安全性、恢复速度）
> 3. **生产怎么选**（混合持久化的真实价值）

---

## 一、为什么需要持久化

Redis 是**内存数据库**，断电/重启就全没了。
- **缓存场景**：可以不持久化，重启冷启动从 DB 重建
- **存储场景**（用 Redis 做 KV 存储、消息队列、分布式锁元信息等）：必须持久化

> **第一个反问**：你的 Redis 用来做啥？只做缓存可以关掉持久化（性能更高）；做存储就必须开。**没有放之四海而皆准的答案**。

---

## 二、RDB（Redis DataBase）

### 2.1 是什么

**周期性快照**：每隔 N 秒把内存数据**完整 dump 到磁盘**，生成一个二进制文件 `dump.rdb`。

### 2.2 触发方式

| 方式 | 触发条件 | 阻塞主线程 |
| --- | --- | --- |
| `SAVE` | 手动命令 | **是**（生产禁用） |
| `BGSAVE` | 手动命令 / 自动触发 | 否（fork 子进程） |
| 配置文件 `save` | 自动按规则 | 否 |
| 主从复制 | 全量同步时 | 否 |
| `SHUTDOWN` | 服务正常关闭 | 否（自动 BGSAVE） |

**自动配置**（默认）：
```ini
save 900 1        # 900 秒内有 1 个 key 变化 → 触发
save 300 10       # 300 秒内有 10 个 key 变化 → 触发
save 60 10000     # 60 秒内有 10000 个 key 变化 → 触发
```

### 2.3 BGSAVE 的核心机制：fork + COW

```
1. 主进程 fork 一个子进程
2. 子进程拥有主进程的"内存快照"（共享物理内存页，写时复制 COW）
3. 子进程把内存数据序列化成 RDB 文件
4. 主进程继续处理客户端请求
5. 主进程修改数据时，触发 COW，复制对应内存页
6. 子进程完成后，atomically 替换旧 RDB 文件
```

**关键技术：Copy-On-Write（写时复制）**

Linux 的 `fork()` 不会真的复制内存——父子进程共享同一份物理内存页（标记为只读）。
当父进程要修改某一页时：
1. 触发缺页中断
2. 内核复制这一页（仅这一页）
3. 父进程改的是新的副本，子进程看到的还是 fork 那一刻的快照

→ 这就是为什么 BGSAVE 能"在不暂停 Redis 的前提下生成一致性快照"。

### 2.4 RDB 的隐藏成本（很多人答不到的点）

#### 成本 1：fork 本身可能阻塞主线程

虽然 BGSAVE 不阻塞执行命令，但**`fork()` 这一刻是阻塞的**：
- 内存越大，fork 越慢
- 单实例 10GB → fork 可能阻塞 100ms+
- 触发期间所有客户端请求都会卡住

**生产监控指标**：`latest_fork_usec`（最近一次 fork 耗时，单位 μs）

#### 成本 2：内存翻倍风险

COW 在**写多场景**下会失效——大量页被复制：
- 极端情况下子进程持有的"快照"占用的物理内存接近主进程
- 实例 8GB，写入压力大时可能瞬间用 12-16GB

→ 部署 Redis 时**预留 50% 内存**给 fork。

#### 成本 3：CPU 与磁盘 IO

子进程序列化 + 压缩 + 写盘，吃 CPU 和磁盘带宽。机械盘可能写 5-10 分钟。

### 2.5 优缺点

| 优点 | 缺点 |
| --- | --- |
| 文件**紧凑、小**（二进制 + LZF 压缩） | **会丢数据**（两次快照之间的写入） |
| **恢复快**（直接 load 内存，不重放命令） | **fork 开销大**（大实例阻塞主线程） |
| 适合**备份、灾难恢复**（可拷到异地） | 频繁 fork 影响性能 |
| 子进程操作，不影响主进程吞吐 | 老版本 RDB 不向后兼容 |

## 三、AOF（Append Only File）

### 3.1 是什么

**写命令日志**：把每条**写命令**追加写到 `appendonly.aof` 文件，重启时按顺序回放。

```
SET key1 v1     → 追加到 AOF
SET key2 v2     → 追加到 AOF
DEL key1        → 追加到 AOF
```

### 3.2 三种 fsync 策略

| 策略 | 含义 | 数据安全性 | 性能 |
| --- | --- | --- | --- |
| `appendfsync always` | 每条命令立刻 fsync 到磁盘 | 最安全（不丢） | 最差（QPS 几千） |
| `appendfsync everysec` | **每秒 fsync 一次**（默认） | 最多丢 1 秒 | 较好 |
| `appendfsync no` | 由 OS 决定（通常 30s） | 最不安全 | 最好 |

**关键认识**：**fsync 才是真正写到磁盘**，单纯的 `write()` 只到 PageCache，断电会丢。

### 3.3 AOF 重写（关键机制）

AOF 越写越大怎么办？例如：
```
INCR counter   # 执行 1000 万次
```
AOF 里有 1000 万条命令，回放也要 1000 万次。

**重写**：把当前内存状态用**最少的命令**重新表达。
```
重写前: INCR counter (1000 万条)
重写后: SET counter 10000000 (1 条)
```

#### 重写流程（AOF rewrite）

```
1. 主进程 fork 子进程（同 RDB，COW）
2. 子进程根据当前内存生成新 AOF（精简版）
3. 主进程同时把新写入的命令缓存到 AOF rewrite buffer
4. 子进程完成后，主进程把 buffer 追加到新 AOF
5. atomically 替换旧 AOF
```

**触发条件**（默认）：
```ini
auto-aof-rewrite-percentage 100   # 比上次重写大一倍
auto-aof-rewrite-min-size 64mb    # 最小 64MB 才考虑重写
```

也可以手动 `BGREWRITEAOF`。

### 3.4 优缺点

| 优点 | 缺点 |
| --- | --- |
| **数据安全性高**（最多丢 1s） | **文件大**（明文命令日志） |
| 顺序追加写，IO 友好 | **恢复慢**（要逐条回放） |
| 可读（文本格式，便于排错） | 重写期间也会 fork |
| 误删数据可手动 reset 时间点 | 高负载下 IO 压力大 |

## 四、RDB vs AOF 全方位对比

| 维度 | RDB | AOF |
| --- | --- | --- |
| **数据格式** | 二进制压缩 | 命令文本 |
| **文件大小** | 小（紧凑 + 压缩） | 大 |
| **数据丢失** | 两次快照间全丢 | 最多丢 1 秒 |
| **写入性能** | 触发时 fork 一次 | 持续追加 |
| **CPU 消耗** | 子进程序列化耗 CPU | 主进程写命令耗 CPU 少；fsync 耗磁盘 |
| **磁盘 IO** | 周期性大量 IO | 持续小量 IO |
| **恢复速度** | **快**（直接读内存映像） | 慢（逐条回放） |
| **适合场景** | 备份、灾难恢复 | 主持久化 |
| **重启耗时** | 秒级 | 分钟级（取决于文件大小） |
| **跨版本兼容** | 一般兼容 | 完全兼容（命令文本） |

## 五、混合持久化（Redis 4.0+，推荐）

### 5.1 为什么需要混合

- **纯 RDB**：丢数据多，不安全
- **纯 AOF**：恢复慢
- **混合**：取两者之长

### 5.2 工作机制

开启方式：
```ini
aof-use-rdb-preamble yes    # 默认开启
```

**核心**：AOF 重写时，前半部分写 RDB 格式（基线快照），后半部分写新增的 AOF 命令。

```
[RDB 二进制快照][增量 AOF 命令]
   ↑                ↑
   重写时刻的       重写后到现在的
   完整数据         新增命令
```

### 5.3 恢复流程

```
1. 读取文件头，识别是混合格式
2. 先 load RDB 部分（快速恢复到基线）
3. 再 replay 增量 AOF（追到最新）
```

→ **恢复速度接近 RDB，数据安全性接近 AOF**。

### 5.4 缺点

- 文件不再是纯文本，**可读性变差**
- 不向下兼容（旧版本 Redis 读不了）

## 六、生产配置最佳实践

### 6.1 缓存场景（不在乎丢数据）

```ini
save ""                      # 关闭 RDB 自动触发
appendonly no                # 关闭 AOF
```

最大化性能，重启冷启动从 DB 重建。

### 6.2 通用业务（推荐）

```ini
# RDB（保留作为快照备份）
save 900 1
save 300 10
save 60 10000
rdbcompression yes
rdbchecksum yes

# AOF + 混合
appendonly yes
appendfsync everysec
aof-use-rdb-preamble yes
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb

# fork 优化
no-appendfsync-on-rewrite yes   # 重写期间不 fsync（防 IO 抢占）
```

### 6.3 金融级（不能丢任何数据）

```ini
appendonly yes
appendfsync always              # 每条命令都 fsync
```

性能损失大（QPS 降到几千），但绝对不丢。

### 6.4 大实例（>10GB）

- 关闭 THP（透明大页）：`echo never > /sys/kernel/mm/transparent_hugepage/enabled`
  - 否则 fork 后 COW 会以 2MB 粒度复制，写放大严重
- 单实例不要 >32GB：fork 太慢，建议拆分集群
- 关闭 swap，避免 fsync 卡住

## 七、面试高频追问

### Q1：fork 阻塞主线程吗？

`fork()` 系统调用本身**会短暂阻塞**（内存越大越久）。
但 fork 完成后，子进程独立工作，主进程不阻塞。
监控 `latest_fork_usec`，超过 200ms 就要预警。

### Q2：COW 怎么保证子进程看到的是"快照那一刻"的数据？

fork 后父子进程共享物理内存页，所有页标记为**只读**。
谁要写：
- **父进程改**：触发缺页中断，内核复制此页给父进程，父进程改的是副本
- **子进程不修改数据**（只读取序列化）

所以子进程看到的永远是 fork 那一刻的状态。

### Q3：AOF 文件越来越大怎么办？

触发**重写（rewrite）**：fork 子进程，根据当前内存生成最小化命令集，替换旧 AOF。
默认配置：比上次重写大一倍且 >64MB 自动触发。

### Q4：AOF 重写期间，新写入的命令去哪了？

写入两个地方：
1. **当前 AOF 文件**：保证重写失败也能恢复
2. **AOF rewrite buffer**：等子进程写完新文件后追加进去

子进程写完 → 主进程把 buffer 追加到新文件 → 替换旧文件。

### Q5：RDB 和 AOF 同时开启，重启时用哪个？

**优先 AOF**（更新更快、数据更全）。
只有 AOF 不存在时才用 RDB。

### Q6：appendfsync everysec 真的只丢 1 秒吗？

**不一定**。`fsync` 调用本身可能因磁盘繁忙阻塞。极端情况下（磁盘 IO 100%）：
- everysec 可能退化为 30 秒级
- 主线程被 fsync 拖累，QPS 暴跌

**生产监控**：fsync 耗时（`aof_delayed_fsync` 计数器）。

### Q7：怎么对线上 Redis 做无损重启？

1. 先 BGSAVE 生成 RDB（or 等 AOF rewrite 完）
2. 复制 dump.rdb / appendonly.aof
3. 优雅 shutdown（`SHUTDOWN`，会自动持久化）
4. 启动新实例
5. 监控启动日志，确认数据加载成功

**或者**：用 Redis 主从切换，避免重启主节点。

### Q8：内存用满了，持久化还有用吗？

持久化的是"已经在内存里的数据"。内存满了后：
- `noeviction` 策略：写入直接报错，不写 AOF
- 其他策略：触发淘汰，淘汰命令也会写 AOF（DEL）

→ 持久化机制不影响内存淘汰，二者独立。

### Q9：主从架构下，从库需要持久化吗？

可以关掉，由主库负责。
**但要小心**：从库重启时无持久化数据 → 触发全量同步 → 主库 fork 阻塞。
**最佳实践**：从库也开 RDB，避免重启时拖主库。

### Q10：RDB 文件损坏怎么办？

- `redis-check-rdb dump.rdb`：检查文件
- 修复：通常无法修复，只能丢失数据
- **预防**：开启 `rdbchecksum yes`（默认开），写入时校验
- **实战**：多备份 RDB（异地、云存储）

### Q11：持久化对性能影响多大？

| 操作 | 影响 |
| --- | --- |
| BGSAVE fork | 几十 ms ~ 几百 ms 的阻塞 |
| RDB 写盘期间 | CPU + 磁盘 IO 占用，主线程 QPS 略降 |
| AOF everysec | QPS 降 5-10% |
| AOF always | QPS 降 50% 以上 |
| AOF 重写 | 类似 BGSAVE，fork 阻塞 + IO 抢占 |

### Q12：Redis 4.0 之前怎么持久化？

只有纯 RDB 或纯 AOF（or 同时开两个）。混合持久化是 4.0 新增的。

## 八、生产真实踩坑

### Case 1：fork 阻塞导致雪崩

实例内存 16GB，BGSAVE 触发时 fork 阻塞 800ms，期间所有请求超时返回 → 上游服务雪崩。
**修复**：
1. 拆分集群，单实例控制在 4-8GB
2. 关闭 THP（`/sys/kernel/mm/transparent_hugepage/enabled = never`）
3. 用 SSD（机械盘 fork 更慢）

### Case 2：写入压力大时 COW 内存翻倍

8GB 实例在大促期间 BGSAVE，COW 触发大量页复制，物理内存从 8GB 涨到 14GB → OOM Killer 把 Redis 杀了。
**修复**：
1. 服务器内存预留 50%（8GB 实例放 16GB 机器）
2. 大促前手动触发一次 BGSAVE，避免运行时触发
3. 监控 `mem_fragmentation_ratio` 和 RSS

### Case 3：appendfsync always 拖垮性能

误用 always，QPS 从 5 万降到 3 千 → 业务超时。
**修复**：改回 everysec。always 只在金融级用。

### Case 4：AOF 重写期间磁盘 IO 100%

机械盘 + 大 AOF，重写期间 fsync 卡住 → 主线程响应延迟暴涨。
**修复**：
- 加 `no-appendfsync-on-rewrite yes`：重写期间不 fsync 主 AOF（牺牲 1-2 秒数据换性能）
- 用 SSD

### Case 5：RDB 文件被压缩工具破坏

运维定期把老 dump.rdb 压成 zip 归档，误把当前 dump.rdb 也压了 → Redis 读不到数据。
**修复**：rdb 文件目录单独隔离，禁止运维脚本动。

### Case 6：从库持久化关掉，重启全量同步拖死主库

从库为了性能关了所有持久化 → 重启后 dataset 空 → 触发全量同步 → 主库 BGSAVE 阻塞 → 业务卡顿。
**修复**：从库也开 RDB（不开 AOF 也行）。

### Case 7：磁盘满导致 AOF 写入失败

磁盘满后 AOF 写入失败，Redis 进入只读模式。
**修复**：
- 监控磁盘使用率，>80% 告警
- 单独磁盘卷给 Redis，不和应用日志混用

## 九、答题模板（60 秒话术）

> 答 Redis 持久化先反问场景——**纯缓存可以不开持久化**，作为存储才必须开。
>
> **RDB** 是周期快照、二进制紧凑、恢复快，但**会丢两次快照间的数据**；BGSAVE 用 fork + COW 不阻塞主线程，但 fork 本身有微秒级停顿。
>
> **AOF** 是命令日志，三种 fsync 策略（always / everysec / no），everysec 是默认平衡点；AOF 重写也用 fork + COW 把当前数据集压缩成最小命令集。
>
> **4.0+ 推荐混合持久化**——RDB 头 + 增量 AOF 尾，恢复快又少丢。
>
> 生产配置默认 everysec + 混合持久化；监控 `latest_fork_usec`、`aof_delayed_fsync`、`rdb_bgsave_in_progress`；运维上**关闭 THP、禁用 swap、上 SSD**，可让副本承担持久化压力。
