# Redis 主从一致性

> 中高频面试题。
> 回答的关键是讲清 **三件事**：复制的协议（PSYNC）、全量与增量同步的切换条件、主从延迟带来的一致性问题与生产应对。

---

## 一、为什么要主从

| 目的 | 说明 |
| --- | --- |
| **读写分离** | 主写从读，扩展读 QPS |
| **数据冗余** | 主挂了从顶上 |
| **故障转移** | 配合哨兵/Cluster 实现高可用 |
| **数据备份** | 在从库上做 RDB，避免影响主库性能 |

> Redis 主从是**异步复制**，所以**必然不是强一致**——这是一切讨论的起点。

---

## 二、复制流程总览

```
┌─────────┐                   ┌─────────┐
│ Slave   │ ──── PSYNC ────→  │ Master  │
└─────────┘                   └─────────┘
     │                              │
     │                              │ ① 判断全量 or 增量
     │                              │
     │  ←─── FULLRESYNC / CONTINUE ─┤
     │                              │
     │                              │ ② 全量：BGSAVE → RDB → 传输
     │                              │
     │  ←─────── RDB 文件 ──────────┤
     │                              │
     │                              │ ③ 增量：积压缓冲区中的命令
     │                              │
     │  ←─────── 命令流 ────────────┤
     │                              │
     │  （持续接收命令，应用到本地）  │
     │                              │
```

## 三、PSYNC 协议（2.8+）

### 3.1 三个关键概念

| 概念 | 含义 |
| --- | --- |
| `runid` / `replid` | 主库的运行 ID，每次重启变化 |
| `offset` | 主从复制的字节偏移量（命令流的累计字节数） |
| `repl_backlog` | 主库的"积压缓冲区"，环形数组，默认 1MB |

### 3.2 全量同步 vs 增量同步的判断逻辑

从库连上主库，发 `PSYNC ${replid} ${offset}`：

```
if replid != 主库当前 replid:
    return FULLRESYNC                  # 主库不认识这个从库（首次或主切换）
elif offset 在 repl_backlog 范围内:
    return CONTINUE + 增量命令         # 增量同步
else:
    return FULLRESYNC                  # 偏移量太老，缓冲区没了
```

### 3.3 全量同步流程

```
1. 主库收到 FULLRESYNC，向从库发送 replid + offset
2. 主库 BGSAVE 生成 RDB 快照（fork 子进程）
3. 此时主库收到的新写命令缓存到 replication buffer
4. RDB 完成 → 通过 socket 传给从库
5. 从库清空旧数据，加载 RDB
6. 主库把 replication buffer 中的命令发给从库
7. 从库追赶到最新状态
8. 之后进入"持续命令同步"阶段
```

**全量同步的代价**：
- 主库 fork（短暂阻塞）
- 网络传输大量数据
- 从库重启阻塞（清数据 + 加载 RDB）

→ **要尽量避免触发全量同步**。

### 3.4 增量同步

主库的写命令一边发给客户端响应，一边：
1. 写入 `repl_backlog`（环形缓冲区）
2. 同时通过 socket 异步发给所有从库

从库重连时，根据 offset 在 backlog 里找到断点之后的命令，从那里继续。

### 3.5 repl_backlog 的容量

```ini
repl-backlog-size 1mb         # 默认 1MB，太小！
```

**建议**：`repl-backlog-size = 网络断开最长时间 × 主库写入速率`
- 主库写入 10MB/s，期望容忍 60 秒断网 → 600MB
- 1MB 默认值在线上几乎一断就触发全量同步

## 四、复制的几种细节场景

### 4.1 第一次连接

从库刚启动，没有任何数据 → 直接全量同步。

### 4.2 短暂断网

从库重连发 PSYNC，offset 在 backlog 里 → 增量同步，秒级追上。

### 4.3 长时间断网

backlog 已经被新写入覆盖（环形覆盖）→ 全量同步。

### 4.4 主库重启

主库 `replid` 变了 → 从库根本不认识 → 全量同步。

> 这就是为什么"主库重启"代价巨大：所有从库都要全量同步。

### 4.5 主库故障切换

哨兵把某个从库升为主库：
- 新主库的 `replid` 是新的
- 旧从库挂上新主库 → 全量同步

Redis 4.0+ 引入 `replid2`：从库升主时记住旧 replid，老的从库可以增量。

### 4.6 从库的从库（级联复制）

```
Master ──→ Slave1 ──→ Slave2
```

减轻主库负担，但增加延迟和故障路径。一般不推荐，复杂度大。

## 五、主从延迟带来的一致性问题

### 5.1 异步复制的窗口

```
T1: 客户端 A 写 master：SET k v1
T2: master 返回 OK
T3: 客户端 B 读 slave：GET k → 旧值！
T4: master 把 v1 同步给 slave
T5: 客户端 B 再读 slave：GET k → v1
```

**T2 ~ T4 之间，master 和 slave 不一致**。
延迟取决于：网络延迟 + slave 处理速度，正常 ms 级，糟糕情况秒级。

### 5.2 写后立即读问题

经典场景：
- 用户改头像 → 写主库
- 跳转个人主页 → 读从库（还没同步）
- 用户看到旧头像 → 投诉

**解决方案**（详见 [双写一致性](./双写一致性.md)）：
1. **写后强读主**：写完后 N 秒内读主库
2. **同步等待**：`WAIT 1 100`（等至少 1 个从库同步，超时 100ms）
3. **业务可接受短暂不一致**：大多数场景这样

### 5.3 WAIT 命令

```bash
SET k v
WAIT 2 1000      # 等至少 2 个从库收到，最多等 1000ms
```

**返回**：实际收到的从库数量。可以做"半同步"语义。
**注意**：仍不是强一致——WAIT 只保证收到，不保证应用成功；超时也不会回滚主库写入。

### 5.4 监控延迟

```bash
INFO replication
```

关键字段：
- `master_repl_offset`：主库当前 offset
- `slave_repl_offset`：从库 offset（在主库的视角）
- `lag`：从库距上次心跳秒数

`master_repl_offset - slave_repl_offset` 就是积压未同步的字节数。

## 六、复制时的过期处理

详见 [过期策略](./过期策略.md)。

| 角色 | 过期处理 |
| --- | --- |
| 主库 | 惰性 + 定期，过期时显式发 `DEL` 给从库 |
| 从库 | **不主动过期**，等主库 DEL |

3.2 之前从库读过期 key 返回旧值；3.2+ 修复成返回 nil（但仍不主动 DEL）。

## 七、和持久化的关系

| 场景 | 行为 |
| --- | --- |
| 主库无持久化 + 从库有持久化 | **危险**！主库重启数据为空 → 同步给从库 → 从库也清空 |
| 主库有持久化 + 从库无持久化 | 从库重启全量同步（拖累主库） |
| 主从都有持久化 | 推荐 |

**生产建议**：
- 主库开 RDB + AOF 混合
- 从库至少开 RDB（避免重启拖主库 fork）
- 关闭从库 AOF 可减少 IO 压力

---

## 八、主从复制的一致性级别（CAP 视角）

| 级别 | 实现 | 代价 |
| --- | --- | --- |
| 异步复制（默认） | AP | 主挂可能丢数据 |
| 半同步（WAIT） | 折中 | 性能略降 |
| 完全同步 | 不支持 | 不实际 |

> Redis 永远是 **AP**：保可用性，不保强一致。要 CP 用 ZooKeeper / etcd。

## 九、面试高频追问

### Q1：主从复制是同步还是异步？

**异步**。主库写完立刻返回客户端，再异步推给从库。
副作用：主挂时可能丢失"已 ack 但未同步"的数据（几 ms 量级）。
半同步可用 `WAIT` 命令做。

### Q2：为什么从库不主动过期 key？

避免主从过期时间不一致导致数据不一致。统一由主库控制：主库过期后发 DEL 同步给从库。

### Q3：如何避免触发全量同步？

- **加大 repl_backlog_size**（关键！默认 1MB 太小）
- **避免主库重启**（重启 replid 变，所有从库全量）
- **网络稳定**（避免长时间断网）
- **避免主从切换太频繁**

### Q4：主库重启会导致全量同步吗？

会。主库 replid 变了，从库不认识，必然全量。
**避免方法**：
- 从库提前接管：先把某个从库切成主，再修复原主库（运维操作）
- 4.0+ 的 replid2 机制可缓解：从库记住前任主库的 replid，新主库延续旧 replid 一段时间

### Q5：怎么读到最新的数据？

- 直接读主库（牺牲读 QPS）
- 关键写后强制读主一段时间
- 用 `WAIT` 半同步
- 业务层加版本号 / 时间戳，过期时间窗口内读主

### Q6：从库可以直接写吗？

默认不行（只读模式 `slave-read-only yes`）。
理论可写但**强烈不建议**：写入会被主库的同步流覆盖，数据丢失。

### Q7：主从延迟很大怎么办？

排查：
1. 主库 QPS 突增？查看慢命令
2. 网络带宽够？跨机房复制特别注意
3. 从库性能瓶颈？`top` 看 CPU、磁盘
4. 大 key 同步？单个大 key 序列化慢

应对：
- 优化主库写入（分流、限流）
- 升级网络（万兆）
- 拆分集群

### Q8：哨兵和主从复制的关系？

主从复制提供"数据冗余"，哨兵提供"自动故障转移"。
没有哨兵：主库挂了要人工介入切主。
有哨兵：自动选举新主，从库重连新主。

### Q9：Cluster 模式下主从怎么工作？

每个分片（slot 范围）有一个主 + N 个从，主从内部就是 PSYNC 复制。
分片之间不复制（数据按 slot 分布）。
故障转移由 Cluster 自己负责（gossip 协议 + 投票），不需要哨兵。

### Q10：repl_backlog_size 设多大合适？

```
repl_backlog_size = 主库平均写入速率（MB/s） × 期望容忍断网时间（秒）
```

例：主库 5MB/s，要能容忍 60s 断网 → 300MB。

监控：`INFO replication` 里 `repl_backlog_active`、连续观察增量同步率。

### Q11：能否一主多从同时工作？

可以。一主可以挂任意多个从（实际部署 1-3 个）。
所有从库通过同一份 PSYNC 流程同步，主库写一次，并行推送给所有从库。
代价：主库带宽 = 写入速率 × 从库数。

### Q12：主从切换时会丢数据吗？

会。异步复制必然有丢失：
- 已写主库但未同步给从库的数据，在主挂后会丢
- 哨兵选新主时优先选 offset 最大的，但不保证就是最新

→ 关键写要 `WAIT` 等同步确认，或上 ZK。

## 十、生产真实踩坑

### Case 1：主库重启数据全空

主库无持久化（误以为有从库就够），重启后空数据 → 同步给从库 → **从库数据也被清空** → 整个集群挂。
**修复**：主库必须开持久化。从库重启不会传播，但主库重启会。

### Case 2：repl_backlog 太小，频繁全量

默认 1MB，一断网 30s 就全量。每次全量 fork 阻塞 + 网络传输 + 从库重载，业务受影响。
**修复**：调到 100MB+，根据写入速率算。

### Case 3：从库慢导致积压

从库性能差（CPU 满 / 网络慢），跟不上主库写入 → backlog 在主库爆 → 触发断连 → 重新连接全量同步。
**修复**：
- 升级从库硬件
- 监控 `master_repl_offset - slave_repl_offset`，差值持续增大就告警
- 不要在从库上跑高消耗任务（如 BGREWRITEAOF）

### Case 4：写后读不到最新值

用户支付完跳转订单详情页，读从库还没同步 → "订单不存在"。
**修复**：支付完后的关键页面读主库（业务标记 + 中间件路由）。

### Case 5：跨机房主从复制延迟

主库北京，从库上海，网络抖动 → 延迟到秒级 → 从库读旧数据。
**修复**：
- 同机房主从，跨机房用 Cluster
- 跨机房的从库只做备份，不接读流量

### Case 6：从库被升主，老主库回来后数据冲突

哨兵把 slave A 升主，老主库恢复后变成 slave，发现自己的 replid 已被取代 → 全量同步，**自己原有的写入丢失**。
**修复**：
- 接受丢失（异步复制的代价）
- 关键场景关掉自动故障切换，人工介入
- 上 Cluster + 业务幂等

### Case 7：误开 slave-read-only no

从库可写之后，业务误写从库 → 后来主库同步过来覆盖 → 数据不一致或丢失。
**修复**：保持 `slave-read-only yes`，写都走主库。

## 十一、答题模板（60 秒话术）

> Redis 主从是**异步复制**，必然是 AP 不是 CP——要强一致用 ZooKeeper 而不是 Redis。
>
> 复制协议是 **PSYNC**：主从用 replid + offset 标识同步状态，主库判断走全量还是增量。**全量同步**走 BGSAVE → RDB → 网络传输 → 从库 flush 后加载——代价大，要尽量避免。**增量同步**靠主库写 repl_backlog 环形缓冲，从库断网在 backlog 窗口内可走增量——所以 `repl_backlog_size` 默认 1MB 太小，**生产改 100MB+**。
>
> **主从延迟**问题用三招：写后立即读走主库、用 WAIT 命令等指定数量从库 ack（半同步）、或业务容忍最终一致。
>
> 关键配置：repl_backlog_size 加大、从库开持久化分担主库压力、保持 read-only 防误写。**故障切换**由哨兵或 Cluster 自动选主，**会丢失主库还没同步给新主的事务**——这是异步复制的固有代价。
