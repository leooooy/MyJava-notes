# Redis 工作流程

> 高频面试题。"Redis 单线程怎么扛住高并发"几乎每场都问。
> 答得好的关键：能讲清 **epoll 的本质**、**Reactor 模式**、**6.0 多线程到底改了什么**。
> 不要只背"基于内存所以快"——这是初级答案。

---

## 一、Redis 为什么这么快（综合答案）

四个层次，由表及里：

| 因素 | 说明 |
| --- | --- |
| **1. 全内存操作** | 数据在内存，纳秒级访问，比磁盘快 5-6 个数量级 |
| **2. 高效数据结构** | SDS、跳表、压缩列表、整数集合……针对不同场景定制 |
| **3. 单线程 + 无锁** | 没有锁竞争、没有 CPU 上下文切换、没有死锁 |
| **4. IO 多路复用** | 单线程同时监听海量连接，避免每连接一线程的开销 |

**核心**：3 + 4 是关键。前两条很多内存数据库都做到了，**第 3、4 条才是 Redis 的灵魂**。

## 二、网络模型：Reactor + IO 多路复用

### 2.1 Reactor 模式

```
        ┌─────────────┐
        │  Client 1   │──┐
        └─────────────┘  │
        ┌─────────────┐  │     ┌──────────────┐
        │  Client 2   │──┼───→ │ IO 多路复用器  │ (epoll)
        └─────────────┘  │     └──────┬───────┘
        ┌─────────────┐  │            │
        │  Client N   │──┘            ▼
        └─────────────┘        ┌──────────────┐
                               │ 文件事件分派器 │
                               └──────┬───────┘
                                      │
                  ┌───────────────────┼───────────────────┐
                  ▼                   ▼                   ▼
          ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
          │ 连接应答处理器 │  │ 命令请求处理器 │  │ 命令回复处理器 │
          └──────────────┘  └──────────────┘  └──────────────┘
```

**4 个组件**：
1. **多个 Socket**：每个客户端一个连接
2. **IO 多路复用程序**：一个线程同时监听所有 Socket（核心是 epoll）
3. **文件事件分派器**：按事件类型路由到对应处理器
4. **事件处理器**：连接应答、命令请求、命令回复 3 种

### 2.2 IO 多路复用：select / poll / epoll

#### 演进路径

| 函数 | 时间复杂度 | 上限连接数 | 触发方式 | 缺点 |
| --- | --- | --- | --- | --- |
| `select` | O(n) | 1024 | 每次都要把 fd 集合从用户态拷贝到内核态 | 上限低 |
| `poll` | O(n) | 无硬上限 | 同 select 但用链表 | 仍然 O(n) 扫描 |
| **`epoll`** | **O(1)** | 数十万 | 内核回调 + 就绪队列 | **Linux 主流** |

#### epoll 的核心优势

```
1. epoll_create：内核创建 epoll 实例（含红黑树 + 就绪链表）
2. epoll_ctl：注册 fd 到红黑树（注册一次即可，不像 select 每次都要传全集）
3. epoll_wait：阻塞等待事件
   - fd 上有事件 → 内核把这个 fd 加入就绪链表
   - 用户态只拿到"有事件的 fd"列表，不用扫描全部
```

**关键点**：
- **注册一次，多次复用**：避免 select 每次系统调用都要拷贝 fd 集合
- **回调式**：内核主动通知就绪 fd，不是用户态轮询
- **O(1) 复杂度**：处理 10 万连接和 100 个连接性能几乎一样

#### 触发模式

| 模式 | 含义 | Redis 用哪个 |
| --- | --- | --- |
| **LT（水平触发）** | 只要 fd 上还有数据可读，就一直通知 | ✓ 默认 |
| **ET（边缘触发）** | 仅在状态变化时通知一次，必须一次性读完 | 编程难 |

Redis 用 LT：编程简单，每次只读一部分也行。

### 2.3 多平台适配

Redis 抽象了一层 ae（async event）库，根据系统选择最优 IO 多路复用：

```c
// ae.c
#ifdef HAVE_EVPORT
#include "ae_evport.c"   // Solaris
#else
    #ifdef HAVE_EPOLL
    #include "ae_epoll.c"   // Linux ★ 主流
    #else
        #ifdef HAVE_KQUEUE
        #include "ae_kqueue.c"  // macOS / FreeBSD
        #else
        #include "ae_select.c"  // 兜底
        #endif
    #endif
#endif
```

## 三、命令执行流程

### 3.1 单条命令的完整生命周期

```
1. 客户端 → TCP 连接 → Redis Server（连接应答处理器，accept）
2. 客户端发命令 → epoll 通知 → 命令请求处理器
3. Redis 解析 RESP 协议 → 拿到命令名和参数
4. 查找命令表（dict 结构）→ 拿到命令实现函数
5. 检查权限（ACL）、检查参数数量
6. 执行命令（操作内存数据结构）★ 单线程串行
7. 把结果写入客户端的输出缓冲区
8. epoll 监听到 socket 可写 → 命令回复处理器写回客户端
```

### 3.2 串行执行的含义

```
[T1] 客户端 A: SET k1 v1
[T2] 客户端 B: SET k2 v2
[T3] 客户端 C: GET k1

→ 全部进入"命令队列"
→ 主线程依次执行：A → B → C
→ 不会有两条命令"同时"执行
```

**含义**：
- **天然原子**：单条命令 + Lua 脚本都是原子的
- **不需要锁**：没有竞争
- **慢命令会卡所有人**：一个 `KEYS *` 扫 10 秒，所有客户端都阻塞

## 四、为什么 Redis 选择单线程

### 4.1 官方理由（antirez）

> CPU is not the bottleneck of Redis. The bottleneck is memory and network.

**翻译**：
- Redis 操作的是内存，单核 CPU 已经能跑出 10 万+ QPS
- 瓶颈是网卡带宽和内存大小
- 多核加 CPU 也不会让单实例更快

### 4.2 单线程的优势

1. **代码简单**：没有多线程并发问题
2. **没有锁开销**：避免互斥锁/读写锁的成本
3. **没有上下文切换**：CPU 不浪费在调度
4. **天然原子性**：所有命令串行执行
5. **可维护性强**：调试简单，bug 可复现

### 4.3 单线程的代价

- **慢命令会阻塞所有客户端**：必须避免 `KEYS *`、大 key 操作、复杂 Lua
- **多核 CPU 利用率低**：单实例只用一个核
- **解决方案**：单机部署多实例（端口隔离）+ Cluster 分片

## 五、Redis 6.0 多线程

### 5.1 为什么 6.0 引入多线程

随着网卡到 10Gbps、25Gbps，**网络 IO 成了瓶颈**：
- 解析 RESP 协议、读写 socket 的 CPU 占了相当比重
- 单线程做这些事限制了 QPS 上限

### 5.2 改了什么（关键澄清）

**只是网络 IO 多线程化**——核心命令执行仍然是单线程。

```
┌─────────────────────────────────────────┐
│       6.0+ 多线程模式                    │
│                                         │
│  IO 线程池 ──┐                          │
│   - 读 socket          主线程            │
│   - 解析协议  ──→   (单线程)            │
│                      执行命令            │
│  IO 线程池 ──┐                          │
│   - 写 socket  ←──   返回结果            │
│   - 序列化协议                           │
└─────────────────────────────────────────┘
```

**保留单线程的部分**：
- 命令实际执行（操作数据结构）
- 数据访问（SET、GET、LPUSH...）

→ 因为命令执行还是要串行，避免锁。

### 5.3 配置

```ini
io-threads 4                  # IO 线程数（含主线程，所以是 1 个主 + 3 个 IO）
io-threads-do-reads yes       # 读也开多线程（默认 no，只有写多线程）
```

**官方建议**：
- 4 核机器 → 2-3 个 IO 线程
- 8 核机器 → 6 个 IO 线程
- 不超过 8 个，否则收益边际下降

### 5.4 性能提升

实测：
- 写多线程：QPS 提升 ~50%
- 读+写多线程：QPS 提升 ~80-100%

适合**网络 IO 密集**场景（短连接多、value 大）。

### 5.5 是否要开

| 场景 | 建议 |
| --- | --- |
| 高 QPS（>10 万）且 CPU 用满 | 开 |
| 大 value（如缓存大对象） | 开 |
| 长连接、命令简单（如 GET/SET 短 key） | 开不开都行 |
| 集群已经分片，单实例压力不大 | 不开 |

## 六、慢命令排查（必备技能）

### 6.1 慢日志

```bash
CONFIG SET slowlog-log-slower-than 10000   # 10ms 以上算慢
CONFIG SET slowlog-max-len 128

SLOWLOG GET 10                               # 看最近 10 条
SLOWLOG RESET                                # 清空
```

### 6.2 常见慢命令黑名单

| 命令 | 风险 | 替代 |
| --- | --- | --- |
| `KEYS *` | O(n) 扫全库 | `SCAN` 渐进式 |
| `SMEMBERS / HGETALL`（大集合） | 一次返回全部 | `SSCAN / HSCAN` |
| `SORT`（大列表） | O(n log n) | 业务层排序 |
| `DEL`（大 key） | 阻塞主线程 | `UNLINK` 异步删除 |
| `FLUSHALL / FLUSHDB` | 阻塞 | `FLUSHALL ASYNC` |
| 大 key 的过期 | 同步删除阻塞 | 拆分大 key |
| 复杂 Lua | 长时间占用主线程 | 拆解为多个命令 |

### 6.3 大 key 治理

```bash
redis-cli --bigkeys              # 扫描大 key
MEMORY USAGE keyname             # 查看 key 占用
```

**判断标准**：
- String value > 10KB
- List/Hash/Set/ZSet 元素 > 10000

**治理**：
- 拆分（按业务维度散列到多个 key）
- 异步删除（`UNLINK`）
- 过期时间错开

## 七、面试高频追问

### Q1：Redis 真的是单线程吗？

**精确说**：
- **6.0 之前**：网络 + 命令执行都是单线程（除了持久化、AOF rewrite 等子进程）
- **6.0+**：网络 IO 可多线程，**命令执行仍是单线程**

所以"Redis 是单线程"这个说法不严谨，应该说"**Redis 命令执行是单线程**"。

### Q2：单线程怎么处理 10 万并发连接？

靠 **IO 多路复用（epoll）**：
- 一个线程通过 epoll 同时监听 10 万 socket
- epoll_wait 只返回有事件的 fd（O(1)）
- 主线程遍历就绪 fd，依次处理

→ 不是"同时"处理 10 万请求，而是"快速轮询" + "事件触发"。

### Q3：epoll 的 LT 和 ET 有什么区别？Redis 用哪个？

- **LT（水平触发）**：只要 fd 缓冲区有数据，每次 `epoll_wait` 都通知。读多少都行。
- **ET（边缘触发）**：仅在数据"到达"那一刻通知一次。必须一次读完，否则丢事件。

Redis 用 **LT**，编程简单容错性好。Nginx 用 ET 追求极致性能。

### Q4：select / poll / epoll 区别？

- **select**：1024 上限，每次拷贝 fd 全集到内核，O(n) 扫描
- **poll**：无硬上限，但仍 O(n)
- **epoll**：O(1)，注册一次复用，回调式通知

epoll 是 Linux 特有，macOS 用 kqueue（思路相同）。

### Q5：6.0 多线程改了哪部分？为什么命令执行还是单线程？

**改的部分**：socket 读写 + RESP 协议解析/序列化 → 多线程
**没改**：命令实际执行 → 单线程

原因：
- 命令执行涉及内存数据结构，多线程要加锁，复杂度暴涨
- 网络 IO 才是瓶颈，改这部分收益最大
- 保持核心单线程，向下兼容简单

### Q6：有没有可能让命令执行也多线程？

理论可以，但代价巨大：
- 每个数据结构要加锁（SDS、dict、跳表）
- 复杂命令（如 SUNIONSTORE）涉及多个 key，要分布式加锁
- 性能可能反而下降（锁开销）

→ 工程上得不偿失。如果真要多核，**部署多个实例 + 集群分片**更优。

### Q7：单线程下慢命令怎么办？

避免：
- `KEYS *` → `SCAN`
- 大 key 的全量操作 → 拆分或用 `*SCAN`
- 大 key DEL → `UNLINK`
- 复杂 Lua → 拆解
- `CLIENT KILL ADDR`：kill 慢客户端

监控：`SLOWLOG`、`MONITOR`（生产慎用，影响性能）

### Q8：Redis 为什么不用阻塞 IO？

阻塞 IO 模型下，每个连接一个线程。10 万连接 = 10 万线程：
- 内存爆（每线程 1MB 栈）
- 上下文切换开销巨大
- 大部分线程都在 idle

非阻塞 IO + epoll = 一个线程管所有连接，效率提升数量级。

### Q9：MONITOR 命令对性能影响多大？

影响巨大。MONITOR 把所有命令实时返回客户端：
- Redis 主线程要把每条命令塞到 MONITOR 客户端的输出缓冲区
- 高 QPS 下，主线程被拖慢
- 内存暴涨（缓冲区堆积）

**生产严禁开 MONITOR**，调试也只在测试环境用。

### Q10：Redis 处理一条命令耗时多少？

简单命令（GET / SET 小 key）：~微秒级（几 μs）
复杂命令（ZADD 到大 ZSet）：~10 μs~ms 级
大 key 操作：~ms~秒级

主线程理论上限 QPS：10 万~20 万。

### Q11：Redis 为什么不用协程？

历史原因 + 理念坚持：
- 单线程 + epoll 已经够快
- 协程会引入新的复杂度（用户态调度、栈管理）
- 命令执行的串行性如果靠协程也要重新设计

KeyDB（Redis 衍生品）走了多线程路线，但 Redis 核心团队选择保守演进。

### Q12：单实例 Redis 性能极限是多少？

- 简单命令（GET / SET）：10-15 万 QPS（单线程，6.0 多线程可达 20-30 万）
- 复杂命令：1-5 万
- 网卡是瓶颈：万兆网卡 + value 1KB → 理论 100 万 QPS

要更高 QPS：**Cluster 分片**，每个分片承担一部分流量。

## 八、生产真实踩坑

### Case 1：KEYS * 卡死生产

运维同学一时手快，在 1 亿 key 的实例上 `KEYS user:*` → 阻塞 30 秒 → 业务超时雪崩。
**修复**：
- 永久禁用：`rename-command KEYS ""`
- 用 `SCAN` 渐进式遍历

### Case 2：DEL 大 key 阻塞

删除一个 500MB 的大 List → 主线程阻塞 1 秒 → 上游业务超时。
**修复**：用 `UNLINK`（4.0+），异步删除。或先 `LTRIM` 到 0 长度再 DEL。

### Case 3：大 Lua 脚本卡主线程

一段 Lua 在大 ZSet 上做复杂计算，单次执行 200ms → 期间所有命令排队 → 业务超时。
**修复**：拆解逻辑到客户端，Lua 只做原子小操作。

### Case 4：MONITOR 没退出

调试用 `MONITOR` 后没退出客户端，输出缓冲区一直在增长，Redis 主线程被拖慢 30%。
**修复**：用 `CLIENT LIST` 查找，`CLIENT KILL` 干掉。

### Case 5：HGETALL 大 Hash 拖慢

某用户行为日志写到一个 Hash 里，长到 100 万字段，HGETALL 一次返回 200MB → 网络 + 主线程双卡。
**修复**：HSCAN 分批拉取；或拆 Hash。

### Case 6：6.0 多线程开了反而慢

8 核机器开了 7 个 IO 线程，但实际 QPS 不高 → 线程竞争锁，性能反而降。
**修复**：根据实际 QPS 调整，QPS < 5 万的实例不开多线程。

## 九、答题模板（60 秒话术）

> 先澄清概念：Redis **6.0 之前完全单线程，6.0 后网络 IO 多线程，但命令执行始终单线程**。
>
> 快的根本原因有四：**纯内存操作**、**高效数据结构**（SDS / 跳表 / ziplist 等）、**单线程无锁**省去切换和竞争开销、**IO 多路复用**（epoll 一次系统调用监听海量连接，Reactor 模式分派事件）。
>
> 代价是慢命令（KEYS、HGETALL 大 Hash）和大 key 会阻塞所有客户端。
>
> **6.0 多线程**只解决网络 IO 这个瓶颈（解析/序列化协议），不改变命令执行的串行性——CPU 密集场景要更高吞吐还得靠 **Cluster 分片**或多实例部署。
