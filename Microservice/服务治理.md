# 服务治理（熔断 / 降级 / 重试 / 隔离 / 超时 / 兜底）

> 微服务的"高可用兜底体系"——P6+ 必考，跟 Sentinel 配合是国内最主流栈。
> 本篇要解决的问题：
> ① 限流 / 熔断 / 降级 三件事到底是什么关系？很多人混着说，面试一下就露馅
> ② 熔断的**三态状态机**怎么工作？阈值参数怎么调？
> ③ 重试为什么会引发**雪崩**？**指数退避 + Jitter** 怎么解决？
> ④ 线程池隔离 vs 信号量隔离怎么选？
> ⑤ Hystrix / Sentinel / Resilience4j / Istio 各自适合什么场景？
>
> 跟 [限流算法](./限流算法.md) 是孪生篇——限流是"主动拒绝部分请求"的算法层，本篇是"系统全栈高可用模式"的工程层。

---

## 一、为什么需要服务治理

### 1.1 没治理的雪崩

```
微服务调用链：A → B → C → D

D 突然抖动 → 响应从 10ms 变成 30s
   ↓
C 的线程池被 D 的慢请求打满
   ↓
B 的线程池被 C 的慢请求打满
   ↓
A 的线程池被 B 的慢请求打满
   ↓
整个调用链路所有服务全卡死 → 雪崩
```

**根因**：分布式系统里，**慢比挂更可怕**——挂的话快速 fail，慢的话占着资源不放。

### 1.2 服务治理的"七板斧"

| 模式 | 作用 | 典型工具 |
| --- | --- | --- |
| **限流** | 拒绝超过容量的请求 | Sentinel、Guava |
| **熔断** | 下游故障时快速失败，停止调用一段时间 | Sentinel、Hystrix |
| **降级** | 主流程失败时返回兜底数据 | Sentinel @Fallback |
| **重试** | 偶发失败自动重试 | Spring Retry、Resilience4j |
| **超时** | 限制单次调用最大耗时 | Feign timeout、HttpClient |
| **隔离** | 不同业务线程池 / 信号量隔离 | Hystrix 线程池、Sentinel 信号量 |
| **兜底** | 终极防线：缓存 / 默认值 / 静态页 | 业务代码 + CDN |

**口诀**：**限流防过载、熔断防级联、降级保体验、重试容偶发、超时控边界、隔离防扩散、兜底保最后**。

## 二、熔断（Circuit Breaker）

### 2.1 类比：家里的保险丝

```
正常：电流通过 → 家电工作
故障：短路（电流过大）→ 保险丝熔断 → 断电保护
修复：换上新保险丝 → 恢复供电
```

熔断器原理一样——**下游故障率高时主动断开调用，避免雪崩**。

### 2.2 三态状态机（必背）

```
                 失败率 > 阈值
            ┌─────────────────────┐
            │                     ▼
        [Closed]              [Open]
        正常调用              快速失败
            ▲                     │
            │                     │ 等待时间窗口（10s）
            │                     ▼
            └────成功率高────[Half-Open]
                              试探性放行
```

| 状态 | 行为 | 触发转移 |
| --- | --- | --- |
| **Closed**（关闭）| 正常调用，统计失败率 | 失败率超阈值 → Open |
| **Open**（打开）| 直接失败，不调用下游 | 等待时间窗口结束 → Half-Open |
| **Half-Open**（半开）| 放少量请求试探 | 成功率高 → Closed；失败率高 → Open |

**关键参数**：
- 统计窗口：通常 10s
- 触发熔断的最低请求数：< 20 个请求不熔断（避免少样本误判）
- 失败率阈值：50%
- Open 持续时间：10-30s
- Half-Open 试探数：5-10 个

### 2.3 Sentinel 三种熔断策略

```java
@SentinelResource(value = "createOrder",
                  fallback = "createOrderFallback")
public Order createOrder(...) {
    return remoteService.create(...);
}

public Order createOrderFallback(..., Throwable t) {
    return Order.empty();  // 降级返回
}
```

熔断规则三种：

| 策略 | 触发条件 | 适用 |
| --- | --- | --- |
| **慢调用比例** | RT > 阈值 的占比 > 阈值 | 下游响应变慢 |
| **异常比例** | 异常占比 > 阈值 | 下游报错率高 |
| **异常数** | 单位时间异常数 > 阈值 | 下游零星错误也想保护 |

### 2.4 熔断器框架对比

| 维度 | **Hystrix** | **Sentinel** | **Resilience4j** |
| --- | --- | --- | --- |
| 出品 | Netflix | 阿里 | 社区 |
| 维护 | **已停更**（2018） | 活跃 | 活跃 |
| 隔离方式 | 线程池 + 信号量 | **信号量**为主 | 信号量 |
| 限流 | ❌ | ✅（最强） | ✅ |
| 熔断 | ✅ | ✅ | ✅ |
| 控制台 | 简陋 | **强大** | 无 |
| 动态规则 | ❌ | ✅（接 Nacos） | 代码 API |
| 编程模型 | 命令模式 | 注解 + API | **函数式** |
| Java 8+ Lambda | ❌ | 部分 | ✅ |
| 国内主流 | 否 | **是** | 否 |

**结论**：
- 国内 Spring Cloud Alibaba 项目 → **Sentinel**
- 海外 / Spring Cloud 官方 → **Resilience4j**
- Hystrix 不要再用

## 三、降级（Fallback / Degradation）

### 3.1 两种降级

#### 业务降级

主动关闭非核心功能，保护核心流程：

```
双 11 大促时降级清单：
  ❌ 关闭：评价晒图功能（写多）
  ❌ 关闭：商品推荐（耗 CPU）
  ❌ 关闭：物流详情查询（依赖下游）
  ✅ 保留：下单、支付、库存
```

**实现方式**：配置中心动态开关。

```java
@Value("${biz.recommend.enable:true}")
private boolean recommendEnable;

public List<Product> getRecommendation(Long userId) {
    if (!recommendEnable) return Collections.emptyList();
    // 正常推荐逻辑
}
```

#### 系统降级（异常时）

调用下游失败 → 返回兜底数据：

```java
@SentinelResource(value = "getUserInfo", fallback = "userFallback")
public User getUserInfo(Long id) {
    return userClient.getUser(id);
}

public User userFallback(Long id, Throwable t) {
    // 兜底：从本地缓存取，或返回默认对象
    return localCache.getOrDefault(id, User.GUEST);
}
```

### 3.2 降级数据从哪来

| 来源 | 适用 |
| --- | --- |
| **本地缓存**（Caffeine） | 数据有缓存值 |
| **Redis 缓存** | 缓存还在但 DB 挂了 |
| **静态默认值** | 推荐列表返回热门商品 |
| **静态页 / CDN** | 商品详情页 |
| **空对象** | 列表查询返回空 |
| **历史快照** | 行情/数据类返回上次值 |

**原则**：**永远不要返回 null 和异常给用户**——前端处理不了。

### 3.3 降级的边界

降级**不是万能的**——要分清"可以降级"和"绝对不能降级"：

| 类型 | 能降级 |
| --- | --- |
| 商品推荐 | ✅（返回热门兜底） |
| 物流详情 | ✅（返回"运输中"） |
| 评价 | ✅（关闭写） |
| **支付** | ❌（必须强一致） |
| **库存扣减** | ❌（不能降到"假扣"） |
| **订单生成** | ❌（不能降到"先记录后处理"） |

## 四、重试（Retry）

### 4.1 重试的两面性

> 重试是把双刃剑——**用对救命，用错催命**。

#### 用对：消除偶发抖动

```
HTTP 请求 → 504 Gateway Timeout（偶发网络抖动）
   ↓ 重试一次
   → 200 OK
```

#### 用错：放大故障

```
下游已经挂了
   ↓ 1000 个请求都失败 → 每个重试 3 次
   ↓ 实际打到下游 = 4000 个请求 → 下游死得更彻底
   ↓ 雪崩
```

### 4.2 重试的三大铁律

#### 铁律 1：被重试的接口必须幂等

非幂等接口重试 → 重复扣款、重复下单 → 资金事故。
→ 详见 [幂等](../Distributed/幂等.md)

#### 铁律 2：用指数退避 + Jitter 防雪崩

朴素重试：失败立即重试 → 1000 个请求同时重试 → 风暴。

**指数退避**：每次重试间隔翻倍

```
第 1 次失败 → 等 100ms 重试
第 2 次失败 → 等 200ms 重试
第 3 次失败 → 等 400ms 重试
第 4 次失败 → 等 800ms 重试
```

**Jitter（抖动）**：在退避时间上加随机数，避免"所有重试同时发起"

```java
long delay = baseDelay * Math.pow(2, retryCount);
long jitter = ThreadLocalRandom.current().nextLong(delay / 2);
Thread.sleep(delay + jitter);
```

#### 铁律 3：限制重试上限

- 重试次数：3 次（最多 5 次）
- 总超时：5-10s
- 配合熔断：熔断打开期间不重试

### 4.3 重试的代码实现

#### Spring Retry

```java
@Retryable(value = {RemoteException.class},
           maxAttempts = 3,
           backoff = @Backoff(delay = 100, multiplier = 2, random = true))
public User fetchUser(Long id) {
    return userClient.getUser(id);
}

@Recover
public User recover(RemoteException e, Long id) {
    return User.GUEST;  // 重试全失败时兜底
}
```

#### Resilience4j

```java
RetryConfig config = RetryConfig.custom()
    .maxAttempts(3)
    .waitDuration(Duration.ofMillis(100))
    .intervalFunction(IntervalFunction.ofExponentialRandomBackoff())
    .retryOnException(e -> e instanceof RemoteException)
    .build();

Retry retry = Retry.of("userService", config);
Supplier<User> decorated = Retry.decorateSupplier(retry, () -> userClient.getUser(id));
User user = decorated.get();
```

### 4.4 重试和熔断的配合

```
[请求]
   ↓
[熔断器]──Open──→ 直接失败，不进入重试
   ↓ Closed
[重试器]──最多 3 次──→ 仍失败
   ↓
[熔断器统计]──失败计数++──→ 触发熔断 → 后续请求不再重试
```

**关键点**：**重试要被熔断器包住**——熔断打开后不再重试，避免在故障期间制造更多压力。

### 4.5 不能重试的场景

| 场景 | 不能重试的原因 |
| --- | --- |
| 非幂等接口（POST 创建） | 会重复创建 |
| 4xx 客户端错误 | 业务参数有问题，重试也是错 |
| 用户取消操作 | 没必要 |
| 已知下游不可用（熔断 Open） | 浪费资源 |
| 连接拒绝（明确 Connection refused） | 立即失败比等待好 |

## 五、超时（Timeout）

### 5.1 三层超时

```
[Client] ── ① 连接超时 ── [TCP 层]
            ② 读超时 ── 等响应
            ③ 全局超时 ── 整体不超过这么久

① Connect Timeout：建立 TCP 连接的最大时间（推荐 1-3s）
② Read Timeout：等待响应的最大时间（推荐 3-10s）
③ Total Timeout：整个调用包括重试（推荐 10-30s）
```

### 5.2 级联超时陷阱

```
A 调 B 设超时 5s
B 调 C 设超时 5s
C 调 D 设超时 5s

D 卡死 → C 等 5s → B 等了 C 的 5s 后还想自己继续等 5s → 但 A 已经把 B 超时了
```

**正确做法**：**超时要递减**——上游必须比下游短。

```
A → B：5s
B → C：3s（留 2s 给 A 处理）
C → D：1s（留 2s 给 B 处理）
```

### 5.3 各组件默认超时（生产值得改）

| 组件 | 默认超时 | 生产推荐 |
| --- | --- | --- |
| Feign | **1s**（太短） | 3-5s |
| Ribbon ConnectTimeout | 1s | 1-3s |
| Ribbon ReadTimeout | 1s | 3-10s |
| OkHttp connect | 10s | 1-3s |
| OkHttp read | 10s | 3-10s |
| Hystrix | 1s | 跟下游约定 |
| HikariCP connectionTimeout | 30s | 5-10s |
| Redis Lettuce | 10s | 1-3s |
| MyBatis defaultStatementTimeout | 无限 | **必须配**（5-10s） |

**血的教训**：MyBatis 不配 SQL 超时 → 慢 SQL 把数据库连接池占满 → 整服务 503。

## 六、隔离（Isolation）

### 6.1 为什么要隔离

不隔离的灾难：

```
[共用线程池 200 个]
   │
   ├─ 调用 A 服务（正常 10ms）
   ├─ 调用 B 服务（正常 50ms）
   └─ 调用 C 服务（突然抖动，30s 不返回）
   
C 占着 200 个线程不释放 → A 和 B 也卡死
```

### 6.2 两种隔离方式

#### 线程池隔离（Hystrix 主推）

每个下游服务一个独立线程池：

```
[A 线程池: 10]   [B 线程池: 20]   [C 线程池: 50]
     ↓                ↓                ↓
   调 A            调 B            调 C（出问题只占 50 个线程）
```

**优点**：
- ✅ 隔离彻底，C 卡死不影响 A、B
- ✅ 可以异步、可以加队列
- ✅ 可以为不同服务设不同优先级

**缺点**：
- ❌ 线程切换开销（每个请求多 ~1ms）
- ❌ 线程池数量爆炸（100 个下游 = 100 个线程池）
- ❌ ThreadLocal 失效（请求换线程，TraceId 丢失）

#### 信号量隔离（Sentinel 主推）

不切换线程，用计数器限制并发数：

```java
Semaphore semaphore = new Semaphore(50);  // 最多 50 个并发

if (semaphore.tryAcquire()) {
    try { return remoteCall(); }
    finally { semaphore.release(); }
}
```

**优点**：
- ✅ 没有线程切换开销
- ✅ ThreadLocal 不丢
- ✅ 资源占用小

**缺点**：
- ❌ 不能异步（占着调用方线程）
- ❌ 队列只能业务自己实现

### 6.3 怎么选

| 场景 | 选 |
| --- | --- |
| 调用第三方网络服务 | **线程池**（异步 + 隔离彻底） |
| 内部 RPC 调用 | **信号量**（性能更好） |
| 数据库慢查询 | 信号量（连接池本身就有限制） |
| Redis 调用 | 信号量（响应通常很快） |

> Sentinel 默认用信号量，认为大多数场景下"超时 + 信号量"组合够用，不需要线程池的开销。

### 6.4 Bulkhead 模式（隔离的别名）

> "船舱"模式——船被撞破一个舱，水进不到其他舱。
> 在分布式系统里就是把不同业务线、不同下游、不同优先级的资源完全隔离。

实战分组：
- 核心交易：独立 DB 实例 + 独立 Redis + 独立线程池
- 非核心查询：共享一组资源
- 内部管理：单独一组

## 七、兜底（Fallback Defaults）

### 7.1 兜底的层次

```
[CDN / 静态页]              ← 第 5 层：极端兜底（系统全挂还能展示页面）
       ↓
[本地缓存 Caffeine]         ← 第 4 层：Redis 全挂时
       ↓
[Redis 缓存]                ← 第 3 层：DB 挂时
       ↓
[降级数据 / 默认值]         ← 第 2 层：业务故障时
       ↓
[正常流程]                  ← 第 1 层
```

### 7.2 兜底的设计原则

1. **兜底数据要正确**：返回过时数据 ≠ 返回错误数据
2. **兜底必须告知用户**：UI 上加"系统繁忙，显示历史数据"
3. **兜底要监控**：兜底触发率高时要告警
4. **兜底不能带来新问题**：缓存兜底不能击穿、默认值不能引发逻辑 bug

## 八、Hystrix vs Sentinel vs Resilience4j vs Istio

### 8.1 核心对比

| 维度 | Hystrix | Sentinel | Resilience4j | Istio |
| --- | --- | --- | --- | --- |
| 部署形式 | 应用内 | 应用内 | 应用内 | **Sidecar** |
| 隔离 | 线程池 + 信号量 | 信号量 | 信号量 | 进程级 |
| 限流 | 弱 | **强** | 中 | 中 |
| 熔断 | ✅ | ✅ | ✅ | ✅ |
| 多语言 | Java | Java（Go/C++ 弱） | Java | **多语言** |
| 控制台 | 简陋 | **强大** | 无 | Kiali |
| 学习曲线 | 中 | 中 | 低 | 高 |
| 维护现状 | 已停更 | 活跃 | 活跃 | 活跃 |

### 8.2 选型建议

```
Java + Spring Cloud Alibaba          → Sentinel
Java + Spring Cloud（官方）         → Resilience4j
多语言混合架构 + K8s                → Istio Sidecar
老项目                              → 不要再选 Hystrix
```

> Istio 的优势是**业务零侵入**——治理逻辑在 Sidecar 里，应用代码不用引依赖。代价是 K8s 学习曲线和 Sidecar 性能开销（5-10% RT 增加）。

## 九、生产踩过的坑

### 坑 1：MyBatis 不配 SQL 超时

> 慢 SQL 把数据库连接池打满 → 整服务 503 → 全站不可用。
> **修复**：`mybatis.configuration.default-statement-timeout=10`，单条 SQL 不超过 10s。

### 坑 2：Feign 默认 1s 超时

> 业务调用经常要 2-3s，Feign 默认 1s 超时 → 大量误超时 → 降级数据满天飞。
> **修复**：`feign.client.config.default.read-timeout=5000`，按业务调整。

### 坑 3：重试没设次数上限

> 实习生写重试 `while(!success) retry()` → 下游挂了进入死循环 → 服务 CPU 100%。
> **修复**：永远设 maxAttempts，3-5 次封顶。

### 坑 4：重试 + 没指数退避

> 偶发抖动时所有客户端立即重试 → 1ms 内重试请求暴增 10 倍 → 下游被打死。
> **修复**：指数退避 + Jitter。

### 坑 5：熔断打开后没监控

> 熔断打开后业务侧不知道 → 用户感觉"系统好慢"但监控看着正常 → 故障 30 分钟才发现。
> **修复**：熔断状态变化打标 + Prometheus 告警。

### 坑 6：线程池隔离 ThreadLocal 失效

> Hystrix 切线程后 MDC 的 TraceId 丢了 → 链路追踪断了。
> **修复**：① 用 TransmittableThreadLocal；② 改用信号量隔离；③ Sentinel 不切线程。

### 坑 7：降级返回了错误数据

> 用户余额查询降级返回 0 → 前端展示"余额 0" → 用户以为账户被清空 → 投诉爆炸。
> **修复**：降级要么返回明确的"无法显示"，要么返回上次成功值；不能返回逻辑上错误的默认值。

### 坑 8：超时设得太宽松

> Feign 配置 30s → 下游慢请求堆积 → 调用方线程池打满 → 雪崩。
> **修复**：超时要严格——P99 响应时间 × 2 是上限。

## 十、面试高频追问

### Q1：限流、熔断、降级到底什么关系？

| | 触发原因 | 行为 | 主体 |
| --- | --- | --- | --- |
| 限流 | 入口流量超阈值 | **拒绝**部分请求 | 自己保护自己 |
| 熔断 | **下游**故障率高 | 暂时**断开**对下游调用 | 调用方保护自己 |
| 降级 | 主流程失败 | 返回**兜底数据** | 给用户一个像样的体验 |

**触发顺序**：流量高 → 限流 → 调下游失败率高 → 熔断 → 不调了走降级返回。

### Q2：熔断三态怎么转换？

```
Closed：失败率 > 50%（窗口 10s + 至少 20 个请求）→ Open
Open：等 10-30s → Half-Open
Half-Open：放 5-10 个请求 → 成功率高 → Closed；失败率高 → Open
```

### Q3：重试为什么会引发雪崩？

朴素重试：1000 个请求失败 → 全部立即重试 → 实际打到下游 = 1000 × N 次。
**指数退避 + Jitter**：错峰 + 限次，避免风暴。
**配合熔断**：熔断打开后不再重试。

### Q4：线程池隔离和信号量隔离怎么选？

| 场景 | 选 |
| --- | --- |
| 第三方网络调用 | 线程池（隔离彻底 + 异步） |
| 内部 RPC、Redis、DB | 信号量（开销小） |
| 需要 ThreadLocal 透传 | 信号量 |
| 需要队列 + 超时 | 线程池 |

阿里 Sentinel 选信号量为主，理由：现代微服务大多是 RPC/Redis 调用，本身够快，不需要线程池开销。

### Q5：调用链超时怎么设计？

**递减原则**：A → B → C → D，超时设置 5s → 3s → 1s → 0.5s。
让下游的超时严格小于上游，避免上游已超时但下游还在等。

### Q6：降级和熔断的区别？

熔断：**自动机制**，下游故障率高时主动断开，是状态机驱动的。
降级：**业务决定**，对外提供 fallback 数据，可以是熔断触发的，也可以是手动开关触发的。

熔断**通常会触发降级**，但降级不一定来自熔断（也可以是限流触发、手动开关触发）。

### Q7：怎么动态调整治理规则？

Sentinel 接 Nacos：

```yaml
spring:
  cloud:
    sentinel:
      datasource:
        flow:
          nacos:
            server-addr: nacos:8848
            data-id: ${spring.application.name}-flow-rules
            rule-type: flow
```

控制台改规则 → 推到 Nacos → Sentinel 监听变更 → 实时生效。

### Q8：Sentinel vs Hystrix vs Resilience4j 怎么选？

- 国内 Spring Cloud Alibaba 项目 → **Sentinel**
- Spring Cloud 官方 / 函数式编程偏好 → **Resilience4j**
- 多语言 + K8s 已用 Istio → **Istio Sidecar 治理**
- Hystrix → **不要选**（停更 5 年了）

### Q9：什么场景不能熔断？

- 强一致核心：支付、扣库存、转账（熔断后业务直接错乱）
- 单次重要操作：用户下单的核心流程

兜底方案：业务侧加重试 + 异步补偿，但不能让熔断器直接失败返回"假成功"。

### Q10：Istio 的服务治理跟 Sentinel 比好在哪？

| | Sentinel | Istio |
| --- | --- | --- |
| 业务侵入 | 加注解 + 依赖 | **零侵入**（Sidecar） |
| 多语言 | Java 强，其他弱 | **全语言一致** |
| 部署 | 跟应用一起 | **独立 Sidecar** |
| 性能 | 高（应用内） | **多一跳 Sidecar** |
| 学习曲线 | 中 | 高 |

K8s + 多语言体系选 Istio，单语言 Java 体系 Sentinel 更轻。

## 十一、答题模板（60 秒话术）

> 服务治理的"七板斧"：**限流防过载、熔断防级联、降级保体验、重试容偶发、超时控边界、隔离防扩散、兜底保最后**。
>
> **熔断三态**：Closed（正常）→ 失败率 > 50% → **Open**（快速失败）→ 等 10-30s → **Half-Open**（试探）→ 成功率高回 Closed，否则回 Open。Sentinel 三种策略：慢调用比例、异常比例、异常数。
>
> **重试三铁律**：① 接口必须幂等；② **指数退避 + Jitter**防风暴；③ 限制次数（3-5 次）。**重试要被熔断器包住**——熔断打开后不再重试。
>
> **超时递减原则**：上游超时必须严格大于下游，否则上游已超时但下游还在等。Feign 默认 1s 太短，生产改 3-5s；MyBatis 默认无限超时是大坑，必须配 10s。
>
> **隔离两选**：线程池（彻底但有开销 + ThreadLocal 失效）vs 信号量（性能好但不能异步）。Sentinel 默认信号量。
>
> **框架选型**：国内 Sentinel、Spring Cloud 官方 Resilience4j、多语言 K8s 选 Istio Sidecar，**Hystrix 已停更不要选**。
>
> **生产关键坑**：① MyBatis SQL 必须配超时；② 重试不指数退避会雪崩；③ 熔断要监控+告警；④ 降级数据不能错误（返回 0 余额能要命）；⑤ 调用链超时要递减。
