# 链路追踪（SkyWalking / Zipkin / Jaeger）

> 微服务排障的"X 光机"——服务多了，没有链路追踪等于盲人摸象。
> 本篇要解决的问题：
> ① 一次请求经过 N 个服务，怎么把它们**串成一条链路**？
> ② **TraceId / SpanId / ParentSpanId** 是什么关系？怎么透传？
> ③ **Dapper 论文**（Google 2010）定义的核心模型，所有现代追踪工具都在跟它
> ④ **SkyWalking / Zipkin / Jaeger** 各自的特点和取舍
> ⑤ **OpenTelemetry** 是什么？为什么是未来的标准？
> ⑥ 怎么做**采样策略**避免追踪本身打挂系统？
>
> 跟 [服务治理](./服务治理.md) 是孪生篇——治理是"防出问题"，追踪是"出问题时能找到根因"，可观测性是微服务三支柱之一。

---

## 一、为什么需要链路追踪

### 1.1 没追踪的痛苦

```
用户投诉：下单接口慢了

排查路径：
   API 网关日志 → 订单服务日志 → 库存服务日志 → 优惠券服务 → DB 慢查询日志
   ↓                ↓               ↓               ↓               ↓
   各服务时间不同步、TraceId 不一致、跨日志聚合困难

  ↓
  3 小时后才定位到：是优惠券服务调外部 API 超时了
```

**根因**：
- 服务多（10+ 个），日志分散
- 时间戳不同步（机器时钟差几百 ms）
- 没有统一的"这次请求"标识
- 无法可视化调用拓扑和耗时分布

### 1.2 链路追踪的目标

**一次请求 = 一条链路**：

```
用户点击"下单"
   ↓ TraceId = abc123
   
  [Gateway]   ─── 5ms
       ↓
  [Order]     ─── 80ms
       ├── [Inventory]   ─── 30ms
       ├── [Coupon]      ─── 60ms ← 慢点在这
       └── [Payment]     ─── 25ms
       
总耗时 170ms，瓶颈定位到 Coupon
```

**好处**：
- ✅ 一眼看出全链路耗时分布
- ✅ 自动找到性能瓶颈
- ✅ 跨服务排障——同一个 TraceId 串起所有日志
- ✅ 服务依赖拓扑自动绘制

## 二、Dapper 论文：链路追踪的鼻祖

> Google 2010 年发布《Dapper, a Large-Scale Distributed Systems Tracing Infrastructure》——所有现代追踪工具的祖师爷。

### 2.1 核心数据模型

```
Trace（一次完整请求）
  └── Span（一个调用单元，可能是 RPC、DB、Redis 调用）
        ├── Span（嵌套子调用）
        │     └── Span
        └── Span
```

### 2.2 关键字段

| 字段 | 含义 |
| --- | --- |
| **TraceId** | 全链路唯一 ID，整条调用链共享 |
| **SpanId** | 单个调用的唯一 ID |
| **ParentSpanId** | 父调用的 SpanId（构造树形结构） |
| **OperationName** | 操作名（如 `OrderService.create`） |
| **StartTime** | 开始时间（微秒级） |
| **Duration** | 耗时 |
| **Tags** | 元数据（http.method、user.id、error=true）|
| **Logs** | 时间点事件（exception 堆栈、关键节点）|

### 2.3 Span 树结构

```
Trace abc123
  Span 1 (root)         Gateway              0~170ms
    Span 2              Order.create         5~165ms
      Span 3            Inventory.deduct     10~40ms
      Span 4            Coupon.use           45~105ms
        Span 5          ExternalAPI.call     50~100ms ← 慢点
      Span 6            Payment.process      110~135ms
```

每个 Span 记录：开始时间 + 耗时 + 父子关系 + Tags → 重建出完整调用链。

### 2.4 ParentSpanId 怎么形成树

```
Span A (id=1, parent=null)        ← root
  Span B (id=2, parent=1)
    Span D (id=4, parent=2)
  Span C (id=3, parent=1)

→ 把 Span 集合按 parent 关系还原成树：

           A
          / \
         B   C
         |
         D
```

## 三、TraceId 透传机制

### 3.1 进程内透传（线程上下文）

```java
// 进入 OrderService.create
MDC.put("traceId", "abc123");   // 写入线程 ThreadLocal

// 调用 Inventory.deduct（同进程）
String traceId = MDC.get("traceId");  // 读取——同一个线程能拿到
```

**坑点**：
- 异步任务（线程池）→ ThreadLocal 不传递 → TraceId 丢失
- 解决：用 **TransmittableThreadLocal**（阿里）或 **MDC + 任务装饰器**

### 3.2 跨进程透传（HTTP / RPC Header）

```
[A 服务] ────HTTP 请求──▶ [B 服务]

请求 Header：
  X-B3-TraceId: abc123
  X-B3-SpanId: span2
  X-B3-ParentSpanId: span1
  X-B3-Sampled: 1
```

**B3 协议**：Zipkin 定义的事实标准，名字来自 BigBrotherBird（早期 Zipkin 项目名）。
**W3C Trace Context**：W3C 制定的新标准（traceparent / tracestate header），OpenTelemetry 默认用。

### 3.3 跨技术栈透传

| 协议 | 透传方式 |
| --- | --- |
| HTTP | Header 字段 |
| Dubbo | RpcContext attachment |
| gRPC | Metadata |
| MQ（Kafka/RocketMQ） | 消息 Header / properties |
| 数据库 | SQL 注释（`/* traceId=abc */ SELECT ...`） |

### 3.4 完整透传示例（Spring Cloud + Sleuth）

Spring Cloud Sleuth 自动透传：

```yaml
spring:
  sleuth:
    sampler:
      probability: 0.1   # 10% 采样
    web:
      enabled: true       # HTTP 自动埋点
    feign:
      enabled: true       # Feign 自动透传
    redis:
      enabled: true       # Redis 客户端追踪
```

业务代码无感知——Sleuth 拦截所有 HTTP/Feign 调用，自动加 Trace Header。

## 四、四大主流框架对比

### 4.1 横向对比表

| 维度 | **SkyWalking** | **Zipkin** | **Jaeger** | **OpenTelemetry** |
| --- | --- | --- | --- | --- |
| 出品 | 华为/Apache | Twitter/开源 | Uber/CNCF | CNCF（统一标准） |
| 探针方式 | **字节码增强**（无侵入） | 代码埋点 | 代码埋点 | SDK + 自动探针 |
| 协议 | 自定义 + OpenTracing | B3 | OpenTracing | **W3C Trace Context** |
| 存储 | ES / TiDB / H2 | ES / Cassandra / MySQL | ES / Cassandra | 后端可选 |
| UI | **强**（自带 + 拓扑图） | 简洁 | 中 | 无（用其他工具） |
| 性能开销 | 低（5%） | 低 | 低 | 取决于 SDK |
| 多语言 | Java 强，其他弱 | 多语言 | 多语言 | **全语言** |
| 服务拓扑 | **自动绘制** | 不强 | 中 | 不直接提供 |
| 告警 | **内置** | 无 | 无 | 不直接提供 |
| 国内主流 | **是** | 否 | 否 | 是（趋势） |

### 4.2 SkyWalking（国内主流）

**核心特点**：
- **字节码增强**——无侵入，不用改业务代码
- **自动绘制服务拓扑**
- **告警 + 指标 + 追踪三合一**（不止追踪）
- **OAP 后端**用 ES 存储

**架构**：

```
[业务应用]
   │ Java Agent（字节码增强）
   ▼
[SkyWalking OAP Server]   ← 数据聚合 + 分析
   │
   ▼
[ES / TiDB]              ← 存储
   │
   ▼
[SkyWalking UI]          ← 可视化
```

**部署**：

```bash
# 启动应用时挂 Java Agent
java -javaagent:/path/skywalking-agent.jar \
     -Dskywalking.agent.service_name=order-service \
     -Dskywalking.collector.backend_service=oap:11800 \
     -jar app.jar
```

**优点**：业务代码零改动，开箱即用。
**缺点**：Java 体系强，其他语言（Python/Node/Go）支持弱。

### 4.3 Zipkin（最简单老牌）

**核心特点**：
- Twitter 2012 年开源，最老
- 协议简单（B3）
- 实现轻量
- Spring Cloud Sleuth 默认对接

**架构**：

```
[Sleuth] ─── 上报 Span ──▶ [Zipkin Collector]
                                 │
                          ┌──────┴──────┐
                          ▼             ▼
                       [Storage]      [Search]
                       ES/Cassandra   ES
                          │
                          ▼
                       [Zipkin UI]
```

**优点**：简单、Spring Cloud 生态完善。
**缺点**：UI 简陋，没拓扑图，没告警。

### 4.4 Jaeger（CNCF 云原生）

**核心特点**：
- Uber 2015 年开源，2017 年捐 CNCF
- 兼容 OpenTracing（已被 OpenTelemetry 取代）
- K8s 友好（Operator 部署）
- 适合多语言混合

**适用**：K8s + 云原生场景。

### 4.5 OpenTelemetry（未来标准）

**背景**：之前有 OpenTracing（API 标准）+ OpenCensus（采集标准），两者合并 → **OpenTelemetry（OTel）**。

**核心理念**：**统一追踪 + 指标 + 日志的标准 SDK**。

```
[业务代码]
   ↓ OpenTelemetry SDK（标准 API）
[OpenTelemetry Collector]
   ↓ 可导出到任何后端
[Jaeger / Zipkin / SkyWalking / Datadog / NewRelic / ...]
```

**优势**：
- ✅ **业务代码只依赖 OTel API**，后端可换
- ✅ 多语言支持最全（Java/Go/Python/Node/...）
- ✅ CNCF 顶级项目，业界共识
- ✅ 自动探针 + 手动埋点都支持

**现状**：新项目优先选 OpenTelemetry，老项目逐步迁移。

## 五、采样策略

### 5.1 为什么要采样

不采样的代价：
- 每个 Span 大约 1KB → 1w QPS × 10 个 Span = 100 MB/s
- 一天 8.6 TB → 存储爆炸 + 网络打挂

**全采样**仅适用于：低 QPS 服务、刚上线调试、关键金融场景。

### 5.2 三种采样策略

| 策略 | 描述 | 适用 |
| --- | --- | --- |
| **恒定采样** | 固定比例（如 10%） | 通用 |
| **限速采样** | 每秒最多 N 个（如 100 QPS） | 防止突发流量打爆 |
| **自适应采样** | 高 QPS 低采样率，低 QPS 高采样率 | 动态调整 |
| **基于规则采样** | 错误请求 100% 采样、慢请求 100% 采样、其他 1% | **生产推荐** |

### 5.3 头部采样 vs 尾部采样

#### 头部采样（Head-based）

请求开始时决定采不采（最常见）。

```
入口 → 决定采样率 10% → 整条链路要么全采要么全不采
```

**优点**：简单、SDK 实现容易。
**缺点**：在请求开始时不知道这个请求会不会出错，**错误请求可能被丢弃**。

#### 尾部采样（Tail-based）

请求完成后才决定采不采（按结果决定）。

```
所有 Span 先暂存到 Collector
   ↓
请求完成 → 评估：有错？慢？满足规则？
   ↓
是 → 100% 采样
否 → 1% 采样
```

**优点**：错误和慢请求 100% 不丢。
**缺点**：Collector 资源开销大（要暂存所有 Span 几秒）。

> **生产推荐**：尾部采样（OTel Collector 支持），错误链路全采、慢链路全采、正常链路低采样。

## 六、链路追踪 + 日志 + 指标 = 可观测性"三支柱"

### 6.1 三支柱

```
[Logs 日志]      ── 谁做了什么、什么时间
[Metrics 指标]   ── 多少 QPS、错误率、RT
[Traces 追踪]    ── 这个请求经过哪些服务、各花了多少时间
```

### 6.2 三者关系

```
异常告警 → Metrics 看到错误率涨
   ↓
查这个时间段的 Traces → 找出慢/错的链路
   ↓
按 TraceId 查 Logs → 看具体异常堆栈
```

**关键点**：日志要写 TraceId！

```java
// 日志格式
[2026-05-09 10:00:00] [INFO] [traceId=abc123,spanId=def456] OrderService - 创建订单成功
```

排障时直接用 TraceId 跨服务搜日志，定位问题秒级。

### 6.3 工具栈

| 类型 | 主流工具 |
| --- | --- |
| 日志 | ELK（Elasticsearch + Logstash + Kibana）、Loki + Grafana |
| 指标 | Prometheus + Grafana |
| 追踪 | SkyWalking / Zipkin / Jaeger / OTel |
| 一体化 | **SkyWalking**（追踪 + 指标 + 告警） / **Datadog** / **New Relic** |

## 七、生产踩过的坑

### 坑 1：异步任务 TraceId 丢失

```java
@Async
public void doAsync() {
    log.info("traceId={}", MDC.get("traceId"));  // null！
}
```

**根因**：`@Async` 切线程，ThreadLocal 不传递。
**修复**：① 用 TransmittableThreadLocal（阿里）；② 在 `TaskDecorator` 里手动传递 MDC：

```java
@Bean
public TaskDecorator taskDecorator() {
    return runnable -> {
        Map<String, String> contextMap = MDC.getCopyOfContextMap();
        return () -> {
            try {
                if (contextMap != null) MDC.setContextMap(contextMap);
                runnable.run();
            } finally {
                MDC.clear();
            }
        };
    };
}
```

### 坑 2：MQ 消费 TraceId 没透传

> 生产者把消息发到 MQ，消费者重新生成 TraceId → 全链路断了。
> **修复**：消息 Header 里带 TraceId，消费者从 Header 提取：

```java
// 生产
Message msg = new Message(...);
msg.putUserProperty("traceId", MDC.get("traceId"));

// 消费
String traceId = msg.getUserProperty("traceId");
MDC.put("traceId", traceId);
```

### 坑 3：100% 采样打爆系统

> 上线时为了"尽量收集数据"配 100% 采样 → 链路追踪后端 ES 写入 1 万 QPS → 集群挂了。
> **修复**：默认 1-10% 采样 + 错误链路 100% 采样。

### 坑 4：SkyWalking Agent 影响应用启动

> Agent 字节码增强阶段慢 → 应用启动从 30s 变 90s → 健康检查超时被 K8s 重启。
> **修复**：① K8s readinessProbe 调大初始超时；② 减少 Agent 增强的类范围；③ 升级到新版 Agent。

### 坑 5：高基数 Tag 打爆存储

```java
span.setTag("user.id", userId);  // 用户 ID 千万级 → ES 索引爆炸
```

**修复**：高基数维度（user.id、订单号）放 Logs 不放 Tags；Tags 只放低基数（http.status、error）。

### 坑 6：跨域请求 TraceId 没透传

> 前端 → API 网关 → 后端，跨域请求时 OPTIONS 预检请求 TraceId 没传 → 链路断在 Gateway。
> **修复**：CORS 配置允许 `X-B3-*` Header 跨域。

### 坑 7：Tag 用错维度

> 把请求 body 整个塞进 Tag → 单个 Span 几 MB → 网络/存储压力大。
> **修复**：Tag 只放关键索引字段（service.name、http.status）；详细 body 放 Logs 字段（且要采样）。

### 坑 8：链路追踪 vs APM 混淆

> 老板要"性能监控" → 用了 SkyWalking → 但只看了链路图，没看 Metrics → 错过磁盘满告警。
> **修复**：APM = 追踪 + 指标 + 告警，三件齐全才有用。

## 八、面试高频追问

### Q1：TraceId 和 SpanId 怎么生成？

| ID | 生成方式 |
| --- | --- |
| TraceId | 入口生成（UUID / 雪花算法 / 16/32 字节随机） |
| SpanId | 每次进入新 Span 生成（8 字节随机） |
| ParentSpanId | 上游 SpanId 直接传过来 |

注意 TraceId 必须**全链路唯一**，所以入口（API 网关）是生成点。

### Q2：跨进程怎么透传 TraceId？

| 协议 | 透传方式 |
| --- | --- |
| HTTP | X-B3-TraceId Header / W3C traceparent |
| Dubbo | RpcContext.getContext().setAttachment() |
| gRPC | Metadata |
| MQ | 消息 Header / properties |
| Redis | 命令注释（少用，业务侵入） |
| DB | SQL 注释（`/* traceId=abc */ SELECT...`） |

### Q3：异步任务 TraceId 怎么不丢？

三个方案：
1. 阿里 **TransmittableThreadLocal**（最简单）
2. Spring **TaskDecorator** 手动传 MDC
3. **CompletableFuture** 自定义 Executor 包装

### Q4：SkyWalking 怎么做到无侵入？

**Java Agent + 字节码增强**：
- 启动时通过 `-javaagent` 加载
- 用 Byte Buddy 拦截目标类（如 `RestTemplate.exchange`）
- 在方法前后插入埋点代码（拿 TraceId、记录耗时）
- 业务代码不用改一行

代价：JVM 启动慢一些（几秒）、CPU 多 1-3%。

### Q5：采样率怎么定？

| 业务规模 | 采样率 |
| --- | --- |
| 小服务（<100 QPS） | 100% |
| 中等（100-1000 QPS） | 10-50% |
| 高 QPS（>1000） | 1-10% |
| 超高 QPS（>10w） | 0.1-1% + 错误请求 100% |

**推荐**：基于规则采样——错误 100%、慢请求 100%、正常请求 1%。

### Q6：OpenTelemetry 跟 OpenTracing 有什么关系？

历史：
- **OpenTracing**（2016）：追踪 API 标准
- **OpenCensus**（2017）：Google 出的指标 + 追踪标准
- 两个标准互相竞争 → 2019 年合并 → **OpenTelemetry**

OpenTelemetry **取代两者**，是现在和未来的事实标准。

### Q7：Zipkin 和 SkyWalking 怎么选？

| 维度 | Zipkin | SkyWalking |
| --- | --- | --- |
| 部署 | 简单 | 中 |
| 业务侵入 | Sleuth 自动 | Java Agent 无侵入 |
| 拓扑图 | ❌ | ✅ |
| 告警 | ❌ | ✅ |
| 多语言 | 强 | 弱（Java 强） |
| 生态 | Spring Cloud 默认 | 国内大厂主流 |

国内项目 → SkyWalking；多语言混合 → Zipkin / Jaeger / OTel。

### Q8：TraceId 写到日志的最佳实践？

```xml
<!-- logback.xml -->
<pattern>
  [%d{yyyy-MM-dd HH:mm:ss}] [%thread] [%X{traceId},%X{spanId}] %-5level %logger - %msg%n
</pattern>
```

`%X{traceId}` 从 MDC 读取——前提是把 TraceId 写到了 MDC。

排障时：

```bash
# Kibana / Grafana 直接搜 TraceId
grep "abc123" *.log
```

### Q9：怎么追踪数据库慢查询的链路？

两种思路：
1. **DB Span**：客户端拦截 JDBC 调用，把 SQL 当作 Span 的 OperationName，耗时记录到 Tags
2. **SQL 注释**：在 SQL 前加 `/* traceId=abc spanId=def */`，DB 慢日志能看到来源

```java
// MyBatis 拦截器
String sql = "/* " + MDC.get("traceId") + " */ " + originalSql;
```

DBA 看慢日志时直接拿 TraceId 反查上游。

### Q10：链路追踪后端用什么存储？

| 后端 | 优缺点 |
| --- | --- |
| **Elasticsearch** | 主流，全文搜索强，但写入瓶颈 |
| **Cassandra** | 写吞吐高，但查询灵活性差 |
| **TiDB** | 兼容 MySQL，国内 SkyWalking 推荐 |
| **ClickHouse** | 列存，分析查询快，新趋势 |

数据量大优先 ClickHouse / Cassandra；强搜索需求选 ES。

## 九、答题模板（60 秒话术）

> 链路追踪解决微服务排障难题——一次请求经过 N 个服务，没有它就是盲人摸象。
>
> **核心模型来自 Google Dapper 论文**：Trace（一次请求）= 多个 **Span**（调用单元），Span 之间通过 **TraceId（全链路唯一）+ SpanId + ParentSpanId** 构造树形结构。所有现代追踪工具都基于这个模型。
>
> **TraceId 透传**：① 进程内用 ThreadLocal/MDC，异步任务用 **TransmittableThreadLocal**；② 跨进程通过 HTTP Header（**B3 协议**或 **W3C Trace Context**）、Dubbo attachment、MQ Header 透传。
>
> **四大框架**：① **SkyWalking**（国内主流，Java Agent 无侵入，自动拓扑图，三合一）；② **Zipkin**（最老最简单，Spring Cloud Sleuth 默认）；③ **Jaeger**（CNCF，云原生）；④ **OpenTelemetry**（**统一标准，未来方向**）。
>
> **采样策略**：默认 1-10%，**错误请求 100% + 慢请求 100% + 正常请求低采**（尾部采样）。100% 采样会把后端打爆。
>
> **可观测性三支柱**：日志（Logs）+ 指标（Metrics）+ 追踪（Traces），三者通过 TraceId 串联——告警时从 Metrics 发现问题，从 Traces 定位链路，从 Logs 看堆栈。
>
> **生产关键**：① 异步任务必须 TransmittableThreadLocal 防 TraceId 丢失；② **日志必须打 TraceId**；③ MQ 消费要从 Header 提取 TraceId；④ 高基数维度（userId）放 Logs 不放 Tags；⑤ 100% 采样会打爆 ES 集群。
>
> **未来选型**：新项目优先 **OpenTelemetry**，业务代码只依赖 OTel API，后端可灵活切换。
