# 限流算法

> 限流是高并发系统的"第一道防线"。面试要回答：
> ① 为什么需要限流（动机、不限会怎样）
> ② **四大经典算法** —— 固定窗口、滑动窗口、漏桶、令牌桶
> ③ **令牌桶 vs 漏桶** —— 怎么选、各自适用什么场景
> ④ **Guava RateLimiter / Sentinel** 各自怎么实现的
> ⑤ 集群限流怎么做（Redis + Lua）

---

## 一、为什么需要限流

### 1.1 不限流的灾难

```
场景：电商秒杀，正常 QPS 1k，秒杀瞬间 100k
没有限流：
    │
    ▼
应用层处理不过来 → 线程池打满 → 所有请求排队 → 用户超时重试 → 雪崩
    │
    ▼
DB 连接池打满 → DB 慢查询 → 整站不可用
```

**限流的本质**：**主动拒绝部分请求**，保护系统**核心可用性** > 保证**所有请求都能成功**。

### 1.2 限流的对象

| 维度 | 例子 |
| --- | --- |
| 接口级 | /api/order/create QPS 限 1000 |
| 用户级 | 单用户 1 分钟最多 60 次 |
| IP 级 | 单 IP 1s 100 次 |
| 业务级 | 同商品 1s 内只能下 1 单 |
| 全局 | 整个网关 QPS 限 10w |

### 1.3 限流 vs 熔断 vs 降级

| 概念 | 触发 | 行为 |
| --- | --- | --- |
| **限流** | 流量超阈值 | **拒绝**部分请求 |
| **熔断** | 错误率高 | **暂时切断**对下游调用 |
| **降级** | 系统压力大 | **返回兜底数据**（如缓存）|

## 二、固定窗口（Fixed Window）

### 2.1 算法

```
1. 维护一个计数器 + 当前窗口起始时间
2. 每个请求到来：
   - 在当前窗口（如 1s）内 → 计数器 +1，如果超过阈值拒绝
   - 跨窗口 → 计数器清零、重置起始时间
```

### 2.2 ASCII 图

```
QPS 限制 5/s

t=0s         t=1s         t=2s
  │            │            │
  ●●●●●●       ●●           ●●●●●
  ↑↑↑↑↑→×      ↑↑           ↑↑↑↑↑
  允5个 拒绝    允许2个      允许5个
```

### 2.3 实现（伪代码）

```java
private long windowStart = System.currentTimeMillis();
private AtomicInteger count = new AtomicInteger(0);
private final int LIMIT = 100;
private final long WINDOW = 1000;

public boolean tryAcquire() {
    long now = System.currentTimeMillis();
    if (now - windowStart >= WINDOW) {
        windowStart = now;
        count.set(0);
    }
    return count.incrementAndGet() <= LIMIT;
}
```

### 2.4 致命缺陷：窗口边界突刺

```
QPS 限 100：

时间    0.0s ─────────── 0.99s ─── 1.0s ─────────── 1.99s
请求               ●●●●●●●●● 100    ●●●●●●●●● 100
                              ↑ 跨界，1ms 内累计 200 请求
```

→ 在 0.99s 和 1.01s 这 0.02s 内，**实际通过 200 请求**——**瞬时翻倍**。

### 2.5 适用场景

- 对突刺不敏感的场景（如统计类）
- **生产几乎不直接用**，因为突刺问题——除非阈值留足缓冲

## 三、滑动窗口（Sliding Window）

### 3.1 算法

把固定窗口**切分为更细的小格**，**滑动**计算。

```
窗口 1s，分 10 个格子（每格 100ms）

t=0      0.1s  0.2s  ...  0.9s  1.0s
[0]   [1]    [2]    [...]  [9]
                                  
看"过去 1 秒"：sum(当前格 + 之前 9 格)
```

### 3.2 ASCII 图

```
当前时刻 t=1.05s
"过去 1 秒"窗口范围：[0.05s, 1.05s]
跨过 [0] 部分（仅 50ms 在窗口内）和 [1]~[9] 全部

count = [0]*0.5 + sum([1..9])     ← 加权或直接舍弃 [0]
```

### 3.3 实现思路

```java
class SlidingWindow {
    private long[] buckets = new long[10];      // 10 个格子
    private long[] timestamps = new long[10];

    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();
        int idx = (int) ((now / 100) % 10);     // 当前格
        if (timestamps[idx] != now / 100) {
            buckets[idx] = 0;                   // 跨格子清零
            timestamps[idx] = now / 100;
        }
        long sum = 0;
        for (int i = 0; i < 10; i++) {
            if (now - timestamps[i] * 100 < 1000) sum += buckets[i];
        }
        if (sum >= LIMIT) return false;
        buckets[idx]++;
        return true;
    }
}
```

### 3.4 vs 固定窗口

```
固定窗口：突刺最高 2x
滑动窗口（10 格）：突刺最高 1.1x（最小化）
滑动窗口（无限细分）：完全没有突刺，等于"过去 1 秒"的精确计数
```

→ **格子越细越准、内存越大**。

### 3.5 实现：Sentinel 用环形数组

Sentinel 的 LeapArray 就是滑动窗口的工程实现：

```java
LeapArray windowArray = new LeapArray(60, 60_000);   // 60 个格子，总共 60s
```

详见 [Sentinel 7.2](#72-sentinel)。

## 四、漏桶（Leaky Bucket）

### 4.1 算法

```
请求 → 桶（FIFO 队列）→ 固定速率出水

桶满了 → 丢弃新请求
```

### 4.2 ASCII 图

```
请求流入（不规则）：●●●● ● ●●●●● ●

      ┌─────────┐
请求 →│  桶     │← 满了丢弃
      │ ●●●●●   │
      │ ●●●●    │
      └─┬───────┘
        ▼
      固定速率流出（如 100/s）
      → 业务处理
```

### 4.3 特征

- **入水率不固定，出水率固定**
- 突发流量被**强制平滑**——吞吐稳定
- 桶满即丢

### 4.4 实现（伪代码）

```java
class LeakyBucket {
    private long lastLeakTime = System.currentTimeMillis();
    private double water = 0;
    private final double CAPACITY = 100;
    private final double LEAK_RATE = 10;     // 每秒漏 10 个

    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();
        double leaked = (now - lastLeakTime) / 1000.0 * LEAK_RATE;
        water = Math.max(0, water - leaked);
        lastLeakTime = now;
        if (water + 1 > CAPACITY) return false;
        water++;
        return true;
    }
}
```

### 4.5 缺点

- **完全没有突发能力**——再小的瞬时高峰也被压平
- 用户体验差（即使系统空闲、流量很小也按固定速率出）

→ 适合**严格速率控制** 场景：如控制对下游的调用速率。

## 五、令牌桶（Token Bucket）

### 5.1 算法

```
后台线程匀速产生令牌 → 放入桶里
请求 → 拿令牌：
  - 桶里有 → 拿一个，通过
  - 桶里没 → 拒绝
桶满了 → 新令牌丢弃
```

### 5.2 ASCII 图

```
令牌生成（匀速 10/s）→ ●●●●●●●●●●

         ┌─────────┐
桶容量 100│ ●●●●●●●● │ ← 满了 = 丢令牌
         │ ●●●●●●●  │
         └─┬───────┘
           ▼
请求 → 拿令牌：有就走，没有就拒
```

### 5.3 关键特征

- **允许突发**：桶里能囤令牌——前 1 秒没流量、第 2 秒突然 100 个请求都能过
- **均速**：长时间下平均速率不超阈值
- **桶大小决定突发上限**

### 5.4 实现（核心思想）

```java
class TokenBucket {
    private long lastRefillTime = System.currentTimeMillis();
    private double tokens = 0;
    private final double CAPACITY = 100;
    private final double RATE = 10;           // 令牌/秒

    public synchronized boolean tryAcquire() {
        refill();
        if (tokens >= 1) {
            tokens--;
            return true;
        }
        return false;
    }

    private void refill() {
        long now = System.currentTimeMillis();
        double newTokens = (now - lastRefillTime) / 1000.0 * RATE;
        tokens = Math.min(CAPACITY, tokens + newTokens);
        lastRefillTime = now;
    }
}
```

→ **不需要后台线程**——惰性补充。每次请求时根据时间差算应补的令牌。

## 六、令牌桶 vs 漏桶 选型

| 维度 | 漏桶 | 令牌桶 |
| --- | --- | --- |
| 速率限制 | 严格固定 | 平均固定 |
| 允许突发 | ❌ | ✅（最多 = 桶容量）|
| 时机 | 主动出水 | 被动消耗 |
| 实现复杂度 | 简单 | 简单 |
| 业务用途 | 控制**下游**调用速率 | **保护自己**接受请求 |
| 工业标准 | 网络协议 | **应用层限流首选** |

**经验法则**：

- **业务限流**（接口 QPS / 用户 QPS）→ **令牌桶**
- **下游调用速率**（写 DB / 调外部 API）→ **漏桶**
- **网络流量**（TCP 整形）→ 漏桶
- **突发友好**（平时空闲）→ 令牌桶

## 七、生产实现

### 7.1 Guava RateLimiter

Google Guava 提供，**令牌桶**实现：

```java
RateLimiter limiter = RateLimiter.create(10);    // 10 token/s

if (limiter.tryAcquire()) {
    // 处理
} else {
    // 拒绝
}

limiter.acquire();    // 阻塞直到拿到令牌
```

**两种模式**：

- `SmoothBursty`（默认）：允许突发（积攒令牌）
- `SmoothWarmingUp`（预热）：刚启动不打满，**逐步爬升**——保护冷启动的服务

```java
RateLimiter.create(100, 5, TimeUnit.SECONDS);    // 5s 内从 0 爬到 100 QPS
```

**局限**：**单机限流**——多机部署不能直接用。

### 7.2 Sentinel

阿里开源，**支持单机 + 集群**，多种限流策略。

**限流模式**：

- 直接（QPS / 线程数）
- 关联（A 流量大时限制 B）
- 链路（按调用链路限流）

**算法**：

- QPS 限流：**滑动窗口（LeapArray）**
- 排队等待：漏桶
- 预热：令牌桶 + 冷启动

**集群限流**：通过 token-server 集中发放令牌。

```java
@SentinelResource(value = "createOrder", blockHandler = "fallback")
public Order createOrder(...) { ... }

public Order fallback(BlockException e) { ... }
```

### 7.3 Redis + Lua 集群限流

**最常见的集群限流方案**——令牌桶用 Lua 原子操作：

```lua
local key = KEYS[1]
local rate = tonumber(ARGV[1])         -- 令牌速率
local capacity = tonumber(ARGV[2])     -- 桶容量
local now = tonumber(ARGV[3])
local requested = tonumber(ARGV[4])    -- 请求令牌数

local tokens = tonumber(redis.call('HGET', key, 'tokens') or capacity)
local lastRefresh = tonumber(redis.call('HGET', key, 'last') or now)

-- 补充令牌
local delta = math.min(capacity, tokens + (now - lastRefresh) * rate / 1000)

if delta < requested then
    return 0     -- 拒绝
else
    redis.call('HMSET', key, 'tokens', delta - requested, 'last', now)
    redis.call('EXPIRE', key, 60)
    return 1     -- 通过
end
```

**Lua 原子性**：Redis 单线程执行，多机请求不冲突。

### 7.4 Nginx limit_req

接入层限流，漏桶：

```nginx
limit_req_zone $binary_remote_addr zone=mylimit:10m rate=10r/s;

server {
    location /api/ {
        limit_req zone=mylimit burst=20 nodelay;
    }
}
```

`burst=20`：允许 20 个请求进队列；`nodelay`：超出立即拒绝（不延迟处理）。

## 八、生产踩坑

### 8.1 单机限流不能保护集群

**现象**：单机 QPS 限 100，10 台机器扩容后**集群 QPS 1000**，下游 DB 还是被打挂。
**修复**：用集群限流（Sentinel 集群 / Redis）；或动态算单机阈值（集群总阈值 / 实例数）。

### 8.2 阈值设错（拍脑袋）

**现象**：限流后用户大量被拒，但系统监控完全闲。
**根因**：阈值定 100，但系统能扛 1000。
**修复**：**压测定阈值**——在准生产环境给系统打满，看 QPS 上限再 *0.7 当阈值。

### 8.3 限流配置不能动态调整

**现象**：流量来了想调阈值，要改代码 + 发版。
**修复**：阈值放配置中心（Apollo / Nacos / Sentinel Dashboard），**热更新**。

### 8.4 限流没区分用户

**现象**：限流配 `1000 QPS`，但 1 个机器人占了 800，正常用户被挤掉。
**修复**：**多维度限流**——总 QPS + 单 IP / 单用户。Sentinel 用 hot key 限流。

### 8.5 限流后没合理降级

**现象**：被限流后直接返回 500，前端报错。
**修复**：限流后返回**降级数据**（缓存、默认值）或**友好提示**（"系统繁忙，请稍候"）。

### 8.6 网关限流和应用限流冲突

**现象**：Nginx 已限流，应用又限流，互相加压。
**修复**：**分层限流**：
- 网关：粗粒度，按 IP / 总 QPS
- 应用：细粒度，按用户 / 接口
- DB：连接池上限兜底

## 九、答题模板（60 秒话术）

> 限流四大算法：
> ① **固定窗口** ——计数器 + 时间窗，简单但有**窗口边界突刺**问题（最高 2x 通过）
> ② **滑动窗口** ——把窗口切小格滑动统计，平滑突刺，Sentinel 用 LeapArray 实现
> ③ **漏桶** ——FIFO 桶 + 固定出水率，**严格平滑**但**无突发能力**，适合控制下游调用速率
> ④ **令牌桶** ——令牌匀速生成 + 请求消耗，**允许突发**（桶大小决定突发上限），**应用层限流首选**
>
> 业务规则：**业务限流用令牌桶**（突发友好）、**下游调用用漏桶**（保护下游）、**网络流量用漏桶**。
>
> **生产实现**：单机用 **Guava RateLimiter**（令牌桶，简单）、集群用 **Sentinel**（滑动窗口 + 多模式）或 **Redis + Lua**（原子令牌桶）。**Nginx limit_req 是漏桶**，做接入层粗粒度限流。
>
> 阈值**必须压测得到**，不要拍脑袋；限流配置要支持**热更新**（配置中心）；限流后要有**降级**，返回兜底数据或友好提示。
