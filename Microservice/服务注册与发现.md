# 服务注册与发现（理论 + 横向对比）

> 微服务的"基础设施级"组件——服务一多，靠静态 IP 配置就崩了，必须有注册中心。
> 本篇要解决的问题：
> ① 没有注册中心，微服务调用怎么挂的？为什么要"注册-发现"模型？
> ② **Eureka / Nacos / Consul / ZooKeeper / etcd** 五大主流方案的核心差异是什么？
> ③ **AP vs CP** 在注册中心选型上为什么 AP 更合适？阿里为什么放弃 ZK 改用 Nacos？
> ④ **客户端发现 vs 服务端发现**两种架构的取舍
> ⑤ 注册中心**自身高可用**怎么做？
>
> 本篇是**理论与选型层**——具体实现细节看 [Spring/Nacos](./Nacos.md)。

---

## 一、为什么需要注册中心

### 1.1 没注册中心的灾难

最朴素的微服务调用：硬编码 IP 列表。

```java
// 调用方
String url = "http://192.168.1.5:8080/user/get";
String result = httpClient.get(url);
```

**三大问题**：

| 问题 | 现象 |
| --- | --- |
| **IP 变更要改代码** | 服务部署到新机器 → 改 N 个调用方 → 重启所有调用方 |
| **不知道实例死活** | IP 写死，那台机器挂了请求继续打过去 → 大量超时 |
| **新增/扩容麻烦** | 加一台机器要让所有调用方知道 |

### 1.2 注册中心模型

```
                      [注册中心]
                       (Nacos)
                      ↗   ↑   ↘
              ① 注册 │   │ ② 心跳
                    │   │
        [user-service]   [order-service]
              │             ↑
              └─③ 发现+调用─┘
              
工作流程：
  ① 服务启动时把自己的 IP:Port 注册到注册中心
  ② 定期发心跳证明自己活着
  ③ 调用方从注册中心拉服务列表 + 负载均衡选实例
  ④ 服务下线 / 心跳超时 → 注册中心剔除
```

**核心三件事**：注册（Register）、发现（Discover）、健康检查（Health Check）。

### 1.3 引入注册中心解决了什么

| 问题 | 解法 |
| --- | --- |
| IP 不再写死 | 服务名 → 动态实例列表 |
| 死实例自动剔除 | 心跳 / 主动探测 + 超时 |
| 扩缩容免重启 | 新实例注册即可被发现 |
| 灰度 / 多机房 | 元数据标签 + 路由策略 |

## 二、注册中心的核心机制

### 2.1 注册流程

```
服务启动
  │
  ├─ 自检（HTTP/TCP 端口能通）
  │
  ├─ 向注册中心 PUT instance
  │   {
  │     serviceName: "user-service",
  │     ip: "192.168.1.5",
  │     port: 8080,
  │     metadata: {version: "1.0", region: "bj"}
  │   }
  │
  └─ 启动心跳线程（5s 一次）
```

### 2.2 健康检查的两种模式

| 模式 | 实现 | 代表 | 优缺点 |
| --- | --- | --- | --- |
| **客户端心跳**（push） | 客户端每 N 秒发 heartbeat | Eureka、Nacos 临时实例 | ✅ 简单、压力分散 ❌ 客户端假死时心跳还在发 |
| **服务端探测**（pull） | 注册中心主动 HTTP/TCP 探测 | Consul、Nacos 永久实例 | ✅ 更可靠 ❌ 注册中心压力大 |

### 2.3 服务发现的两种模型

#### 模型 A：客户端发现（Client-Side Discovery）

```
[Client] ──直接连──► 注册中心拉取实例列表
   │
   └─ 客户端自己负载均衡 → 直接调用 [Server 实例]
```

代表：Eureka + Ribbon、Spring Cloud LoadBalancer、Dubbo。

✅ 性能高（少一跳）
✅ 客户端可定制策略
❌ 多语言成本高（每种语言都要实现 SDK）

#### 模型 B：服务端发现（Server-Side Discovery）

```
[Client] ──► [LB / Gateway] ──► 注册中心查询 → 转发 → [Server 实例]
```

代表：K8s Service + kube-proxy、AWS ELB、Istio Sidecar。

✅ 客户端零感知
✅ 多语言友好
❌ 多一跳（性能损失 1-2ms）
❌ LB / Sidecar 自身要高可用

### 2.4 推送 vs 拉取

| 模式 | 实时性 | 实现 |
| --- | --- | --- |
| **客户端定时拉取** | 秒~10 秒级 | Eureka（30s 拉一次） |
| **长轮询** | 接近实时 | Nacos 1.x 配置中心 |
| **gRPC 长连接推送** | **毫秒级** | Nacos 2.x、etcd Watch |
| **ZK Watcher** | 毫秒级 | ZK 注册中心 |

## 三、五大主流方案对比

### 3.1 横向对比表（必备）

| 维度 | **Nacos** | **Eureka** | **Consul** | **ZooKeeper** | **etcd** |
| --- | --- | --- | --- | --- | --- |
| **CAP** | **AP / CP 可切** | AP | CP | CP | CP |
| **协议** | Distro / Raft | P2P | Raft | ZAB | Raft |
| **健康检查** | 心跳 + 主动探测 | 心跳 | TCP/HTTP/Script/gRPC | 临时节点会话 | Lease + KeepAlive |
| **配置中心** | ✅ **一体** | ❌ | ✅ KV | ❌ | ✅ KV |
| **多语言 SDK** | Java / Go / Python / Node | Java 为主 | 多语言 | 多语言 | 多语言 |
| **服务发现协议** | HTTP / gRPC | HTTP | HTTP / DNS | TCP | gRPC |
| **运维复杂度** | 中 | 低 | 中 | **高** | 中 |
| **维护现状** | 阿里持续维护 | **已停更** | HashiCorp | Apache | CNCF |
| **典型用户** | 阿里、字节、美团 | Netflix（已迁走） | 海外为主 | 老 Java 项目 | K8s、云原生 |

### 3.2 五大方案各自的核心特点

#### Nacos（国内事实标准）
- **AP/CP 双模式**：注册走 Distro AP，配置走 Raft CP
- **临时实例 vs 永久实例**：临时给微服务，永久给基础设施
- **二合一**：注册中心 + 配置中心
- 详见 [Spring/Nacos](./Nacos.md)

#### Eureka（已退场）
- Netflix 出品，Spring Cloud 早期标配
- 纯 AP，自我保护机制（短时间剔除过多实例就不剔除了）
- **2.0 闭源、1.x 停止维护**——新项目别选

#### Consul（HashiCorp）
- 海外更流行，**功能最全**
- 健康检查机制最丰富（HTTP/TCP/Script/gRPC/Docker）
- 自带 KV、ACL、多数据中心、DNS 接口
- Go 写的，性能好但 Java 生态不强

#### ZooKeeper（老牌劲旅）
- 强一致 CP，临时节点 + Watcher
- **不适合做注册中心**：CP 性质让分区时整片不可用
- 阿里早期用 ZK，2018 年迁到 Nacos
- 现在 ZK 主要做：分布式锁、配置中心、Kafka/HBase 协调

#### etcd（K8s 御用）
- Raft 协议，CP，云原生明星
- K8s 所有元数据存 etcd
- gRPC + Watch + Lease，接口现代
- 但 Java 生态不如 ZK 成熟

## 四、AP vs CP：注册中心的核心选择

### 4.1 为什么注册中心**应该选 AP**

**核心矛盾**：网络分区时，调用方应该看到"过时但能用"的服务列表，还是"啥也看不到"？

| 选 CP | 选 AP |
| --- | --- |
| 分区时少数派注册中心拒绝服务 | 分区时各节点独立维护服务列表 |
| 调用方拿不到任何列表 → 业务直接挂 | 调用方拿到可能过时的列表 → 配合熔断重试可以恢复 |
| **小问题放大成致命故障** | **小问题被业务侧的容错机制吸收** |

### 4.2 阿里弃 ZK 改 Nacos 的根因

阿里巴巴 2018 年发文《阿里巴巴为什么不用 ZooKeeper 做服务发现》，三大理由：

#### 理由 1：CP 性质不匹配

> 当 Master 挂掉，ZK 集群进入选举状态（典型 30s+），期间集群整体不可写，导致整个微服务体系**瘫痪**。
> 而注册中心场景下，宁愿调用方拿到"过期 1 分钟的实例列表"，也不能"啥都看不到"。

#### 理由 2：写性能差

> ZK 所有写都要走 Leader，过半数 Follower 确认才成功。
> 阿里规模下 1 万+服务、几十万实例，**ZK 写 QPS 撑不住**。

#### 理由 3：Watch 羊群效应

> ZK Watcher 一次性触发：一个节点变化 → 所有 watch 它的客户端被通知 → 大规模实例时**广播风暴**。
> Nacos 用长轮询 + 推送，**只通知关心这个服务的客户端**。

### 4.3 配置中心为什么要 CP

跟注册中心反过来——配置不能短暂不一致：

```
分区时：
  [A 集群] 配置里 enable_payment=true
  [B 集群] 配置里 enable_payment=false   ← 一半实例放行交易、一半实例拦截 → 数据混乱
```

CP 牺牲一点可用性（少数派拒绝写入），换来"配置永远一致"。这就是为什么 Nacos 配置中心走 Raft（CP），而注册走 Distro（AP）。

## 五、注册中心自身高可用

### 5.1 集群部署

注册中心必须**奇数节点**（3 / 5 / 7），CP 协议要求过半数确认：

```
[Nacos-1]   [Nacos-2]   [Nacos-3]
    │          │           │
    └──────────┴───────────┘
                │
        ┌───────┴────────┐
        │                │
   [MySQL 主]      [MySQL 从]    ← 配置和永久实例持久化
   
   临时实例 → 内存 + Distro 同步
```

### 5.2 客户端容错

注册中心也会挂 → **客户端必须能容错**：

| 容错策略 | 作用 |
| --- | --- |
| **本地缓存** | 上次拉到的服务列表存内存 → 注册中心挂了仍能调用 |
| **本地磁盘快照** | 启动时注册中心慢，从磁盘快照恢复（`~/nacos/naming/`） |
| **Failover 模式** | 注册中心全挂时切到本地静态配置 |
| **熔断 + 重试** | 调到死实例自动切下一个 |

### 5.3 注册中心前置 SLB

```
[Client]  →  [SLB / Nginx VIP]  →  [Nacos-1, Nacos-2, Nacos-3]
              ↑
              客户端只配 SLB 地址，不感知节点变化
```

好处：节点扩缩容客户端不用改配置；SLB 自动剔除挂掉的 Nacos 节点。

## 六、生产踩过的坑

### 坑 1：用 ZK 当注册中心，机房抖动整站挂

> 公司初期用 ZK 注册中心，机房网络抖 30s → ZK Leader 切换 → 服务发现 503 → 全站不可用。
> **修复**：迁移到 Nacos AP 模式，分区时容错。

### 坑 2：Eureka 自我保护误伤

> Eureka 自我保护：15 分钟内心跳丢失超过 85% → 不剔除任何实例（防止网络抖动误剔除）。
> 真发生大面积故障时（如机房断电）→ 实例真的死了，但 Eureka 不剔除 → 调用方一直打死实例。
> **修复**：紧急关闭自我保护 `eureka.server.enable-self-preservation=false` 或调整阈值。

### 坑 3：1.x → 2.x Nacos 升级防火墙挂了

> 升级 Nacos 到 2.x，客户端报 `Client not connected` → 防火墙没开 9848/9849（gRPC 端口）。
> **修复**：开放 8848 + 9848 + 9849 三个端口；安全组也要放行。

### 坑 4：服务发布时流量打到已下线实例

> Pod 关闭瞬间从 Nacos 注销，但客户端有 10s 缓存延迟 → 这 10s 流量打到 502。
> **修复**：① 优雅下线（先 deregister，等 30s 再停服务）；② Spring Boot Actuator `/shutdown` 钩子；③ K8s `preStop` 配合 `terminationGracePeriodSeconds`。

### 坑 5：Nacos 控制台默认账号被扫

> 公网暴露 Nacos 控制台，默认 `nacos/nacos` 被扫到 → 配置全被读走（包括 DB 密码）。
> **修复**：① 控制台放内网；② 启用鉴权 `nacos.core.auth.enabled=true`；③ 改默认密码 + 加 IP 白名单。

### 坑 6：临时实例和永久实例混用

> 开发把 MySQL 实例注册成"临时实例"——MySQL 当然不主动发心跳 → 30s 后被 Nacos 剔除 → 业务找不到 DB。
> **修复**：基础设施类（DB / Redis / 第三方 API）必须用**永久实例**（`ephemeral=false`），由 Nacos 主动探测。

### 坑 7：心跳间隔过短打爆 Nacos

> 几万实例每 1s 一次心跳 → Nacos QPS 几万 → CPU 100%。
> **修复**：心跳间隔 5s 起步；Nacos 2.x 用 gRPC 长连接，省掉独立心跳。

## 七、面试高频追问

### Q1：服务注册发现解决什么问题？

三个核心问题：① IP 写死要改代码；② 不知道实例死活；③ 扩缩容麻烦。
注册中心的本质是**动态服务名 → 实例列表的映射 + 健康状态维护**。

### Q2：Eureka / Nacos / Consul / ZK / etcd 怎么选？

```
新项目 + 国内 + Java                → Nacos（事实标准）
K8s / 云原生                        → etcd（K8s 自带）+ Service Discovery
Polyglot（多语言混合）              → Consul / Nacos
老项目 + 已有 ZK                    → ZK（不推荐，但能用）
新项目                              → 不要选 Eureka（已停更）
```

### Q3：为什么注册中心选 AP 而不是 CP？

调用方宁愿拿到"过时但有"的实例列表（业务侧靠熔断重试容错），也不能拿不到任何列表（业务直接挂）。
注册中心 1 秒延迟可接受，整体不可用不可接受。

### Q4：阿里为什么放弃 ZK 改用 Nacos？

三个根因：① ZK 是 CP，分区时不可用；② 写性能差，撑不住几十万实例；③ Watch 羊群效应导致广播风暴。
Nacos 用 AP（Distro）+ 长连接推送 + 配置中心一体化，解决这些问题。

### Q5：客户端发现 vs 服务端发现 怎么选？

| | 客户端发现 | 服务端发现 |
| --- | --- | --- |
| 性能 | 高（少一跳） | 低（多一跳 1-2ms） |
| 多语言 | 难 | 易 |
| 客户端复杂度 | 高 | 零 |
| 代表 | Spring Cloud、Dubbo | K8s Service、Istio |

Java 体系基本都是客户端发现；K8s 体系基本是服务端发现。

### Q6：服务下线后调用方多久能感知？

| 注册中心 | 下线感知延迟 |
| --- | --- |
| Eureka | 30~90s（自我保护时更长） |
| Nacos 1.x | 10~15s（5s 心跳 + 客户端缓存） |
| Nacos 2.x | **秒级**（gRPC 推送） |
| ZK | **毫秒级**（Watcher） |
| Consul | 取决于健康检查间隔 |

业务侧必须配合：**优雅下线** + **熔断**，避免那个延迟窗口打死实例。

### Q7：注册中心挂了业务还能跑吗？

**应该能**——靠客户端兜底：
1. 本地缓存上次的服务列表（内存 + 磁盘快照）
2. 现有连接保持不动
3. 新建连接用缓存的实例
4. 配合熔断重试

如果注册中心挂了业务就挂——架构有问题。

### Q8：注册中心和配置中心为什么要分开 CAP 取舍？

注册中心：服务发现，**短暂过时可接受**，要 AP（高可用优先）。
配置中心：配置一致性，**短暂不一致致命**（一半实例新配置一半旧配置），要 CP。

Nacos 用同一套基础设施支持两种模式，是它对比 Eureka 的核心优势。

### Q9：服务实例的元数据有什么用？

```yaml
metadata:
  version: 1.0
  region: bj-1
  weight: 80
  canary: false
```

用途：
- **灰度发布**：按 version 路由（v1.1 给 1% 流量）
- **就近调用**：按 region 优先选同机房实例
- **权重负载**：按 weight 分流
- **金丝雀**：canary=true 只接受灰度用户

### Q10：服务发现的健康检查机制对比？

| 机制 | 灵敏度 | 资源占用 |
| --- | --- | --- |
| 心跳（客户端推） | 中（5-30s） | 客户端 CPU 一点 |
| 主动探测（HTTP） | 中（5-30s） | 注册中心带宽 |
| 长连接保活（gRPC） | **高**（秒级） | 长连接资源 |
| 临时节点会话（ZK） | **高**（毫秒级） | TCP 连接 |

## 八、答题模板（60 秒话术）

> 注册中心解决三个问题：**IP 不写死、自动剔除死实例、扩缩容免重启**。
>
> **五大方案**：① **Nacos**（国内事实标准）AP/CP 双模式，注册走 Distro AP、配置走 Raft CP，二合一；② **Eureka**（Netflix）纯 AP，已停更不要选；③ **Consul**（HashiCorp）CP，海外流行，功能最全；④ **ZooKeeper** CP，**不适合做注册中心**——分区不可用 + 写性能差 + Watch 羊群效应；⑤ **etcd** CP，K8s 御用。
>
> **核心选型逻辑**：注册中心**必须 AP**——调用方宁愿拿过时列表也不能拿不到列表。配置中心**必须 CP**——一半实例新一半旧会出大问题。这就是 Nacos 双模式的根源。
>
> **阿里弃 ZK 改 Nacos**：CP 不匹配 + 写性能差 + Watch 羊群效应。
>
> **生产关键**：① 客户端**本地缓存**，注册中心挂了业务还能跑；② 心跳 5s 起步避免压垮注册中心；③ **优雅下线**（先 deregister 再停服务）；④ 控制台放内网 + 鉴权（默认密码会被扫）；⑤ DB / Redis 用永久实例（不会主动心跳）；⑥ 注册中心前置 SLB 简化客户端配置。
>
> 跟 Spring Cloud 配套：注册中心 Nacos + 客户端发现 + Ribbon/LoadBalancer 负载均衡 + Feign RPC，是国内微服务最主流栈。
