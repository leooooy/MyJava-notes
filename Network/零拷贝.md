# 零拷贝（Zero-Copy）

> "Kafka 为什么这么快？" / "Netty 的零拷贝有几种？" / "sendfile 和 mmap 谁快？" —— 这是中间件面试的**性能题三连击**。
> 本篇要解决：
> ① 传统 IO **4 次拷贝 + 4 次切换** 的浪费在哪
> ② **mmap / sendfile / splice / sendfile + DMA gather** 各减了几次拷贝
> ③ **Java 层零拷贝**（FileChannel.transferTo、MappedByteBuffer、Netty CompositeByteBuf）和**OS 层零拷贝**的区别
> ④ Kafka / RocketMQ / Netty / Nginx 各自用的是哪种

---

## 一、为什么需要零拷贝

### 1.1 传统 IO 的浪费

场景：从磁盘读文件 → 通过网络发送（最常见的 Web/MQ/CDN 场景）。

```c
read(file_fd, buf, len);
write(socket_fd, buf, len);
```

**这两行代码背后的真实成本**：

```
                                    用户态                            内核态                          硬件
                              ┌───────────────┐               ┌───────────────────┐              ┌────────┐
                              │  用户缓冲区    │               │   PageCache       │              │  磁盘   │
                              │     buf       │ ◄───CPU拷贝──│   (内核缓冲区)     │ ◄──DMA拷贝──│         │
                              └───────────────┘               └───────────────────┘              └────────┘
                                                                                                 ┌────────┐
                                                              ┌───────────────────┐              │  网卡   │
                                                              │  socket buffer    │ ───DMA拷贝──►│         │
                                                              └───────────────────┘              └────────┘
                                                                       ▲
                                                                       │ CPU 拷贝
                                                              ┌───────────────┐
                                                              │  用户缓冲区    │
                                                              │     buf       │
                                                              └───────────────┘
```

**4 次拷贝 + 4 次上下文切换**：

| 步骤 | 操作 | 拷贝次数 | 切换次数 |
| --- | --- | --- | --- |
| 1 | 调 `read()` | — | 用户→内核（切换 1） |
| 2 | DMA：磁盘 → PageCache | DMA 拷贝 1 | — |
| 3 | CPU：PageCache → 用户 buf | **CPU 拷贝 1** ⚠️ | — |
| 4 | `read()` 返回 | — | 内核→用户（切换 2） |
| 5 | 调 `write()` | — | 用户→内核（切换 3） |
| 6 | CPU：用户 buf → socket buffer | **CPU 拷贝 2** ⚠️ | — |
| 7 | DMA：socket buffer → 网卡 | DMA 拷贝 2 | — |
| 8 | `write()` 返回 | — | 内核→用户（切换 4） |

**浪费的本质**：数据**根本没被用户态修改**，却被 CPU 来回拷贝两次。`read` 把数据从内核拉到用户，`write` 又把它推回内核——纯属多余。

### 1.2 零拷贝的目标

**砍掉 CPU 拷贝**（DMA 拷贝是硬件干的，砍不掉）+ **减少用户↔内核切换**。

> ⚠️ "零拷贝"不是**真的零次拷贝**——硬件 DMA 拷贝是必须的。指的是**减少 CPU 参与的拷贝**和**减少用户态↔内核态切换**。

## 二、零拷贝技术演进

### 2.1 mmap + write（减 1 次 CPU 拷贝）

**原理**：`mmap` 把内核 PageCache **映射到用户虚拟地址**——用户态可以直接访问 PageCache，不需要拷贝过来。

```c
void *mapped = mmap(NULL, len, PROT_READ, MAP_PRIVATE, file_fd, 0);
write(socket_fd, mapped, len);
```

**流程**：

```
用户调 mmap()      → 切换 1 (用户→内核)
DMA: 磁盘 → PageCache
mmap 返回地址      → 切换 2 (内核→用户)
                     ⚠️ 此时 PageCache 已映射到用户空间，无需拷贝
用户调 write()     → 切换 3
CPU: PageCache → socket buffer  ⚠️ 仍有 1 次 CPU 拷贝
DMA: socket buffer → 网卡
write 返回         → 切换 4
```

**收益**：
- ✅ **3 次拷贝**（2 DMA + 1 CPU），少 1 次 CPU 拷贝。
- ❌ **4 次切换** 没变。

**适用**：用户态需要修改数据后再发送（如加水印、加密）的场景。

**坑**：
- 多进程并发写同一 mmap 文件，可能出现页面抖动。
- mmap 文件被截断（truncate）会触发 SIGBUS。
- **大文件 mmap 会消耗大量虚拟地址空间**（32 位系统直接撑爆）。

---

### 2.2 sendfile（减 1 次切换）

**Linux 2.1 引入**，专为"文件 → socket"场景设计。

```c
ssize_t sendfile(int out_fd, int in_fd, off_t *offset, size_t count);
```

**流程**（Linux 2.1~2.4 版本）：

```
用户调 sendfile()       → 切换 1
DMA: 磁盘 → PageCache
CPU: PageCache → socket buffer  ⚠️ 仍有 1 次 CPU 拷贝
DMA: socket buffer → 网卡
sendfile 返回           → 切换 2
```

**收益**：
- ✅ **3 次拷贝**（2 DMA + 1 CPU）。
- ✅ **2 次切换**（少了 read/write 中间的两次）。

**Java 对应**：

```java
FileChannel src = new FileInputStream("foo").getChannel();
SocketChannel dst = ...;
src.transferTo(0, src.size(), dst);     // 底层调 sendfile
```

---

### 2.3 sendfile + DMA gather（**真·零 CPU 拷贝**）⭐

**Linux 2.4 起**，配合**支持 SG-DMA（Scatter-Gather DMA）的网卡**。

**关键点**：socket buffer 不再存数据，只存**指向 PageCache 的描述符**（地址 + 长度）。网卡通过 SG-DMA 直接从 PageCache **多段聚合读取**。

```
用户调 sendfile()       → 切换 1
DMA: 磁盘 → PageCache
内核把 PageCache 的地址+长度写入 socket buffer   ⚠️ 不是数据，只是描述符
SG-DMA: 网卡按描述符直接从 PageCache 拉数据 → 网卡
sendfile 返回           → 切换 2
```

**收益**：
- ✅ **2 次 DMA 拷贝，0 次 CPU 拷贝** —— **真正的零拷贝**！
- ✅ **2 次切换**。

**前提**：
- 网卡支持 SG-DMA（现代万兆/百兆网卡都支持）。
- Linux 2.4+。

---

### 2.4 splice（任意 fd 间零拷贝）

**Linux 2.6.17 引入**，比 sendfile 更通用：可在**任意两个 fd 之间**用管道传输（不限于"文件→socket"）。

```c
ssize_t splice(int fd_in, loff_t *off_in,
               int fd_out, loff_t *off_out,
               size_t len, unsigned int flags);
```

底层用**内核管道**（pipe buffer）作中转，但只传**指针**不复制数据。

**适用**：socket → socket（代理服务器）、文件 → 文件等更复杂场景。

## 三、对比一图流

| 方案 | 拷贝次数 | 切换次数 | CPU 拷贝 | 典型应用 |
| --- | --- | --- | --- | --- |
| 传统 read+write | 4 | 4 | **2 次** | — |
| mmap + write | 3 | 4 | 1 次 | 数据库 buffer pool、JVM CMS old gen |
| sendfile（2.1~2.4） | 3 | **2** | 1 次 | 旧版 Kafka |
| **sendfile + SG-DMA**（2.4+） | **2** | **2** | **0 次** ⭐ | **Kafka / Nginx / RocketMQ** |
| splice | 2 | 2 | 0 次 | 代理（HAProxy）、socket-to-socket |

## 四、Java 层零拷贝实现

### 4.1 `FileChannel.transferTo` / `transferFrom`

底层在 Linux 上调 **sendfile**。

```java
// Kafka 的 NetworkSend 大致逻辑
FileChannel fileChannel = new FileInputStream(logFile).getChannel();
fileChannel.transferTo(position, count, socketChannel);
```

**Kafka 之所以快**就靠这个 + PageCache。Producer 写入直接进 PageCache，Consumer 读取通过 sendfile 从 PageCache 直接到网卡——**全程不进 JVM 堆**。

### 4.2 `MappedByteBuffer`（mmap）

```java
FileChannel ch = new RandomAccessFile("data", "rw").getChannel();
MappedByteBuffer buf = ch.map(FileChannel.MapMode.READ_WRITE, 0, ch.size());
buf.put(...);                    // 直接修改 PageCache
```

**RocketMQ CommitLog 用 mmap**——消息写入直接写映射区，由内核异步刷盘。
**问题**：`unmap` 没有标准 API，靠 GC 释放，可能内存泄漏（生产用 `Cleaner.clean()` 反射强制释放）。

### 4.3 Netty 的"零拷贝"（**广义零拷贝**）

**注意**：Netty 自称的零拷贝**主要不是指 OS 层 sendfile**，而是**应用层减少 ByteBuf 之间的拷贝**：

| Netty 零拷贝技术 | 含义 |
| --- | --- |
| **CompositeByteBuf** | 把多个 ByteBuf **逻辑组合**为一个，无需 memcpy。常用于 header + body 的合并。 |
| **Unpooled.wrappedBuffer** | 把 byte[] / ByteBuffer **包装**成 ByteBuf，不拷贝底层数组。 |
| **slice / duplicate** | **共享内存**的视图切片。 |
| **FileRegion**（DefaultFileRegion） | 底层调 `transferTo` → sendfile，**这个才是 OS 层零拷贝**。 |
| **DirectByteBuf** | 用堆外内存，省去 JVM 堆 → Native 之间一次拷贝（JVM IO 时通常要先拷到堆外）。 |

**面试题**："说说 Netty 的零拷贝"——要区分**应用层（CompositeByteBuf）**和**OS 层（FileRegion）**。

## 五、生产应用场景速记

| 中间件 | 零拷贝技术 | 用在哪 |
| --- | --- | --- |
| **Kafka** | sendfile（transferTo） | Consumer 读消息：log file → socket |
| **Kafka** | mmap | index 文件读写 |
| **RocketMQ** | mmap | CommitLog 写入（顺序写 + PageCache） |
| **RocketMQ** | sendfile | 消息推给 Consumer |
| **Nginx** | sendfile | 静态文件下发（`sendfile on;`） |
| **Netty** | FileRegion + transferTo | 大文件下载、CDN |
| **Netty** | CompositeByteBuf | 协议编解码（header+body 合并） |
| **MySQL InnoDB** | mmap（部分） | 双写缓冲、redo log（依赖配置） |
| **HAProxy** | splice | TCP 代理转发 |

## 六、生产踩坑

### 坑 1：MappedByteBuffer 内存泄漏

**现象**：JVM 堆只用了 2GB，但 RES 涨到 20GB，最终 OOM Killer 杀进程。

**根因**：mmap 的虚拟内存不受 -Xmx 限制；`unmap` 没标准 API，靠 `Cleaner` 在 GC 时触发。如果**老年代 GC 频率低**，mmap buffer 一直不释放。

**修复**（RocketMQ 源码做法）：

```java
public static void clean(ByteBuffer buffer) {
    if (buffer == null || !buffer.isDirect() || buffer.capacity() == 0) return;
    // 反射调 sun.misc.Cleaner.clean()
    Method getCleanerMethod = buffer.getClass().getMethod("cleaner");
    Object cleaner = getCleanerMethod.invoke(buffer);
    Method cleanMethod = cleaner.getClass().getMethod("clean");
    cleanMethod.invoke(cleaner);
}
```

### 坑 2：sendfile 大文件阻塞 IO 线程

**现象**：Kafka 单条消息特别大（比如 1GB），sendfile 调用阻塞 IO 线程几秒，整个 Reactor 卡住。

**根因**：sendfile 是**同步系统调用**，文件越大、网络越慢，阻塞越久。

**修复**：
- 限制单条消息大小（Kafka `message.max.bytes` 默认 1MB）。
- IO 线程和业务线程分离（Netty 主从 Reactor）。
- 流式分块发送，避免单次 sendfile 过长。

### 坑 3：mmap 文件被 truncate 触发 SIGBUS

**现象**：进程突然挂掉，dmesg 看到 SIGBUS。

**根因**：mmap 映射的文件被另一个进程 truncate，访问已映射但已释放的页面 → 内核发 SIGBUS。

**修复**：
- 文件系统加锁。
- mmap 之前先校验文件大小，运行期间禁止 truncate。

### 坑 4：sendfile 不能用于"中间需要修改"的场景

**误区**：业务想加水印、加密、压缩，还想用 sendfile。

**真相**：sendfile 是**纯透传**——文件数据原封不动从 PageCache 到网卡，**用户态根本看不到数据**。要修改必须 read 到用户空间。

**折中**：用 mmap（数据在 PageCache，用户态可访问） + write。

### 坑 5：网卡不支持 SG-DMA 时 sendfile 仍有 CPU 拷贝

老机器、虚拟网卡（virtio）可能不支持 SG-DMA → sendfile 退化为 1 次 CPU 拷贝。

**排查**：`ethtool -k <iface>` 看 `tx-scatter-gather: on` 是否开启。

### 坑 6：DirectByteBuf 内存泄漏

Netty 的 DirectByteBuf 需要**手动 `release()`**，否则堆外内存一直涨。

```java
ByteBuf buf = ctx.alloc().directBuffer(1024);
try {
    // 用 buf
} finally {
    buf.release();              // 必须！或用 ReferenceCountUtil.release(msg)
}
```

**生产排查**：开启 `-Dio.netty.leakDetection.level=PARANOID`，泄漏时打印创建堆栈。

## 七、面试高频追问

**Q1：Kafka 为什么这么快？**
- **顺序写 PageCache**：磁盘顺序写比随机写快 3 个数量级。
- **零拷贝（sendfile）**：Consumer 读消息全程 0 次 CPU 拷贝，PageCache → 网卡。
- **批量发送 + 压缩**：Producer 端攒批，减少网络往返。
- **分区并行**：partition 物理隔离，多消费者并行消费。
- 详见 [MQ 模块](../MQ/RocketMQ架构.md)。

**Q2：mmap 和 sendfile 怎么选？**
- 数据**只读不改 + 文件→socket**：sendfile（最少拷贝）。
- 数据**需要在用户态修改**：mmap（用户态可访问）。
- **Kafka/RocketMQ 同时用**：写入用 mmap（顺序写 PageCache），读取发送用 sendfile。

**Q3：sendfile 和 sendfile + SG-DMA 区别？**
- 普通 sendfile：1 次 CPU 拷贝（PageCache → socket buffer）。
- SG-DMA：0 次 CPU 拷贝，socket buffer 只存描述符，网卡 SG-DMA 直接拉 PageCache 数据。
- 现代 Linux + 现代网卡默认就是后者。

**Q4：Netty 的零拷贝是 OS 零拷贝吗？**
**主要不是**。Netty 的零拷贝是**应用层概念**：
- CompositeByteBuf 逻辑合并（避免 ByteBuf 之间 memcpy）。
- slice/duplicate（共享内存视图）。
- 只有 **FileRegion** 是真正调 sendfile 的 OS 零拷贝。

**Q5：DirectByteBuf 跟零拷贝什么关系？**
DirectByteBuf 用**堆外内存**，避免 JVM 在 IO 时把堆内数据拷到堆外（JNI 限制）。这少了**一次 JVM 内的拷贝**，是 JVM 层零拷贝。

**Q6：零拷贝节省的 CPU 拷贝、PageCache 命中率，分别要多少 ns？**
| 操作 | 时延量级 |
| --- | --- |
| L1 cache | ~1 ns |
| memcpy 1KB（CPU 拷贝） | ~100 ns |
| memcpy 1MB | ~100 μs |
| 系统调用切换 | ~100 ns ~1 μs |
| 磁盘随机读（HDD） | ~10 ms |
| 磁盘顺序读（SSD） | ~100 μs |
所以**零拷贝在大文件 + 高并发场景**收益最显著。

**Q7：splice 和 sendfile 有啥不同？**
- sendfile 只能"文件 → socket"（in_fd 必须可 mmap）。
- splice 通过内核管道做中转，**任意 fd 之间都行**（socket → socket、socket → file 等）。
- 代理服务器（HAProxy）用 splice，Kafka 用 sendfile。

**Q8：零拷贝和 PageCache 的关系？**
零拷贝**强依赖 PageCache**——sendfile 拷的就是 PageCache 数据。所以：
- PageCache 命中率 = 零拷贝实际效果上限。
- Kafka 之所以推荐 **giant memory + 不调小 PageCache**，就是这个原因。
- Direct IO（绕 PageCache）反而失去零拷贝收益。

**Q9：为什么 read+write 比直接 sendfile 慢这么多，仅仅是 CPU 拷贝吗？**
不止：
- CPU 拷贝（CPU 周期）。
- 用户态缓冲区占内存。
- 4 次模式切换 vs 2 次（每次切换都要保存/恢复寄存器）。
- L1/L2 cache 失效（数据在内核↔用户来回，cache 命中差）。

**Q10：Java NIO `FileChannel.transferTo` 在 Windows 上是零拷贝吗？**
看 JVM 实现。HotSpot 在 Windows 用 `TransmitFile`（也是 Windows 的零拷贝 API）。但**有 2GB 限制**（一次 transferTo 上限），需循环调。Linux 下 sendfile 也有 2GB 单次限制（`MAX_RW_COUNT`）。

## 八、答题模板（60 秒话术）

> "传统 IO 读文件发网络，**4 次拷贝 + 4 次用户态↔内核态切换**——其中 2 次是 **CPU 拷贝**完全多余，因为数据在用户态根本没改过。
>
> **零拷贝**就是减少这部分浪费，主要 4 种方案：
>
> ① **mmap + write**：用户态直接映射 PageCache，省 1 次 CPU 拷贝（变 3 次拷贝 4 次切换）。适合**用户要改数据**的场景，如 RocketMQ CommitLog。
>
> ② **sendfile**：内核内部一次性把文件→PageCache→socket buffer→网卡，省 1 次 CPU 拷贝 + 2 次切换（变 3 次拷贝 2 次切换）。Java 对应 `FileChannel.transferTo`。
>
> ③ **sendfile + SG-DMA（Linux 2.4+）**：socket buffer 只存描述符，网卡直接拉 PageCache → **0 次 CPU 拷贝、2 次 DMA、2 次切换**——真正的零拷贝。Kafka、Nginx 用这个。
>
> ④ **splice**：基于内核管道，**任意 fd 之间**零拷贝（不限文件→socket），代理服务器用。
>
> Netty 的零拷贝是**两层**：① OS 层 `FileRegion` → sendfile；② 应用层 `CompositeByteBuf` / `slice` 减少 ByteBuf 之间的 memcpy。
>
> 经典应用：**Kafka 写 PageCache（顺序写）+ 读 sendfile**，这是 Kafka 高吞吐的核心。**RocketMQ CommitLog 用 mmap，消费下发用 sendfile**。**Nginx `sendfile on`** 默认开。
>
> 关键限制：① 数据要改不能用 sendfile；② mmap 大文件吃虚拟地址；③ Java mmap 释放靠 GC，生产要反射调 Cleaner.clean。"
