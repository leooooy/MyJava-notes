# 反向代理（Reverse Proxy）

> 引子：几乎所有互联网公司的流量入口，第一跳都是反向代理（Nginx / HAProxy / LVS / 云 SLB / API 网关），它是后端架构里**最容易被当成"就是个 Nginx 配置"而答浅**的题。
> ① 它是什么、和正向代理到底差在哪（一刀切：代理的是**客户端**还是**服务端**）
> ② 它凭什么成为机房入口的"统一前台"——解决了隐藏后端、横向扩展、TLS/限流/鉴权集中卸载这几件事
> ③ 三组高频混淆边界：反向代理 vs 负载均衡 vs API 网关 vs CDN；以及绕不开的**真实客户端 IP 透传（X-Forwarded-For）**
>
> 前置：[TCP 协议](./TCP协议.md)（反代是两段 TCP 的终结点）、[HTTP 协议](./HTTP协议.md)（七层代理改的就是 HTTP 头）。落地实现见 [Middleware/Nginx](../Middleware/Nginx.md)。

---

## 一、是什么：机房入口的"统一前台"

先用一个贯穿全篇的核心类比定心智模型：

> **反向代理 = 公司前台。** 你（客户端）打电话到公司总机，前台接起来，你以为是在跟"公司"说话，其实前台把你的需求转给后面真正干活的某个工位（后端服务器），再把结果拿回来念给你听。你**从头到尾不知道**是哪个工位处理的，也不知道公司里到底有几个工位——这就是"反向"的本质：**代理站在服务端这一侧，对客户端隐藏了真实服务器**。

对照"正向代理"（VPN / 公司上网代理）就一清二楚了：正向代理是**你家门口的中介**，替**你**去访问外网，隐藏的是**你**；反向代理是**对方公司门口的前台**，隐藏的是**服务器**。

| 维度 | 正向代理（Forward Proxy） | 反向代理（Reverse Proxy） |
| --- | --- | --- |
| 代理谁、站哪边 | 代理**客户端**，部署在客户端侧 | 代理**服务端**，部署在机房入口 |
| 谁感知不到对方 | 服务器不知道真实客户端 | 客户端不知道真实服务器 |
| 谁主动配置 | 客户端**主动**配置代理地址 | 客户端**无感知**，以为在直连 Server |
| 隐藏的是 | 隐藏**客户端** | 隐藏**真实后端** |
| 典型场景 | 科学上网、公司统一出口、爬虫 IP 池、缓存加速下载 | 负载均衡入口、HTTPS 卸载、API 网关、CDN 边缘 |
| 代表 | Squid / VPN / Shadowsocks / Clash | **Nginx** / HAProxy / Envoy / LVS / CDN / 云 SLB |

**一句话区分法则（面试可直接背）**：*代理服务器替谁隐身、帮谁说话——帮客户端隐身就是正向，帮服务器隐身就是反向。* 二者技术栈可以是同一个软件（Nginx 既能做正向也能做反向），区别只在**部署位置和代理对象**。

## 二、核心原理：两段连接 + 一个"终结点"

反向代理最关键、也最常被答漏的一点：**它不是"透传"，而是把一条连接拆成了两段，自己是中间的终结点（terminator）。**

```
   客户端                反向代理（Nginx/HAProxy）              后端 upstream
     │                          │                                  │
     │  ① TCP/TLS 连接 A         │                                  │
     ├─────────────────────────►│                                  │
     │  GET /api HTTP/1.1        │                                  │
     │  Host: api.foo.com        │  ② 选一台后端 + 建/复用连接 B     │
     │                          ├─────────────────────────────────►│
     │                          │  GET /api HTTP/1.1                │
     │                          │  Host: api.foo.com                │
     │                          │  X-Forwarded-For: <真实客户端IP>   │
     │                          │  X-Forwarded-Proto: https         │
     │                          │◄─────────────────────────────────┤
     │◄─────────────────────────┤        200 OK + body              │
     │       200 OK + body       │                                  │
     │                          │                                  │
     └── 连接 A：客户端 ↔ 代理     └── 连接 B：代理 ↔ 后端（可 keepalive 复用）
```

> **术语澄清：为什么后端叫 upstream（上游）？**（面试偶尔单独问）
> 以**请求流的方向**为基准，而不是"谁在上面"。把数据想象成一条河：**数据/响应从源头流向使用者**——后端**生产**响应、是源头，所以是**上游 upstream**；客户端**消费**响应，是**下游 downstream**。Nginx 里 `upstream {}` 块就是定义"这组后端是谁 + 怎么分发"。
> 注意这是**相对视角**：整条链路 `客户端 → Nginx → Tomcat → MySQL`，越往右越上游。站在 Nginx 看 upstream 是 Tomcat，站在 Tomcat 看 upstream 是 MySQL。常见近义词：`backend`（口语，≈ upstream）、`origin/回源`（CDN 语境下的真正源站）。

由"两段连接"推出的几个**必考结论**：

1. **TLS 在代理这里终结**（HTTPS 卸载）：客户端的 TLS 握手对端是代理，不是后端。所以证书装在代理上、后端可以走明文 HTTP，省掉后端 CPU 解密开销。代价：代理↔后端这段若跨机房，安全性要另想办法（mTLS / 内网隔离）。
2. **后端默认拿不到真实客户端 IP**：后端看到的 `remote_addr` 是代理的 IP（连接 B 的源地址）。真实 IP 必须靠代理塞进 `X-Forwarded-For` 头透传——这是第六节的重头戏。
3. **两段连接可以独立优化**：客户端侧大量短连接，后端侧用**长连接池复用**（keepalive），削掉后端反复三次握手 + TIME_WAIT 的开销。这正是反代能"扛流量"的工程基础。
4. **代理能改请求/响应**：加头、改 URL、压缩、缓存、限流、鉴权——因为它是完整收完再转发的应用层节点（七层代理时）。

### L4 vs L7：在哪一层做代理（面试核心分水岭）

反向代理按工作的网络层次分两类，这是高频追问点：

| 维度 | **四层代理（L4 / 传输层）** | **七层代理（L7 / 应用层）** |
| --- | --- | --- |
| 基于什么转发 | IP + 端口（TCP/UDP） | HTTP URL / Header / Cookie / Host |
| 看不看得到 HTTP 内容 | ❌ 看不到（不解析应用层） | ✅ 完整解析 HTTP |
| 能否按 URL/域名路由 | ❌ 不能 | ✅ 能（`/api` 走 A 集群，`/img` 走 B 集群） |
| TLS 能否卸载 | ❌ 一般透传（除非 SNI 路由） | ✅ 在此终结 |
| 性能 / 吞吐 | **更高**（不解析、可做 DR 直接路由） | 略低（要解析、缓冲、改头） |
| 代表 | **LVS** / F5 / Nginx stream / HAProxy(tcp) | **Nginx http** / HAProxy(http) / Envoy / Traefik |
| 典型部署 | 最外层入口，扛超大流量 | LVS 后面一层，做精细路由 |

**大厂典型分层**：`客户端 → DNS/CDN → LVS(L4，扛百万并发) → Nginx 集群(L7，按域名/路径路由 + TLS 卸载) → 后端微服务`。L4 负责"量"，L7 负责"精"。

#### 进阶追问：是不是每个代理都同时有 L4 和 L7？

**不是。** 而且先纠正一个常见误解：L4/L7 **不是同一个代理对一条连接同时干的两件事**——一旦在七层解析了 HTTP，就已经付出"完整收包 + 解析"的成本，不再是四层的纯转发。**同一条连接只能选一种处理方式**；一个软件"支持两层"指的是能**配成** L4 模式或 L7 模式，不是自动同时具备。

| 代理 | L4 | L7 | 说明 |
| --- | :---: | :---: | --- |
| **LVS** | ✅ | ❌ | **只有四层**。内核态 IPVS，不进用户态、不解析应用层 |
| **Nginx** | ✅ | ✅ | 分块：`http{}` 做 L7、`stream{}`(1.9+) 做 L4 |
| **HAProxy** | ✅ | ✅ | `mode tcp`(L4) / `mode http`(L7) 切换 |
| **Envoy** | ✅ | ✅ | 以 L7 为主，TCP proxy filter 做 L4 |
| **云 SLB** | ✅ | ✅ | 通常**拆成两个产品**：NLB(L4) / ALB(L7) |

**为什么 LVS 偏偏没有七层？**（设计取舍）LVS 工作在**内核态（IPVS）**，只看 IP+端口改包转发，**不需要把数据拷到用户态、不需要完整收完一个 HTTP 请求**；而七层必须"收包重组 → 解析 HTTP → 用户态决策 → 重新建连转发"，内核态做不了。**LVS 用"放弃七层能力"换来百万级并发**——这就是它只做 L4 的根因。

**那一条链路能不能既有 L4 又有 L7？** 能，但靠**分层串联、不是一个节点兼职**：`LVS(L4 扛量) → Nginx(L7 路由+卸载) → 后端`，每个节点只干一层，合起来这条链路就两层兼得——这正是大厂入口分层的意义：**外层 L4 扛量、内层 L7 做精**。

## 三、反向代理到底解决了什么（核心价值）

把"为什么要在后端前面摆这么一层"讲透，而不是只说"做负载均衡"：

### 3.1 安全：把后端藏在身后
后端 IP 不暴露公网，DDoS / 扫描打到的是边缘代理（可弹性扩容、可上高防）。WAF、IP 黑白名单、限流都在入口统一拦，后端只信任内网来源。**类比**：前台帮你挡掉推销电话，不让它们直接打到工位。

### 3.2 横向扩展：后端加机器对客户端无感
客户端永远只认一个入口域名/VIP，后端从 2 台扩到 20 台、滚动发布、摘除故障节点，客户端**完全感知不到**。这就是"统一入口"带来的解耦——配合负载均衡算法分发流量（详见 [Nginx §五](../Middleware/Nginx.md)）。

### 3.3 横切能力统一卸载（最值钱的一点）
把每个后端服务都要做、但又跟业务无关的"脏活"上提到入口集中做：

| 能力 | 放在反代做的收益 |
| --- | --- |
| **TLS/HTTPS 卸载** | 证书集中管理 + 续期，后端不耗 CPU 解密 |
| **Gzip/Brotli 压缩** | 后端只吐原文，压缩在边缘做 |
| **限流 / 熔断** | 入口统一限速，保护整个后端（漏桶/令牌桶） |
| **缓存** | 静态资源 / 热点接口响应缓存，挡掉大量回源 |
| **鉴权前置** | JWT 校验、API Key 在网关层做，后端只管业务 |
| **灰度 / 蓝绿 / A-B** | 按 Header/Cookie/权重把流量切到新版本 |

> **trade-off**：能力越往入口堆，入口越"重"、越容易成为瓶颈和单点。所以超大流量场景会做分层（L4 只转发、L7 做轻路由、复杂逻辑下沉到 API 网关/Service Mesh）。

## 四、和"近义概念"的边界（高频混淆，必问）

面试官最爱问"反向代理和 XX 有什么区别"，因为大多数人会混。记住一句话：**它们在能力上是"包含 / 递进"关系，不是并列关系。**

| 概念 | 本质 | 和反向代理的关系 |
| --- | --- | --- |
| **负载均衡（LB）** | 把流量按算法分到多个后端 | 是反向代理的**一个功能子集**。反代必然知道有多个后端，分发就是 LB。LVS 是"纯 LB（L4）"，Nginx 是"反代 + LB（L7）"。 |
| **API 网关（Gateway）** | 反向代理 + 业务治理 | 是反向代理的**超集 / 升级版**：在反代基础上加了鉴权、限流、熔断、协议转换、聚合、可观测。Spring Cloud Gateway / Kong / APISIX 底层都是反代。 |
| **CDN** | 地理就近的分布式反向代理 + 缓存 | 是反向代理在**地理上分布化**：全球边缘节点都是反代，命中缓存就近返回，未命中回源。 |
| **正向代理** | 代理客户端 | 见第一节，方向相反，唯一容易记反的点。 |
| **Service Mesh（Sidecar）** | 服务间east-west流量的代理 | Envoy 做 sidecar = 给每个服务实例配一个"专属反代"，管服务**之间**的调用（区别于南北向入口反代）。 |

**一句话总线**：*LB ⊂ 反向代理 ⊂ API 网关；CDN = 分布式反向代理 + 边缘缓存；Mesh = 把反代下沉到每个实例旁。*

## 五、真实客户端 IP 透传（强制：XFF 系列）

这是反向代理**最高频的生产坑 + 面试题**，单独成节。

### 5.1 问题根因
由第二节"两段连接"：后端 TCP 连接的对端是代理，所以后端 `request.getRemoteAddr()` 拿到的是**代理 IP**，不是真实用户 IP。日志全是 `10.0.0.5`，风控/限流/审计全废。

### 5.2 解法：代理在转发时把真实 IP 塞进 HTTP 头

```nginx
# 反向代理转发时补头（Nginx）
proxy_set_header X-Real-IP        $remote_addr;                 # 直连客户端 IP
proxy_set_header X-Forwarded-For  $proxy_add_x_forwarded_for;   # 追加到 XFF 链
proxy_set_header X-Forwarded-Proto $scheme;                     # http / https（卸载后告诉后端原始协议）
proxy_set_header Host             $host;                        # 保留原始 Host，避免后端路由/重定向错
```

三个头的区别（高频追问）：

| 头 | 含义 | 注意 |
| --- | --- | --- |
| `X-Real-IP` | 单个 IP，通常是**直连代理的那个客户端 IP** | 非标准，多层代理下会被覆盖 |
| `X-Forwarded-For` | **逗号分隔的 IP 链**：`真实IP, 代理1, 代理2` | 事实标准，但**最左可被客户端伪造** |
| `Forwarded`（RFC 7239） | 标准化版本：`for=1.2.3.4;proto=https;host=...` | 较新，普及度不如 XFF |

### 5.3 多层代理与伪造防护（架构师必答）
请求经过 `客户端 → CDN → LVS → Nginx → 后端`，XFF 会变成 `真实IP, CDN出口IP, LVS-IP`。**取真实 IP 不能简单取第一个**——因为客户端可以请求时自带一个伪造的 `X-Forwarded-For: 1.1.1.1`，它会排在最左边。

**正确做法**：维护一份**可信代理白名单**（你自己的 CDN/LVS/Nginx 出口 IP 段），从 XFF 链**从右往左**剔除可信代理 IP，第一个**不可信**的 IP 才是真实客户端 IP。Nginx 用 `realip` 模块的 `set_real_ip_from` 配置可信段自动完成。

### 5.4 L4 代理怎么透传 IP？—— PROXY protocol
七层代理靠 HTTP 头，但**四层代理（LVS/HAProxy tcp）看不到 HTTP**，怎么传真实 IP？答案是 **PROXY protocol**：在 TCP 连接建立后、应用数据之前，先发一行明文（`PROXY TCP4 1.2.3.4 ... src_port dst_port\r\n`）告诉后端真实四元组。后端需显式开启支持（Nginx `proxy_protocol on`）。这是 L4 透传 IP 的标准答案。

## 六、主流实现选型对比

| 方案 | 层 | 定位 | 特点 / 适用 |
| --- | --- | --- | --- |
| **Nginx** | L7（含 L4 stream） | Web 入口事实标准 | 配置成熟、生态广、动静分离/缓存强；C 写、Master-Worker |
| **HAProxy** | L4 + L7 | 专业 LB | 负载均衡/健康检查能力最强，常做 TCP 层代理 |
| **LVS** | L4（内核态） | 超大流量入口 | 内核 IPVS，DR 模式不经过回程、性能天花板，扛百万并发 |
| **Envoy** | L7 | 云原生 / Mesh 数据面 | xDS 动态配置、可观测强，Istio/网关底座 |
| **Traefik / APISIX / Kong** | L7 | 云原生 API 网关 | 动态路由、插件化、K8s Ingress 友好 |
| **云 SLB/ALB（云厂商）** | L4 / L7 | 托管负载均衡 | 免运维、弹性、按量计费，中小团队首选 |

**典型选型**：自建机房超大流量 → `LVS(L4) + Nginx(L7)`；云上 → `云 SLB + Nginx/网关`；微服务东西向 → `Envoy sidecar`；需要业务治理 → `APISIX / Spring Cloud Gateway`。

### 接入层分层全景（**纠正"把它们当竞品横向比"的头号误区**）

LVS / Nginx / 云 SLB / API 网关 / Service Mesh **不是互相替代的竞品，而是一条串联的流水线**——每层解决不同的问题，生产里往往同时存在：

```
                          ┌─────────── 南北向（入口流量）───────────┐
 客户端 → DNS/CDN(边缘缓存) → ┃ L4 入口 ┃ → ┃ L7 接入 ┃ → ┃ 业务网关 ┃ → 微服务 ⇄ ┃ Sidecar ┃
                          ┃ LVS/SLB ┃   ┃ Nginx  ┃   ┃ SCG/   ┃            ┃ Envoy  ┃
                          ┃ (NLB)   ┃   ┃ (ALB)  ┃   ┃ APISIX ┃            └────┬───┘
                          └────┬────┘   └───┬────┘   └───┬────┘    └─ 东西向（服务间）─┘
                          扛量/四元组转发   TLS卸载/      鉴权/限流/
                          百万并发         域名路径路由   灰度/聚合/协议转换
                                          静态/缓存
```

| 层 | 代表 | 解决什么（别的层替不了） | 云上能否省 |
| --- | --- | --- | --- |
| **L4 入口** | LVS / 云 NLB | 纯转发扛量、健康检查、VIP 高可用 | ✅ 云 NLB 托管替代 LVS |
| **L7 接入** | Nginx / 云 ALB | TLS 卸载、域名/路径路由、静态资源、缓存、入口限流 | ⚠️ 云 ALB 能替一部分，但动静分离/复杂 rewrite 仍常自建 Nginx |
| **业务网关** | Spring Cloud Gateway / APISIX / Kong | **感知业务**：鉴权、按用户灰度、接口聚合、协议转换、跟注册中心联动 | ❌ 业务逻辑，不可托管替代 |
| **Sidecar（东西向）** | Envoy / Istio | 服务**之间**调用的治理（与南北向入口正交） | ❌ 架构选型，非托管能省 |

**一句话心智**：*L4 管"量"、L7 管"接入横切"、网关管"业务治理"、Sidecar 管"服务间"。云 SLB 只是把 L4/L7 这两层托管化，省的是运维不是层次。* 面试被问"Nginx 和网关/SLB 怎么选"时，先纠正前提——**它们多数时候是叠加的，不是二选一**。

#### 进阶追问：业务网关能否替代 L7 接入（Nginx）？

上图把网关和 Nginx 画成两层，但它们能不能**塌缩成一层**？答案不是"能/不能"，而是**取决于网关的底座**——这是高级答法的分水岭。

**先承认本质**：SCG / APISIX / Kong 自己就是 L7 反向代理，功能上确实覆盖了 Nginx 那层的大部分。所以问题不在"功能够不够"，而在"**让它裸奔公网入口，代价划不划算**"。而代价取决于它用什么写的：

| 网关 | 底座 | 能否合并 L7 接入 |
| --- | --- | --- |
| **APISIX / Kong** | **OpenResty = Nginx + LuaJIT** | ✅ **本来就是 Nginx**，合并天经地义——一个进程同时干接入层 + 业务网关 |
| **Spring Cloud Gateway / Zuul** | **JVM 应用（Reactor Netty）** | ⚠️ **不建议裸奔**，大厂通常前面仍留 Nginx/SLB |

**为什么 JVM 网关（SCG）不该直接做公网入口**——Nginx 这层的价值不在"路由"，而在 JVM 不擅长的几件事：

| 维度 | Nginx 在前 | SCG 裸奔入口 |
| --- | --- | --- |
| 静态资源/大文件 | sendfile 零拷贝直返 | JVM 返静态=杀鸡用牛刀，性能差 |
| TLS 卸载 | C 实现 + 可挂硬件加速 | JVM 解 TLS 吃 CPU |
| 海量空闲长连接 | C100K，内存极省 | 慢客户端 keep-alive 挂在**堆内存**，GC 压力 |
| 慢客户端攻击（Slowloris） | 缓冲层隔离，收完再转 | 直接占 Netty 线程/连接 |
| 发版隔离 | 配置稳定、极少重启 | 业务路由高频发版→重启 JVM，入口稳定性跟着抖 |
| 第一道防护（WAF/防 DDoS） | 最外层就拦 | 要穿透到 JVM 才拦，浪费且危险 |

**判断清单（生产怎么定）**：

```
网关是 OpenResty 系(APISIX/Kong)?  → 合并，无需再前置 Nginx
网关是 JVM 系(SCG/Zuul)?          → 前面留 Nginx/云ALB
有大量静态资源 / 大文件下载?         → 留 Nginx(动静分离)
流量巨大 / 慢连接多 / 暴露公网?       → 留 Nginx 做连接收敛+缓冲+WAF
网关业务路由发版频繁?               → 分层，隔离入口稳定性
中小流量 / 云上 / 内网入口?          → 可以合并，省一层运维
```

真实工程实践：
- **大厂自建（SCG）**：`LVS → Nginx → Spring Cloud Gateway → 微服务`，四层各司其职。
- **云原生/中小（APISIX）**：`云SLB(L4) → APISIX(接入+网关合一) → 微服务`，APISIX 一层顶两层。

##### 面试金句

> **业务网关能否替代 L7 接入，取决于它的底座**：APISIX/Kong 基于 OpenResty、本身就是 Nginx，合并是常态；**Spring Cloud Gateway 是 JVM 应用**，裸奔公网入口会在静态资源、TLS 性能、海量长连接（堆内存）、慢客户端防护、发版隔离上吃亏，所以大厂仍用 Nginx/SLB 收口，SCG 只承担鉴权/限流/灰度这层业务治理。一句话：**OpenResty 系合并，JVM 系分层。**

## 七、生产踩坑（强制）

### 坑 1：后端日志/风控全是代理 IP
**现象**：限流误杀、风控失效、日志无法定位用户。**根因**：没透传 XFF，或后端没从 XFF 解析。**修复**：代理补 `X-Forwarded-For` + 后端配可信代理白名单从 XFF 取真实 IP（见第五节）。**监控**：抽样比对 `remote_addr` 与 XFF 是否一致。

### 坑 2：超时三件套配错，后端慢请求拖垮入口
**现象**：后端偶发慢响应，大量请求堆在 Nginx，连接数飙升直至 502/504。**根因**：`proxy_connect_timeout`（连后端）/ `proxy_send_timeout` / `proxy_read_timeout`（等后端响应）默认 60s 太长。**修复**：按业务设置合理超时（如读超时 3~10s），配合重试与熔断。

### 坑 3：代理↔后端没开 keepalive，全是短连接
**现象**：后端机器 `TIME_WAIT` 暴涨、端口耗尽、CPU 浪费在握手。**根因**：upstream 未配 `keepalive`，每个请求新建/关闭 TCP。**修复**：
```nginx
upstream backend { server 10.0.0.1; keepalive 64; }   # 连接池
# 且 location 内：
proxy_http_version 1.1;
proxy_set_header Connection "";   # 清掉 close，启用长连接复用
```

### 坑 4：`Host` 头丢失 → 后端路由错 / 重定向跳到内网地址
**现象**：后端按 Host 做多租户路由失效；或 302 的 `Location` 头返回了内网域名。**根因**：没透传原始 `Host`，或重定向时用了 upstream 内部名。**修复**：`proxy_set_header Host $host;`，必要时用 `proxy_redirect` 改写 Location。

### 坑 5：`proxy_buffering` 默认开，大文件/流式接口内存涨或延迟高
**现象**：下载大文件时 Nginx 内存涨；SSE/流式接口客户端迟迟收不到数据。**根因**：默认开启响应缓冲，Nginx 要收完（或缓冲满落盘）才转发。**修复**：流式/大文件场景对该 location 关 `proxy_buffering off;` 或调大 buffer。

### 坑 6：自动重试导致非幂等请求重复执行
**现象**：一次下单变成两次扣款。**根因**：`proxy_next_upstream` 默认在 error/timeout 时重试下一台，但请求可能已到后端执行了一半。**修复**：对非幂等接口（POST 下单/支付）限制重试条件，或后端做幂等（去重表 / 幂等键）。

### 坑 7：反向代理自己成了单点
**现象**：Nginx 节点宕机，整个入口不可用。**根因**：只部署一台反代。**修复**：`Keepalived + VIP` 双活，或前置 LVS/云 SLB 做反代的反代，多副本 + 健康检查。

## 八、面试高频追问

**Q1：正向代理和反向代理的区别？一句话怎么记？**
代理替谁隐身：帮客户端隐身、客户端主动配置 → 正向（VPN/上网代理）；帮服务器隐身、客户端无感知 → 反向（Nginx/CDN）。技术栈可相同，区别在部署位置与代理对象。

**Q2：反向代理为什么后端拿不到真实 IP？怎么解决？**
因为反代把连接拆成两段，后端连的是代理，`remote_addr` 是代理 IP。解决：七层靠 `X-Forwarded-For`/`X-Real-IP` 透传，后端配可信代理白名单从右往左剔除取真实 IP（防伪造）；四层靠 PROXY protocol 在 TCP 数据前发一行真实四元组。

**Q3：L4 和 L7 代理的区别？各用在哪？**
L4 基于 IP+端口转发、看不到 HTTP、性能高（LVS），用于最外层扛量；L7 解析 HTTP、能按 URL/Host/Cookie 路由、能卸载 TLS（Nginx），用于精细路由和横切能力。大厂常 LVS(L4) + Nginx(L7) 分层。

**Q4：反向代理、负载均衡、API 网关、CDN 什么关系？**
LB ⊂ 反向代理 ⊂ API 网关（能力递进）；CDN = 地理分布式反向代理 + 边缘缓存；Service Mesh = 把反代下沉成每实例的 sidecar。负载均衡只是反代分发流量这一个功能。

**Q5：HTTPS 卸载在哪做？后端怎么知道原始是 HTTP 还是 HTTPS？**
TLS 在反代终结（客户端的握手对端是代理），后端走明文省 CPU。靠 `X-Forwarded-Proto` 头告诉后端原始协议——否则后端生成重定向/绝对 URL 时可能错用 http，导致死循环跳转。

**Q6：反向代理为什么能提升性能 / 扛流量？**
① 客户端侧短连接、后端侧 keepalive 长连接池复用，省后端握手与 TIME_WAIT；② 静态资源/热点响应缓存挡掉回源；③ TLS/压缩等 CPU 活在边缘做；④ 七层缓冲削峰，慢客户端不直接占后端连接。

**Q7：反向代理是单点吗？怎么做高可用？**
单台是单点。方案：Keepalived + VIP 双机热备（主挂了 VIP 漂移到备）；或多副本反代前置 LVS/云 SLB；配健康检查自动摘除故障节点。本质是"给入口再加一层入口"。

**Q8：proxy_buffering 是什么？什么时候要关？**
反代缓冲后端响应再转发给客户端的机制。开启利于削峰、隔离慢客户端；但大文件下载会涨内存、流式接口（SSE/chunked）会被攒住延迟变高。流式/大文件 location 应关闭。

**Q9：客户端伪造了 X-Forwarded-For 怎么办？**
XFF 最左 IP 可被客户端任意伪造。不能盲取第一个。要维护可信代理 IP 白名单（自家 CDN/LVS/Nginx 出口），从 XFF 链右侧逐个剔除可信 IP，第一个不可信 IP 才是真实客户端。Nginx `realip` 模块 + `set_real_ip_from` 自动处理。

## 九、答题模板（60 秒话术）

> **反向代理是部署在服务端入口、对客户端隐藏真实后端的代理**（类比公司前台）。和正向代理的区别是：正向代理客户端、隐藏用户；**反向代理服务端、隐藏后端**，客户端无感知。
>
> 它的本质是**把一条连接拆成两段、自己做终结点**：客户端连代理、代理连后端。由此带来四个价值——**① 安全**（藏后端 IP、入口统一 WAF/限流）；**② 横向扩展**（后端增删对客户端透明，即负载均衡）；**③ 横切能力卸载**（TLS、压缩、缓存、鉴权集中在入口做）；**④ 灰度/蓝绿**按流量切版本。
>
> 按层分 **L4（LVS，看 IP+端口、性能高，扛量）和 L7（Nginx，看 HTTP、能按 URL 路由、卸载 TLS）**，大厂常分层组合。
>
> 两个必踩的坑：**真实客户端 IP** 要靠 **X-Forwarded-For** 透传 + 可信代理白名单防伪造（L4 用 PROXY protocol）；以及代理↔后端要开 **keepalive 长连接池**，否则后端 TIME_WAIT 打爆。
>
> 关系上记一句：**负载均衡 ⊂ 反向代理 ⊂ API 网关，CDN 就是分布式反向代理 + 边缘缓存。**
