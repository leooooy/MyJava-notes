# 多路复用 select / poll / epoll

> 上一篇 [网络IO模型](./网络IO模型.md) 讲了 NIO 的"What"——这一篇讲 **How**：内核到底怎么做到一个线程管 N 个连接的。
> 本篇要解决：
> ① select / poll / epoll **三个的差异**——为什么 epoll 是 C10K 的解药
> ② epoll 的 **三个核心数据结构**：红黑树 / 就绪链表 / 等待队列
> ③ **LT vs ET**：水平触发和边缘触发到底差什么，Nginx 为什么用 ET
> ④ epoll 的 **惊群问题** 与 `EPOLLEXCLUSIVE` / `SO_REUSEPORT` 工程解法

> 大厂面试这块**深度题**特别多——能讲到红黑树/链表/中断回调，就过 P6 线了。

## 一、为什么需要多路复用

### 1.1 BIO 的死结

一个线程只能 `read` 一个 fd → 想监听 N 个连接就得 N 个线程 → 1w 连接 = 1w 线程 = 上下文切换打死 CPU。

### 1.2 朴素 NIO 的死结

```c
fcntl(fd, F_SETFL, O_NONBLOCK);
while (1) {
    for (int i = 0; i < N; i++) {
        if (read(fd[i], buf, sizeof(buf)) > 0) handle(buf);
    }
}
```

- 每次循环都要遍历所有 fd，调 N 次 read（**N 次系统调用** = N 次用户态↔内核态切换）。
- 大部分 fd 没数据，纯空转 CPU。

### 1.3 多路复用的核心想法

**让用户线程一次性把 N 个 fd 交给内核**，内核在一次调用里告诉你"哪些 fd 准备好了"。

- ✅ 1 次系统调用监听 N 个 fd（不是 N 次）。
- ✅ 没就绪时 内核挂起线程（不空转）。
- ✅ 就绪事件由内核**收集**好返回（不用用户态遍历）。

## 二、select（1983 年，POSIX 标准）

### 2.1 接口

```c
int select(int nfds,
           fd_set *readfds, fd_set *writefds, fd_set *exceptfds,
           struct timeval *timeout);
```

`fd_set` 是个**位图**，每位代表一个 fd。

### 2.2 工作流程

```
用户                                     内核
 │                                        │
 │  1. 把 fd_set 从用户空间拷贝到内核 ───►│
 │                                        │ 2. 遍历 fd_set，检查每个 fd 状态
 │                                        │ 3. 没就绪则挂起当前进程（睡眠）
 │                                        │ 4. fd 就绪时唤醒（中断回调）
 │  ◄─── 5. 把 fd_set 拷贝回用户态 ────── │
 │                                        │
 │  6. 用户再遍历 fd_set 找出就绪的 fd      │
```

### 2.3 三大致命缺陷

1. **fd 数量上限 1024**（`FD_SETSIZE`，编译时写死）。
2. **每次都要拷贝整个 fd_set**（用户↔内核）：1k fd × 2 次 = 浪费。
3. **O(n) 遍历两次**：内核检查就绪一次，用户拿到结果遍历找就绪 fd 一次。

→ **C10K 完全不够**，只适合连接数 < 1000 的场景。

## 三、poll（1986 年，AT&T）

### 3.1 接口

```c
struct pollfd {
    int fd;
    short events;       // 关心的事件
    short revents;      // 实际发生的事件
};
int poll(struct pollfd *fds, nfds_t nfds, int timeout);
```

### 3.2 与 select 的区别

| 对比项 | select | poll |
| --- | --- | --- |
| 数据结构 | 位图 fd_set | 数组 pollfd[] |
| fd 数量上限 | **1024**（编译期） | 无上限（受系统资源） |
| 每次拷贝 | 整个 bitmap | 整个数组 |
| 复杂度 | O(n) 遍历 | O(n) 遍历 |

**结论**：poll 只解决了 fd 数量上限，**性能问题（拷贝、遍历）一个没解决**。所以高并发依然不行。

## 四、epoll（2002 年，Linux 2.5.44）⭐

### 4.1 接口（三件套）

```c
int epoll_create(int size);                           // 创建 epoll 实例（返回 epfd）
int epoll_ctl(int epfd, int op, int fd,
              struct epoll_event *event);             // 注册/修改/删除 fd
int epoll_wait(int epfd, struct epoll_event *events,
               int maxevents, int timeout);          // 等就绪事件
```

### 4.2 内核数据结构（**面试高频**）

```
epoll 实例 (struct eventpoll)
├── 红黑树 (rbr) ────────────► 存所有注册的 fd（O(logN) 增删查）
│   ├── fd=3
│   ├── fd=17
│   └── fd=99 ...
├── 就绪链表 (rdllist) ──────► 存已就绪 fd（双向链表）
│   ├── fd=3 (EPOLLIN)
│   └── fd=99 (EPOLLOUT)
└── 等待队列 (wq) ───────────► 调用 epoll_wait 时挂起的进程
```

**关键点**：
- 红黑树 = **fd 的注册表**，调用 `epoll_ctl(ADD)` 把 fd 加进来，O(logN)。
- 就绪链表 = **就绪事件队列**，内核中断回调把就绪 fd 直接挂上去，不用遍历。
- 等待队列 = **谁在等**，`epoll_wait` 没就绪事件时把当前进程挂上去睡眠。

### 4.3 完整工作流程

```
1. epoll_create()
   └─► 内核创建 eventpoll 实例（红黑树 + 就绪链表 + 等待队列）

2. epoll_ctl(EPOLL_CTL_ADD, fd, EPOLLIN)
   ├─► 把 fd 加到红黑树
   └─► 给 fd 注册回调 ep_poll_callback：
       "当 fd 上有数据，把 fd 加入 rdllist，唤醒 wq 里的进程"

3. epoll_wait()
   ├─► 检查 rdllist：
   │   ├── 有就绪事件 → 直接拷贝给用户，O(就绪数) 不是 O(总数)
   │   └── 无 → 把当前进程挂到 wq，睡眠
   │
4. 网卡收到数据 → 软中断 → TCP 协议栈处理 → socket recv buffer 有数据
   └─► 触发之前注册的 ep_poll_callback：
       ├── 把 fd 加到 rdllist
       └── 唤醒 wq 上的进程

5. 进程被唤醒 → 从 rdllist 取出就绪 fd → 拷贝给用户态
```

### 4.4 epoll 为什么快（标准答案）

| 维度 | select/poll | epoll |
| --- | --- | --- |
| **fd 数量上限** | 1024 / 系统限制 | 几乎无上限（10w+ 没问题） |
| **每次系统调用** | 传递所有 fd | 只传 epoll_ctl 增量；epoll_wait 不传 |
| **fd 拷贝** | 每次全量拷贝 | 注册时一次性拷贝（mmap），之后不拷 |
| **就绪事件查找** | O(n) 遍历所有 fd | O(1)，直接拿 rdllist |
| **就绪通知机制** | 主动遍历 | **被动回调**（中断驱动） |

> ⚠️ **常见误区**："epoll 用 mmap 共享内存所以快" —— 对一半。Linux 实现里 epoll 不是真正 mmap，而是**事件复制**到用户态。但**减少全量 fd 拷贝**是真的。

## 五、LT vs ET（水平触发 vs 边缘触发）⭐

### 5.1 概念

| 模式 | 触发条件 | 用一句话总结 |
| --- | --- | --- |
| **LT 水平触发**（默认） | 只要 fd 可读/可写**状态持续**，就一直通知 | 没读完没关系，下次还提醒你 |
| **ET 边缘触发** | 仅在 fd **状态变化的瞬间**通知一次 | 必须一次读到 EAGAIN，错过就没了 |

### 5.2 举例：socket 收到 100 字节，应用每次读 50 字节

```
LT 模式：
  收到 100 字节 → 通知   → 用户读 50 → 还有 50 → 下次 epoll_wait 又通知
                                            → 用户再读 50 → 缓冲区空

ET 模式：
  收到 100 字节 → 通知一次 → 用户读 50 → 还有 50，但状态没变化（一直可读）
                                       → 下次 epoll_wait 不通知（事件丢了！）
                                       → 必须 while(read) 直到 EAGAIN
```

### 5.3 ET 的正确写法

```c
while (true) {
    int n = read(fd, buf, sizeof(buf));
    if (n > 0) process(buf, n);
    else if (n == -1 && errno == EAGAIN) break;     // 必须读到 EAGAIN
    else if (n == 0) { close(fd); break; }
}
```

### 5.4 选型

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| **业务代码、JDK NIO** | **LT** | 简单可靠，少读没事 |
| **Nginx / Netty epoll transport** | **ET** | 减少 epoll_wait 调用次数（百万连接下显著），但要保证一次读完 |

**面试题**："Java NIO 默认是 LT 还是 ET？"
**答案**：**LT**。`EPollSelectorImpl` 没用 `EPOLLET` 标志。Netty 的 `EpollEventLoop` 提供了 ET 模式（性能更好）。

## 六、惊群问题（Thundering Herd）

### 6.1 现象

多个进程/线程在**同一个 fd 上 epoll_wait**（典型场景：Nginx 多 worker 进程都监听同一个 listen socket）。

新连接到来时 → 内核唤醒**所有等待的进程** → 但只有一个能 accept 成功 → 其他空跑一圈被唤醒后又睡 → 上下文切换浪费。

### 6.2 解决方案演进

| 方案 | Linux 版本 | 做法 | 缺点 |
| --- | --- | --- | --- |
| **应用层加锁** | 古老 | Nginx accept_mutex：worker 抢锁后才 epoll_wait | 锁开销，不均衡 |
| **EPOLLEXCLUSIVE** | 4.5+ | epoll_ctl 时加 `EPOLLEXCLUSIVE`，内核只唤醒一个等待者 | 仍可能有少量惊群 |
| **SO_REUSEPORT** | 3.9+ | **每个 worker 各开一个 listen socket，绑同一端口**，内核做负载均衡分发到不同 socket | **最佳方案**，无惊群、连接均衡 |

```c
// SO_REUSEPORT 写法（每个 worker 自己监听）
int sock = socket(AF_INET, SOCK_STREAM, 0);
int opt = 1;
setsockopt(sock, SOL_SOCKET, SO_REUSEPORT, &opt, sizeof(opt));
bind(sock, ...);
listen(sock, ...);
// 每个 worker 进程用自己的 sock 调 epoll_wait，互不干扰
```

**生产**：Nginx 1.9.1+、HAProxy、Envoy 全部默认 `SO_REUSEPORT`。

## 七、生产踩坑

### 坑 1：epoll 文件描述符泄漏（FD 用尽）

**现象**：服务运行几小时后 `accept` 返回 `EMFILE: Too many open files`。

**根因**：连接关闭时没调 `epoll_ctl(EPOLL_CTL_DEL)` + 没 `close(fd)` → fd 卡在 epoll 红黑树里。

**排查**：
```bash
ls /proc/<pid>/fd | wc -l           # 看进程当前 fd 数
cat /proc/<pid>/limits | grep files # 看上限
ulimit -n                           # 通常 1024，生产要调大
```

**修复**：
1. 所有错误路径都要 `close(fd)`。
2. 提升 `ulimit -n` 到 65535+，`/etc/security/limits.conf`。

### 坑 2：JDK NIO epoll 空轮询 BUG（再提一次，必考）

详见 [网络IO模型](./网络IO模型.md#坑-1jdk-nio-的-epoll-空轮询-bug必考)。

### 坑 3：ET 模式下数据没读完导致丢消息

**现象**：用 ET 模式，每次只 read 一次，业务发现"消息总是少一段"。

**根因**：ET 仅在状态变化时通知，没读完缓冲区数据就不会再通知。

**修复**：循环读到 EAGAIN，且 socket 必须 `O_NONBLOCK`（否则会卡死）。

### 坑 4：多线程操作同一 epoll 实例

**误区**：以为 epoll 是线程安全的，多个线程并发 `epoll_wait` 同一 epfd。

**真相**：内核操作是线程安全的，但**多个线程同时 wait 会惊群**——多个线程同时被唤醒处理同一个 fd，重复处理数据。

**解决**：
- Netty 一个 EventLoop 一个线程一个 Selector，**fd 与 EventLoop 绑死**。
- 或用 `SO_REUSEPORT`。

### 坑 5：LT 模式下 EPOLLOUT 必须按需注册

**误区**：写事件 EPOLLOUT 一直注册着。

**问题**：LT 下 socket 缓冲区只要可写就触发，导致 epoll_wait 100% 返回，CPU 飙高。

**正确做法**：
- 默认**只注册 EPOLLIN**。
- 当 `write()` 返回 EAGAIN 时（缓冲区满），临时加 EPOLLOUT。
- 写完后立刻取消 EPOLLOUT。

## 八、面试高频追问

**Q1：select / poll / epoll 三个的核心差异？**
- select：fd_set 位图，1024 上限，每次全量拷贝 + 遍历 O(n)。
- poll：数组替位图，无 1024 上限，但拷贝/遍历仍 O(n)。
- epoll：红黑树注册（O(logN)）+ 就绪链表（O(1)）+ 中断回调（无遍历）。

**Q2：epoll 的红黑树和就绪链表分别干嘛？**
- 红黑树：**注册表**，所有被监听的 fd 在这里。`epoll_ctl(ADD/MOD/DEL)` 操作它。
- 就绪链表：**事件队列**，已经发生 IO 事件的 fd 被中断回调挂上去。`epoll_wait` 直接从这里拿。

**Q3：epoll_wait 怎么实现的"等"？**
当前进程加入 epoll 实例的等待队列，进入 TASK_INTERRUPTIBLE 睡眠。fd 就绪时内核回调把进程从等待队列摘下、加入就绪队列。

**Q4：LT 和 ET 怎么选？为什么 Nginx 用 ET？**
- LT 编程简单，但每次状态持续都触发，内核被多次唤醒。
- ET 只在状态变化触发一次，**减少 epoll_wait 系统调用次数**——百万连接下能省 30%+ CPU。但必须配合非阻塞 + 循环读到 EAGAIN。
- Nginx 极致性能场景选 ET；JDK NIO 默认 LT 因为通用安全。

**Q5：epoll 是 mmap 共享内存吗？**
**不是真正 mmap**（这是网上传得最广的错误）。Linux 实现里 epoll_wait 仍要把就绪事件**拷贝**到用户提供的 events 数组。但 epoll 减少了**fd 注册列表**的重复拷贝（注册一次后内核长期持有），整体拷贝量远低于 select/poll。

**Q6：epoll 能跨进程共享吗？**
可以——`epoll_create` 返回的 fd 可通过 `fork()` 继承，多个子进程共享同一个 epoll 实例 → 但会**惊群**，要用 `EPOLLEXCLUSIVE` 或更推荐 `SO_REUSEPORT`。

**Q7：什么是 SO_REUSEPORT？跟 SO_REUSEADDR 区别？**
- `SO_REUSEADDR`：允许 socket 复用 TIME_WAIT 状态的端口（重启不用等）。
- `SO_REUSEPORT`（Linux 3.9+）：允许**多个 socket 绑定同一个端口**，内核做四元组哈希分发到不同 socket → 解决惊群、连接均衡。

**Q8：Java NIO Selector 在 Linux 上是 LT 还是 ET？怎么改 ET？**
默认 LT。改 ET 要么用 Netty 的 `EpollEventLoopGroup`（直接 JNI epoll），要么自己写 JNI。

**Q9：epoll 监听数量上限是多少？**
单个 epoll 实例没硬上限（受 `/proc/sys/fs/epoll/max_user_watches`，通常每用户百万级）。**进程总 fd 数**受 `ulimit -n` 限制。

**Q10：select 的 1024 上限能改吗？**
重新编译内核改 `__FD_SETSIZE`——但这是头文件级，应用要重新编译，**生产不可行**。直接换 epoll/kqueue。

**Q11：BSD 系统的 kqueue 和 epoll 区别？**
kqueue（FreeBSD/macOS）：比 epoll 更通用，能监听文件、信号、AIO、定时器等多种事件源（不止 socket）。epoll 只能监听 fd。Java NIO 在 macOS 用 kqueue。

**Q12：io_uring 是什么？跟 epoll 区别？**
io_uring（Linux 5.1+，2019）：基于**共享 ring buffer**（用户态/内核态共享内存），提交读写请求和获取结果**几乎不需要系统调用**。**真正的异步 IO**——不仅事件通知异步，连数据拷贝也异步。
- vs epoll：epoll 只通知"可读了"，用户还得调 read；io_uring 直接告诉你"我读完了，数据在 buf 里"。
- 性能：io_uring 在高并发小包场景比 epoll 快 30%~50%。Netty 5、Tokio（Rust）已支持。

## 九、答题模板（60 秒话术）

> "select / poll / epoll 是 Linux 三代多路复用方案，核心区别是**怎么告诉内核'我要监听哪些 fd' 和 内核怎么告诉用户'哪些 fd 就绪了'**。
>
> **select** 用位图，**fd 上限 1024**，每次都把整个位图从用户态拷贝到内核态，内核还要遍历 O(n)，C10K 直接崩。
>
> **poll** 把位图换成数组，**取消了 1024 上限**，但拷贝和遍历问题没解决，仍是 O(n)。
>
> **epoll** 是真正的解药，三件套：
> - `epoll_create` 创建实例（内核维护**红黑树存所有注册 fd**，**双向链表存就绪 fd**）。
> - `epoll_ctl` 增删查 fd（O(logN)，注册一次，内核长期持有）。
> - `epoll_wait` 拿就绪事件，**O(就绪数) 不是 O(总数)**。
>
> 关键性能点：内核给每个 fd 注册了**中断回调**，数据到达时回调把 fd 加到就绪链表 —— **不是遍历找出来的**，是被动通知。
>
> epoll 还分 **LT 水平触发**（只要可读就一直通知，默认）和 **ET 边缘触发**（只通知状态变化一次，必须循环读到 EAGAIN）。Nginx / Netty epoll 用 ET 性能更好。
>
> 多进程惊群问题用 **SO_REUSEPORT** 解决——多 worker 绑定同一端口，内核做负载均衡。Nginx 1.9+ 默认开。
>
> Java NIO 在 Linux 默认就是 epoll LT 模式，Netty 提供原生 epoll transport 支持 ET。下一代是 **io_uring**（Linux 5.1+），基于共享环形缓冲区，连数据拷贝都异步，是 epoll 的进化版。"
