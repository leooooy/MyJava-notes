# 进程与线程

> 并发面试的"地基题"，几乎每场都问：
> ① 进程 / 线程 / 协程到底什么关系？为什么 Java 没有协程（虚拟线程之前）？
> ② 创建线程的几种方式？大厂为什么禁用 `new Thread()`？
> ③ 线程的 6 种状态怎么转换？BLOCKED 和 WAITING 区别？
> ④ 怎么"优雅"地停一个线程？为什么 `stop()` 被废弃？
> ⑤ 并发 ≠ 并行，区别在哪？

---

## 一、进程 vs 线程 vs 协程

### 1.1 三者本质区别

| 维度 | 进程 (Process) | 线程 (Thread) | 协程 (Coroutine) |
| --- | --- | --- | --- |
| 调度方 | 操作系统内核 | 操作系统内核 | 用户态（语言运行时） |
| 内存空间 | 独立（页表隔离） | 共享所属进程的堆 / 方法区 | 共享线程的栈 |
| 切换成本 | 高：刷新 TLB + 内核态切换 ≈ μs 级 | 中：内核态切换 ≈ μs 级 | 低：寄存器 + 栈切换 ≈ ns 级 |
| 通信方式 | 管道 / 共享内存 / Socket / 信号 | 共享内存 + 同步原语 | 通常是 channel / async-await |
| 故障隔离 | 强（一个进程挂不影响别的） | 弱（一个线程 OOM 整个 JVM 都死） | 弱 |
| 数量上限 | 千级 | 万级（受栈大小制约：默认 1MB / 线程） | 百万级 |
| 典型语言 | OS 层 | Java / C++ pthread | Go goroutine / Kotlin / Java 21 虚拟线程 |

**关键洞察**：进程是"资源分配的最小单位"，线程是"CPU 调度的最小单位"。Java 线程是 1:1 映射到 OS 内核线程的，因此万级线程后，**线程切换的内核态开销** 就成为瓶颈，这是引入虚拟线程（Project Loom，JDK 21 GA）的核心动因。

### 1.2 为什么 Java 长期没有协程？

JDK 21 之前，Java 线程 = OS 线程。一个 Tomcat 服务每个请求一个线程，几千 QPS 下：
- 每个线程默认 1MB 栈 → 1 万线程吃 10GB 虚拟内存
- 大量线程在 IO 等待，CPU 上下文切换开销巨大
- Reactor 模型（Netty）虽然用 NIO 解决了，但代码写起来反人类（callback hell / 一堆 `flatMap`）

JDK 21 的 **虚拟线程（Virtual Thread）** 就是 Java 版的协程，由 JVM 调度到少量"载体线程"上，解决了"线程贵 + 阻塞写法不友好"的痛点。

## 二、创建线程的方式（4 种）

### 2.1 继承 Thread 类

```java
class MyThread extends Thread {
    @Override public void run() { System.out.println("hi"); }
}
new MyThread().start();
```

**问题**：Java 单继承，继承了 Thread 就不能继承别的类。**生产代码几乎不用**。

### 2.2 实现 Runnable 接口（推荐）

```java
Thread t = new Thread(() -> System.out.println("hi"));
t.start();
```

`Runnable` 是函数式接口，可以用 lambda。**任务和执行解耦**，是面向对象设计的体现。

### 2.3 实现 Callable + FutureTask（带返回值）

```java
Callable<Integer> task = () -> 42;
FutureTask<Integer> ft = new FutureTask<>(task);
new Thread(ft).start();
Integer result = ft.get();   // 阻塞等结果
```

`Runnable` 没返回值且不能抛检查异常，`Callable` 弥补这两点。

### 2.4 通过线程池（生产唯一推荐）

```java
ExecutorService pool = new ThreadPoolExecutor(...);
Future<Integer> f = pool.submit(() -> 42);
```

**阿里巴巴 Java 开发手册【强制】禁用 `Executors` 工厂方法**（FixedThreadPool / CachedThreadPool 默认无界队列或无界线程数，容易 OOM），必须 `new ThreadPoolExecutor()` 显式声明全部参数。详见 [线程池](./线程池.md)。

## 三、线程的 6 种状态（必背）

```
NEW ──start()──► RUNNABLE ──┬──► WAITING        (wait/join/park 无超时)
                            │
                            ├──► TIMED_WAITING  (sleep/wait(t)/join(t)/parkNanos)
                            │
                            ├──► BLOCKED        (等 synchronized 锁)
                            │
                            └──► TERMINATED     (run() 结束)
```

| 状态 | 含义 | 典型触发 |
| --- | --- | --- |
| **NEW** | 已 `new`，未 `start()` | `Thread t = new Thread()` |
| **RUNNABLE** | 可运行（包含"运行中"和"等 CPU"） | `start()` 之后 |
| **BLOCKED** | 等 monitor 锁 | 进 synchronized 块 |
| **WAITING** | 无限期等待，需被唤醒 | `wait()` / `join()` / `LockSupport.park()` |
| **TIMED_WAITING** | 限时等待 | `sleep()` / `wait(t)` / `join(t)` / `parkNanos()` |
| **TERMINATED** | 已结束 | `run()` 返回或抛未捕获异常 |

### 3.1 BLOCKED vs WAITING（高频陷阱）

| | BLOCKED | WAITING |
| --- | --- | --- |
| 触发 | 想拿 synchronized 锁但没拿到 | 显式调用 wait/join/park |
| 是否持有锁 | 没有锁 | 进入 wait 前必须持有锁，wait 时**释放**锁 |
| 唤醒方式 | 锁被释放后 OS 调度 | 必须 notify/notifyAll/unpark/中断 |
| jstack 显示 | `BLOCKED on monitor` | `WAITING on condition` |

```java
// BLOCKED 例
synchronized (lock) {  // 拿不到锁就 BLOCKED
    ...
}

// WAITING 例
synchronized (lock) {
    lock.wait();        // 释放锁后变 WAITING，等 notify
}
```

### 3.2 RUNNABLE 不等于"正在跑"

`Thread.State.RUNNABLE` 包含两种：
1. CPU 上正在跑
2. 在 OS 就绪队列等 CPU 调度

JVM 看不到 OS 调度细节，所以合并表达。

## 四、并发 vs 并行

| | 并发（Concurrency） | 并行（Parallelism） |
| --- | --- | --- |
| 定义 | 多个任务交替执行（宏观同时，微观分时） | 多个任务**同时**执行（多核） |
| 硬件要求 | 单核也能 | 必须多核 |
| 典型场景 | 协程 / 单核多线程 | Stream parallel / ForkJoin |

**Erlang 之父 Joe Armstrong 经典比喻**：
- 并发：一台咖啡机，2 个队列轮流取
- 并行：两台咖啡机，2 个队列各自取

**面试追问**：8 核机器跑 100 个线程，是并发还是并行？
答：**既是并发又是并行**——8 个真正并行（占满 8 核），剩下 92 个在 OS 调度队列里和它们交替（并发）。

## 五、Thread.sleep / yield / join / wait 区别

| 方法 | 类 | 是否释放锁 | 入参 | 状态变化 |
| --- | --- | --- | --- | --- |
| `sleep(ms)` | Thread（静态） | **不释放** | 时间 | RUNNABLE → TIMED_WAITING |
| `yield()` | Thread（静态） | 不释放 | 无 | RUNNABLE → RUNNABLE（让出 CPU 提示） |
| `join()` | Thread（实例） | **不释放当前对象锁**（持有的 this 锁会保留），但会进入 WAITING | 无 | RUNNABLE → WAITING |
| `wait()` | Object | **释放**当前 monitor | 可有时间 | RUNNABLE → WAITING / TIMED_WAITING |

> 易错：`sleep` 是 Thread 的静态方法，"睡的是当前线程"。`thread.sleep()` 这种写法虽然能编译，但会误导读者。

## 六、优雅地停止线程

### 6.1 为什么 `Thread.stop()` 被废弃？

`stop()` 直接强行终止线程，**释放该线程持有的所有锁**，但被锁保护的数据可能处于不一致状态（写到一半），导致诡异 bug。Java 1.2 起标记为 `@Deprecated`。

类似的还有 `suspend()` / `resume()`：suspend 不释放锁，容易死锁，同样废弃。

### 6.2 标准做法：interrupt + 协作

```java
class Worker extends Thread {
    @Override public void run() {
        while (!Thread.currentThread().isInterrupted()) {
            try {
                doWork();
                Thread.sleep(100);
            } catch (InterruptedException e) {
                // 注意：sleep/wait 抛出 InterruptedException 后，会清除中断标志
                Thread.currentThread().interrupt();   // 重新打标，否则下一轮 while 检测不到
                break;
            }
        }
        cleanup();
    }
}

worker.interrupt();   // 不是"立刻中断"，是"打个招呼"
```

**核心三件套**：
- `interrupt()`：把目标线程的中断标志位置 true（不会立即停止）
- `isInterrupted()`：检查标志，**不清除**
- `Thread.interrupted()`：检查并**清除**标志（静态方法）

### 6.3 InterruptedException 的坑

`sleep` / `wait` / `join` / `BlockingQueue.take` 等阻塞方法在线程被中断时抛 `InterruptedException`，**抛出时会清除中断标志位**。

如果你的 catch 块只是 `e.printStackTrace()` 然后继续 while 循环，下一轮 `isInterrupted()` 是 false，**线程永远停不下来**。

正确处理：要么往外抛，要么 `Thread.currentThread().interrupt()` 重新打标。

## 七、生产踩坑

### 7.1 用 new Thread() 处理高 QPS 任务

**现象**：监控发现 JVM 线程数飙到 5000+，CPU sys% 50%（上下文切换炸了）。
**根因**：业务用 `new Thread(task).start()` 处理每个请求，没用线程池。
**修复**：换 `ThreadPoolExecutor`，限制最大线程数 + 队列。

### 7.2 sleep 在 synchronized 里不释放锁

**现象**：定时任务每分钟跑一次，业务里有个 `sleep(60000)` 在 `synchronized` 块里，结果其他线程一分钟都进不来。
**修复**：sleep 移出同步块，或者改 `wait(60000)` 用条件等待。

### 7.3 InterruptedException 静默吃掉

**现象**：用 shutdown 线程池 → 任务里 sleep 被打断 → 业务 catch 后没处理 → 线程池怎么也关不掉。
**修复**：catch 后必须 `Thread.currentThread().interrupt()` 重打标，或者向上抛。

### 7.4 守护线程的坑

```java
Thread t = new Thread(() -> writeLogToFile());
t.setDaemon(true);   // 守护线程
t.start();
```

JVM 在所有非守护线程都结束时退出，**不等守护线程**。如果守护线程正在写文件，可能写到一半被强杀，文件损坏。

**结论**：守护线程只用于纯辅助任务（GC 线程、心跳线程），有 IO / 状态的不要设守护。

## 八、面试高频追问

**Q1：`run()` 和 `start()` 区别？**
`start()` 由 JVM 启动一个新 OS 线程，然后调用 `run()`；直接调 `run()` 是普通方法调用，**就在当前线程跑**，没有任何并发效果。`start()` 不能调用两次（`IllegalThreadStateException`）。

**Q2：线程切换时，OS 都做了什么？**
1. 保存当前线程的 CPU 上下文（PC、通用寄存器、栈指针）到 PCB
2. 选下一个线程，从 PCB 恢复其上下文
3. 如果跨进程，还要刷新页表 / TLB（更贵）
**面试加分点**：每次切换 ~ 1-10 μs；`vmstat 1` 看 `cs` 列，`pidstat -w` 看每个进程切换次数；切换过多时 `cpu sys%` 飙高。

**Q3：守护线程是什么？典型用例？**
`setDaemon(true)` 设置；JVM 退出时不等守护线程。GC 线程、Finalizer 线程、`@Async` 默认线程池的辅助线程都是守护线程。

**Q4：怎么获取一个线程的执行结果？**
- `FutureTask` + `get()`（阻塞）
- `CompletableFuture.thenApply` / `whenComplete`（回调，不阻塞）
- `ExecutorService.submit()` 返回 Future

**Q5：一个进程能开多少线程？**
理论上由 `(虚拟内存上限 - 元空间 - 堆) / 线程栈大小` 决定。Linux 64 位 + JVM 默认 `-Xss1M`，几万线程就能把虚拟内存吃光。生产 Java 应用一般不超过 1000 工作线程，超过基本是设计问题。

**Q6：虚拟线程（JDK 21）和平台线程区别？**
平台线程 = OS 线程（重）；虚拟线程由 JVM 调度到少量"载体线程"（默认 = CPU 核数），阻塞时载体线程能切别的虚拟线程跑。开虚拟线程几乎免费（创建仅几百纳秒），适合"线程数远多于 CPU 核数 + IO 密集"的场景（如传统 Spring MVC + JDBC）。**不适合 CPU 密集**（虚拟线程占着载体不会让出）。

## 九、答题模板（30 秒话术）

> **进程是资源分配单位**（独立内存 + 文件描述符），**线程是 CPU 调度单位**（共享进程内存）。Java 线程 1:1 映射 OS 线程，所以创建/切换都贵，生产里**用线程池复用**。
>
> 线程有 6 个状态：**NEW / RUNNABLE / BLOCKED / WAITING / TIMED_WAITING / TERMINATED**。BLOCKED 是等 synchronized 锁、不持锁；WAITING 是 wait/park 显式等、释放了锁。
>
> 创建线程 4 种：继承 Thread / Runnable / Callable+FutureTask / **线程池**（生产唯一推荐）。
>
> 停止线程靠 **interrupt 协作机制**：`interrupt()` 只是打标，业务在循环里 `isInterrupted()` 主动退出；`stop()` 因为强行释放锁导致状态不一致，已废弃。
