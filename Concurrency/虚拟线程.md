> ③ Continuation + ForkJoinPool：JVM 怎么"切线程"

> ⑤ 适用 / 不适用场景：IO 密集 ✅ / CPU 密集 ❌

## 一、为什么需要虚拟线程

### 1.1 传统 Java 线程的瓶颈

Java 线程从 JDK 1.2 起就是 **1:1 模型** —— 一个 `java.lang.Thread` 对应一个 OS 内核线程。看起来没什么问题，但放到现代 Web 应用就是灾难：

| 资源 | 单线程开销 | 1 万线程总和 |
| --- | --- | --- |
| 默认栈 (`-Xss1M`) | 1 MB | **10 GB 虚拟内存** |
| OS 内核结构（task_struct + 页表） | ~16 KB | 160 MB |
| 创建 / 销毁（fork+exec） | ~10 μs | 慢 |
| 上下文切换 | ~1-10 μs | 高负载下 sys% 飙高 |

**典型场景**：Spring MVC + JDBC，每个 HTTP 请求一个线程跑业务、阻塞等数据库 / Redis / 下游 RPC。Tomcat 默认 200 工作线程，超过就排队 —— **明明 CPU 闲着，吞吐却上不去**，因为线程数跟不上 IO 并发度。

### 1.2 旧方案的不完美

业界过去十年的几条解法：
- **NIO + Reactor**（Netty / WebFlux）：异步回调，吞吐高但**写起来反人类**（callback hell、`flatMap` 套娃、栈跟踪难诊断）
- **协程**（Kotlin、Go）：编译器把 suspend 函数改写成状态机 —— 但 Java 没语言级支持
- **响应式编程**（Reactor / RxJava）：操作符链 + 背压，学习曲线陡，团队接受度低

业界的呼声：**"我能不能继续写 `Connection conn = ds.getConnection(); ResultSet rs = stmt.executeQuery();` 这种顺序代码，但不被 OS 线程数限制？"**

### 1.3 虚拟线程的承诺

> "Write synchronous code, get asynchronous performance."

JEP 444（JDK 21 GA）给出的方案：
- **API 完全兼容** `Thread` —— 所有现有阻塞代码（`Thread.sleep` / `synchronized` / `BlockingQueue.take` / `Connection.executeQuery`）继续工作
- 创建虚拟线程几乎免费（~1 μs，相比平台线程 ~10-100 μs）
- 一个 JVM 跑**百万级**虚拟线程毫无压力

## 二、原理：M:N 调度

### 2.1 平台线程 vs 虚拟线程

```
传统 1:1 模型（平台线程）
─────────────────────────
   JVM 线程 ─── 1:1 ─── OS 内核线程
   ↑ 创建昂贵、切换贵、栈占内存大


M:N 模型（虚拟线程）
─────────────────────────
   M 个虚拟线程  ───┐
                    ├─► N 个载体线程（Carrier）─── N:N ─── OS 内核线程
                    │   N 默认 = CPU 核数
                    │
                    └─ JVM 内部 ForkJoinPool 调度
                       阻塞时虚拟线程让出载体，去跑别的
```

**关键变化**：
- **平台线程**：JVM 调用 OS API 创建，调度由 OS 内核完成
- **虚拟线程**：在用户态由 JVM 调度，复用少数载体线程
- 阻塞时（`Thread.sleep` / IO）虚拟线程**不会占住载体线程**，载体立刻去跑别的虚拟线程

### 2.2 Continuation：JVM 的"暂停 / 恢复"机制

虚拟线程的核心 trick 是 `jdk.internal.vm.Continuation`：
1. 虚拟线程的栈帧分配在**堆上**（不是 OS 栈）
2. 阻塞时，JVM 把当前栈帧"卷起来"放到 `VirtualThread` 对象里（**unmount**），载体线程重获自由
3. 阻塞结束（如 IO 完成），调度器找一个空闲载体把这个虚拟线程**装回去**（**mount**）继续跑

```
       Virtual Thread (V1)
       ┌───────────────────┐
       │  调用栈快照（堆）  │ ← 不在 OS 栈
       │  PC、局部变量等    │
       └───────────────────┘
                ▲
                │ mount/unmount
                ▼
       Carrier Thread (C1)  ←──── OS 线程
       ┌───────────────────┐
       │  当前正在跑哪个 V  │
       └───────────────────┘
```

unmount 时**只保存活跃栈帧**（不是整个 1MB 栈），所以一个虚拟线程的内存占用从 **1MB 降到 ~几百字节起步**（按需扩缩）。

### 2.3 调度器：ForkJoinPool

JDK 21 默认调度器是一个专用的 ForkJoinPool（不是 commonPool）：
- 默认线程数 = `Runtime.getRuntime().availableProcessors()`
- 用 **Work Stealing** 在载体之间负载均衡
- 调度参数可调：`-Djdk.virtualThreadScheduler.parallelism=N`

详见 [ForkJoinPool](./ForkJoinPool.md)。

## 三、API 用法

### 3.1 创建虚拟线程

```java
// 1. Thread.startVirtualThread (一行起一个)
Thread t = Thread.startVirtualThread(() -> log.info("hello"));

// 2. Thread Builder (推荐)
Thread t = Thread.ofVirtual()
    .name("worker-", 0)              // 命名 worker-0, worker-1, ...
    .uncaughtExceptionHandler((th, e) -> log.error("", e))
    .start(runnable);

// 3. ExecutorService 风格 ★ 生产推荐
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 100_000).forEach(i ->
        executor.submit(() -> {
            handleRequest(i);
            return null;
        })
    );
}  // try-with-resources 自动等所有任务完成
```

> `newVirtualThreadPerTaskExecutor` 不是传统线程池——**每个任务一个新虚拟线程**，无 corePool / maxPool / queue 概念。这是 Loom 的设计哲学：虚拟线程便宜，不需要复用。

### 3.2 判断当前是不是虚拟线程

```java
Thread.currentThread().isVirtual();
```

### 3.3 改造现有代码

```java
// JDK 17 及以前的 Spring MVC
@RestController
class OrderController {
    @GetMapping("/order/{id}")
    public Order get(@PathVariable Long id) {
        return restTemplate.getForObject(downstream + "/" + id, Order.class);
    }
}
// Tomcat 默认 200 平台线程，下游慢请求 → 200 都阻塞 → 503

// JDK 21 + Spring Boot 3.2+，开启虚拟线程
spring.threads.virtual.enabled=true   // 一行配置，Tomcat / Jetty 切换到虚拟线程
// 同样代码不改，可承载几万 IO 阻塞并发
```

**Spring 的开关怎么实现**：把 Tomcat 的 worker `Executor` 替换成 `Executors.newVirtualThreadPerTaskExecutor()`。代码 0 改动。

## 四、pin 问题（最大的坑）

### 4.1 什么是 pin

虚拟线程**钉住（pin）载体线程** = 虚拟线程在阻塞时**没法 unmount**，被迫和载体线程绑死，载体也不能切别的虚拟线程跑 → 退化成传统线程模型。

### 4.2 引发 pin 的两类场景

**1. synchronized 块** ★ 最常见

```java
synchronized (lock) {
    db.query(...);          // ❌ 阻塞期间 carrier 被 pin
}
```

JDK 21 现状：synchronized 持有的 monitor 在 JVM 内部用 OS mutex 实现，无法支持 unmount。
**JEP 491（Java 24，2025 GA）已修复**——synchronized 持锁阻塞时也能让出载体。在那之前要靠规避。

**2. native 方法 / 外部 IO（非 NIO）**

JNI / `Object.wait()` 在 native frame 里 / 非 NIO 阻塞 IO（如 `FileInputStream.read()`）—— 也会 pin。
JDK 21 已经把绝大多数标准库 IO 改成可让出版本（NIO、Socket、Files、JDBC 大部分驱动）。

### 4.3 怎么发现 pin

```bash
# 启动参数
-Djdk.tracePinnedThreads=full   # 详细栈
-Djdk.tracePinnedThreads=short  # 简略

# 跑业务，触发 pin 时控制台会打印
Thread[#23,ForkJoinPool-1-worker-1,5,CarrierThreads]
    java.base/java.lang.VirtualThread$VThreadContinuation.onPinned(VirtualThread.java:183)
    java.base/java.lang.VirtualThread.parkOnCarrierThread(VirtualThread.java:646)
    your.app.PaymentService.charge(PaymentService.java:42) <== monitors:1
```

`<== monitors:1` 说明持有 1 个 synchronized 的 monitor 卡住了。

### 4.4 怎么避免 pin

| 替换 | 原 | 改成 |
| --- | --- | --- |
| 锁 | `synchronized (lock)` | `ReentrantLock` ★ JDK 21 已优化为不 pin |
| 等待唤醒 | `obj.wait/notify` | `Condition.await/signal` |
| 集合 | `Collections.synchronizedXxx` | `ConcurrentHashMap` 等 |
| 文件 | `FileInputStream.read` | `Files.readAllBytes` / NIO |

**生产规则**：**虚拟线程 + 锁场景一律 ReentrantLock**，等 Java 24 普及后再 evaluate。

## 五、适用 / 不适用场景

### 5.1 ✅ 适合：IO 密集 + 高并发

经典：传统 Spring MVC / JDBC 类应用 —— 每请求一线程的写法没变，但能扛 10 倍以上并发。

```
4 核机器 + 平台线程 200：吞吐 ~1000 QPS（CPU 都没用满，瓶颈在线程数）
4 核机器 + 虚拟线程：    吞吐 ~10000 QPS（CPU 跑满才到顶）
```

### 5.2 ❌ 不适合：CPU 密集

```java
// 反例
try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 1_000_000; i++)
        ex.submit(() -> compute(i));   // 纯 CPU
}
```

虚拟线程**不让出载体**就停不下来——CPU 任务一直占着载体，N 个载体线程被 N 个 CPU 任务霸占，剩下 99 万个虚拟线程干瞪眼。这不仅没好处，调度开销反而比直接用 `ForkJoinPool` 大。

**规则**：CPU 密集 → `ForkJoinPool` / `parallelStream` / 平台线程池。

### 5.3 ❌ 不适合：依赖 ThreadLocal 缓存

虚拟线程很多很多个，每个都有自己的 `threadLocals` —— 把 ThreadLocal 当缓存用 → 内存爆炸。
官方建议：用 **ScopedValue**（JEP 446 预览）替代部分 ThreadLocal 用法。

### 5.4 ⚠️ 慎用：用传统线程池跑虚拟线程

```java
// 反例
ExecutorService pool = Executors.newFixedThreadPool(100);
Thread t = Thread.ofVirtual().unstarted(() -> ...);
pool.execute(t);   // 线程池只能跑 100 个，虚拟线程的扩展性反被限制
```

虚拟线程的设计哲学：**便宜、扔掉、不复用**。配 fixed pool 就退回传统模型了。
**正解**：`Executors.newVirtualThreadPerTaskExecutor()`，每任务一新虚拟线程。

## 六、ScopedValue（搭档）

### 6.1 痛点

虚拟线程下 ThreadLocal 不再合适：
- 每个虚拟线程都有独立 ThreadLocalMap
- 数量多 → 内存浪费 + GC 压力大
- 弱引用清理机会变少

### 6.2 ScopedValue（JDK 21 incubator → JDK 24 final）

```java
public class Server {
    static final ScopedValue<User> CURRENT_USER = ScopedValue.newInstance();

    void handle(Request req) {
        ScopedValue.where(CURRENT_USER, authenticate(req)).run(() -> {
            // 这个 scope 内 CURRENT_USER.get() 是 authenticate 的结果
            doBusinessLogic();
        });
        // scope 结束后自动清理
    }
}
```

特性：
- **不可变**（无 set，只在 where().run 中写入）
- **范围限定**（scope 出去自动清理，不会泄漏）
- **跨虚拟线程能继承**（结合 StructuredTaskScope）

业务最常用的 ThreadLocal 用例（用户上下文 / 事务上下文）大都能换 ScopedValue。

## 七、StructuredConcurrency（结构化并发，JDK 21 incubator）

### 7.1 思路

经典并发的痛：父任务和子任务的生命周期没绑定 —— 父挂了子还在跑、子挂了父继续跑、子异常了父不知道。

```java
// 老写法
ExecutorService pool = ...;
Future<X> f1 = pool.submit(taskA);
Future<Y> f2 = pool.submit(taskB);
X x = f1.get();
Y y = f2.get();   // 如果 taskA 已经抛异常了，taskB 还在傻跑
```

### 7.2 StructuredTaskScope

```java
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Subtask<X> sx = scope.fork(taskA);
    Subtask<Y> sy = scope.fork(taskB);
    scope.join().throwIfFailed();    // 等所有完成；任一失败就取消其他
    return new Pair<>(sx.get(), sy.get());
}  // try-with-resources 保证 scope 关闭，所有子任务必然终止
```

**核心保证**：父任务 scope 退出时，所有 fork 的子任务**必然终止**——天然防泄漏。

业务里替代 `CompletableFuture.allOf` 模式，更结构化、可读性更好。

## 八、与 Reactor / Coroutine 的对比

| | 虚拟线程 | Reactor (WebFlux) | Kotlin 协程 |
| --- | --- | --- | --- |
| 写法 | 顺序代码 | 链式操作符 | suspend 函数 |
| 学习曲线 | **平**（API 同 Thread） | 陡 | 中 |
| 改造代码量 | 一行 enable | 全栈重写 | 标 suspend |
| 栈跟踪 | **正常顺序栈** | 难（异步链路）| 协程栈 |
| 背压 | 无（业务自管） | ✅ Reactive Streams | ✅ Channel |
| 阻塞 API 兼容 | ✅ JDBC 等都能用 | ❌ 必须全异步 | 部分 |
| 性能上限 | 高 | 最高 | 高 |
| 生态成熟度 | 2024 起爆发 | 成熟 | Kotlin 圈 |

**判断**：
- 全栈新项目、追求极致性能 + 团队乐意学 → WebFlux
- 老项目 / 团队上手成本敏感 / Spring MVC + JDBC 体系 → **虚拟线程一行配置升级**
- Kotlin 项目 → 协程

## 九、生产踩坑

### 9.1 synchronized 引发隐性 pin → 吞吐反降

**现象**：升级 JDK 21 + Spring Boot 3.2 + virtual thread enable，压测吞吐没涨甚至降了。
**排查**：`-Djdk.tracePinnedThreads=full` 看到大量 `<== monitors:1` —— 业务里 synchronized + DB 调用。
**修复**：替换为 ReentrantLock，或等 Java 24（JEP 491）。

### 9.2 ThreadLocal 内存膨胀

**现象**：跑了一会儿后老年代涨得快。
**根因**：100w 虚拟线程 × 每个 ThreadLocalMap 几个 entry = 大量 Entry 对象。
**修复**：能换 ScopedValue 的场景换 ScopedValue；不能换的尽量减少 ThreadLocal 使用。

### 9.3 数据库连接池打爆

**现象**：以前 200 平台线程 200 个数据库连接刚刚好；上虚拟线程后并发飙升，HikariCP 连接耗尽。
**根因**：业务并发数 × 单请求持有连接时长 = 连接需求；虚拟线程把第一项放大几十倍。
**修复**：要么扩连接池上限（DB 容量允许），要么用 `Semaphore` 限流。**虚拟线程不是银弹** —— 下游容量没扩之前光放大并发是把瓶颈推下去。

### 9.4 用 ForkJoinPool.commonPool 跑阻塞任务

```java
CompletableFuture.supplyAsync(() -> jdbcCall());   // 在 commonPool 跑
```
commonPool 是给虚拟线程调度用的（也是 parallelStream 的基础），阻塞任务把它占住——虚拟线程调度也卡了。
**修复**：CompletableFuture 永远传专用 pool。

### 9.5 误把虚拟线程当 CPU 加速器

CPU 密集任务塞虚拟线程没好处反而慢——载体被霸占 + 调度开销。
**修复**：CPU 密集走 `ForkJoinPool`、`parallelStream`、平台线程池。

### 9.6 Tomcat 老版本不支持虚拟线程

Tomcat 10.1.10+ 才支持。Spring Boot 3.0 默认 Tomcat 10.1，但建议升 3.2+ 以获得完整虚拟线程支持。

## 十、面试高频追问

**Q1：虚拟线程和平台线程区别？**
- 平台线程：1:1 映射 OS 线程，创建贵（~10μs）、栈占 1MB、数量级 1000
- 虚拟线程：M:N 调度到少量载体线程，创建廉价（~1μs）、栈按需扩缩、数量级 1000000+

**Q2：虚拟线程怎么实现"阻塞时不占线程"？**
基于 Continuation：阻塞时 JVM 把虚拟线程的栈帧打包放堆上（unmount），载体线程释放出来跑别的虚拟线程；阻塞结束后再装回某个空闲载体（mount）继续。

**Q3：synchronized 为什么 pin 载体线程？怎么解？**
JDK 21 的 synchronized 持有 monitor 锁是在 JVM 内部用 OS mutex 实现的，没法在持锁阻塞时 unmount。**解法**：换 ReentrantLock（JDK 21 已优化）；等 JEP 491（Java 24+）后 synchronized 也能 unmount。

**Q4：虚拟线程适合什么场景？不适合什么？**
- ✅ IO 密集 + 高并发：JDBC、HTTP、Redis、文件
- ❌ CPU 密集：占着载体不让出，反而更慢
- ❌ 大量 ThreadLocal 缓存：每个 VT 都有自己的 ThreadLocalMap，内存爆
- ❌ 与传统 fixed 线程池配合：失去扩展性

**Q5：Tomcat 接虚拟线程后怎么改造业务代码？**
**几乎不用改**——这是虚拟线程最大卖点。Spring Boot 3.2 加 `spring.threads.virtual.enabled=true` 就开。原 JDBC 阻塞代码、`RestTemplate` 同步调用全部不变。

**Q6：虚拟线程能完全替代 Reactor / WebFlux 吗？**
- 改造成本：✅ 大幅降低
- 性能上限：WebFlux 仍略高（无 unmount/mount 开销）
- 背压：Reactor 自带 Reactive Streams，虚拟线程要业务自管
- 栈跟踪可读性：虚拟线程 ✅（顺序栈），Reactor ❌（链路化）
**结论**：除非追求极致性能 / 已用 Reactor，**虚拟线程是更好的默认选择**。

**Q7：怎么诊断 pin 问题？**
启动加 `-Djdk.tracePinnedThreads=full`，触发 pin 时控制台打印栈，看 `<== monitors:N` 标记的位置。也可以接 JFR 事件 `jdk.VirtualThreadPinned`。

**Q8：ScopedValue 和 ThreadLocal 怎么选？**
- ScopedValue：**新代码 + 范围明确**（请求级、事务级），不可变 + 自动清理
- ThreadLocal：兼容老代码、可变状态、需要 set / remove 显式管理
虚拟线程多的场景 ScopedValue 内存占用更友好。

**Q9：StructuredConcurrency 解决什么？**
解决"父子任务生命周期失控"——父退出时所有子任务必然终止；任一子任务失败可以触发兄弟取消。替代 CompletableFuture allOf 模式。

**Q10：JDK 21 之前怎么"近似"虚拟线程的效果？**
- 用 Reactor / WebFlux 全栈异步
- 用 Kotlin 协程（虽然 JVM 上跑）
- 用 Quasar（开源协程库，需要字节码插桩）
- 直接 NIO + 自己写状态机
都没虚拟线程的"零改造代码"优势。

## 十一、答题模板（120 秒话术）

> 虚拟线程是 JDK 21 GA 的 Project Loom 产物，**目标是让"顺序阻塞代码"享受异步级吞吐**。
>
> 原理：M:N 调度——M 个虚拟线程复用 N 个**载体线程**（默认 N = CPU 核数）。基于 **Continuation**：阻塞时 JVM 把栈帧从 OS 栈卷到堆上（**unmount**），载体释放去跑别的虚拟线程；IO 结束后再装回某个空闲载体（**mount**）。栈按需扩缩，单个虚拟线程几百字节起步，**百万级并发**毫无压力。
>
> API 完全兼容 `Thread`：`Thread.startVirtualThread()` / `Executors.newVirtualThreadPerTaskExecutor()`。Spring Boot 3.2 一行 `spring.threads.virtual.enabled=true` 接管 Tomcat 工作池，**业务代码 0 改动**。
>
> **最大坑是 pin 问题**：synchronized 持锁阻塞、native 方法 / 部分老 IO 库——载体被钉死无法切换，退化成传统线程模型。**JDK 21 现状要避开 synchronized，改用 ReentrantLock**（已优化）；JEP 491（Java 24+）才彻底修复。诊断用 `-Djdk.tracePinnedThreads=full`。
>
> 适用场景：**IO 密集 + 高并发**（传统 Spring MVC + JDBC + RPC）。
> 不适用：CPU 密集（占载体不让出）、大量 ThreadLocal 缓存（每个 VT 一份，内存爆）、与 fixed 线程池配合（失去扩展性）。
>
> 配套：**ScopedValue** 替代 ThreadLocal（不可变 + 范围限定），**StructuredTaskScope** 提供结构化并发（父子任务生命周期绑定）。
>
> 与 Reactor 对比：**改造成本 vs 性能上限的取舍**——新项目极致性能选 WebFlux，老项目升级或团队上手成本敏感选虚拟线程。
