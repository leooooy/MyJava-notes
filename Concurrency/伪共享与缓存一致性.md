# 伪共享与缓存一致性（False Sharing & MESI）

> 中间件 / 高性能岗位高频题。Disruptor / Netty / LongAdder 不理解这个就用不好。本篇讲清：
> ① CPU 缓存层级 + 缓存行（cache line）
> ② **MESI 协议**：缓存怎么保持一致
> ③ **伪共享**：两个无关变量共一个 cache line 导致性能崩盘
> ④ `@Contended` 注解 + 手动 padding 解法
> ⑤ JDK 哪些地方在用：LongAdder、ConcurrentHashMap、Disruptor

> 前置：[JMM 内存模型](./JMM内存模型.md)、[Volatile](./Volatile.md)、[CAS 与原子类](./CAS与原子类.md)

## 一、CPU 缓存基础

### 1.1 三级缓存层级

```
       ┌──────────────────────────────────────┐
       │             CPU Core                  │
       │      ┌────────────────────────┐       │
       │      │     寄存器 (Register)   │       │ <1 ns
       │      └─────────┬──────────────┘       │
       │                ▼                       │
       │      ┌────────────────────────┐       │
       │      │  L1 Cache (~32-64KB)   │       │ ~1 ns
       │      └─────────┬──────────────┘       │
       │                ▼                       │
       │      ┌────────────────────────┐       │
       │      │  L2 Cache (~256KB-1MB) │       │ ~3-10 ns
       │      └─────────┬──────────────┘       │
       └────────────────┼───────────────────────┘
                        ▼
       ┌──────────────────────────────────────┐
       │   L3 Cache (~8-64MB, 多核共享)         │ ~10-40 ns
       └──────────────┬───────────────────────┘
                      ▼
       ┌──────────────────────────────────────┐
       │       主内存 DRAM                      │ ~100-200 ns
       └──────────────────────────────────────┘
```

**核心数字**：访问主内存比访问 L1 慢 **~100 倍**。CPU 运行速度远超内存——所以有缓存。

### 1.2 缓存行（Cache Line）

CPU 加载数据**不是按字节**而是按**缓存行**（典型 **64 字节**）：
```
要读 long a，CPU 把 a 所在的 64 字节整块拉进 L1：
[a (8 bytes) | b (8) | c (8) | d (8) | e (8) | f (8) | g (8) | h (8)]
                              ↑ 一共 64 字节，整块加载，整块标记
```

**好处**：空间局部性——下次读 a 附近的数据直接命中 L1。
**坏处**：**伪共享**（下面要讲的核心问题）

### 1.3 看自己机器的缓存行

```bash
# Linux
cat /sys/devices/system/cpu/cpu0/cache/index0/coherency_line_size
# 通常返回 64

# Java
Unsafe.dataCacheLineFlushSize()
```

绝大多数现代 CPU（x86 / ARM）都是 **64 字节**。

## 二、MESI 协议（缓存一致性）

### 2.1 痛点

多核 CPU 各自有自己的 L1/L2 cache。如果 Core 1 改了变量 X，Core 2 的 L1 里 X 还是旧值，怎么保证一致？

**MESI 协议**：每个缓存行 4 个状态。

### 2.2 4 种状态

| 状态 | 含义 |
| --- | --- |
| **M (Modified)** | 已修改，本核独占，**未写回主内存** |
| **E (Exclusive)** | 独占未修改，跟主内存一致，只有本核有 |
| **S (Shared)** | 共享，多核都有，跟主内存一致 |
| **I (Invalid)** | 无效，必须重新从主内存（或别的核）加载 |

### 2.3 工作流程

```
初始：主内存 X = 1，所有 cache 都 I（没缓存）

Core 1 读 X
  → 主内存读出 X=1，Core 1 cache: E
Core 2 读 X
  → 跨核协议：Core 1 cache 降级 S，Core 2 cache 也 S
Core 1 写 X = 2
  → 广播失效：Core 2 cache 变 I
  → Core 1 cache 变 M（本核 X=2，主内存仍是 1）
Core 2 读 X
  → cache 是 I，必须查询：Core 1 把 X=2 给 Core 2（cache to cache 传输）
  → Core 1 cache 变 S，Core 2 cache 变 S
```

**关键代价**：
- 状态切换涉及**核间通信**（消息总线 / 环形互联）
- 一次缓存行从 M 变 I 大概要 **几十纳秒**
- 高频争用同一缓存行 → "**缓存行乒乓**"（cache line ping-pong）

### 2.4 MESIF / MOESI 是什么

Intel 用 **MESIF**（多了 Forward 状态，一个负责响应别人请求）；AMD 用 **MOESI**（多了 Owner，可以脏数据共享）。原理一致，细节差异面试不必深究。

## 三、伪共享（False Sharing）

### 3.1 灾难场景

```java
class Counter {
    volatile long a;
    volatile long b;
}
Counter c = new Counter();

// Thread 1
while (true) c.a++;

// Thread 2
while (true) c.b++;
```

a 和 b 是**完全无关的两个变量**，但因为它们在内存里**挨着**（Java 对象布局），都落在**同一个 64 字节缓存行**：

```
缓存行 [obj_header | a (8) | b (8) | padding...]
                    ↑核1写  ↑核2写
```

每次 Core 1 写 `a`：
- Core 1 cache 变 M
- 广播失效：Core 2 cache 变 I（即使 b 没变）
- Core 2 写 b 时发现 cache 是 I，要重新拉取
- Core 2 cache 变 M，反过来让 Core 1 cache 变 I
- ...无限乒乓

**结果**：两个变量"逻辑上互不相关"，物理上"互相争抢缓存行"——**性能可能比串行还慢 5-10 倍**。

### 3.2 实测对比

```java
// 不修复
class Sharing {
    volatile long a;
    volatile long b;
}

// 修复：padding 隔离
class Padded {
    volatile long a;
    long p1, p2, p3, p4, p5, p6, p7;   // ★ 7 个 long 填满 56 字节
    volatile long b;
}
```

64 位机器，对象头 16 字节 + a（8 字节）+ 7 个 long padding（56 字节）= 80 字节，b 必然落到下一个缓存行。

实测（i7，2 核分别狂写 a / b）：
- 不修复：~3 秒
- padding：~0.5 秒（**6× 提速**）

## 四、@Contended 注解（JDK 8+）

### 4.1 用法

```java
import sun.misc.Contended;     // JDK 8
// 或 jdk.internal.vm.annotation.Contended;  JDK 9+

class Cell {
    @Contended
    volatile long value;
}
```

JVM 自动给 value 字段前后填充 128 字节（默认值，比 64 大是为了防止某些 CPU 的 prefetch 把相邻缓存行也拉进来）。

### 4.2 启用

JDK 9+ 默认对**应用代码**禁用 `@Contended`，需要：
```bash
-XX:-RestrictContended
```
JDK 8 默认开启。

JDK 内部代码（如 LongAdder）不受这个限制——`-XX:-RestrictContended` 主要影响业务代码。

### 4.3 padding 大小调

```bash
-XX:ContendedPaddingWidth=128   # 默认 128，可调
```

### 4.4 为什么默认 128 而不是 64

**CPU prefetch 优化**：某些 CPU（Intel Sandy Bridge+）会预读相邻缓存行（Adjacent Cache Line Prefetch）。所以连续的 2 个 64 字节缓存行可能"打包失效"——padding 128 才彻底隔离。

## 五、JDK 实战案例

### 5.1 LongAdder

```java
@jdk.internal.vm.annotation.Contended
static final class Cell {
    volatile long value;
    Cell(long x) { value = x; }
    final boolean cas(long cmp, long val) { ... }
}
```

LongAdder 的核心思想是**分散累加**到多个 Cell，每个线程根据 hash 命中不同 Cell——但如果两个 Cell 共一缓存行，分散就白做了。`@Contended` 保证每个 Cell 独占缓存行。

详见 [CAS 与原子类 - LongAdder](./CAS与原子类.md#四longadder高竞争利器jdk-8)。

### 5.2 ConcurrentHashMap.CounterCell

```java
@jdk.internal.vm.annotation.Contended
static final class CounterCell {
    volatile long value;
    CounterCell(long x) { value = x; }
}
```

CHM 的 size 计数也用分段 + `@Contended`。

### 5.3 ForkJoinPool.WorkQueue

每个 Worker 的本地 Deque 也用 `@Contended` —— Worker 之间的字段（base、top）经常被偷者读，本人写，必须隔离。

### 5.4 Thread 类（JDK 8+）

```java
public class Thread {
    @Contended("tlr")
    long threadLocalRandomSeed;
    @Contended("tlr")
    int threadLocalRandomProbe;
    ...
}
```

`ThreadLocalRandom` 的种子也 padding——多线程频繁调 `nextInt()` 时避免缓存行争用。

## 六、Disruptor 的极致优化

### 6.1 Disruptor 简介

LMAX 开源的高性能内存队列（核心交易系统用），单线程处理 600 万 TPS。秘诀就是**死磕缓存行**。

### 6.2 RingBuffer 的 padding

```java
class RingBuffer {
    long p1, p2, p3, p4, p5, p6, p7;       // 头部 padding
    private volatile long cursor;
    long p8, p9, p10, p11, p12, p13, p14;  // cursor 后 padding

    private final Object[] entries;        // 数组本身
    long p15, p16, p17, p18, p19, p20, p21;
}
```

cursor 这个高频读写的字段独占一个缓存行——生产者写 cursor、消费者读 cursor，互不影响对方的缓存。

### 6.3 序列号也是缓存行级 padding

```java
class Sequence extends RhsPadding {
    static final long INITIAL_VALUE = -1L;
    private static final long VALUE_OFFSET;
    static { ... }
    public long get() { return value; }
    ...
}
class LhsPadding   { long p1, p2, p3, p4, p5, p6, p7; }
class Value extends LhsPadding { volatile long value = -1L; }
class RhsPadding extends Value { long p9, p10, p11, p12, p13, p14, p15; }
```

继承链堆 padding——**手动构造缓存行布局**，比 `@Contended` 还显式。Disruptor 早于 JDK 8 没法用注解。

## 七、什么时候要关心伪共享

### 7.1 ✅ 该关心

- **多核狂写** 不同字段（高频累加 / 状态切换）
- 字段是 **volatile / Atomic**（每次写都触发缓存一致性）
- 性能敏感路径（中间件、交易系统、监控埋点）
- 字段紧密相邻、对象数组（`Cell[]`、`Sequence[]`）

### 7.2 ❌ 不必关心

- 单线程访问
- 读多写少（MESI 在 S 状态下读不冲突）
- 业务代码 99% 场景（QPS 不到 10w 时伪共享差异不显著）

### 7.3 性能差异有多大

实测 16 核机器，4 个线程各自更新自己的字段：
| | 吞吐 |
| --- | --- |
| 同一缓存行（伪共享） | 1× baseline |
| 不同缓存行（padding） | **8-15× baseline** |

但前提是**真的高频争用**——单字段每秒访问百万次以上。普通业务感知不明显。

## 八、生产踩坑

### 8.1 自定义计数器没 padding，QPS 上不去

**现象**：自研监控埋点，每个 metric 一个 AtomicLong，几个线程压测吞吐曲线异常陡降。
**根因**：100 个 AtomicLong 数组紧凑布局，10 个 metric 共一缓存行。
**修复**：换 LongAdder（自带 @Contended）。

### 8.2 `@Contended` 不生效

**现象**：JDK 9+，加了 `@Contended` 注解但没效果。
**根因**：默认开启 `-XX:+RestrictContended`，业务代码注解被忽略。
**修复**：启动加 `-XX:-RestrictContended`。

### 8.3 数组元素的伪共享被忽略

```java
volatile long[] counters = new long[8];
// 8 个 long * 8 字节 = 64 字节，全在一个缓存行
```

数组里 `@Contended` 不能直接用（注解只能加字段）。
**修复**：包成对象数组：
```java
class PaddedCounter {
    @Contended volatile long value;
}
PaddedCounter[] counters = new PaddedCounter[8];
```

### 8.4 误以为 padding 一定能加速

低频场景：每秒访问 1000 次的字段，加 padding 没差异，反而徒增内存占用。**只有真热点 + 高频写争用才值得**。

### 8.5 ThreadLocal 改造为 padding 数组

ThreadLocal 性能不够，业务以为换"每核一份 + padding 数组"会更快。
**问题**：Java 没办法绑定线程到固定核（OS 调度），所以"每核一份"的前提就不成立——这种优化在 JVM 上做不到 native 那么彻底。

## 九、面试高频追问

**Q1：缓存行多大？为什么是 64 字节？**
绝大多数 x86 / ARM 是 64 字节。原因是历史 + 平衡：8 个 long、8 个 int+8 字节的 Java 对象头都能装下，太小空间局部性收益小，太大伪共享代价大。

**Q2：MESI 4 个状态？**
**M**odified（独占已改）/ **E**xclusive（独占未改）/ **S**hared（多核共享）/ **I**nvalid（失效）。状态切换通过核间通信实现一致性。

**Q3：伪共享是什么？**
两个或多个线程访问的**不同变量**恰好落在**同一个缓存行**，缓存行被反复失效—— MESI 协议下"互相干扰"，性能像在争用同一个变量。

**Q4：怎么解决伪共享？**
- `@Contended` 注解（JDK 8+，业务代码需要 `-XX:-RestrictContended`）
- 手动 padding（继承链 / 填充字段）
- 把热点字段拆到不同对象

**Q5：为什么 padding 用 128 字节而不是 64？**
某些 CPU 有相邻缓存行 prefetch（一次读 2 行）—— 64 padding 仍可能被打包失效。128 是更安全的默认值。

**Q6：JDK 哪些地方用了 @Contended？**
LongAdder.Cell、ConcurrentHashMap.CounterCell、ForkJoinPool.WorkQueue、Thread 的 ThreadLocalRandom 字段、StripedLock 等。

**Q7：volatile 和伪共享什么关系？**
volatile 写要广播失效（StoreLoad 屏障）—— 一次 volatile 写让所有别的核的对应缓存行进 I 态。如果有伪共享，**别的无关变量被连带失效**，影响放大。**伪共享对 volatile / atomic 字段的影响最严重**。

**Q8：Disruptor 为什么这么快？**
- RingBuffer 数组（avoid GC + cache friendly）
- 单写多读 / 多写单读避免锁
- **手动 padding 消除伪共享**（cursor / sequence）
- 内存预分配，无 GC

**Q9：单核机器需要担心伪共享吗？**
不需要——伪共享是多核 cache 一致性导致的，单核没这个问题。

**Q10：怎么实测某段代码有伪共享？**
- Linux `perf` 工具：`perf c2c` 可看 cache miss 详情
- JMH 微基准 + 加 / 不加 padding 对比吞吐
- 看 CPU `cache-miss` 计数器

## 十、答题模板（90 秒话术）

> CPU 加载数据按**缓存行**（典型 64 字节）。多核之间用 **MESI 协议**保持缓存一致性：每个缓存行 Modified / Exclusive / Shared / Invalid 4 个状态，写时广播让别的核失效。
>
> **伪共享**：两个无关变量恰好落在同一缓存行——一个核写 A，让别的核的整个缓存行失效，**连带 B 也得重新加载**。MESI 状态在多核间反复切换形成"缓存行乒乓"，volatile / 高频写场景下性能可能差 5-10 倍。
>
> **解法**：
> - **`@Contended` 注解**（JDK 8+）：JVM 自动 padding；业务代码需要 `-XX:-RestrictContended`
> - **手动 padding**：填充 7 个 long 字段（56 字节），保证关键字段独占缓存行
> - **padding 默认 128 字节**（不是 64）—— 防 CPU 相邻缓存行 prefetch
>
> JDK 实战：**LongAdder.Cell、ConcurrentHashMap.CounterCell、Thread.ThreadLocalRandom 字段、ForkJoinPool.WorkQueue**——都用了 @Contended。**Disruptor** 没法用注解（早于 JDK 8），用继承链手动 padding，单线程 600 万 TPS 的核心秘诀之一。
>
> 适用场景：**多核高频写 + 紧凑布局 + 性能敏感**（中间件、交易、监控埋点）。普通业务 QPS 1w 以下基本感知不到，**不要过度设计**。
