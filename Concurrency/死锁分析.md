# 死锁分析

> 并发面试的"压轴题"，生产事故的"经典款"。本篇讲清：
> ① 死锁四个必要条件：互斥 / 持有等待 / 不可剥夺 / 循环等待
> ② 5 大典型死锁模式（嵌套锁 / 锁顺序倒转 / 重入嵌套 / 数据库锁 / 线程池死锁）
> ③ 怎么用 jstack / jconsole / Arthas 排查
> ④ 6 大预防策略
> ⑤ 经典案例（转账、生产者-消费者、AbstractQueuedSynchronizer）

> 前置：[Synchronized](./Synchronized.md)、[Lock 原理](./Lock原理.md)、[线程池](./线程池.md)

---

## 一、死锁四要素（Coffman 条件）

```
1. 互斥（Mutual Exclusion）：资源不能同时被多个线程占有
2. 持有等待（Hold and Wait）：线程持有一些资源同时还在请求别的
3. 不可剥夺（No Preemption）：资源只能被持有者主动释放，不能被强夺
4. 循环等待（Circular Wait）：T1 等 T2 持有的资源，T2 等 T1 持有的（环）
```

**只要破坏任一条件就不会死锁**——这是预防策略的依据。

### 1.1 经典最小死锁

```java
final Object A = new Object();
final Object B = new Object();

new Thread(() -> {
    synchronized (A) {
        sleep(100);
        synchronized (B) { /* 永远到不了这 */ }
    }
}).start();

new Thread(() -> {
    synchronized (B) {
        sleep(100);
        synchronized (A) { /* 永远到不了这 */ }
    }
}).start();
```

T1 持 A 等 B；T2 持 B 等 A。互相等死。

## 二、5 大典型死锁模式

### 2.1 模式 1：嵌套锁顺序不一致（最常见）

经典转账：
```java
class Account {
    int balance;
    void transfer(Account from, Account to, int amount) {
        synchronized (from) {
            synchronized (to) {
                from.balance -= amount;
                to.balance += amount;
            }
        }
    }
}
// T1: transfer(A, B, 100)  → 锁 A → 等 B
// T2: transfer(B, A, 200)  → 锁 B → 等 A  → 死锁
```

**修复**：**统一加锁顺序**——按对象 hashCode / id 排序，永远先锁小的：
```java
void transfer(Account from, Account to, int amount) {
    Object first  = from.id < to.id ? from : to;
    Object second = from.id < to.id ? to   : from;
    synchronized (first) {
        synchronized (second) { ... }
    }
}
```

### 2.2 模式 2：synchronized + ReentrantLock 混用

```java
synchronized (obj) {           // T1 持有 obj 锁
    lock.lock();                // 尝试拿 lock
    ...
}
// 同时另一线程
lock.lock();                    // T2 持有 lock
synchronized (obj) {            // 尝试拿 obj 锁  → 死锁
}
```

**修复**：要么全 synchronized，要么全 Lock；坚决不要混用同一组对象。

### 2.3 模式 3：数据库 SELECT FOR UPDATE 顺序倒转

```sql
-- T1
BEGIN;
SELECT * FROM order WHERE id=1 FOR UPDATE;
SELECT * FROM order WHERE id=2 FOR UPDATE;   -- 等 T2

-- T2
BEGIN;
SELECT * FROM order WHERE id=2 FOR UPDATE;
SELECT * FROM order WHERE id=1 FOR UPDATE;   -- 等 T1   → 死锁
```

InnoDB 自动检测死锁后回滚一个事务。详见 [MySQL 死锁分析](../MySQL/死锁分析.md)。

### 2.4 模式 4：线程池任务相互依赖

```java
ExecutorService pool = Executors.newFixedThreadPool(2);
Future<X> f = pool.submit(() -> {
    Future<Y> inner = pool.submit(() -> getY());
    return wrap(inner.get());           // 等子任务结果
});
f.get();
```
2 个线程的池子，2 个父任务并行进来，子任务 submit 进队 → 父任务等子任务 → 子任务等线程槽 → **饥饿死锁**。

**修复**：
- 子任务别用同一个池
- 用 ForkJoinPool（任务窃取，不会因为递归饿死）
- pool 数量足够大，预留子任务空间

### 2.5 模式 5：Condition 用错锁对象

```java
private final ReentrantLock lock1 = new ReentrantLock();
private final Condition cond = lock1.newCondition();
private final ReentrantLock lock2 = new ReentrantLock();

void waitMe() {
    lock2.lock();           // ❌ 拿的是 lock2
    cond.await();           // 但 cond 属于 lock1
    lock2.unlock();
}
```
抛 IllegalMonitorStateException。不算死锁但常和死锁一起出现。**修复**：cond 必须配它属于的 lock 用。

## 三、排查死锁（生产标准流程）

### 3.1 jstack（首选）

```bash
jps                          # 找 PID
jstack -l <PID> > t.log      # -l 打印锁信息
```

死锁会在末尾打印：
```
Found one Java-level deadlock:
=============================
"Thread-1":
  waiting to lock monitor 0x00007f... (object 0x00000000d6..., a java.lang.Object),
  which is held by "Thread-0"
"Thread-0":
  waiting to lock monitor 0x00007f... (object 0x00000000d7..., a java.lang.Object),
  which is held by "Thread-1"

Java stack information for the threads listed above:
"Thread-1":
        at com.example.Demo.lambda$1(Demo.java:24)
        - waiting to lock <0x00000000d6...>
        - locked <0x00000000d7...>
"Thread-0":
        at com.example.Demo.lambda$0(Demo.java:14)
        - waiting to lock <0x00000000d7...>
        - locked <0x00000000d6...>

Found 1 deadlock.
```

**核心信息**：
- 哪些线程死锁
- 各自持有什么锁
- 各自等待什么锁
- 代码行号（`at com.example.Demo.lambda$1(Demo.java:24)`）

### 3.2 jconsole / VisualVM / JMC

GUI 工具，连上 JVM 后"线程"标签页有"检测死锁"按钮。

### 3.3 Arthas（生产首选）

```bash
$ arthas
[arthas]$ thread -b               # ★ 一键找出阻塞其他线程的线程
"Thread-0" Id=11 BLOCKED on java.lang.Object@xx
    at ...
"Thread-1" Id=12 BLOCKED on java.lang.Object@xx
    at ...
```
`thread -b` 直接输出"持锁还在阻塞其他线程"的线程。

### 3.4 ThreadMXBean（运行时检测）

```java
ThreadMXBean bean = ManagementFactory.getThreadMXBean();
long[] deadlocked = bean.findDeadlockedThreads();   // synchronized + Lock 都能查
if (deadlocked != null) {
    for (long tid : deadlocked) {
        ThreadInfo info = bean.getThreadInfo(tid);
        log.error("DEADLOCK: {}", info);
    }
}
```
可以接到监控告警里，**自动检测 + 报警 + dump**。

## 四、6 大预防策略

### 4.1 加锁顺序统一（最有效）

按对象 ID / hashCode 全局排序，保证所有路径加锁顺序一致。破坏循环等待。

### 4.2 用 tryLock 限时获取

```java
if (lock1.tryLock(100, MS)) {
    try {
        if (lock2.tryLock(100, MS)) {
            try { ... } finally { lock2.unlock(); }
        } else {
            // 拿不到 lock2，主动释放 lock1 + 重试
        }
    } finally { lock1.unlock(); }
}
```
破坏"持有等待"——拿不到就放弃 + 重试。

### 4.3 一次性申请所有资源

业务前置检查 + 一次性锁所有需要的：
```java
synchronized (allLocksHolder) {
    // 拿到所有需要的资源后再操作
}
```
但实际很难做到（资源是动态的）。

### 4.4 减少锁粒度 + 缩短临界区

锁内不做 IO、不调用未知代码（外部回调）、不做长操作。

### 4.5 用并发容器代替显式锁

ConcurrentHashMap / CopyOnWriteArrayList / BlockingQueue 已经处理好并发，不用自己锁。

### 4.6 避免嵌套锁

最好同一时刻只持一把锁。需要多把时优先用单一更粗粒度的锁，或者拆分业务消除嵌套需要。

## 五、相关问题：活锁与饥饿

### 5.1 活锁（Livelock）

线程都在动，但**始终在做"礼让"动作**，进展为零。

```java
while (true) {
    if (lock.tryLock()) {
        try { doWork(); break; }
        finally { lock.unlock(); }
    } else {
        sleep(random());     // 礼让
    }
}
```
两个线程都"我先让你"——互相让，谁也不干活。

**修复**：礼让间隔加随机化（伯努利试验）；或用公平锁强制 FIFO。

### 5.2 饥饿（Starvation）

线程一直得不到资源。常见：
- 非公平锁下队尾线程被新来的反复插队
- 优先级反转：低优先级持锁，高优先级等不到
- 线程池任务相互依赖导致部分任务永远跑不到

**修复**：公平锁（代价：吞吐降）；优先级继承；任务隔离不同池。

## 六、生产案例

### 6.1 案例：订单系统转账死锁

**现象**：晚上 8 点高峰偶发"接口卡死"，几分钟自动恢复。
**排查**：jstack 看到 `transferBalance` 方法上 30+ 线程 BLOCKED。
**根因**：转账方法 `synchronized (from); synchronized (to)`，A → B 和 B → A 同时发生时死锁；MySQL InnoDB 自动检测后回滚才"恢复"。
**修复**：改成按账户 ID 升序加锁。

### 6.2 案例：缓存刷新嵌套锁死

**现象**：某 RPC 服务偶发完全卡死。
**排查**：所有线程在等同一个 ReentrantLock；持锁线程在 `Loader.loadFromDB`，里面又调了相同 cache 的 `get`，再次走到 `lock.lock()`——**ReentrantLock 是可重入的**，正常不会死锁。但 Loader 里又用了另一个 ReentrantLock（缓存刷新锁）→ 顺序倒转 → 死锁。
**修复**：解耦缓存写锁 + 数据加载，加载放到锁外。

### 6.3 案例：线程池递归任务饿死

```java
ExecutorService pool = Executors.newFixedThreadPool(4);
class Task implements Callable<Integer> {
    int n;
    public Integer call() {
        if (n <= 1) return 1;
        Future<Integer> f1 = pool.submit(new Task(n-1));   // 自己又 submit
        Future<Integer> f2 = pool.submit(new Task(n-2));
        return f1.get() + f2.get();
    }
}
pool.submit(new Task(20));   // 20 层递归 → 几千个任务塞队列，4 个线程都在等子任务 → 死锁
```
**修复**：用 `ForkJoinPool`，它的 Work Stealing 让线程在等待时去帮别的任务跑。

## 七、面试高频追问

**Q1：死锁的四个必要条件？**
互斥、持有等待、不可剥夺、循环等待。**只要破坏任一条件就不会死锁**。

**Q2：怎么排查线上死锁？**
- jstack -l 看线程栈，搜 "Found one Java-level deadlock"
- Arthas `thread -b` 一键定位
- ThreadMXBean 程序内检测自动告警
- jconsole / VisualVM GUI

**Q3：synchronized 会死锁吗？**
会。可重入只解决了"同一线程递归调同步方法不死锁"，但**多线程跨多个锁的循环等待 synchronized 完全不能解**。

**Q4：tryLock 能完全避免死锁吗？**
能避免死锁，但可能引入活锁（互相让、谁都不干活）。要配合**随机退避** + 重试上限。

**Q5：ReentrantLock 死锁时怎么强制释放？**
正常路径不能。极端场景用 `lock.tryLock(timeout)` 超时让出，或 `lockInterruptibly()` 配合 `interrupt()` 中断等锁。但已经持有的锁如果业务卡死，只能 kill 线程 / JVM。

**Q6：MySQL 死锁会自己解开吗？**
InnoDB 有死锁检测，**自动回滚事务权重小的那个**（一般是修改行少的）。回滚后另一个事务正常完成。详见 [MySQL 死锁分析](../MySQL/死锁分析.md)。

**Q7：活锁和死锁区别？**
- 死锁：线程互相 BLOCKED，不动了
- 活锁：线程都在动，但**进展为零**（互相礼让 / 反复重试同一个失败操作）

**Q8：怎么避免线程池死锁？**
- 任务别在同一个池里 submit 子任务
- 真要嵌套用 ForkJoinPool（Work Stealing）
- 或者用 CompletableFuture + 不同 pool 链式编排

## 八、答题模板（90 秒话术）

> 死锁的四个必要条件：**互斥、持有等待、不可剥夺、循环等待**——破坏任一就不死锁。
>
> 5 大典型模式：
> - **嵌套锁顺序不一致**（A→B 和 B→A 转账），破解：**按 ID 排序统一加锁顺序**
> - **synchronized + Lock 混用**——禁
> - **数据库 SELECT FOR UPDATE 顺序倒转**——InnoDB 自动检测回滚
> - **线程池任务递归依赖**——用 ForkJoinPool 或分池
> - **Condition 配错 lock**——要配它属于的 lock
>
> 排查工具链：
> - **jstack -l**：看线程栈，最末尾 "Found one Java-level deadlock"
> - **Arthas thread -b**：一键找阻塞源头线程
> - **ThreadMXBean.findDeadlockedThreads**：程序内自动检测告警
>
> 6 大预防：
> - 统一加锁顺序（最常用）
> - tryLock 限时尝试
> - 缩小锁粒度 + 短临界区
> - 用并发容器代替显式锁
> - 避免嵌套锁
> - 锁内不调外部代码
>
> 衍生问题：
> - **活锁**——互相礼让无进展，加随机退避
> - **饥饿**——线程长期等不到资源，公平锁 + 优先级继承
