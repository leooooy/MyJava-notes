# 阻塞队列与并发容器

> 线程池的"后院"，生产者-消费者模式的脊梁。本篇讲清：
> ① BlockingQueue 接口的 4 组方法（抛异常 / 返回布尔 / 阻塞 / 超时）
> ② 7 种实现详解：ArrayBlockingQueue / LinkedBlockingQueue / SynchronousQueue / PriorityBlockingQueue / DelayQueue / LinkedBlockingDeque / LinkedTransferQueue
> ③ ABQ 一锁 vs LBQ 双锁：核心设计差异
> ④ DelayQueue 延迟原理（小顶堆 + leader 线程）
> ⑤ CopyOnWriteArrayList / ConcurrentSkipListMap 等其他并发容器
> ⑥ 与线程池配合的选型

> 前置：[Lock 原理](./Lock原理.md)、[等待唤醒机制](./等待唤醒机制.md)

## 一、BlockingQueue 接口

### 1.1 4 组方法

```java
public interface BlockingQueue<E> extends Queue<E> {
    // 入队
    boolean add(E e);              // 满则抛 IllegalStateException
    boolean offer(E e);            // 满则返回 false
    void put(E e) throws InterruptedException;                          // 满则阻塞
    boolean offer(E e, long t, TimeUnit u) throws InterruptedException; // 满则限时阻塞

    // 出队
    E remove();                    // 空则抛 NoSuchElementException
    E poll();                      // 空则返回 null
    E take() throws InterruptedException;                               // 空则阻塞
    E poll(long t, TimeUnit u) throws InterruptedException;             // 空则限时阻塞

    // 检查
    E element();                   // 空则抛
    E peek();                      // 空则 null
}
```

**记忆口诀**：4 组方法
| 操作 | 抛异常 | 返回特殊值 | 阻塞 | 超时 |
| --- | --- | --- | --- | --- |
| 入队 | add | offer | **put** | offer(t,u) |
| 出队 | remove | poll | **take** | poll(t,u) |

线程池 / 生产者-消费者**必用 put / take**——空 / 满时阻塞，省心高效。

### 1.2 阻塞机制

`put` / `take` 内部都是一把锁 + 两个 Condition：
```java
final ReentrantLock lock = new ReentrantLock();
final Condition notFull  = lock.newCondition();
final Condition notEmpty = lock.newCondition();
```

**put 满了**：`notFull.await()` → 等到有人 take 后 `notFull.signal()`
**take 空了**：`notEmpty.await()` → 等到有人 put 后 `notEmpty.signal()`

详见 [等待唤醒机制 - Condition](./等待唤醒机制.md#四reentrantlock--condition)。

## 二、ArrayBlockingQueue（ABQ）

### 2.1 特点

- **数组**实现，**有界**，构造时必须指定容量
- **一把锁**保护 put 和 take（同一个 ReentrantLock，2 个 Condition）
- **公平 / 非公平**可选（`new ArrayBlockingQueue<>(100, true)` 即公平）

### 2.2 数据结构

```
        items[capacity]
        ┌──┬──┬──┬──┬──┬──┐
        │ A│ B│ C│  │  │  │      ← 循环数组
        └──┴──┴──┴──┴──┴──┘
         takeIndex^   ^putIndex

        put: items[putIndex] = e; putIndex = (putIndex+1) % capacity
        take: e = items[takeIndex]; takeIndex = (takeIndex+1) % capacity
```

### 2.3 缺点

- 一把锁让 put 和 take **互相阻塞**——同时只有一个动作能进行
- 容量固定，初始化时定，跑期不能变

### 2.4 适用

- 容量明确、生产消费速度相近
- 线程池**有界队列**首选（防 OOM）

---

## 三、LinkedBlockingQueue（LBQ）

### 3.1 特点

- **单向链表**，**默认无界**（`Integer.MAX_VALUE`，构造时可传容量变有界）
- **两把锁**：putLock + takeLock —— **put 和 take 不互相阻塞**
- 仅支持非公平（无 fair 参数）

### 3.2 双锁的精髓

```java
private final ReentrantLock putLock = new ReentrantLock();
private final Condition notFull = putLock.newCondition();

private final ReentrantLock takeLock = new ReentrantLock();
private final Condition notEmpty = takeLock.newCondition();
```

put 锁 putLock，take 锁 takeLock，**生产者和消费者并行无阻塞**——这是 LBQ 比 ABQ 高吞吐的根。

但代价：要小心维护两个锁的协调。比如 put 完成后要 signal notEmpty——这要先拿 takeLock：
```java
private void signalNotEmpty() {
    takeLock.lock();
    try { notEmpty.signal(); }
    finally { takeLock.unlock(); }
}
```

### 3.3 LBQ vs ABQ

| 维度 | ABQ | LBQ |
| --- | --- | --- |
| 数据结构 | 数组 | 单向链表 |
| 容量 | 必须传 | 可选，默认无界 |
| 锁 | **一把** | **两把** |
| put / take 互斥 | 互斥 | **不互斥** |
| 高竞争吞吐 | 较低 | **较高** |
| 内存碎片 | 紧凑（数组）| 分散（每个 Node 独立分配）|
| GC 压力 | 小 | 大（每个 put 创建 Node）|
| 公平模式 | ✅ | ❌ |

**经验**：ABQ 适合容量小、可预测的场景；LBQ 适合高吞吐、对 GC 不敏感的场景。

### 3.4 警告：LBQ 默认无界

`Executors.newFixedThreadPool()` 内部就是 LBQ 默认无界。生产环境如果消费者跟不上，**任务堆积导致 OOM**。这是阿里手册【强制】禁用 Executors 工厂方法的根源。

## 四、SynchronousQueue（SQ）

### 4.1 特点

- **零容量**——既不存元素，也不持元素
- put 必须等到一个 take 配对，否则阻塞
- 适合"**直接交付**"场景

### 4.2 工作模式

```
T1: queue.put("a")       ──► 阻塞等待 take
T2: queue.take()         ──► 直接拿到 "a"，T1 也立刻返回
```

类似"接力棒"——producer 把元素直接塞到 consumer 手里。

### 4.3 用例：CachedThreadPool

```java
new ThreadPoolExecutor(0, Integer.MAX_VALUE, 60L, SECONDS, new SynchronousQueue<>());
```

- 来一个任务，**直接尝试塞给空闲线程**
- 没空闲？SQ 满（其实是没人接），立刻创建新线程
- 没任务时线程 60 秒空闲后销毁

适合短时大量小任务，缺点：**线程数无上限**，高峰可能创建上千线程，CPU 调度都吃不消。

### 4.4 公平 vs 非公平

```java
new SynchronousQueue<>(true)   // 公平：FIFO，按提交顺序配对
new SynchronousQueue<>(false)  // 非公平：LIFO，最后来的先配对（默认）
```

## 五、PriorityBlockingQueue

### 5.1 特点

- **无界**优先级队列（基于二叉堆数组）
- 出队顺序由 `Comparator` 决定（不是 FIFO）
- **不允许 null**

### 5.2 用例

```java
PriorityBlockingQueue<Task> q = new PriorityBlockingQueue<>(11,
    Comparator.comparingInt(Task::getPriority));   // 数字小的先出
```

- 任务调度（VIP 任务先执行）
- 邮件 / 消息按优先级处理

### 5.3 注意

- **无界**——没消费者会 OOM
- 出队不保证 FIFO（同优先级也可能乱序）

## 六、DelayQueue

### 6.1 特点

- 元素必须实现 `Delayed` 接口
- **元素到期才能取出**——延迟未到 take 阻塞
- **无界**

### 6.2 实现思路

```java
public class DelayQueue<E extends Delayed> {
    private final PriorityQueue<E> q = new PriorityQueue<>();   // 小顶堆
    private final ReentrantLock lock = new ReentrantLock();
    private Thread leader = null;                                 // ★ leader/follower 优化
    private final Condition available = lock.newCondition();

    public E take() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            for (;;) {
                E first = q.peek();
                if (first == null) available.await();
                else {
                    long delay = first.getDelay(NANOSECONDS);
                    if (delay <= 0) return q.poll();           // 已到期
                    if (leader != null) available.await();    // 有 leader 在等队首
                    else {
                        leader = Thread.currentThread();
                        try { available.awaitNanos(delay); }   // 我等队首，等满 delay
                        finally { if (leader == Thread.currentThread()) leader = null; }
                    }
                }
            }
        } finally {
            if (leader == null && q.peek() != null) available.signal();
            lock.unlock();
        }
    }
}
```

**Leader-Follower 模式**：只有一个线程（leader）真正等队首到期；其他线程无限等待。leader 取走元素后唤醒下一个。这样**避免多线程同时等同一个时间点的惊群效应**。

### 6.3 用例

- **延迟任务**（如订单 30 分钟未付自动取消、定时关闭连接）
- **本地缓存过期**

但生产环境延迟任务一般用 RocketMQ 延迟消息 / Redis ZSet 方案——DelayQueue 是单机内存方案，重启全丢。

### 6.4 ScheduledThreadPoolExecutor 内部就是 DelayQueue

`ScheduledThreadPoolExecutor` 的内部队列是 `DelayedWorkQueue`，本质就是 DelayQueue 变种——所以定时任务到期才会被 take。

---

## 七、LinkedBlockingDeque

- **双端队列**，put / take 两端都可
- 实现类似 LBQ 但用双向链表
- 用例：**工作窃取（Work Stealing）**——ForkJoinPool 的每个 Worker 用 Deque，自己从头部取，被偷的从尾部取，减少竞争

---

## 八、LinkedTransferQueue（JDK 7）

- 比 SynchronousQueue 更强：既能像 LBQ 一样存元素，也能像 SQ 一样直接交付
- `transfer(e)`：必须等 take 配对（同 SQ）；
- `tryTransfer(e)`：能直接交付就交付，否则不入队，立刻返回 false
- 性能比 LBQ 略好，业务里很少直接用

## 九、CopyOnWriteArrayList / Set

### 9.1 思路

写时**拷贝**整个底层数组，CAS 替换引用：
```java
public boolean add(E e) {
    final ReentrantLock lock = this.lock;
    lock.lock();
    try {
        Object[] elements = getArray();
        int len = elements.length;
        Object[] newElements = Arrays.copyOf(elements, len + 1);   // 全量拷贝
        newElements[len] = e;
        setArray(newElements);                                       // CAS 替换
        return true;
    } finally { lock.unlock(); }
}
```

- 读不加锁（读 volatile 引用，所以读是无锁的）
- 写时全量拷贝（O(N) 内存）

### 9.2 适用

- **读极多写极少**：监听器列表、白名单、配置项
- 读写比 100:1 以上

### 9.3 不适合

- 频繁写：每次写拷贝 N 元素，O(N) 内存 + GC 压力
- 强一致：写完立即读 **可能仍然读到旧数据**（迭代器是创建时的快照）

### 9.4 弱一致迭代器

```java
COWList list = new CopyOnWriteArrayList(...);
Iterator it = list.iterator();   // 拍快照
list.add("new");                   // 不会反映在 it 里
```
读不抛 ConcurrentModificationException，但读到的也不是最新数据——**业务能接受这种弱一致才能用**。

## 十、ConcurrentSkipListMap / Set

### 10.1 跳表

ConcurrentSkipListMap 是**跳表**实现的并发有序 Map：
```
 4 ──────────────► 13
 4 ──► 7 ────────► 13
 4 ─► 6 ─► 7 ─► 9 ─► 13     ← 数据层
```

每层是一个有序链表，上层是下层的"索引"。查询 / 插入 / 删除都是 O(log N) 平均。

### 10.2 vs ConcurrentHashMap / TreeMap

| | ConcurrentHashMap | ConcurrentSkipListMap | TreeMap |
| --- | --- | --- | --- |
| 有序 | ❌ | ✅（按 Key） | ✅ |
| 线程安全 | ✅ | ✅ | ❌ |
| 查找复杂度 | O(1) 平均 | O(log N) | O(log N) |
| 实现 | 数组+链表+红黑树 | 跳表 | 红黑树 |

**用例**：需要并发 + 有序的 NavigableMap 操作（subMap、headMap、firstKey 等）。

### 10.3 为什么跳表而不是并发红黑树？

- 红黑树旋转涉及多个节点的链接，并发实现难（要锁多个节点）
- 跳表插入 / 删除只影响**单节点的链接更新**，能用 CAS 实现无锁
- 实现简单，性能接近红黑树

## 十一、选型速查（与线程池配合）

| 场景 | 队列 | 拒绝策略 |
| --- | --- | --- |
| 通用业务 | **ArrayBlockingQueue（有界）** | CallerRunsPolicy |
| 高吞吐 + 不怕 OOM | LinkedBlockingQueue（有界） | CallerRunsPolicy |
| 短任务 + 突发流量 | SynchronousQueue（配大 maxPoolSize）| AbortPolicy |
| 任务有优先级 | PriorityBlockingQueue（务必有界）| - |
| 延迟任务 | DelayQueue / ScheduledThreadPoolExecutor | - |
| 工作窃取 | LinkedBlockingDeque（ForkJoinPool）| - |

**红线**：线程池队列**必须有界**（默认 LBQ 无界 = 隐患）。

## 十二、生产踩坑

### 12.1 LinkedBlockingQueue 无界 → OOM

`Executors.newFixedThreadPool(10)` 内部 LBQ 默认 `Integer.MAX_VALUE`。消费者跟不上，10w+ 任务堆积，堆 OOM。
**修复**：自建 ThreadPoolExecutor，传 `new LinkedBlockingQueue<>(2000)` 限定容量。

### 12.2 PriorityBlockingQueue 内存炸

下游慢，PBQ 无上限地堆，堆 GC 频繁。
**修复**：自定义有界优先级队列（继承重写 offer，满则拒绝），或换持久化方案。

### 12.3 DelayQueue 任务永远不出队

**根因**：业务实现 `getDelay()` 永远返回正数（写错时间单位、忘了减当前时间）。
**修复**：`getDelay = expireAt - currentTimeMillis`。

### 12.4 CopyOnWriteArrayList 写多导致 GC 风暴

**现象**：CMS old gen 频繁 GC。
**根因**：每次 `add` 拷贝整个 N 长度数组，N=10000 时每秒拷贝 100w 个引用。
**修复**：改 `Collections.synchronizedList` 或 `ConcurrentLinkedQueue`，或用 ConcurrentHashMap 替代（如果元素能用 key 区分）。

### 12.5 SynchronousQueue 配 fixed 线程池

`new ThreadPoolExecutor(10, 10, ..., new SynchronousQueue<>())` —— SQ 不存元素，10 个线程都忙时新任务直接被拒绝。
**修复**：SQ 必须配大 maxPoolSize（CachedThreadPool 模式）；fixed 模式必须用 ABQ / LBQ。

## 十三、面试高频追问

**Q1：BlockingQueue 的 4 组方法各自适用什么场景？**
- add/remove：业务严格不允许容量超限，越界要立刻 fail-fast
- offer/poll：尝试性操作，无副作用
- put/take：阻塞，**生产者-消费者标配**
- offer(t)/poll(t)：限时阻塞，超时降级

**Q2：ABQ 用一把锁，LBQ 用两把锁，原因是？**
ABQ 是循环数组，put 和 take 操作**同一个底层数组**，要协调 putIndex / takeIndex / count，一把锁简单。LBQ 是链表，put 操作 tail，take 操作 head，**两端独立**，可以并行——所以拆两把锁提升吞吐。

**Q3：DelayQueue 怎么实现"到期才能取出"？**
小顶堆按到期时间排序；take 时看队首：到期就取，没到期就 awaitNanos 等到队首到期。**Leader-Follower** 优化避免惊群。

**Q4：SynchronousQueue 容量是 0，能放数据吗？**
准确说"**不存数据**"。put 必须有 take 同时存在才能完成（直接交接）。底层用 TransferStack（非公平）或 TransferQueue（公平）实现。

**Q5：CopyOnWriteArrayList 为什么读不加锁？**
读的是 `final transient volatile Object[] array` —— 引用本身 volatile 保证可见性。写时拷贝完整新数组后 CAS 替换引用，旧数组的读者看到旧数据但不会出错（弱一致）。

**Q6：什么时候用 ConcurrentSkipListMap 而不是 ConcurrentHashMap？**
需要**有序遍历**或 NavigableMap 操作（subMap、ceilingKey 等）。CHM 是 hash 散列，无序。

**Q7：BlockingQueue 和 ConcurrentLinkedQueue 区别？**
- BlockingQueue：**阻塞** API（put/take），基于锁 + Condition
- ConcurrentLinkedQueue：**非阻塞**，基于 CAS 实现的无锁队列。take 空时返回 null（不阻塞）。
**选型**：生产者-消费者模式用 BlockingQueue（阻塞天然实现限速）；纯通信 + 无需阻塞用 ConcurrentLinkedQueue。

## 十四、答题模板（90 秒话术）

> BlockingQueue 是生产者-消费者模式的脊梁，提供 4 组方法（**抛异常 / 返回布尔 / 阻塞 put-take / 超时 offer-poll**）。实现核心是 **ReentrantLock + 2 个 Condition**（notFull / notEmpty）。
>
> 7 大实现：
> - **ArrayBlockingQueue**：数组 + **一锁**，有界，可公平 → 通用首选
> - **LinkedBlockingQueue**：链表 + **双锁**（putLock/takeLock 不互斥），默认无界 → 高吞吐但容易 OOM
> - **SynchronousQueue**：零容量直接交付 → CachedThreadPool 内部用
> - **PriorityBlockingQueue**：堆排序优先级 → 任务调度
> - **DelayQueue**：到期才出，Leader-Follower → 延迟任务、定时器（ScheduledThreadPoolExecutor 内部用）
> - **LinkedBlockingDeque**：双端 → 工作窃取（ForkJoinPool）
> - **LinkedTransferQueue**：SQ + LBQ 二合一
>
> 配套并发容器：
> - **ConcurrentHashMap**：高并发 hash
> - **ConcurrentSkipListMap**：并发有序 Map（跳表实现，CAS 友好）
> - **CopyOnWriteArrayList**：写时拷贝，**读多写极少**专用
>
> 与线程池配合的红线：**队列必须有界**——LBQ 默认无界是阿里手册禁用 Executors 工厂方法的根。
