# 等待唤醒机制

> 三种等待唤醒，不止是用法不同，**底层机制完全不同**。本篇讲清：
> ① synchronized + wait/notify：基于 ObjectMonitor 的 WaitSet / EntryList
> ② ReentrantLock + Condition.await/signal：基于 AQS 的 Condition Queue
> ③ LockSupport.park/unpark：底层原语，无需配合锁，靠"许可"
> ④ wait vs sleep / yield / join 的区别（高频陷阱题）
> ⑤ 虚假唤醒和为什么 wait 必须用 while 不能用 if

> 前置：[Synchronized](./Synchronized.md)、[AQS 原理](./AQS原理.md)

---

## 一、三种机制对比

| 维度 | wait/notify | Condition | LockSupport |
| --- | --- | --- | --- |
| 配合 | synchronized | Lock（一般 ReentrantLock） | 任意 |
| 底层 | ObjectMonitor | AQS Condition 队列 | UNSAFE.park |
| 锁释放 | 自动（wait 时） | 自动（await 时） | 不释放任何锁（也没拿锁） |
| 等待队列数 | 1 个 / 对象 | 任意多个 / Lock | n/a |
| 精确唤醒 | ❌（notifyAll 一锅端） | ✅（按 Condition 分组） | ✅（指定 Thread.unpark） |
| 中断响应 | ✅（抛 InterruptedException）| ✅ | ✅（不抛异常，但 park 立即返回） |
| 历史 | JDK 1.0 | JDK 1.5 | JDK 1.5 |

## 二、synchronized + wait/notify

### 2.1 基本用法

```java
final Object lock = new Object();
boolean ready = false;

// 等待方
synchronized (lock) {
    while (!ready) {                 // ★ 必须 while 不能 if
        lock.wait();                 // 释放 lock，进 WaitSet
    }
    doAfterReady();
}

// 通知方
synchronized (lock) {
    ready = true;
    lock.notifyAll();                 // 推荐 notifyAll，避免漏通知
}
```

### 2.2 ObjectMonitor 的 WaitSet 与 EntryList

```
┌──────────────────────────────────────┐
│         ObjectMonitor                │
├──────────────────────────────────────┤
│ Owner: T1（持有锁）                  │
├──────────────────────────────────────┤
│ EntryList: 等锁的线程（BLOCKED）     │
│   T2 → T3 → T4                       │
├──────────────────────────────────────┤
│ WaitSet:    调 wait() 的线程（WAITING）│
│   T5 → T6                            │
└──────────────────────────────────────┘
```

**wait() 三件事**（必须持有锁才能调，否则抛 IllegalMonitorStateException）：
1. **释放锁**（关键！与 sleep 的核心区别）
2. **当前线程加入 WaitSet**，状态 RUNNABLE → WAITING
3. park 挂起，等待 notify

**notify() 一件事**：
- 从 WaitSet 取一个线程（**JVM 自由选择，不保证 FIFO**），移到 EntryList
- 这个线程**不会立即执行**——它要等当前线程释放锁后，重新和 EntryList 里其他线程竞争锁

**notifyAll()**：把 WaitSet 全部线程移到 EntryList。

### 2.3 wait/notify 必须在 synchronized 内

```java
lock.wait();           // ❌ 没拿锁，IllegalMonitorStateException
synchronized(lock) {
    lock.wait();        // ✅
}
```

**为什么强制**：wait 要"先释放锁再挂起"，没有锁可释放谈何释放？JVM 通过 ObjectMonitor 的 owner 字段判断当前线程是否持锁。

### 2.4 wait(timeout) 三种返回原因

```java
synchronized (lock) {
    while (!cond) {
        lock.wait(1000);
        // 三种唤醒方式都会让 wait 返回：
        // (a) 别人调 notify/notifyAll
        // (b) 等够 timeout
        // (c) 被 interrupt（抛 InterruptedException）
        // (d) 虚假唤醒（spurious wakeup） ← 必须 while 重检
    }
}
```

## 三、虚假唤醒（必须用 while）

### 3.1 现象

```java
synchronized (lock) {
    if (!cond) lock.wait();   // ❌
    doSomething();             // 可能在 cond 仍然 false 的时候执行
}
```

POSIX 标准明确允许 wait/notify 实现 **spurious wakeup**——没人 notify，wait 自己也可能返回。这是 OS 层 futex 实现的优化（避免在 signal 处理时阻塞）。

### 3.2 修复

**永远用 while**：
```java
synchronized (lock) {
    while (!cond) lock.wait();
    doSomething();
}
```
醒来重检条件——还是 false 就再 wait，是 true 才向下走。

### 3.3 为什么 if 也错（即使不考虑虚假唤醒）

notifyAll 会唤醒所有等待者，他们抢锁串行执行。第一个进来的可能改了状态让 cond 不再成立——后续被唤醒的如果用 if，会"以为条件成立"地往下走，错。

## 四、ReentrantLock + Condition

### 4.1 用法

```java
final ReentrantLock lock = new ReentrantLock();
final Condition notFull  = lock.newCondition();
final Condition notEmpty = lock.newCondition();

void put(E x) throws InterruptedException {
    lock.lock();
    try {
        while (count == capacity) notFull.await();   // 等"不满"
        enqueue(x);
        notEmpty.signal();                           // 通知"非空"
    } finally { lock.unlock(); }
}
```

### 4.2 vs wait/notify

最大优势：**多个 Condition 实现精确唤醒**。

| | synchronized + wait/notify | ReentrantLock + Condition |
| --- | --- | --- |
| 等待队列 | 1 个 ObjectMonitor 1 个 WaitSet | 1 个 Lock 可创建任意多个 Condition |
| 唤醒粒度 | notifyAll 一锅端 | signal 精确唤醒某类等待者 |
| 中断 | wait() 抛 InterruptedException | await() 同样支持中断 |

**生产典型**：BlockingQueue 内部就是 1 把 ReentrantLock + 2 个 Condition（notFull、notEmpty）。

### 4.3 实现底层（详见 [AQS](./AQS原理.md)）

```
        AQS 主队列（等锁）           Condition 1 队列（等条件）
        head ─ T1 ─ T2 ─ T3          C1.firstWaiter ─ T5 ─ T6
                                     C2.firstWaiter ─ T7
        ▲                            ▲
        │                            │
       释放锁后唤醒 head 的 next     signal 把队首挪到 AQS 主队列
```

`await()`：
1. 把当前 Node 从 AQS 主队列删除（释放锁，state=0）
2. 把 Node 加到对应 Condition 的等待队列
3. park

`signal()`：
1. 从 Condition 队列取队首 Node
2. 加到 AQS 主队列尾
3. 它会按主队列 FIFO 规则被唤醒（**不会立即执行**）

## 五、LockSupport.park/unpark（底层原语）

### 5.1 用法

```java
Thread t = new Thread(() -> {
    LockSupport.park();          // 阻塞当前线程
    System.out.println("woken");
});
t.start();

Thread.sleep(100);
LockSupport.unpark(t);           // 唤醒指定线程
```

### 5.2 "许可"模型

每个线程有一个 **Permit（许可）**，0 / 1 两种状态：
- `unpark(t)`：把 t 的 permit 设 1（已经是 1 也不累加）
- `park()`：消耗 permit；permit 是 0 就阻塞，是 1 就立刻消耗后返回

```java
LockSupport.unpark(t);          // permit: 0 → 1
LockSupport.unpark(t);          // permit 仍 1（不累加！）
LockSupport.park();             // 消耗 permit，立即返回
LockSupport.park();             // 没 permit，阻塞
```

**关键性质**：**先 unpark 再 park 不会死锁**——这是 wait/notify 做不到的。

### 5.3 vs wait/notify 的优势

| 场景 | wait/notify | park/unpark |
| --- | --- | --- |
| 必须先 wait 再 notify | ✅（否则 notify 丢失） | ❌ 顺序无关 |
| 必须持有锁 | ✅ | ❌ 不需要任何锁 |
| 唤醒指定线程 | ❌（notify 随机选） | ✅ unpark(thread) |
| 中断处理 | 抛 InterruptedException | 不抛异常，park 直接返回 |

### 5.4 中断的处理

```java
LockSupport.park();
if (Thread.interrupted()) {       // park 不抛异常，要主动检查
    handleInterrupt();
}
```

### 5.5 谁在用 park/unpark

- AQS：acquireQueued 里 park 阻塞，release 后 unpark 后继
- ReentrantLock / Semaphore / CountDownLatch
- LockSupport / 锁的最底层

## 六、wait vs sleep vs yield vs join（高频陷阱）

| 方法 | 类 | 释放锁 | 状态变化 | 唤醒方式 |
| --- | --- | --- | --- | --- |
| `wait()` / `wait(t)` | Object | **释放** monitor 锁 | RUNNABLE → WAITING / TIMED_WAITING | notify / notifyAll / interrupt / 超时 |
| `sleep(t)` | Thread | **不释放**任何锁 | RUNNABLE → TIMED_WAITING | 时间到 / interrupt |
| `yield()` | Thread | 不释放 | 仍 RUNNABLE | OS 调度自行决定（提示性，可能立刻被重选） |
| `join()` / `join(t)` | Thread | 不释放当前对象锁，但内部用 wait（在 t 的 Thread 对象上） | RUNNABLE → WAITING / TIMED_WAITING | 目标线程 TERMINATED / interrupt / 超时 |

**易错点**：
- sleep 是 Thread.sleep（静态），睡的是当前线程
- wait 是 Object.wait（实例），必须配合 synchronized，**释放锁**
- join 内部就是 `synchronized (target) { target.wait() }`

## 七、生产踩坑

### 7.1 用 if 替代 while → 虚假唤醒后逻辑错

详见第 3 节。**永远用 while**。

### 7.2 notify 而不是 notifyAll → 信号丢失

**场景**：生产者 / 消费者用同一把锁同一个 wait 队列，notify 可能唤醒了"自己人"（同方向的等待者）而不是对面，导致都卡死。
**修复**：要么 notifyAll，要么用 ReentrantLock + 2 个 Condition 精确唤醒。

### 7.3 wait 不在 synchronized 里 → IllegalMonitorStateException

新人最常见的 NPE 之外的运行时错误。修复：移进 synchronized 块。

### 7.4 wait 的对象与锁的对象不一致

```java
synchronized (lockA) {
    lockB.wait();   // ❌ 拿的是 lockA 的锁，wait 的是 lockB 的 monitor
}
```
**修复**：wait/notify 必须用同一个对象。

### 7.5 没处理 InterruptedException

```java
try { lock.wait(); }
catch (InterruptedException e) { /* 默默吃掉 */ }
```
中断标志被清除，循环里 `Thread.currentThread().isInterrupted()` 永远 false → 线程关不掉。
**修复**：catch 后 `Thread.currentThread().interrupt()` 重打标，或者向上抛。

### 7.6 await 没在 lock 里调

```java
condition.await();   // ❌ 没拿锁，IllegalMonitorStateException
```
和 wait 一样，**Condition.await 也必须先 lock.lock**。

## 八、面试高频追问

**Q1：wait 为什么必须在 synchronized 块里？**
wait 的语义是"释放当前持有的锁，然后挂起"。没拿锁就没东西可释放，JVM 通过 ObjectMonitor.owner 校验当前线程是否持锁，没有就抛 `IllegalMonitorStateException`。

**Q2：wait(0) 和 wait() 区别？**
没区别，wait(0) = 永远等。

**Q3：notify 和 notifyAll 怎么选？**
- 等待者都在等同一个条件 → notify 节省（生产者-消费者用同一个 Condition 时不行）
- 多种等待者共用一个 wait 队列 → 必须 notifyAll
- **生产建议默认 notifyAll**，除非确认所有等待者都"等价"
- 升级到 Condition：用多个 Condition 精确唤醒，不用 notifyAll 一锅端

**Q4：notify 后会立即唤醒线程吗？**
不会。notify 只是把线程从 WaitSet 移到 EntryList，要等当前线程**释放锁**后，被唤醒的线程才能争锁。所以 notify 通常是 synchronized 块的最后一行。

**Q5：park/unpark 的"许可"是单个还是多个？**
**单个**。多次 unpark 不累加，permit 始终 0/1。这是和信号量的区别。

**Q6：先 unpark 再 park 会怎样？**
park 立刻返回，permit 被消耗。所以 park/unpark 顺序无关，**不会丢失唤醒**——这是它比 wait/notify 优秀的地方。

**Q7：Thread.sleep 为什么不释放锁？**
sleep 是 Thread 的静态方法，跟"对象锁"没关系。它只是让当前线程让出 CPU，所有持有的锁都还在。如果在 sleep 期间释放锁，其他线程可能把状态改了，醒来后逻辑错。

**Q8：Condition.signal 唤醒哪个线程？**
Condition 队列是 FIFO（单向链表，从 firstWaiter 开始），signal 唤醒队首。signalAll 唤醒整队（依次挪到 AQS 主队列尾）。

## 九、答题模板（90 秒话术）

> Java 三种等待唤醒机制：
>
> **synchronized + wait/notify**——基于 ObjectMonitor 的 WaitSet / EntryList。**wait 释放锁并挂起**，notify 把一个线程从 WaitSet 移到 EntryList（不立即唤醒）。必须**在 synchronized 内**调用，否则抛 IllegalMonitorStateException。一个对象只有一个 WaitSet，notify 不能精确唤醒。
>
> **ReentrantLock + Condition.await/signal**——基于 AQS Condition 队列。**每个 Lock 可以有多个 Condition**，实现精确唤醒（典型如 BlockingQueue 的 notFull / notEmpty）。await/signal 行为类似 wait/notify，但底层换成 AQS 队列管理。
>
> **LockSupport.park/unpark**——底层原语，**不需要任何锁**。基于"许可（permit）"模型，**先 unpark 再 park 不丢失唤醒**（wait/notify 做不到）。可以**唤醒指定线程**（notify 不行）。AQS / JUC 锁全靠它。
>
> 三个易错点：
> - **wait 必须用 while** 防虚假唤醒
> - **wait 释放锁、sleep 不释放**——区别核心
> - **wait/await 必须先持锁**，park 不需要
