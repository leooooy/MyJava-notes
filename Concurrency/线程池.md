# 线程池

> 后端面试 Top 1 高频。Spring / Tomcat / Dubbo / RocketMQ 全在用。本篇讲清：
> ① 7 大核心参数：corePoolSize / maxPoolSize / keepAliveTime / unit / workQueue / threadFactory / handler
> ② 工作流程：核心线程 → 队列 → 临时线程 → 拒绝
> ③ 4 种拒绝策略 + 5 种线程池状态
> ④ ctl 字段的位运算技巧
> ⑤ **阿里手册为什么禁用 Executors 工厂方法**
> ⑥ 核心线程数怎么算（CPU / IO 密集型公式）
> ⑦ 监控、动态调参、Tomcat 线程池

> 前置：[阻塞队列](./阻塞队列.md)、[Lock 原理](./Lock原理.md)

## 一、为什么要线程池

### 1.1 痛点：每请求一线程

```java
new Thread(task).start();         // 每请求新建线程
```
- **创建 / 销毁线程贵**：Linux 上一个 pthread 创建 ~10μs，OS 要分页表 / 内核栈
- **栈占内存**：默认 1MB / 线程，1 万线程 = 10GB 虚拟内存
- **OS 调度成本**：线程数远超 CPU 核数时上下文切换吃满 CPU

### 1.2 线程池的价值

| 价值 | 说明 |
| --- | --- |
| **复用** | 创建一次反复用，省掉 fork / join 的 OS 开销 |
| **限流** | 最多 N 个线程，超过限制走队列或拒绝，防止过载 |
| **统一管理** | 状态、监控、生命周期一处管 |
| **解耦** | 提交任务和执行任务分离，业务代码不关心调度 |

## 二、7 大核心参数（必背）

```java
public ThreadPoolExecutor(
    int corePoolSize,                  // ① 核心线程数
    int maximumPoolSize,               // ② 最大线程数
    long keepAliveTime,                // ③ 空闲存活时间
    TimeUnit unit,                     // ④ 时间单位
    BlockingQueue<Runnable> workQueue, // ⑤ 工作队列
    ThreadFactory threadFactory,       // ⑥ 线程工厂
    RejectedExecutionHandler handler   // ⑦ 拒绝策略
)
```

### 2.1 corePoolSize（核心线程数）

- 池子里**常驻的线程数**（默认即使空闲也不销毁）
- 第一次提交任务时不会预创建——任务来了才一个个建
- `prestartAllCoreThreads()` 可以预热全部
- `allowCoreThreadTimeOut(true)` 让核心线程也参与空闲销毁

### 2.2 maximumPoolSize（最大线程数）

- 队列满了之后，最多还能临时再开多少线程
- 这些"临时线程"超过 corePoolSize 的部分，**空闲超过 keepAliveTime 会被销毁**

### 2.3 keepAliveTime + unit（空闲存活时间）

临时线程（超过 corePoolSize 的部分）的最大空闲时间。

### 2.4 workQueue（工作队列）

详见 [阻塞队列](./阻塞队列.md)。线程池常用：
| 队列 | 性质 | 适用 |
| --- | --- | --- |
| `ArrayBlockingQueue` | 有界 | 通用 |
| `LinkedBlockingQueue` | 默认无界（隐患！） | 慎用 |
| `SynchronousQueue` | 零容量 | CachedThreadPool 模式 |
| `PriorityBlockingQueue` | 优先级 + **无界** | 任务排序 |
| `DelayQueue` | 延迟 | 定时调度 |

### 2.5 threadFactory（线程工厂）

定制线程：命名（**生产必须命名！**）、是否守护、优先级、UncaughtExceptionHandler。

```java
ThreadFactory factory = r -> {
    Thread t = new Thread(r);
    t.setName("order-pool-" + counter.incrementAndGet());
    t.setDaemon(false);
    t.setUncaughtExceptionHandler((th, e) -> log.error("uncaught", e));
    return t;
};
```

**生产规范**：用 Guava 的 `ThreadFactoryBuilder` 或 Apache Commons 的 `BasicThreadFactory`，避免线程名都是 `pool-1-thread-N`，jstack 排查时一脸懵。

### 2.6 handler（拒绝策略）

队列满 + 线程数到 max 时触发：

| 策略 | 行为 |
| --- | --- |
| **AbortPolicy**（默认） | 抛 `RejectedExecutionException` |
| **CallerRunsPolicy** | **提交任务的线程自己跑**（生产推荐：天然背压） |
| **DiscardPolicy** | 静默丢弃 |
| **DiscardOldestPolicy** | 丢弃队首最老任务，再尝试入队 |

**自定义**：实现 `RejectedExecutionHandler` 接口——常见做法是落 MQ / DB 持久化，避免任务丢失。

## 三、工作流程（必背）

```
                  submit(task)
                       │
                       ▼
      ┌─────────────────────────────┐
      │ 工作线程数 < corePoolSize？  │
      └─────────────────────────────┘
                ▼ NO          ▼ YES
                │              ▼
                │            创建核心线程执行任务
                ▼
      ┌─────────────────────────────┐
      │ workQueue 入队成功？         │
      └─────────────────────────────┘
                ▼ NO          ▼ YES
                │              ▼
                │           入队，等核心线程空闲
                ▼
      ┌─────────────────────────────┐
      │ 工作线程数 < maximumPoolSize？│
      └─────────────────────────────┘
                ▼ NO          ▼ YES
                │              ▼
                │          创建临时线程执行
                ▼
      ┌─────────────────────────────┐
      │      执行 RejectedHandler    │
      └─────────────────────────────┘
```

**口诀**：核 → 队 → 临 → 拒。

> **关键认知**：很多人以为"先开满 max 再入队"，**错了**。是"先开核心，满了进队，队满才开临时，再满才拒绝"。这意味着**有界队列 + max>core 才能真正在突发流量时弹性扩线程**——LBQ 无界永远入队成功，max 永远不会触发。

## 四、生命周期：5 种状态

```
RUNNING ──shutdown()──► SHUTDOWN ──队列空 + 无任务执行──► TIDYING ──terminated()──► TERMINATED
   │                       ▲
   └──shutdownNow()──► STOP ┘
```

| 状态 | 接收新任务 | 执行队列任务 | 中断进行中任务 |
| --- | --- | --- | --- |
| **RUNNING** | ✅ | ✅ | - |
| **SHUTDOWN** | ❌ | ✅ | ❌ |
| **STOP** | ❌ | ❌（清空队列）| ✅ interrupt 所有 worker |
| **TIDYING** | - | - | terminated() 钩子调用前 |
| **TERMINATED** | - | - | 完全结束 |

**shutdown vs shutdownNow**：
- `shutdown()`：温和——拒新任务，把队列里现有任务跑完
- `shutdownNow()`：强硬——拒新任务 + 清空队列 + interrupt 在跑的任务 → 返回未执行的任务列表

### 4.1 ctl 的位运算

```java
private final AtomicInteger ctl = new AtomicInteger(ctlOf(RUNNING, 0));

private static final int COUNT_BITS = Integer.SIZE - 3;          // 29
private static final int CAPACITY = (1 << COUNT_BITS) - 1;       // 5亿多

private static final int RUNNING    = -1 << COUNT_BITS;         // 高 3 位 = 111
private static final int SHUTDOWN   =  0 << COUNT_BITS;         // 高 3 位 = 000
private static final int STOP       =  1 << COUNT_BITS;
private static final int TIDYING    =  2 << COUNT_BITS;
private static final int TERMINATED =  3 << COUNT_BITS;
```

ctl 一个 int 同时存：
- **高 3 位**：线程池状态（5 种）
- **低 29 位**：worker 线程数

```java
private static int runStateOf(int c)     { return c & ~CAPACITY; }
private static int workerCountOf(int c)  { return c &  CAPACITY; }
```

**为什么这么搞**：CAS 同时改"状态 + 线程数"——一次 CAS 原子改两个字段（如 STOP + 线程数 0）。**这是高性能并发代码的经典套路**。

## 五、Executors 工厂方法的坑

JDK 自带 5 种工厂方法，**阿里手册【强制】禁用**，全部要自己 `new ThreadPoolExecutor()`：

| 工厂 | 内部实现 | 致命问题 |
| --- | --- | --- |
| `newFixedThreadPool(N)` | core=max=N, **LinkedBlockingQueue 无界** | 任务无限堆积 → OOM |
| `newSingleThreadExecutor` | core=max=1, **LBQ 无界** | 同上 |
| `newCachedThreadPool` | core=0, **max=Integer.MAX_VALUE**, SynchronousQueue | 突发流量瞬间创建几千线程 → 资源耗尽 |
| `newScheduledThreadPool(N)` | core=N, max=MAX, DelayedWorkQueue（无界）| 任务堆积 OOM |
| `newWorkStealingPool` | ForkJoinPool | 一般业务很少用 |

**生产正确姿势**：
```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    10,                                          // core
    50,                                          // max
    60L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(2000),              // ★ 必须有界
    new ThreadFactoryBuilder()
        .setNameFormat("order-pool-%d")
        .build(),
    new ThreadPoolExecutor.CallerRunsPolicy()    // ★ 推荐
);
```

## 六、核心线程数怎么算

### 6.1 经验公式

| 任务类型 | 公式 | 原理 |
| --- | --- | --- |
| **CPU 密集** | `线程数 = N + 1` | N 是 CPU 核数；+1 防止偶发 page fault 时 CPU 空闲 |
| **IO 密集** | `线程数 = N × (1 + WT/CT)` | WT = 等 IO 时间；CT = 计算时间 |
| **混合（绝大多数业务）** | 看链路：IO 越多线程越多 | 4-8 核机器一般 50-200 |

例：4 核机器，单请求 CPU 1ms + IO 10ms：
线程数 = 4 × (1 + 10/1) = **44**

### 6.2 实测调优更靠谱

公式只是起点，真值要靠压测：
1. 起 corePoolSize=N+1，逐步加大
2. 看 QPS 曲线 + 每个线程 CPU 利用率
3. QPS 不再上升或 CPU sys% 飙高（上下文切换太多）→ 不能再加

### 6.3 美团团队 4 公式（动态调参用）

业务看到的 P99 延迟 = 队列等待时间 + 任务执行时间。
- 队列等待时间过长 → 加 corePoolSize
- 任务被拒绝多 → 加 max + 队列长度

详见美团技术博客《Java 线程池实现原理及其在美团业务中的实践》。

## 七、生产实战

### 7.1 监控指标

最低要打这些（暴露成 Prometheus 指标）：
| 指标 | 来源 |
| --- | --- |
| 活跃线程数 | `getActiveCount()` |
| 池大小 | `getPoolSize()` |
| 队列大小 | `getQueue().size()` |
| 已完成任务数 | `getCompletedTaskCount()` |
| 累积提交数 | `getTaskCount()` |
| 拒绝次数 | 自定义计数器（在 Handler 里 +1）|

### 7.2 动态调参

JDK 7+ 起，ThreadPoolExecutor 提供 setter：
```java
pool.setCorePoolSize(20);
pool.setMaximumPoolSize(100);
pool.setKeepAliveTime(30, SECONDS);
```

但**队列容量没有 setter**——这是动态调参最尴尬的点。
**美团方案**：自己写 `ResizableCapacityLinkedBlockingQueue`，反射改 capacity 字段。
**Hippo4j / Dynamic-tp**：开源框架，配合 Apollo / Nacos 动态推参数。

### 7.3 Tomcat 线程池的特殊改造

Tomcat 的 `org.apache.tomcat.util.threads.ThreadPoolExecutor` 与 JDK 不同：
- **先创建临时线程，再入队** —— 而不是 JDK 的"先入队再开临时线程"
- 这更符合 Web 场景"突发请求要快"的需求

```java
public void execute(Runnable command, long timeout, TimeUnit unit) {
    int count = submittedCount.incrementAndGet();
    try {
        super.execute(command);
    } catch (RejectedExecutionException rx) {
        // ★ Tomcat 改造：被拒后强行 offer 一次
        if (super.getQueue() instanceof TaskQueue) {
            final TaskQueue queue = (TaskQueue)super.getQueue();
            if (!queue.force(command, timeout, unit)) {
                submittedCount.decrementAndGet();
                throw new RejectedExecutionException("队列+max 全占满");
            }
        }
    }
}
```

`TaskQueue` 重写 `offer`，让"线程数 < max" 时直接返回 false（强制创建新线程），等于"线程优先" 而非"队列优先"。

## 八、生产踩坑

### 8.1 newFixedThreadPool 任务堆积 OOM

经典案例：任务里阻塞调一个慢服务 → 任务来得快、走得慢 → LBQ 无界堆 100w+ 任务 → 老年代满 OOM。
**修复**：换自建有界 ThreadPoolExecutor。

### 8.2 任务里抛异常无人知

```java
pool.submit(() -> {
    int x = 1 / 0;        // 异常被 Future 吞了，不打印
});
```
`submit` 返回的 Future 包装了异常——业务不调 `f.get()` 就看不到。
**修复**：
- `pool.execute(...)` 走 UncaughtExceptionHandler
- `submit(...)` 后必须调 `f.get()`
- 任务内 try-catch 兜底

### 8.3 线程池里 ThreadLocal 泄漏

详见 [ThreadLocal](./ThreadLocal.md#311-引用链)。线程不死，ThreadLocalMap 累积，必须 finally remove。

### 8.4 拒绝策略选错丢任务

- AbortPolicy（默认）：业务没 catch 就崩 → 用户报错
- DiscardPolicy / DiscardOldestPolicy：默默丢失 → **生产禁用**
- **CallerRunsPolicy**：调用线程自己跑 → 天然背压，但要小心调用线程是否能阻塞
- **自定义**：丢 MQ / DB 持久化兜底

### 8.5 corePoolSize 设的太大造成饥饿死锁

任务里又往同一个池子里 submit 子任务，子任务等父任务结果——**自己等自己** → 死锁。
**修复**：父子任务分不同池；或者用 ForkJoinPool 的 Work Stealing。

### 8.6 ScheduledThreadPoolExecutor 任务异常后不再调度

定时任务一旦抛了未捕获异常，**这个任务以后就不再被调度**（直接被 cancel）。
**修复**：定时任务体内必须 try-catch 兜底。

### 8.7 线程池关闭挂起

```java
pool.shutdown();
pool.awaitTermination(...);   // 卡住——某个任务用了 sleep 没处理 InterruptedException
```
**修复**：任务里 catch InterruptedException 后必须 break / interrupt 重打标。

### 8.8 同一个线程池给 IO 密集 + CPU 密集任务用

CPU 密集占 CPU 时，IO 任务也排队等——延迟飙高。
**修复**：分两个线程池。

## 九、面试高频追问

**Q1：execute 和 submit 区别？**
- `execute(Runnable)`：无返回值，异常走 UncaughtExceptionHandler
- `submit(Runnable/Callable)`：返回 Future，异常被 Future 包装，**不调 get 看不到**

**Q2：线程池工作流程，先用核心还是先入队？**
**先开核心**（直到 corePoolSize），核心满才入队，队满才开临时（直到 max），max + 队都满才走拒绝。
注意：**Tomcat 改了顺序**——先开临时再入队。

**Q3：核心线程能销毁吗？**
默认不行。`allowCoreThreadTimeOut(true)` 后核心线程也参与 keepAliveTime 销毁。

**Q4：怎么确定核心线程数？**
- CPU 密集：N+1（N=核数）
- IO 密集：N × (1 + WT/CT)
- 实际靠**压测**，公式只是起点

**Q5：4 种拒绝策略各自适用？**
- AbortPolicy：能 catch 报错的内部业务
- CallerRunsPolicy：希望背压自动调节速度（推荐）
- DiscardPolicy / DiscardOldestPolicy：可以丢的非关键任务（如埋点）
- 自定义：落 MQ / DB 持久化兜底关键任务

**Q6：为什么阿里禁用 Executors？**
- newFixedThreadPool / newSingleThreadExecutor 用无界 LBQ → 任务堆积 OOM
- newCachedThreadPool max=MAX_VALUE → 突发创建几千线程，资源耗尽
**正确姿势**：自己 new，明确所有参数，队列必须有界。

**Q7：如何优雅停机？**
```java
pool.shutdown();
if (!pool.awaitTermination(60, SECONDS)) {
    pool.shutdownNow();
    pool.awaitTermination(30, SECONDS);
}
```
配合任务正确处理 InterruptedException。

**Q8：ctl 字段怎么用一个 int 表示状态 + 线程数？**
高 3 位状态，低 29 位线程数。CAS 一次原子改两个字段——保证状态切换 + 线程数加减的一致性。

**Q9：动态调参怎么做？**
JDK 提供 setCorePoolSize / setMaximumPoolSize 等 setter，但队列容量没 setter。生产用 Hippo4j / Dynamic-tp 配合 Nacos / Apollo 实现。美团方案：自己改 LBQ 的 capacity 字段。

**Q10：JDK 21 虚拟线程下线程池还需要吗？**
虚拟线程"创建几乎免费"——`Executors.newVirtualThreadPerTaskExecutor()`。但**不要用传统线程池跑虚拟线程**——传统线程池的限流逻辑（core/max）反而限制了虚拟线程的扩展性。生产场景：
- IO 密集 → 虚拟线程
- CPU 密集 → 平台线程池

## 十、答题模板（120 秒话术）

> 线程池核心是 7 个参数：`corePoolSize / maximumPoolSize / keepAliveTime+unit / workQueue / threadFactory / handler`。
>
> 工作流程口诀：**核 → 队 → 临 → 拒**。任务先用核心线程；核心满进队；队满开临时（直到 max）；max + 队都满走拒绝策略。注意 Tomcat 改成"核 → 临 → 队 → 拒"，更适合突发流量。
>
> 4 种拒绝策略：AbortPolicy（默认抛异常）、**CallerRunsPolicy（推荐，自动背压）**、DiscardPolicy（静默丢，禁用）、DiscardOldestPolicy。生产关键任务自定义策略落 MQ / DB 兜底。
>
> 5 种状态用 **ctl 一个 int** 表示：高 3 位状态、低 29 位线程数，CAS 一次改两个字段。状态机 RUNNING → SHUTDOWN → TIDYING → TERMINATED；STOP 是 shutdownNow 进入。
>
> **阿里手册禁用 Executors 工厂方法**：FixedThreadPool / SingleThreadExecutor 用**无界 LBQ** 会 OOM；CachedThreadPool max=MAX_VALUE 会创建几千线程。生产必须自建 ThreadPoolExecutor + 有界队列。
>
> 核心线程数：CPU 密集 N+1；IO 密集 N×(1+WT/CT)；实际靠**压测**。
>
> 监控**必须打**：active / pool size / 队列长度 / 已完成 / 拒绝次数。
>
> 经典坑：**LBQ 无界 OOM**、submit 异常被吞、ThreadLocal 在线程池泄漏、CallerRunsPolicy 背压调用方阻塞、ScheduledTPE 任务异常后不再调度。
