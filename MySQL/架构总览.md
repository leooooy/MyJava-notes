# MySQL 架构总览

> MySQL 的"分层架构 + 可插拔存储引擎"是它能横扫互联网二十多年的根本设计。
>
> 面试要拿下三件事：① 四层是什么、各自职责 → ② 为什么要做"Server 层 / 引擎层"分离 → ③ InnoDB 凭什么打败 MyISAM 成为默认。

---

## 一、四层架构

```
 ┌────────────────────────────────────────────────┐
 │  Connector  连接器（接入层）                    │
 │   - TCP 三次握手 / TLS                          │
 │   - 用户鉴权（mysql.user）                       │
 │   - 长连接 / 连接池 / wait_timeout              │
 └────────────────────────────────────────────────┘
                       │
 ┌────────────────────────────────────────────────┐
 │  Server 层（SQL 层，所有引擎共用）              │
 │   ├─ Query Cache（8.0 已删，了解即可）          │
 │   ├─ Parser     词法 + 语法分析 → 解析树         │
 │   ├─ Preprocessor 表名列名校验、权限           │
 │   ├─ Optimizer  生成执行计划（基于代价估算）    │
 │   └─ Executor   调引擎接口、统计 affected_rows  │
 │   ↕                                            │
 │   binlog（Server 层的逻辑日志，所有引擎都生成） │
 └────────────────────────────────────────────────┘
                       │  Handler API
 ┌────────────────────────────────────────────────┐
 │  存储引擎层（可插拔）                           │
 │   InnoDB │ MyISAM │ Memory │ Archive │ ...     │
 │   ├─ 数据 / 索引文件                            │
 │   ├─ Buffer Pool（InnoDB）                      │
 │   ├─ redo log / undo log（仅 InnoDB）           │
 │   └─ 锁、事务、MVCC（仅 InnoDB）                │
 └────────────────────────────────────────────────┘
                       │
 ┌────────────────────────────────────────────────┐
 │  系统文件层（操作系统）                         │
 │   *.frm / *.ibd / ib_logfile / binlog 等        │
 └────────────────────────────────────────────────┘
```

### 1.1 Connector：解决"谁能连上来"

- 维护 TCP 长连接（默认 `wait_timeout = 8h`）
- 验证账号密码 + 主机白名单，加载该用户的权限快照
- **坑点**：账号被改权限后，**已建立的连接不感知**，需要等下次重连。生产改权限后要主动 kill 老连接。

### 1.2 Server 层：解决"SQL 怎么变成执行计划"

四个核心组件按顺序工作：

| 组件 | 输入 | 输出 | 干啥 |
| --- | --- | --- | --- |
| Parser | 文本 SQL | 解析树 AST | 词法 + 语法检查 |
| Preprocessor | AST | 校验后的 AST | 表/列存在性、视图展开、权限校验 |
| Optimizer | AST | 执行计划 | 选索引、定 join 顺序、估代价 |
| Executor | 执行计划 | 结果集 | 调引擎 API 行迭代，做 LIMIT、聚合等 Server 层操作 |

**Optimizer 是高频追问**：它基于**代价估算**（行数 × IO 因子 + CPU 因子），不一定选你以为最优的索引——这就是 `FORCE INDEX` 存在的原因。

> **8.0 删 Query Cache 的原因**：缓存粒度是整个 SQL 文本，**只要表里任何一行改了**，相关 SQL 缓存全失效。OLTP 场景命中率低于 1%，维护成本远大于收益。

### 1.3 存储引擎层：解决"数据怎么存、怎么读"

通过 **Handler API** 与 Server 层解耦，让上层 SQL 处理完全不关心底层是 B+Tree 还是 LSM。Server 层调 `ha_innobase::index_read()` 就能拿一行，不在乎是 InnoDB、MyISAM 还是别的。

```sql
SHOW ENGINES;     -- 看本机支持的引擎
SHOW TABLE STATUS WHERE Name='t';  -- 看某表用了哪个引擎
```

### 1.4 系统文件层：解决"持久化怎么落地"

```
data_dir/
├── mysql/                  系统库
├── ibdata1                 系统表空间（共享）
├── ib_logfile0/1           redo log（环形写）
├── undo_001 ...            undo 表空间（5.7+ 可独立）
├── binlog.000001 ...       Server 层 binlog
└── <db>/
    ├── <table>.frm         5.7 表结构（8.0 已合并到 ibd）
    └── <table>.ibd         InnoDB 表空间（数据 + 索引）
```

## 二、一条 SQL 的全流程示例

以 `SELECT * FROM t WHERE id=10` 为例：

```
客户端
  │ 1. TCP/SSL 连接 + 身份认证
  ↓
Connector 鉴权 → 加载权限
  │ 2. SQL 文本上来
  ↓
Parser 词法/语法分析 → AST
  │ 3. 校验表 t 存在、列 id 存在、SELECT 权限
  ↓
Optimizer 决定走 PRIMARY 索引、估读 1 行
  │ 4. 生成执行计划
  ↓
Executor 调 InnoDB handler→index_read(10)
  │ 5. 进入引擎层
  ↓
InnoDB 在 Buffer Pool 找数据页 → 没有则发起 IO 加载
  │ 6. 走聚簇索引 B+Tree 三层查找到行
  ↓
返回行给 Executor → 网络协议序列化 → 客户端
```

详细流程见 [SQL 执行过程](./sql语句执行过程.md)。

## 三、为什么要"Server 层 / 引擎层"分离？

| 好处 | 案例 |
| --- | --- |
| **可插拔**：换引擎不改 SQL | 同一张表能从 MyISAM `ALTER` 到 InnoDB |
| **专业化**：引擎专注存取性能 | InnoDB 做事务，TokuDB/Fractal 做高写入，HEAP 做内存 |
| **生态扩展**：第三方引擎 | RocksDB（MyRocks）、TiDB 的 TiKV（虽然不是 MySQL，但思想一致） |

代价：

- 部分优化跨不过这层墙——典型的 binlog 与 redo log 的两阶段提交（详见 [日志](./日志.md)）。
- 一些功能割裂：MyISAM 不支持事务，是因为 Server 层不强制要求引擎实现事务，引擎自己选。

## 四、存储引擎对比（高频面试题）

| 维度 | InnoDB | MyISAM | Memory |
| --- | --- | --- | --- |
| 事务 | ✅ ACID | ❌ | ❌ |
| 锁粒度 | 行锁（基于索引） | 表锁 | 表锁 |
| 外键 | ✅ | ❌ | ❌ |
| 崩溃恢复 | ✅（redo log） | ❌（要 REPAIR TABLE） | 进程重启即丢 |
| 索引结构 | 聚簇索引（数据存叶子） | 非聚簇（独立 .MYI） | Hash（默认） |
| 全文索引 | 5.6+ 支持 | 支持 | ❌ |
| 适用场景 | OLTP（默认选它） | 只读统计、日志归档 | 临时表、缓存 |

### 4.1 InnoDB 凭什么是默认？

1. **事务 + 行锁**：高并发 OLTP 必须
2. **崩溃自恢复**：MyISAM 宕机要人工 REPAIR
3. **MVCC**：读不阻塞写，并发吞吐更高
4. **聚簇索引**：主键查询少一次回表
5. **外键**：业务一致性兜底（虽然互联网规范禁用，但底层支持是加分项）

### 4.2 MyISAM 还活着吗？

- 老系统遗留 / 静态数据归档表（年报、日志）会用
- 8.0 后**系统库 `mysql.*` 自身已全部转 InnoDB**——MySQL 团队自己都不用 MyISAM 了

### 4.3 InnoDB 自身关键能力

| 能力 | 由什么实现 | 详见 |
| --- | --- | --- |
| 事务 ACID | undo log + redo log + 锁 + MVCC | [事务的原理](./事务的原理.md) |
| 行锁 | 基于索引项加锁 | [锁机制](./行锁.md) |
| 崩溃恢复 | redo log 重放 + binlog 协调 | [日志](./日志.md) |
| 高并发读 | MVCC 快照读 | [MVCC](./mvcc.md) |
| 高效查询 | B+Tree 聚簇索引 | [索引](./索引.md) |
| 高效写入 | Change Buffer + 顺序 redo | [InnoDB 存储引擎](./InnDB.md) |

## 五、版本演进速记

| 版本 | 关键变化 |
| --- | --- |
| 5.5 | InnoDB 成为**默认**引擎（之前是 MyISAM） |
| 5.6 | 在线 DDL；redo log 大小可调；GTID |
| 5.7 | JSON 类型；并行复制；innodb_buffer_pool 在线 resize |
| 8.0 | **数据字典转 InnoDB**（.frm 没了）；窗口函数；CTE；隐藏索引；移除 Query Cache；redo log 改无锁链表；ATOMIC DDL |

> 面试遇到"用过哪个版本"，**5.7 / 8.0 是主流**；如果还说 5.5 / 5.6，会被怀疑技术栈太旧。

```
单机                          → 开发/测试
主从（一主一从）              → 中小业务，读写分离
一主多从                      → 读多写少（电商、社区）

```

## 七、连接管理生产坑

### 7.1 连接数被打爆

```sql
SHOW VARIABLES LIKE 'max_connections';   -- 默认 151，远远不够
SHOW STATUS LIKE 'Threads_connected';    -- 当前连接数
SHOW STATUS LIKE 'Threads_running';      -- 当前真正干活的
```

线上典型告警：`Too many connections`。

**根因排查**：
- 应用连接池配置过大 × 实例数 > max_connections
- 应用没正确归还连接（连接泄漏）
- 慢查询堆积，连接被占住

**应急**：调大 `max_connections` 是治标，排查连接池和慢 SQL 才是治本。

### 7.2 长连接与内存膨胀

MySQL 单连接在执行过程中**临时使用的内存**绑在连接对象上，长连接执行复杂查询后，内存不会立即释放——**长连接累积导致 OOM**。

**对策**：
- `mysql_reset_connection()` 定期重置（5.7+）
- 应用连接池配置 `maxLifetime`（HikariCP 默认 30 分钟）

### 7.3 wait_timeout 与连接被切

中间件（如 LB、防火墙）静默 TCP 超时（典型 5 分钟）后切连接 → 应用拿到的旧连接 send 时报 `Communication link failure`。

**对策**：
- HikariCP `keepaliveTime` < LB 静默超时
- 或在连接池启用 `testOnBorrow=true`（性能差，慎用）

## 八、面试高频追问

### Q1：MySQL 一条 SQL 经过哪些步骤？

Connector → Parser → Preprocessor → Optimizer → Executor → Storage Engine → 系统文件。

### Q2：8.0 为什么删 Query Cache？

OLTP 写多场景下，缓存粒度是整 SQL，**任何写都让相关缓存失效**。命中率 <1%，维护开销不值。

### Q3：Optimizer 选错索引怎么办？

四招：
1. `ANALYZE TABLE` 让统计信息更准
2. `FORCE INDEX(idx_xx)` 强制
3. 改写 SQL 让优化器更容易选对（去掉无谓的函数、范围）
4. 删除干扰索引（互联网严格控制单表索引数 ≤5）

### Q4：MyISAM 和 InnoDB 怎么选？

互联网业务**一律选 InnoDB**——事务、行锁、崩溃恢复缺一不可。MyISAM 只在静态归档表才考虑（且 8.0 系统库已全部转 InnoDB，趋势是"忘掉 MyISAM"）。

### Q5：count(*) 在 MyISAM 和 InnoDB 上有区别吗？

- MyISAM：表级维护一个行数，`SELECT count(*)` 是 **O(1)**
- InnoDB：因为有事务+MVCC，每个事务可见的行数不同，**必须扫表**，`count(*)` 是 **O(N)**

但 InnoDB 上 `count(*)` 优化器会选最小的辅助索引扫——比 `count(主键)` 还快一点（避免读聚簇索引大叶子节点）。

### Q6：连接数打爆怎么救？

短期：调 `max_connections`；
中期：连接池调小 + `maxLifetime`；
根本：排查慢 SQL 和连接泄漏。

### Q7：为什么 MySQL 要做 Server / 引擎分离？

可插拔（业务可换引擎）+ 专业化（引擎专攻存取）+ 生态扩展（第三方引擎），代价是部分优化（如 redo + binlog 一致性）需两阶段提交协调。

## 九、答题模板（30 秒话术）

> MySQL 是**分层架构**：连接器（鉴权 + 长连接管理）→ Server 层（解析、优化、执行，所有引擎共用）→ 存储引擎（InnoDB/MyISAM/...，可插拔）→ 系统文件。
>
> Server 和引擎之间通过 Handler API 解耦，所以同一张表能换引擎、第三方引擎能接进来。
>
> InnoDB 是默认引擎，因为它支持**事务、行锁、崩溃恢复、MVCC、聚簇索引**——OLTP 高并发刚需。MyISAM 没事务、表锁、宕机要人工修，已经是淘汰品。
>
> 8.0 删除了 Query Cache（写多场景命中率低）；系统库也全转 InnoDB——MySQL 团队自己都不用 MyISAM 了。
