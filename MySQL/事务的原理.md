# 事务 ACID 与实现原理

> 事务是 MySQL 的灵魂——也是面试官最喜欢"层层往下问"的话题：从 ACID 概念 → 怎么实现 → 三大日志各负责什么 → 长事务危害。
>
> 本篇按"概念 → 映射 → 实现"组织：① ACID 是什么 → ② 各特性具体由什么机制保证 → ③ 三大日志（redo / undo / binlog）的职责分工。
>
> 注意：MySQL 事务**仅在 InnoDB 引擎下生效**。MyISAM 不支持事务。

---

## 一、ACID

### 1.1 四大特性

| 特性 | 含义 | 由什么实现 |
| --- | --- | --- |
| **A** Atomicity 原子性 | 一组操作要么全成功，要么全失败 | **undo log** |
| **C** Consistency 一致性 | 事务前后数据库整体处于一致状态 | A + I + D **共同保证** + 业务约束 |
| **I** Isolation 隔离性 | 并发事务之间互不干扰 | **锁 + MVCC** |
| **D** Durability 持久性 | 事务提交后修改不会丢 | **redo log** |

> **常见误区**：把"一致性"理解为某个机制实现的——实际上它是**业务正确性的总目标**，由其它三个特性 + 业务自己的约束（外键、CHECK、唯一索引、转账时金额相等）共同保证。

### 1.2 经典例子（转账）

```
A 转账 100 给 B
   1. UPDATE A SET balance = balance - 100;
   2. UPDATE B SET balance = balance + 100;
```

- **原子性**：两步必须同生同死。第 2 步失败要回滚第 1 步。
- **一致性**：转账前后 A+B 总和不变（业务约束）。
- **隔离性**：另一并发事务不能看到"A 已扣 100 但 B 未加"的中间状态。
- **持久性**：commit 后即使断电也不丢。

## 二、原子性（Atomicity）→ undo log

### 2.1 怎么回滚？

**思路**：每修改一条记录前，把"如何撤销该修改"的逻辑写进 undo log，回滚时反向应用。

| 操作 | undo log 记录 | 回滚时执行 |
| --- | --- | --- |
| INSERT (id=1) | 一条 DELETE id=1 的撤销 | DELETE id=1 |
| DELETE id=1（旧值 v1） | 完整旧行 v1 | INSERT v1 |
| UPDATE id=1 v1→v2 | 旧值 v1 | UPDATE id=1 v2→v1 |

> undo log 是**逻辑日志**——记录的是反向操作，不是物理页修改。

### 2.2 ROLLBACK 流程

```
ROLLBACK
  │
  ├─ 1. 找到本事务的 undo log 链（按事务 ID 串起）
  │
  ├─ 2. 倒序应用每条 undo
  │     INSERT → DELETE
  │     UPDATE → 反向 UPDATE
  │     DELETE → INSERT
  │
  └─ 3. 释放锁
```

### 2.3 提交也要写 undo

> 注意：不只是回滚要 undo，**MVCC 也用 undo**——快照读会沿 roll_pointer 找历史版本。所以即使事务正常 COMMIT，update undo 也不能立刻删，要等没有任何 ReadView 还可能用到时由 Purge 线程异步清。详见 [MVCC](./mvcc.md)。

## 三、持久性（Durability）→ redo log

### 3.1 为什么需要 redo log？

**矛盾**：
- 修改数据 → 改 Buffer Pool 中的内存页（脏页）。如果直接刷盘，每个事务都触发**随机 IO** → 性能崩溃。
- 不刷盘？断电时所有未刷的脏页就丢了 → 违反持久性。

**解法（WAL，Write-Ahead Logging）**：

```
事务提交时：
  ✅ redo log 必须落盘（顺序 IO，快）
  ❌ 数据页脏页不必立即落盘（异步刷）
  
崩溃恢复：
  从最后一次 checkpoint 起，重放 redo log → 恢复未刷盘的脏页修改
```

### 3.2 redo log 是物理日志

记录"在表空间 X 的页 Y 偏移 Z 写入字节 ABC"——**对页的物理修改**，不是 SQL。

```
[表空间号][页号][偏移量][修改长度][修改内容]
```

### 3.3 环形写

redo log 由两个文件循环写（默认 `ib_logfile0` 和 `ib_logfile1`）：

```
[文件 0: 1G] [文件 1: 1G]   ← 5.6+ 默认；8.0 单文件可调更大
   ↑              ↑
   write          checkpoint
```

- `write_pos`：当前写位置
- `checkpoint`：脏页已经刷盘到磁盘的位置——这部分 redo 不再需要

当 `write_pos` 追上 `checkpoint` → **redo 满**，必须停下来等 Page Cleaner 推进 checkpoint → 业务暂停。

### 3.4 刷盘控制

```sql
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
```

| 取值 | 行为 | 风险 |
| --- | --- | --- |
| **0** | 每秒一次刷盘（不在事务提交时） | MySQL 崩溃丢 1 秒事务 |
| **1**（默认） | 每次提交都 fsync | **最安全**，IO 重 |
| **2** | 每次提交写到 OS page cache，每秒 fsync | OS 崩溃丢 1 秒 |

> 金融场景设 1。互联网允许少量丢失常用 2 + sync_binlog=1000。

### 3.5 LSN（Log Sequence Number）

整个 redo 流是一条单调递增的字节流，每个位置叫 LSN。

| 概念 | 含义 |
| --- | --- |
| `log sequence number` | 当前最新 LSN |
| `log flushed up to` | 已 fsync 的 LSN |
| `pages flushed up to` | 已刷盘到数据文件的脏页对应 LSN |
| `last checkpoint at` | checkpoint 推进到的 LSN |

```sql
SHOW ENGINE INNODB STATUS\G
-- LOG 段会列出这些值
```

## 四、隔离性（Isolation）→ 锁 + MVCC

### 4.1 两条路径

| 解法 | 适用 |
| --- | --- |
| **锁**（悲观） | 写操作、当前读（FOR UPDATE） |
| **MVCC**（乐观） | 快照读（普通 SELECT） |

> 详见 [事务的隔离级别](./事务的隔离级别.md) 和 [MVCC](./mvcc.md)。

### 4.2 不同隔离级别的实现

| 级别 | 脏读 | 不可重复读 | 幻读 | 实现 |
| --- | --- | --- | --- | --- |
| READ UNCOMMITTED | 有 | 有 | 有 | 不做特殊保护 |
| READ COMMITTED | 无 | 有 | 有 | **每次 SELECT 新 ReadView** |
| **REPEATABLE READ**（默认） | 无 | 无 | 无（部分） | **首次 SELECT 建 ReadView 复用 + 间隙锁** |
| SERIALIZABLE | 无 | 无 | 无 | 所有 SELECT 加共享锁 |

> RR 是 MySQL 默认级别，与 SQL 标准不同（标准默认 RC）。原因是 MySQL 早期主从复制基于 STATEMENT 格式 binlog，需要 RR 保证主从一致——8.0 后已不强制，但默认仍是 RR。

## 五、一致性（Consistency）→ 综合保证

### 5.1 数据库层面的一致性

由前三个特性兜底：
- A 保证不会有"半成品"
- I 保证并发不会写飞
- D 保证不会断电丢

### 5.2 业务层面的一致性

由**业务约束 + 应用代码**保证：
- 主键、外键、唯一索引、CHECK
- 转账时业务代码确保 `from + to` 总额不变
- 库存扣减时业务确保不超扣

> 数据库只能保证"操作执行成功了"，不能替你保证"业务是对的"。

## 六、三大日志对比（高频考点）

| 维度 | undo log | redo log | binlog |
| --- | --- | --- | --- |
| **层** | InnoDB 引擎 | InnoDB 引擎 | Server 层 |
| **类型** | 逻辑日志（反向操作） | 物理日志（页字节修改） | 逻辑日志（行变更或 SQL） |
| **作用** | 回滚 + MVCC | 崩溃恢复 | 主从复制 + 时间点恢复 |
| **写时机** | 事务进行中 | 事务进行中（顺序追加） | 事务提交时（一次性） |
| **存储** | undo 表空间 / 系统表空间 | ib_logfile0/1 环形 | binlog.NNNNNN |
| **删除** | Purge 线程异步清 | 环形覆盖（checkpoint 后） | 按 expire_logs_days |
| **格式** | INSERT/UPDATE/DELETE 撤销 | 物理操作 | ROW / STATEMENT / MIXED |

### 6.1 redo vs binlog 区别（最高频）

```
redo log (InnoDB)               binlog (Server)
┌────────────────┐              ┌────────────────┐
│ 物理日志        │              │ 逻辑日志        │
│ 页 Y 偏移 Z 改 W │              │ UPDATE x SET..  │
│                │              │                │
│ 环形覆盖        │              │ 追加新文件      │
│ ib_logfile0/1   │              │ binlog.000001..│
│                │              │                │
│ 崩溃恢复        │              │ 主从复制        │
│ 仅 InnoDB       │              │ 所有引擎        │
└────────────────┘              └────────────────┘
       ↑                              ↑
       └─── 两阶段提交协调一致 ────────┘
```

### 6.2 两阶段提交流程

```
事务 commit
  │
  ├─ Phase 1: redo 写入 + 状态置 PREPARE
  │
  ├─ Phase 2: binlog 写入磁盘
  │
  └─ Phase 3: redo 状态置 COMMIT
```

详见 [SQL 执行过程 - 两阶段提交](./sql语句执行过程.md#三两阶段提交-xa--2pc)。

## 七、生产踩坑

### 7.1 大事务

```sql
BEGIN;
UPDATE order SET status=1 WHERE create_time < '2024-01-01';  -- 涉及 1000 万行
COMMIT;
```

**多重打击**：
- undo log 巨大 → 占用磁盘
- 锁持有时间长 → 业务大面积阻塞
- binlog 单事件巨大 → 主从延迟数小时
- 一旦失败回滚耗时数小时（rollback 比 commit 还慢）

**解法**：拆 BATCH，每批 1000~5000 行：

```sql
WHILE EXISTS (SELECT 1 FROM order WHERE status=0 AND create_time < '2024-01-01' LIMIT 1) DO
  UPDATE order SET status=1 WHERE status=0 AND create_time < '2024-01-01' LIMIT 5000;
END WHILE;
```

### 7.2 长事务

```
BEGIN;
SELECT * FROM huge_table;  -- 跑了 1 小时
-- 还没 COMMIT
```

**危害**：
- undo 不能 Purge → 历史版本堆积，磁盘膨胀
- 全局事务等待者越来越多 → 死锁概率激增
- 主从延迟（旧版本一直保留）

**监控**：
```sql
SELECT * FROM information_schema.innodb_trx
WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 60
ORDER BY trx_started;
```

> 业务规范：单事务执行时间 ≤ 1 秒，强烈建议在应用层用 `@Transactional` 框定边界。

### 7.3 错把"读操作"放进事务

```java
@Transactional
public Order getOrder(Long id) {
    return orderMapper.selectById(id);  // 纯读，不必事务
}
```

→ 仍开了事务 + 持有连接 + 占 ReadView。线上接口慢一半都因为 Spring 事务边界乱用。

**规范**：
- 只读方法用 `@Transactional(readOnly=true)` 或干脆不加
- 复杂场景应用层主动 `@Transactional(propagation=REQUIRES_NEW)`

### 7.4 commit 后还以为可以 ROLLBACK

```sql
BEGIN;
UPDATE ...;
COMMIT;   -- 已落盘
ROLLBACK; -- 没用，commit 后回滚是 no-op
```

commit 是不可逆的——出错只能业务层做反向操作（补偿事务）。

## 八、面试高频追问

### Q1：ACID 各由什么实现？

- A：undo log（回滚机制）
- C：A + I + D + 业务约束共同保证（不是单一机制）
- I：锁 + MVCC
- D：redo log（WAL）

### Q2：为什么 redo log 要做成"环形写"？

固定大小、循环利用——避免日志文件无限增长。代价是：写满前必须把对应脏页刷下去（推进 checkpoint）。

### Q3：redo log 和 binlog 区别？

- **层次**：redo InnoDB 引擎层；binlog Server 层
- **类型**：redo 物理日志（页修改）；binlog 逻辑日志（行/SQL）
- **作用**：redo 崩溃恢复；binlog 主从复制 + PITR
- **写法**：redo 环形覆盖；binlog 追加新文件
- **协调**：两阶段提交保证一致

### Q4：为什么 InnoDB 默认隔离级别是 RR 而不是 RC？

历史原因：早期主从复制 binlog 用 STATEMENT 格式，RC 下可能主从执行顺序不同导致数据不一致；RR 加间隙锁保证一致。8.0 后已不强制，但默认仍 RR。

### Q5：长事务有什么危害？

- undo 堆积（Purge 卡住）
- 锁持有时间长，影响并发
- 主从延迟严重
- 死锁概率上升

### Q6：commit 之后突然断电，事务保留吗？

取决于 commit 时 redo 是否已 fsync：
- `flush_log=1`：已 fsync，保留
- `flush_log=2`：仅在 page cache，OS 崩溃可能丢
- `flush_log=0`：每秒一次 fsync，可能丢 1 秒

### Q7：undo log 什么时候删？

- INSERT undo：事务提交后立即可清
- UPDATE/DELETE undo：要等所有 ReadView 都不再可能用到，由 Purge 线程异步清

长事务会卡住 Purge → undo 膨胀。

### Q8：MyISAM 为什么不支持事务？

存储引擎层不实现：没有 redo log（无持久性保证）、没有 undo log（无回滚）、只有表锁（隔离粒度太粗）。这是设计取舍——MyISAM 追求纯读性能，放弃事务能力。

## 九、答题模板（60 秒话术）

> 事务的 ACID 四特性，**A 由 undo log 实现回滚，D 由 redo log 实现 WAL 保证不丢，I 由锁和 MVCC 实现并发隔离，C 是综合目标——靠 A、I、D 加业务约束共同保证**。
>
> InnoDB 用三大日志：
>
> - **undo**（逻辑日志）：记反向操作，用于 ROLLBACK 和 MVCC 的版本链；事务结束后由 Purge 线程异步清。
> - **redo**（物理日志）：记页修改，环形写，提供崩溃恢复；事务提交时按 `innodb_flush_log_at_trx_commit` 决定刷盘策略。
> - **binlog**（逻辑日志，Server 层）：记行变更或 SQL，提供主从复制和时间点恢复；和 redo 用**两阶段提交**保证一致性。
>
> 默认隔离级别 RR，比 SQL 标准 RC 高一级——历史上是为了主从一致，现在主要靠 RR 的间隙锁解决幻读。
>
> 生产最大坑是大事务和长事务：拆 BATCH、控制单事务时长 ≤ 1s、监控 `information_schema.innodb_trx`。
