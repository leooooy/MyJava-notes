# 主从复制

> 主从复制是 MySQL 高可用、读扩展、容灾的基石。也是面试**高频痛点**——能讲清"binlog 怎么变成从库数据"、"主从延迟根因"、"半同步 vs 异步"，立刻区分初级和高级。
>
> 本篇按"流程 → 模式 → 延迟治理 → 高可用方案"组织：① 主从复制流程（三个线程）→ ② 异步/半同步/全同步对比 → ③ 主从延迟的根因和解法 → ④ MGR 等现代方案。

---

## 一、为什么需要主从复制

| 场景 | 单库的问题 | 主从的解 |
| --- | --- | --- |
| **高可用** | 主库挂 = 服务挂 | 从库可切换为主 |
| **读扩展** | 单库读写在一起，CPU/IOPS 上限 | 写主库、读从库，读容量水平扩展 |
| **数据备份** | 主库直接备份要锁表 | 从库做备份不影响主 |
| **数据迁移** | 业务停机迁移 | 搭从库 → 切主 → 滚动升级 |
| **跨地域容灾** | 单机房风险 | 异地搭从库 |

## 二、复制原理：三个线程

```
   主库                              从库
┌──────────┐                     ┌──────────┐
│ 业务写入  │                     │          │
│   ↓       │                     │          │
│ binlog   │                     │  Relay   │
│           │← dump thread →     │  log     │
│           │                     │   ↑      │
│           │                     │  IO      │
│           │                     │  thread  │
│           │                     │          │
│           │                     │   ↓      │
│           │                     │  SQL     │
│           │                     │  thread  │
│           │                     │   ↓      │
│           │                     │  数据    │
└──────────┘                     └──────────┘
```

### 2.1 主库：dump thread

每个从库连过来时，主库为它启一个 **dump thread**，从指定的 binlog 位置开始**推送**。

> **是推不是拉**——从库注册后，主库主动 push；增量低延迟的关键。

### 2.2 从库：IO thread

接收主库 dump thread 推来的 binlog，**写入本地 relay log**——只搬运、不应用。

### 2.3 从库：SQL thread

读 relay log，**回放**到本地数据。5.7+ 默认多线程，按事务并行。

### 2.4 流程

```
1. 主库写业务 → 自己的 binlog
2. dump thread 把 binlog 推给从库 IO thread
3. IO thread 写本地 relay log
4. SQL thread 读 relay log → 应用到从库表
5. 从库回 ACK 给主库（半同步模式下）
```

### 2.5 监控

```sql
-- 主库
SHOW MASTER STATUS;          -- 当前 binlog 文件 + position
SHOW PROCESSLIST;            -- 找 Binlog Dump 线程

-- 从库
SHOW SLAVE STATUS\G          -- 关键命令
-- 或 8.0+：SHOW REPLICA STATUS
```

`SHOW SLAVE STATUS` 关键字段：

| 字段 | 含义 |
| --- | --- |
| `Slave_IO_Running` | IO thread 状态，应是 Yes |
| `Slave_SQL_Running` | SQL thread 状态，应是 Yes |
| `Master_Log_File` / `Read_Master_Log_Pos` | IO thread 读到主库 binlog 哪儿 |
| `Relay_Log_File` / `Relay_Log_Pos` | SQL thread 应用到 relay log 哪儿 |
| `Exec_Master_Log_Pos` | 转换成 "应用到主库 binlog 哪个位置" |
| **`Seconds_Behind_Master`** | **主从延迟秒数**（核心指标） |
| `Last_Errno` / `Last_Error` | SQL 线程报错 |

## 三、复制模式

### 3.1 异步复制（默认）

```
主库 commit → 立即返回
后台 dump 推 binlog（异步）
```

| 优点 | 缺点 |
| --- | --- |
| 主库性能不受从库影响 | 主库挂时**未传到从库**的事务**丢失** |
| 实现简单 | 主从可能不一致 |

### 3.2 半同步复制（rpl_semi_sync）

```
主库 commit
  ↓
等至少一个从库的 IO thread 收到并写入 relay log，回 ACK
  ↓
主库才返回客户端成功
```

| 优点 | 缺点 |
| --- | --- |
| 主库挂时数据**已到至少一个从库**，不丢 | 主库延迟 +1~2ms（一次网络 RTT） |
| 仍是大部分异步性能 | 从库全部不可用时退化为异步 |

```ini
plugin_load = "rpl_semi_sync_master=semisync_master.so;rpl_semi_sync_slave=semisync_slave.so"
rpl_semi_sync_master_enabled = 1
rpl_semi_sync_master_timeout = 1000   # 等 ACK 超时 1s，超时退化异步
rpl_semi_sync_slave_enabled = 1
```

> **生产建议**：**异步 + 半同步组合**。互联网默认开半同步（RTT 在同机房可忽略），金融场景再上 MGR 多副本。

### 3.3 全同步复制

```
主库 commit
  ↓
等所有从库的 SQL thread 也回放完毕
  ↓
主库才返回成功
```

→ 只在理论模型，实际产品不用——延迟太高。MGR 是它的工程化变种。

### 3.4 三种对比

| 模式 | 主库延迟 | 数据丢失风险 | 主库性能 |
| --- | --- | --- | --- |
| 异步 | 0 | 主挂可能丢未传 | 高 |
| 半同步 | +1~2ms | 主挂数据已到至少一从 | 较高 |
| MGR | +5~10ms | 多数派写入即提交 | 中 |
| 全同步 | +N×回放时间 | 不丢 | 低 |

## 四、binlog 格式与复制

### 4.1 三种 binlog 格式

| 格式 | 复制特点 |
| --- | --- |
| **STATEMENT** | 主从执行同一 SQL；遇 NOW()、UUID()、自增等会主从不一致 |
| **ROW**（5.7+ 默认） | 行变更前后镜像，**主从绝对一致**——生产推荐 |
| **MIXED** | 默认 STATEMENT，遇不确定切 ROW |

### 4.2 ROW 格式的代价

```sql
-- 主库
UPDATE order SET status=1 WHERE create_time<'2024-01-01';   -- 影响 100 万行

-- binlog 记录 100 万条 UPDATE 行变更 → 数 GB
-- 从库 SQL thread 一条条回放 → 延迟数小时
```

**对策**：
- 业务侧拆 BATCH（每次 5000 行）
- 5.7+ 启用并行复制：`slave_parallel_type=LOGICAL_CLOCK`、`slave_parallel_workers=8`

## 五、主从延迟（Replication Lag）

> **生产最高频问题**。延迟 → 读从库读到旧数据 → 业务异常。

### 5.1 延迟根因

```
主库     从库 IO     从库 SQL     从库本地
 ↓        ↓          ↓           ↓
 |--- 网络 ---|       |          |
              |       |          |
              |--- IO 写 relay -|
                     |
                     |--- SQL 回放（最易卡） --|
```

| 阶段 | 卡住的原因 |
| --- | --- |
| 网络 | 跨机房高延迟、带宽不够 |
| IO thread | 几乎不卡（顺序写） |
| **SQL thread** | **最常见**——单线程回放、大事务、慢 SQL、锁等待 |

### 5.2 看 Seconds_Behind_Master 不准

它本质是"SQL thread 当前应用的事件时间 vs 主库 NOW()"。当：
- IO thread 卡住（事件还没收到）→ Seconds 是 0（误以为没延迟）
- 主从时钟不同步 → 数值偏差

**更准的判断**：自己写心跳表，主库定时 INSERT 时间戳，从库读看差。

### 5.3 解决方案

#### 5.3.1 减少大事务

主库一条 UPDATE 影响百万行 → ROW binlog 百万条 → 从库回放数小时。

**对策**：业务侧拆 BATCH。

#### 5.3.2 并行复制（5.7+）

```ini
slave_parallel_type      = LOGICAL_CLOCK   # 或 DATABASE
slave_parallel_workers   = 8                # 并行线程数
slave_preserve_commit_order = 1             # 严格按主库提交顺序
```

**LOGICAL_CLOCK** 模式：主库 binlog 中标记同时提交的事务为同组，从库可并行回放——延迟治理大杀器。

#### 5.3.3 主库压力削峰

主库 QPS 突增 → binlog 飞快 → 从库追不上。
**对策**：主库限流 / 削峰 / 增加从库副本（不解决延迟，但分担读）。

#### 5.3.4 从库硬件升级

从库 IO/CPU 弱于主库 → 回放跟不上。  
**对策**：主从同配置或从库更强（实际生产从库常被忽视）。

#### 5.3.5 业务侧应对

接受**最终一致**：
- 写入后立即读：强制走主库（`@MasterReadAfterWrite`）
- 异步显示：写入后 Toast 提示成功，刷新时再展示
- 关键校验：写完后查主库再做后续

## 六、复制位点与 GTID

### 6.1 传统位点（File + Position）

```sql
CHANGE MASTER TO
  MASTER_HOST = '...',
  MASTER_LOG_FILE = 'binlog.000010',
  MASTER_LOG_POS = 12345;
```

**痛点**：主库切换时，新主的 binlog 文件名 / 位置和老主不同——从库不知道从哪儿继续。

### 6.2 GTID（Global Transaction ID）

5.6+ 引入。每个事务有全局唯一 ID：

```
server_uuid:transaction_id
e.g. 3E11FA47-71CA-11E1-9E33-C80AA9429562:23
```

主从切换时，新主只需告诉从库"你已应用到 X-uuid:N 了，从下个开始给我"——**自动定位**。

```ini
gtid_mode                = ON
enforce_gtid_consistency = ON
log_bin                  = ON
log_slave_updates        = ON      # 从库也写 binlog（链式复制需要）
```

```sql
CHANGE MASTER TO
  MASTER_HOST = '...',
  MASTER_AUTO_POSITION = 1;
```

> **生产强烈建议开 GTID**——主从切换、半同步、MGR 都依赖它。

## 七、读写分离

### 7.1 实现位置

| 层 | 例子 |
| --- | --- |
| 应用代码 | `@DS("master")` / `@DS("slave")` 注解 |
| ORM 框架 | MyBatis-Plus 多数据源 |
| 中间件 | ShardingSphere、MyCat |
| 代理层 | ProxySQL、MaxScale |

### 7.2 应用层做读写分离的痛点

#### 7.2.1 写后立即读

```java
update();    // 写主库
select();    // 读从库 → 主从延迟可能读到旧值
```

**对策**：
- 业务可容忍：接受最终一致
- 不能容忍：强制走主库（`/* MASTER */` 注释提示中间件，或 `@MasterReadAfterWrite`）

#### 7.2.2 事务内读

事务中包含读和写——必须都走主库（同一连接保证 MVCC 一致），否则 ReadView 失效。

#### 7.2.3 多从库负载均衡

随机 / 轮询 / 加权——大部分中间件支持。需要监控某从库延迟过大时**自动剔除**。

## 八、高可用方案

### 8.1 MHA（Master High Availability）

老牌方案。架构：1 个 Manager + N 个 Node。主库挂时 Manager 选最新从库为新主，自动切换 + 配置 binlog 同步。

**问题**：依赖 SSH、Manager 单点、5.7 后逐渐被替代。

### 8.2 MGR（MySQL Group Replication）

5.7+ 官方原生方案。基于 Paxos 变种，多数派写入。

**特性**：
- 多副本（3/5/7 节点）
- 自动选主、自动剔除故障节点
- 强一致（多数派同步）
- 支持单主 / 多主模式

**生产建议**：单主模式 + 半同步 + 多副本。多主模式有写冲突风险，慎用。

### 8.3 MySQL 8.0 Cluster Set

8.0.27+ 官方方案。MGR 的扩展——多个 MGR 集群组成"Cluster Set"，跨地域容灾。

### 8.4 各方案对比

| 方案 | 一致性 | 自动切换 | 复杂度 |
| --- | --- | --- | --- |
| 异步主从 | 弱（可能丢） | 否（人工） | 低 |
| 半同步主从 | 中（数据已到从） | 否 | 低 |
| MHA | 中 | 是 | 中 |
| **MGR** | **强**（多数派） | **是** | **中** |
| Galera Cluster（外部） | 强 | 是 | 高 |

## 九、生产踩坑

### 9.1 主从延迟读到旧数据

**症状**：用户下单成功后立刻刷新，订单不显示。  
**根因**：写主库、读从库，主从延迟 1 秒。  
**对策**：
- 写主接口返回时附带数据 → 前端直接展示
- 写后强制走主库读
- 中间件支持"读自己的写"

### 9.2 ROW binlog 巨大事务卡死从库

主库 `DELETE FROM huge_table WHERE create_time<X` 影响 1 亿行。  
binlog 几十 GB，从库回放数天，期间所有读受影响。

**对策**：永远拆 BATCH。

### 9.3 半同步退化为异步未感知

```ini
rpl_semi_sync_master_timeout = 1000   # 等不到 ACK 1 秒退化为异步
```

如果从库网络抖动 → 经常退化 → 主库挂时丢数据风险增加。

**监控**：`Rpl_semi_sync_master_status` 应该长期为 ON。

### 9.4 从库 SQL thread 报错卡住

从库执行某条 binlog 出错（外键违反、唯一键冲突）→ SQL thread 停止 → 延迟无限增长。

**症状**：`Slave_SQL_Running: No`、`Last_Error` 有内容。

**修复**：
```sql
STOP SLAVE;
SET GLOBAL sql_slave_skip_counter = 1;   -- 跳过这一条
START SLAVE;
```

但这会**导致主从数据不一致**——只是临时救命。根因要修。

### 9.5 多线程回放但 commit 顺序乱

并行复制下若 `slave_preserve_commit_order=0`，从库提交顺序可能与主库不同——业务侧靠主键时间戳判断"先后"会出错。

**对策**：永远开 `slave_preserve_commit_order=1`。

## 十、面试高频追问

### Q1：主从复制流程？

主库 dump thread 推 binlog → 从库 IO thread 写 relay log → 从库 SQL thread 回放。

### Q2：同步、半同步、异步区别？

异步主库不等从库，最快但可能丢；半同步等至少一个从库收到 binlog；同步等所有从库回放完成（实际不用）。

### Q3：主从延迟根因？怎么治理？

最常见是从库 SQL thread 单线程回放慢。治理：
- 主库拆 BATCH 减小事务
- 5.7+ 并行复制
- 监控 `Seconds_Behind_Master`，业务侧"读自己的写"走主库

### Q4：binlog 三种格式怎么选？

ROW（5.7+ 默认）。STATEMENT 主从可能不一致。MIXED 太复杂。

### Q5：什么是 GTID？

全局事务 ID，每个事务有 server_uuid:trx_id 形式的标识。主从切换时不依赖 binlog 文件名/位置，自动续接。

### Q6：怎么保证不丢数据？

- 主库：`flush_log_at_trx_commit=1` + `sync_binlog=1`
- 复制：开半同步（rpl_semi_sync）
- 终极：MGR 多副本

### Q7：写主库读从库读到旧数据怎么办？

- 业务容忍最终一致 → 接受
- 不容忍：写后强制读主、用心跳表确保主从已同步、用版本号字段判断
- 中间件层支持"读自己的写"

### Q8：从库 SQL thread 挂了怎么处理？

`SHOW SLAVE STATUS\G` 看 Last_Error；修复后续行：临时 skip_counter（不一致风险）；或重建从库（最干净）。

### Q9：MGR 和传统主从区别？

MGR 多副本 Paxos 共识，多数派提交即成功，有写冲突自动检测；传统主从是单主链式，依赖应用层切换。

### Q10：从库的 binlog 要不要开？

**链式复制**（M → S1 → S2）下 S1 必须开（`log_slave_updates`）。普通主从可关。但开 binlog 才能 GTID 完整工作，建议**总是开**。

## 十一、答题模板（60 秒话术）

> 主从复制核心是**三个线程**：主库 dump 推 binlog → 从库 IO 写 relay log → 从库 SQL 回放。
>
> 复制模式有：
> - **异步**（默认）：最快，主挂可能丢未传
> - **半同步**：等至少一个从收到 binlog，互联网生产标配
> - **MGR**：多副本 Paxos，金融级强一致
>
> 互联网必开 **GTID**——主从切换时新主告诉从库"你已应用到 X-uuid:N，下一个开始"，无需依赖 binlog 文件名/位置。
>
> binlog **ROW 格式**（5.7+ 默认）保证主从绝对一致，但代价是单条大事务变成百万条 binlog 事件 → 从库回放慢。
>
> **主从延迟**根因 90% 是从库 SQL 线程慢——治理靠拆 BATCH、5.7+ 并行复制（LOGICAL_CLOCK + 8 worker + preserve_commit_order=1）、监控 `Seconds_Behind_Master` 但要知道它不绝对准。
>
> 业务侧读写分离的"写后立即读"问题，常用方案是关键场景强制走主库或写完返回数据让前端直接展示。
