# 数据库设计与范式

> 看似基础的题，但 senior 面试问起来容易翻车——很多人能背三范式定义，问到"第二范式和第三范式区别是什么、订单表为什么经常违反 3NF"就答不上。
>
> 互联网现实是**适度反范式**——为了性能牺牲严格范式，关键是讲清"什么时候反、反到什么程度、代价是什么"。
>
> 本篇按"范式定义 → 反范式取舍 → 实战建模 → 演化"组织。

---

## 一、为什么要讲范式

> **范式（Normal Form）的本质：通过分解表，消除数据冗余、更新异常、插入异常、删除异常。**

### 1.1 不规范设计带来的问题

一张未规范化的"订单+商品+用户"宽表：

| order_id | user_name | user_phone | product_name | product_price | quantity |
| --- | --- | --- | --- | --- | --- |
| 1 | 张三 | 138... | iPhone | 6000 | 1 |
| 2 | 张三 | 138... | iPad | 4000 | 1 |
| 3 | 李四 | 139... | iPhone | 6000 | 2 |

**四种异常**：

| 异常 | 表现 |
| --- | --- |
| **冗余** | 张三的电话存了 N 次，浪费空间 |
| **更新异常** | 张三换电话要 UPDATE N 行；漏一行就数据不一致 |
| **插入异常** | 想新增"未下单的用户"——没法插，必须先编个假订单 |
| **删除异常** | 删了张三所有订单 → 张三的用户信息也没了 |

范式化就是为了消除这四种异常。

## 二、三范式（必背）

### 2.1 1NF：原子性

> **每个字段都是不可再分的原子值。**

❌ 反例：
```
| user_id | hobbies                    |
| 1       | 篮球, 足球, 游泳           |
```

✅ 正例：
```
user_hobby 表
| user_id | hobby |
| 1       | 篮球   |
| 1       | 足球   |
| 1       | 游泳   |
```

> 互联网实践常违反 1NF：tags 字段存 "tag1,tag2,tag3" 字符串、配置存 JSON 等。这是**有意识的反范式**——因为查询模式不需要按单个 tag 检索。

### 2.2 2NF：消除部分依赖

> **在 1NF 基础上，非主键字段必须完全依赖于主键，不能只依赖主键的一部分。**
>
> 仅在**联合主键**场景才有意义；单字段主键自动满足 2NF。

❌ 反例（联合主键 `(order_id, product_id)`）：

| order_id | product_id | product_name | quantity | order_time |
| --- | --- | --- | --- | --- |
| 1 | 100 | iPhone | 1 | 2024-01-01 |
| 1 | 200 | iPad | 1 | 2024-01-01 |

- `product_name` 只依赖 `product_id`（部分依赖）
- `order_time` 只依赖 `order_id`（部分依赖）

✅ 正例：

```
order            (order_id PK, order_time, user_id, ...)
product          (product_id PK, product_name, ...)
order_item       (order_id, product_id) PK, quantity
```

### 2.3 3NF：消除传递依赖

> **在 2NF 基础上，非主键字段必须直接依赖于主键，不能通过其他非主键字段传递依赖。**

❌ 反例：

| order_id (PK) | user_id | user_name | user_phone | total_amount |
| --- | --- | --- | --- | --- |

- `user_name` 依赖 `user_id`，`user_id` 依赖 `order_id`——**传递依赖**

✅ 正例：

```
user      (user_id PK, user_name, user_phone)
order     (order_id PK, user_id FK, total_amount)
```

### 2.4 BCNF（额外）

> **3NF 的强化版**：每个决定因素都必须是候选键。

互联网很少深究 BCNF——3NF 已经够用。面试被问到能说"BCNF 是 3NF 的强化版，用于处理多候选键的特殊场景，互联网项目几乎不主动追求"。

### 2.5 范式速记表

| 范式 | 一句话定义 | 适用 |
| --- | --- | --- |
| 1NF | 字段原子化 | 所有表 |
| 2NF | 非主键完全依赖主键 | 联合主键场景 |
| 3NF | 非主键直接依赖主键 | 所有表 |
| BCNF | 决定因素是候选键 | 极少考 |

## 三、反范式（互联网核心实战）

### 3.1 为什么互联网偏反范式

| 严格范式 | 反范式 |
| --- | --- |
| 每张表只存"自己的"字段 | 冗余字段就近放 |
| 跨表关联多 → JOIN 多 | 减少 JOIN |
| 数据一致性强 | 数据一致性弱（要异步同步冗余） |
| 适合 OLAP / 一致性强的业务 | 适合 OLTP / 高 QPS / 读多写少 |

> 互联网核心理念：**性能优先于范式**——性能是用户体验，范式是设计美感。

### 3.2 典型反范式手法

#### 3.2.1 冗余字段

```sql
-- 严格 3NF
order:        order_id, user_id, ...
user:         user_id, user_name, ...

-- 反范式
order:        order_id, user_id, user_name(冗余), user_phone(冗余), ...
```

**收益**：订单列表不必 JOIN user 表。  
**代价**：用户改名要更新所有相关订单的 user_name。  
**实践**：用 binlog + Canal / Maxwell 异步同步冗余字段。

#### 3.2.2 计算字段冗余

```sql
order:        order_id, total_amount(总金额，订单详情累加)
order_item:   order_id, product_id, price, quantity
```

`total_amount` 可以从 `SUM(price * quantity)` 计算出来——但每次列表展示都聚合一次太贵。**写入时一次计算好、存起来**。

#### 3.2.3 大宽表（OLAP 场景）

数仓 / BI 报表场景把订单+用户+商品+地区全部冗余到一张宽表，几百列。**单次查询不再 JOIN**。代价是数据膨胀和 ETL 复杂度——所以是 OLAP 而非 OLTP。

#### 3.2.4 拆分（垂直分表）

```sql
user_basic:  user_id, name, phone, gender              -- 高频查询
user_extra:  user_id, avatar_url, signature, bio        -- 低频查询、大字段
```

主表行变小 → Buffer Pool 命中率高 → 高频查询更快。

详见 [分库分表](./分库分表.md)。

### 3.3 反范式的代价（必讲）

冗余 = 一致性问题。三种应对：

| 策略 | 说明 |
| --- | --- |
| **写时同步** | 写入主表时同时更新冗余表（事务保证），强一致但慢 |
| **异步同步** | binlog + Canal/Maxwell/Debezium 异步更新冗余 |
| **定时对账** | 凌晨低峰跑全量 / 增量对账，发现不一致告警 |

**互联网默认**：异步同步 + 定时对账。能容忍秒级不一致换取写性能。

## 四、E-R 模型与建模流程

### 4.1 E-R 三要素

```
实体 (Entity)         → 表
属性 (Attribute)      → 字段
关系 (Relationship)   → 外键 / 关联表

[用户] ──下单──→ [订单] ──包含──→ [商品]
  ↓                ↓                  ↓
user_id         order_id          product_id
```

### 4.2 关系类型

| 关系 | 实现 |
| --- | --- |
| **1:1** | 主表 + 扩展表共享主键，或外键 + UNIQUE |
| **1:N** | 多方表加外键 |
| **M:N** | 关联表（中间表）记录两方主键 |

**例**：
- 用户 1:1 用户详情 → user 表 + user_extra 表（user_id 共享）
- 用户 1:N 订单 → order 表加 user_id
- 学生 M:N 课程 → student_course 关联表（student_id, course_id）

### 4.3 完整建模流程

```
1. 业务分析 → 识别核心实体（名词）
   订单系统：用户、商品、订单、支付、地址、优惠券...

2. 识别关系（动词）
   用户【下】订单、订单【包含】商品、订单【关联】支付...

3. 画 E-R 图（PowerDesigner / draw.io）

4. 转关系表
   每个实体 → 一张表
   1:N 关系 → 多方加外键
   M:N 关系 → 中间表

5. 应用范式校验
   3NF 校验，识别冗余

6. 反范式优化
   高频查询场景冗余字段、拆分大字段、宽表化

7. 索引设计
   主键、唯一、组合索引

8. 物理建模
   字段类型、长度、默认值、注释
```

## 五、订单系统建模实战（高频场景）

### 5.1 严格范式版

```sql
user           (user_id PK, name, phone, ...)
address        (address_id PK, user_id FK, province, city, detail, ...)
product        (product_id PK, name, price, ...)
order          (order_id PK, user_id FK, address_id FK, total_amount, status, create_time, ...)
order_item     (id PK, order_id FK, product_id FK, price, quantity)
payment        (payment_id PK, order_id FK, amount, channel, status, ...)
```

**问题**：订单列表展示需要 JOIN 4-5 张表（user、address、product、payment）—— 高并发场景性能不行。

### 5.2 互联网反范式版

```sql
-- order 冗余用户和地址快照（用户改名/换地址不影响历史订单）
order:
  order_id, user_id, user_name(冗余), 
  address_snapshot JSON(冗余整个地址),
  total_amount, status, create_time, payment_status(冗余)

-- order_item 冗余商品快照
order_item:
  id, order_id, product_id, 
  product_name(冗余), product_image(冗余), product_price(冗余),
  quantity, sub_amount

-- 单独的支付表（一对多，分次付款 / 退款）
payment:
  payment_id, order_id, amount, channel, status, ...
```

**关键设计点**：

1. **地址快照用 JSON**：用户改地址不影响历史订单（订单创建时复制当时的地址）
2. **商品快照在 order_item**：商品改价不影响历史订单（"订单价"vs"商品当前价"）
3. **payment_status 冗余到 order**：订单列表不必 JOIN payment 表

> 这就是为什么互联网订单表有几十列、看似不规范——**它在用反范式服务于"订单列表毫秒级响应"**。

## 六、设计原则速查

### 6.1 表设计

| 原则 | 说明 |
| --- | --- |
| **必有主键**：BIGINT UNSIGNED 自增 | 顺序写不页分裂；INT 21 亿不够 |
| **三大必有字段**：create_time / update_time / is_deleted | 时间审计 + 软删除 |
| **冷热数据分离**：高频字段一表，低频/大字段拆扩展表 | Buffer Pool 命中率 |
| **字段 NOT NULL DEFAULT** | 索引/查询/统计都更简单 |
| **金额用 DECIMAL** | 浮点精度问题 |
| **禁外键** | 业务一致性应用层保证 |

详见 [MySQL 规范](./MySQL规范.md)。

### 6.2 关系处理

| 关系 | 互联网做法 |
| --- | --- |
| 1:1 | 共享主键拆扩展表（冷热分离） |
| 1:N | 多方加外键字段（不建外键约束） |
| M:N | 中间表（业务字段：关系类型、创建时间等） |

### 6.3 命名规范

详见 [MySQL 规范 - 命名规范](./MySQL规范.md#二命名规范)。

## 七、常见反范式陷阱

### 7.1 滥用 JSON

```sql
-- 错误：所有数据塞 JSON 偷懒
user:  user_id, profile JSON(name, phone, address, hobbies, ...)
```

**问题**：
- 没法对 JSON 内字段建有效索引（5.7+ 函数索引能勉强用，但慢）
- WHERE profile->'$.name' = 'X' 全表扫
- 改 JSON 部分字段需读出整个 JSON 再写回

**正解**：稳定字段用列存储，**只有真正变化的、查询不索引的、嵌套结构**才用 JSON。

### 7.2 冗余字段没同步策略

冗余了 user_name 但没建 binlog → Canal 异步更新 → 用户改名后所有订单显示老名字。

**铁律**：**冗余必有同步策略**——写时同步、异步 CDC、或定时对账。

### 7.3 历史数据不快照

```
2024-01: 商品 A 价格 100 → 用户下单
2024-06: 商品 A 涨价到 200 → 历史订单详情显示 200（错）
```

**正解**：order_item 必须**快照下单时的价格**，而不是关联到 product 当前价。

### 7.4 软删除滥用

`is_deleted=1` 默默累计 → 表越来越大、索引区分度下降 → 查询变慢。

**正解**：定期归档软删除超过 N 个月的数据到归档表。

## 八、生产踩坑

### 8.1 设计阶段没考虑分库分表

订单表设计时单库单表，半年后数据量暴涨要分 64 片。  
**根因**：分片键选择需要早期考虑（比如订单号编码包含 user_id 基因便于路由）。  
**预防**：单表预估 5000 万行级以上的表，**设计阶段就考虑分片键**。

### 8.2 状态字段直接 ENUM

```sql
status ENUM('待付款', '已付款', '已发货', '已签收', '已取消')
```

→ 增加新状态要 ALTER TABLE，可能锁表数小时。

**正解**：用 TINYINT + 应用层字典：
```sql
status TINYINT NOT NULL DEFAULT 0 
  COMMENT '0待付款 1已付款 2已发货 3已签收 9已取消'
```

### 8.3 用户表 phone 字段没冗余 region

国际化业务后期才加 phone_region，老数据全部 NULL → 历史用户登录受影响。

**预防**：**核心字段（手机号、邮箱、身份证）尽早考虑国际化扩展位**。

### 8.4 大字段没拆分

`description TEXT` 直接放在 order 主表 → 简单 SELECT * 拉几 MB → 网络拥塞。

**正解**：大字段（TEXT/BLOB/超长 VARCHAR）拆扩展表。详见 [MySQL 规范 - 大字段拆分](./MySQL规范.md#34-大字段拆分)。

## 九、面试高频追问

### Q1：三范式各是什么？

- 1NF：字段原子化
- 2NF：非主键字段完全依赖主键（联合主键场景才有意义）
- 3NF：非主键字段直接依赖主键，无传递依赖

### Q2：第二范式和第三范式区别？

- 2NF 解决**部分依赖**——非主键字段不能只依赖主键的一部分（仅联合主键时才会出现）
- 3NF 解决**传递依赖**——非主键字段不能通过其他非主键字段传递依赖到主键

### Q3：互联网为什么不严格遵循范式？

性能优于范式美感。OLTP 高并发要求减少 JOIN，反范式（冗余字段、宽表）能极大提升查询性能。代价是冗余 → 一致性问题，用 binlog + 异步同步 + 定时对账解决。

### Q4：订单表为什么不严格 3NF？

订单 user_name、product_name、product_price 等是**冗余但必要**——
- 用户改名不影响历史订单显示
- 商品涨价不影响历史订单金额（订单"快照"语义）

这不是设计错误，是有意识的反范式。

### Q5：JSON 字段有什么风险？

无法对内部字段建普通索引（5.7+ 函数索引能用但有限制）；改部分字段需读写整个 JSON；查询性能远不如普通列。**只在嵌套且不索引的场景用**。

### Q6：1:1 / 1:N / M:N 怎么实现？

- 1:1：共享主键的扩展表，或外键 + UNIQUE
- 1:N：多方加外键
- M:N：中间表

互联网都**不建外键约束**，由业务代码保证。

### Q7：什么时候用宽表？

OLAP / BI 报表场景。OLTP 永远不用宽表——单行膨胀 + 写入开销 + 锁竞争。

### Q8：冗余字段怎么保证一致？

三层：
- 写时同步（事务内更新冗余，强一致但慢）
- 异步同步（binlog + Canal/Maxwell，最终一致）
- 定时对账（凌晨跑全量校验，发现不一致告警）

互联网默认是后两种组合。

### Q9：怎么判断是否需要反范式？

看查询频率和性能：
- 高频查询要 JOIN 5 张表 → 考虑冗余
- 大字段拖慢主表 → 考虑垂直拆分
- 报表统计要聚合 → 考虑预计算冗余字段

但**先别反**——等真出了性能问题再反，避免过度优化。

### Q10：状态字段用什么类型？

TINYINT + 字典注释（0/1/2/...）。**不要用 ENUM**——加新值要 ALTER TABLE，可能锁表。

## 十、答题模板（60 秒话术）

> 数据库设计的基础是**三范式**：1NF 字段原子化、2NF 消除部分依赖、3NF 消除传递依赖。BCNF 是 3NF 强化版，互联网少用。
>
> 但**互联网偏反范式**——OLTP 追求性能，反范式手法包括**冗余字段**（订单冗余 user_name 避 JOIN）、**预计算字段**（total_amount 写时算好）、**垂直拆分**（冷热分离）、**字段快照**（订单 item 存下单时的商品价格，业务上"快照"语义）。
>
> 反范式的代价是冗余 → 一致性——用 **binlog + Canal/Maxwell 异步同步 + 凌晨对账** 解决。
>
> 关系建模：1:1 共享主键拆扩展表、1:N 多方加外键、M:N 中间表。互联网**不建外键约束**，业务代码保证一致。
>
> 设计阶段就要考虑：分片键（早期决定）、字段国际化扩展（手机号 region、地址）、状态字段用 TINYINT 不用 ENUM、大字段拆扩展表。
>
> 经典体现是**订单表**——表面"违反 3NF"（冗余 user_name、product_snapshot），实际是**性能 + 业务快照语义** 的有意识反范式。
