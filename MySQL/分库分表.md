# 分库分表

> 单机 MySQL 撑不住时的扩展手段。面试不仅要讲"垂直 / 水平 / 分库 / 分表"四象限，还要讲**什么时候该上、分片键怎么选、跨库跨片问题怎么解、为什么互联网现在更倾向于直接上 NewSQL**。
>
> 本篇按"为什么 → 怎么分 → 怎么落地 → 分布式新问题"组织。

---

## 一、为什么需要分库分表

### 1.1 单库单表的瓶颈

| 维度 | 阈值 | 表现 |
| --- | --- | --- |
| **数据量** | 单表 >5000 万行 / >50GB | B+Tree 4 层以上，IO 次数翻倍 |
| **磁盘** | 单库 >1TB | 备份慢、迁移难 |
| **QPS** | 单实例 >5000 写 | 写阻塞、binlog 飞速 |
| **连接数** | >5000 连接 | 内存爆 |
| **并发** | 锁竞争剧烈 | 等待时间长 |

> **B+Tree 三层 ≈ 2000 万行**——这是数据量阈值的物理依据：单页 16KB、主键 8B+指针 6B、单页约 1170 子节点，3 层是 1170² × 16 ≈ 2200 万行。

### 1.2 解决思路总览

```
单库单表
   │
   ├─ 数据归档（热数据保留，冷数据移出）   ← 最简单，先试这个
   │
   ├─ 主从 + 读写分离                     ← 解决读瓶颈
   │
   ├─ 垂直分库                            ← 业务边界拆，磁盘 / 连接数解决
   │
   ├─ 垂直分表                            ← 单表字段太多
   │
   ├─ 水平分表                            ← 单表行数太多
   │
   └─ 水平分库分表（终极）                ← 数据量 + QPS 都打爆
```

## 二、四象限拆分方式

### 2.1 垂直分库（按业务）

```
原 monolith DB
├─ user 表
├─ order 表
├─ product 表
└─ inventory 表

→ 按业务边界拆开：
user_db          order_db          product_db
└─ user 表       └─ order 表       └─ product / inventory 表
```

**收益**：
- 不同业务独立扩展、互不影响
- 不同业务 DBA 团队独立运维
- 单库压力下降

**代价**：
- 跨库 JOIN 没了 → 业务侧两次查询 + 内存聚合
- 跨库事务没了 → 引入分布式事务（Seata / TCC）

> 这一步在**单体拆微服务**时几乎必做。

### 2.2 垂直分表（按字段）

```
原 user 表（30 列）
├─ id, name, age, ...     高频查询字段
└─ avatar_url, signature, profile_json ... 低频字段（大字段）

→ 拆成：
user_basic              user_extra
├─ id, name, age, ...   ├─ user_id, avatar_url, ...
```

**收益**：
- 主表行变小 → Buffer Pool 命中率提升
- 大字段不影响主表查询

**代价**：
- 多表 JOIN（同库）
- 业务复杂度上升

### 2.3 水平分表（同库内多个表）

```sql
-- 一张表
order

-- 拆成 16 张
order_0, order_1, ..., order_15
-- 路由：table = order_{user_id % 16}
```

**收益**：单表数据量减少，B+Tree 矮，查询快。

**代价**：
- 跨表查询痛苦（要并行查所有分表）
- 同一物理库 → 磁盘、连接数、QPS 没解决

> 单纯分表很少做——通常是分库分表组合。

### 2.4 水平分库分表（生产终极）

```
db_0                       db_1                    ...   db_3
├─ order_0, order_1, ...   ├─ order_0, order_1...
├─ order_15                ├─ order_15

总分片：4 库 × 16 表 = 64 个分片
路由：
  db = (user_id % 64) / 16
  table = (user_id % 64) % 16
```

**收益**：磁盘、QPS、连接数全部水平扩展。

**代价**：分布式事务、跨片查询、扩容困难——下文详解。

## 三、分片键（Sharding Key）选择

### 3.1 选什么字段做分片键

**好的分片键**：
- **高频 WHERE 条件**：例如订单表用 user_id（用户查自己订单是高频场景）
- **离散均匀**：避免数据倾斜（某些分片爆满，其它空闲）
- **写入均衡**：避免热点分片
- **不变更**：分片键改变意味着数据要跨片迁移

**经典例子**：
- 订单表：用 `user_id`，因为"我的订单"是高频场景，几乎不会按订单号查
- 用户表：用 `user_id`（主键）
- 商品表：通常**不分片**（行少、缓存命中率高）；如果非要分，用 `merchant_id`

### 3.2 分片算法

#### Hash 取模

```
shard = user_id % N
```

**优点**：均匀。  
**缺点**：扩容时（N 改变）几乎所有数据重新分布——**痛**。

#### 一致性 Hash

虚拟环 + 节点散列。扩容时只影响相邻分片。

但 MySQL 分片实践中较少——通常**预分片**（一开始就 64 / 256 个分片，后续多副本翻倍而不改分片数）。

#### 范围分片

```
2024 年订单 → shard_0
2023 年订单 → shard_1
```

**适合**：时序数据，归档方便。  
**风险**：当前年的分片是热点，其它分片闲。

#### 业务路由

```
华北用户 → shard_0
华南用户 → shard_1
```

**适合**：地域型业务。

### 3.3 双维度分片：基因法

**问题**：订单表分片键是 user_id，但有时按 order_id 查——不知道 user_id 怎么定位分片。

**基因法**：让 order_id 的低位 bits 含 user_id 的低位 bits。

```
user_id = 100 → 低 6 bits = 0b00100100 = 36
生成的 order_id 末 6 bits 强制设为 36
查 order_id 时直接拿末 6 bits 当分片键
```

> 这是阿里电商订单经典方案——一个 order_id 同时编码了归属用户的分片信息。

## 四、分布式新问题

### 4.1 跨片 JOIN

```sql
SELECT u.name, o.amount FROM user u JOIN order o ON u.id = o.user_id;
```

→ user 在 user_db，order 在 order_db **且分了 64 片** → 这条 SQL **直接不能跑**。

**解法**：
- **冗余字段**：order 表冗余 user_name（写入时同步），查询不需要 JOIN
- **业务侧两次查询**：先查 user，再用 ID 列表查 order
- **广播表**：小表（地区、字典）每个分片都存一份

### 4.2 跨片事务

```
扣余额（user_db） + 创建订单（order_db）
```

**解法**：
- **Seata AT 模式**：基于 undo log 自动补偿（推荐）
- **TCC**：业务侧编写 Try-Confirm-Cancel
- **本地消息表 + MQ**：最终一致

详见 [分布式事务](../Distributed/分布式事务.md)。

### 4.3 跨片查询 / 排序

```sql
SELECT * FROM order ORDER BY create_time LIMIT 100;
```

→ 64 个分片每个查最近 100 条，merge 排序——**内存里整 6400 条再取 100**。

**LIMIT 1000, 100 更糟**：每个分片都要查前 1100 条 → 总共 70400 条 → 内存爆。

**解法**：
- **分页改游标**：上一页传 last_id，下一页 `WHERE id > last_id`
- **只允许小范围分页**（第 100 页之后给"请缩小范围"）
- **将统计 / 排序数据冗余到 ES / OLAP**

### 4.4 全局 ID

分片后不能用各库自增 ID（会重复）——需要全局唯一。

**方案**：
- **UUID**：长（36 字符）、无序、不适合主键
- **Snowflake**（推荐）：64bit = 1bit 符号 + 41bit 时间戳 + 10bit workerId + 12bit 序列号
- **号段模式**（美团 Leaf）：业务方批量取一段（1000）缓存本地用
- **数据库步长**：库 0 步长 1、库 1 步长 11、...（不灵活）

详见 [分布式ID](../Distributed/分布式ID.md)。

### 4.5 扩容（最痛）

预分片 64 时数据按 `user_id % 64` 分布。要扩到 128：

- **选项 1**：双倍扩容 + 副本切分。原有 64 库每库一分为二，业务路由从 `% 64` 变 `% 128`，但要数据迁移。
- **选项 2**：上一开始就预分多片（256 / 1024）+ 多分片放一台机器。扩容时**只迁机器**不迁分片（"分片数固定，机器增加"）。

> 第二种方案是阿里 / 美团的实战经验——一开始**预分 1024 片**，前期可能只是 16 台机器（每机器 64 片），后续扩到 128 台机器（每机器 8 片）——分片数永不变。

## 五、中间件方案

### 5.1 ShardingSphere（推荐）

Apache 顶级项目，分两种部署：

| 部署 | 说明 |
| --- | --- |
| **ShardingSphere-JDBC** | Java 应用嵌入，无需独立部署，性能好 |
| **ShardingSphere-Proxy** | 独立代理，应用透明（连它就像连普通 MySQL） |

**特性**：
- 分库分表（包含路由、合并、分布式 ID）
- 读写分离
- 分布式事务（XA / Seata）
- SQL 解析与改写

### 5.2 MyCat

老牌中间件，大厂逐渐用得少了——社区活跃度下降，复杂功能 bug 较多。

### 5.3 Vitess

YouTube 开源，K8s 原生，云上首选。但中文社区少，国内更习惯 ShardingSphere。

### 5.4 应用层手写

简单业务（如 4 库 8 表）可以自己路由，不引入中间件复杂度。但中等以上规模强烈建议用 ShardingSphere。

## 六、什么时候不该分库分表

很多团队"还没碰到瓶颈就先分"——是反模式。

### 6.1 优先尝试的方案

```
1. 慢 SQL 治理（pt-query-digest）
2. 索引优化
3. 数据归档（冷数据移出）
4. 主从读写分离
5. 缓存（Redis）抗读
6. 字段拆分（垂直分表）
   ↓ 上面都试过仍不够
7. 才考虑分库分表
```

### 6.2 NewSQL 替代方案

数据规模直接超出单库 → 现代选择是 **TiDB / OceanBase / PolarDB-X**——分布式 SQL 数据库，**应用层无需改**：

| 方案 | 优势 |
| --- | --- |
| **TiDB** | 兼容 MySQL 协议、HTAP（OLTP+OLAP）、自动扩容 |
| **OceanBase** | 阿里系，金融级，分布式事务原生 |
| **PolarDB-X** | 阿里云原生，自动分库分表，弹性扩容 |

> **互联网新选择**：业务从一开始就用 TiDB——不用未来分库分表的痛苦，云上弹性。代价是成本和上手门槛。

## 七、生产踩坑

### 7.1 分片键选错

某团队订单表用 `order_id` 做分片键 → "我的订单"页要广播 64 个分片 → 性能崩。  
**修复**：换 `user_id`，DTS 全量迁移（耗时、停机）。

### 7.2 没考虑分页深翻页

分页页号到 1000 后 → 64 分片 × 100100 条 = 内存爆。  
**修复**：业务限制最大页号；改游标分页。

### 7.3 分布式事务不一致

应用层只调了一个 `try-catch`，没用 Seata → 部分库提交、部分回滚。  
**修复**：上 Seata 或本地消息表。

### 7.4 扩容前没预分片

一开始就 4 库 4 表，半年后想扩 → 必须改路由 + 全量迁移 → **业务停机数小时**。  
**预防**：一开始就 32 库 32 表，前期多分片放一台机器，扩时只挪机器不动数据。

### 7.5 全局 ID 雪花算法时钟回拨

机器 NTP 时钟回拨 → Snowflake 生成的 ID 可能重复。  
**修复**：检测到回拨直接报错或 sleep 等待时间追上。

## 八、面试高频追问

### Q1：什么时候考虑分库分表？

经验值：单表 >5000 万行 / 50GB、单库 >1TB、单实例 QPS 撑不住。先用归档、读写分离、缓存、字段拆分缓解，最后才分库分表。

### Q2：垂直拆分和水平拆分的区别？

垂直按业务 / 字段拆——业务边界明显时用；水平按行拆——数据量大时用。生产通常**垂直分库 + 水平分库分表**组合。

### Q3：分片键怎么选？

高频 WHERE、离散均匀、写入均衡、不变更。订单表用 user_id；非分片键（如 order_id）查询用基因法编码进 ID。

### Q4：跨片 JOIN 怎么办？

冗余字段、业务侧二次查询、小表广播——杜绝在 SQL 层 JOIN。

### Q5：分布式事务怎么处理？

Seata AT（推荐互联网） / TCC（金融） / 本地消息表 + MQ（最终一致）。

### Q6：跨片分页怎么实现？

游标分页（传 last_id）；不允许深翻页；统计排序数据冗余到 ES。

### Q7：分库分表后扩容怎么做？

预分片 + 多分片放一机器（扩容时只移机器不移数据）。或双倍扩容用"基因法"减小迁移范围。

### Q8：ShardingSphere-JDBC 和 Proxy 怎么选？

JDBC 性能好、应用嵌入；Proxy 透明（应用像连 MySQL）、跨语言。性能优先用 JDBC，多语言混合用 Proxy。

### Q9：互联网现在还自己搞分库分表吗？

新业务很多直接上 **TiDB / OceanBase / PolarDB-X**——免分库分表的痛苦。但旧业务大量是 ShardingSphere 改造。

### Q10：分库分表后怎么保证 ID 唯一？

Snowflake 雪花算法（生产首选）、号段模式（美团 Leaf）。绝对不能用库自增。

## 九、答题模板（60 秒话术）

> 单库单表撑不住时上分库分表。**触发阈值**：单表 >5000 万行 / 50GB、单库 >1TB、单实例写 QPS 撑不住。先尝试归档、读写分离、缓存、垂直分表——这些都不行才水平拆。
>
> 拆分四象限：
> - **垂直分库**：按业务边界，user_db / order_db
> - **垂直分表**：单表字段太多，主表 + 扩展表
> - **水平分库分表**：终极方案，订单表按 `user_id % 64` 分 64 片
>
> **分片键选择**关键：高频 WHERE、离散均匀、不变更。订单表用 user_id，按 order_id 查的需求用**基因法**编码。
>
> **新问题**：
> - 跨片 JOIN → 冗余字段
> - 跨片事务 → Seata AT
> - 跨片分页 → 游标分页或限制深度
> - 全局 ID → Snowflake
> - 扩容 → **预分片**（一开始 1024 片放在 N 台机器，扩容只移机器）
>
> 中间件首选 **ShardingSphere**。新业务建议直接上 **TiDB / OceanBase**——免去分库分表所有痛苦。
