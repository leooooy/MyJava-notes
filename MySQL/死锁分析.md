# 死锁分析与排查

> 死锁是生产高频事故。面试官问"线上发生死锁怎么排查"——能讲清"日志在哪、怎么读、怎么定位、怎么修"，立刻区分初级和资深。
>
> 本篇按"原因 → 检测 → 排查 → 修复"组织：① 死锁是怎么形成的 → ② InnoDB 怎么检测和处理 → ③ 怎么从 LATEST DETECTED DEADLOCK 反推 SQL → ④ 实战中常见的 5 种死锁模式与解法。

---

## 一、什么是死锁

> **两个或多个事务，互相持有对方需要的资源，进入永久等待状态。**

### 1.1 必要条件（操作系统经典）

1. **互斥**：资源不可共享
2. **持有并等待**：已持有资源，又申请新资源
3. **不可剥夺**：不能强制夺取
4. **循环等待**：T1→T2→T3→T1

InnoDB 的行锁满足前三个条件——**循环等待是触发死锁的关键**。

### 1.2 最小复现

```
T1                          T2
BEGIN                       BEGIN
UPDATE t SET v=1 WHERE id=1
                            UPDATE t SET v=2 WHERE id=2
UPDATE t SET v=1 WHERE id=2  -- 等 T2 释放 id=2
                            UPDATE t SET v=2 WHERE id=1  -- 等 T1 释放 id=1
                            ↓ 死锁形成 ↓
```

InnoDB 死锁检测器（每秒后台扫描）发现循环 → 自动**回滚一个事务**（通常是修改行数较少的那个，作为"代价较小"的牺牲品）。

```
ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction
```

## 二、InnoDB 怎么处理死锁

### 2.1 检测策略

```sql
SHOW VARIABLES LIKE 'innodb_deadlock_detect';   -- 默认 ON（5.7+）
```

InnoDB 维护一张"等待图"——某事务等锁时，沿等待边深度优先遍历，看能不能回到自己。如果能 → 找到环 → 回滚一个事务破环。

**性能影响**：高并发场景下死锁检测本身是 CPU 开销——每次新事务等锁都触发全图扫描。极端高并发场景（如秒杀）可能要关掉检测，改用 lock wait timeout：

```sql
SET GLOBAL innodb_deadlock_detect = OFF;
SET GLOBAL innodb_lock_wait_timeout = 5;  -- 5 秒等不到自动放弃
```

但**关掉前必须改业务为短事务 + 重试**，否则会大面积超时。

### 2.2 回滚谁

InnoDB 选**修改行数较少**的事务回滚——回滚代价最小。可通过 `SHOW ENGINE INNODB STATUS` 看 `WE ROLL BACK TRANSACTION (1)` 之类的输出。

## 三、死锁日志的取得

### 3.1 SHOW ENGINE INNODB STATUS

```sql
SHOW ENGINE INNODB STATUS\G
```

找 **LATEST DETECTED DEADLOCK** 段——最近一次死锁的详细信息。**只保存最近一次**，新死锁会覆盖。

### 3.2 永久记录

```sql
SET GLOBAL innodb_print_all_deadlocks = ON;   -- 5.6+
```

把每次死锁写到错误日志（`error_log`），生产**强烈建议开**。

### 3.3 日志结构

```
LATEST DETECTED DEADLOCK
========================
2024-04-15 14:30:00 0x7f8b2c0a9700

*** (1) TRANSACTION:
TRANSACTION 12345, ACTIVE 3 sec starting index read
mysql tables in use 1, locked 1
LOCK WAIT 4 lock struct(s), heap size 1136, 2 row lock(s)
MySQL thread id 99, OS thread handle 0x7f8b2c0a9700, query id 1000
UPDATE t SET v=1 WHERE id=2

*** (1) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS space id 25 page no 5 n bits 72 index PRIMARY of table `db`.`t`
trx id 12345 lock_mode X locks rec but not gap waiting

*** (2) TRANSACTION:
TRANSACTION 12346, ACTIVE 5 sec starting index read
...

*** (2) HOLDS THE LOCK(S):
RECORD LOCKS space id 25 page no 5 n bits 72 index PRIMARY of table `db`.`t`
trx id 12346 lock_mode X locks rec but not gap

*** (2) WAITING FOR THIS LOCK TO BE GRANTED:
...

```

### 3.4 关键信息提取

| 信息 | 在哪看 |
| --- | --- |
| 哪两个事务死锁 | TRANSACTION 1 / TRANSACTION 2 |
| 各自正在跑的 SQL | `query id ... <SQL>` |
| 各自等什么锁 | `WAITING FOR THIS LOCK` 块 |
| 各自持有什么锁 | `HOLDS THE LOCK(S)` 块 |
| 谁被回滚 | `WE ROLL BACK TRANSACTION (X)` |
| 涉及哪个索引 | `index PRIMARY of table`、`index idx_xxx` |
| 锁形态 | `lock_mode X locks rec but not gap`（Record Lock）<br>`lock_mode X locks gap before rec`（Gap Lock）<br>`lock_mode X`（Next-Key Lock，最常见） |

## 四、典型死锁案例

### 4.1 模式 1：经典 AB-BA 顺序

```
T1                          T2
UPDATE t SET v=1 WHERE id=1
                            UPDATE t SET v=2 WHERE id=2
UPDATE t SET v=1 WHERE id=2  -- 等 T2
                            UPDATE t SET v=2 WHERE id=1  -- 等 T1 → 死锁
```

**根因**：两事务获取行锁的顺序相反。  
**修复**：业务代码保证**统一顺序**——例如永远按 ID 升序更新。

### 4.2 模式 2：RR 间隙锁碰撞

```
表 t 有 id 索引，已有 id=10, 20

T1: SELECT * FROM t WHERE id BETWEEN 5 AND 25 FOR UPDATE;
    -- 持有 Next-Key Lock (10,20]、(-∞,10]、(20,+∞)

T2: SELECT * FROM t WHERE id BETWEEN 15 AND 30 FOR UPDATE;
    -- 持有 Next-Key Lock (20,+∞)、(10,20]
    -- 区间重叠 → T1 持有的部分 T2 也想要

T1: INSERT INTO t (id) VALUES (8);    -- 想拿 Insert Intention，但 T2 持有 Gap → 等
T2: INSERT INTO t (id) VALUES (28);   -- 想拿 Insert Intention，但 T1 持有 Gap → 等
                                       -- 死锁
```

**根因**：RR 的间隙锁锁范围大、相互重叠概率高。  
**修复**：
- 切 RC（最彻底，没有 Gap Lock）
- 缩小范围 / 加更精确索引让锁更小

### 4.3 模式 3：唯一索引插入冲突

```
表 t 有唯一索引 uk_email

T1: INSERT INTO t (email) VALUES ('a@b.com');
                            T2: INSERT INTO t (email) VALUES ('a@b.com');
                            -- T2 持有 S 锁，等 T1 提交后看是否冲突
T1: ROLLBACK
                            T2: 转为 X 锁继续插入
                                但如果有 T3 也在插同样值 → S-S 兼容，X 互斥 → 死锁
```

**根因**：唯一索引插入冲突时先加 S 锁验证，转 X 锁时容易死锁。  
**修复**：
- 业务先 `SELECT ... FOR UPDATE` 锁住后再 INSERT
- 或用 `INSERT ... ON DUPLICATE KEY UPDATE`

### 4.4 模式 4：外键级联

```
表 child 有外键引用 parent

T1: UPDATE parent SET ... WHERE id=1;   -- 加 parent 行 X 锁
                                         -- 自动给 child 中相关行加 S 锁
T2: UPDATE child SET ... WHERE parent_id=1;  -- 加 child X 锁
T2: 想加 parent S 锁（外键检查） → 等 T1
T1: 想加 child X 锁（级联）   → 等 T2
                                  → 死锁
```

**根因**：外键带来的隐式锁顺序难控制。  
**修复**：互联网规范**禁用外键**，业务代码自己保证一致性。

### 4.5 模式 5：先 SELECT 再 UPDATE 的更新丢失避免逻辑

```
T1: SELECT * FROM t WHERE id=1;  -- 普通 SELECT，无锁
    （业务计算）
T1: UPDATE t SET v=v+1 WHERE id=1;  -- 加 X 锁
                                  T2: 同样流程
                                  -- 两个 UPDATE 同时来 → 不会死锁，但有更新丢失风险
```

如果业务**先 SELECT FOR UPDATE 再 UPDATE**——多事务并发时 FOR UPDATE 可能死锁。

**修复**：
- 用乐观锁（version 字段 + CAS）：`UPDATE t SET v=v+1, version=version+1 WHERE id=1 AND version=?`
- 或合并成单条 UPDATE：`UPDATE t SET v=v+1 WHERE id=1`（依赖原子性，不需先 SELECT）

## 五、排查思路

### 5.1 四步法

```
1. 看错误日志或 SHOW ENGINE INNODB STATUS
   → LATEST DETECTED DEADLOCK
2. 提取两边的 SQL 与等待/持有的锁
3. 看锁模式 + 涉及的索引
   → 推断锁的具体形态（Record / Gap / Next-Key）
4. 找到加锁顺序冲突或共享间隙
```

### 5.2 实战工具组合

```sql
-- 当前所有事务
SELECT * FROM information_schema.innodb_trx;

-- 当前的锁等待
SELECT * FROM performance_schema.data_lock_waits;     -- 8.0
SELECT * FROM information_schema.innodb_lock_waits;   -- 5.7

-- 当前持有的锁
SELECT * FROM performance_schema.data_locks;          -- 8.0

-- 谁在阻塞谁（典型一键表）
SELECT
  r.trx_id   waiting_trx,
  r.trx_query waiting_query,
  b.trx_id   blocking_trx,
  b.trx_query blocking_query
FROM information_schema.innodb_lock_waits w
JOIN information_schema.innodb_trx r ON w.requesting_trx_id = r.trx_id
JOIN information_schema.innodb_trx b ON w.blocking_trx_id = b.trx_id;
```

### 5.3 模拟死锁的实验方法

把死锁日志里的两组 SQL 在两个 session 中**重放**：

```bash
# Session 1
mysql> BEGIN; UPDATE t SET v=1 WHERE id=1;

# Session 2
mysql> BEGIN; UPDATE t SET v=2 WHERE id=2;

# Session 1
mysql> UPDATE t SET v=1 WHERE id=2;  -- 阻塞

# Session 2
mysql> UPDATE t SET v=2 WHERE id=1;  -- ERROR 1213
```

复现一次胜过看十次日志。

## 六、修复策略

### 6.1 业务侧

| 策略 | 说明 |
| --- | --- |
| **统一加锁顺序** | 多行更新永远按 ID 升序，杜绝交叉等待 |
| **缩短事务** | 越快释放锁，死锁概率越低 |
| **拆 BATCH** | 大批量改成小批量，每批独立事务 |
| **乐观锁替代** | 用 version 字段 CAS，避免显式行锁 |
| **避免外键级联** | 业务代码维护一致性 |
| **失败重试** | 应用层捕获 1213 错误自动重试 |

### 6.2 数据库侧

| 策略 | 说明 |
| --- | --- |
| 切 **RC** | 没 Gap Lock，间隙类死锁消失 |
| 加索引 | 让锁更精确，减小锁范围 |
| 调小 `innodb_lock_wait_timeout` | 锁等不到快速失败重试 |
| 关 `innodb_deadlock_detect` | 高并发场景，但需配合短事务 + 重试 |

### 6.3 应用侧重试模板（Java）

```java
@Retryable(value = DeadlockLoserDataAccessException.class,
           maxAttempts = 3,
           backoff = @Backoff(delay = 50, multiplier = 2))
public void doBusiness() {
    // 事务逻辑
}
```

> 死锁是分布式系统中"概率事件"，比起完全消除，更现实的是**失败-重试**。

## 七、生产案例

### 7.1 案例：电商扣减库存死锁

```
T1: UPDATE stock SET num=num-1 WHERE sku=A;  -- 持有 sku=A 锁
T2: UPDATE stock SET num=num-1 WHERE sku=B;  -- 持有 sku=B 锁
T1: UPDATE stock SET num=num-1 WHERE sku=B;  -- 等 T2
T2: UPDATE stock SET num=num-1 WHERE sku=A;  -- 等 T1 → 死锁
```

**根因**：订单包含多 SKU，业务代码按订单中 SKU 顺序扣减——不同订单顺序不一致。

**修复**：扣减前**对 SKU 列表按字典序排序**，统一加锁顺序。

### 7.2 案例：异步任务批量更新

```
任务 A: UPDATE order SET status=1 WHERE create_time<X;  -- 大范围
任务 B: UPDATE order SET status=2 WHERE id=Y;            -- 单条
```

A 锁了一片范围，B 想改的行恰好在 A 范围内 → B 等。  
反过来 B 已开始事务持锁，A 扫到 B 的行 → A 等 → 死锁。

**修复**：
- 任务 A 拆 BATCH（小范围）
- 任务 A 走索引精确锁，避免全表扫
- 错峰跑

## 八、面试高频追问

### Q1：死锁怎么产生的？

四个必要条件：互斥、持有并等待、不可剥夺、循环等待。InnoDB 行锁前三个天然满足，循环等待是触发关键。

### Q2：InnoDB 怎么检测死锁？

死锁检测器后台扫描等待图，发现循环就回滚一个事务（修改行数少的）。可通过 `innodb_deadlock_detect` 关闭。

### Q3：发生死锁怎么排查？

`SHOW ENGINE INNODB STATUS\G`（看 LATEST DETECTED DEADLOCK），提取两个事务的 SQL、持有/等待的锁、索引，反推加锁顺序。生产开 `innodb_print_all_deadlocks` 让所有死锁记到 error log。

### Q4：常见死锁模式？

- AB-BA 顺序冲突
- RR 间隙锁碰撞
- 唯一索引插入 S→X 冲突
- 外键级联
- SELECT FOR UPDATE 并发冲突

### Q5：怎么预防？

- 业务侧：统一加锁顺序、短事务、乐观锁、批量拆分
- 数据库侧：切 RC、加索引、超时快速失败 + 重试

### Q6：死锁检测开销大吗？

高并发下扫描等待图本身就消耗 CPU。极致并发场景（如秒杀）可关检测，改 `lock_wait_timeout=1` + 应用重试。

### Q7：RR 比 RC 更容易死锁吗？

是。RR 的 Gap Lock 锁范围大、彼此重叠概率高，间隙类死锁多发。互联网生产很多公司因此切 RC。

### Q8：LATEST DETECTED DEADLOCK 只能看最近一次？

是。开 `innodb_print_all_deadlocks=ON` 让所有死锁写错误日志，永久保留。

## 九、答题模板（60 秒话术）

> 死锁是事务之间形成循环等待。InnoDB 后台死锁检测器找到环就回滚一个事务（代价最小的那个），返回 1213。
>
> 排查靠 `SHOW ENGINE INNODB STATUS\G` 的 **LATEST DETECTED DEADLOCK** 段——但只保留最近一次，生产必开 `innodb_print_all_deadlocks` 让所有死锁记到 error log。
>
> 从日志拿到两组事务的 SQL + 持有 / 等待的锁，反推加锁顺序冲突。常见模式有 **AB-BA 顺序、RR 间隙锁碰撞、唯一索引 S→X、外键级联、并发 FOR UPDATE**。
>
> 修复优先级：
> 1. 业务侧统一加锁顺序、短事务、乐观锁
> 2. 数据库侧切 RC、加索引让锁精确
> 3. 应用层捕获 1213 自动重试
>
> 死锁是分布式概率事件，**比完全消除更现实的是失败-重试**。
