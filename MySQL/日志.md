# 三大日志：redo log / undo log / binlog

> "MySQL 有几种日志？各自作用是什么？为什么 redo 和 binlog 要做两阶段提交？"——是面试必考题。
>
> 七种日志中只有这三个跟事务、复制、崩溃恢复直接相关，本篇深入这三个；其它四个（错误日志、慢查询、查询日志、中继日志）末尾简介。

---

## 一、七种日志全景

| 日志 | 层 | 作用 | 重要度 |
| --- | --- | --- | --- |
| **redo log** | InnoDB | 崩溃恢复，保证持久性 | ⭐⭐⭐ |
| **undo log** | InnoDB | 回滚 + MVCC | ⭐⭐⭐ |
| **binlog** | Server | 主从复制 + 时间点恢复 | ⭐⭐⭐ |
| relay log | Server | 从库存放主库 binlog | ⭐⭐ |
| slow query log | Server | 慢 SQL 排查 | ⭐⭐ |
| error log | Server | 错误诊断 | ⭐ |
| general query log | Server | 全量查询日志（生产关闭） | ⭐ |

## 二、redo log（重做日志）

### 2.1 设计动机：WAL

> **核心矛盾**：
> - 修改数据 → 改 Buffer Pool 中的脏页。如果每个事务提交都把脏页刷盘 → **随机 IO** 性能崩溃。
> - 不刷？断电就丢。
>
> **解法（WAL，Write-Ahead Logging）**：每次提交只刷"日志"（顺序写，快），数据页异步刷盘。崩溃时重放日志恢复。

### 2.2 物理日志

redo log 记录的是**对页的物理修改**，格式：

```
[表空间号][页号][偏移量][修改长度][修改后内容]
```

**例**：把表空间 11 的页 5 偏移 100 处的 4 字节改为 `0x12345678`。

> **物理 vs 逻辑**：
> - 物理日志（redo）：页字节修改，幂等（重放多次结果一样）
> - 逻辑日志（binlog/undo）：高层操作（SQL/反向操作）

### 2.3 文件结构

默认 `ib_logfile0` 和 `ib_logfile1`，**环形写**：

```
[ib_logfile0: 1G] [ib_logfile1: 1G]
       ↑                ↑
       checkpoint       write_pos
```

| 指针 | 含义 |
| --- | --- |
| `write_pos` | 当前写到哪儿 |
| `checkpoint` | 已经"用过"的位置——脏页已刷盘的部分 |

**两种状态**：
- `write_pos < checkpoint`：还有空间可写（正常）
- `write_pos 追上 checkpoint`：**redo 满**，必须暂停业务等 Page Cleaner 推 checkpoint

> **生产建议**：`innodb_log_file_size` 设大（1G ~ 4G），减少 checkpoint 推进频率。

### 2.4 LSN（Log Sequence Number）

整个 redo 是单调递增字节流，每个位置叫 LSN。

```sql
SHOW ENGINE INNODB STATUS\G
-- LOG 段：
-- Log sequence number          1234567890   ← 当前最新 LSN
-- Log flushed up to            1234567880   ← 已 fsync 的 LSN
-- Pages flushed up to          1234567000   ← 已刷盘脏页对应 LSN
-- Last checkpoint at           1234566000   ← checkpoint 推进位置
```

四个值之差反映系统状态：
- `seq_no - flushed`：未 fsync 的 redo（log buffer 内）
- `flushed - pages_flushed`：未刷盘的脏页对应 redo
- `pages_flushed - checkpoint`：可清理的 redo

### 2.5 刷盘控制（重要）

```sql
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
```

| 取值 | 写入路径 | 风险 |
| --- | --- | --- |
| 0 | 提交时不动，每秒一次刷盘 | MySQL 崩溃丢 1 秒 |
| **1**（默认） | 每次提交 fsync | 最安全 |
| 2 | 每次提交写 OS page cache，每秒 fsync | OS 崩溃丢 1 秒 |

> **生产**：金融用 1（双 1，配合 `sync_binlog=1`）；互联网容许少量丢失常用 2 + sync_binlog=1000，吞吐量提升 5~10 倍。

### 2.6 崩溃恢复流程

```
重启 MySQL
  │
  ├─ 1. 从最后一个 checkpoint LSN 开始读 redo
  │
  ├─ 2. 按 LSN 顺序对每个页 apply redo（已 apply 过的跳过——靠 page LSN 比较）
  │
  ├─ 3. 处于 PREPARE 状态的事务：
  │     ├─ binlog 完整 → COMMIT（实际是把 redo 状态置 COMMIT）
  │     └─ binlog 不完整 → ROLLBACK
  │
  └─ 4. 处于 ACTIVE 但未到 PREPARE 的事务 → 全部 ROLLBACK（用 undo log）
```

## 三、undo log（回滚日志）

### 3.1 作用

1. **事务回滚**（ROLLBACK）
2. **MVCC**（快照读沿 roll_pointer 找历史版本）

### 3.2 逻辑日志

记录的是**反向操作**：

| 当前操作 | undo log 内容 | 回滚时 |
| --- | --- | --- |
| INSERT id=1 | "DELETE id=1" 的语义信息 | DELETE id=1 |
| DELETE 旧行 v1 | 完整旧行 v1 | INSERT v1 |
| UPDATE id=1 v1→v2 | 旧值 v1 + 旧 trx_id + 旧 roll_pointer | UPDATE id=1 v2→v1 |

### 3.3 两类 undo

| 类型 | 触发 | 删除时机 |
| --- | --- | --- |
| Insert undo | INSERT | 事务提交后**立即可清** |
| Update undo | UPDATE / DELETE | 必须等到**没有任何 ReadView** 还可能用到——由 **Purge 线程**异步清理 |

> **DELETE 是特殊的 UPDATE**：标记 deleted_flag=1，并不真正删除——保留行用于 MVCC。Purge 才真正物理删除。

### 3.4 存储

5.7 前 undo 在 `ibdata1` 系统表空间内；5.7+ 可独立到 undo 表空间，便于回收。

```ini
innodb_undo_tablespaces = 2     # 5.7+ 推荐独立 undo 表空间
innodb_undo_log_truncate = ON   # 自动截断超过阈值的 undo
```

### 3.5 与 redo 的协同

undo 本身**也写 redo**——意味着 undo log 自己也是持久的。这样崩溃时：
- 已 commit 的事务：redo 重放保证已生效
- 未 commit 的事务：用 undo 回滚（undo 通过 redo 已恢复）

**循环依赖问题如何解？** redo 是物理日志，记的是"页的字节修改"——其中也包括"undo 段所在页的修改"。所以重放 redo 时既恢复数据页也恢复 undo 段。

## 四、binlog（二进制日志）

### 4.1 作用

1. **主从复制**：从库读主库 binlog 回放
2. **时间点恢复**（PITR）：备份 + binlog 重放到任意时刻

### 4.2 三种格式

```sql
SHOW VARIABLES LIKE 'binlog_format';
```

| 格式 | 记录内容 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **STATEMENT** | 原始 SQL | 日志量小 | 含 NOW() / RAND() / 自增 / UUID 等不确定函数会主从不一致 |
| **ROW**（**5.7+ 默认**） | 行变更前后镜像 | **绝对一致** | 日志量大（一条 UPDATE 影响百万行就是百万条记录） |
| **MIXED** | 默认 STATEMENT，遇不确定切 ROW | 兼顾 | 实现复杂，少见 |

> **生产强烈建议 ROW**：
> - 主从一致是基础
> - 配合工具（Canal、Maxwell、Debezium）做异构同步、CDC
> - 日志量大可以拆 binlog（`max_binlog_size`、`expire_logs_days`）

### 4.3 写入时机

事务提交时**一次性**写入：

```sql
SHOW VARIABLES LIKE 'sync_binlog';
```

| 取值 | 行为 |
| --- | --- |
| 0 | 由 OS 决定刷盘 |
| **1**（默认） | 每次提交 fsync |
| N | 每 N 次提交 fsync |

### 4.4 文件管理

```
binlog.000001
binlog.000002
...
binlog.index   <- 索引文件
```

```ini
max_binlog_size  = 1G          # 单文件大小
expire_logs_days = 7           # 过期天数（5.7）
binlog_expire_logs_seconds = 604800   # 8.0
```

### 4.5 binlog 内容查看

```bash
mysqlbinlog --base64-output=DECODE-ROWS -v binlog.000001
```

ROW 格式下能看到每行修改前后的值，便于反查"是谁改了 X 行"。

## 五、redo vs binlog 对比

| 维度 | redo log | binlog |
| --- | --- | --- |
| **层** | InnoDB | Server |
| **类型** | 物理日志 | 逻辑日志 |
| **写入时机** | 事务进行中持续写 | 事务提交时一次写 |
| **顺序** | 按页修改顺序 | 按事务提交顺序 |
| **存储** | 环形覆盖 ib_logfile | 追加新文件 binlog.NNNNNN |
| **大小** | 固定 | 持续增长 |
| **作用** | 崩溃恢复 | 主从复制 + PITR |
| **是否依赖引擎** | 仅 InnoDB | 所有引擎 |

> 关键区别：**redo 是页修改流（物理）、binlog 是事务变更流（逻辑）**。

## 六、两阶段提交（重要）

> **为什么要两阶段提交？保证 redo 和 binlog 的一致性。**

```
事务 commit
  │
  ├─ Phase 1: redo log 写入 + 状态置 PREPARE
  │
  ├─ Phase 2: binlog 写入磁盘
  │
  └─ Phase 3: redo log 状态置 COMMIT
```

### 6.1 不做 2PC 的反例

**反例 A**（先 redo 再 binlog）：

```
1. redo 写完，事务持久化
2. 崩溃
3. 重启后 redo 重放 → 主库有数据
4. binlog 没记 → 从库永远收不到 → 主从不一致
```

**反例 B**（先 binlog 再 redo）：

```
1. binlog 写完，已发到从库
2. 崩溃
3. redo 没写 → 重启后主库没有这事务
4. 从库已执行 → 主从不一致
```

### 6.2 2PC 的崩溃恢复

```
扫 redo
├─ COMMIT 状态 → 提交
├─ PREPARE 且 binlog 完整 → 提交（"binlog 已发，必须保留"）
├─ PREPARE 但 binlog 不完整 → 回滚
└─ 不存在 → 数据未变，不处理
```

判断 binlog 完整性：每个事务在 binlog 中以 `XID` 标记开始 + commit 标记结束，扫到 commit 才算完整。

### 6.3 group commit（组提交，性能优化）

如果每事务都做完整的 redo prepare → binlog → redo commit，三次 fsync 太重。

5.6+ 的 **binlog group commit**：

```
多个事务的 commit 被收集
  │
  ├─ 一次 fsync 把所有事务的 redo prepare 落盘
  ├─ 一次 fsync 把所有事务的 binlog 落盘
  └─ 一次 fsync 完成所有 redo commit
```

将 N 次 fsync 合成 3 次——吞吐量提升一个量级。

```ini
binlog_group_commit_sync_delay = 100        # 微秒，等更多事务一起提交
binlog_group_commit_sync_no_delay_count = 100
```

## 七、其它日志简介

### 7.1 Relay Log（中继日志）

从库 IO 线程拉取主库 binlog 后，写到本地 relay log；SQL 线程读 relay log 回放。

详见 [主从复制](./主从复制.md)。

### 7.2 Slow Query Log（慢查询）

```ini
slow_query_log = 1
slow_query_log_file = /var/log/mysql/slow.log
long_query_time = 0.5     # 超过 500ms 记录
log_queries_not_using_indexes = 1
```

配合 `pt-query-digest` / `mysqldumpslow` 分析。

### 7.3 Error Log

报错诊断的第一现场。

```ini
log_error = /var/log/mysql/error.log
```

### 7.4 General Query Log

记录每条 SQL（包括 SELECT），用于审计。**生产严禁开**——磁盘和性能双重灾难。

```ini
general_log = 0   # 永远关
```

## 八、生产踩坑

### 8.1 binlog 占满磁盘

`expire_logs_days` 没设、备份没及时归档 → binlog 几百 GB，磁盘满 → 主库挂。

**修复**：
```ini
binlog_expire_logs_seconds = 604800  # 7 天
```
不能直接 `rm` binlog——会让从库失同步。安全方式：
```sql
PURGE BINARY LOGS BEFORE NOW() - INTERVAL 7 DAY;
```

### 8.2 主从延迟巨大

主库 binlog 飞快，从库回放慢。常因：
- STATEMENT 主库一条 SQL，从库也只有一条 → 没问题
- ROW 主库 UPDATE 影响百万行，binlog 百万条 → 从库一条条回放 → 延迟数小时

**修复**：
- 拆 BATCH（业务侧把大事务拆小）
- 5.7+ 启用并行复制（`slave_parallel_type=LOGICAL_CLOCK`、`slave_parallel_workers=8`）

### 8.3 redo log 太小导致频繁 checkpoint

```sql
SHOW STATUS LIKE 'Innodb_log_waits';   -- 长时间不为 0 = redo 太小
```

调大 `innodb_log_file_size = 1G`（5.6+ 在线 resize）。

### 8.4 sync_binlog=0 主从不一致

DBA 为抗写改了 0 → 主库崩溃 → binlog 丢 → 从库永远缺这部分数据。

**结论**：sync_binlog 永远不要设 0；写压力大设 100~1000，不要设 0。

## 九、面试高频追问

### Q1：MySQL 为什么需要两个日志（redo + binlog）？

- redo 是 InnoDB 的崩溃恢复机制（物理日志，页修改）
- binlog 是 Server 层主从复制 + 时间点恢复（逻辑日志，事务变更）

职责不重叠也不能合一——所有引擎都生成 binlog，但只有 InnoDB 有 redo。

### Q2：redo log 和 binlog 的差别？

- 层次：引擎 vs Server
- 类型：物理 vs 逻辑
- 存储：环形覆盖 vs 追加新文件
- 作用：崩溃恢复 vs 主从复制
- 写时机：事务进行中持续 vs 事务提交一次性

### Q3：为什么要两阶段提交？

保证 redo 与 binlog 一致——任一日志写完后崩溃，都不会出现"主库有 / 从库没"或"主库没 / 从库有"。

### Q4：crash 恢复时怎么决定 PREPARE 事务的命运？

看 binlog 是否完整：
- 完整 → 提交（已发出去，必须保留）
- 不完整 → 回滚

### Q5：binlog 三种格式怎么选？

ROW（5.7+ 默认）。STATEMENT 主从可能不一致，MIXED 太复杂。生产一律 ROW，配合 Canal/Maxwell 做 CDC。

### Q6：undo log 删除时机？

- INSERT undo：事务提交后立即可清
- UPDATE/DELETE undo：要等所有 ReadView 不再可能用到，Purge 线程异步清

长事务卡 Purge → undo 膨胀。

### Q7：什么是组提交？

把多个事务的 fsync 合并成一次——大幅提升吞吐。5.6+ binlog 组提交。配置：`binlog_group_commit_sync_delay`。

### Q8：redo log 满了会怎样？

业务暂停——必须等 Page Cleaner 推进 checkpoint。生产避免方法：调大 `innodb_log_file_size`（1~4G）。

### Q9：能用 binlog 替代 redo 做崩溃恢复吗？

不能。binlog 是逻辑日志，恢复时要"从头回放所有事务"——而 redo 是物理日志，只需重放最后一段 checkpoint 之后的部分，效率高得多。

### Q10：写一个事务的全流程，三个日志各扮演什么角色？

```
BEGIN
UPDATE …
  → 修改 Buffer Pool 数据页（脏）
  → 旧值写 undo log（也带 redo）
  → 修改写 redo log buffer

COMMIT
  → redo log fsync + 状态 PREPARE
  → binlog 写入 + fsync
  → redo log 状态 COMMIT

后续异步
  → 脏页刷盘（Page Cleaner）
  → undo Purge（无 ReadView 引用）
  → binlog 推从库
```

## 十、答题模板（60 秒话术）

> MySQL 三大日志各司其职：
>
> **undo log**：InnoDB 引擎的逻辑日志，记反向操作。用于回滚（ROLLBACK）和 MVCC 的历史版本链。Purge 线程异步清理，长事务会卡 Purge。
>
> **redo log**：InnoDB 的物理日志，记页字节修改。环形写，提供崩溃恢复——这就是 WAL（Write-Ahead Logging）思想：日志顺序写、数据页异步刷。`innodb_flush_log_at_trx_commit=1` 是默认最安全。
>
> **binlog**：Server 层的逻辑日志，记事务变更。用于主从复制和时间点恢复。**ROW 格式**主从一致，5.7+ 默认。`sync_binlog=1` 配合 `flush_log=1` 是双 1 高可靠配置。
>
> redo 和 binlog **两阶段提交**保证一致：redo PREPARE → binlog 写 → redo COMMIT。崩溃恢复时按 binlog 完整性决定 PREPARE 事务提交还是回滚。
>
> 5.6+ 的 group commit 把多事务的 fsync 合并，吞吐量提升一个量级。
