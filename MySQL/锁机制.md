# 锁机制（全局锁 / 表锁 / 行锁 / 间隙锁）

> InnoDB 的锁体系是面试硬骨头——分类多、规则细、组合复杂。一道"`SELECT ... FOR UPDATE` 加了什么锁"能问出八种情况。
>
> 本篇按"粒度 → 模式 → 实现 → 加锁规则"四层组织：① 粒度（全局/表/行）→ ② 模式（共享/排他/意向）→ ③ 行锁的三种形式（Record/Gap/Next-Key）→ ④ 加锁规则的等值/范围 × 唯一/非唯一 8 种组合。

---

## 一、锁的分类全景

```
按粒度
├─ 全局锁                               FTWRL (备份用)
├─ 表级锁
│   ├─ 表锁 (LOCK TABLES)              很少手动用
│   ├─ MDL (Metadata Lock)             自动加，DDL 与 DML 互斥
│   └─ 意向锁 (IS / IX)                 自动加，表 vs 行锁的桥梁
└─ 行级锁 (InnoDB 独有)
    ├─ Record Lock                     锁单条索引记录
    ├─ Gap Lock                        锁索引间隙
    └─ Next-Key Lock                   = Record + Gap

按模式
├─ 共享锁 S                            读读相容
└─ 排他锁 X                            写写、读写互斥

按思想
├─ 悲观锁                              加锁串行
└─ 乐观锁 (CAS / version)              不加锁
```

---

## 二、全局锁

```sql
FLUSH TABLES WITH READ LOCK;   -- FTWRL，全库只读
UNLOCK TABLES;
```

**唯一用途**：**逻辑全库备份**（mysqldump --master-data）。整个实例只读 → 数据快照一致。

**生产替代**：
- InnoDB 用 `mysqldump --single-transaction`，靠 MVCC 不加全局锁
- 或用 Xtrabackup 物理备份

> 全局锁会让所有写阻塞——绝不能在主库白天搞。

## 三、表级锁

### 3.1 表锁（手动 LOCK TABLES）

```sql
LOCK TABLES t READ;     -- 共享读锁
LOCK TABLES t WRITE;    -- 排他写锁
UNLOCK TABLES;
```

| 对方持有 | READ | WRITE |
| --- | --- | --- |
| 想加 READ | ✅ 相容 | ❌ 阻塞 |
| 想加 WRITE | ❌ 阻塞 | ❌ 阻塞 |

> InnoDB 几乎不用——行锁更精细。MyISAM 没行锁，靠表锁。

### 3.2 MDL（Metadata Lock，元数据锁）

> **5.5+ 引入，自动加，无需手动**。是面试和生产事故的高频源头。

#### 3.2.1 作用

防止"事务期间表结构被改"导致：
- 列对不上（事务里 SELECT a,b → ALTER 删 b → SELECT 报错）
- 主从复制 binlog 顺序错乱

#### 3.2.2 加锁规则

| 操作 | MDL 模式 |
| --- | --- |
| SELECT / INSERT / UPDATE / DELETE | MDL **共享读**（可并发） |
| ALTER TABLE / DROP TABLE / TRUNCATE | MDL **排他写**（与所有 DML 互斥） |

**关键**：MDL 共享读之间可以并发，但任意一个 DML 都会阻塞 DDL。

#### 3.2.3 经典生产事故

```
T1: SELECT * FROM t WHERE id=1;  -- 持有 MDL 共享读
                                  -- 长事务，MDL 不释放
T2: ALTER TABLE t ADD COLUMN ...;  -- 等待 MDL 写锁，被 T1 阻塞
T3, T4...: SELECT * FROM t;        -- 阻塞在 T2 之后（FIFO 队列，写优先）
                                    -- 整张表 SELECT 全部卡住
```

**经典症状**："就改了个字段，怎么所有查询都挂了？"

**修复**：
1. 找到长事务：`information_schema.innodb_trx` + `processlist`
2. kill 它
3. **预防**：DDL 前确认无长事务；MDL 加 `lock_wait_timeout` 超时（默认 1 年！）

```sql
SET SESSION lock_wait_timeout = 30;   -- DDL 等待最多 30 秒
ALTER TABLE t ADD COLUMN ...;
```

> 8.0+ 引入 **online DDL** 大幅缓解，但 prepare 和 commit 阶段仍要短暂 MDL 写锁。

### 3.3 意向锁（IS / IX）

> **意向锁是表级锁**，但目的是**协调表锁与行锁**——避免每次加表锁都遍历所有行检查行锁。

#### 3.3.1 加锁规则

事务在表 t 上加行锁前，**自动**先在表上加对应意向锁：

| 行锁类型 | 表上的意向锁 |
| --- | --- |
| 行 S 锁 | 意向共享锁 IS |
| 行 X 锁 | 意向排他锁 IX |

#### 3.3.2 兼容性矩阵

| 持有 → / 想加 ↓ | IS | IX | S | X |
| --- | --- | --- | --- | --- |
| **IS** | ✅ | ✅ | ✅ | ❌ |
| **IX** | ✅ | ✅ | ❌ | ❌ |
| **S** | ✅ | ❌ | ✅ | ❌ |
| **X** | ❌ | ❌ | ❌ | ❌ |

**重点**：
- IS 和 IX 之间**互相兼容**——多个事务可同时持有意向锁
- IX 与 S 互斥：当某事务持有行 X 锁（自动有 IX）时，其他事务想加表 S 锁要等

#### 3.3.3 为什么需要意向锁？

```
没有意向锁的世界：
T1 持有某行 X 锁
T2 想加表 S 锁
T2 必须遍历表所有行 → 检查每行有没被锁 → O(N)

有意向锁：
T1 加行 X 锁前先加 IX 表锁
T2 想加表 S 锁
T2 看表上有 IX → 直接知道有冲突 → 等
```

**收益**：行锁 vs 表锁的兼容性判断从 O(N) 变 O(1)。

## 四、行级锁（InnoDB 重点）

### 4.1 共享 vs 排他

| 锁类型 | 加锁方式 | 兼容关系 |
| --- | --- | --- |
| 共享锁 S | `SELECT ... LOCK IN SHARE MODE` 或 `FOR SHARE`（8.0+） | S-S 相容、S-X 互斥 |
| 排他锁 X | `SELECT ... FOR UPDATE` / UPDATE / DELETE | 任何 X 都互斥 |

**自动加锁**：
- INSERT / UPDATE / DELETE → 行 X 锁（自动）
- 普通 SELECT → 不加锁（走 MVCC 快照读）
- 显式锁定读 → 加锁

### 4.2 行锁基于索引

> **InnoDB 的行锁是加在索引项上的，不是数据行本身。**

**含义**：
1. 没用索引的 UPDATE 会**全表扫 + 锁所有行**（实际是逐行加锁）
2. 同一行通过不同索引被定位，锁的是不同索引项

**例子**：
```sql
KEY idx_name (name)
-- 表有 100 万行
UPDATE t SET status=1 WHERE create_time > '2024-01-01';  -- 没走索引！
```

→ 全表扫 + 一行一行加 X 锁 → 几乎所有 INSERT/UPDATE 阻塞。

**修复**：给 create_time 加索引；或缩小条件范围。

### 4.3 三种行锁形态

> InnoDB 的行锁包含三种细分类型，**只在 RR 隔离级别才有 Gap / Next-Key Lock**。

#### Record Lock（记录锁）

锁单条索引记录。

```sql
SELECT * FROM t WHERE id=10 FOR UPDATE;  -- id 是主键
-- 仅锁 id=10 这条记录
```

#### Gap Lock（间隙锁）

锁索引记录之间的"间隙"，**阻止其他事务在该间隙 INSERT**。

```
索引值序列：  ... 10 .... 20 .... 30 ...
间隙：        ↑    ↑     ↑     ↑
           (-∞,10)(10,20)(20,30)(30,+∞)
```

**特点**：
- Gap 锁之间**互相兼容**（多个事务可同时锁同一间隙）——它的目的不是互斥，是**防 INSERT**
- 仅 RR 才有；RC 完全不加 Gap Lock

#### Next-Key Lock（临键锁）= Record + Gap

```
锁 id=20 的 Next-Key Lock：
  锁 id=20 这条记录 + 间隙 (上一个键, 20]

范围是 "前开后闭"
```

InnoDB 的**默认行锁单位**就是 Next-Key Lock。

### 4.4 三种锁的兼容性

| 持有 → / 想加 ↓ | Record(X) | Gap | Next-Key(X) |
| --- | --- | --- | --- |
| Record(X) | ❌ | ✅ | ❌ |
| Gap | ✅ | ✅ | ✅ |
| Next-Key(X) | ❌ | ✅ | ❌ |

**关键**：Gap 锁不阻塞别的 Gap 锁、不阻塞读取，**只阻塞 INSERT**。

## 五、加锁规则（高频考点）

### 5.1 三大原则（必背）

> 来源：DBA-丁奇《MySQL 实战 45 讲》总结

1. **加锁的基本单位是 Next-Key Lock**（前开后闭）
2. 查找过程中**访问到的对象才加锁**
3. RR 隔离级别下生效；RC 下没有 Gap

### 5.2 两条优化规则

1. 唯一索引的**等值**查询，命中记录 → Next-Key 退化为 **Record Lock**
2. 等值查询，向右遍历且最后一个值不满足等值条件 → Next-Key 退化为 **Gap Lock**

### 5.3 一个 bug

唯一索引的**范围**查询，会访问到**第一个不满足条件的行为止**——多锁一个。

### 5.4 总结表

| 索引类型 | 查询条件 | 命中 | 加锁结果 |
| --- | --- | --- | --- |
| 唯一索引（含主键） | 等值 | 命中 | Record Lock |
|  |  | 不命中 | Gap Lock |
|  | 范围 | — | Next-Key Lock（**多锁一行**） |
| 普通索引 | 等值 | 命中 | Next-Key Lock + 后续 Gap |
|  |  | 不命中 | Gap Lock |
|  | 范围 | — | Next-Key Lock |
| 无索引 | — | — | 全表 Next-Key Lock（基本=表锁） |

## 六、加锁实战分析

假设表：

```sql
CREATE TABLE t (
  id INT PRIMARY KEY,
  c INT,
  d INT,
  KEY idx_c (c)
);
INSERT INTO t VALUES (5,5,5),(10,10,10),(15,15,15),(20,20,20),(25,25,25);
```

### 6.1 主键等值，命中

```sql
SELECT * FROM t WHERE id=10 FOR UPDATE;
```

- 唯一索引等值命中 → **Record Lock(id=10)**

### 6.2 主键等值，不命中

```sql
SELECT * FROM t WHERE id=11 FOR UPDATE;
```

- 唯一索引等值不命中 → 退化为 **Gap Lock (10, 15)**
- 别的事务可以 INSERT id=11、12、14 之外的吗？不行——整个 (10,15) 间隙被锁

### 6.3 主键范围

```sql
SELECT * FROM t WHERE id>=10 AND id<11 FOR UPDATE;
```

- `id>=10`：等值匹配 → Record Lock(id=10)
- 范围扫到 `id=15` 才停 → Next-Key Lock (10, 15]
- 最终：Record Lock(10) + Next-Key (10, 15]

### 6.4 主键范围（"bug"案例）

```sql
SELECT * FROM t WHERE id>10 AND id<=15 FOR UPDATE;
```

- 范围 → Next-Key (10, 15]
- 但唯一索引范围会**多扫一行**到 id=20 → Next-Key (15, 20]
- 最终：Next-Key (10, 15] + Next-Key (15, 20]

### 6.5 普通索引等值，命中

```sql
SELECT * FROM t WHERE c=10 FOR UPDATE;
```

- Next-Key (5, 10]
- 普通索引：要扫到第一个不满足的（c=15）才停
- 退化优化：c=15 不满足等值 → Gap (10, 15)
- 最终：Next-Key (5,10] + Gap (10, 15)

### 6.6 普通索引等值，不命中

```sql
SELECT * FROM t WHERE c=7 FOR UPDATE;
```

- 找不到 c=7 → 退化为 Gap (5, 10)

## 八、生产踩坑

### 8.1 大表 UPDATE 没走索引 → 全表锁住

```sql
UPDATE t SET status=1 WHERE create_time < '2024-01-01';  -- create_time 没索引
```

→ 优化器全表扫 + 一行一行加 X 锁 → 整张表写阻塞。

**修复**：
- 加索引
- 拆 BATCH（每批小范围）

### 8.2 RR 间隙锁导致死锁

```sql
-- T1 和 T2 都执行
INSERT INTO t (id, c) VALUES (?, ?);
```

如果两事务尝试在同一间隙插入，可能各自拿了 Insert Intention Lock 等对方 → 死锁。

**对策**：切 RC，或 INSERT 前 SELECT FOR UPDATE 占位。

### 8.3 MDL 锁拖慢全表

DDL 期间一个普通 SELECT 没及时结束 → ALTER 等 MDL → 后面所有 SELECT 排队 → 雪崩。

**对策**：
- DDL 前查 `processlist` 没长事务才动手
- 设置 `lock_wait_timeout` 让 DDL 失败快速重试

### 8.4 误以为 RC 不需要任何锁

RC 仍然在写时加行锁——只是没有 Gap Lock。误用 RC 不能减少行锁本身的争用。

## 九、面试高频追问

### Q1：InnoDB 行锁是怎么实现的？

加在**索引项**上，不是数据行。所以 UPDATE 没走索引 → 全表锁。

### Q2：什么是 MDL？为什么生产容易出事？

元数据锁，DML 加共享读、DDL 加排他写。长事务 + DDL → 整表阻塞。预防靠"DDL 前看 processlist + 设 lock_wait_timeout"。

### Q3：意向锁是什么？为什么需要？

表级锁，事务加行锁前先在表加 IS/IX。让"表锁与行锁是否冲突"的判断从 O(N) 变 O(1)。

### Q4：Gap Lock 在哪个隔离级别才有？

仅 RR。RC 完全没有 Gap Lock。

### Q5：Next-Key Lock 是什么？为什么前开后闭？

Record Lock + 前面间隙 Gap Lock 的组合。InnoDB 默认行锁形态。前开后闭——锁住"上一个值之后到当前值"的范围。

### Q6：InnoDB 在 RR 怎么解决幻读？

- 快照读：MVCC ReadView 复用
- 当前读：Next-Key Lock 阻止 INSERT 进来

### Q7：写一条 SQL 推下加锁结果

按"基本单位 Next-Key + 优化规则"推。例如 `WHERE id=10 FOR UPDATE`：唯一索引等值命中 → 退化 Record Lock(10)。

### Q8：怎么减少锁冲突？

- 让所有 SQL 走索引（避免行锁升表锁）
- 减小事务范围（短事务）
- 对范围查询用更小的范围
- 必要时切 RC 减 Gap Lock
- 业务用乐观锁（version 字段）替代部分悲观锁

## 十、答题模板（60 秒话术）

> InnoDB 的锁体系按**粒度**分全局/表/行，按**模式**分 S/X，按**思想**分悲观/乐观。
>
> 表级有手动表锁、自动 MDL（DDL 与 DML 互斥）、意向锁（行锁与表锁的桥梁，让兼容性判断 O(1)）。
>
> 行级是 InnoDB 重头戏：**Record Lock**（单行）、**Gap Lock**（间隙，仅 RR 有，目的是防 INSERT）、**Next-Key Lock**（前开后闭组合，默认形态）。**行锁加在索引项上**——没走索引会变全表锁。
>
> 加锁规则三原则：基本单位 Next-Key、访问到才加、唯一索引等值命中退化 Record。
>
> RR 用 Next-Key 解决当前读幻读，但代价是死锁概率高、并发低；RC 没 Gap Lock 并发更高、死锁少，互联网常用 RC。
>
> 生产最大坑是 MDL 与长事务——DDL 前必看 `processlist`。
