# 事务的隔离级别

> 隔离级别是 MySQL 面试**最容易考、也最容易答错**的题。多数人能背 4 级别 + 3 现象，但被追问"InnoDB 的 RR 真的解决了幻读吗""为什么 MySQL 默认 RR 不是 RC"就答不上。
>
> 本篇按"现象 → 级别 → 实现 → 选型"组织：① 三种并发现象到底是啥 → ② 4 个级别如何对应解决 → ③ 各级别的内部实现 → ④ RC vs RR 在生产中怎么选。

---

## 一、并发事务的三种现象

### 1.1 脏读（Dirty Read）

**定义**：读到了**未提交**事务的修改。

```
T1                          T2
BEGIN
                            BEGIN
                            UPDATE balance=900 WHERE id=1
SELECT balance WHERE id=1   -- 读到 900（脏数据）
                            ROLLBACK
                            -- T2 回滚后真实值仍是 1000
                            -- 但 T1 已经基于 900 做了决策 → 错乱
```

**根本问题**：读到的"事实"可能根本不存在。

### 1.2 不可重复读（Non-Repeatable Read）

**定义**：同一事务中两次读到**已修改+已提交**的同行数据，结果不同。

```
T1                          T2
BEGIN
SELECT balance WHERE id=1   -- 读到 1000
                            UPDATE balance=900 WHERE id=1
                            COMMIT
SELECT balance WHERE id=1   -- 读到 900
COMMIT
```

**根本问题**：读到的"事实"在事务期间发生了变化。

### 1.3 幻读（Phantom Read）

**定义**：同一事务中按相同条件查询，**行数发生变化**（多了或少了行）。

```
T1                          T2
BEGIN
SELECT COUNT(*) WHERE age>20  -- 5 行
                              INSERT (age=25)
                              COMMIT
SELECT COUNT(*) WHERE age>20  -- 6 行
COMMIT
```

**根本问题**：事务中"同一条件命中的集合"发生了变化。

> **不可重复读 vs 幻读**：
> - 不可重复读关注**同一行**的值变化（修改）
> - 幻读关注**结果集**的行数变化（插入/删除）

### 1.4 三者对比表

| 现象 | 触发 | 看到的 |
| --- | --- | --- |
| 脏读 | 读 + 别人的**未提交**写 | 假数据 |
| 不可重复读 | 读 + 别人的**已提交**写 | 同行新值 |
| 幻读 | 读 + 别人的**已提交**插入 | 多/少行 |

## 二、四个隔离级别

```
                  脏读   不可重复读   幻读   并发性
READ UNCOMMITTED   ✓         ✓        ✓     最高
READ COMMITTED     ✗         ✓        ✓     高
REPEATABLE READ    ✗         ✗        ✗*    中
SERIALIZABLE       ✗         ✗        ✗     最低

* InnoDB 的 RR 通过 MVCC + 间隙锁解决了大部分幻读
```

```sql
SELECT @@transaction_isolation;        -- 8.0 用 transaction_isolation
SELECT @@tx_isolation;                 -- 5.7 用 tx_isolation
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

### 2.1 READ UNCOMMITTED（读未提交）

读不加锁、写加排他锁——**读能直接看到别人未提交的数据**。

**特点**：
- 三种现象全有
- 几乎没人用，反例对比讲解时才出现

### 2.2 READ COMMITTED（读已提交）

**所有主流数据库默认级别**（Oracle、PostgreSQL、SQL Server）。MySQL 是异类，默认 RR。

**实现**：
- 读：MVCC 快照读，**每次 SELECT 都生成新 ReadView** → 总能看到最新已提交
- 写：行级排他锁，提交后释放
- **没有间隙锁**

**特点**：解决脏读，仍有不可重复读 + 幻读。

### 2.3 REPEATABLE READ（可重复读）

**MySQL 默认级别**。

**实现**：
- 读：MVCC 快照读，**事务首次 SELECT 生成 ReadView，复用到事务结束** → 多次读结果一致
- 写：行级排他锁 + **间隙锁 + 临键锁（Next-Key Lock）** → 阻止其他事务在范围内插入

**特点**：解决脏读、不可重复读、**大部分幻读**（详见第 4 节）。

### 2.4 SERIALIZABLE（串行化）

**实现**：所有 SELECT 自动加 S 锁、所有写加 X 锁——**完全退化成纯锁方案**。

**特点**：
- 三种现象全无
- 并发性能极差，几乎只在纯只读 + 强一致场景才用

## 三、各级别的实现机制

| 级别 | 读策略 | 写策略 | 间隙锁 |
| --- | --- | --- | --- |
| RU | 当前读（最新值，不查 MVCC） | 行级 X 锁 | 无 |
| RC | **MVCC 每次新 ReadView** | 行级 X 锁 | **无** |
| RR | **MVCC 首次 ReadView 复用** | 行级 X 锁 | **有 Next-Key Lock** |
| Serializable | 所有 SELECT 加 S 锁 | 行级 X 锁 | 有 |

### 3.1 RC vs RR 在 MVCC 上的区别

> **同一套机制，只是 ReadView 生成时机不同**——这是高频追问。

```
RC: 每条 SELECT 都重新生成 ReadView
T1: BEGIN
T1: SELECT * WHERE id=1   -- ReadView A，看到 v1
            T2: UPDATE; COMMIT
T1: SELECT * WHERE id=1   -- ReadView B（新生成），看到 v2 ← 不可重复读

RR: 整个事务复用首次的 ReadView
T1: BEGIN
T1: SELECT * WHERE id=1   -- ReadView A，看到 v1
            T2: UPDATE; COMMIT
T1: SELECT * WHERE id=1   -- 仍用 ReadView A，看到 v1 ← 一致
```

详见 [MVCC](./mvcc.md)。

### 3.2 RR 的间隙锁（Gap Lock / Next-Key Lock）

仅在 RR 才生效，目的是**阻止其他事务在范围内插入**——这是 InnoDB 解决幻读的关键。

```sql
-- RR 下
SELECT * FROM t WHERE age > 20 FOR UPDATE;
-- 不仅锁住 age>20 的现有行，还锁住 (20, +∞) 的间隙
-- 别的事务想 INSERT (age=25) 会阻塞
```

详见 [锁机制](./行锁.md)。

## 四、RR 真的解决了幻读吗？（高频陷阱）

**答案分两半**：
- **快照读**（普通 SELECT）：✅ 通过 ReadView 复用解决
- **当前读**（FOR UPDATE / UPDATE / DELETE）：⚠️ 通过 Next-Key Lock 解决，**但不是无条件的**

### 4.1 快照读下的幻读（已解决）

```
T1: BEGIN
T1: SELECT * WHERE age>20            -- 3 行
            T2: INSERT (age=25); COMMIT
T1: SELECT * WHERE age>20            -- 3 行（ReadView 复用）✅
```

### 4.2 当前读下的幻读（Next-Key Lock 解决）

```
T1: BEGIN
T1: SELECT * WHERE age>20 FOR UPDATE  -- 3 行 + 锁住 (20,∞) 间隙
            T2: INSERT (age=25)        -- 阻塞！直到 T1 结束
T1: SELECT * WHERE age>20 FOR UPDATE  -- 仍 3 行 ✅
T1: COMMIT
            T2: INSERT 成功
```

### 4.3 RR 仍可能幻读的情况

**先快照读，再当前读**：

```
T1: BEGIN
T1: SELECT * WHERE age>20            -- 快照读 3 行（建 ReadView）
            T2: INSERT (age=25); COMMIT
T1: SELECT * WHERE age>20 FOR UPDATE  -- 当前读 4 行！⚠️ 幻读
```

**根因**：当前读绕过 ReadView，看最新数据。`FOR UPDATE` 之前没有先用当前读"占位"。

**解法**：业务上**先用 `SELECT ... FOR UPDATE` 锁住范围**，再读，杜绝中间插入。

> 这就是为什么生产代码中"先 SELECT 再 UPDATE"的事务，第一次 SELECT 通常要写 `FOR UPDATE`——否则别人能在 SELECT 后插队，破坏假设。

## 五、RC vs RR 生产选型

### 5.1 历史背景

MySQL 默认 RR 是因为早期主从复制基于 **STATEMENT** 格式 binlog，RC 会导致主从执行顺序不一致 → 数据不一致。RR 用间隙锁强制串行 → 保证主从一致。

5.6+ 默认 binlog 是 ROW 格式后，RC 也能保证主从一致——很多互联网大厂（**阿里、腾讯**）线上**默认设 RC**。

### 5.2 选型对比

| 维度 | RC | RR |
| --- | --- | --- |
| 锁范围 | 行锁 | 行锁 + 间隙锁 |
| 并发性 | **更高** | 较低 |
| 死锁概率 | 低 | **高**（间隙锁锁范围大） |
| 主从一致 | ROW binlog 下 OK | OK |
| 幻读 | 有 | 大部分被 Next-Key Lock 解 |
| 长事务 ReadView 影响 | 每次 SELECT 重建，影响小 | 整事务复用，长事务卡 Purge |

### 5.3 实际选择

| 场景 | 选择 |
| --- | --- |
| 业务能容忍不可重复读、追求高并发 | **RC** |
| 业务依赖"事务内多次读结果一致" | **RR** |
| 大厂规范 | **RC**（互联网常见） / **RR**（金融常见） |

> **重要**：选哪个不是技术 vs 业务的对立——是和业务模型耦合的。改隔离级别要全量回归测试，特别检查 SELECT...FOR UPDATE 的相关业务。

## 六、显式开启事务的方式

```sql
-- 方式 1：BEGIN / COMMIT
BEGIN;
UPDATE ...;
COMMIT;

-- 方式 2：START TRANSACTION（同义）
START TRANSACTION;
UPDATE ...;
COMMIT;

-- 方式 3：5.7+ 一致性快照（事务开启即建 ReadView，否则首条 SELECT 才建）
START TRANSACTION WITH CONSISTENT SNAPSHOT;
SELECT ...;
COMMIT;

-- 方式 4：set autocommit=0
SET autocommit = 0;
UPDATE ...;
COMMIT;
SET autocommit = 1;
```

> Spring 的 `@Transactional` 默认走方式 1（关闭 autoCommit + COMMIT 提交）。

## 七、生产踩坑

### 7.1 RR 下间隙锁导致死锁

```sql
-- T1
SELECT * FROM t WHERE age=25 FOR UPDATE;  -- 锁 age=25 + 间隙 (20,30)

-- T2（同时）
INSERT INTO t (age) VALUES (28);  -- 在间隙里 → 阻塞
```

间隙锁锁范围大、彼此重叠概率高 → RR 下死锁高发。

**对策**：
- 切 RC（最彻底）
- 减小事务范围、加索引让锁更精确

### 7.2 RR 下"读了不存在的行也锁住"

```sql
-- 表里没有 id=100 的行
SELECT * FROM t WHERE id=100 FOR UPDATE;  -- 居然锁住了 (上一个值, 100) 间隙
```

→ 别的事务 INSERT id=100 会阻塞。RC 下不会有这个锁。

### 7.3 长事务 + RR

```
T1: BEGIN; SELECT ...; -- ReadView 已建立
-- 接着跑 1 小时业务
T1: COMMIT
```

**危害**：
- T1 期间，其他事务的 update undo 都不能 Purge（T1 的 ReadView 还可能用到）
- ibdata 持续膨胀
- 二级索引 MVCC 检查变慢（版本链长）

**对策**：单事务不超过 1 秒；只读查询走从库或 OLAP 系统。

### 7.4 把 SELECT 写成 FOR UPDATE 拖慢系统

新人看到"读完要做判断再写"，全部加 `FOR UPDATE` → 行锁 + 间隙锁满天飞。

**正解**：仅在"读完做判断再 UPDATE 这一行"才需要 FOR UPDATE。其它情况快照读 + 乐观锁（version 字段 CAS）足够。

## 八、面试高频追问

### Q1：MySQL 默认隔离级别？为什么不是标准 RC？

RR。历史上 STATEMENT binlog 主从一致需要 RR；现在 ROW binlog 已无此限制，但默认仍 RR。

### Q2：RR 解决幻读吗？

**部分**。
- 快照读：MVCC ReadView 复用 → ✅
- 当前读：Next-Key Lock 间隙锁 → ✅（但若先快照后当前读，仍可能幻读）

### Q3：脏读、不可重复读、幻读区别？

- 脏读：读到**未提交**写
- 不可重复读：读到**已提交**的修改（同行不同值）
- 幻读：读到**已提交**的插入/删除（行数变化）

### Q4：RC 和 RR 在 MVCC 上的差别？

ReadView 生成时机：RC 每次 SELECT 都新建，RR 事务首次 SELECT 建后复用。

### Q5：什么是间隙锁？什么时候生效？

锁住索引记录之间的"间隙"，阻止 INSERT。**只在 RR 才生效**，是 InnoDB 解决幻读的关键。

### Q6：互联网公司一般用 RC 还是 RR？

各家不同。阿里 / 腾讯系常用 RC（高并发 + 死锁少）；金融场景多用 RR（强一致）。重要的是**统一并测试**。

### Q7：Serializable 怎么实现？为什么不用？

所有 SELECT 自动加共享锁、写加排他锁——退化成纯锁。并发极差，仅极特殊场景。

### Q8：BEGIN 之后立即建 ReadView 吗？

**不**。RR 下 ReadView 在事务内**第一条 SELECT** 才建。要事务一开始就建快照，用 `START TRANSACTION WITH CONSISTENT SNAPSHOT`。

### Q9：能在事务中切换隔离级别吗？

可以但**只对后续生效**：`SET TRANSACTION ISOLATION LEVEL ...`；`SET SESSION ...` 影响整 session；`SET GLOBAL` 改全局。生产很少这么干。

## 九、答题模板（60 秒话术）

> SQL 标准定义 4 个隔离级别——RU、RC、RR、Serializable，对应解决脏读、不可重复读、幻读三种现象。
>
> MySQL 默认是 **RR**，与标准（RC）不同。原因是早期 STATEMENT binlog 主从一致依赖 RR，现在 ROW binlog 已不强制。
>
> 实现机制：
> - **RC**：MVCC 快照读，每条 SELECT 重新生成 ReadView。
> - **RR**：MVCC + **首次 SELECT 建 ReadView 复用**，写操作还加 **Next-Key Lock**（行锁 + 间隙锁）解决幻读。
>
> RR 解决幻读分两半：快照读由 ReadView 复用解；当前读由 Next-Key Lock 解。**先快照读再当前读仍可能幻读**——业务上要么先 FOR UPDATE 锁范围，要么直接 RC。
>
> 互联网公司常用 RC，因为间隙锁少、死锁概率低、并发高，且 ROW binlog 已保证主从一致。
