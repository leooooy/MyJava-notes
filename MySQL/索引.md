# 索引

> 索引是 MySQL 面试**最高频**的话题，没有之一。它的考察分四层：
> ① 数据结构层（**为什么是 B+Tree，不是别的**）→ ② 物理存储层（聚簇 vs 非聚簇、回表、覆盖）→ ③ 使用层（最左前缀、索引下推、失效场景）→ ④ 设计层（什么字段建索引、如何不滥用）。
>
> 答题节奏：先给结论 → 然后讲为什么 → 最后举生产例子。本文按这个顺序组织。

---

## 一、为什么是 B+Tree

### 1.1 候选数据结构对比

| 结构 | 等值查询 | 范围查询 | 磁盘 IO | 是否适合索引 |
| --- | --- | --- | --- | --- |
| 哈希表 | O(1) | ❌ 不支持 | 小 | 仅 Memory 引擎、精确等值用 |
| 二叉搜索树 | O(log N) 退化 O(N) | ✅ | 多 | 否：不平衡 |
| AVL 平衡树 | O(log N) | ✅ | **多**（一节点一值） | 否：树太高 |
| 红黑树 | O(log N) | ✅ | 多 | 否：还是太高 |
| **B+Tree** | O(log N) | ✅ + 叶子链表 | **少**（一节点多值） | ✅ |
| LSM-Tree | O(log N) | ✅ | 写优化 | RocksDB 走这条路 |

> 数据库索引的瓶颈是**磁盘 IO**，不是 CPU。AVL/红黑一节点一个 key，几亿数据要走 30+ 层；B+Tree 一节点放几百个 key，3 层就能索引几亿行——这就是核心动机。

### 1.2 B+Tree 关键特性

```
                       ┌─ 12 ─ 25 ─┐                ← 非叶子（仅索引）
                      /            \
            ┌─ 3 ─ 8 ─┤              ┌─ 18 ─ 22 ─┐  ← 非叶子
           /         |              |            \
       [1,2,3] ─→ [5,8] ─→ [12,15] ─→ [18,20] ─→ [22,25]  ← 叶子（数据）
                                    ↕（双向链表）
```

1. **非叶节点只存 key**（不存 data），单页能放更多 key → 树更"矮胖"
2. **数据全在叶子**，等值查询路径长度固定 → 性能稳定
3. **叶子双向链表**，范围查询和有序遍历直接顺着链走，O(M)（M=结果数）
4. 默认 16KB 一页，主键 8B、指针 6B，单页可索引 ~1170 个子节点；3 层 B+Tree 可容纳 ~21 亿行

> **问题：B-Tree 行不行？** B-Tree 非叶节点也存数据 → 单页能存的 key 少 → 树更高 → IO 更多。**B+Tree 是 B-Tree 的针对磁盘场景的优化版本。**

### 1.3 为什么不用哈希索引

- 不支持范围查询（最致命）
- 无法用于排序（ORDER BY、GROUP BY）
- 哈希冲突大量退化时还不如 B+Tree

哈希索引在 InnoDB 里只有"自适应哈希索引（AHI）"自动维护，**不能手动建**。Memory 引擎才支持显式哈希索引。

## 二、聚簇索引 vs 非聚簇索引

### 2.1 定义对比

| 维度 | 聚簇索引（Clustered） | 非聚簇索引（Secondary） |
| --- | --- | --- |
| 叶子节点存什么 | **整行数据** | **主键值** |
| 一张表能有几个 | **1 个** | 多个 |
| InnoDB 里是谁 | 主键索引 | 普通索引 / 唯一索引 |
| 别名 | 主键索引 | 二级索引 / 辅助索引 |

### 2.2 InnoDB 怎么决定聚簇索引

按以下顺序：

1. 定义了主键 → 主键
2. 没主键，找**第一个 NOT NULL UNIQUE 列**
3. 都没有 → InnoDB 自动生成 6 字节隐藏列 `DB_ROW_ID`

> **生产规范**：永远显式定义主键（建议自增 BIGINT）。靠隐藏 row_id 的表，多个连接写入时争用同一锁、批量插入相互阻塞。

### 2.3 MyISAM 的索引结构（对比）

MyISAM **没有聚簇索引**——主键索引和普通索引都是非聚簇的，叶子节点存的是**行的物理地址**（指针）。所以 MyISAM 的主键查找也要一次磁盘寻址，比 InnoDB 慢。

## 三、回表与覆盖索引

### 3.1 回表

```sql
CREATE TABLE t (
  id INT PRIMARY KEY,
  name VARCHAR(50),
  age INT,
  KEY idx_name (name)
);

SELECT * FROM t WHERE name = '张三';
```

执行步骤：
1. 走 `idx_name` B+Tree → 叶子拿到主键 id
2. **回表**：拿 id 再走主键 B+Tree → 拿到完整行
3. 返回

→ 一次查询走了**两棵 B+Tree**。

### 3.2 覆盖索引（Covering Index）

```sql
SELECT id, name FROM t WHERE name = '张三';
```

→ `idx_name` 叶子已经有 name + id（主键值），不需回表，**只走一棵树**。EXPLAIN 看 `Extra: Using index`。

**面试加分点**：
- `SELECT *` 几乎一定回表（除非是只有索引列的小表）
- 设计组合索引时，把"经常一起查询的字段"塞进去，覆盖索引省回表

### 3.3 索引下推（ICP，Index Condition Pushdown）

5.6+ 优化。

```sql
KEY idx_name_age (name, age)
SELECT * FROM t WHERE name LIKE '张%' AND age = 25;
```

**5.5 之前**：先按 name 过滤拿一堆主键 → 全部回表 → 再用 age 过滤
**5.6+ ICP**：在引擎层，扫描索引时**就用 age 过滤**，不满足直接跳过 → **大幅减少回表次数**

EXPLAIN 看 `Extra: Using index condition`。

## 四、组合索引与最左前缀

### 4.1 排序规则

```sql
KEY idx_a_b_c (a, b, c)
```

B+Tree 排序按 (a, b, c) 字典序：
```
(1,1,1) (1,1,2) (1,2,1) (1,2,3) (2,1,1) (2,3,5) ...
```

**只有 a 整体有序**；b 仅在 a 相同时有序；c 仅在 a、b 相同时有序。

### 4.2 最左前缀原则

可以走索引：
- `WHERE a = ?`
- `WHERE a = ? AND b = ?`
- `WHERE a = ? AND b = ? AND c = ?`
- `WHERE a = ? AND c = ?` ← **a 走索引、c 不走，但比全表扫好**

不走索引：
- `WHERE b = ?`
- `WHERE b = ? AND c = ?`

> "最左"指的是**索引列的左边连续匹配**，跳过中间列会失效。

### 4.3 范围查询导致的失效

```sql
SELECT * FROM t WHERE a > 10 AND b = 5 AND c = 3;
```

`a > 10` 是范围 → b、c **不走索引**（因为 a 范围内 b、c 是无序的）。但**等值条件可以放一起**：

```sql
SELECT * FROM t WHERE a = 10 AND b = 5 AND c > 3;  -- a、b、c 全走
```

**生产建议**：组合索引设计时，等值字段放前面、范围字段放最后。

### 4.4 ORDER BY 走索引的条件

走索引：
- `ORDER BY` 的列必须满足最左前缀
- 排序方向必须一致（都 ASC 或都 DESC，8.0 前不支持混排）

```sql
KEY (a, b, c)
ORDER BY a, b      ✅ 走索引
ORDER BY a DESC, b DESC   ✅ 走索引（统一倒序）
ORDER BY a, b DESC ❌ 8.0 前不行；8.0+ 用 KEY (a, b DESC) 可
ORDER BY b, c      ❌ 跳过 a
```

不走索引时 EXPLAIN 看 `Extra: Using filesort`——是性能危险信号。

## 五、索引失效全场景

### 5.1 高频失效原因（必背）

| 场景 | 例子 | 为什么 |
| --- | --- | --- |
| **左模糊** | `WHERE name LIKE '%三'` | 索引按从左到右排序，`%` 开头无法用前缀定位 |
| **函数 / 表达式** | `WHERE YEAR(create_time)=2024` | B+Tree 存的是原值，函数算完认不出 |
| **隐式类型转换** | `WHERE phone = 13800138000`（phone 是 varchar） | 转 double 比较 → 全表扫 |
| **OR 一边没索引** | `WHERE a=1 OR b=2`（b 无索引） | 必须扫一次全表来满足 b=2 |
| **!= / <> / NOT IN** | `WHERE a != 5` | 高基数下 not 效率不如全表扫，优化器放弃索引 |
| **`IS NULL`/`IS NOT NULL`** | 取决于优化器估代价 | 大量 null 时可能不走索引 |
| **跳过最左前缀** | `KEY(a,b)` 但 `WHERE b=?` | 不满足索引顺序 |
| **范围列后续列** | `WHERE a>10 AND b=?` | b 无序，无法走 |
| **数据分布太均匀** | 性别字段（男/女） | 走索引还要回表，优化器算下来不如全表扫 |

### 5.2 隐式类型转换的细节（高频陷阱）

**字符串列 vs 数字常量**：
```sql
-- phone 是 VARCHAR
SELECT * FROM user WHERE phone = 13800138000;  -- ❌ 不走索引
SELECT * FROM user WHERE phone = '13800138000'; -- ✅ 走索引
```

**为什么？** 比较时 MySQL 把字符串转 double，索引上的字符串值要逐个 ToFloat 比较 → 等效于全表扫。

**数字列 vs 字符串常量**：
```sql
-- id 是 INT
SELECT * FROM user WHERE id = '10';   -- ✅ 走索引（字符串转 int 是无歧义的）
```

**记忆口诀**：**数字字段无所谓，字符串字段必加引号**。

### 5.3 在 WHERE 里用 IS NULL 走不走索引？

走，**但前提是字段允许 NULL**。MySQL 给 NULL 留了索引位置（用一个 NULL bitmap 标记），可以走。但：
- 大量 NULL 时区分度低，优化器可能放弃
- **规范上禁止字段允许 NULL**（更难维护、占空间），不要在这上花心思

### 5.4 LIKE 走不走索引

| 写法 | 是否走索引 |
| --- | --- |
| `LIKE '张%'` | ✅ 前缀匹配 |
| `LIKE '%三'` | ❌ |
| `LIKE '%三%'` | ❌ |
| `LIKE '_三'` | ❌（首位通配符） |

模糊搜索建议走 ES 或全文索引（FULLTEXT），不要用 LIKE。

## 六、索引设计原则

### 6.1 加索引的字段

| 优先级 | 类型 | 例子 |
| --- | --- | --- |
| 必须 | 主键 | `id` |
| 高 | WHERE 经常出现的列 | `user_id, status` |
| 高 | JOIN 关联列 | `order.user_id` |
| 中 | ORDER BY / GROUP BY 列 | `create_time` |
| 中 | 唯一约束列 | `email, phone` |

### 6.2 不加索引的字段

- 区分度极低（性别、状态枚举）—— 走全表扫更划算
- 频繁更新（改 1 行可能要改多个索引页 + 页分裂）
- BLOB / TEXT（要建必须用前缀索引）

### 6.3 组合索引设计

**原则**：
1. 等值列放前面，范围列放后面
2. 区分度高的列放前面（让早期分支多）
3. 高频 SELECT 字段加进来，争取覆盖索引

**例子**：电商订单表，高频查询 `WHERE user_id=? AND status=? ORDER BY create_time`：
```sql
KEY idx_user_status_time (user_id, status, create_time)
-- user_id 区分度极高
-- status 等值过滤
-- create_time 既支持范围又支持排序
```

### 6.4 单表索引数量

互联网规范：**单表 ≤ 5 个索引**。理由：
- 写性能下降（每次更新都要维护所有受影响索引）
- 优化器选择空间大，可能选错
- 索引占空间（聚簇索引一份数据，每个二级索引一份主键 + 索引列）

### 6.5 前缀索引

```sql
KEY idx_email (email(20))
```

只用前 20 字符建索引——节省空间，但**不能用于覆盖索引**（拿到的 email 是截断的，要回表读完整值）。

**选择长度的方法**：找区分度 0.95 以上的最短长度：
```sql
SELECT COUNT(DISTINCT LEFT(email, 5)) / COUNT(*) FROM t;
SELECT COUNT(DISTINCT LEFT(email, 10)) / COUNT(*) FROM t;
-- 找区分度足够的最小长度
```

## 七、特殊索引

### 7.1 唯一索引

| 维度 | 普通索引 | 唯一索引 |
| --- | --- | --- |
| 写入性能 | 高（可走 Change Buffer） | 低（必须读页判重） |
| 查询性能 | 找到一行可能继续扫（验证非唯一） | 找到即停 |
| 业务约束 | 无 | 防重复 |

> **微妙点**：唯一索引插入必须读页查冲突，**走不了 Change Buffer**——大量写入场景，普通索引 + 应用层去重可能比唯一索引更快。

### 7.2 全文索引（FULLTEXT）

5.6+ InnoDB 支持。中文需要用 ngram 解析器（5.7+）：
```sql
CREATE TABLE article (
  id INT PRIMARY KEY,
  content TEXT,
  FULLTEXT KEY ft_content (content) WITH PARSER ngram
);
```

但**生产建议直接用 ES**，全文索引功能受限、不易维护。

### 7.3 隐藏索引（Invisible Index，8.0+）

```sql
ALTER TABLE t ALTER INDEX idx_xxx INVISIBLE;
```

测试"删了这个索引会怎样"，先隐藏观察，确认不影响再删——避免误删后立刻撤回不及。

### 7.4 函数索引（8.0+）

```sql
CREATE INDEX idx_year ON t ((YEAR(create_time)));
SELECT * FROM t WHERE YEAR(create_time) = 2024;  -- 8.0+ 走索引
```

5.7 及以前**只能改写 SQL**避免函数。

## 八、生产踩坑

### 8.1 隐式转换吞 QPS

线上 phone 字段是 varchar，应用代码 `String sql = "WHERE phone=" + phone`（拼数字进去）→ **不走索引** → CPU 100%。

**解法**：所有 SQL 用预编译参数（PreparedStatement），自动带类型；CodeReview 拦截字符串拼接 SQL。

### 8.2 索引太多 INSERT 慢

订单表加了 12 个索引，单条 INSERT 50ms→500ms。  
**根因**：每加一行要更新 12 棵 B+Tree，多个还触发页分裂。  
**解法**：合并冗余索引（`(a)` 和 `(a,b)` 留 `(a,b)` 即可）；归档冷数据。

### 8.3 ORDER BY filesort

`ORDER BY create_time DESC LIMIT 10` 没走 idx_create_time → filesort 全表排序 → 慢。  
**根因**：WHERE 子句让优化器选了别的索引。  
**解法**：建复合索引 `(where_col, create_time)`，让排序直接走索引。

### 8.4 深分页爆炸

```sql
SELECT * FROM t ORDER BY id LIMIT 1000000, 10;
```

要扫前 100 万行才取 10 行 → **数十秒**。  
**解法**：延迟关联：
```sql
SELECT t.* FROM t INNER JOIN (
  SELECT id FROM t ORDER BY id LIMIT 1000000, 10
) AS x USING (id);
```
内层只走索引（覆盖索引）找 id，外层小数据回表。

或上一页传 max_id：
```sql
SELECT * FROM t WHERE id > 1000000 ORDER BY id LIMIT 10;
```

## 九、面试高频追问

### Q1：MySQL 索引为什么用 B+Tree，不用 B-Tree、跳表、红黑树？

- **vs B-Tree**：B+Tree 非叶子不存 data，单页索引更多 key，树更矮 → IO 更少；叶子链表，范围查询稳定。
- **vs 红黑/AVL**：单节点单 key，几亿数据要 30+ 层，IO 太多。
- **vs 跳表**：跳表每个节点要存指针，空间放大；磁盘场景没有内存场景的指针访问优势。Redis 用跳表是因为它在内存里跑。

### Q2：聚簇索引和非聚簇索引区别？

聚簇索引叶子存整行（一表一个，InnoDB 主键），非聚簇叶子存主键值（多个），用非聚簇查 `*` 必须**回表**。

### Q3：什么是回表？怎么避免？

通过二级索引找到主键 → 再用主键查整行的过程。避免方法：**覆盖索引**——SELECT 字段全在索引里，叶子直接拿全。

### Q4：最左前缀是什么？范围查询为什么会断？

组合索引按 (a, b, c) 字典序排，b 仅在 a 相同时有序。`a > 10` 让 a 的取值多变 → 这些行的 b 整体无序 → b 无法走索引。

### Q5：索引下推（ICP）？

5.6+ 优化。引擎层扫描二级索引时直接用 WHERE 中的额外条件过滤，减少回表。EXPLAIN 看 `Using index condition`。

### Q6：索引为什么会失效？举几个例子

- 函数 / 表达式：`YEAR(t)=2024`
- 隐式转换：`varchar 列 = 数字常量`
- 左模糊：`LIKE '%xx'`
- 跳过最左前缀
- 范围列后的列
- OR 一边无索引

### Q7：聚簇索引的主键为什么推荐自增？

- 顺序写入，B+Tree 末尾追加，不触发**页分裂**
- 主键值小，二级索引存的也小，整体磁盘占用低
- UUID 主键随机插入会导致频繁页分裂、空间碎片

### Q8：为什么不建议字段允许 NULL？

- NULL 让索引、统计、比较都变复杂（IS NULL 才能查、不能用 = 比较）
- NULL 占用额外的 bitmap 位
- 业务语义不清——0、空字符串、NULL 三者难辨

### Q9：唯一索引和普通索引怎么选？

- 业务有唯一性约束 → 唯一索引（防止脏数据）
- 纯加速查询 → 普通索引，写性能更好（可走 Change Buffer）

### Q10：count(*)、count(1)、count(主键)、count(字段) 哪个最快？

InnoDB 下：
- `count(*)` ≈ `count(1)`：优化器走最小辅助索引扫，最快
- `count(主键)`：扫聚簇索引，叶子是整行，IO 比 count(*) 多
- `count(字段)`：扫该列，遇 NULL 跳过，比 count(*) 慢

→ **永远用 count(*)**。

## 十、答题模板（60 秒话术）

> MySQL 索引底层用 B+Tree——非叶节点只存 key，单页能存几百个 key，3 层就索引几亿行，IO 极少；叶子双向链表，范围和排序都快。
>
> InnoDB 的**主键索引是聚簇索引**，叶子存整行；二级索引叶子存主键值，按 `*` 查要**回表**——所以业务上能用**覆盖索引**就不写 `SELECT *`。
>
> 组合索引遵循**最左前缀**原则，等值字段放前面、范围字段放后面，否则后续列断索引；ICP（5.6+）下推过滤减少回表。
>
> 索引失效高频四种：函数、隐式类型转换、左模糊、跳过最左前缀。生产规范上单表索引 ≤5、自增 BIGINT 主键、字段 NOT NULL DEFAULT。
>
> 深分页的问题用**延迟关联**或**游标主键**解。
