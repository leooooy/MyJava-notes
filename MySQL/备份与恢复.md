# 备份与恢复（PITR）

> 备份不是 DBA 专属——后端工程师面试也常问"线上数据库挂了你怎么恢复""能恢复到任意时间点吗""备份策略怎么定的"。
>
> 本篇解决：① 逻辑 vs 物理备份选哪个 → ② 增量备份怎么做 → ③ **PITR（Point-in-Time Recovery 时间点恢复）的完整链路** → ④ 生产备份策略 → ⑤ 验证机制。

---

## 一、为什么备份与恢复是面试高频题

```
事故场景            危害          恢复手段
─────────────────────────────────────────────
DROP TABLE 误操作   数据全丢      备份 + binlog
DELETE WHERE 漏写  大批量丢      备份 + binlog
UPDATE 漏 WHERE   全表覆盖      备份 + binlog
机房断电、磁盘损坏  实例不可用    备份恢复或主从切换
逻辑炸弹（恶意）   不定时触发    备份 + 审计
```

**铁律**：**没有备份的系统是定时炸弹**——再强的高可用都救不了"DROP TABLE"。

## 二、备份的两个维度

### 2.1 备份类型

| 维度 | 选项 |
| --- | --- |
| **逻辑 vs 物理** | mysqldump（逻辑）/ Xtrabackup（物理） |
| **全量 vs 增量** | 全量 RDB / 增量 binlog |
| **冷备 vs 热备** | 停机备份 / 在线备份 |
| **单机 vs 主从** | 主库备份 / 从库备份（首选，不影响主） |

### 2.2 逻辑 vs 物理备份对比（高频）

| 维度 | 逻辑（mysqldump） | 物理（Xtrabackup） |
| --- | --- | --- |
| **形式** | SQL 语句文本 | 数据文件副本（.ibd / ibdata） |
| **速度** | **慢**（执行 SQL 重放） | **快**（直接拷文件） |
| **空间** | 紧凑（压缩后小） | 大（接近原数据库） |
| **跨版本** | ✅ 跨版本兼容 | ❌ 严格同版本 |
| **细粒度** | 单表 / 单库可选 | 全库为主 |
| **校验** | 文本可读 | 二进制 |
| **恢复速度** | 慢（要 INSERT 一条条插） | 快（拷回文件） |
| **适合规模** | <100GB | >100GB |

> **经验值**：100GB 是分水岭。100GB 以下逻辑备份够用；以上必须物理备份，否则备份/恢复要数小时。

## 三、mysqldump（逻辑备份）

### 3.1 基本用法

```bash
# 全库备份
mysqldump -u root -p \
  --all-databases \
  --single-transaction \
  --master-data=2 \
  --routines --triggers --events \
  > backup.sql

# 单库
mysqldump -u root -p mydb > mydb.sql

# 单表
mysqldump -u root -p mydb mytable > mytable.sql
```

### 3.2 关键参数（必懂）

| 参数 | 作用 | 必加？ |
| --- | --- | --- |
| `--single-transaction` | InnoDB 用 MVCC 保证一致快照，**不锁表** | ✅ 必加 |
| `--master-data=2` | 在 dump 文件中记录当时的 binlog 位点（注释形式） | ✅ 必加（PITR 需要） |
| `--lock-tables` | MyISAM 才需要；InnoDB 千万别加 | ❌ |
| `--routines` | 备份存储过程和函数 | 视情况 |
| `--triggers` | 备份触发器 | 视情况 |
| `--events` | 备份事件 | 视情况 |
| `--quick` | 一行行 dump，不加载整张表到内存 | ✅ 大表必加（默认开） |
| `--default-character-set=utf8mb4` | 字符集 | ✅ 必加 |
| `--hex-blob` | 二进制字段以 16 进制输出 | 含 BLOB 时加 |

### 3.3 --single-transaction 工作原理

```
1. mysqldump 开启事务 (BEGIN; SET TRANSACTION ISOLATION LEVEL REPEATABLE READ)
2. 立即建立一致性快照（START TRANSACTION WITH CONSISTENT SNAPSHOT）
3. dump 期间使用 MVCC 读历史版本，不阻塞业务写
4. dump 结束 COMMIT
```

**前提**：仅 InnoDB 有效。MyISAM 没事务/MVCC，必须加 `--lock-tables`。

> **互联网生产**：所有表 InnoDB → `--single-transaction` 一定加。

### 3.4 恢复

```bash
mysql -u root -p mydb < backup.sql
# 或
mysql -u root -p < backup.sql   # backup.sql 内含 USE 语句
```

### 3.5 mysqldump 的局限

- **大库慢**：100GB 库 dump 几小时、恢复十几小时
- **恢复阶段不能并行**：单线程 INSERT，重放慢
- **生成 SQL 占空间**：压缩后还是比原库大

## 四、mysqlpump（mysqldump 升级版）

5.7+ 推出的 mysqldump 升级版，支持**并行 dump**。

```bash
mysqlpump --user=root --password \
  --default-parallelism=4 \
  --include-databases=mydb \
  > backup.sql
```

实际用得比 mysqldump 少——主流向 Xtrabackup 靠拢。

## 五、Percona Xtrabackup（物理备份，生产首选）

### 5.1 优点

- **物理拷文件**，速度比 mysqldump 快 10x+
- **热备**：在线备份不锁表（InnoDB）
- **支持增量备份**（必须的）
- **流式备份**：边备份边压缩边传到远程
- **业界标准**：阿里云 / 腾讯云 RDS 底层都用 Xtrabackup

### 5.2 8.0 后的命名

5.7 用 `xtrabackup` 二进制（innobackupex 已废）。8.0 用 **Percona XtraBackup 8.0**（命令仍是 `xtrabackup`）。

### 5.3 全量备份

```bash
xtrabackup --backup \
  --target-dir=/backup/full_20240415 \
  --user=root --password=xxx \
  --datadir=/var/lib/mysql

# 准备阶段（apply redo log，让备份处于一致状态）
xtrabackup --prepare \
  --target-dir=/backup/full_20240415
```

### 5.4 增量备份（核心）

> **思路**：从上一次（全量或增量）备份的 LSN 开始，只拷数据页 LSN ≥ 该值的页。

```bash
# 增量 1（基于全量）
xtrabackup --backup \
  --target-dir=/backup/inc1_20240416 \
  --incremental-basedir=/backup/full_20240415

# 增量 2（基于增量 1）
xtrabackup --backup \
  --target-dir=/backup/inc2_20240417 \
  --incremental-basedir=/backup/inc1_20240416
```

**收益**：单次增量可能只有几 GB，全量几百 GB——大幅减少备份时间和存储。

### 5.5 准备增量备份（合并）

```bash
# 准备全量（注意 --apply-log-only，不要做最终 redo apply）
xtrabackup --prepare --apply-log-only \
  --target-dir=/backup/full_20240415

# 把增量 1 合并进全量
xtrabackup --prepare --apply-log-only \
  --target-dir=/backup/full_20240415 \
  --incremental-dir=/backup/inc1_20240416

# 合并增量 2
xtrabackup --prepare --apply-log-only \
  --target-dir=/backup/full_20240415 \
  --incremental-dir=/backup/inc2_20240417

# 最后一次 prepare（不加 --apply-log-only）
xtrabackup --prepare \
  --target-dir=/backup/full_20240415
```

### 5.6 恢复

```bash
# 1. 停 MySQL
systemctl stop mysql

# 2. 清空 datadir
rm -rf /var/lib/mysql/*

# 3. 复制备份
xtrabackup --copy-back \
  --target-dir=/backup/full_20240415

# 4. 修权限
chown -R mysql:mysql /var/lib/mysql

# 5. 启动
systemctl start mysql
```

## 六、binlog（增量恢复的关键）

> **PITR 的灵魂**：定期全量 + 持续 binlog = 可恢复到任意时间点。

### 6.1 binlog 管理

```ini
# my.cnf
log_bin                   = /var/log/mysql/binlog
binlog_format             = ROW           # 必须 ROW
sync_binlog               = 1             # 高可靠
expire_logs_days          = 7             # 保留 7 天
max_binlog_size           = 1G
binlog_row_image          = full          # ROW 格式记录完整行
```

### 6.2 binlog 备份策略

```
方式 1: 主库本地保留 7 天 + 上传 OSS 长期保存
方式 2: 实时 mysqlbinlog --read-from-remote-server 拉取到备份服务器
方式 3: 从库开 binlog 自动备份
```

### 6.3 mysqlbinlog 用法

```bash
# 解析查看
mysqlbinlog binlog.000001 | less

# ROW 格式可读输出
mysqlbinlog --base64-output=DECODE-ROWS -v binlog.000001

# 按时间过滤
mysqlbinlog --start-datetime="2024-04-15 10:00:00" \
            --stop-datetime="2024-04-15 11:00:00" \
            binlog.000001 > recovery.sql

# 按位置过滤
mysqlbinlog --start-position=12345 \
            --stop-position=67890 \
            binlog.000001 > recovery.sql

# 应用到数据库
mysql -u root -p < recovery.sql
```

## 七、PITR 完整流程（核心）

> **PITR**（Point-in-Time Recovery）：恢复到任意指定时间点。这是面试**必背**的链路。

### 7.1 前置要求

1. 定期**全量备份**（每天 / 每周）
2. binlog **持续保留**（至少 = 全量备份周期 × 2）
3. 全量备份记录**当时的 binlog 位点**（`--master-data=2`）

### 7.2 误操作恢复实战

**场景**：`2024-04-15 10:30:00` 误删了订单表的所有数据。

```bash
#  ─────────────  时间线  ────────────
#  04-14 02:00 全量备份 (binlog.000010, pos=12345)
#  04-14 ~ 04-15 binlog.000010 ~ binlog.000015 持续写
#  04-15 10:30 误操作！
#  目标：恢复到 04-15 10:29:59
```

**步骤**：

```bash
# 1. 在新实例上恢复全量备份
xtrabackup --copy-back --target-dir=/backup/full_20240414
systemctl start mysql

# 2. 准备 binlog（从全量备份的位点开始 → 误操作前一秒）
mysqlbinlog --start-position=12345 \
            --stop-datetime="2024-04-15 10:29:59" \
            binlog.000010 binlog.000011 binlog.000012 binlog.000013 binlog.000014 binlog.000015 \
            > recovery.sql

# 3. 应用 binlog 到新实例
mysql -u root -p < recovery.sql

# 4. 验证数据
SELECT COUNT(*) FROM order WHERE create_time > '2024-04-15 10:00:00';

# 5. 把恢复后的数据导出 → 导入主库（或直接切换主库）
```

**关键参数**：
- `--start-position`：全量备份记录的位点（避免重放已备份的部分）
- `--stop-datetime` 或 `--stop-position`：精确停在误操作前

### 7.3 GTID 简化 PITR

开了 GTID 后，可以用 `--exclude-gtids` 跳过特定事务（比如误删事务），不必一秒一秒猜：

```bash
mysqlbinlog --include-gtids='abc:1-100,abc:102-200' binlog.* > recovery.sql
# 跳过 abc:101 这个误操作事务
```

## 八、备份策略（生产实战）

### 8.1 经典分层策略

```
全量备份（Xtrabackup）
  ├─ 每周日凌晨 2 点
  └─ 保留 4 周

增量备份（Xtrabackup）
  ├─ 每日凌晨 2 点（除周日）
  └─ 保留 7 天

binlog 备份
  ├─ 实时同步到备份服务器
  ├─ 主库保留 7 天
  └─ 备份服务器保留 30 天

逻辑备份（mysqldump）
  ├─ 每周关键表 dump 一次
  └─ 用于跨版本兼容性预案
```

### 8.2 备份位置

| 层级 | 说明 |
| --- | --- |
| 本地磁盘 | 快，但单点故障 |
| **备份服务器**（同机房） | 推荐基础保障 |
| **OSS / S3 等远程对象存储** | 跨机房容灾 |
| **异地存储** | 金融场景必有，跨地域容灾 |

> **3-2-1 原则**：3 份副本、2 种介质、1 份异地。

### 8.3 主库 vs 从库备份

**永远在从库备份**——主库备份占 IO 影响业务。

```
主库 ← 写
  ↓ 复制
从库 1 → 业务读
从库 2 → 备份专用（业务不读）
```

## 九、备份验证（最容易被忽视）

> **没验证过的备份等于没有备份**。线上事故无数次发生在"备份文件存在，但恢复时发现损坏 / 不完整 / 旧格式"。

### 9.1 验证策略

| 频率 | 内容 |
| --- | --- |
| **每次备份后** | 校验文件完整性（checksum）+ 大小合理性 |
| **每周一次** | 在测试环境实际恢复一次全量备份 |
| **每月一次** | 完整 PITR 演练（全量 + binlog 重放到指定时间点） |
| **每季度** | DR（灾难恢复）演练，模拟主库整挂 |

### 9.2 自动化校验脚本

```bash
# 校验 Xtrabackup 备份完整性
xtrabackup --prepare --target-dir=/backup/test \
  && echo "Prepare OK" \
  || echo "BACKUP CORRUPTED!"

# 起一个临时 MySQL 实例验证
mysqld --datadir=/backup/test --port=3307 --user=mysql &
mysql -P 3307 -e "SELECT COUNT(*) FROM mydb.user;"
```

## 十、生产踩坑

### 10.1 备份占满磁盘

备份脚本没设保留期 → 几年备份累计几 TB → 磁盘满 → 主库挂。

**预防**：
```bash
find /backup -mtime +30 -delete   # 30 天前的删除
```
配合监控告警（磁盘 >85%）。

### 10.2 binlog 没保留够长

全量每周一次，binlog 只留 3 天 → 周三全量损坏 → 周二的 binlog 也已删 → **完全无法恢复**。

**铁律**：**binlog 保留时长 ≥ 全量备份周期 × 2**。

### 10.3 备份验证流于形式

只看备份文件存在 + 大小不为 0，没真正恢复过。结果某次需要时发现备份文件损坏。

**预防**：每周自动恢复一次到测试环境 + 跑 SELECT 验证。

### 10.4 跨版本恢复失败

物理备份（Xtrabackup）严格依赖 MySQL 版本——5.7 备份不能恢复到 8.0 实例。

**预防**：升级前先用逻辑备份（mysqldump）兜底。

### 10.5 sync_binlog=0 + 主从切换丢数据

为抗写性能改 0 → 主库崩 → binlog 丢最近事务 → 备份+binlog 恢复也丢。

**铁律**：`sync_binlog=1`（高可靠）或 `sync_binlog=100~1000`（折中），**永远不设 0**。

### 10.6 误删后还在主库直接操作

DBA 在主库直接 `ROLLBACK` 试图救——无效（commit 已提交）+ 可能让事情更糟。

**正解**：
1. 立即停业务（避免新数据进来覆盖）
2. 找一个**新实例**做 PITR 恢复
3. 验证后再切换或导回主库

## 十一、面试高频追问

### Q1：MySQL 怎么备份？

逻辑用 mysqldump（适合 <100GB），物理用 Xtrabackup（>100GB 必选）。生产必加 `--single-transaction`（不锁表，InnoDB 用 MVCC）和 `--master-data=2`（记录 binlog 位点）。

### Q2：什么是 PITR？

Point-in-Time Recovery，时间点恢复。靠**全量备份 + 持续 binlog**：先恢复最近全量，再用 mysqlbinlog 重放到指定时间点。

### Q3：mysqldump 加 --single-transaction 的原理？

InnoDB 启动一致性事务（START TRANSACTION WITH CONSISTENT SNAPSHOT），dump 期间用 MVCC 读历史版本，**不阻塞业务写**。仅 InnoDB 有效，MyISAM 还得加 --lock-tables。

### Q4：Xtrabackup 怎么实现热备？

边拷数据文件、边记录 redo log。最后用 redo log 把"拷贝期间产生的修改"应用到副本，得到一致快照。所以 prepare 阶段是必须的。

### Q5：增量备份怎么做？

Xtrabackup 用 LSN 标记，下次只拷 LSN ≥ 上次的页。或者用 binlog 当增量——全量 + 持续 binlog 等同增量备份能力。

### Q6：误删了一张表怎么救？

如果有 binlog，PITR 恢复到误操作前一秒：
1. 新实例恢复最近全量
2. mysqlbinlog --stop-datetime 重放 binlog 到误操作前
3. 验证后导回主库

### Q7：什么情况下 PITR 救不了？

- binlog 没开 / 已删
- 全量备份损坏
- sync_binlog=0 主库崩 binlog 丢

### Q8：备份策略怎么定？

3-2-1 原则：3 份副本、2 种介质、1 份异地。互联网典型：每周全量 + 每日增量 + 实时 binlog 到对象存储 + 跨机房副本。

### Q9：备份多久验证一次？

每周自动恢复测试一次；每月做一次完整 PITR 演练；每季度做一次跨机房 DR 演练。**未验证的备份不算备份**。

### Q10：备份在主库还是从库做？

**从库**。主库备份占 IO 影响业务。生产典型架构是 1 主 + N 个业务从库 + 1 个备份专用从库。

## 十二、答题模板（60 秒话术）

> MySQL 备份分**逻辑**（mysqldump / mysqlpump）和**物理**（Percona Xtrabackup）。100GB 以下用 mysqldump，以上必须 Xtrabackup——速度差 10x。
>
> **mysqldump 必加** `--single-transaction`（InnoDB 用 MVCC 不锁表）和 `--master-data=2`（记录 binlog 位点供 PITR 用）。**Xtrabackup** 物理热备，prepare 阶段 apply redo log 得到一致快照，支持基于 LSN 的增量备份。
>
> **PITR（时间点恢复）**靠**全量备份 + 持续 binlog**：先恢复最近全量到新实例，再用 mysqlbinlog 重放 binlog 到指定时间点（`--stop-datetime` 或 `--stop-position`），验证后切回主库。GTID 模式下用 `--exclude-gtids` 精准跳过误操作事务。
>
> 生产策略遵循 **3-2-1 原则**：3 份副本、2 种介质、1 份异地。每周全量 + 每日增量 + 实时 binlog 到对象存储；备份**永远在从库做**避免影响主库。
>
> 最容易被忽视的是**备份验证**——没恢复过的备份等于没有。每周自动恢复测试、每月 PITR 演练、每季度 DR 演练。生产铁律：`sync_binlog=1` 永远不设 0、binlog 保留 ≥ 全量周期 × 2、磁盘监控告警。
