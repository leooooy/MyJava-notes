# 反射与动态代理

> 反射是 Java 的"逃生舱"——绕过编译期类型检查，运行时操作类。**Spring / MyBatis / Hibernate / 序列化框架**全靠它。
>
> 面试要点：
> ① 反射四大件——**Class / Field / Method / Constructor**
> ② **反射性能**为什么慢、怎么优化
> ③ **JDK 动态代理 vs CGLIB** 区别——Spring AOP 选哪个
> ④ Method.invoke 内部做什么
> ⑤ 反射访问 private —— `setAccessible(true)` 的代价

---

## 一、反射是什么、解决什么问题

### 1.1 没有反射的世界

```java
User u = new User();
u.setName("Alice");
String name = u.getName();
```

→ 编译时**已经知道 User 类、setName 方法**——直接生成调用字节码。

### 1.2 反射的世界

```java
String className = config.get("entity.class");      // 从配置读类名
Class<?> clazz = Class.forName(className);
Object obj = clazz.getDeclaredConstructor().newInstance();
Method m = clazz.getMethod("setName", String.class);
m.invoke(obj, "Alice");
```

→ 编译时**完全不知道**有什么类、什么方法——**运行时动态决定**。

**典型应用**：

| 场景 | 用反射干什么 |
| --- | --- |
| Spring IoC | 根据配置/注解扫描类，反射 new + 注入 |
| MyBatis | ResultSet 转 POJO，反射 setter 注入 |
| Jackson | JSON 解析，反射赋值字段 |
| JUnit | 找 @Test 方法，反射调用 |
| Mockito | 修改私有字段，反射 setAccessible |
| 注解处理 | 扫描 @Override / @Autowired，反射读取 |

## 二、反射四大件

### 2.1 Class 对象

```java
// 三种获取 Class 的方式
Class<User> c1 = User.class;                    // 编译期已知类
Class<?> c2 = Class.forName("com.foo.User");    // 运行时根据字符串
Class<?> c3 = user.getClass();                  // 运行时根据实例

// Class 提供的能力
c1.getName();                  // 全限定名 com.foo.User
c1.getSimpleName();            // User
c1.getSuperclass();            // 父类
c1.getInterfaces();            // 接口
c1.getDeclaredFields();        // 所有字段（含 private）
c1.getFields();                // 仅 public 字段（含继承）
c1.getDeclaredMethods();       // 所有方法（含 private，仅本类）
c1.getDeclaredConstructors();  // 所有构造器
c1.getAnnotations();           // 注解
c1.isAssignableFrom(other);    // 类型关系
```

### 2.2 Constructor

```java
Constructor<User> ctor = User.class.getDeclaredConstructor(String.class, int.class);
ctor.setAccessible(true);                                  // 突破访问控制
User u = ctor.newInstance("Alice", 30);
```

### 2.3 Field

```java
Field nameField = User.class.getDeclaredField("name");
nameField.setAccessible(true);
nameField.set(user, "Alice");                              // 写
String name = (String) nameField.get(user);                // 读
```

### 2.4 Method

```java
Method m = User.class.getDeclaredMethod("setName", String.class);
m.setAccessible(true);
m.invoke(user, "Alice");                                   // 调用
```

## 三、反射的代价

### 3.1 三个维度的开销

| 开销 | 来源 |
| --- | --- |
| **API 调用本身** | getMethod / getField 要遍历比较签名 |
| **invoke 机制** | 多层包装 + 类型检查 + 数组装拆 |
| **JIT 优化失效** | 反射调用对 JIT 是黑盒，无法内联 |

### 3.2 反射性能为什么慢

`Method.invoke()` 内部做的事：

```
1. 检查 accessible（如果没 setAccessible(true) 还要做权限检查）
2. 检查参数类型匹配（强制每参数转 Object，调用时还要拆）
3. 反射调用前 15 次走 native 实现
4. 第 16 次开始 JVM 自动生成字节码 stub（GeneratedMethodAccessor）—— 此后接近原生
5. JIT 难以内联反射调用（看不见目标方法）
```

**实测**：

| 调用方式 | 相对耗时 |
| --- | --- |
| 直接调用 | 1x |
| 反射 invoke（缓存 Method）| ~3-10x |
| 反射 invoke（每次 getMethod） | ~100x |
| Class.forName + newInstance | ~50x |

→ **生产规范**：反射 Method / Field 一定要**缓存**，不要每次循环里 getMethod。

### 3.3 setAccessible(true) 的代价

```java
field.setAccessible(true);    // 关闭安全检查
```

**收益**：每次访问跳过权限检查，性能 **提升 5-10x**。
**代价**：

- 每次调 setAccessible 本身有开销
- JDK 9+ **强封装**（模块化）下，访问 java.base 内部字段会警告 / 失败
- JDK 17+ 默认 strong encapsulation

**生产做法**：

```java
private static final Field FIELD;
static {
    try {
        FIELD = User.class.getDeclaredField("name");
        FIELD.setAccessible(true);     // 静态块只调一次
    } catch (Exception e) { throw new RuntimeException(e); }
}
```

## 四、动态代理是什么

代理模式：用一个**代理类**包装目标对象，**在调用前后插入额外逻辑**（日志、事务、权限）。

```
不用代理：
    Caller → UserService.save()

用代理：
    Caller → UserServiceProxy.save()
                       │
                       ├── 前置：开启事务
                       ├── 调用：UserService.save()
                       └── 后置：提交事务
```

**静态代理**：手写代理类，每个目标类要写一个代理——**冗余**。
**动态代理**：运行时**生成**代理类——一份代码代理任意类。

## 五、JDK Proxy vs CGLIB（面试必考）

### 5.1 JDK Proxy（基于接口）

```java
public interface UserService {
    void save(User u);
}

public class UserServiceImpl implements UserService {
    public void save(User u) { System.out.println("save " + u); }
}

// 动态代理
UserService proxy = (UserService) Proxy.newProxyInstance(
    UserService.class.getClassLoader(),
    new Class[] { UserService.class },                 // 必须是接口
    (proxyObj, method, args) -> {                      // InvocationHandler
        System.out.println("before");
        Object result = method.invoke(target, args);
        System.out.println("after");
        return result;
    });

proxy.save(new User());
```

**核心**：

- 目标类**必须实现接口** —— JDK Proxy 生成的代理类继承 `Proxy` + 实现目标接口
- `InvocationHandler.invoke` 是统一拦截入口

**生成的代理类**（伪代码）：

```java
class $Proxy0 extends Proxy implements UserService {
    public void save(User u) {
        h.invoke(this, m1, new Object[] { u });    // 转发到 InvocationHandler
    }
}
```

### 5.2 CGLIB（基于继承）

```java
Enhancer enhancer = new Enhancer();
enhancer.setSuperclass(UserServiceImpl.class);             // 继承目标类
enhancer.setCallback(new MethodInterceptor() {
    public Object intercept(Object obj, Method method, Object[] args, MethodProxy proxy) {
        System.out.println("before");
        Object result = proxy.invokeSuper(obj, args);     // 调父类方法
        System.out.println("after");
        return result;
    }
});

UserServiceImpl proxy = (UserServiceImpl) enhancer.create();
proxy.save(new User());
```

**核心**：

- 目标类**不需要接口**——CGLIB 用字节码生成**目标类的子类**
- 继承的局限：**不能代理 `final` 类、`final` 方法、`private` 方法**

### 5.3 对比表（背）

| 维度 | JDK Proxy | CGLIB |
| --- | --- | --- |
| 实现机制 | 反射生成 Proxy 子类 | ASM 生成目标类子类 |
| 是否需要接口 | ✅ 必须 | ❌ 不需要 |
| 能代理 final | ❌（接口里没 final） | ❌（继承不了 final） |
| 能代理 private | ❌（接口没 private） | ❌（子类访问不到） |
| 性能（创建） | 快 | 慢（生成字节码） |
| 性能（调用） | 反射 invoke，慢 | FastClass 优化，**接近原生** |
| 内置依赖 | JDK 自带 | 第三方（Spring 内置） |

### 5.4 CGLIB 的 FastClass 优化

CGLIB 不用反射调父类方法——用 **FastClass 索引法**：

```java
// 生成的伪代码
class UserServiceImpl$$FastClassByCGLIB {
    public Object invoke(int methodIndex, Object obj, Object[] args) {
        switch (methodIndex) {
            case 0: ((UserServiceImpl)obj).save((User)args[0]); return null;
            case 1: return ((UserServiceImpl)obj).find((Long)args[0]);
        }
    }
}
```

→ **switch + 直接调用**——比反射 Method.invoke 快 10x。

## 六、Spring AOP 的代理选型

```java
// SpringBoot 默认配置
spring.aop.proxy-target-class=false    // 默认 false：有接口走 JDK，无接口走 CGLIB
                                       // 设 true：强制走 CGLIB
```

**默认行为**：

```
目标类有接口 → JDK Proxy
目标类无接口 → CGLIB
```

**Spring Boot 2.x 之后**：默认 **强制 CGLIB**（`proxy-target-class=true`）。原因：

1. 一个 JDK Proxy 只能代理接口里的方法 → 目标类自身的非接口方法走不到 AOP
2. 不少老代码注入 UserServiceImpl 而不是 UserService → JDK Proxy 不能强转
3. CGLIB 性能现在已经接近 JDK Proxy

### 6.1 self-invocation 失效

```java
@Service
class UserService {
    @Transactional
    public void save() { update(); }       // 1
    
    @Transactional
    public void update() { ... }           // 2
}

userService.save();    // 1、2 都在同一事务？
```

**答案：不在同一事务**。

`save` 调 `update` 是**对象内部 this 调用**，不走代理 → `@Transactional` 不生效。

**修复**：

- 自注入：`@Autowired UserService self; self.update();`
- 拆服务：把 update 移到另一个 Service
- AspectJ（编译期织入，绕过代理）

## 七、注解读取

### 7.1 注解的存活范围

```java
@Retention(RetentionPolicy.SOURCE)       // 源码（不进 class）
@Retention(RetentionPolicy.CLASS)        // 进 class，不进运行时（默认）
@Retention(RetentionPolicy.RUNTIME)      // 运行时可见 ← 反射能读
```

→ 想用反射读注解，必须 `RUNTIME`。

### 7.2 反射读注解

```java
@Service
class UserService { }

UserService.class.isAnnotationPresent(Service.class);    // true
Service ann = UserService.class.getAnnotation(Service.class);
ann.value();                                             // 注解值
```

### 7.3 自定义注解

```java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface Loggable {
    String value() default "";
    boolean printArgs() default false;
}

@Loggable(value = "user-update", printArgs = true)
public void update() { ... }

// 反射处理
for (Method m : clazz.getDeclaredMethods()) {
    if (m.isAnnotationPresent(Loggable.class)) {
        Loggable l = m.getAnnotation(Loggable.class);
        // 织入逻辑
    }
}
```

## 八、生产踩坑

### 8.1 反射调用没缓存

**现象**：循环里 `getMethod` + `invoke`，CPU 飙高。
**根因**：`getMethod` 是 O(方法数) 遍历，每次都走签名匹配。
**修复**：把 Method 抽成 static final 缓存：

```java
private static final Method M = User.class.getDeclaredMethod("save");
static { M.setAccessible(true); }
```

### 8.2 反射拿不到泛型类型

```java
List<User> list = ...;
list.getClass();              // class java.util.ArrayList
list.getClass().getTypeParameters();    // List<E> 的 E，不是 User
```

→ 实例的泛型擦除，拿不到。要拿必须**类继承时固化**：

```java
class UserList extends ArrayList<User> { }    // 这里 User 写死在父类签名里
ParameterizedType pt = (ParameterizedType) UserList.class.getGenericSuperclass();
pt.getActualTypeArguments()[0];    // class User ✅
```

参见 [泛型 - 反射坑](./泛型.md#73-泛型擦除导致的反射坑)。

### 8.3 setAccessible 在 JDK 17 失败

**现象**：升级到 JDK 17 后，反射访问报 `InaccessibleObjectException`。
**根因**：JDK 17 默认 strong encapsulation，反射访问 `java.base` 等内部模块的 private 字段被禁。
**修复**：

- 临时：`--add-opens java.base/java.lang=ALL-UNNAMED`
- 长期：升级到合规库（Spring 6+、Hibernate 6+ 都已合规）

### 8.4 CGLIB 代理 final 类失败

**现象**：Spring AOP 报 `Cannot subclass final class`。
**根因**：CGLIB 通过继承生成代理，**不能代理 final 类 / final 方法**。
**修复**：去掉 final，或改用接口 + JDK Proxy。

### 8.5 反射 setAccessible 影响 JIT

**现象**：性能 profile 发现 `Method.invoke` 始终在热点。
**根因**：反射调用 JIT 难以内联，即便 setAccessible 也只是省了权限检查。
**修复**：

- 用 MethodHandle（JDK 7+）代替反射，**JIT 可识别可内联**
- LambdaMetafactory 生成 lambda（JDK 8+）
- ByteBuddy / ASM 生成字节码

## 九、面试高频追问

### Q1：反射是什么？

运行时**动态获取类信息、操作类成员**的能力。Java 在编译期生成 .class 文件时把类元信息也写入字节码，运行时 ClassLoader 加载后这些元信息可以被读出，反射就是读 + 改这些元信息的 API。

### Q2：反射性能为什么慢？

- API 调用要遍历方法 / 字段做签名匹配
- invoke 内部多层包装 + 参数装拆
- JIT 难以内联反射调用（黑盒）
- setAccessible 默认每次有权限检查

**缓存 Method + setAccessible(true) 后开销可控**，但仍不如直接调用。

### Q3：JDK Proxy 和 CGLIB 区别？

JDK Proxy 基于**接口**，生成实现目标接口的 Proxy 子类，反射调用，性能稍慢；CGLIB 基于**继承**，ASM 生成目标类子类，**FastClass 优化**接近原生。CGLIB 不能代理 final 类 / final 方法。

### Q4：Spring AOP 默认用哪个？

老版本：有接口走 JDK Proxy、无接口走 CGLIB。
**Spring Boot 2.x+：默认强制 CGLIB**（`proxy-target-class=true`）——为了避免接口外的方法不被 AOP 代理。

### Q5：self-invocation（this 调用）为什么 AOP 失效？

代理只在外部调用入口拦截，对象内部 `this.xxx()` 不走代理。修复：自注入 + `self.xxx()`，或拆服务。

### Q6：Method.invoke 内部做什么？

参数检查 + 类型转换 → 委托 MethodAccessor 执行。前 15 次走 native（NativeMethodAccessor），第 16 次起 JVM 生成字节码 stub（GeneratedMethodAccessor），后续接近原生。

### Q7：怎么减少反射开销？

- 缓存 Method / Field（static final）
- setAccessible(true)
- 用 **MethodHandle**（JDK 7+，JIT 可内联）
- 用 **LambdaMetafactory** 生成 lambda
- 字节码生成（ByteBuddy / ASM）

### Q8：注解怎么用反射读？

注解必须 `@Retention(RUNTIME)` 才能反射读。`clazz.getAnnotation(X.class)` 拿到注解实例，`isAnnotationPresent(X.class)` 判断是否存在。

### Q9：反射能修改 final 字段吗？

`String` 等类的 final 字段**理论上可改**（setAccessible + Field.set），但：

- JIT 可能把 final 字段内联，改了后续读不到
- JDK 9+ 强封装下访问 java.base 内部字段被禁
- 不要这么干（业务规范）

### Q10：CGLIB 和 ASM 关系？

ASM 是底层字节码操作库；CGLIB 是基于 ASM 的高层代理生成库。Spring 内置 CGLIB（重打包到 `org.springframework.cglib`）。

## 十、答题模板（60 秒话术）

> 反射是 Java 的"逃生舱"——运行时动态拿到类信息、操作字段方法。**Spring IoC、MyBatis、Jackson、JUnit、Mockito** 全靠它。
>
> 四大件：**Class / Constructor / Field / Method**。`Method.invoke` 内部前 15 次走 native，第 16 次起 JVM 生成字节码 stub 接近原生——但 JIT **无法内联**反射调用。生产规范：**Method / Field 静态缓存 + setAccessible(true)**，否则每次循环里 getMethod 性能爆炸。
>
> 动态代理两大流派：
> - **JDK Proxy**：基于接口，反射 invoke
> - **CGLIB**：基于继承，ASM 生成子类 + FastClass 优化，**接近原生但不能代理 final**
>
> Spring AOP **2.x+ 默认强制 CGLIB**（避免 self-invocation 和接口外方法不代理）。**self-invocation（this 调用）AOP 失效**——必须自注入或拆服务。
>
> 高性能场景反射可以替换为 **MethodHandle**（JIT 可内联）、**LambdaMetafactory**、或 **ByteBuddy / ASM** 字节码生成。
>
> JDK 9+ 模块化默认 **强封装**——反射访问 java.base 内部字段会失败，需要 `--add-opens` 或升级到合规库。
