# 异常体系

> 异常是工程功底题——不会问你"什么是异常"，会问：
> ① **Throwable / Error / Exception / RuntimeException** 的层级
> ② **Checked vs Unchecked** —— Java 独有的设计，是优点还是缺点
> ③ **try-finally 里 return** 的执行顺序——经典面试坑
> ④ **try-with-resources** 怎么实现的、抑制异常（suppressed）是什么
> ⑤ **生产里异常该怎么用**——异常吞掉 / 当流程控制 / 包了又包

---

## 一、Throwable 体系全景

```
                        Throwable
                       /         \
                  Error           Exception
                  /                /         \
            VirtualMachineError   IOException   RuntimeException
            OutOfMemoryError      SQLException  /        \
            StackOverflowError    ...           NullPointerException
            ...                                 IllegalArgumentException
                                                ClassCastException
                                                ConcurrentModificationException
                                                ...

            ←——— Checked ———→  ←——— Unchecked ———→
```

### 1.1 三大流派

| 类别 | 是否检查 | 谁抛 | 怎么处理 |
| --- | --- | --- | --- |
| **Error** | ❌ Unchecked | JVM | 一般不 catch，直接重启 |
| **Checked Exception** | ✅ 编译器强制处理 | 业务 / API | try-catch 或 throws |
| **RuntimeException** | ❌ Unchecked | 业务 | 可处理可不处理 |

### 1.2 Throwable 自身的方法

```java
public class Throwable {
    public String getMessage();
    public Throwable getCause();         // 异常链
    public StackTraceElement[] getStackTrace();
    public void addSuppressed(Throwable);   // try-with-resources 用
    public Throwable[] getSuppressed();
    public void printStackTrace();
}
```

> 注意：`getStackTrace()` 是**重操作**——每次调用都要分析栈。生产高频路径不要随便取栈。

## 二、Checked vs Unchecked

### 2.1 Checked Exception

```java
public void readFile() throws IOException {     // 必须声明
    Files.readAllLines(Path.of("a.txt"));
}

// 调用方必须 catch 或继续 throws
try { readFile(); }
catch (IOException e) { ... }
```

→ **编译器强制要求**：要么 catch，要么继续 throws。

**典型 Checked**：`IOException`、`SQLException`、`InterruptedException`、`ClassNotFoundException`、`FileNotFoundException`。

### 2.2 Unchecked Exception

```java
RuntimeException e = new RuntimeException("oops");
throw e;     // 不需要声明、不需要 catch
```

**典型 Unchecked**：`NullPointerException`、`IllegalArgumentException`、`IllegalStateException`、`ClassCastException`、`ConcurrentModificationException`、`NumberFormatException`。

### 2.3 Error

```java
OutOfMemoryError ←  堆溢出
StackOverflowError ← 栈溢出
NoClassDefFoundError ← 类找不到
```

**生产建议**：

- Error **一般不 catch**——发生说明程序根本撑不下去（OOM / SOF）
- 但有时需要捕获**最外层** Error 做一次清理（例如关闭连接、写监控）

```java
public static void main(String[] args) {
    try {
        runApp();
    } catch (Throwable t) {        // 最外层兜底
        log.error("FATAL", t);
        sendAlert(t);
        System.exit(1);
    }
}
```

### 2.4 Checked 的争议

**Java 的设计本意**：Checked Exception 让编译器强制业务处理可恢复异常。

**实际问题**：

1. **接口层级问题**：每个抽象层都要声明、捕获或转换 → 大量样板代码
2. **Lambda 不友好**：`Stream.map(Files::read)` 编译报错（`read` 抛 IOException）
3. **业务很多时候根本无法恢复**——只能 try-catch-rethrow，毫无意义

→ **现代趋势**：**包成 RuntimeException**：

```java
try {
    Files.readString(path);
} catch (IOException e) {
    throw new UncheckedIOException(e);     // JDK 8 已经提供
}

// 或自定义
try { ... }
catch (SQLException e) {
    throw new DataAccessException("查询失败", e);    // Spring 风格
}
```

Spring、Hibernate 等框架**都把 Checked 全包成 Unchecked** ——这是工程上的事实标准。

### 2.5 什么时候抛 RuntimeException

| 场景 | 推荐 |
| --- | --- |
| 业务校验（参数错、状态错） | `IllegalArgumentException` / `IllegalStateException` |
| 资源 / IO / 数据库失败 | 自定义 RuntimeException 子类（DataAccessException） |
| 业务逻辑错（金额超额、库存不足） | 自定义业务异常（BusinessException） |
| 编程错（不该出现的状态） | `IllegalStateException` |
| 显式给调用方信号"必须处理" | Checked Exception（少数场景） |

## 三、try-catch-finally

### 3.1 执行顺序

```java
try {
    // ① 业务代码
} catch (Exception e) {
    // ② 异常处理
} finally {
    // ③ 一定执行（即使 try / catch 里 return）
}
```

### 3.2 多 catch 顺序

```java
try { ... }
catch (FileNotFoundException e) { ... }    // 子类先
catch (IOException e) { ... }              // 父类后
catch (Exception e) { ... }
```

子类异常必须放父类前，否则**编译报错**（unreachable catch block）。

### 3.3 multi-catch（JDK 7+）

```java
try { ... }
catch (IOException | SQLException e) {     // 多类型一起 catch
    log.error("err", e);
}
```

注意：multi-catch 里 e 是 effectively final，不能重新赋值。

## 四、try-with-resources

### 4.1 语法

```java
try (FileInputStream in = new FileInputStream("a.txt");
     FileOutputStream out = new FileOutputStream("b.txt")) {
    // 使用资源
} // 自动调用 close
```

### 4.2 实现原理

要求资源实现 `AutoCloseable` 接口（包括 `Closeable`）：

```java
public interface AutoCloseable {
    void close() throws Exception;
}
```

编译器会**自动展开**为：

```java
FileInputStream in = new FileInputStream("a.txt");
Throwable primary = null;
try {
    FileOutputStream out = new FileOutputStream("b.txt");
    try {
        // 使用资源
    } catch (Throwable t) {
        primary = t;
        throw t;
    } finally {
        if (primary != null) {
            try { out.close(); } catch (Throwable t) { primary.addSuppressed(t); }
        } else {
            out.close();
        }
    }
} catch (Throwable t) { ... } finally { ... 同样处理 in ... }
```

→ 复杂得吓人。这就是为什么 try-with-resources 是**重大的工程胜利**——把这堆模板代码自动化了。

### 4.3 关闭顺序（必背）

资源**按声明的反顺序关闭**：

```java
try (A a = new A(); B b = new B(); C c = new C()) {
    // ...
}
// 关闭顺序：c → b → a
```

类似栈——**先开后关**。

### 4.4 抑制异常（Suppressed Exception）

经典坑：

```java
try {
    // 业务抛 BusinessException
} finally {
    // close 抛 IOException 把业务异常覆盖了 ⚠
}
```

try-with-resources **解决**这个：业务抛主异常 + close 异常通过 `addSuppressed` 附加到主异常里：

```java
try {
    throw new RuntimeException("primary");
} finally {
    // close 抛 IOException
}

// 打印：
// Exception in thread "main" RuntimeException: primary
// 	Suppressed: IOException: close failed
```

→ **不丢任何异常信息**。这是 try-with-resources 的最大价值。

## 五、try-finally-return 经典坑

### 5.1 finally 总是执行

```java
public int test() {
    try {
        return 1;
    } finally {
        return 2;        // ⚠ 真的会 return 2 覆盖 1
    }
}
test();    // 返回 2
```

**编译后字节码**：try 的 return 1 先把 1 推栈，但还没执行 ireturn，跳到 finally 把 2 推栈，finally 的 ireturn 执行——**返回 2**。

→ **生产规范：finally 不要 return**——会吞掉 try 的返回值和异常。

### 5.2 finally 修改返回值

```java
public int test() {
    int x = 1;
    try {
        return x;        // 已经把 x 的值（1）推上返回栈
    } finally {
        x = 2;           // ⚠ 这里改的是局部变量 x，不影响已推栈的返回值
    }
}
test();    // 返回 1
```

**对照（引用类型）**：

```java
public List<Integer> test() {
    List<Integer> list = new ArrayList<>();
    try {
        list.add(1);
        return list;     // 把 list 引用推栈
    } finally {
        list.add(2);     // ⚠ 这里改的是引用指向的对象——会反映到返回值
    }
}
test();    // 返回 [1, 2]
```

→ finally 改**值类型**变量不影响返回值；改**引用指向的对象**会反映到返回值。

### 5.3 finally 抛异常

```java
public void test() {
    try {
        throw new RuntimeException("primary");
    } finally {
        throw new RuntimeException("finally");    // ⚠ primary 异常被吞
    }
}
```

→ finally 的异常**覆盖 try 的异常**——正常 catch 看不到 primary。
→ try-with-resources **不会**这样——会用 suppressed 附加。

## 六、性能：异常不要当流程控制

### 6.1 异常的代价

```java
new Throwable();        // 创建时调用 fillInStackTrace —— 慢
e.getStackTrace();      // 解析栈 —— 慢
```

异常的栈跟踪生成涉及：

1. 遍历所有栈帧
2. 把帧信息（class、method、line）拷到 StackTraceElement[]
3. 分配字符串

**实测**：throw + catch 一次 RuntimeException ≈ 1~5 微秒（看栈深度）。

### 6.2 别这么写

```java
// ❌ 用异常做流程控制
try {
    return Integer.parseInt(s);
} catch (NumberFormatException e) {
    return 0;        // s 不是数字
}

// ✅
if (s != null && s.matches("-?\\d+")) {
    return Integer.parseInt(s);
}
return 0;
```

**最经典反例**：用 `IndexOutOfBoundsException` 跳出循环、用 `NullPointerException` 当判空——**性能掉一个数量级**。

### 6.3 优化技巧

**关闭栈跟踪**（仅业务异常）：

```java
public class FastException extends RuntimeException {
    @Override
    public synchronized Throwable fillInStackTrace() {
        return this;     // 不收集栈
    }
}
```

→ 不需要栈信息的高频业务异常可以这么写——**性能提升 10x**。生产里限流异常常这么用。

## 七、生产踩坑

### 7.1 异常被吞掉

```java
try {
    // 业务
} catch (Exception e) {
    log.error("error");      // ⚠ 没传 e，栈丢了
}

// 或者更糟
try { ... } catch (Exception e) { /* 啥都没干 */ }   // 完全静默
```

**修复**：

```java
log.error("error", e);       // 一定要传异常对象
log.error("error: {}", e.getMessage(), e);
```

业务允许的话**绝对不要 catch 后什么也不做**——出问题完全无法定位。

### 7.2 catch Exception 范围太大

```java
try {
    // 200 行业务
} catch (Exception e) {        // ⚠ 业务的 RuntimeException 和 IO 的 IOException 都进来了
    log.error("err", e);
    return Result.fail();
}
```

**问题**：

- 业务校验异常（IllegalArgumentException）和系统异常一起处理——丢失语义
- catch Exception 把 InterruptedException 也吞了——破坏中断协议

**修复**：

```java
try { ... }
catch (BusinessException e) { return Result.bizFail(e.getCode()); }
catch (IOException e) { return Result.systemFail(); }
catch (InterruptedException e) {
    Thread.currentThread().interrupt();   // 补回中断标志
    throw new RuntimeException(e);
}
```

### 7.3 InterruptedException 不补中断

```java
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    log.error("interrupted", e);    // ⚠ 没补回中断
}
```

**根因**：catch InterruptedException 时，**JVM 已清除中断标志**。如果不补，外层代码看不到中断信号。

**修复**：

```java
catch (InterruptedException e) {
    Thread.currentThread().interrupt();   // 补回
    // 然后抛或返回
}
```

### 7.4 异常包了又包，丢失原始异常

```java
try { /* 数据库操作 */ }
catch (SQLException e) {
    throw new DataAccessException("db fail");    // ⚠ 没传 cause
}
```

**修复**：永远传 cause：

```java
throw new DataAccessException("db fail", e);
```

否则线上日志只有"db fail"，根本不知道是哪个 SQL 错。

### 7.5 自定义异常没继承 RuntimeException

```java
public class BusinessException extends Exception { }   // ⚠ Checked
```

→ 整个调用链全都要 throws，污染所有方法签名。

**修复**：99% 的业务异常应该 **extends RuntimeException**。

### 7.6 finally 抛异常覆盖 try 的异常

见 [5.3](#53-finally-抛异常)。**修复**：finally 里用 try-catch 包住可能抛异常的代码，或者用 try-with-resources。

## 八、面试高频追问

### Q1：异常体系画一下？

Throwable → Error / Exception；Exception → Checked（IOException 等）/ RuntimeException（NPE / IAE 等）。Error 一般不 catch，Checked 编译强制处理，RuntimeException 可选处理。

### Q2：Checked 和 Unchecked 区别？

Checked：编译期强制 try 或 throws，典型 IOException / SQLException；Unchecked：RuntimeException 及其子类、Error，编译不强制。**现代实践**几乎都包成 Unchecked（Spring 风格）——Checked 让 Lambda 难写、调用链污染。

### Q3：Error 和 Exception 区别？

Error 是 JVM 层面的严重故障（OOM / SOF），程序通常无法恢复，**一般不 catch**。Exception 是程序级问题，可处理。但 Error 在最外层兜底监控时**也可以 catch Throwable**。

### Q4：try-finally 里 finally 一定会执行吗？

几乎一定。例外：`System.exit(0)` 在 try 里、JVM crash、守护线程被杀。

### Q5：finally 改返回值会怎样？

值类型变量：try 已把值推栈，finally 改的是局部变量，**返回值不变**。
引用类型：返回的是引用，finally 改对象状态会反映到返回值。

### Q6：finally 里 return 会怎样？

**会覆盖 try / catch 的 return 和异常**——生产严禁这么写。

### Q7：try-with-resources 怎么实现的？

编译器展开为嵌套 try-finally，关闭按反序，**用 addSuppressed** 把 close 异常附加到业务异常上——避免互相覆盖。要求资源实现 AutoCloseable。

### Q8：异常会影响性能吗？

会。`new Throwable()` 调用 fillInStackTrace 收集栈——10 万次创建在微秒级。**不要用异常做流程控制**。高频业务异常可以重写 fillInStackTrace 返回 this 跳过栈收集。

### Q9：怎么自定义异常？

99% 场景 **extends RuntimeException**：

```java
public class BusinessException extends RuntimeException {
    private final String code;
    public BusinessException(String code, String msg) {
        super(msg); this.code = code;
    }
    public BusinessException(String code, String msg, Throwable cause) {
        super(msg, cause); this.code = code;
    }
}
```

**永远提供带 cause 的构造器**——避免丢失原始异常。

### Q10：catch 之后该 throw 还是 swallow？

视情况：

- 业务层（Controller / Service）：catch + 返回 Result，**不要再抛**
- 框架 / 工具层：catch + 包成业务异常 throw（带 cause）
- 中间层：**不要 catch**——让它向上冒泡到统一处理

最忌讳：`catch + log + return null`——上层不知道出错，业务静默错误。

## 九、答题模板（60 秒话术）

> Throwable 分两支：**Error**（JVM 故障，一般不 catch）和 **Exception**。Exception 又分 **Checked**（编译强制处理，典型 IOException）和 **Unchecked**（RuntimeException，编译不强制）。
>
> Checked 设计的本意是强制处理可恢复异常，但实际**污染调用链、Lambda 不友好**——现代框架（Spring / Hibernate）都包成 Unchecked。**业务异常 99% 都该 extends RuntimeException**。
>
> try-finally：finally 一定执行（除非 System.exit / JVM crash）。**finally 里改值类型变量不影响 try 的返回值**（值已推栈），改引用对象状态影响。**finally 里 return 会覆盖 try 的 return 和异常——生产严禁**。
>
> **try-with-resources**：要求 AutoCloseable，编译器展开为嵌套 try-finally，**按反序关闭**；业务异常 + close 异常用 **addSuppressed** 附加，**不丢任何异常信息**。
>
> 性能上 **异常不要当流程控制**——`new Throwable()` 收集栈是慢的；高频业务异常可以重写 fillInStackTrace 跳过栈。生产几个原则：**catch 后日志一定传 e**、**InterruptedException 必须补回中断标志**、**自定义异常带 cause 构造器**。
