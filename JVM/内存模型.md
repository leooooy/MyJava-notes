# Java 内存模型 JMM

> ⚠️ **千万别和"运行时数据区"混了**——它们完全是两回事：
> - [运行时数据区](./内存区域.md)：JVM 物理上的内存划分（堆 / 栈 / 方法区 / ...）
> - **JMM**：定义**线程间共享变量的访问规则**，是一套规范，不是物理内存
>
> 本篇解决：① 为什么需要 JMM；② 主内存 / 工作内存的抽象；③ **三大特性**（原子性 / 可见性 / 有序性）；④ 重排序的三种来源；⑤ **happens-before** 8 条规则；⑥ volatile / synchronized / final 在 JMM 层的语义。
>
> **面试链路**：JMM → volatile → 重排序 → happens-before → DCL 单例 → 内存屏障。

---

## 一、为什么要有 JMM

### 1.1 硬件层面的问题

```
CPU0 ─┐                       ┌─ CPU1
   寄存器 ─ L1 Cache ─ L2 Cache ─ L3 Cache ─ 主内存（RAM）
```

CPU 与内存之间速度差 **几个数量级**——CPU 不能等内存，所以引入多级缓存。

**带来的问题**：
1. **缓存一致性**：多个 CPU 缓存同一个变量，谁改了别人不知道
2. **指令重排**：CPU 流水线 / 编译器为提升性能会乱序执行
3. **内存屏障语义跨平台不一致**：x86 比 ARM 强多了

### 1.2 JMM 的目的

> Java 想"一次编写，到处运行"——不能让程序员针对 x86 / ARM / PowerPC 写不同代码。
>
> **JMM 屏蔽底层硬件差异**，给程序员一套**统一的内存访问规则**。

## 二、主内存 vs 工作内存（抽象模型）

```
┌────────────── 主内存 Main Memory ─────────────┐
│   所有共享变量（堆中的实例字段、静态字段、数组元素）│
└──────────────────────────────────────────────┘
         ↑               ↑               ↑
       read/load      write/store     read/load
         ↓               ↓               ↓
┌─────────┐       ┌─────────┐       ┌─────────┐
│线程1工作内存│   │线程2工作内存│   │线程3工作内存│
│  变量副本   │   │  变量副本   │   │  变量副本   │
└─────────┘       └─────────┘       └─────────┘
```

**关键约束**：
1. 所有共享变量存在**主内存**
2. 每条线程有自己的**工作内存**（实际对应 CPU 寄存器、缓存）
3. 线程操作变量必须先读到工作内存，改完写回主内存
4. 线程之间**不能直接访问**对方工作内存——只能通过主内存通信

> ⚠️ 这是**抽象模型**，不是 JVM 内存区域里的"堆和栈"。工作内存可能对应寄存器、L1/L2 Cache，主内存是 RAM。

### 2.1 8 个原子操作（了解即可）

JMM 规定了线程与主内存交互的 8 个底层操作：

| 操作 | 作用对象 | 含义 |
| --- | --- | --- |
| `lock` | 主内存 | 标记变量为线程独占 |
| `unlock` | 主内存 | 释放独占 |
| `read` | 主内存 → 工作内存 | 把变量值读到工作内存（不立即给执行引擎） |
| `load` | 工作内存 | 把 read 来的值放入变量副本 |
| `use` | 工作内存 → 执行引擎 | 把副本传给执行引擎 |
| `assign` | 执行引擎 → 工作内存 | 引擎计算结果赋给副本 |
| `store` | 工作内存 → 主内存 | 把副本传到主内存（不立即写） |
| `write` | 主内存 | 把 store 的值写到主内存的变量 |

**约束**：
- read 和 load 必须连续，store 和 write 必须连续（中间可有别的指令但不能拆开成对）
- 不允许丢弃 assign（变量值在工作内存改了必须同步回主内存）

> JDK 1.5 之后 JMM 用 happens-before 规则替代了这 8 个操作的描述方式——更易理解。

## 三、三大特性（必背）

### 3.1 原子性（Atomicity）

操作不可被中断、要么全做要么全不做。

| 操作 | 是否原子 |
| --- | --- |
| `int i = 0;` | ✅ 原子 |
| `i = 5;` | ✅ 基本类型赋值原子 |
| `i++` | ❌ 非原子（拆 load + add + store 三步） |
| `long l = 0L;`（32 位 JVM） | ❌ 非原子（高 32 / 低 32 分两次） |
| `long l = 0L;`（64 位 JVM） | ✅ 原子 |
| `synchronized` 块 | ✅ 块内原子 |
| `Atomic*` 类（CAS） | ✅ 原子 |

**保证原子性的手段**：
- `synchronized`
- `Lock`（ReentrantLock 等）
- `Atomic*` 类（基于 CAS）

### 3.2 可见性（Visibility）

一个线程修改了共享变量，其他线程能立刻看到。

**为什么默认没可见性**：
- CPU 缓存：线程 1 改了，只在自己 L1 里，线程 2 还看到主内存旧值
- 编译器优化：可能把变量优化到寄存器，根本不写回主内存

**保证可见性的手段**：
- `volatile`：写后立即刷主内存，读前从主内存重新加载
- `synchronized`：解锁前必须把变量同步回主内存
- `final`：构造完成后所有线程能看到正确的 final 字段

### 3.3 有序性（Ordering）

代码执行顺序与源码一致。

**为什么会乱序**：见下一节"重排序"。

**保证有序性的手段**：
- `volatile`：禁止特定的指令重排（插入内存屏障）
- `synchronized`：单线程内串行（happens-before 监视器锁规则）

## 四、重排序的三种来源

```
源码          ─┐
              ├─ ① 编译器重排序
JVM 字节码    ─┘
              ─┐
              ├─ ② 指令级重排序（CPU 流水线）
机器指令      ─┘
              ─┐
              ├─ ③ 内存系统重排序（CPU 写缓冲 / Invalidate Queue）
最终内存效果   ─┘
```

| 类型 | 主体 | 例子 |
| --- | --- | --- |
| ① 编译器重排序 | javac / JIT | 不影响单线程语义的前提下调整指令顺序 |
| ② 指令级并行重排序 | CPU | 没有数据依赖的指令乱序执行（流水线） |
| ③ 内存系统重排序 | CPU + 缓存 | Store Buffer、Invalidate Queue 导致的"延迟可见" |

**JMM 通过禁止特定重排序 + 插入内存屏障**，给程序员稳定语义。

### 4.1 经典反例：DCL 单例必须用 volatile

```java
class Singleton {
    private static volatile Singleton instance;   // ⚠️ volatile 必不可少
    
    public static Singleton getInstance() {
        if (instance == null) {                    // ① 第一次检查（无锁）
            synchronized (Singleton.class) {
                if (instance == null) {            // ② 第二次检查（有锁）
                    instance = new Singleton();    // ③ 这里有重排序坑
                }
            }
        }
        return instance;
    }
}
```

`new Singleton()` 三步：
1. 分配内存
2. 初始化对象
3. 把引用赋给 instance

**没 volatile 时**，可能被重排成 1 → 3 → 2：另一线程在 ① 处看到 `instance != null`，但对象还没初始化完 → **空对象**。

`volatile` 在写 instance 前插 StoreStore + LoadStore 屏障，禁止 2/3 重排。

## 五、happens-before（核心）

> JMM 给程序员的**承诺**：如果 A happens-before B，那么 A 的结果对 B 可见，且 A 看起来在 B 之前发生。

⚠️ **happens-before 不等于物理上"先发生"**——它只是保证可见性 + 顺序。

### 5.1 八条规则（必背）

| # | 规则 | 含义 |
| --- | --- | --- |
| 1 | **程序顺序规则** | 单线程内，前面的操作 happens-before 后面 |
| 2 | **监视器锁规则** | unlock happens-before 后续的 lock（同一锁） |
| 3 | **volatile 规则** | volatile 写 happens-before 后续的 volatile 读 |
| 4 | **传递性** | A→B 且 B→C，则 A→C |
| 5 | **线程启动规则** | `Thread.start()` happens-before 该线程的任何操作 |
| 6 | **线程终止规则** | 线程内任何操作 happens-before 其它线程检测到该线程结束（join 返回 / isAlive==false） |
| 7 | **线程中断规则** | `Thread.interrupt()` happens-before 被中断线程检测到中断 |
| 8 | **对象终结规则** | 对象初始化完成 happens-before finalize() |

### 5.2 用 happens-before 推可见性

```java
int a = 0;
volatile boolean flag = false;

// 线程 1
a = 1;              // ①
flag = true;        // ②   volatile 写

// 线程 2
if (flag) {         // ③   volatile 读
    System.out.println(a);   // ④  能看到 a == 1
}
```

推导：
- ① hb ②（程序顺序）
- ② hb ③（volatile 规则）
- ③ hb ④（程序顺序）
- 传递性：① hb ④ → 线程 2 的 ④ 看到 a=1 ✅

> volatile 的可见性传播能力比想象中强——它能把"前面的非 volatile 写"也带过去给读方看到（4.0 之后的内存语义增强）。

## 六、volatile 完整语义

### 6.1 两个保证

| 保证 | 实现 |
| --- | --- |
| **可见性** | 写：立刻 store + write 到主内存；读：每次必须 load |
| **有序性** | 插入内存屏障，禁止特定重排序 |

### 6.2 不保证的

- **不保证原子性**——`volatile int i; i++` 仍然不安全（i++ 是三步）
- **不保证互斥**——多个线程同时写 volatile，结果仍可能丢

### 6.3 内存屏障插入位置

```
volatile 写：
   [前置普通写]
   StoreStore 屏障    ← 禁止上面的普通写与 volatile 写重排
   volatile 写
   StoreLoad 屏障     ← 禁止 volatile 写与下面的 volatile 读/写重排（最重屏障）
   
volatile 读：
   volatile 读
   LoadLoad 屏障      ← 禁止 volatile 读与下面的普通读重排
   LoadStore 屏障     ← 禁止 volatile 读与下面的普通写重排
```

> 详见 [内存屏障](./内存屏障.md)。

### 6.4 适用场景

✅ 状态标志：
```java
volatile boolean shutdown = false;   // 线程间发停止信号
```

✅ 双重检查锁单例（必须）

✅ 独立观察发布：
```java
volatile long lastUpdate;   // 一个线程写，多个线程读
```

❌ 计数器（用 AtomicInteger）

❌ 复合操作（如 `if (a) b = 1` 这种 read-modify-write）

## 七、synchronized 的 JMM 语义

```java
synchronized (lock) {
    // 临界区
}
```

JMM 层面保证：
1. **进入同步块**：清空工作内存中的变量副本 → 重新从主内存加载
2. **退出同步块**：把工作内存中变更过的变量刷到主内存
3. **同一锁的解锁 hb 后续加锁**：线程 A 在 sync 块里写的变量，线程 B 拿到锁后能看到

→ **synchronized 同时保证原子性 / 可见性 / 有序性**——比 volatile 强大但更重。

## 八、final 的 JMM 语义（高频追问）

### 8.1 两条规则

```java
class Foo {
    final int x;
    int y;
    
    Foo() {
        x = 5;        // ①
        y = 6;
        // ②  构造函数返回前
    }
}

// 线程 A
foo = new Foo();     // ③

// 线程 B
Foo f = foo;
int xx = f.x;        // ④  能保证看到 x=5
int yy = f.y;        // ⑤  ⚠️ 不保证看到 y=6
```

JMM 对 final 字段：
1. **构造函数内对 final 的写 hb 构造函数返回**——禁止重排到构造函数外
2. **读到对象引用的线程能保证看到 final 字段的初始化值**

→ 这就是 **不可变对象（Immutable）天然线程安全** 的根本原因。

### 8.2 安全发布

```java
class UnsafeBox {
    int x;
    UnsafeBox() { x = 5; }
}

// 多线程下，一个线程发布 UnsafeBox 实例，另一线程可能读到 x=0（默认值）
// 因为 x 不是 final，构造完成的可见性没有保证
```

→ 把 `int x` 改成 `final int x` 即可安全发布。

## 九、生产踩坑

### 9.1 双重检查锁不加 volatile

经典反例。第一次访问可能拿到"半初始化"对象，触发 NPE 或字段 0 值。

### 9.2 用 volatile 想保护计数

```java
volatile int counter = 0;
counter++;   // 仍然不安全
```

→ 用 `AtomicInteger.incrementAndGet()`。

### 9.3 long / double 在 32 位 JVM 上非原子读

```java
long money = 0L;   // 32 位 JVM 上一个线程读可能读到一半新一半旧
```

→ 64 位 JVM 默认原子；老 32 位 JVM 加 `volatile long money` 强制原子。

### 9.4 用 sleep 等不到另一个线程的修改

```java
boolean flag = false;          // ⚠️ 没 volatile

new Thread(() -> {
    while (!flag) { /* 可能死循环 */ }
}).start();

Thread.sleep(1000);
flag = true;   // 主线程改了，但子线程可能永远看不到
```

子线程把 flag 缓存在寄存器里，不去主内存读。**加 volatile 解决**。

### 9.5 假设 happens-before 实现的具体方式

```java
volatile int a;
volatile int b;

// 线程 1
a = 1;
b = 1;

// 线程 2
if (b == 1) {
    System.out.println(a);   // 一定看到 1
}
```

正确——但**不要假设**这是因为"a=1 先于 b=1 物理执行"。**JMM 只保证 happens-before 可见性**，不保证物理顺序。

## 十、面试高频追问

### Q1：JMM 和 JVM 内存区域有什么区别？

完全不同的两件事：
- **JVM 内存区域**：物理划分，堆 / 栈 / 方法区 / PC / 本地方法栈
- **JMM**：线程间共享变量的访问**规则**，是规范不是物理内存

JMM 中的"主内存 / 工作内存"是**抽象**——主内存大致对应堆和方法区，工作内存对应 CPU 寄存器和缓存。

### Q2：volatile 怎么保证可见性？

写时插 StoreStore + StoreLoad 屏障，强制刷主内存；读时插 LoadLoad + LoadStore 屏障，强制重新读主内存。
底层在 x86 上对应 `lock; addl $0,0(%esp)` 指令——它隐含一次内存屏障。

### Q3：volatile 怎么保证有序性？

通过插入内存屏障禁止特定重排：
- 普通写不能与 volatile 写重排（StoreStore）
- volatile 写不能与后续 volatile 读重排（StoreLoad，最重）
- volatile 读不能与后续读 / 写重排（LoadLoad / LoadStore）

### Q4：volatile 能替代 synchronized 吗？

**不能**。volatile 不保证原子性，无法保护"读-改-写"这种复合操作。
什么时候能用 volatile 替代 synchronized：
- 只有一个线程写 + 多个线程读（如状态标志）
- 写操作不依赖当前值

### Q5：DCL 单例为什么必须 volatile？

`new Singleton()` 包含 ①分配 ②初始化 ③赋引用 三步，可能被重排成 1→3→2。
另一线程在第一次 if 检查时看到引用非空，但对象未初始化 → 用空对象。
volatile 禁止这次重排。

### Q6：synchronized 是怎么保证可见性的？

JMM 规定：**unlock 前必须把工作内存的变更刷主内存**，**lock 后必须重新从主内存加载**。
所以同一锁保护下，前一个线程的修改对后一个线程可见。

### Q7：什么是 happens-before？为什么要有这个概念？

JMM 给程序员的**可见性 + 顺序承诺**——如果 A hb B，就保证 A 的结果对 B 可见且看起来 A 在 B 之前发生。

为什么要：直接讲"读 / 写 / lock / unlock"8 个操作太底层难懂；hb 是更高层的语义，让程序员能推导线程间可见性。

### Q8：写 volatile 之前的普通写会被读 volatile 的线程看到吗？

**会**——这就是 volatile 的"内存语义传播"。
写 volatile 时插 StoreStore 屏障禁止之前的普通写重排到 volatile 写之后；读到 volatile 后再读普通字段，能看到写线程之前的修改。

### Q9：final 字段什么时候安全？

构造函数没逃逸 this 引用，且构造函数正常返回，则其它线程通过 happens-before 看到该对象时一定能看到 final 字段的正确初始化值。

**典型坑**：构造函数里把 `this` 注册到回调 / 加入集合 → 可能被另一线程在构造未完成时拿到。

### Q10：64 位 JVM 还需要担心 long / double 非原子吗？

**不需要**。32 位 JVM 上才有问题（拆高 32 / 低 32 两次写入），64 位 JVM 一次原子读写。

## 十一、答题模板（60 秒话术）

> JMM 是 Java 屏蔽底层硬件差异、定义**线程间共享变量访问规则**的规范，注意它**不是 JVM 内存区域**。
>
> 模型上：所有共享变量在**主内存**，每条线程有**工作内存**（对应寄存器和 CPU Cache），线程间通信只能通过主内存。
>
> JMM 保证三大特性：**原子性**（基本类型读写、synchronized、Atomic\*）、**可见性**（volatile、synchronized、final）、**有序性**（volatile 内存屏障、synchronized 串行）。
>
> 重排序来自三处：编译器、CPU 指令级、内存系统。JMM 通过**插入内存屏障 + happens-before 规则**禁止破坏语义的重排。
>
> **happens-before 是核心**——8 条规则：程序顺序、监视器锁、volatile、传递性、线程启动 / 终止 / 中断、finalize。
>
> **volatile** 的两个保证：可见性 + 有序性，但不保证原子性，所以 `i++` 还是不安全。**synchronized** 三特性都保证。**final** 字段在构造函数返回后对所有线程可见——不可变对象天然线程安全的根因。
>
> 经典反例：**DCL 单例必须用 volatile**，否则会被重排出"半初始化对象"被另一线程读到。
