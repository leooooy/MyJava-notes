# 垃圾收集器全景

> 面试常问"你知道哪些垃圾收集器？"——光说"G1 / CMS"不够，要会画**演进时间轴**讲清每代设计取舍。
>
> 本篇覆盖 7 个主力收集器：**Serial / ParNew / Parallel Scavenge / Serial Old / Parallel Old / CMS / G1 / ZGC / Shenandoah**，重点对比、选型、参数。
>
> 前置：[垃圾回收](./垃圾回收.md)、[G1垃圾回收器](./G1垃圾回收器.md)。

```

─────────────────────────────────────────────────────────────────
Serial      → ParNew + CMS    → G1                → ZGC / Shenandoah

              │                  │                  │
            Parallel Scavenge   JDK 9 默认          JDK 11+ 实验
            (吞吐优先)                              JDK 15+ 生产可用
              │                  │
            JDK 8 默认           CMS 在 JDK 14 删除
```

## 三、9 大收集器一览

| 收集器 | 区域 | 算法 | 线程 | 特点 | JDK |
| --- | --- | --- | --- | --- | --- |
| **Serial** | 新生代 | 复制 | 串行 | 客户端模式默认；单核 / 几百 MB 堆 | 一直在 |
| **ParNew** | 新生代 | 复制 | 并行 | Serial 多线程版；CMS 配套 | JDK 9 deprecated（必须配 CMS 才能用） |
| **Parallel Scavenge** | 新生代 | 复制 | 并行 | **吞吐优先**；JDK 8 默认 | 一直在 |
| **Serial Old** | 老年代 | 标记-整理 | 串行 | Serial 老年代版；CMS 兜底 | 一直在 |
| **Parallel Old** | 老年代 | 标记-整理 | 并行 | PS 老年代版；JDK 8 默认 | JDK 6 起 |
| **CMS** | 老年代 | 标记-清除 | 并发 | **低延迟先驱**；碎片化 | 1.4 → JDK 14 删除 |
| **G1** | 全堆（Region） | 标记-整理 + 复制 | 并发 | 软实时；JDK 9+ 默认 | JDK 7u4 起 |
| **ZGC** | 全堆（Region） | 染色指针 + 读屏障 | 并发 | 亚毫秒；超大堆 | JDK 11 实验 → JDK 15 生产 |
| **Shenandoah** | 全堆（Region） | Brooks 指针 + 读屏障 | 并发 | 亚毫秒；OpenJDK only | OpenJDK 12+ |

## 四、Serial 系列（古典派）

### 4.1 Serial（新生代）

```
GC 时单线程，所有用户线程 STW
   │
   ▼
[简单] [快] [STW 久]
```

- 客户端模式默认
- 单核或几百 MB 堆，开销小
- `-XX:+UseSerialGC` 启用

### 4.2 Serial Old（老年代）

- 服务端做 CMS 兜底（CMS Concurrent Mode Failure 时退回它）
- **几十 GB 堆 + 全 STW** = 灾难场景

---

## 五、Parallel 系列（吞吐派）

### 5.1 Parallel Scavenge（新生代）

> 关注**吞吐量**（用户代码运行时间 / 总时间）而不是停顿时间。

参数：
```bash
-XX:+UseParallelGC                # 启用 PS（同时启 Parallel Old）
-XX:ParallelGCThreads=N           # GC 线程数
-XX:MaxGCPauseMillis=200          # 期望停顿（不保证）
-XX:GCTimeRatio=99                # 期望 GC 时间占比 1%（公式 1/(1+N)）
-XX:+UseAdaptiveSizePolicy        # 让 JVM 自适应调 Eden / Survivor 比例
```

**适用**：批处理、离线分析、对停顿不敏感、要求高吞吐的服务。

### 5.2 Parallel Old

PS 的老年代版，标记-整理算法的并行版本。**JDK 8 默认（PS + PO 组合）**。

## 六、CMS（Concurrent Mark-Sweep）—— 已废

### 6.1 流程（4 步）

```
1. 初始标记 (STW，短)
   └─ 标 GC Roots 直接引用
       │
       ▼
2. 并发标记
   └─ 三色标记，与用户线程并发
   └─ 增量更新（Incremental Update）记录黑→白引用
       │
       ▼
3. 重新标记 (STW，比初始标记长)
   └─ 处理增量更新队列
       │
       ▼
4. 并发清理
   └─ 清除标记的垃圾，与用户线程并发
   └─ 不整理 → 碎片化
```

### 6.2 致命问题

1. **Concurrent Mode Failure**：并发清理时老年代不够 → 退回 Serial Old → 单线程整理超大堆 → STW 数十秒
2. **碎片化**：标记-清除天然问题；`-XX:+UseCMSCompactAtFullCollection` 在 FullGC 时整理（带来更长 STW）
3. **CPU 敏感**：并发线程数 = (CPU + 3) / 4，4 核机吃掉 1 核
4. **浮动垃圾**：并发清理期间产生的垃圾要等下轮回收

→ JDK 9 deprecated，**JDK 14 正式移除**。

---

## 七、G1（Garbage First）—— 当前主流

详见 [G1垃圾回收器](./G1垃圾回收器.md)。

**速记**：
- Region 化（1~32MB），物理不连续逻辑分代
- Mixed GC：YGC + 部分 OldGC，按价值优先回收
- 可指定 MaxGCPauseMillis（软实时）
- 写屏障维护 RSet
- SATB 解决漏标
- 适用：6GB+ 堆、能接受 100~500ms 停顿

---

## 八、ZGC（Z Garbage Collector）—— 未来

> Oracle 主导，JDK 11 实验性，**JDK 15 起生产可用**。目标：**任何堆大小（数 GB ~ 数 TB）下 STW < 10ms**。

### 8.1 设计创新

1. **染色指针（Colored Pointers）**：把对象状态信息**塞进对象引用本身**（指针的高位）
2. **读屏障（Load Barrier）**：每次读对象时检查指针颜色，触发对应处理
3. **并发整理**：对象搬动期间，读屏障转发到新地址——几乎无 STW
4. **Region 化**：分小（2MB）/ 中（32MB）/ 大（动态）三种 Region

### 8.2 染色指针原理

```
传统对象引用：       0x00007F8B12345678   (64 位地址)

染色指针：           [reserved][marked0][marked1][remapped][finalizable]   [actual address]
                       4 bit                                              42 bit (4TB 寻址)
```

通过指针自身的位标记 GC 状态——**不需要在对象头上修改 Mark Word，也不需要写屏障维护卡表**。

### 8.3 性能特点

| 维度 | ZGC |
| --- | --- |
| 最大堆 | **16 TB**（理论） |
| 单次 STW | **< 10ms**（实测多在 1~2ms） |
| 吞吐损失 | ~ 10% （读屏障开销） |
| CPU 占用 | 较高（并发线程多） |
| 内存额外开销 | ~ 10%（读屏障 + Forwarding Table） |

### 8.4 启用 / 参数

```bash
-XX:+UseZGC                         # JDK 15+ 直接用
-XX:+UnlockExperimentalVMOptions    # JDK 11~14 需要
-XX:+UseZGC

-Xms16g -Xmx16g                     # 大堆才有意义
-XX:ConcGCThreads=4
-XX:ZCollectionInterval=120         # 主动 GC 间隔（秒）
```

### 8.5 ZGC 局限

- **JDK 15 才稳定**——老项目升级成本
- **不支持 Class Data Sharing**（早期版本，新版改善）
- **JDK 21 才有分代 ZGC**（之前是无分代——所有对象一起处理，对短命对象不够高效）

→ 适合：**金融交易、大堆缓存（几十 GB+ Redis 兜底）、大数据 Server**。

---

## 九、Shenandoah —— Red Hat 版 ZGC

> Red Hat 主导，OpenJDK 12+ 自带（**Oracle JDK 不带**）。目标和 ZGC 类似——亚毫秒 STW。

### 9.1 与 ZGC 的差别

| | ZGC | Shenandoah |
| --- | --- | --- |
| 主导方 | Oracle | Red Hat |
| 实现技术 | 染色指针 | **Brooks 转发指针** |
| 大堆支持 | 16TB | 几十 GB（实践上） |
| 内存开销 | 低（指针本身） | 较高（每个对象多 8B forwarding pointer） |
| 加入时间 | JDK 11 | OpenJDK 12 |

```bash
-XX:+UseShenandoahGC
```

→ Oracle JDK 用户没得选，只能 ZGC。OpenJDK 用户两个都能用。

## 十、收集器选型决策树

```
你的堆多大？
├─ < 2GB → 客户端 / 工具：Serial GC
├─ 2~6GB → Parallel GC（吞吐优先）或 G1（默认）
├─ 6~32GB → G1（默认就好）
├─ 32GB~ → 看延迟敏感度
│   ├─ 不敏感（批处理）→ Parallel GC（最大吞吐）
│   ├─ 一般敏感 → G1
│   └─ 严苛（毫秒级）→ ZGC / Shenandoah
└─ TB 级 → ZGC

你需要 STW < 10ms?
└─ 是 → ZGC / Shenandoah

业务有什么特殊性？
├─ 批处理 / 离线分析 → Parallel
├─ Web 服务 / 中间件 → G1（默认）
├─ 高频交易 / 实时风控 → ZGC
└─ Spark / 大数据 Driver → G1 / ZGC
```

## 十一、生产经验

### 11.1 常见线上配置

**Spring Boot 微服务（4-8 核 / 4-8GB 堆）**：
```bash
-Xms4g -Xmx4g
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-XX:+HeapDumpOnOutOfMemoryError
```

**Kafka Broker（大堆 16-32GB）**：
```bash
-Xms16g -Xmx16g
-XX:+UseG1GC
-XX:MaxGCPauseMillis=20         # Kafka 推荐 20ms
-XX:InitiatingHeapOccupancyPercent=35
-XX:G1HeapRegionSize=16m
```

**Elasticsearch（大堆 + 低延迟）**：
```bash
-Xms16g -Xmx16g                 # 不超 31GB（压缩指针）
-XX:+UseG1GC                    # JDK 11+
# 或
-XX:+UseZGC                     # JDK 15+ 极致延迟
```

**Spark Driver（短期 ETL，吞吐优先）**：
```bash
-XX:+UseParallelGC
```

### 11.2 升级 GC 注意

- **CMS → G1**：去掉 CMS 相关参数（UseCMSCompactAtFullCollection 等），重调 IHOP / Region
- **G1 → ZGC**：去掉 G1 参数，**确认 JDK 版本 ≥ 15**，监控 RSS（ZGC 占用比 G1 多 10%）
- 升级前**压测 + 灰度**——GC 行为差异很大，业务延迟分布可能完全不同

## 十二、面试高频追问

### Q1：JDK 8 / 11 / 17 默认 GC 是什么？

- JDK 7：Parallel Scavenge + Parallel Old
- JDK 8：Parallel Scavenge + Parallel Old（JDK 8 后期版本可手动开 G1）
- **JDK 9~21**：**G1**

### Q2：CMS 为什么被淘汰？

碎片化 + Concurrent Mode Failure（退化 SerialOld 巨长 STW）+ CPU 敏感（吃 1/4 核）+ 维护复杂。
JDK 9 deprecated，JDK 14 删除，G1 全面接班。

### Q3：G1 和 ZGC 区别？

| | G1 | ZGC |
| --- | --- | --- |
| 停顿目标 | 100~500ms | < 10ms |
| 堆 | ~ 数十 GB | 数 GB ~ TB |
| 写/读屏障 | 写屏障维护 RSet | 读屏障 + 染色指针 |
| 分代 | 是 | 不分代（JDK 21+ 可选分代） |
| 吞吐 | 损失 < 5% | 损失 ~ 10% |

### Q4：什么是染色指针？

把对象 GC 状态（是否被标记 / 是否被搬动）编码进对象引用的高位 bit ——每次读对象通过读屏障检查这些位。
**优点**：不用在对象头维护，不用写屏障维护卡表。**缺点**：每次读都过屏障（吞吐损失）。

### Q5：什么是吞吐优先 vs 低延迟优先？

- **吞吐优先（Parallel）**：最大化用户代码占总时间比例，不在乎单次停顿——批处理 / 离线
- **低延迟优先（CMS / G1 / ZGC）**：最小化单次 STW——Web 服务 / 在线交易

### Q6：为什么吞吐优先的收集器停顿反而长？

吞吐优先攒批一起回收——单次 GC 时间长但总时间短。
低延迟把工作分散到多次小 GC + 并发执行——单次短但总开销大。

### Q7：Parallel GC 和 ParNew 区别？

- **ParNew**：Serial 的多线程版，JDK 9 之后**只能配 CMS**，CMS 删除后基本无用
- **Parallel Scavenge**：独立设计，关注吞吐量，配 Parallel Old

### Q8：ZGC 为什么需要读屏障，不用写屏障？

ZGC 的核心创新是**并发整理**——对象在被读的瞬间发现已搬走，通过读屏障转发到新地址。
读屏障 + 染色指针组合，让对象搬动几乎无 STW。

写屏障只是 GC 阶段标记跨代引用用，传统 GC 才需要。

### Q9：堆超过 32GB 会有什么问题？

压缩指针失效（默认 32GB 上限），所有对象引用从 4B 变 8B → 内存膨胀 30%。
**经验**：要么 ≤ 31GB（Elasticsearch 著名建议），要么 ≥ 48GB 才能用回省下的空间。

### Q10：如何选择 GC？

按"延迟要求 + 堆大小"二维选：
- 不在乎延迟 + 任意堆 → Parallel
- 一般延迟（< 200ms）+ 堆 ≤ 数十 GB → G1
- 严苛延迟（< 10ms）+ 大堆 → ZGC / Shenandoah
- 大数据 Driver / 短期任务 → Parallel
- 长期在线服务 → G1（默认）/ ZGC（极致）

## 十三、答题模板（90 秒话术）

> Java 主流收集器按演进分四代：**Serial（单线程）→ Parallel（吞吐）→ CMS（低延迟先驱）→ G1（分区软实时）→ ZGC / Shenandoah（亚毫秒）**。
>
> JDK 8 默认 **Parallel Scavenge + Parallel Old**（吞吐优先），JDK 9+ 默认 **G1**，**CMS JDK 14 已删除**。
>
> 选型按两维：
> - **延迟敏感度**：批处理 → Parallel；Web 服务 → G1；金融 / 实时 → ZGC
> - **堆大小**：< 4GB Parallel；6-32GB G1；32GB+ 或 TB 级 ZGC
>
> **ZGC 的核心创新**：染色指针（GC 状态编码进引用）+ 读屏障（读时检查 + 转发到新地址）→ 并发整理几乎无 STW。代价是吞吐损失 10%、内存额外 10%。
>
> Oracle JDK 用户大堆低延迟场景上 **ZGC**；OpenJDK 也可以选 **Shenandoah**（Red Hat）。
>
> 堆 > 32GB 注意压缩指针失效，要么 ≤ 31GB 要么 ≥ 48GB 避开负优化区间。
