# 内存屏障 Memory Barrier

> 也叫"内存栅栏 (Memory Fence)"，是 [JMM](./内存模型.md) 落到 CPU 层的具体武器。
>
> 本篇解决：① 没有屏障会出什么乱子；② 四种屏障语义；③ x86 / ARM 屏障强弱差异；④ volatile 的屏障到底插在哪；⑤ 为什么 StoreLoad 是最重的屏障；⑥ Unsafe 的 fullFence / loadFence / storeFence。

---

## 一、为什么需要内存屏障

### 1.1 重排序导致的乱

```
源代码顺序           CPU 实际执行顺序
a = 1               b = 2     ← 与 a=1 没数据依赖，CPU 流水线乱序
b = 2               a = 1
```

单线程内 CPU 自己保证"看起来顺序"（as-if-serial），单线程怎么乱都没事。  
**多线程共享变量**就要命了——线程 2 可能先看到 b=2 后看到 a=1，做出错误推断。

### 1.2 CPU 写缓冲（Store Buffer）

```
CPU0                            CPU1
寄存器                           寄存器
  ↓ write a=1                    ↓ read a
Store Buffer                     L1 Cache (老 a=0)
  ↓ 异步刷                          
L1 Cache → L2 → L3 → 主内存
```

CPU0 写 a=1 后**先进 Store Buffer 异步刷**——CPU1 在 Store Buffer 还没刷到主内存前去读，看到的是旧值。

→ **内存屏障的核心作用：阻止 CPU 把指令重排过屏障 + 强制刷新缓冲**。

---

## 二、四种内存屏障

> 按 "屏障前的操作" + "屏障后的操作" 组合命名，4 种：

| 屏障 | 作用 |
| --- | --- |
| **LoadLoad** | 屏障前的读 happens-before 屏障后的读 |
| **StoreStore** | 屏障前的写 happens-before 屏障后的写 |
| **LoadStore** | 屏障前的读 happens-before 屏障后的写 |
| **StoreLoad** | 屏障前的写 happens-before 屏障后的读 ⭐ **最重** |

```
LoadLoad:    Load1; LoadLoad; Load2
             保证 Load1 完成后才执行 Load2

StoreStore:  Store1; StoreStore; Store2
             保证 Store1 对其它处理器可见后才执行 Store2

LoadStore:   Load1; LoadStore; Store2
             保证 Load1 完成后才执行 Store2

StoreLoad:   Store1; StoreLoad; Load2
             保证 Store1 对其它处理器可见后才执行 Load2  ← 这条最贵
```

**为什么 StoreLoad 最贵**：
- 必须**清空 Store Buffer**，等所有写入在所有 CPU 上可见
- x86 上对应 `mfence`，ARM 上对应 `dmb sy`
- 通常一次 StoreLoad 几十纳秒——比一次 L1 缓存命中（约 1ns）慢一两个量级

## 三、不同 CPU 的屏障强度

> 各架构的"内存模型"强弱不同——同样的代码在 x86 上跑没问题，到 ARM 上可能错。

| 架构 | 内存模型 | 哪些重排允许 |
| --- | --- | --- |
| **x86 / x64** | TSO（Total Store Order）**强一致** | **只允许 Store-Load 重排** |
| **ARM / PowerPC** | **弱一致** | StoreStore / LoadLoad / LoadStore / StoreLoad 全允许 |
| **Itanium** | 弱一致 | 全允许 |

**含义**：
- x86 上，CPU 自己只会做 StoreLoad 一种重排——对应 JVM 在 x86 上**只需要 StoreLoad 屏障**即可实现 volatile，其它三个屏障是 no-op
- ARM 上每种屏障都要真插指令（`dmb` 系列）

→ 这就是为什么 **同样的并发 bug 在 x86 上很难复现，到 ARM 服务器上立马翻车**。

## 四、x86 上的屏障实现

JVM 在 x86 上的内存屏障对应 CPU 指令：

| JMM 屏障 | x86 指令 | 备注 |
| --- | --- | --- |
| LoadLoad | no-op | x86 不允许 LoadLoad 重排 |
| StoreStore | no-op | x86 不允许 StoreStore 重排 |
| LoadStore | no-op | x86 不允许 LoadStore 重排 |
| **StoreLoad** | `mfence` 或 `lock; addl $0, 0(%rsp)` | 唯一需要硬件指令的 |

`lock` 前缀 + 一条无意义的指令，是早期实现 StoreLoad 的便宜替代——`lock` 隐含 fence 语义且更便宜。

### 4.1 实测

```bash
# 看 hotspot 在 x86 怎么实现 volatile 写
javap -c -p -v MyVolatileClass
# 在 hsdis 反汇编输出里能看到 volatile 写后跟着 lock add 0,...
```

## 五、Java 中触发内存屏障的 4 个时机

### 5.1 volatile 读 / 写

```
volatile 写：
  [前置普通写]
  StoreStore   ← 禁止前面的普通写重排到 volatile 写之后
  volatile write
  StoreLoad    ← 禁止 volatile 写与后面的 volatile 读 / 写重排（最重）

volatile 读：
  volatile read
  LoadLoad     ← 禁止 volatile 读与后面的普通读重排
  LoadStore    ← 禁止 volatile 读与后面的普通写重排
```

> **设计取舍**：写贵读便宜——StoreLoad 放在写后保守地保证可见。
>
> JIT 优化时，会按"安全前提"省略多余屏障（如连续两个 volatile 写中间的 LoadLoad / LoadStore 可以省）。

### 5.2 synchronized 出入

```
monitorenter
  → 隐式 LoadLoad + LoadStore（重新读主内存）
临界区
monitorexit
  → 隐式 StoreLoad + StoreStore（刷主内存）
```

### 5.3 final 字段构造

```java
class Foo {
    final int x;
    Foo() {
        x = 5;
        // ↓ JVM 在构造函数返回前插 StoreStore 屏障
    }
}
```

保证别的线程拿到 Foo 引用时，能看到 x = 5 而不是 0。

### 5.4 Unsafe 显式调用

```java
Unsafe unsafe = Unsafe.getUnsafe();
unsafe.loadFence();     // ≈ LoadLoad + LoadStore
unsafe.storeFence();    // ≈ StoreStore + LoadStore
unsafe.fullFence();     // ≈ StoreLoad（最重）
```

JDK 9+ 改用更友好的 `VarHandle`：
```java
VarHandle.fullFence();
VarHandle.acquireFence();   // ≈ loadFence
VarHandle.releaseFence();   // ≈ storeFence
```

## 六、屏障实战：写一个 happens-before 推导

```java
class Example {
    int a = 0;
    volatile boolean v = false;
    
    void writer() {
        a = 1;          // ① 普通写
        v = true;       // ② volatile 写
                        //   写之前插 StoreStore，禁止 ① 重排到 ② 之后
                        //   写之后插 StoreLoad
    }
    
    void reader() {
        if (v) {        // ③ volatile 读
                        //   读之后插 LoadLoad / LoadStore，禁止后面的读 / 写重排到 ③ 之前
            int x = a;  // ④ 一定能看到 a = 1
        }
    }
}
```

推导：
- ① hb ②（程序顺序 + StoreStore 屏障保证）
- ② hb ③（volatile 规则）
- ③ hb ④（程序顺序 + LoadLoad 屏障保证）
- 传递性：① hb ④ ✅

## 七、acquire / release 语义（C++ 风格）

> 现代并发库越来越多用 acquire / release 描述屏障——比 LoadLoad/StoreStore 更直观。

| 语义 | 等价屏障 | 用法 |
| --- | --- | --- |
| **acquire** | LoadLoad + LoadStore | 读屏障，"获取"一个值，后续操作不能重排到它前面 |
| **release** | LoadStore + StoreStore | 写屏障，"发布"一个值，前面的操作不能重排到它后面 |
| **full barrier** | 全部 | volatile / synchronized 的语义 |

**acquire-release 模式**比 fullFence 便宜，因为不需要 StoreLoad。

JDK 9 的 VarHandle：
```java
v.getAcquire(this);          // 类似 volatile 读，但不需要 StoreLoad
v.setRelease(this, value);   // 类似 volatile 写，但不需要 StoreLoad
```

## 八、生产意义

### 8.1 Disruptor / Netty 用 acquire-release 优化

高性能并发库不会无脑用 volatile（每次 StoreLoad 几十纳秒）。它们会：
1. 把状态字段拆分（一些只在单线程读 → 不需要 volatile）
2. 用 `getAcquire / setRelease` 替代 volatile
3. 自定义内存屏障的精确插入位置

### 8.2 ARM 服务器上要更小心

阿里、腾讯、亚马逊这几年大量上 ARM 服务器（Graviton / 倚天 / 鲲鹏）。在 x86 写出来"看起来没问题"的并发代码，到 ARM 可能频繁出 bug——**因为 ARM 的弱内存模型暴露了原本被 x86 强内存模型掩盖的重排序**。

→ 上 ARM 前重点 review 涉及共享变量的代码：
- 缺失的 volatile
- 没有正确发布的对象
- 自实现的同步原语（不用 volatile/synchronized 自己玩屏障）

## 九、面试高频追问

### Q1：内存屏障到底是什么？

CPU 指令级的"栅栏"，强制：
1. **禁止重排**：屏障前后的指令不能互相穿越
2. **强制刷缓冲**：把 Store Buffer 的写、Invalidate Queue 的失效消息处理完

JMM 通过四种屏障（LoadLoad / StoreStore / LoadStore / StoreLoad）实现 volatile / final / synchronized 的内存语义。

### Q2：volatile 写为什么后面要 StoreLoad？

为了禁止 "volatile 写" 与 "后续的 volatile 读 / 写" 重排——这个组合是 x86 上唯一允许的重排。
StoreLoad 强制刷 Store Buffer，是 4 种屏障里**最贵**的一种（几十纳秒）。

### Q3：为什么 x86 上 volatile 性能没那么差？

因为 x86 是 TSO 强内存模型——LoadLoad / StoreStore / LoadStore 三个屏障在 x86 上是 no-op，只有 StoreLoad 真插指令（`lock add` 或 `mfence`）。
ARM 上 volatile 比 x86 贵得多。

### Q4：synchronized 出入隐含什么屏障？

进入：LoadLoad + LoadStore（清空工作内存副本，重新读主内存）
退出：StoreStore + StoreLoad（把工作内存的修改刷主内存）

→ 所以 synchronized 临界区内的所有写，对下一个拿锁的线程都可见。

### Q5：Unsafe.fullFence / loadFence / storeFence 区别？

- `loadFence` = LoadLoad + LoadStore（禁止后续读 / 写跑到读屏障之前）
- `storeFence` = StoreStore + LoadStore（禁止前面的读 / 写跑到写屏障之后）
- `fullFence` = StoreLoad（最重，对应 mfence）

JDK 9+ 推荐用 `VarHandle.acquireFence / releaseFence / fullFence` 替代。

### Q6：final 字段为什么不需要 volatile？

JMM 保证：构造函数返回前插入 StoreStore 屏障——别的线程拿到对象引用时，一定能看到 final 字段的正确初始化值。
这就是不可变对象天然线程安全的根因。

⚠️ 前提：构造过程中 `this` 没有逃逸（没传给别的线程 / 注册回调 / 加进集合）。

### Q7：什么是 acquire-release 语义？

C++ 11 引入的更细粒度屏障：
- **acquire**（读屏障）：后续操作不能重排到它前
- **release**（写屏障）：前面操作不能重排到它后
- 比 full fence 便宜，因为不需要 StoreLoad

JDK 9 VarHandle 提供了 `getAcquire / setRelease`，高性能并发库（Disruptor）大量使用。

### Q8：为什么 ARM 上 Java 并发更容易出 bug？

ARM 是弱内存模型，**允许 LoadLoad / StoreStore / LoadStore / StoreLoad 全部重排**。x86 是 TSO 只允许 StoreLoad 重排。

x86 上很多"看起来无害的代码"靠的是 CPU 隐式不重排；到 ARM 这种保护没了 → 缺失的 volatile / 错误发布问题立刻暴露。

## 十、答题模板（30 秒话术）

> 内存屏障是 CPU 指令级的"栅栏"，**禁止指令重排** + **强制刷缓冲**——是 JMM 落地的硬件机制。
>
> 四种语义：**LoadLoad / StoreStore / LoadStore / StoreLoad**，最后一种最重（强制清空 Store Buffer）。
>
> 触发时机：**volatile** 读写、**synchronized** 出入、**final** 构造结束、**Unsafe / VarHandle.fence**。
>
> volatile 写前插 StoreStore，写后插 StoreLoad；volatile 读后插 LoadLoad + LoadStore——保证可见性 + 有序性。
>
> x86 是强内存模型（TSO），只有 StoreLoad 真插指令；**ARM 是弱模型，每种屏障都要真插 dmb 指令**——这是 x86 上"看起来正常"的并发代码到 ARM 上出 bug 的根因。
