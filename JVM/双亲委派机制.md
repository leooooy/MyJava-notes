# 双亲委派机制

> 高频面试题——"为什么 JDK 要用双亲委派？" "怎么打破？" "Tomcat 为什么打破？" "SPI 为什么打破？"
>
> 本篇解决：① 双亲委派的工作流程；② 解决了什么核心问题（不只是"防止重复加载"）；③ 三个经典反例：JNDI / JDBC / Tomcat / OSGi；④ 怎么自己打破。

---

## 一、双亲委派是什么

> ⚠️ "双亲" 这个翻译不准——原文叫 **Parents Delegation Model**，"双亲"实际是"父加载器们"（递归向上）。中文一直叫习惯了。

### 1.1 工作流程

```
ClassLoader.loadClass("com.foo.Bar")
   │
   ▼
1. 检查是否已加载？已加载 → 直接返回
   │
   ▼
2. 委派给父加载器 parent.loadClass(name)
   │
   ▼  (parent 不是 Bootstrap)
3. 父再委派给爷爷 → 爷爷再委派 → 一直到 Bootstrap
   │
   ▼
4. Bootstrap 尝试加载 → 找不到 → 抛 ClassNotFoundException
   │
   ▼
5. 子加载器接到异常 → 自己尝试 findClass
   │
   ▼
6. 自己也找不到 → 再抛 ClassNotFoundException 给下层
```

**核心规则**：**先向上委派，向上找不到才自己找**。

### 1.2 源码结构（ClassLoader.loadClass）

```java
protected Class<?> loadClass(String name, boolean resolve) {
    synchronized (getClassLoadingLock(name)) {
        Class<?> c = findLoadedClass(name);    // ① 已加载？
        if (c == null) {
            try {
                if (parent != null) {
                    c = parent.loadClass(name, false);   // ② 向上委派
                } else {
                    c = findBootstrapClassOrNull(name);  // ③ Bootstrap
                }
            } catch (ClassNotFoundException e) {
                // 父加载器没找到
            }
            if (c == null) {
                c = findClass(name);            // ④ 自己找
            }
        }
        return c;
    }
}
```

→ **打破双亲委派 = 重写 loadClass()**（而不是 findClass）。

## 二、为什么需要双亲委派

### 2.1 表面：防止重复加载

同一个类在 JVM 里只加载一次（按 全限定名 + ClassLoader 算唯一性）。

### 2.2 核心：保证核心类的安全和一致性

```java
// 用户写一个恶意 java.lang.String
package java.lang;
public class String {
    static { Runtime.getRuntime().exec("rm -rf /"); }
}
```

如果没有双亲委派，应用 ClassLoader 会先加载用户的 `String` → JVM 启动时核心库引用 `java.lang.String` 实际拿到恶意类 → **整个 Java 安全模型崩塌**。

**有了双亲委派**：
- 用户的 `java.lang.String` → 委派到 Bootstrap → Bootstrap 在 rt.jar 里找到正版 String → 用户的版本永远加载不了

### 2.3 核心：让所有类只有一个权威来源

确保 **所有 Java 程序看到的 `java.lang.Object` 是同一个 Object**——避免类型不一致 / instanceof 失效。

## 三、双亲委派的三个例外（必考）

### 3.1 JDBC 驱动 / SPI 机制

**问题**：`DriverManager` 在 rt.jar，由 Bootstrap 加载；MySQL 驱动 `com.mysql.cj.jdbc.Driver` 在 classpath，由 Application 加载。
按双亲委派，Bootstrap 看不到 Application 的类——**DriverManager 怎么调到 MySQL 驱动？**

**解法：线程上下文类加载器（TCCL）**
```java
Thread.currentThread().setContextClassLoader(...)
ServiceLoader<Driver> loader = ServiceLoader.load(Driver.class);
// 内部：Driver.class.getClassLoader() = Bootstrap
//      但实际加载用 Thread.currentThread().getContextClassLoader() = Application
```

**TCCL 默认是 Application ClassLoader**——通过它，**父加载器可以借子加载器的能力**。

→ 这就是 **SPI（Service Provider Interface）的核心机制**。`ServiceLoader.load()` 内部全靠 TCCL。

**典型 SPI**：JDBC、JNDI、JCE、JBI、Dubbo SPI、Spring Factories。

### 3.2 Tomcat 的 WebApp ClassLoader

**问题**：Tomcat 同时跑两个 webapp，都依赖不同版本的 commons-logging：
- App A 用 1.1
- App B 用 1.2

如果按双亲委派，Application ClassLoader 会先加载哪个版本，另一个就没机会 → 冲突。

**解法**：Tomcat 给每个 webapp 一个独立的 **WebappClassLoader**，并**反向加载**（先自己找，找不到才委派父）。

```
Bootstrap
   └─ System ClassLoader
        └─ Common ClassLoader        (Tomcat 通用类)
             ├─ Catalina ClassLoader (Tomcat 自身)
             └─ Shared ClassLoader   (各 webapp 共享类)
                  ├─ WebappClassLoader 1   ← 隔离
                  └─ WebappClassLoader 2   ← 隔离
```

WebappClassLoader 重写 `loadClass()`：
```
1. 先看缓存
2. 先委派给 Bootstrap（防止用户重写 java.lang.* 等核心类）
3. 然后自己找 /WEB-INF/classes 和 /WEB-INF/lib
4. 自己找不到才委派给 Common ClassLoader
```

→ **打破双亲委派**：自己优先 → 实现 webapp 之间的类隔离。

### 3.3 OSGi 的网状类加载

OSGi 把每个 Bundle 当成独立模块，**ClassLoader 之间不是树形而是网状**——每个 Bundle 通过 Import-Package / Export-Package 声明依赖，ClassLoader 按图找类。

完全打破双亲委派——OSGi 是这套机制的极端。

### 3.4 JDK 9+ 的模块系统（JPMS）

模块系统也对双亲委派做了调整——加入了 **Platform ClassLoader**（替代 Extension），加载顺序加入了模块解析步骤。

JDK 9+ ClassLoader 树：
```
Bootstrap → Platform → Application
```

加载流程加入"先看是否在已知模块中" → 模块决定 ClassLoader → 再走双亲委派。

## 四、怎么打破双亲委派

### 4.1 重写 loadClass()（不推荐）

```java
public class CustomClassLoader extends ClassLoader {
    @Override
    protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
        // 不调 super.loadClass()
        // 自己处理委派逻辑
    }
}
```

⚠️ 风险大——破坏类的全局唯一性，容易出 ClassCastException。

### 4.2 用线程上下文类加载器（推荐）

```java
ClassLoader cl = Thread.currentThread().getContextClassLoader();
Class<?> clazz = cl.loadClass("com.foo.Bar");
```

让父加载器借用子加载器的能力——SPI 全靠这个。

### 4.3 OSGi 风格的 ClassLoader 网络

工程量大，普通项目不要碰。Equinox / Felix 等 OSGi 框架已经实现。

## 五、双亲委派的源码细节

### 5.1 findClass vs loadClass

| 方法 | 推荐重写 | 用途 |
| --- | --- | --- |
| `loadClass()` | ❌（除非要打破双亲委派） | 整个加载流程入口 |
| `findClass()` | ✅ | 自己加载逻辑（如读字节流） |
| `defineClass()` | ❌（基类已实现） | 把字节流转成 Class 对象 |

**自定义 ClassLoader 的标准做法**：只重写 `findClass()`，不动 `loadClass()` → 自动尊重双亲委派。

```java
class MyClassLoader extends ClassLoader {
    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        byte[] bytes = loadFromCustomSource(name);
        return defineClass(name, bytes, 0, bytes.length);
    }
}
```

### 5.2 已加载缓存

`findLoadedClass(name)` 内部维护一个 `Vector<Class<?>>`，每个 ClassLoader 实例独立。

→ 一个 ClassLoader 加载过的类不会再加载第二次。

## 六、生产踩坑

### 6.1 ClassCastException 的迷之 bug

```java
// 类 A
public interface Service { ... }

// ClassLoader CL1 加载了 Service 和 ServiceImpl
// ClassLoader CL2 也加载了 Service

Service s = (Service) CL2.loadClass("ServiceImpl").newInstance();
// ClassCastException: ServiceImpl cannot be cast to Service
```

**根因**：CL1 和 CL2 加载的 `Service` 是两个不同的 Class——尽管类名一样。

**解决**：让接口类只由共同的父加载器加载（如 Common ClassLoader），实现类才放在子加载器。

### 6.2 SPI 类找不到

```java
ServiceLoader<MyService> loader = ServiceLoader.load(MyService.class);
// java.util.ServiceConfigurationError: ...
```

可能原因：
- 当前线程的 TCCL 没设对（如线程池里的线程默认用创建时的 ClassLoader）
- `META-INF/services/com.foo.MyService` 文件没打进 jar

**显式指定 ClassLoader**：
```java
ServiceLoader.load(MyService.class, Thread.currentThread().getContextClassLoader());
```

### 6.3 Tomcat 多 webapp 共享 Logger 实例

```
WebappA 自带 commons-logging.jar
WebappB 不带
→ B 走 Shared 或 Common ClassLoader 拿到 commons-logging
→ A 自己加载一份
→ A 和 B 看到的是不同的 Log 类
```

**统一规范**：依赖统一放 Tomcat 的 `lib/`（Common ClassLoader），不让 webapp 自带——避免冲突。

## 七、面试高频追问

### Q1：什么是双亲委派？

子 ClassLoader 加载类时，先委派给父 ClassLoader 加载；父加载不到才自己加载。**先委派、再自己找**。

### Q2：为什么需要双亲委派？

两个核心目的：
1. **安全**：防止用户篡改核心类（如自定义 `java.lang.String`）
2. **一致性**：保证全局只有一个权威版本的类（所有 `Object` 都是同一个）

附带：避免重复加载。

### Q3：双亲委派"双亲"是指什么？

中文翻译误导——原文是 Parents Delegation，"父加载器们"，**递归向上**直到 Bootstrap。不是字面意义的"双亲"。

### Q4：哪些场景打破了双亲委派？

1. **SPI（JDBC / JNDI / Dubbo SPI）**：通过 Thread Context ClassLoader 让 Bootstrap 加载的类调到 Application 加载的实现
2. **Tomcat WebappClassLoader**：webapp 内的类先自己找，再委派父——实现多 webapp 类隔离
3. **OSGi**：每个 Bundle 独立 ClassLoader，按 Import/Export 网状加载
4. **JDK 9+ 模块系统**：先看模块归属再走委派

### Q5：怎么实现自定义 ClassLoader？

继承 `ClassLoader`，**重写 `findClass()`**（不要重写 loadClass，否则破坏双亲委派）：
```java
class MyCL extends ClassLoader {
    protected Class<?> findClass(String name) {
        byte[] bytes = loadFromMyStorage(name);
        return defineClass(name, bytes, 0, bytes.length);
    }
}
```

### Q6：JDBC 是怎么打破的？

`DriverManager`（rt.jar，Bootstrap 加载）需要拿到 `com.mysql.cj.jdbc.Driver`（classpath，Application 加载）。
按双亲委派 Bootstrap 看不到子加载器的类——通过 **Thread.currentThread().getContextClassLoader()** 拿到 Application ClassLoader，绕过来加载 Driver。

→ **TCCL 让父加载器借子加载器的能力**，是 SPI 的核心机制。

### Q7：Tomcat 为什么打破？

每个 webapp 要独立类空间（不同版本依赖共存）→ 给每个 webapp 一个 WebappClassLoader，反向加载（先自己找，找不到再委派父），实现隔离。

但**核心类**（java.* 包）还是按双亲委派——避免用户篡改。

### Q8：findClass 和 loadClass 区别？

- `loadClass()`：整个加载流程入口，含"先委派父"的逻辑
- `findClass()`：实际"找字节流并定义类"的钩子

自定义 ClassLoader **只重写 findClass**，loadClass 用基类实现 → 自动尊重双亲委派。

### Q9：JDK 9+ 的 Platform ClassLoader 替代了什么？

替代了 JDK 8 的 **Extension ClassLoader**。
原因：JDK 9 引入模块系统，原本 `JAVA_HOME/lib/ext` 这种"扩展机制"被废除——所有 JDK 自带模块由 Platform ClassLoader 管。

### Q10：两个 ClassLoader 加载的同一个类是同一个吗？

**不是**。**类的唯一性 = 全限定名 + ClassLoader 实例**。
所以 instanceof 会返回 false，强转会 ClassCastException。这是 Tomcat 隔离原理，也是 OSGi 报错的常见根因。

## 八、答题模板（60 秒话术）

> 双亲委派：子 ClassLoader 加载类时，**先委派给父加载器**，父加载不到才自己加载。
>
> **目的**：① 安全——防止用户写恶意 `java.lang.String` 替换核心类；② 一致性——保证全局只有一个权威版本（所有 `Object` 都是同一个）；③ 顺带防重复加载。
>
> ClassLoader 体系：**Bootstrap → Ext/Platform → Application → 自定义**。父子是组合关系不是继承——通过 `parent` 字段串起来。
>
> **三个经典打破场景**：
> ① **SPI**（JDBC / JNDI）：用 Thread Context ClassLoader 让父加载器借子加载器能力；
> ② **Tomcat WebappClassLoader**：先自己找再委派，实现 webapp 间类隔离；
> ③ **OSGi**：网状 ClassLoader，按 Import/Export 加载。
>
> **怎么打破**：重写 `loadClass()`（不推荐）或用 TCCL（推荐）。
>
> **自定义 ClassLoader 标准做法**：只重写 `findClass()`，loadClass 用基类——自动尊重双亲委派。
