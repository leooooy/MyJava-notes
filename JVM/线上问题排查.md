# 线上问题排查

> 面试官最爱问的"实战题"——线上 CPU 飙高、内存泄漏、死锁、接口慢、Full GC 频繁，怎么排查？
>
> 本篇是**命令速查 + 标准排查链**：① CPU 飙高三连；② 内存泄漏排查；③ 死锁定位；④ FullGC 频繁；⑤ 接口慢；⑥ 进程消失（OOM Killer）。
>
> 工具：**jcmd / jstack / jmap / jstat / jinfo / arthas / async-profiler / JFR**。
>
> 配套：[JVM 调优](./jvm调优.md)、[JVM 参数](./jvm参数.md)。

## 一、CPU 飙高（排查标准三连）

### 1.1 现象

```bash
top
# 看到某个 java 进程 CPU 100%+
```

### 1.2 三连命令

```bash
# 步骤 1: 找占 CPU 高的进程
top
# 假设 PID = 21993

# 步骤 2: 找该进程内占 CPU 高的线程
top -Hp 21993
#   PID USER      PR  NI    VIRT    RES    SHR S  %CPU
# 22021 root      20   0 8588456 4.2g  17056 R   95.0
                                              ↑
                                        线程 ID

# 步骤 3: 转十六进制（jstack 用十六进制）
printf '%x\n' 22021
# 5605

# 步骤 4: jstack 看该线程在干啥
jstack 21993 | grep -A 30 'nid=0x5605'
```

输出示例：
```
"http-nio-8080-exec-3" #45 daemon prio=5 os_prio=0 tid=0x... nid=0x5605 runnable [...]
   java.lang.Thread.State: RUNNABLE
        at com.foo.UserService.findAll(UserService.java:42)   ← 元凶
        at com.foo.UserController.list(UserController.java:18)
        ...
```

### 1.3 常见根因

| 根因 | 特征 | 修复 |
| --- | --- | --- |
| **死循环** | 一直 RUNNABLE 在某行 | 修代码 |
| **复杂正则** | RUNNABLE 在 Pattern.matcher | 简化正则 / 加 timeout |
| **大集合 contains** | RUNNABLE 在 ArrayList.contains | 改 HashSet |
| **GC 线程繁忙** | jstack 看到大量 GC threads | 按 [GC 调优](./jvm调优.md#43-频繁-fullgc) |
| **JSON 序列化大对象** | 在 Jackson / Fastjson | 拆分 / 限制大小 |
| **死锁导致自旋** | BLOCKED 大量 | jstack 找死锁 |

### 1.4 用 arthas 更快

```bash
# 一键找最忙的线程
thread -n 5
# 直接列出 CPU 占用前 5 的线程及其堆栈
```

## 二、内存泄漏 / 频繁 FullGC

### 2.1 监控阶段

```bash
# 实时看 GC
jstat -gcutil <pid> 1000
#   S0     S1     E      O      M      CCS    YGC   YGCT   FGC   FGCT     GCT
#  0.00  85.71  100.00  98.34  92.45  88.12  450   12.34  120  45.67   58.02
                                ↑                                ↑
                            老年代 98%                       FullGC 120 次
```

`-gcutil` 字段：

| 字段 | 含义 |
| --- | --- |
| S0 / S1 / E / O | Survivor 0/1、Eden、Old 占用率 |
| M / CCS | Metaspace、压缩类空间 占用率 |
| YGC / YGCT | YoungGC 次数、累计耗时 |
| FGC / FGCT | FullGC 次数、累计耗时 |
| GCT | 累计 GC 时间 |

### 2.2 dump 分析

```bash
# 1. 触发 dump（不要在堆很大时随便跑——会 STW）
jmap -dump:format=b,file=/data/log/heap.hprof <pid>

# 2. 仅 live 对象（更小）
jmap -dump:live,format=b,file=/data/log/heap.hprof <pid>

# 3. 不能 dump 时，先看类直方图
jmap -histo:live <pid> | head -30
#  num     #instances         #bytes  class name
#    1:       2456789      590049336  [B                  ← byte[]
#    2:        923456       73876480  java.lang.String
#    3:        234567       18765360  java.util.HashMap$Node
```

### 2.3 MAT 分析步骤

1. 用 [Eclipse MAT](https://www.eclipse.org/mat/) 打开 .hprof
2. **Leak Suspects 报告**：自动列嫌疑（最常用）
3. **Dominator Tree**：看谁支配最多内存
4. 选可疑大对象 → 右键 → **Path to GC Roots** → exclude weak / soft → 找强引用持有者

> dump 文件大于 4G 时 MAT 启动堆要够大：编辑 `MemoryAnalyzer.ini` 加 `-Xmx8g`。

### 2.4 推荐用 -XX:+HeapDumpOnOutOfMemoryError

```bash
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/log/heap.hprof
```

OOM 时自动 dump，省得人工抢救。

## 三、死锁

### 3.1 jstack 自动检测

```bash
jstack -l <pid>
```

底部会输出：
```
Found one Java-level deadlock:
=============================
"Thread-1":
  waiting to lock monitor 0x00007f... (object 0x00..., a java.lang.Object),
  which is held by "Thread-0"
"Thread-0":
  waiting to lock monitor 0x00007f... (object 0x00..., a java.lang.Object),
  which is held by "Thread-1"
```

### 3.2 jconsole / VisualVM

带 GUI 的死锁检测，"Detect Deadlock" 按钮一键。

### 3.3 ReentrantLock 死锁

`jstack` **检测不到**——它只查 `synchronized` 监视器锁。
ReentrantLock 死锁要靠 **arthas 的 `thread -b`** 或人工分析 BLOCKED 线程的栈。

```bash
# arthas
thread -b
# 找出阻塞其他线程的根因线程
```

## 四、FullGC 频繁

详见 [JVM 调优 - 频繁 FullGC](./jvm调优.md#43-频繁-fullgc)。

### 4.1 速查命令

```bash
# 实时 GC 监控
jstat -gcutil <pid> 1000

# 看堆分布
jmap -heap <pid>
jcmd <pid> GC.heap_info

# GC 日志（启动加 -Xlog:gc*=info:file=gc.log）
tail -f /data/log/gc.log
```

### 4.2 三类根因区分

| FullGC 后老年代占用 | 根因 |
| --- | --- |
| 90%+ → 89%（回收很少） | **内存泄漏**（dump 分析） |
| 95% → 30%（回收很多） | **老年代不够 / 大对象**（增 -Xmx） |
| 固定时间触发 | **System.gc() 调用**（找代码） |

## 五、接口慢 / 响应延迟高

### 5.1 排查链路

```
用户感知慢
    │
    ▼
是 Java 进程慢吗？
    ├─ DB 慢 → 看慢查询日志（[MySQL SQL优化](../MySQL/sql优化.md)）
    ├─ 缓存慢 → 看 Redis 慢日志
    ├─ 网络慢 → ping / mtr / netstat
    └─ JVM 慢 → 继续往下查
            │
            ▼
        是 GC 拖累的吗？
            ├─ 是 → 按 4 节排
            └─ 否 → 是代码慢
                    │
                    ▼
                arthas 在线诊断
```

### 5.2 arthas 在线诊断

```bash
# 启动 arthas
curl -O https://arthas.aliyun.com/arthas-boot.jar
java -jar arthas-boot.jar

# 1. 看接口耗时
trace com.foo.UserService findAll
# 输出：每个调用层耗时

# 2. 看方法参数 / 返回值
watch com.foo.UserService findAll '{params, returnObj}' -x 3

# 3. 看哪个方法占 CPU
profiler start
# 跑一段时间
profiler stop --format html
# 输出火焰图

# 4. 反编译类（看上线代码版本）
jad com.foo.UserService

# 5. 查看 JVM 信息
dashboard      # 实时 dashboard
```

### 5.3 async-profiler 火焰图

```bash
./profiler.sh -d 60 -f /tmp/flame.html <pid>
```

→ 浏览器打开 flame.html，最高的最宽的方块就是热点。

## 六、进程消失（OOM Killer）

### 6.1 现象

进程没留 hprof，没留任何错误日志，悄无声息消失。`-XX:+HeapDumpOnOutOfMemoryError` 也没用。

### 6.2 根因

**OS 的 OOM Killer**——内存不足时 Linux 内核杀进程。Java 堆没爆但**直接内存 / Metaspace / Code Cache / 线程栈**占满。

### 6.3 排查

```bash
# 看内核日志
dmesg | grep -i "killed process"
# Out of memory: Kill process 12345 (java) score 900 or sacrifice child

# 看历史
journalctl -k | grep -i "out of memory"

# 容器里
kubectl describe pod <pod-name>
# 看 LastState: Reason: OOMKilled
```

### 6.4 修复

```bash
# 1. 设 NMT 排查堆外
-XX:NativeMemoryTracking=summary
jcmd <pid> VM.native_memory summary

# 2. 限制堆外
-XX:MaxDirectMemorySize=1g
-XX:MaxMetaspaceSize=512m
-Xss256k

# 3. 监控 RSS
ps -p <pid> -o rss,vsz       # 长期监控 RSS 涨势

# 4. 容器化用 MaxRAMPercentage 而不是手算
-XX:MaxRAMPercentage=75.0
```

## 七、命令速查总表

### 7.1 jcmd（瑞士军刀，推荐优先）

```bash
jcmd <pid> help                                # 列所有命令
jcmd <pid> VM.flags                            # 看启动参数
jcmd <pid> VM.system_properties
jcmd <pid> VM.uptime
jcmd <pid> VM.native_memory summary            # NMT
jcmd <pid> GC.heap_info                        # 堆信息
jcmd <pid> GC.run                              # 触发 FullGC（慎用）
jcmd <pid> GC.class_histogram                  # 类直方图
jcmd <pid> Thread.print                        # = jstack
jcmd <pid> JFR.start duration=60s filename=/tmp/x.jfr
jcmd <pid> JFR.stop name=1
```

### 7.2 jstat（实时 GC 监控）

```bash
jstat -gcutil <pid> 1000          # 每秒打印一次（百分比）
jstat -gc <pid> 1000              # 详细字节数
jstat -gccapacity <pid>           # 各区容量
jstat -class <pid>                # 类加载统计
```

### 7.3 jmap（内存）

```bash
jmap -heap <pid>                                # 堆配置和使用
jmap -histo:live <pid>                          # 类直方图（仅存活）
jmap -dump:format=b,file=heap.hprof <pid>       # 完整 dump
jmap -dump:live,format=b,file=heap.hprof <pid>  # 仅存活
```

### 7.4 jstack（线程）

```bash
jstack <pid>                  # 普通线程栈
jstack -l <pid>               # 含锁信息（死锁检测必加）
jstack -F <pid>               # 强制（进程卡死时）
```

### 7.5 jinfo（参数）

```bash
jinfo -flags <pid>            # 看启动参数
jinfo -flag MaxGCPauseMillis <pid>
jinfo -flag +PrintGC <pid>    # 运行时改 flag（仅可改的）
```

### 7.6 OS 层

```bash
top -Hp <pid>                                  # 看进程内线程 CPU
ps -mp <pid> -o THREAD,tid,time | head         # 同上
pmap -x <pid>                                  # 内存映射
strace -p <pid>                                # 系统调用（慎用，可能卡进程）
lsof -p <pid> | wc -l                          # 文件描述符数量
```

## 九、JFR + JMC（生产神器）

```bash
# 1. 启动时录制
-XX:StartFlightRecording=duration=60s,filename=/tmp/recording.jfr

# 2. 运行时启动
jcmd <pid> JFR.start duration=60s filename=/tmp/recording.jfr

# 3. dump 当前正在跑的录制
jcmd <pid> JFR.dump filename=/tmp/dump.jfr

# 4. 用 JDK Mission Control 打开
# https://www.oracle.com/java/technologies/jdk-mission-control.html
```

JFR 能采集：GC、JIT、堆分配热点、IO、Socket、文件、线程、锁、CPU 采样、安全事件……几乎一切。
**开销 < 2%**，可在生产长期开启。

## 十、典型案例

### 10.1 案例：deepClone 死循环

**现象**：CPU 100%，单线程持续 RUNNABLE。

```java
@Service
public class TreeService {
    public Tree deepClone(Tree t) {
        Tree c = new Tree(t.value);
        for (Tree child : t.children) {
            c.children.add(deepClone(child));   // ⚠️ 循环引用 → 死循环
        }
        return c;
    }
}
```

**排查**：top -Hp → jstack → 看到栈无限重复 deepClone。
**修复**：加访问标记防环。

### 10.2 案例：ThreadLocal 内存泄漏

**现象**：FullGC 后老年代不释放，MAT 看到大量 ThreadLocal$ThreadLocalMap$Entry。

**根因**：线程池里的线程长寿，`set` 后没 `remove`，Entry 的 key 是弱引用（ThreadLocal 被回收），value 是强引用——value 永不释放。

**修复**：
```java
try {
    threadLocal.set(value);
    // ... 业务
} finally {
    threadLocal.remove();    // 必须！
}
```

### 10.3 案例：日志框架阻塞所有业务线程

**现象**：业务线程大量 BLOCKED 在 log4j。

**根因**：log4j 1.x 同步写文件，磁盘满 / IO 慢时阻塞。

**修复**：升 log4j2 + AsyncAppender / Logback async。

### 10.4 案例：堆外内存泄漏（Netty）

**现象**：堆没满，进程 RSS 持续涨，最终 OOM Killer 杀。

**排查**：
```bash
-XX:NativeMemoryTracking=detail
jcmd <pid> VM.native_memory summary
# 看到 "Other" 或 "Internal" 异常大
```

**根因**：Netty ByteBuf 没 release，引用计数泄漏。

**修复**：开启泄漏检测：
```bash
-Dio.netty.leakDetection.level=advanced
```

## 十一、面试高频追问

### Q1：CPU 飙高排查链路？

`top` → `top -Hp <pid>` → `printf '%x\n' <tid>` → `jstack <pid> | grep <hex_tid> -A 30`。
或用 arthas 的 `thread -n 5`。

### Q2：怎么判断是内存泄漏还是堆设小了？

看 FullGC 后老年代回收率：
- 回收很少（前后差 < 10%）→ 内存泄漏
- 回收充分（> 50%）→ 堆设小或大对象多

### Q3：dump 大文件 MAT 跑不动？

- MemoryAnalyzer.ini 加 `-Xmx16g`
- 用 dump live：`jmap -dump:live,...`（已死对象不算）
- 用云分析平台：阿里 ATA、GCEasy.io

### Q4：jstack 检测得到 ReentrantLock 死锁吗？

**不能**。jstack 只检测 synchronized 监视器锁。ReentrantLock 死锁要靠 arthas `thread -b` 或人工分析。

### Q5：进程突然消失没留 hprof 怎么办？

OOM Killer 嫌疑——`dmesg | grep -i "killed process"` 验证。
排查方向：直接内存（Netty）/ Metaspace / 线程栈过多 / 堆外内存（NMT 看）。

### Q6：arthas 和 jstack 有什么区别？

- jstack：CLI，瞬时快照，只有线程栈
- arthas：连接式，能 trace / watch / monitor / 反编译 / 修改字节码——**功能强 100 倍**，生产线上必备

### Q7：JFR 怎么用？

启动时 `-XX:StartFlightRecording=duration=60s,filename=/tmp/x.jfr`，或运行时 `jcmd ... JFR.start`。
用 JDK Mission Control（JMC）打开分析。
**开销 < 2%**，可生产长期开。

### Q8：火焰图怎么看？

横轴是 CPU 时间，纵轴是调用栈。**最宽的方块 = 占 CPU 最多**。
async-profiler `-f flame.html`，浏览器打开。

### Q9：怎么排查接口慢？

按层排：DB → 缓存 → 网络 → JVM。
JVM 层用 arthas trace 看具体方法耗时。

### Q10：所有 JVM 监控指标里哪几个最关键？

四金刚：
1. **堆使用率**（老年代占比 > 80% 警告）
2. **FullGC 频率**（> 1 次/小时警告）
3. **GC 累计耗时占比**（> 5% 警告）
4. **直接内存 / 元空间使用率**（> 90% 警告）

## 十二、答题模板（90 秒话术）

> 线上排查标准链路：**监控告警 → 看现象 → 定位区域（CPU / 内存 / 线程 / 网络）→ 取证（dump / jstack / GC log / JFR）→ 分析（MAT / arthas / 火焰图）→ 修复 → 灰度验证**。
>
> **CPU 飙高**：`top -Hp <pid>` 找线程 → 转 16 进制 → `jstack` 看堆栈。或 arthas `thread -n 5` 一步到位。
>
> **内存泄漏**：`jstat -gcutil` 看 FullGC 后老年代回收率，回收少就是泄漏；`jmap -histo:live` 看类分布；`jmap -dump` + MAT 找支配树和 GC Roots 路径。
>
> **死锁**：`jstack -l` 自动检测 synchronized；ReentrantLock 用 arthas `thread -b`。
>
> **进程突然消失**：`dmesg | grep killed` 看 OOM Killer，开 NMT 排查堆外内存。
>
> **接口慢**：先看 DB / 缓存 / 网络是不是元凶，排除后用 arthas trace + 火焰图。
>
> **生产必备**：`-XX:+HeapDumpOnOutOfMemoryError`、GC 日志滚动、JFR / 监控 / arthas，否则线上事故等于瞎子。
