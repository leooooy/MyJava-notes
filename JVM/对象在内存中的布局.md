# 对象在内存中的布局

> 高频面试题三连击：① 一个 `Object` 对象多大？② 对象头里的 Mark Word 是什么？③ 锁状态怎么在 Mark Word 里切换？
>
> 这三个问题串起来其实是同一件事——**对象的内存布局**直接决定了 synchronized 的偏向 / 轻量 / 重量级锁怎么实现、`hashCode()` 调用后为什么不能再加偏向锁、压缩指针怎么省内存。
>
> 本篇解决：① 对象三段式布局是什么；② Mark Word 64 位完整结构；③ 压缩指针 (-XX:+UseCompressedOops) 的来龙去脉；④ 对象创建的 7 步流程；⑤ 用 JOL 实测对象大小。

---

## 一、对象的三段式布局（HotSpot 64 位）

```
┌────────────────── Object ──────────────────┐
│  对象头 Header       12 字节（开压缩指针）   │  ← 16B 不开压缩
│   ├─ Mark Word       8B (64 位)             │
│   └─ Class Pointer   4B（开压缩）/ 8B       │
├────────────────────────────────────────────┤
│  实例数据 Instance Data                     │  ← 父类 + 子类字段
│   按 8B / 4B / 2B / 1B 顺序紧排（Field 重排序）│
├────────────────────────────────────────────┤
│  对齐填充 Padding                          │  ← 凑 8 的倍数
│   0~7 字节                                  │
└────────────────────────────────────────────┘
```

**为什么对齐 8 字节**？  
HotSpot 要求对象起始地址必须是 8 的倍数。这样 32 位的对象指针 ÷ 8 后还能寻址 32GB（这就是压缩指针的原理）。

**典型大小**（开压缩指针）：
- `new Object()` = 12（头）+ 0（无字段）+ 4（填充）= **16 字节**
- `new Integer(0)` = 12 + 4（int value）+ 0 = **16 字节**
- 数组对象额外多 **4B 长度域**

## 二、对象头（Object Header）—— 重头戏

### 2.1 Mark Word（8 字节）

> 存对象的**运行时元数据**：HashCode、GC 分代年龄、锁状态、线程 ID 等。
>
> **设计精髓**：64 位空间复用——同一片 8B 在不同锁状态下含义不同。

#### 2.1.1 64 位 Mark Word 完整结构

| 锁状态 | 25 bit unused | 31 bit hashCode | 1 bit unused | 4 bit 分代年龄 | 1 bit 偏向锁标志 | 2 bit 锁标志位 |
| --- | --- | --- | --- | --- | --- | --- |
| **无锁** | — | hashCode | — | age | 0 | **01** |
| **偏向锁** | 54 bit 线程 ID + epoch | — | age | 1 | **01** |
| **轻量级锁** | 62 bit 指向栈中 Lock Record 的指针 | **00** |
| **重量级锁** | 62 bit 指向 Monitor 的指针 | **10** |
| **GC 标记** | — | **11** |

**关键点**：**最后 2 bit 是锁状态机**——`01 / 00 / 10 / 11` 四种状态 + 偏向锁专用的第 3 bit。

#### 2.1.2 锁升级路径

```
无锁 (01, 偏向位=0)
   ↓ 第一个线程调用 synchronized
偏向锁 (01, 偏向位=1, 记录线程 ID)
   ↓ 第二个线程来抢（撤销偏向）
轻量级锁 (00, 指向当前线程栈中的 Lock Record)
   ↓ CAS 自旋失败 / 等待线程 > 1
重量级锁 (10, 指向 ObjectMonitor)
```

> 详见 [Synchronized](../Concurrency/Synchronized.md)、[锁](../Concurrency/锁.md)。

#### 2.1.3 调 hashCode 之后的副作用（高频追问）

```java
Object o = new Object();
synchronized(o) { ... }       // ✅ 正常进入偏向 / 轻量
o.hashCode();                  // ⚠️ 把 hashCode 写进 Mark Word
synchronized(o) { ... }       // ❌ 此对象再也无法获得偏向锁
```

**根因**：hashCode 占 31 bit，挤占了偏向锁要存"线程 ID + epoch"的位置。
- **无锁 → 偏向锁**：被禁止，直接进入轻量级锁
- **已偏向 → 调 hashCode**：偏向锁直接撤销升级到重量级锁（hashCode 要存到 ObjectMonitor 里）

> ⚠️ JDK 15 起偏向锁默认关闭（`-XX:UseBiasedLocking=false`），现代 JVM 上这个坑反而少了。

### 2.2 Class Pointer（类型指针）

指向方法区中该对象的 Klass 元数据，让 JVM 知道这是什么类。

- 不开压缩：8B
- 开压缩（`-XX:+UseCompressedClassPointers`，默认开）：4B

### 2.3 数组的额外字段：Length

```
数组对象布局
├─ Mark Word (8B)
├─ Class Pointer (4B / 8B)
├─ Length (4B)        ← 数组特有
├─ 元素数据
└─ Padding
```

JVM 必须知道数组长度（普通对象通过 Klass 推算字段总长度，数组长度运行时才确定）。

## 三、压缩指针（CompressedOops）

> 64 位 JVM 默认开启，能省 30%~50% 内存。

### 3.1 为什么要压缩

64 位机器上，对象引用本来 8B；但堆 < 32GB 时其实只需要 4B 表示。

**原理**：
- 对象起始地址 = 8 的倍数 → 引用低 3 位永远是 0
- 32 位指针 × 8 = 35 位寻址空间 = **32 GB**

### 3.2 何时关闭

```bash
-XX:-UseCompressedOops     # 关闭对象指针压缩
-XX:-UseCompressedClassPointers  # 关闭类指针压缩
```

- 堆 > 32GB：压缩失效，自动关闭
- 堆 28~32GB 区间反而比 32GB+ 更费内存（指针压缩 + 大堆开销）→ 这就是著名的"**32GB 堆陷阱**"，要么 ≤ 32GB，要么直接上 64GB+

### 3.3 -Xmx 31GB 比 33GB 内存利用率还高（生产经验）

```
堆设 31GB（开压缩） → 实际可用约 31GB（指针 4B）
堆设 33GB（关压缩） → 实际可用约 28GB（指针 8B 全面膨胀）
```

→ **要么 ≤ 31GB，要么直接 ≥ 48GB**，避开 32~48GB 这个负优化区间。

## 四、实例数据布局（Field Rearrangement）

JVM 不按源码顺序排字段，而是按**对齐策略重排**：

**默认排序**：long/double (8B) → int/float (4B) → short/char (2B) → byte/boolean (1B) → 引用 (4B/8B)

**为什么重排**：CPU 访问对齐数据更快，避免跨缓存行；同时尽量填满每一行减少 padding。

**子类字段不会插入父类字段间**——父类字段先放，子类字段紧跟。但子类字段有自己的对齐边界。

```java
class A { long a; byte b; }
class B extends A { long c; byte d; }
```

布局（开压缩）：
```
[Header 12B][a 8B][b 1B][padding 3B]   ← A 的字段
[c 8B][d 1B][padding 7B]               ← B 的字段
```

> 注意：**不同 JVM 实现允许不同排序**。Oracle JDK 默认开 `-XX:FieldsAllocationStyle=1`（先放父类）。

### 4.1 用 JOL 实测

Maven：
```xml
<dependency>
    <groupId>org.openjdk.jol</groupId>
    <artifactId>jol-core</artifactId>
    <version>0.16</version>
</dependency>
```

```java
import org.openjdk.jol.info.ClassLayout;

System.out.println(ClassLayout.parseInstance(new Object()).toPrintable());
```

输出（典型）：
```
java.lang.Object object internals:
OFFSET  SIZE   TYPE DESCRIPTION                    VALUE
     0     4        (object header)                01 00 00 00
     4     4        (object header)                00 00 00 00
     8     4        (object header)                e5 01 00 f8
    12     4        (loss due to the next object alignment)
Instance size: 16 bytes
```

## 五、对象创建的 7 步（必背）

```
new Object()
   │
   ▼
1. 检查类加载
   找常量池里 Object 的符号引用 → 是否已加载？没加载触发类加载
   │
   ▼
2. 分配内存
   ├─ 指针碰撞（Bump-the-Pointer）：内存规整时（Serial/ParNew）
   └─ 空闲列表（Free List）：内存碎片化时（CMS）
   │
   并发分配靠 ↓
   ├─ CAS + 失败重试（HotSpot 早期）
   └─ TLAB（每线程独占缓冲，优先用）
   │
   ▼
3. 内存清零
   字段默认值（int=0, Object=null, boolean=false）
   ⚠️ TLAB 分配可省此步（TLAB 申请时已清零）
   │
   ▼
4. 设置对象头
   Mark Word（无锁状态）+ Class Pointer + Hash 等
   │
   ▼
5. 执行 <init> 方法
   ├─ 父类构造器
   ├─ 字段显式初始化
   └─ 构造代码块 + 构造函数
   │
   ▼
6. 返回对象引用给栈帧的局部变量表
```

> **追问**：为什么先清零再设头？  
> 答：JMM 要求字段读到的初始值至少是默认值，不能是别人遗留的脏数据；对象头是元信息，最后写。实际 HotSpot 实现里这两步顺序可调，关键是**对外可见时必须是合法状态**。

## 六、对象的访问定位

```java
Object o = new Object();   // o 是引用，存在栈
                            // new Object() 实例存在堆
```

JVM 怎么通过 `o` 找到堆里的对象？两种实现：

| 方式 | 引用存什么 | 找对象 | 找类型 | 优缺点 |
| --- | --- | --- | --- | --- |
| **句柄** | 句柄池地址 | 句柄→实例池 | 句柄→类型池 | 对象移动时只改句柄，引用稳定；多一次跳转 |
| **直接指针**（HotSpot） | 对象地址 | 直接访问 | Class Pointer | **快**，只一次寻址；GC 移动对象需更新所有引用 |

HotSpot 用直接指针——以**对象移动成本** 换 **访问性能**（移动是 GC 的事，访问是每秒亿次的事）。

## 七、生产踩坑

### 7.1 对象太大撑爆缓存行（False Sharing）

```java
class Counter {
    volatile long a;  // 8B
    volatile long b;  // 8B  ← 与 a 在同一 64B 缓存行
}
```

线程 1 改 `a`，线程 2 改 `b`，**伪共享**导致缓存行反复失效。

**解法**：JDK 8+ 用 `@Contended` 注解填充（启动加 `-XX:-RestrictContended`）：
```java
@Contended
volatile long a;
@Contended
volatile long b;
```

或手动 Padding 7 个 long：
```java
long p1, p2, p3, p4, p5, p6, p7;
```

### 7.2 Map.Entry 大量小对象 + 16B 对齐导致内存浪费

```java
Map<Integer, Integer> map = new HashMap<>(); // 一千万个 Entry
```

每个 Entry：12B 头 + 4B hash + 4B key 引用 + 4B value 引用 + 4B next 引用 + padding = 32B
+ 装箱 Integer：16B × 2 = 32B
→ 单个 Entry 实际占 64B，1000 万 = **610MB**

**解法**：用 `int[] / long[]` 直接存原始类型，或用 Eclipse Collections / Trove4j 等原始类型集合。

### 7.3 字符串大量 padding 浪费

`String s = "A"` → 12B 头 + 4B value 引用 + 4B hash + padding = 24B
JDK 9+ Compact String 优化：`byte[] value` 替代 `char[]`，存纯 ASCII 时省 50%。

## 八、面试高频追问

### Q1：一个 `new Object()` 对象多大？

64 位 JVM 开压缩指针：**16 字节**
- Mark Word: 8B
- Class Pointer: 4B
- 实例数据: 0B
- Padding: 4B（凑齐 16）

不开压缩指针：16 字节（Class Pointer 8B，padding 0B）。

### Q2：Mark Word 里都存什么？

**复用同一片 8B**，按锁状态切换含义：
- 无锁：HashCode + 分代年龄 + 锁标志位
- 偏向锁：线程 ID + epoch + 年龄 + 标志位
- 轻量级锁：指向栈中 Lock Record 的指针 + 标志位
- 重量级锁：指向 ObjectMonitor 的指针 + 标志位

### Q3：调过 hashCode 的对象还能用偏向锁吗？

**不能**。HashCode 占 31 bit 写到了原本要存"线程 ID"的位置——偏向锁因此被禁用，直接进入轻量级锁；如果当时已经偏向，则升级到重量级锁。

### Q4：压缩指针为什么能用 4B 表示 32GB 堆？

对象起始地址都是 8 字节对齐 → 引用值低 3 位恒为 0 → 4B（32 bit）的指针实际可寻址 `2^32 × 8 = 32GB`。

### Q5：堆为什么不要设成 32~48GB 之间？

32GB 是压缩指针上限，超过会自动关压缩，所有引用从 4B 变 8B → 内存全面膨胀。
**经验值**：要么 `-Xmx ≤ 31GB`，要么 `-Xmx ≥ 48GB` 才能用回省下的内存。

### Q6：对象访问用句柄还是直接指针？

HotSpot 用**直接指针**——访问快，但 GC 移动对象时要更新所有引用。
句柄方式访问慢一次跳转，但移动对象只改句柄表——大多数 JVM 没采用。

### Q7：为什么父类字段先排？

JVM 规范允许实现自定义排序，但**父类字段排在前面是 HotSpot 的默认**——这样子类对象可以直接被当作父类对象访问，offset 完全对得上（多态实现的内存基础）。

### Q8：实例数据为什么不按声明顺序排？

按对齐策略重排（long/double → int → short → byte → 引用），目的是**减少 padding 浪费**。例如 `byte b; long l; byte b2;` 按声明顺序要 padding 14B；重排后只 padding 6B。

### Q9：对象创建过程中，哪些步骤可能并发？

`new` 在字节码层面是 `new + dup + invokespecial <init>`，**不是原子的**。
- "分配内存" 和 "初始化为零值" 两步之间、或 init 期间可能被另一线程看到"半初始化对象"
- 这就是 **DCL（Double-Checked Locking）单例必须用 volatile** 的根因——禁止指令重排让"未初始化对象"被发布

### Q10：数组对象和普通对象布局有什么不同？

数组多一个 4B 的 Length 字段（在 Class Pointer 之后、元素数据之前），因为 JVM 必须运行时知道数组长度。

## 九、答题模板（60 秒话术）

> Java 对象在堆中的内存布局分**三段**：**对象头 / 实例数据 / 对齐填充**，要求 8 字节对齐。
>
> **对象头**含 Mark Word（8B，存 HashCode / 分代年龄 / 锁状态）和 Class Pointer（指向方法区的 Klass，开压缩 4B）；数组多一个 4B 的 Length。
>
> **Mark Word** 是 64 位空间复用——同一片 8B 在无锁 / 偏向 / 轻量 / 重量四种状态下含义不同，最后 2 bit 是锁状态机。⚠️ 调过 hashCode 的对象不能再加偏向锁——HashCode 挤占了线程 ID 的位置。
>
> **实例数据**按对齐重排（long → int → short → byte → 引用），父类字段先排；**Padding** 凑齐 8 的倍数。
>
> **压缩指针**（默认开）让 64 位机的引用从 8B 压成 4B，前提是堆 ≤ 32GB——超过自动关闭，所以堆要么 ≤ 31GB 要么 ≥ 48GB，避开负优化区间。
>
> **访问对象**用直接指针（HotSpot）——快，但 GC 移动对象要更新所有引用。
>
> **创建流程 7 步**：检查类加载 → 分配内存（指针碰撞 / 空闲列表 + TLAB 优先）→ 清零 → 设对象头 → 执行 \<init\> → 返回引用。
