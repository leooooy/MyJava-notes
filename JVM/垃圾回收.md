# 垃圾回收（GC）

> 必考四大件之一。GC 这块面试链路最长，几乎能问 30 分钟：
> ① 怎么判断对象是垃圾（引用计数 vs 可达性分析）→
> ② 引用强度（强 / 软 / 弱 / 虚）→
> ③ 三大算法（标记清除 / 复制 / 标记整理）→
> ④ 分代假说 + 跨代引用 → 卡表 / Remember Set →
> ⑤ Stop The World 与三色标记 / 漏标 → CMS 增量更新 vs G1 SATB →
> ⑥ 收集器演进：Serial → Parallel → CMS → G1 → ZGC / Shenandoah
>
> 本篇覆盖前 5 块核心理论，G1 / 收集器全景在 [G1垃圾回收器](./G1垃圾回收器.md) 和 [收集器全景](./收集器全景.md)。

## 一、判断对象存活：引用计数 vs 可达性分析

### 1.1 引用计数（Reference Counting）

```
每个对象一个引用计数器
   ├─ 被引用 +1
   ├─ 引用失效 -1
   └─ 计数为 0 → 可回收
```

**优点**：实现简单，回收即时。

**致命缺陷**：**循环引用无法回收**。

```java
class Node { Node next; }

Node a = new Node();
Node b = new Node();
a.next = b;
b.next = a;
a = null;
b = null;
// 引用计数器都是 1，永远不为 0 → 内存泄漏
```

→ Java、C# 等主流 JVM **不用引用计数**。Python、Swift 用，但都需要配合循环检测。

### 1.2 可达性分析（Reachability Analysis）—— Java 用的方法

```
GC Roots
   │
   ├─→ 对象 A ──→ 对象 B ──→ 对象 C   ← 这些都"可达"
   │              ↑
   │              └── 对象 D
   │
   └─→ 对象 E

      对象 X ←─→ 对象 Y    ← 互相引用但和 GC Roots 没连通 → 可回收
```

**核心**：从 GC Roots 出发，能追到的对象都活着；追不到的就是垃圾——**即使有循环引用**也能识别。

### 1.3 GC Roots 包括哪些（必背）

| 来源 | 例子 |
| --- | --- |
| **虚拟机栈**（栈帧的局部变量表）的引用 | 当前方法的局部变量 / 方法参数 |
| **本地方法栈**（JNI 的引用） | C++ 代码持有的 Java 对象引用 |
| **方法区中类静态属性**引用的对象 | `static Foo foo = new Foo();` |
| **方法区中常量**引用的对象 | `final Foo FOO = new Foo();` |
| **被 synchronized 锁住**的对象 | `synchronized(obj)` 中的 obj |
| **JVM 内部引用** | 基本类型 Class 对象（`int.class`）、异常对象（OutOfMemoryError） |
| **正在运行的线程** | Thread 对象本身 |
| **GC 跨代引用** | 由其它代的 RememberSet 标记的对象（局部 GC 时） |

> 口诀：**两栈两方法 + 锁 + 线程**（栈、本地栈、方法区 static、方法区常量、synchronized、活跃线程）。

## 二、四种引用强度（高频题）

> JDK 1.2 起把引用细分为强/软/弱/虚——给 GC 提供不同回收策略。

| 引用类型 | 回收时机 | 用途 |
| --- | --- | --- |
| **强引用 Strong** | 永远不回收（直到 GC Roots 不可达） | 默认，`Object o = new Object()` |
| **软引用 Soft** | **内存不足时回收** | 缓存（图片缓存、对象缓存） |
| **弱引用 Weak** | **下次 GC 必回收**（无视内存够不够） | ThreadLocal 的 Entry、WeakHashMap |
| **虚引用 Phantom** | 任何时候都可能被回收（拿不到对象） | **跟踪对象被回收的通知**（DirectByteBuffer 的 Cleaner） |

### 2.1 软引用（SoftReference）

```java
SoftReference<byte[]> ref = new SoftReference<>(new byte[1024 * 1024]);
byte[] data = ref.get();   // 可能拿到，也可能 null
```

JVM 会在 OOM 之前把所有 SoftReference 引用的对象清掉——**最后的求生**。

> ⚠️ 别拿 SoftReference 当万能缓存——回收时机不可控，命中率不稳定。生产用 Caffeine / Guava Cache 更合理。

### 2.2 弱引用（WeakReference）

```java
WeakReference<Object> ref = new WeakReference<>(new Object());
System.gc();
ref.get();   // 大概率 null
```

**典型应用**：
- **WeakHashMap**：key 是弱引用，key 没强引用了 entry 自动消失
- **ThreadLocal.ThreadLocalMap.Entry**：key 弱引用 ThreadLocal，避免 ThreadLocal 不能被回收

### 2.3 虚引用（PhantomReference）

```java
ReferenceQueue<Object> queue = new ReferenceQueue<>();
PhantomReference<Object> ref = new PhantomReference<>(obj, queue);
ref.get();   // 永远返回 null
// 当 obj 被 GC 时，ref 进入 queue → 可以做善后清理
```

**典型应用**：DirectByteBuffer 用 `Cleaner extends PhantomReference`，对象被 GC 时触发 `Cleaner.clean()` 释放堆外内存。

### 2.4 finalize() —— 垂死挣扎（不要用）

```java
@Override
protected void finalize() {
    // GC 给对象的最后一次机会——可以重新被 GC Root 引用
}
```

- **只调用一次**——救活后下次 GC 不会再调
- **不可预测**——FinalizerThread 优先级低，可能很久才执行
- **JDK 9+ 已 deprecated**

→ **生产严禁使用**。资源清理用 try-with-resources 或显式 close。

## 三、三大经典 GC 算法

### 3.1 标记-清除（Mark-Sweep）—— 最古老

```
标记阶段：从 GC Roots 出发标记所有可达对象
清除阶段：扫描整个堆，清除未标记对象

[可达][垃圾][可达][垃圾][垃圾][可达]   清除前
[可达][    ][可达][    ][    ][可达]   清除后  → 大量碎片
```

**优点**：实现简单。  
**缺点**：
- **碎片化**：清后不整理，再分配大对象时找不到连续空间 → 提前触发 FullGC
- **效率低**：扫描整个堆

### 3.2 复制（Copying）—— 新生代用

```
把内存分两半，每次只用一半。
GC 时把存活对象复制到另一半，原一半全清空。

A: [O1][O2][O3][O4]    B: [           ]   GC 前

GC: 把存活的 O1, O3 复制到 B

A: [           ]       B: [O1][O3]       GC 后  → A 清空，下次写 B
```

**优点**：
- 无碎片
- 分配只需 bump-pointer（指针碰撞）

**缺点**：**浪费一半内存**——所以做了优化：

#### 3.2.1 Eden + 2 Survivor 优化

```
Eden : S0 : S1 = 8 : 1 : 1

新对象 → Eden
GC：把 Eden + S0 的存活对象复制到 S1
       清空 Eden + S0
       下一轮把 Eden + S1 的存活对象复制到 S0
```

**只浪费 10%**（一个 Survivor）而不是 50%。

依据：**98% 的新对象很快死亡** → 大部分新生代对象在第一次 GC 就被清理了。

### 3.3 标记-整理（Mark-Compact）—— 老年代用

```
标记阶段：同标记-清除
整理阶段：把存活对象往一端移动，然后清掉边界外

[可达][垃圾][可达][垃圾][垃圾][可达]   整理前
[可达][可达][可达][         ]         整理后  → 无碎片
```

**优点**：无碎片，空间利用率高  
**缺点**：移动对象成本高（需要更新所有引用 + STW 时间长）

### 3.4 三种算法对比

| 算法 | 优点 | 缺点 | 用在 |
| --- | --- | --- | --- |
| 标记-清除 | 简单 | 碎片化 | CMS（除最后整理） |
| 复制 | 无碎片、快 | 浪费空间 | **新生代** |
| 标记-整理 | 无碎片、节约空间 | 移动开销大 | **老年代** |

## 四、分代收集理论

### 4.1 两个核心假说

1. **弱分代假说（Weak Generational Hypothesis）**：绝大多数对象都是朝生夕死
2. **强分代假说（Strong Generational Hypothesis）**：熬过越多次 GC 的对象越难死

→ 把堆分新生代 + 老年代，**新生代用复制（针对短命）、老年代用标记-整理（针对长命）**。

### 4.2 跨代引用假说

> **跨代引用相对于同代引用是少数**。

否则每次 Minor GC 都要扫描整个老年代找引用——成本不可接受。

**解法**：在新生代上维护一个数据结构记录"哪些老年代对象引用了我"——叫 **Remember Set / 卡表（Card Table）**。

```
老年代被切成 N 个 512B 的"卡页"
卡表 byte[N]，每个 byte 标记对应卡页是否含跨代引用

写屏障（Write Barrier）：
  老年代对象写入新生代引用时
    → 找到所属卡页
    → 标记对应 byte 为 dirty

Minor GC 时只需扫 dirty 卡页 → 而不是整个老年代
```

→ **卡表 + 写屏障**是 GC 性能关键。G1 的 Remember Set 是这个思路的进阶（每个 Region 一个 RSet）。

### 4.3 GC 类型

| 类型 | 范围 | 触发 |
| --- | --- | --- |
| **Minor GC / Young GC** | 新生代 | Eden 满 |
| **Major GC / Old GC** | 老年代 | CMS 老年代占用阈值 |
| **Mixed GC** | 新生代 + 部分老年代 | G1 特有 |
| **Full GC** | 整个堆 + 方法区 | 各种"兜底"场景 |

#### 触发 FullGC 的常见原因

1. 调用 `System.gc()`
2. 老年代空间不足（晋升失败 / 大对象直接进老年代）
3. 方法区 / 元空间不足
4. CMS Concurrent Mode Failure
5. JDK 8 以前调 `Runtime.getRuntime().traceMethodCalls(true)`

## 五、Stop The World（STW）

> GC 进行某些操作时**所有用户线程必须暂停**——这就是 STW。

**为什么 STW**：
- 标记阶段：用户线程改对象引用，标记结果不准
- 复制 / 整理阶段：移动对象时引用必须冻结

**目标**：现代 GC（G1 / ZGC / Shenandoah）尽可能减少 STW 时间——并发标记 / 并发整理。

### 5.1 安全点（SafePoint）

JVM 不是 "立即冻结所有线程" 这么简单——线程必须跑到 **安全点**才能停。

**安全点位置**：
- 方法调用
- 循环跳转
- 异常跳转

**为什么需要安全点**：JVM 要在线程暂停时知道每个线程的"对象引用 map"——只有特定位置 JVM 才有完整的 OopMap（对象引用映射），其它位置寄存器里的值类型未知。

### 5.2 安全区域（SafeRegion）

线程已经 sleeping / blocked → 不可能跑到 safepoint → 标记自己进入 SafeRegion，GC 可以认为它就在安全点。

## 六、三色标记法（必背）

> 现代并发标记 GC（CMS / G1 / ZGC）的核心算法。

### 6.1 三色定义

| 颜色 | 含义 |
| --- | --- |
| **白** | 未被访问（可能是垃圾） |
| **灰** | 已访问，但其引用还没被遍历完 |
| **黑** | 已访问，且所有引用都已遍历 |

### 6.2 标记流程

```
初始：所有对象白色
       ↓
GC Roots 标记为灰（入待遍历队列）
       ↓
取一个灰对象 → 遍历其所有引用：
   ├─ 引用对象白色 → 标灰
   └─ 自己变黑
       ↓
直到没有灰对象
       ↓
剩下的白对象都是垃圾
```

### 6.3 漏标问题（必考）

并发标记时，用户线程改引用，可能产生**漏标**：

```
初始：A(黑) → B(灰) → C(白)
                A(黑)   B(灰)

并发标记时，用户线程做了：
   1. A.field = C   （A 现在指向 C）
   2. B.field = null （B 不再指向 C）

结果：
   A(黑) → C(白)，但 A 已黑不会再扫
   B(灰) 没指向 C 了，扫描 B 时不会发现 C
   → C 永远是白，被错杀
```

**漏标条件（同时满足）**：
1. 黑色对象新指向白色对象
2. 灰色对象不再指向该白色对象

**两种解法**：

#### 6.3.1 增量更新（Incremental Update）—— CMS 用

> **针对条件 1**：黑→白的引用建立时记下来，并发标记结束后 STW 阶段重新扫这些黑对象。

```
A.field = C  时
   → 写屏障：把 A 重新放回灰队列
   → 重新标记阶段会再扫 A，发现 C 应该是灰 → 救回来
```

#### 6.3.2 原始快照（SATB - Snapshot At The Beginning）—— G1 用

> **针对条件 2**：灰对象断开白对象的引用时，把这条引用记下来。

```
B.field = null 时
   → 写屏障：把"B 原本指向 C"这条引用记下来
   → 重新标记阶段以 C 为根重新扫
```

**对比**：
- **增量更新**：关注"新引用"，扫描成本可能更高（要重扫黑对象）
- **SATB**：保留旧引用，可能浮动垃圾多（误存一些应该被回收的），但效率稳定

## 七、垃圾收集器演进

```
Serial          → Parallel       → CMS              → G1               → ZGC / Shenandoah
单线程串行       多线程并行       并发低延迟         分区软实时        几乎无停顿
1990s           2000s           2004              2012              2018+

Serial GC       Parallel GC     CMS               G1                ZGC
(新)新生代       (新)新生代       (老)老年代        (新+老)分区        (全堆)分区
ParNew          Parallel Old                    
(新)新生代       (老)老年代       
```

| 收集器 | 区域 | 算法 | 并发? | 默认? |
| --- | --- | --- | --- | --- |
| Serial | 新生代 | 复制 | 串行 | 客户端默认（已少见） |
| Serial Old | 老年代 | 标记-整理 | 串行 | — |
| ParNew | 新生代 | 复制 | 并行 | 配 CMS |
| Parallel Scavenge | 新生代 | 复制 | 并行（吞吐优先） | JDK 8 默认 |
| Parallel Old | 老年代 | 标记-整理 | 并行 | 配 PS |
| **CMS** | 老年代 | 标记-清除 | **并发** | JDK 14 已删 |
| **G1** | 全堆（Region） | 标记-整理 + 复制 | 并发 | **JDK 9+ 默认** |
| **ZGC** | 全堆（Region） | 染色指针 + 读屏障 | 并发 | JDK 11+ 实验 → JDK 15+ 生产可用 |
| Shenandoah | 全堆（Region） | Brooks 指针 + 读屏障 | 并发 | OpenJDK 12+ |

详见 [收集器全景](./收集器全景.md)、[G1垃圾回收器](./G1垃圾回收器.md)。

### 7.1 CMS 的问题（为什么被淘汰）

1. **CPU 敏感**：并发标记线程数 = (CPU+3)/4，4 核机吃掉 1 核
2. **浮动垃圾 + Concurrent Mode Failure**：并发期间产生新垃圾来不及回收，老年代不够 → 退回 Serial Old 全 STW（致命）
3. **碎片化**：标记-清除算法的天然问题，CMS 用 `-XX:+UseCMSCompactAtFullCollection` 在 FullGC 时整理，但带来更长 STW
4. **JDK 9 deprecated，JDK 14 删除**

## 八、GC 调优实战

### 8.1 频繁 FullGC 排查

```bash
# 1. 看 GC 日志
-Xlog:gc*:file=gc.log:time,uptime:filecount=10,filesize=100M

# 2. 实时监控
jstat -gcutil <pid> 1000     # 每秒打印一次
# 输出：S0 S1 E O M CCS YGC YGCT FGC FGCT GCT
#  S0/S1/E/O/M：各代占用率
#  YGC/FGC：YoungGC/FullGC 次数
#  YGCT/FGCT：累计耗时

# 3. 看是不是大对象 / 内存泄漏
jmap -histo:live <pid> | head -30

# 4. dump
jmap -dump:format=b,file=heap.hprof <pid>
# 用 MAT / JProfiler 打开

# 5. 看分代分布
jmap -heap <pid>
```

### 8.2 调优思路

| 现象 | 可能根因 | 调优方向 |
| --- | --- | --- |
| YoungGC 频繁（< 1s 一次） | 新生代太小 / 对象分配速率高 | 增大 -Xmn 或检查热点代码 |
| YoungGC 单次时间长 | 新生代太大 / Survivor 复制过多 | 调小 -Xmn / 调 SurvivorRatio |
| FullGC 频繁 | 老年代不够 / 内存泄漏 | dump 分析 / 增大 -Xmx / 改用 G1 |
| FullGC 单次很久（10s+） | 老年代很大 + 标记整理慢 | 改用 G1（Region 化分摊 STW） |
| Concurrent Mode Failure | CMS 老年代不够触发退化 | 升 G1 / 增大老年代 |
| Promotion Failed | YoungGC 时晋升失败 | 增大老年代 / 调晋升年龄 |

### 8.3 关键参数（详见 [JVM 参数](./jvm参数.md)）

```bash
# 堆
-Xms4g -Xmx4g                    # 堆大小
-Xmn1.5g                         # 新生代

# GC 选择
-XX:+UseG1GC                     # G1（推荐 JDK 8+）
-XX:MaxGCPauseMillis=200         # G1 期望最大停顿

# Survivor 比例
-XX:SurvivorRatio=8              # Eden:S0:S1 = 8:1:1
-XX:MaxTenuringThreshold=15      # 晋升年龄

# 大对象
-XX:PretenureSizeThreshold=1m    # 大对象直进老年代

# OOM
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/heap.hprof
```

## 九、生产踩坑

### 9.1 大对象触发 PromotionFailed

```
现象：YGC 突然变慢，伴随 FullGC 飙升
根因：业务突然产生 100MB 的 List → Survivor 放不下 → 直进老年代 → 老年代很快满 → FullGC
修复：
  1. 排查代码（避免一次性加载大数据）
  2. 增大 -Xmn 让 Survivor 能装下
  3. 调 -XX:PretenureSizeThreshold 让大对象直接进老年代（避免反复复制）
```

### 9.2 显示调用 System.gc() 触发 FullGC

```
现象：固定时间出现 FullGC，业务无变化
根因：某个组件（特别是老的 RPC、Netty 早期版本）显式调 System.gc() 触发 DirectByteBuffer 回收
修复：-XX:+DisableExplicitGC（禁用 System.gc）
     ⚠️ 但要确保堆外内存有别的回收机制（Netty 用引用计数 OK）
```

### 9.3 元空间无限涨

详见 [内存区域 - Metaspace OOM](./内存区域.md#41-元空间-oom最常见)。
**必设** `-XX:MaxMetaspaceSize`。

### 9.4 堆大小不当 GC 卡死

8 核机器 -Xmx32g 用 Parallel GC → FullGC 一次卡 30s+
**修复**：升 G1 / ZGC，分区化把 STW 压到几百 ms。

### 9.5 finalize() 拖死 FinalizerThread

某些类（DirectByteBuffer 老版本、第三方）大量用 finalize → FinalizerThread 处理不过来 → 这些对象一直不回收 → OOM。
**根治**：不用 finalize。生产排查用 `jstack` 看 FinalizerThread 队列长度。

## 十、面试高频追问

### Q1：怎么判断对象是垃圾？

可达性分析——从 GC Roots 出发追引用链，追不到的就是垃圾。
不用引用计数因为解决不了循环引用。

### Q2：GC Roots 包括哪些？

栈帧本地变量、本地方法栈 JNI 引用、方法区静态属性 / 常量、被 synchronized 锁住的对象、活跃线程、JVM 内部引用、跨代引用 RSet 标记的对象。

### Q3：四种引用强度的区别和用途？

- 强：永不回收（默认）
- 软：内存不够时回收（缓存）
- 弱：下次 GC 必回收（WeakHashMap、ThreadLocal）
- 虚：拿不到对象，用于通知（DirectByteBuffer.Cleaner）

### Q4：为什么 finalize() 不可靠？

不可预测调用时机、只调一次、FinalizerThread 优先级低、可能拖垮 GC。JDK 9 已 deprecated。资源清理用 try-with-resources。

### Q5：三种 GC 算法的优劣和应用？

- 标记-清除：简单但碎片化
- 复制：快无碎片但浪费空间 → **新生代**（朝生夕死）
- 标记-整理：无碎片但移动开销 → **老年代**（存活率高）

### Q6：为什么新生代分 Eden + 2 Survivor，比例 8:1:1？

因为 98% 新对象很快死亡——只需要 10% 的空间就够装存活的。两个 Survivor 是为了**复制算法切换 from/to**，避免每次 GC 都要预留独立的复制目标空间。

### Q7：跨代引用怎么处理？卡表是什么？

老年代被切成 512B 的卡页，卡表 byte[N] 标记每个卡页是否有跨代引用。
写屏障：老年代写入新生代引用时，标记对应卡页 dirty。
Minor GC 时只扫 dirty 卡页 → 不用扫整个老年代。

### Q8：三色标记法的漏标怎么解决？

漏标条件（同时满足）：① 黑对象新指向白对象 ② 灰对象断开白对象引用。
- **CMS 用增量更新**：写屏障在黑→白引用建立时把黑重新标灰
- **G1 用 SATB**：写屏障在灰→白断开时记录原引用，以白对象为根重新扫

### Q9：什么是 Stop The World？为什么需要安全点？

GC 时所有用户线程暂停。
线程必须跑到安全点才能停——只有方法调用 / 循环跳转 / 异常跳转处 JVM 才有完整的 OopMap 知道哪些寄存器存对象引用。

### Q10：FullGC 触发条件？

- 调 System.gc()
- 老年代空间不足（晋升失败 / 大对象直进老年代）
- 元空间不足
- CMS Concurrent Mode Failure
- 显式触发的某些操作

### Q11：CMS 为什么被淘汰？

四个致命伤：① CPU 敏感（吃 1/4 核）② Concurrent Mode Failure 退化为 SerialOld（巨长 STW）③ 标记-清除碎片化 ④ 维护复杂。
JDK 9 deprecated，JDK 14 删除。**G1 全面接班**。

## 十一、答题模板（90 秒话术）

> Java 用**可达性分析**判断对象是否存活——从 **GC Roots**（栈帧本地变量 / 静态字段 / 常量 / JNI 引用 / 活跃线程）追引用链，追不到的对象是垃圾。引用还分**强 / 软 / 弱 / 虚**四级别。
>
> 三大算法：**标记-清除**（碎片）/ **复制**（浪费空间但快）/ **标记-整理**（无碎片但移动慢）。
> 基于**分代假说**——98% 对象朝生夕死——堆分**新生代（复制，Eden+S0+S1=8:1:1）**和**老年代（标记-整理）**。
>
> **跨代引用**用**卡表（Card Table）+ 写屏障**优化——512B 卡页，老年代写新生代引用时标 dirty，Minor GC 只扫 dirty 卡页。
>
> 现代并发标记用**三色标记**（白未访问 / 灰部分访问 / 黑全访问）。**漏标**靠两种解法：CMS 用**增量更新**（写屏障关注黑→白新引用），G1 用 **SATB 原始快照**（写屏障关注灰→白断开）。
>
> **Stop The World** 不可避免——但要等线程跑到**安全点**（含 OopMap 的位置）才能停。
>
> 收集器演进：**Serial → Parallel（吞吐优先）→ CMS（低延迟，已删）→ G1（JDK 9+ 默认，分区软实时）→ ZGC / Shenandoah（亚毫秒，染色指针 + 读屏障）**。
>
> 调优套路：日志（`-Xlog:gc*`）→ jstat 监控 → jmap dump → MAT 分析。**避免 FullGC** 是核心目标——大对象、内存泄漏、System.gc()、元空间无限涨是常见根因。
