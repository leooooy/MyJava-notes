# G1 垃圾回收器

> JDK 9+ 默认 GC，几乎所有现代 Java 服务（Spring Boot / Kafka / Elasticsearch）都跑在 G1 上。
>
> 本篇解决：① G1 凭什么取代 CMS；② Region 化的内存布局；③ Mixed GC 与可预测停顿模型怎么实现；④ Remember Set + Card Table + 写屏障 + SATB 在 G1 里怎么协作；⑤ 调优实战与典型坑。
>
> 前置：[垃圾回收](./垃圾回收.md)（三色标记 / SATB / 卡表）。

---

## 一、G1 是什么

**G1 = Garbage-First Garbage Collector**

由 Sun（后被 Oracle 收购）2004 提出，2012 在 JDK 7u4 正式发布，**JDK 9 起成为默认**。

### 1.1 设计目标

针对 CMS 的痛点（碎片化 / Concurrent Mode Failure / 大堆 STW 不可控），G1 给出三个新承诺：

1. **可预测的停顿时间**（软实时）—— 用户用 `-XX:MaxGCPauseMillis=200` 指定期望 STW 不超过 200ms
2. **大堆友好** —— 推荐堆 ≥ 6GB，最高数十 GB
3. **无碎片** —— 整体看是标记-整理，局部看是复制

### 1.2 核心设计：Region 化

```
传统分代：
┌──── Young ────┬──────── Old ────────┐
│  Eden│ S0│ S1│                      │
└──────────────┴──────────────────────┘
   连续内存

G1 分代：
┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
│E │O │S │O │E │ U│O │E │ U│O │ H│ H│O │
└──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘
   E=Eden   S=Survivor   O=Old   U=Unused   H=Humongous
   每个 Region 1~32MB（必须是 2 的幂），默认根据堆大小自动算
   
   总数 ≤ 2048 个 Region
```

**关键点**：
- 物理上**不再有连续的 Eden / Old 区** —— 每个 Region 角色动态分配
- **逻辑上仍然分代** —— Region 标记自己是 E / S / O / H
- **大对象**（> Region 一半）单独放 **Humongous Region**（连续多个 Region）

> **追问**：Region 大小怎么定？  
> 答：`-XX:G1HeapRegionSize` 可手动指定 1~32MB（必须 2 的幂）；不指定则按 `堆大小 / 2048` 自动选。生产堆 8GB → 4MB Region，堆 32GB → 16MB Region。

## 二、Region 类型与分配

### 2.1 五种 Region

| 类型 | 用途 | 备注 |
| --- | --- | --- |
| **Eden** | 新对象分配 | 同传统 Eden |
| **Survivor** | YGC 后存活的对象 | 同传统 Survivor |
| **Old** | 长寿对象 | 同传统老年代 |
| **Humongous** | 大对象（> Region 一半） | 直接进老年代 |
| **Unused / Free** | 空闲 Region 池 | 可分配给任意角色 |

### 2.2 大对象处理（Humongous）

```
对象 > Region/2 → Humongous
   ├─ 占据连续 N 个 Humongous Region
   └─ 不通过 YGC 回收，仅 Mixed GC / Full GC 回收
```

**坑**：大对象浪费——比如 Region=4MB，对象 5MB → 占两个 Region = 8MB（浪费 3MB）。

**生产建议**：
- 大数组、大字符串、大 byte[] 容易踩
- 监控 `-Xlog:gc+heap=info`
- 调大 `-XX:G1HeapRegionSize` 让大对象不再 Humongous

## 三、GC 类型

| 类型 | 触发 | 范围 |
| --- | --- | --- |
| **Young GC** | Eden 满 | 所有 Eden + Survivor Region（STW，并行） |
| **Mixed GC** | 老年代占用达阈值（`InitiatingHeapOccupancyPercent`，默认 45%） | 全部 Young + 部分 Old Region（**G1 招牌特性**） |
| **Full GC** | Mixed GC 跟不上分配速度 | 全堆 STW，**Serial 单线程**（JDK 10 之前）/ 并行（JDK 10+） |

> Full GC 在 G1 里是**兜底**——一旦发生说明调优失败。**JDK 10 之前 Full GC 是 Serial 单线程**，特别慢；JDK 10+ 改为并行，但仍要避免。

## 四、Mixed GC 流程（必背）

```
① 初始标记（Initial Marking）  STW
   └─ 只标 GC Roots 直接引用的对象
   └─ 借 Young GC 的 STW 顺带做（无额外停顿）
       │
       ▼
② 并发标记（Concurrent Marking）
   └─ 与用户线程并发
   └─ 三色标记 + SATB 写屏障记录"灰→白断开"
       │
       ▼
③ 最终标记（Final / Remark）  STW
   └─ 处理 SATB 队列里的剩余引用
   └─ 时间短
       │
       ▼
④ 筛选回收（Cleanup / Evacuation）  STW
   ├─ 计算每个 Old Region 的"回收价值"（可回收空间 / STW 成本）
   ├─ 按价值排序，选 STW 预算内能装下的 Region 集合（CSet, Collection Set）
   ├─ 复制 CSet 中存活对象到空 Region（→ 整理 + 清理一步完成）
   └─ 释放 CSet 原 Region
```

**关键点**：
- ① / ③ / ④ 都是 STW，但都很短
- ② 并发执行，用户线程几乎无感
- ④ 是"复制"——把有价值 Region 的存活对象搬走，原 Region 整体释放——天然无碎片

### 4.1 名字 "Garbage First" 的由来

筛选回收阶段按 **回收价值排序，优先回收垃圾最多的 Region** —— 在 STW 预算内尽可能多回收 → 这就是 "Garbage First"。

## 五、可预测停顿模型

> G1 让用户用 `-XX:MaxGCPauseMillis=200` 指定期望最大 STW（默认 200ms）。

### 5.1 怎么实现的

```
G1 在后台维护：
   每个 Region 的 "回收成本"（基于历史数据预测）
       └─ 复制存活对象的时间
       └─ 更新 RSet 的时间
       └─ ...
   每个 Region 的 "回收收益"（垃圾占比）

筛选回收阶段：
   按 收益/成本 比排序
   挑选若干 Region 组成 CSet
   保证 ∑成本 ≤ MaxGCPauseMillis
```

### 5.2 不是硬实时

**MaxGCPauseMillis 只是期望值**，G1 会尽量满足，但不保证：
- 设太小（如 50ms）→ 单次能回收的 Region 少 → GC 频繁 → 总停顿时间反而高
- 大对象 / Region 巨大 → 复制时间不可压缩

**经验值**：100~500ms。**默认 200ms 不要乱调**。

## 六、Remember Set（RSet）—— G1 跨代引用机制

> 比传统卡表更复杂——每个 Region 一个 RSet，记"哪些其它 Region 的对象指向我"。

```
Region A          Region B (RSet 里记录"A 引用我")
[obj_a] ───→ [obj_b]
              ↑
           RSet of B = { 卡页地址 of obj_a }
```

**为什么需要**：
- 回收 Region B 时要知道哪些外部引用要更新——遍历 RSet 而不是全堆扫描
- 类似传统 Card Table，但更细粒度（每 Region 独立 RSet）

### 6.1 RSet 维护：写屏障

```
obj_a.field = obj_b
   │
   ▼ 写屏障拦截
判断：源 Region ≠ 目标 Region？
   │
   ▼ 是
把"obj_a 所在卡页"加进 obj_b 所在 Region 的 RSet
```

**代价**：写屏障比 CMS 的卡表更重——每次跨 Region 引用赋值都要更新 RSet。

→ **G1 的写性能比 CMS 略差**，但换来可预测停顿和无碎片。

### 6.2 RSet 内存开销

RSet 自己也占内存——通常占堆的 **1%~20%**，老年代多写跨 Region 引用时占用更高。

> 监控 `jcmd <pid> GC.heap_info` 查看 RSet 大小。

## 七、SATB（原始快照）—— G1 漏标解法

> G1 选 SATB 而非 CMS 的"增量更新"。

```
并发标记开始时 → 给所有引用拍快照
   │
   ▼
用户线程执行：B.field = null（B 不再引用 C）
   │
   ▼ 写屏障
把"B 原本指向 C"这条引用入 SATB 队列
   │
   ▼
最终标记阶段
   └─ 处理 SATB 队列：以这些原引用的目标为根重新扫
```

**优点**：标记结果稳定（按"快照那一刻"算），扫描效率可控。

**缺点**：**浮动垃圾**——快照之后变成垃圾的对象，本轮无法回收，下轮再来。

详见 [垃圾回收 - 三色标记](./垃圾回收.md#六三色标记法必背)。

## 八、关键参数

```bash
# 启用
-XX:+UseG1GC                                  # 启用 G1（JDK 9+ 默认）

# 停顿时间
-XX:MaxGCPauseMillis=200                      # 期望最大 STW（默认 200ms）

# 并发线程
-XX:ConcGCThreads=4                           # 并发标记线程数（默认 ParallelGCThreads/4）
-XX:ParallelGCThreads=8                       # STW 阶段并行线程数（默认 = CPU 核数，最多 8）

# Region 大小
-XX:G1HeapRegionSize=4m                       # Region 大小（1~32MB，2 的幂）

# Mixed GC 触发
-XX:InitiatingHeapOccupancyPercent=45         # 老年代占比阈值，触发并发标记（默认 45）
                                              # JDK 9+ 改名为 IHOP，自适应

# Mixed GC 单次回收 Region 数
-XX:G1MixedGCCountTarget=8                    # 一轮 Mixed GC 分几次完成（默认 8）
-XX:G1OldCSetRegionThresholdPercent=10        # 单次 Mixed GC 最多回收老年代 Region 比例

# Survivor 比例
-XX:G1NewSizePercent=5                        # 新生代最小占比
-XX:G1MaxNewSizePercent=60                    # 新生代最大占比

# 大对象
-XX:G1HeapWastePercent=5                      # 允许浪费的堆比例

# 字符串去重（节省内存）
-XX:+UseStringDeduplication                   # 重复字符串共用 char[]
```

### 8.1 生产推荐配置（JDK 11，8 核 16GB 堆）

```bash
-Xms16g -Xmx16g
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-XX:ParallelGCThreads=8
-XX:ConcGCThreads=2
-XX:InitiatingHeapOccupancyPercent=45
-XX:+UseStringDeduplication
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/heap.hprof

# GC 日志（JDK 9+ 统一日志）
-Xlog:gc*,gc+phases=trace,gc+heap=info:file=/data/log/gc.log:time,uptime,level,tags:filecount=10,filesize=100M
```

## 九、G1 vs CMS 对比（必考）

| 维度 | CMS | G1 |
| --- | --- | --- |
| **算法** | 标记-清除 | 标记-整理（局部复制） |
| **碎片** | ⚠️ 严重 | ✅ 无 |
| **STW** | 不可预测 | 可指定上限 |
| **大堆** | < 4GB 优 | ≥ 6GB 优 |
| **CPU 占用** | 1/4 核（CMS 线程） | 较少 |
| **写屏障开销** | 卡表（轻） | RSet（重） |
| **漏标** | 增量更新 | SATB |
| **Concurrent Mode Failure** | 退化 SerialOld（致命） | 退化 Full GC（也很慢） |
| **JDK 状态** | JDK 14 已删 | JDK 9+ 默认 |

### 9.1 什么时候不该用 G1

- **小堆**（< 4GB）：分区开销不划算 → Parallel GC 吞吐更优
- **极致低延迟**（< 10ms）：升 ZGC / Shenandoah
- **极致吞吐**（不在乎停顿，只追总速度）：Parallel GC

## 十、生产踩坑

### 10.1 Humongous 大对象触发频繁 Mixed GC

**现象**：服务时不时长 STW，GC 日志看到 `Humongous Allocation` 频繁。

**根因**：业务有大 byte[] / 大 String / 大 List，超过 Region/2 → 直接 Humongous → 老年代占用快速上涨 → 触发 Mixed GC。

**修复**：
1. 排查代码：拆分大对象
2. 调大 Region：`-XX:G1HeapRegionSize=16m`，让对象 < Region/2 不再 Humongous
3. 升 JDK 11+：对 Humongous Region 的回收效率更高

### 10.2 IHOP 设太低导致 Mixed GC 抖动

```
-XX:InitiatingHeapOccupancyPercent=20  # 太低
```

老年代刚到 20% 就触发并发标记 → 还没标完老年代又涨上来 → 总是在标记 → CPU 全在 GC。

**修复**：默认 45 不要乱动；JDK 9+ 用 **自适应 IHOP**（`-XX:+G1UseAdaptiveIHOP` 默认开），让 G1 自己学。

### 10.3 To-space exhausted（晋升失败）

**现象**：GC 日志见 `to-space exhausted`、`Evacuation Failure`，伴随 Full GC。

**根因**：YGC / Mixed GC 时，存活对象要复制到目标 Region，但**没有足够空闲 Region**。

**修复**：
- 增大堆 -Xmx
- 调高 `-XX:G1ReservePercent=15`（默认 10%——预留给 evacuation 的 Region 比例）
- 检查 RSet 是否过大占用了空闲 Region

### 10.4 GC 频繁但堆使用率不高

**根因**：`-XX:MaxGCPauseMillis` 设太小（如 50ms） → G1 单次能回收的 Region 太少 → 频繁 GC → 总停顿反而长。

**修复**：默认 200ms，特别低延迟才 100ms，不要 < 100ms。

### 10.5 Mixed GC 不触发，老年代涨满 → Full GC

**根因**：老年代涨速 > IHOP 触发后并发标记完成的速度 → 来不及做 Mixed GC → 直接 Full GC 退化。

**修复**：
- 降低 IHOP 让 Mixed GC 早点开始
- 增大 `-XX:G1MixedGCCountTarget`（一轮 Mixed GC 多分几次）
- 升 JDK 17+，G1 改进很多

## 十一、面试高频追问

### Q1：G1 和 CMS 有什么区别？

- 算法：CMS 标记-清除（碎片）vs G1 标记-整理 + 局部复制（无碎片）
- 内存：CMS 连续分代 vs G1 Region 化
- 停顿：CMS 不可控 vs G1 可指定上限（软实时）
- 大堆：G1 优；小堆：CMS 略优（但 CMS 已废）
- CMS 已 JDK 14 删除，G1 是 JDK 9+ 默认

### Q2：G1 为什么叫"Garbage First"？

筛选回收阶段按"回收价值（垃圾占比 / 回收成本）"排序，优先回收垃圾最多的 Region —— 在 STW 预算内最大化回收量。

### Q3：G1 的 Region 一定是 1MB 吗？

不是，1~32MB（必须 2 的幂）。`-XX:G1HeapRegionSize` 手动设；不设则按 `堆大小 / 2048` 自动算。

### Q4：什么是 Humongous Region？

对象大小 > Region/2 时，直接放 Humongous Region（占连续多个），不进 YGC 回收，只在 Mixed GC / Full GC 回收。
**坑**：浪费空间（Region=4MB，对象 5MB → 占 8MB）。

### Q5：什么是 Mixed GC？

回收"全部 Young + 部分 Old Region"的 GC —— G1 招牌特性。
触发：老年代占比达 IHOP（默认 45%）→ 并发标记完成 → 接下来若干次 GC 是 Mixed GC（默认分 8 次完成）。

### Q6：G1 能保证 MaxGCPauseMillis 吗？

不能，**只是期望值**。G1 按历史数据预测 Region 回收成本，挑选若干 Region 组成 CSet 让总成本 ≤ MaxGCPauseMillis。
设太小反而频繁 GC 总停顿更长。

### Q7：G1 怎么处理跨 Region 引用？

每个 Region 一个 **Remember Set（RSet）**，记录"哪些其它 Region 引用了我"。
通过写屏障维护——每次跨 Region 引用赋值都更新 RSet。
代价：写性能略差于 CMS，但换来快速回收。

### Q8：G1 漏标怎么解决？

用 **SATB（原始快照）**——并发标记开始时拍快照，灰→白引用断开时写屏障记录原引用，最终标记阶段以原引用为根重新扫。
代价：浮动垃圾（快照后变垃圾的本轮不回收）。

### Q9：G1 还会发生 Full GC 吗？

会——是兜底机制。触发：Mixed GC 跟不上分配速度 / Evacuation Failure。
JDK 10 之前 Full GC 是 Serial 单线程（巨慢），JDK 10+ 改并行。**生产应避免**。

### Q10：G1 和 ZGC 区别？

- G1：分区 + 标记-整理，停顿 100-500ms，堆 ~ 数十 GB
- ZGC：染色指针 + 读屏障，停顿 < 10ms，堆可 TB 级
- 选择：低延迟严苛 → ZGC；通用业务 → G1 默认就好

## 十二、答题模板（90 秒话术）

> G1 是 JDK 9+ 默认 GC，针对 CMS 的碎片化、不可控 STW、大堆吃不消三大痛点。
>
> **核心设计**：把堆切成 ≤ 2048 个 1~32MB 的 **Region**，每个 Region 角色（Eden / Survivor / Old / Humongous）动态分配——**物理不连续，逻辑仍分代**。大对象（> Region/2）单独放 Humongous Region。
>
> **三种 GC**：Young GC、**Mixed GC（招牌）**、Full GC（兜底）。Mixed GC 流程：**初始标记（借 YGC STW）→ 并发标记（SATB）→ 最终标记 → 筛选回收（按价值排 CSet）**。
>
> **可预测停顿**：用 `-XX:MaxGCPauseMillis=200` 指定期望——G1 按历史预测每个 Region 的回收成本，挑选总成本不超预算的 Region 组成 CSet。**只是期望，不是硬实时**。
>
> **跨 Region 引用** 用 **Remember Set**——每个 Region 一个 RSet，写屏障维护——比 CMS 的 Card Table 重，但换来可控 STW。
>
> **漏标** 用 **SATB**（原始快照）：并发标记开始拍快照，写屏障在灰→白引用断开时记原引用。
>
> 适用场景：堆 ≥ 6GB、能接受 100-500ms 停顿的业务。极致低延迟用 ZGC，极致吞吐用 Parallel。
>
> 生产坑：**Humongous 大对象**（拆代码或调大 Region）、**To-space exhausted**（增 ReservePercent）、**Mixed GC 跟不上**（早触发 IHOP / 升 JDK 17+）。
