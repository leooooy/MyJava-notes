# JVM 运行时数据区

> JVM 八股文里最高频的一道——"画一下 JVM 内存模型"，几乎每场面试都会问。
>
> 本篇解决：① **5 大区**到底各放什么、为什么这么分；② 线程私有 vs 共享的边界；③ 方法区 / 永久代 / 元空间的演进与坑；④ 字符串常量池在 JDK 6/7/8 的搬家史；⑤ 直接内存为什么算"堆外"却仍归 JVM 管。
>
> ⚠️ 注意区分：**运行时数据区** ≠ **Java 内存模型 JMM**。前者是物理上的内存划分，后者是线程间共享变量的访问规则，详见 [内存模型](./内存模型.md)。

│  │  （字节码行号）   （栈帧:     （Native 方法     │              │

│  │   └─ 字符串常量池**                                │             │
│  │                                                  │             │

**记忆口诀**：**5 个区 + 直接内存** = 程序计数器 / 虚拟机栈 / 本地方法栈 / 堆 / 方法区 + Direct Memory。

| 区域 | 线程私有？ | GC 涉及？ | OOM 类型 |
| --- | --- | --- | --- |
| 程序计数器 | ✅ 私有 | ❌ | **唯一不抛 OOM 的区** |
| 虚拟机栈 | ✅ 私有 | ❌ | `StackOverflowError` / `OutOfMemoryError` |
| 本地方法栈 | ✅ 私有 | ❌ | 同上 |
| 堆 | ❌ 共享 | ✅ 主战场 | `Java heap space` |
| 方法区 | ❌ 共享 | ✅ 类卸载 / 常量回收 | `Metaspace` / `PermGen space` |
| 直接内存 | — | ❌ JVM 不直接管 | `Direct buffer memory` |

## 二、线程私有区

### 2.1 程序计数器（PC Register）

> 当前线程执行字节码的**行号指示器**。

- **作用**：线程上下文切换后能恢复执行位置。
- **大小**：极小，可忽略不计。
- **特殊点**：执行 **Native 方法时为 Undefined**（Native 方法由本地方法栈管）。
- **为什么不抛 OOM**：固定大小、随线程生灭，根本不会膨胀。

> **追问**：为什么 PC 是线程私有？  
> 答：线程切换需要恢复"执行到哪一行字节码了"，每条线程必须独立保留这个游标，否则切换回来会跑乱。

### 2.2 Java 虚拟机栈（JVM Stack）

> Java 方法执行的内存模型——**每个方法 = 一个栈帧（Stack Frame）**，方法调用 = 栈帧入栈，方法返回 = 栈帧出栈。

#### 2.2.1 栈帧结构（必背）

```
栈帧 (Stack Frame)
├─ 局部变量表（Local Variables）
│    ├─ index[0]：非静态方法存 this 引用
│    ├─ index[1..N]：方法参数 + 局部变量
│    └─ slot：32 位机 4B / 64 位机 8B（long/double 占 2 slot）
├─ 操作数栈（Operand Stack）
│    └─ 字节码计算用的临时栈，JVM 是"基于栈"的执行引擎
├─ 动态链接（Dynamic Linking）
│    └─ 指向运行时常量池中该方法的引用，支持多态分派
└─ 方法返回地址（Return Address）
     └─ 正常返回：调用者下一条指令
     └─ 异常返回：异常处理器入口
```

#### 2.2.2 i++ 不是原子操作（高频追问）

```java
volatile int i = 0;
i++;   // 即使 volatile 也不安全
```

字节码层面 `i++` 拆成 3 步：
1. `iload`：从局部变量表取 i 压入操作数栈
2. `iinc` / `iadd`：栈顶 +1
3. `istore`：写回局部变量表

线程 A 执行到第 2 步，被线程 B 完整执行 3 步打断 → A 写回的是过时值 → 数据丢失。

**volatile 只解决可见性，不解决原子性**。要原子用 `AtomicInteger`（CAS）或 `synchronized`。

#### 2.2.3 异常类型

| 触发场景 | 异常 |
| --- | --- |
| 栈深度超过 `-Xss` 限制（深度递归） | `StackOverflowError` |
| 栈动态扩展时申请不到内存 | `OutOfMemoryError` |

```java
public void recurse() { recurse(); }   // StackOverflowError
```

> **生产经验**：`-Xss256k` 起步，业务复杂的服务（深调用链）开 `512k~1M`。降低 Xss 可以提升单 JVM 能开的线程数（线程多时栈是大头）。

### 2.3 本地方法栈（Native Method Stack）

- 服务于 **Native 方法**（JNI 调的 C/C++ 实现），与 JVM 栈对应。
- HotSpot **把它和 JVM 栈合二为一**——所以 `-Xss` 同时管两者。
- 同样会抛 `StackOverflowError` / `OutOfMemoryError`。
- 进入 Native 方法时，JVM 栈不再压新栈帧，而是切到本地方法栈。

> 典型 Native 方法：`System.currentTimeMillis()`、`Object.hashCode()`、`Thread.start0()`、Netty 的 epoll 调用。

## 三、堆（Heap）—— GC 主战场

### 3.1 定位

- JVM 管理的**最大一块内存**（`-Xmx` 设置上限，`-Xms` 初始大小）
- **所有线程共享**，几乎所有对象实例和数组都在这里分配
- **GC 99% 的时间都在这里**

> **生产建议**：`-Xms` 和 `-Xmx` 设成一样的，避免运行时堆动态伸缩带来的额外 STW。

### 3.2 分代结构（HotSpot 实现）

```
堆 Heap
├─ 新生代 Young Generation（默认 1/3 堆，-Xmn）
│   ├─ Eden            (8/10)   ← 新对象分配
│   ├─ Survivor From   (1/10)
│   └─ Survivor To     (1/10)
└─ 老年代 Old Generation（默认 2/3 堆）
    └─ 长寿对象 / 大对象 / 担保失败晋升
```

**比例**：
- Young : Old = 1 : 2 （`-XX:NewRatio=2`，默认）
- Eden : S0 : S1 = 8 : 1 : 1 （`-XX:SurvivorRatio=8`，默认）

> ⚠️ G1/ZGC 已经**不再有物理上的连续年轻代/老年代**，而是 Region 化（详见 [G1垃圾回收器](./G1垃圾回收器.md)）。但分代思想还在。

### 3.3 对象分配流程

```
new Object()
   │
   ▼
① TLAB 优先（Thread Local Allocation Buffer，每线程在 Eden 的私有缓冲）
   │  避免多线程在 Eden 头指针上 CAS 竞争
   ▼
② Eden 不够 → 触发 Minor GC（YGC）
   │  存活对象复制到 Survivor To，年龄 +1
   ▼
③ Survivor 放不下 / 大对象（> -XX:PretenureSizeThreshold）
   │  → 直接进老年代（分配担保）
   ▼
④ 年龄 ≥ -XX:MaxTenuringThreshold（默认 15） → 晋升老年代
   │  + 动态年龄判断：S 区某年龄段对象 > S 一半，>= 该年龄全部晋升
   ▼
⑤ 老年代不够 → Full GC
```

> **追问**：TLAB 是什么？为什么需要？  
> 答：每个线程在 Eden 划一小块（默认 1% Eden）独占分配，用 bump-pointer（指针碰撞）分配——无锁、纯内存自增，比堆全局分配快得多。`-XX:+UseTLAB` 默认开。

### 3.4 OOM

```
Exception in thread "main" java.lang.OutOfMemoryError: Java heap space
```

排查见 [线上问题排查](./线上问题排查.md)，标准三连：
1. `jmap -histo:live <pid>` 看大对象类型
2. `jmap -dump:format=b,file=heap.hprof <pid>` 转储
3. MAT / JProfiler 分析支配树（Dominator Tree）找泄漏

## 四、方法区（Method Area）

### 4.1 概念 vs 实现

> **方法区**是《Java 虚拟机规范》定义的逻辑区，**永久代 / 元空间**是 HotSpot 的具体实现——这是面试最容易混的地方。

| JDK 版本 | 方法区实现 | 内存位置 |
| --- | --- | --- |
| 1.6 及之前 | **永久代（PermGen）** | JVM 堆内（受 `-XX:MaxPermSize` 限制） |
| 1.7 | 永久代（**字符串常量池搬到堆**） | JVM 堆内 |
| **1.8+** | **元空间（Metaspace）** | **本地内存**（不在 JVM 堆内） |

### 4.2 方法区存什么

```
方法区
├─ 类元信息 Klass（Class 加载后的内存表示）
│   ├─ 类名 / 父类 / 接口 / 修饰符
│   ├─ 字段表 Field
│   └─ 方法表 Method（含字节码、异常表）
├─ 运行时常量池 Runtime Constant Pool
│   └─ 类常量池（字面量 + 符号引用）解析后入此
├─ 静态变量（JDK 7 起搬到堆）
└─ JIT 编译后的本地代码（Code Cache，独立计费）
```

### 4.3 永久代 → 元空间的演进（必考）

**永久代的痛点**：
1. **大小固定难调**：`-XX:MaxPermSize` 设小了 → `PermGen space` OOM；设大了浪费
2. **字符串 intern 容易把 PermGen 写满** → JDK 7 先把字符串常量池搬到堆
3. **类加载多的应用（OSGi / 反射 / 动态代理）必爆**：典型 Tomcat 多应用部署
4. **影响 GC 复杂度**：FullGC 必须跨永久代

**元空间的改进**：
- 用 **本地内存（Native Memory）**，不再受 JVM 堆大小限制
- 默认无上限——但可以用 `-XX:MaxMetaspaceSize` 限制（生产强烈建议设）
- 类卸载更彻底
- 字符串常量池、静态变量已经在堆里

> **生产坑**：`MaxMetaspaceSize` 不设 → 类加载泄漏（如热部署、CGLIB 动态生成类）→ 元空间无限涨 → 进程被 OS OOM Killer 杀。**必设上限**：`-XX:MaxMetaspaceSize=512m`。

### 4.4 OOM

```
java.lang.OutOfMemoryError: Metaspace          // JDK 8+
java.lang.OutOfMemoryError: PermGen space      // JDK 7-
```

常见原因：
1. **动态代理 / CGLIB / Javassist 滥用**：每次生成新 Class，未卸载
2. **频繁部署**：热加载导致旧版本 Class 没释放
3. **反射 / 脚本引擎**：Groovy / Nashorn 频繁编译

## 五、运行时常量池 vs 字符串常量池 vs Class 常量池

> 三个"常量池"很容易混，这是面试官最爱的陷阱。

| 名称 | 位置 | 内容 | 时机 |
| --- | --- | --- | --- |
| **Class 常量池**（也叫静态常量池） | `.class` 文件内 | 字面量（字符串、数字）+ 符号引用 | 编译期 |
| **运行时常量池** | 方法区 | Class 常量池被解析后的内容（含直接引用） | 类加载完成后 |
| **字符串常量池**（StringTable） | **堆**（JDK 7+） | 字符串实例的引用，HashTable 实现 | 运行时（intern 等） |

### 5.1 字面量 / 符号引用 / 直接引用

```java
String s = "hello";   // "hello" 是字面量
new com.foo.Bar();    // com.foo.Bar 是符号引用（编译时还不知道地址）
```

- **符号引用**：用全限定名表示的引用（编译期不知道目标地址）
- **直接引用**：解析阶段把符号引用转成实际内存地址
- **字面量**：编译期能确定的常量值

### 5.2 字符串常量池搬家史

| JDK | 位置 | 原因 |
| --- | --- | --- |
| 6 | 永久代 | — |
| **7** | **堆** | 永久代固定大小，intern 容易爆；堆 GC 频繁，回收快 |
| 8 | 堆 | 元空间替换永久代，常量池已经在堆 |

### 5.3 String.intern() 的坑（高频追问）

```java
String s1 = new String("abc");
String s2 = s1.intern();
String s3 = "abc";
System.out.println(s2 == s3);  // true（JDK 7+）
```

JDK 7 之后 `intern()` 行为变了：
- **JDK 6**：发现常量池没有，**复制一份** char[] 进常量池，返回常量池中的引用
- **JDK 7+**：发现常量池没有，直接**把堆中已存在的引用登记到常量池**，返回堆中的引用

→ JDK 7 后 `intern()` 节省内存，但若大量乱 intern 会撑爆常量池。

## 六、直接内存（Direct Memory）

> **不是 JVM 规范定义的运行时数据区**，但 JVM 在用——属于"堆外"内存。

### 6.1 来源

```java
ByteBuffer buf = ByteBuffer.allocateDirect(1024);   // 直接内存
ByteBuffer buf = ByteBuffer.allocate(1024);          // 堆内内存
```

NIO 用 `Unsafe.allocateMemory()` 在 OS 申请，避开 JVM 堆。Netty 大量用直接内存。

### 6.2 为什么用直接内存

```
传统 IO：
内核态 PageCache → 复制到 → JVM 堆内 ByteBuffer → 用户操作

直接内存：
内核态 PageCache → 直接映射 → DirectByteBuffer → 用户操作
```

**省一次内存拷贝**——网络 / 磁盘 IO 密集场景吞吐显著提升（详见 [零拷贝](../Network/零拷贝.md)）。

### 6.3 OOM

```
java.lang.OutOfMemoryError: Direct buffer memory
```

- 上限：`-XX:MaxDirectMemorySize`（默认 = `-Xmx`）
- DirectByteBuffer 通过 **Cleaner（PhantomReference）** 在被 GC 时释放本地内存
- **坑**：直接内存的回收依赖 Full GC——如果堆不大、没触发 FullGC，直接内存先撑爆

**Netty 的 PooledByteBufAllocator** 自带池化，避免反复申请 / 释放本地内存。

## 七、各区域 OOM 速查表

| 异常信息 | 区域 | 典型场景 | 排查 |
| --- | --- | --- | --- |
| `Java heap space` | 堆 | 大对象 / 内存泄漏 | jmap dump + MAT |
| `GC overhead limit exceeded` | 堆 | GC 占了 98% 时间但回收 < 2% | 同上 |
| `Metaspace` | 方法区 | 动态类生成 / 频繁热部署 | jmap -histo \| grep -i class |
| `PermGen space` | 方法区（≤7） | 同上 | 升 JDK 8 / 调 MaxPermSize |
| `Direct buffer memory` | 直接内存 | NIO/Netty 不释放 | -XX:MaxDirectMemorySize / NMT |
| `unable to create new native thread` | 线程栈（OS 限制） | 线程数过多 | -Xss 调小 / 限制线程池 |
| `StackOverflowError` | JVM 栈 | 深递归 | 改递归为迭代 / -Xss 调大 |

## 八、生产配置建议

```bash
# 堆
-Xms4g                           # 初始堆
-Xmx4g                           # 最大堆（Xms = Xmx 避免动态伸缩）
-Xmn1.5g                         # 新生代（或用 -XX:NewRatio=2）
-XX:SurvivorRatio=8              # Eden : S0 : S1 = 8:1:1

# 栈
-Xss256k                         # 栈大小（线程多时调小）

# 方法区（JDK 8+）
-XX:MetaspaceSize=256m           # 初始触发 GC 阈值
-XX:MaxMetaspaceSize=512m        # 上限（必设！防类泄漏）

# 直接内存
-XX:MaxDirectMemorySize=1g       # 显式指定（默认 = Xmx，容易掩盖问题）

# OOM 时自动 dump
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/log/heap_dump.hprof
-XX:+ExitOnOutOfMemoryError      # OOM 直接退出（Pod 自愈）

# GC 日志（详见 jvm参数）
-Xlog:gc*:file=/data/log/gc.log:time,uptime,level,tags:filecount=10,filesize=100M  # JDK 9+
```

## 九、生产踩坑

### 9.1 元空间 OOM（最常见）

**现象**：服务跑几小时 / 几天后 `OutOfMemoryError: Metaspace`。

**根因**：
- Spring AOP / MyBatis / CGLIB 大量动态生成 Class
- Groovy / Nashorn 脚本反复编译
- ClassLoader 泄漏（典型：Tomcat 应用热部署后旧 ClassLoader 没卸载）

**修复**：
```bash
-XX:MaxMetaspaceSize=512m         # 设上限暴露问题
-XX:+TraceClassLoading            # 看哪些类被反复加载
-XX:+TraceClassUnloading
jcmd <pid> GC.class_stats         # 类统计
```

### 9.2 直接内存泄漏

**现象**：堆没满，但进程 RSS 持续涨，最终被 OOM Killer 杀。

**根因**：Netty / NIO 用 `ByteBuffer.allocateDirect` 没释放，依赖 FullGC 触发 Cleaner——堆没压力 → 不 FullGC → 直接内存堆积。

**排查**：
```bash
# 开 NMT（Native Memory Tracking）
-XX:NativeMemoryTracking=detail
jcmd <pid> VM.native_memory summary
```

**修复**：用 `PooledByteBufAllocator`，或在合适时机手动 `((DirectBuffer) buf).cleaner().clean()`。

### 9.3 线程栈把内存吃光（unable to create new native thread）

**现象**：服务启动一段时间后报 `unable to create new native thread`，但 `top` 看堆没满。

**根因**：
- 线程数失控（默认线程池 `LinkedBlockingQueue` 无界 → 任务堆积但线程不增）反例不存在；真实场景是反复 `new Thread()` 或线程池 max 配置无上限
- 单线程栈 `-Xss1m` × 3000 线程 = 3GB 直接内存

**修复**：
- `-Xss256k` 或 `512k`
- 系统级：`ulimit -u` 调高
- 排查线程数：`jstack <pid> | grep 'java.lang.Thread.State' | wc -l`

### 9.4 字符串 intern 撑爆常量池

**现象**：JDK 6 老服务跑大数据 ETL，频繁 intern 大文本片段 → `PermGen space` OOM。

**根因**：每个新字符串都 intern 进永久代，永久代固定大小很快爆。

**修复**：升 JDK 8（常量池在堆，回收频繁）或者业务上避免对长字符串 intern。

## 十、面试高频追问

### Q1：为什么 PC 寄存器是线程私有？

线程切换需要恢复"执行到字节码哪一行"，这个游标必须每条线程独立。否则切换回来读到别人的位置，程序直接乱跳。

### Q2：方法区一定在堆里吗？

**逻辑上是堆的一部分**（《Java 虚拟机规范》语境），有别名 "Non-Heap"——表示物理上不在堆。
HotSpot 在 JDK 8 之前用永久代实现（在堆里），JDK 8+ 用元空间（在本地内存里，**不在堆**）。

### Q3：JDK 8 为什么取消永久代？

四个原因：
1. 永久代大小难调（设小爆，设大浪费）
2. 字符串常量池在永久代回收频率低，容易 OOM
3. 永久代和老年代必须一起 FullGC，复杂度高
4. Oracle 想合并 HotSpot 和 JRockit，JRockit 没永久代

### Q4：堆里一定是新生代 + 老年代吗？

**不一定**。
- Serial / Parallel / CMS / ParNew：是
- **G1**：物理上把堆切成 Region，逻辑上还有年轻代/老年代但不是连续的
- **ZGC / Shenandoah**：默认无分代（ZGC 21 起有可选的分代模式）

### Q5：栈溢出和堆溢出分别什么时候发生？

| 错误 | 触发 |
| --- | --- |
| StackOverflowError | 递归过深、栈帧过大（局部变量太多） |
| OutOfMemoryError: Java heap space | 大对象 / 内存泄漏 / 堆设小了 |
| OutOfMemoryError: unable to create new native thread | 线程数 ×Xss > 可用内存 |

### Q6：i++ 为什么不是原子操作？字节码角度讲？

字节码拆 `iload → iinc → istore` 三步，可被其他线程的三步打断。volatile 只保证可见性（每次读最新值），但读完到写回之间仍可能被覆盖。要原子用 `AtomicInteger` 的 CAS 或 `synchronized`。

### Q7：字符串常量池在哪？为什么要搬？

JDK 6 在永久代，JDK 7 起搬到堆。
搬的原因：永久代固定大小、回收频率低，大量 intern 会爆 PermGen；堆有完整 GC 体系，回收彻底。

### Q8：直接内存为什么属于"堆外"？JVM 怎么管？

通过 `Unsafe.allocateMemory()` 直接向 OS 申请，不在 JVM 堆里。JVM 通过 DirectByteBuffer 对象（在堆里，很小）持有指针；DirectByteBuffer 被 GC 时，注册的 Cleaner（PhantomReference）会调用 `Unsafe.freeMemory()` 释放本地内存。

→ **风险**：堆没压力时不 FullGC，直接内存可能先爆。Netty 用引用计数 + 池化绕开这个。

### Q9：TLAB 是什么？解决什么问题？

Thread Local Allocation Buffer：每个线程在 Eden 区独占一小块（默认 1% Eden）。
**解决问题**：多线程在 Eden 头指针上 CAS 抢分配 → 高并发场景成为瓶颈。
TLAB 内 bump-pointer 分配（指针碰撞，无锁），TLAB 用完才回到 Eden 全局分配。`-XX:+UseTLAB` 默认开。

### Q10：static 修饰的对象在哪？

| JDK | 位置 |
| --- | --- |
| 6 | 方法区（永久代） |
| **7+** | **堆**（方法区只存指向堆中对象的引用） |

⚠️ 但**类元信息中的 static 字段槽位**还在方法区（JDK 8+ 元空间）；指向的对象实例在堆。

### Q11：栈帧的局部变量表能放对象吗？

**只能放对象引用**（4B 或 8B 的指针，看是否压缩指针），对象本身在堆。  
基本类型（int / long / double / boolean / char / byte / short / float）可直接存值。

## 十一、答题模板（60 秒话术）

> JVM 运行时数据区分**5 个区**：**程序计数器 / 虚拟机栈 / 本地方法栈** 是线程私有，**堆 / 方法区** 是线程共享。再加上 JVM 在用但规范没规定的**直接内存**。
>
> **PC** 是字节码行号指示器，唯一不抛 OOM。**虚拟机栈**装栈帧，每个栈帧含局部变量表 / 操作数栈 / 动态链接 / 返回地址，过深抛 StackOverflowError，扩展失败抛 OOM。
>
> **堆**是 GC 主战场，HotSpot 分新生代（Eden + S0 + S1，默认 8:1:1）和老年代，新对象优先 TLAB → Eden，YGC 后晋升，达年龄阈值进老年代。
>
> **方法区**存类元信息 / 运行时常量池 / 静态变量 / JIT 代码。JDK 8 之前是永久代（堆内），JDK 8+ 改成元空间（本地内存）——主因是永久代大小难调、字符串 intern 易爆。**字符串常量池在 JDK 7 搬到堆**。
>
> **直接内存**通过 NIO 的 DirectByteBuffer 申请，省一次内核到 JVM 的拷贝，但回收依赖 Cleaner，堆没压力时不释放容易 OOM。
>
> 各区 OOM：堆 → `Java heap space`，方法区 → `Metaspace`，直接内存 → `Direct buffer memory`，栈 → `StackOverflowError` 或 `unable to create new native thread`。
