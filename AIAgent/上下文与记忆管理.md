# 上下文与记忆管理

> 引子：长对话 / 长任务 Agent 一定会遇到的问题：**上下文窗口快爆了怎么办**？这一篇覆盖：
>
> ① **上下文为什么会爆**——客服多轮 / Agent 长任务 / RAG 大召回的真实计算。
> ② **滑动窗口 / Summary Buffer / 向量记忆** 怎么选？长上下文模型（1M）是不是就不需要这些了？
> ③ **Anthropic Prompt Cache** 是怎么省钱的？什么时候不命中？
> ④ **Lost in the Middle** 真存在吗？怎么对抗？
> ⑤ **多用户长期记忆**怎么持久化？KG Memory / Mem0 这些方案到底什么场景用？
>
> 这是 Agent 工程化里**最容易出 P0 事故的环节**——上下文超限直接 502，记忆混乱让用户体验崩。

---

## 一、上下文是怎么爆的

### 1.1 真实场景：5 轮客服对话的 Token 增长

```
轮 1：
  System Prompt           5,000  （含 Few-shot）
  RAG 召回 (Top-5)         3,000
  用户输入                 100
  历史消息                 0
  Tool 定义                500
  → 总 Input Token         8,600

轮 2：
  System Prompt            5,000
  RAG 召回（新一轮）        3,000  ← 重新检索
  用户输入                 100
  历史消息（轮 1 的全部）   8,800
  Tool 定义                500
  → 总 Input Token         17,400

轮 5：
  System + RAG + Tool 定义  8,500
  用户输入                  100
  历史消息（前 4 轮）        50,000+
  → 总 Input Token         58,600  ← 5 轮就 5.8 万 Token

轮 10：
  → 总 Input Token         140,000+ ← GPT-5 接近上限
轮 20：
  → 总 Input Token         300,000+ ← GPT-5 已超
```

> ⚠️ **不只是上限问题**：每多 1000 Token，单次成本 +$0.003-0.015，单次延迟 +10-30ms。**长会话指数级烧钱 + 拖慢**。

### 1.2 Agent 长任务的 Token 增长

```
ReAct 模式做"分析 100 个订单"任务：
- 每步思考 200 Token
- 每个 Tool Call 200 Token (input)
- 每个 Tool Result 500 Token (返回数据)
- 50 步后历史消息 ≈ 45,000 Token + System 5,000 = 50,000 Token / 单次推理

长任务必爆窗口
```

## 二、上下文管理的四种策略

### 2.1 策略 A：滑动窗口（最简单）

```python
# 保留最近 K 轮 + System Prompt 永远在
def truncate(messages, max_messages=20):
    system_msgs = [m for m in messages if m.role == "system"]
    user_assistant = [m for m in messages if m.role != "system"]
    return system_msgs + user_assistant[-max_messages:]
```

**优势**：简单、可预测、Token 上限稳。
**劣势**：**暴力丢失历史**——用户上一次说的话被截掉，模型"失忆"。

**适用**：短对话、一次性任务、不依赖历史的场景。

### 2.2 策略 B：Summary Buffer（摘要缓冲）

```python
def manage_context(messages, threshold=10):
    if len(messages) <= threshold:
        return messages
    
    # 把最早的旧消息（除 System 外）压成摘要
    old_messages = messages[1:len(messages) - threshold + 1]
    summary = llm.summarize(old_messages)
    
    return [
        messages[0],   # System
        Message(role="system", content=f"历史摘要: {summary}"),
        *messages[-threshold:]  # 保留最近 threshold 轮
    ]
```

**优势**：保留历史核心信息、上限稳。
**劣势**：摘要本身要花一次 LLM、可能丢细节、摘要质量影响下游。

**适用**：客服多轮对话、长任务 Agent、对历史有依赖。

### 2.3 策略 C：向量记忆（Vector Memory）

```python
# 写入：每轮对话存向量库
def remember(user_msg, assistant_msg, session_id):
    text = f"用户: {user_msg}\n助手: {assistant_msg}"
    vec = embed(text)
    vector_store.insert(text=text, vector=vec, metadata={"session_id": session_id, "ts": now})

# 读取：当前 query 召回最相关的历史
def recall(current_query, session_id, top_k=5):
    vec = embed(current_query)
    results = vector_store.search(vec, top_k=top_k, filter=f"session_id='{session_id}'")
    return [r.text for r in results]

# 用法
relevant_history = recall(user_input, session_id)
prompt = f"""
[历史相关对话]
{chr(10).join(relevant_history)}

[当前问题]
{user_input}
"""
```

**优势**：可"查询式"召回历史、不受上下文窗口限制、跨会话记忆可用。
**劣势**：实现复杂、有召回不准的风险、向量库成本。

**适用**：长期用户记忆（个性化）、跨会话场景、ToB 客服跟踪。

### 2.4 策略 D：状态固化（State Fix）

```python
# 把任务 plan / 关键决策固化到 State
class AgentState:
    original_query: str       # 用户原始问题
    plan: List[str]           # 任务规划
    key_findings: Dict        # 关键中间结果
    todo: List[str]           # 待办

# 每次 inject 到 System Prompt，不依赖消息历史
def build_system_prompt(state):
    return f"""
你是 Agent。

## 用户原始任务
{state.original_query}

## 当前规划
{format_plan(state.plan, completed=state.completed)}

## 关键发现
{json.dumps(state.key_findings, ensure_ascii=False)}

## 待办
{format_todo(state.todo)}
"""
```

**优势**：长任务进度始终可见、模型不会"忘"目标、便于断点恢复。
**劣势**：要做状态建模、不适合自由对话。

**适用**：长任务 Agent、Plan-and-Execute、StateGraph 场景。

### 2.5 四种策略对比

| 维度 | 滑动窗口 | Summary Buffer | 向量记忆 | 状态固化 |
|---|---|---|---|---|
| 实现难度 | ★ | ★★ | ★★★★ | ★★★ |
| Token 控制 | 强 | 强 | 弱（召回数可控） | 强 |
| 历史保真 | 差 | 中 | 高 | 仅关键信息 |
| 长会话适配 | 差 | 中 | 优 | 优 |
| 跨会话记忆 | ❌ | ❌ | ✅ | ❌ |
| 调试难度 | ★ | ★★ | ★★★ | ★★ |

**生产推荐组合**：滑动窗口（基线）+ Summary Buffer（旧消息压缩）+ State 固化（任务核心）+ 向量记忆（用户偏好）四管齐下。

## 三、Anthropic Prompt Cache：省钱的核武器

### 3.1 原理

LLM 每次推理要把整个 Prompt 走一遍 Transformer，前缀的 KV Cache 重复算了 N 次浪费。Anthropic 把"前缀完全相同的部分"标记 `cache_control`，下次相同前缀**直接复用 KV Cache**，不重算。

```
请求 1：
  [System 5000 Token + Tools 1000 + 用户输入 100]
  → 全部 Input Token 计费 6100，前缀缓存 5 分钟

请求 2（5 分钟内）：
  [System 5000 + Tools 1000 + 不同用户输入 100]
  ↑ 前 6000 Token 命中 cache（计费 0.1×）
  → 实际计费 = 6000 × 0.1 + 100 × 1 = 700（省 88%）
```

### 3.2 用法

```python
client.messages.create(
    model="claude-sonnet-4-6",
    system=[
        {
            "type": "text",
            "text": LONG_SYSTEM_PROMPT,
            "cache_control": {"type": "ephemeral"}    # ← 标缓存
        }
    ],
    tools=[
        {
            "name": "...",
            "description": "...",
            "input_schema": {...},
            "cache_control": {"type": "ephemeral"}    # 工具定义也可缓存
        }
    ],
    messages=[
        {"role": "user", "content": [...]}
    ]
)
```

### 3.3 计费规则

| 类型 | 单价（相对 Input） |
|---|---|
| **写入缓存**（Cache Write） | **1.25x**（写一次稍贵） |
| **读取缓存**（Cache Read） | **0.1x**（读极便宜） |
| 普通 Input | 1.0x |

**单次请求经济性**：
- 写入一次成本：5000 × 1.25 = 6250 等效
- 第一次复用就回本（5000 × 1.0 - 5000 × 0.1 = 4500 节省）
- 复用越多，省得越多

**典型场景节省**：
| 场景 | 缓存命中率 | 节省比例 |
|---|---|---|
| 客服多轮对话（System 不变） | 95%+ | 60-80% |
| RAG 长 System Prompt | 90%+ | 50-70% |
| Agent 多步 Tool Call | 80%+ | 40-60% |
| 单次独立请求 | 0% | 0% |

### 3.4 命中条件（坑）

**严苛条件**：
- 前缀字节级别完全一致（**多空格 / 时间戳 / 用户名嵌入** 全部破坏命中）
- 模型版本不变（`claude-sonnet-4-6` → `claude-sonnet-4-7` 重写）
- 5 分钟内（默认 TTL，可设 1 小时但贵）
- `cache_control` 标记位置正确（标在 message / system 块的最后一个）

**生产典型不命中场景**：
```python
# ❌ 坏：把当前时间塞进 System
system = f"今天是 {datetime.now()}，..."  # 每次都不一样，Cache miss

# ❌ 坏：把用户名拼进 System
system = f"用户 {user.name} 你好，..."   # 每个用户都 miss

# ✅ 好：固定前缀 + 用户信息放 user message
system = "你是 XX 助手..."  # 静态，cache 命中
messages = [
    {"role": "user", "content": f"我是 {user.name}，问题：{question}"}
]
```

### 3.5 Anthropic 上下文管理特性（Context Editing）

Anthropic 在 Claude 4.5+ 开始支持 **Context Management**——模型可以"自主清理"工具调用历史，保留关键信息丢弃噪声。

```python
# 启用 context_management
client.messages.create(
    model="claude-sonnet-4-6",
    extra_body={"context_management": {"enabled": True}},
    ...
)
```

效果：长 Agent 任务自动清理冗余 Tool Result，Token 消耗下降 30-50%。

## 四、Lost in the Middle（中间遗忘）

### 4.1 现象

把关键信息放在长 Prompt 的**中段**，模型回忆准确率显著低于放在**首尾**。

NIAH（Needle in a Haystack）评测：
```
Recall 准确率（不同位置）：
- 开头 (0-10%):    98%
- 前段 (10-30%):   92%
- 中段 (40-60%):   62%   ← 显著下降
- 后段 (70-90%):   88%
- 末尾 (90-100%): 99%
```

### 4.2 原因（理论解释）

- **位置编码权重失衡**：训练数据中"重要信息往往在开头/结尾"，模型学到了这种偏好
- **注意力分布**：长序列下中段位置的注意力被稀释
- 不同模型程度不同（Claude / GPT 都有，Gemini 略好）

### 4.3 对抗策略

```
策略 1：关键信息前置 + 末尾重述
  System 开头：核心规则
  user 末尾：请基于上面 <retrieved> 中的所有内容回答，特别注意 X 和 Y。
  
策略 2：分段查询（chunking the prompt）
  长文档 100K → 切 5 段 × 20K → 多次询问综合
  
策略 3：减少中段内容
  RAG Top-K 只取 3-5 段精选，而不是 20 段拼一起
  
策略 4：明确"重要性标注"
  在 prompt 里用 [重要] 标记关键段，让模型聚焦
```

## 五、长期记忆（跨会话）

### 5.1 用户画像 / 偏好

```
场景：用户在多次对话中提到"我对芒果过敏"
需求：下次推荐食物时自动避开

实现：
1. 每轮对话后，让 LLM 提取关键事实（preference）
2. 写入 KV 存储（Redis/PG）：user_id → {preferences: [...], facts: [...]}
3. 下次会话注入到 System Prompt
```

```python
# 提取 + 存储
extract_prompt = f"""
从对话中提取需要长期记住的用户信息（偏好、限制、关键事实）。
忽略：闲聊 / 一次性问题 / 临时信息。

对话：
{conversation}

返回 JSON: {{"facts": [{{"key": "...", "value": "..."}}]}}
"""
new_facts = llm.complete(extract_prompt)
user_memory.update(user_id, new_facts)
```

```python
# 注入到下次会话
def build_system(user_id):
    facts = user_memory.get(user_id)
    facts_text = "\n".join(f"- {f.key}: {f.value}" for f in facts)
    return f"""
你是助手。

[关于此用户的记忆]
{facts_text}
"""
```

### 5.2 主流方案

| 方案 | 类型 | 适用 |
|---|---|---|
| **简单 KV** | Redis / PG | 用户偏好（< 100 条） |
| **向量记忆** | Milvus / pgvector | 历史对话回忆（语义召回） |
| **Mem0** | 开源中间件 | 自动化记忆 + 智能更新 |
| **Knowledge Graph Memory** | Neo4j + KG schema | 复杂关系（家人 / 工作 / 喜好关联） |
| **OpenAI Memory** / **Claude Projects** | 官方托管 | 不想自建 |

### 5.3 Mem0 的工作流

```
对话发生 → Mem0 自动提取关键事实 → 存向量库
              ↓
查询时 → 检索相关历史记忆 → 注入 prompt
              ↓
新事实与旧事实冲突 → LLM 仲裁更新（"过敏 X" → "过敏 X 和 Y"）
```

适用：要快速上线长期记忆且不想自建的场景。

## 六、生产踩坑

### 坑 1：滑动窗口把用户原始问题截没了

**现象**：长任务 Agent 跑到第 14 步，模型回复"我可以帮你做什么"——它"忘"了用户最初的问题。

**根因**：
- 滑动窗口只保留最近 K 条消息（典型 K=20）
- 14 步 × 平均 5 条 message/步 = 70 条，用户首条早被截
- 没有"原始 query 始终保留"机制

**修复**：
- 滑动窗口策略改为：**System + 用户首条 + 最近 K-1 条**
- 长任务用 State.original_query 显式存储 + 注入 System
- 加监控：每轮检查"原始 query 是否还在 messages 里"

```python
def truncate_v2(messages, max_recent=20, original_query=None):
    system = [m for m in messages if m.role == "system"]
    rest = [m for m in messages if m.role != "system"]
    
    # 始终保留 user 首条
    if rest and rest[0].role == "user":
        first_user = rest[:1]
        recent = rest[-(max_recent-1):]
        if first_user[0] not in recent:
            return system + first_user + recent
    return system + rest[-max_recent:]
```

### 坑 2：把当前时间塞 System，Prompt Cache 全 miss

**现象**：上线 Anthropic Prompt Cache 后，账单没下降反而涨了 25%。

**根因**：
- System Prompt 里有 `今天是 {now}`，每次请求都不一样
- 第一次请求计费 1.25x（cache write），第二次还是 1.25x（前缀变了 → 重写）
- 反而比不开缓存更贵

**修复**：
- System 内只放静态内容
- 当前时间放到 user message 末尾
- 验证：跑两次相同请求，对比 `usage.cache_read_input_tokens` 是否非 0

```python
# 修复后
client.messages.create(
    system=[{"type": "text", "text": STATIC_PROMPT, "cache_control": {"type": "ephemeral"}}],
    messages=[
        {"role": "user", "content": f"当前时间 {now}\n用户问题：{q}"}
    ]
)
```

### 坑 3：Summary Buffer 摘要丢失关键金额

**现象**：用户在 5 轮前说"我转账了 1000 元"，第 8 轮问"我刚说的金额是多少"，模型答 100 元。

**根因**：
- Summary 时把"1000 元"压成"用户提到一笔转账"
- LLM 摘要默认压缩了具体数字 / 名称 / 时间

**修复**：
- 摘要 Prompt 中明确："**保留所有具体数字 / 时间 / 名称 / 金额**，只压缩描述性叙述"
- 业务关键场景（金融 / 医疗）**不要纯靠摘要**，改用 State 固化
- 加 fallback：摘要里没有的关键信息，从原始消息存档中再次召回（向量记忆兜底）

### 坑 4：跨会话记忆混乱，张三的偏好串到李四

**现象**：用户 A 说"我喜欢羊肉"，用户 B 提问时模型回答带了"考虑到您喜欢羊肉"。

**根因**：
- 用户记忆没按 user_id 隔离
- Embedding 检索时 filter 没起作用
- Mem0 等中间件配置错租户

**修复**：
- **强制按 user_id 过滤** + Schema 校验
- 多租户场景：tenant_id + user_id 双重隔离
- 写入时校验：每条记忆必带 user_id，缺失即拒绝写入
- 单元测试覆盖："切换用户后旧记忆完全不召回"

```python
# 强校验
def remember(user_id, fact):
    assert user_id, "user_id required"
    vector_store.insert(
        text=fact,
        metadata={"user_id": user_id, "ts": now}
    )

def recall(user_id, query, top_k=5):
    return vector_store.search(
        query_vec=embed(query),
        top_k=top_k,
        filter=f"user_id='{user_id}'"  # 强过滤
    )
```

### 坑 5：长上下文塞 200K，回答忽略中段内容

**现象**：把整本产品手册（200K Token）塞 Claude 1M，问"第 80 页的功能 X 怎么用"，模型答"找不到"。

**根因**：Lost in the Middle。Claude 对 200K 的中段（80-120K 区间）召回率降到 60-70%。

**修复**：
- **关键信息前置 / 后置**：把"问题"放 user message 末尾，"答案应该在文档第几节"提示放开头
- **分段查询**：先让 LLM 列出章节，再针对相关章节单独查询
- **改用 RAG**：检索 Top-3-5 段（每段 500-1000 Token）拼起来，远好于全文塞
- **加重述策略**：末尾加"请确认 <retrieved_passages> 中的全部内容都被考虑，特别是中段"

## 七、面试高频追问

**Q1：上下文窗口快爆了怎么办？**

四种策略组合：① **滑动窗口**——保留最近 K 轮 + System + 用户首条；② **Summary Buffer**——超出的旧消息 LLM 摘要压缩（注意保留具体数字 / 名称）；③ **向量记忆**——存历史对话向量化，按当前 query 召回相关；④ **状态固化**——任务核心（plan / 关键结果）放 State 显式注入 System，不依赖消息历史。**生产组合用**——基线滑动窗口、长任务加 State 固化、跨会话上向量记忆。

**Q2：长上下文模型（1M）是不是就不需要这些了？**

不是。即便有 1M context，仍然要管：① **成本**——填满 1M 一次 $20+，账单飞；② **延迟**——TTFT 30-60s 用户体感崩；③ **Lost in the Middle**——长 prompt 中段召回率显著下降；④ **Cache miss**——长 prompt 一旦不命中 cache 单次几美元。**长上下文 ≠ RAG / 上下文管理的替代品**，依然要做。

**Q3：滑动窗口 / Summary Buffer / 向量记忆 怎么选？**

短对话 / 一次性任务用**滑动窗口**（简单稳定）；客服多轮 / 长任务依赖历史用 **Summary Buffer**（保留核心 + Token 可控）；跨会话个性化 / 历史对话回忆用**向量记忆**（按需召回）。**生产推荐**：基线滑动窗口 + 旧消息压缩 + 关键事实存 State + 跨会话记忆走向量库。

**Q4：Anthropic Prompt Cache 怎么省钱？**

把 Prompt 中**前缀完全相同**的部分标 `cache_control: ephemeral`（System / Tools / 长 Few-shot）。下次相同前缀的请求**前缀部分计费 0.1x**（cache read）而不是 1.0x（普通 input）。命中率 90% 时节省 60-80%。**坑**：① 前缀必须字节级完全一致——多空格 / 时间戳 / 用户名嵌入都破坏；② 5 分钟 TTL（可设 1 小时但贵 2x）；③ cache write 第一次是 1.25x，复用 1 次以上才回本；④ 模型版本变了 cache 重置。

**Q5：什么时候 Prompt Cache 不命中？**

7 个典型 miss 场景：① System 含动态内容（时间 / 用户名）；② Tool 定义经常变；③ 5 分钟内没第二次请求（TTL 过期）；④ 模型版本切换；⑤ `cache_control` 标记位置错；⑥ Prompt 前缀加了一个空格 / 换行；⑦ 客户端 batch 请求顺序不固定。**生产经验**：保持 System / Tools / Few-shot 静态化，动态变量放 user message。

**Q6：Lost in the Middle 真存在吗？怎么对抗？**

存在。NIAH 评测显示长 prompt 中段（40-60% 位置）召回率比首尾低 20-30%。Claude / GPT / Gemini 都有，程度不同。对抗策略：① 关键信息前置 + 末尾重述；② 分段查询（长文档切多次询问综合）；③ 减少中段噪声（RAG Top-K 取精不取多）；④ 明确"重要性标注"提示模型聚焦。**生产做法**：长上下文 + RAG 配合，长上下文负责"看全局"，RAG 负责"找精确"。

**Q7：跨会话长期记忆怎么做？**

四种方案：① **简单 KV**（Redis / PG）——存用户偏好 / 关键事实，< 100 条够用；② **向量记忆**——存历史对话向量化，语义召回；③ **Mem0** 等中间件——自动提取 + 智能更新（事实冲突自动仲裁）；④ **KG Memory**——存复杂关系（适合家庭 / 工作场景关联）。**生产做法**：用户偏好 KV，对话回忆向量库。**强校验** user_id / tenant_id 防记忆错位。

**Q8：Summary Buffer 摘要质量怎么保证？**

三个要点：① **摘要 Prompt 强约束**——"保留所有具体数字 / 时间 / 名称 / 金额，仅压缩描述性叙述"；② **业务关键场景 fallback**——金融 / 医疗别全靠摘要，改用 State 固化关键字段；③ **保留原文存档**——摘要后的旧消息别直接删，存数据库，缺失时回查。摘要由便宜模型（Haiku / DeepSeek）做，成本可控。

**Q9：Agent 长任务怎么不忘记原始目标？**

State 固化是关键。把用户原始 query / plan / 关键中间结果**显式存到 State**，每轮**注入到 System Prompt**，不依赖消息历史。这样即便滑动窗口截掉了用户首条，目标依然在。Plan-and-Execute 模式下还要把 plan 完成进度也固化（每步执行完更新 todo），让模型始终看到全局进度。

**Q10：Anthropic 的 Context Management 是什么？**

Claude 4.5+ 引入的特性，模型**自主清理**冗余的工具调用历史，保留关键信息。启用后长 Agent 任务 Token 消耗下降 30-50%。开启方式：`extra_body={"context_management": {"enabled": True}}`。**坑**：模型自主决定保留什么，可能误清关键内容——重要场景仍然 State 固化兜底。

> "上下文管理的核心是 **保住关键信息 + 控制 Token 上限**。"

>
> "**长期记忆**：偏好走 KV（Redis），历史对话走向量库，**强校验 user_id 防记忆串户**。Mem0 等中间件适合不想自建。"
