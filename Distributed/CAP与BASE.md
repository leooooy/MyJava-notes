# CAP 与 BASE 理论

> 分布式系统的"世界观"——任何分布式题的根都在这里。
> 本篇要解决的问题：
> ① **CAP** 到底是什么？为什么是"三选二"而不是"三个都要"？
> ② 为什么 **P（分区容错性）必选**，"选 CA 不选 P" 是个伪命题？
> ③ 业界组件如何归类（CP / AP）？Nacos 为什么能两种切换？
> ④ **BASE** 是 CAP 的工程妥协，怎么落到具体方案上？
>
> 这篇不是为了背概念，而是为了把"为什么分布式做不到完美强一致" 讲透——后面所有分布式事务、分布式锁、注册中心选型都是从这里推下去的。

---

## 一、为什么有 CAP

单机系统里没有这个问题——所有数据都在一台机器，读写有锁就够了。

到了分布式，事情变了：

```
[Client] ──写─► [Node A]  ◄─同步─►  [Node B]
                  │                     │
                  └──── 读 ─────────────┘
                             ↑
                        Client 可能读到 A，也可能读到 B
```

三个新挑战：
1. **网络可能挂**：A 和 B 之间网络断了（**分区**）
2. **节点可能挂**：A 挂了，B 还在
3. **延迟客观存在**：A 写完同步到 B 总有 ms 级延迟

CAP 定理就是在描述：**这三件事让你不可能同时拿到完美的"一致性 + 可用性 + 分区容错性"**。

## 二、CAP 定理

### 2.1 三个字母的精确定义

| 字母 | 名称 | 工程含义 | 反面 |
| --- | --- | --- | --- |
| **C** | Consistency 一致性 | 任何节点在任何时刻读到的数据**完全一致**（线性一致性） | 读到旧数据、读到不同节点不同值 |
| **A** | Availability 可用性 | 任何**非故障节点**在合理时间内**必须返回响应**（不能阻塞、不能拒绝） | 客户端阻塞、超时、被拒绝服务 |
| **P** | Partition Tolerance 分区容错性 | 当网络分区发生时，系统**仍能继续工作**（不是整体瘫痪） | 网络一断系统就挂 |

> 注意 C 这里指的是 **线性一致性（Linearizability）**——比 ACID 的 C（事务约束）更严格。是数据库领域的"强一致"。

### 2.2 为什么是"三选二"

**关键场景**：网络分区已经发生（A 和 B 不能通信）。

```
[Client1] ──写 x=2──► [Node A]    [Node B] ◄──读 x──[Client2]
                          ╳ 网络断 ╳
```

此时 Node A 收到写请求 x=2，但同步不到 B。Node B 收到 Client2 的读请求，怎么办？

- **如果保证 C（一致性）**：B 必须等到能跟 A 通信、确认数据一致后才返回 → **A 给不了响应，牺牲 A**
- **如果保证 A（可用性）**：B 立刻返回它本地的旧数据 → **数据不一致，牺牲 C**

**网络分区发生时，C 和 A 必须二选一**。这就是 CAP 三选二的本质。

### 2.3 P 为什么必选——"CA 不选 P" 是伪命题

互联网公司的网络故障是**客观存在的**（光纤被挖断、机房断电、跨地域专线抖动）。
你不能假设网络永远不分区，所以 **P 必选**。

剩下的选择是：

- **CP**：分区时拒绝服务（牺牲 A）
- **AP**：分区时返回旧数据（牺牲 C）

**单机数据库（不分布式）才能选 CA**——因为单机不存在网络分区。
真正的分布式系统都在 CP 和 AP 之间二选一。

> 面试坑题：**"你能举个 CA 系统的例子吗？"** → 答："单机 MySQL 就是 CA。分布式系统不存在 CA。"

### 2.4 一个常见误解

CAP 不是"永远只能二选一"——**它是描述网络分区那一刻的取舍**。
没分区的时候，C 和 A 都能拿到——大家都好好的。

正确理解：

```
没分区时：    C ✅  A ✅  （岁月静好）
分区发生时：  C ✅  A ❌    或    C ❌  A ✅（必须二选一）
```

## 三、典型组件归类

| 组件 | 类型 | 取舍逻辑 |
| --- | --- | --- |
| **ZooKeeper** | CP | 半数节点写成功才返回，分区时拒绝服务 |
| **etcd** | CP | Raft 协议，少数派写不进 |
| **HBase** | CP | RegionServer 挂了那段数据短暂不可用 |
| **Consul** | CP | Raft 协议，类似 etcd |
| **Redis Cluster** | AP（弱一致） | 异步复制，主挂从切，可能丢少量写 |
| **Eureka** | AP | 心跳剔除，分区时各节点独立服务 |
| **Cassandra** | AP（可调） | Quorum 可调，默认 AP |
| **DynamoDB** | AP | 最终一致 |
| **Nacos** | **AP / CP 可切换** | 默认 AP（注册中心场景），配置中心 CP |
| **Kafka** | CP（min.insync.replicas） | ISR 机制，写入不达副本数失败 |

### 3.1 为什么注册中心一般选 AP

**注册中心的核心矛盾**：分区时，调用方应该看到"过时但能用"的服务列表，还是"啥也看不到"？

- **AP**（Eureka / 默认 Nacos）：分区时各节点独立维护服务列表，调用方拿到的可能是过时数据，**但能调通服务**
- **CP**（ZK）：分区时少数派注册中心拒绝服务，调用方**完全拿不到服务列表，业务直接挂**

线上事故案例：
> 某公司用 ZK 当注册中心，机房网络抖动 30s → ZK Leader 切换 → 大量服务读不到注册信息 → 整站 503 → 改用 Eureka/Nacos 后没再出过这事。

注册中心**优先保证可用**，过时的列表客户端可以容错（调一个挂的、自动重试），但拿不到列表是致命的。

### 3.2 配置中心为什么要 CP

配置中心存的是"权威配置"——支付通道开关、降级开关、限流阈值。

如果用 AP：分区时可能两个节点配置不一致，应用读到不同配置 → 一半实例放行交易、一半实例拦截 → 数据混乱。

CP 牺牲一点可用性（分区时少数派拒绝写入），换来"配置永远一致"。

### 3.3 ZK 不适合做注册中心的真正原因

阿里内部论证后弃用 ZK 改用 Nacos，三个理由：
1. **ZK 是 CP，注册中心场景应该 AP**（上面讲了）
2. **ZK 的写性能差**（Leader 单点写，每次写都要过半数确认）
3. **ZK 客户端 watch 在大规模实例下可能"羊群效应"**（一个节点变化，所有客户端都触发回调）

详见阿里巴巴技术博客《阿里巴巴为什么不用 ZooKeeper 做服务发现》。

## 四、BASE 理论（CAP 的工程化妥协）

### 4.1 为什么需要 BASE

CAP 告诉你"不能完美"，但没告诉你"具体怎么做"。
BASE 给出工程层面的指导思想：**承认强一致难达成，追求最终一致**。

由 eBay 工程师提出，现在是互联网架构的事实标准。

### 4.2 三个字母

| 字母 | 含义 | 落地表现 |
| --- | --- | --- |
| **B** | **B**asically **A**vailable 基本可用 | 故障时**降级**而非完全不可用：响应变慢、部分功能关闭、返回兜底数据 |
| **S** | **S**oft state 软状态 | **允许中间状态存在**：订单"支付中"、库存"冻结中"、消息"发送中" |
| **E** | **E**ventually consistent 最终一致 | **经过一段时间后**所有副本数据一致（不要求实时） |

### 4.3 BASE vs ACID

| 维度 | ACID（强一致） | BASE（最终一致） |
| --- | --- | --- |
| 一致性 | 强一致 | 最终一致 |
| 可用性 | 牺牲（事务期间锁等待） | 高可用 |
| 适用 | 单库事务、金融核心 | 互联网分布式 |
| 复杂度 | 低（DB 包办） | 高（业务自己设计） |
| 典型方案 | MySQL ACID 事务 | 本地消息表、事务消息、Saga |

> 不是 BASE 取代 ACID——单库内部还是 ACID，跨库才用 BASE 思想。

### 4.4 BASE 怎么落到具体方案

| BASE 元素 | 实际方案 |
| --- | --- |
| **基本可用** | 限流、熔断、降级、超时、Hystrix/Sentinel |
| **软状态** | 订单中间状态、TCC 的 Try 阶段、消息的 half 状态 |
| **最终一致** | 消息重试、对账系统、定时补偿 |

举例：电商下单的 BASE 落地

```
用户下单 → 订单状态 = "已创建"            ← 软状态
       → 发 MQ 给库存服务（异步）         ← 最终一致
       → 库存扣减失败？重试 / 补偿         ← 基本可用
       → 最终库存对齐                      ← 最终一致
```

如果用强一致（XA）：每下一单卡 50ms 等所有服务确认，QPS 上不去 → 互联网无法接受。

## 五、CAP / BASE / ACID 三者关系

```
[ACID]  单机事务的"完美保证"
   │
   │ 进入分布式
   ↓
[CAP]   告诉你"不可能完美"，必须取舍
   │
   │ 工程化落地
   ↓
[BASE]  教你"如何取舍"——基本可用 + 软状态 + 最终一致
```

记忆口诀：**ACID 是理想，CAP 是约束，BASE 是妥协。**

## 六、生产案例

### 案例 1：注册中心选型踩坑

> 公司初期用 ZK，机房网络抖动 → Leader 切换 30s → 服务发现 502 → 全站不可用。
> 切换到 Nacos AP 模式后，分区时各节点照常工作，调用方拿过期列表也能调通（配合熔断重试）→ 类似事件再没复现。

**教训**：注册中心选 AP，"我宁可拿到过时数据，也不能拿不到数据"。

### 案例 2：跨城多活的 CAP 取舍

> 某金融系统跨北京/上海双机房：
> - **强一致方案（CP）**：每次写都跨城同步 → RTT 30ms → 单笔交易延迟极高
> - **最终一致方案（AP）**：本地写 + 异步同步 → 延迟低但可能短暂不一致
>
> 最终方案：**核心交易（账户余额）用 CP**，**非核心（积分、通知）用 AP**——按数据敏感度分别取舍。

### 案例 3：Redis 集群丢数据

> 业务用 Redis Cluster 缓存订单状态。Master 挂了从切上来 → 因为是异步复制，最近 100ms 的写丢了 → **业务以为订单已支付，实际 Redis 里还是未支付**。

**根因**：Redis Cluster 是 AP，主从异步复制，故障切换会丢数据。
**修复**：关键状态不能只信缓存，必须 DB 兜底（Cache Aside 失效）。

### 案例 4：ZK Watcher 雪崩

> 某团队 1000+ 个微服务用 ZK 注册，Leader 切换时所有客户端 watch 触发 → 1000+ 个客户端同时拉服务列表 → ZK 写流量打爆 → 雪崩。

**根因**：ZK 通知风暴 + 客户端羊群效应。
**修复**：迁移到 Nacos，长轮询代替 watch。

## 七、面试高频追问

### Q1：CAP 是不是永远只能二选一？

不是。**只在网络分区那一刻才需要二选一**。
没分区时，C 和 A 都能拿到——所以日常运行中分布式系统看起来很正常。
分区发生时，CP 系统牺牲 A（拒绝服务），AP 系统牺牲 C（返回旧数据）。

### Q2：为什么说 CAP 的 C 比 ACID 的 C 严格？

| | ACID 的 C | CAP 的 C |
| --- | --- | --- |
| 含义 | 事务前后数据满足业务约束（外键、check） | 任意节点在任意时刻读到的数据完全一致 |
| 等级 | 业务规则约束 | **线性一致性**（强一致） |

ACID 的 C 是"事务不破坏业务规则"，CAP 的 C 是"任何客户端任何时刻看到的数据都一样"——是分布式语境下的"强一致"。

### Q3：MySQL 主从复制是 CP 还是 AP？

**默认 AP**：异步复制，主挂从顶上来可能丢最近写。
半同步复制：从 AP 偏向 CP，但仍非完全 CP。
MySQL Group Replication / MGR：CP（多数派提交）。

### Q4：ZK 是 CP，那 ZK 集群分区时怎么办？

ZK 用 ZAB 协议（类 Paxos）：
- **多数派分区**（Leader 在多数派）：继续工作，少数派节点拒绝服务
- **少数派分区**（Leader 在少数派）：Leader 失去多数 → 集群无 Leader → **整体不可用**

这就是 CP 的代价——少数派直接 503。

### Q5：Nacos 既是 AP 又是 CP，怎么做到的？

Nacos 用两套协议：
- **AP 模式**：自研 Distro 协议（弱一致 + 心跳）→ 用于服务注册发现
- **CP 模式**：Raft 协议 → 用于配置中心、命名空间元数据

可以在配置文件里指定服务实例是 ephemeral（AP）还是 persistent（CP）：

```properties
spring.cloud.nacos.discovery.ephemeral=true   # AP，默认
spring.cloud.nacos.discovery.ephemeral=false  # CP
```

### Q6：BASE 一定优于 ACID 吗？

不一定。
- **金融核心**（账务、转账）：必须 ACID，BASE 不能用
- **互联网通用**：BASE 性价比高
- **混合架构**：核心数据 ACID，非核心 BASE

举例：电商下单
- 扣余额 / 写订单：本地 ACID 事务
- 扣库存 / 加积分：BASE 最终一致

### Q7：怎么保证最终一致性？

工程上靠 **3+1 套机制**：
1. **消息中间件**：把变更事件可靠投递（本地消息表 + MQ）
2. **重试 + 补偿**：失败重试，超过阈值进死信
3. **对账系统**：定时扫描双方数据差异，自动修复
4. **兜底告警**：补偿失败的人工介入

详见 [分布式事务](./分布式事务.md)。

### Q8：CAP 理论是不是过时了？

理论本身没过时，但工程界已经超越了它：
- **PACELC 理论**：扩展 CAP，加入"没分区时的 L（Latency）vs C 取舍"
- **分级一致性**：强一致 / 因果一致 / 会话一致 / 最终一致 多档可选
- **NewSQL（TiDB / Spanner）**：用 Raft + Paxos + TSO 在保证强一致的同时几乎不牺牲可用性

但 CAP 的核心思想——"分布式不能完美" 永远成立。

## 八、答题模板（60 秒话术）

> **CAP 是描述分布式系统在网络分区时的取舍**：一致性 C、可用性 A、分区容错性 P，三者只能选两个。
> 但 P 是必选项——网络故障客观存在，**真正的取舍是 CP 还是 AP**。
> CP 的代表是 ZooKeeper、etcd，分区时少数派拒绝服务；AP 的代表是 Eureka、Cassandra，分区时返回过时数据但保证响应。**Nacos 两种模式可切**，注册中心走 AP，配置中心走 CP。
>
> **BASE 是 CAP 的工程妥协**——基本可用、软状态、最终一致。承认强一致难达成，靠**消息中间件 + 重试补偿 + 对账系统**最终对齐数据。互联网分布式事务（本地消息表、事务消息、Saga）几乎都是 BASE 思路。
>
> 选型逻辑：**金融核心走 ACID，注册中心走 AP，配置中心走 CP，互联网通用业务走 BASE**。
>
> **关键认知**：单机才有 CA，分布式没有；CAP 只在分区那一刻取舍，平时 C 和 A 都能拿到；BASE 不是 ACID 的替代，是它的"分布式版本"。
