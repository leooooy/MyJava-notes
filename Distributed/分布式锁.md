# 分布式锁（Redis vs ZooKeeper vs etcd 横向对比）

> 大厂面试 P6+ 必考——选型类题目最容易答得浅。
> 本篇要解决的问题：
> ① 分布式锁要满足哪些**正确性**约束？
> ② Redis / ZK / etcd 三种实现各自的**核心机制**是什么？
> ③ Redlock 为什么被 Martin Kleppmann 反对？这场争论的本质是啥？
> ④ **选型决策**：高并发选哪个？强一致选哪个？K8s 生态选哪个？
>
> Redis 锁的演进细节（SETNX → Redisson 看门狗 → Redlock）见 [Redis/分布式锁](../Redis/分布式锁.md)，本篇聚焦"三方对比 + 选型 + 争议"。

## 一、分布式锁的四大正确性要求

任何分布式锁都必须满足（缺一不可）：

| 要求 | 含义 | 不满足的后果 |
| --- | --- | --- |
| **互斥性** | 任意时刻只有一个客户端持有锁 | 业务逻辑被并发执行 |
| **避免死锁** | 客户端崩溃后锁能自动释放 | 资源永久锁死 |
| **容错性** | 部分节点故障时锁服务仍可用 | 锁服务瘫痪 |
| **解铃还须系铃人** | 只有加锁的客户端能解锁 | 锁被错误释放（A 解了 B 的锁） |

**进阶要求**（生产场景常见）：
- **可重入**：同一线程多次拿同一锁不阻塞（业务里 A 调 B，B 也想拿同一把锁）
- **公平性**：先到先得，避免饥饿
- **锁续约（看门狗）**：业务超时不死锁也不超期
- **支持读写锁**：读读不互斥，提高并发

## 二、Redis 分布式锁（核心：SETNX + Lua + 看门狗）

### 2.1 核心原理（一句话）

```bash
SET lock_key client_uuid NX EX 30
# NX：key 不存在才设置（互斥）
# EX 30：30 秒后自动过期（避免死锁）
# value=UUID：标识持有者（解铃还须系铃人）
```

释放锁用 Lua 保证"判断 + 删除"原子：

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
```

### 2.2 演进路径（必背）

```
V1: SETNX                        ← 拿锁后崩溃就死锁
 ↓
V2: SETNX + EXPIRE               ← 两条命令非原子，仍死锁
 ↓
V3: SET NX EX（2.6.12+）         ← 原子拿锁，但锁过期会误删别人锁
 ↓
V4: V3 + value=UUID + Lua 删     ← 解决误删，但锁过期业务还没完
 ↓
V5: V4 + 看门狗（Redisson）      ← 自动续约，生产标配
 ↓
V6: Redlock（多 Master 投票）    ← 解决主从切换丢锁，但有争议
```

→ 详细演进见 [Redis/分布式锁](../Redis/分布式锁.md)

### 2.3 Redisson 看门狗机制

业务超过 30s 没完？后台线程每 10s（leaseTime/3）检查一次，自动续约到 30s：

```java
// Redisson 默认开启看门狗
RLock lock = redisson.getLock("lock:order:1001");
lock.lock();  // 默认 30s TTL，自动续约
try {
    doBusiness();  // 哪怕跑 1 小时也不会丢锁
} finally {
    lock.unlock();  // 显式释放，停止续约
}
```

**注意**：必须用无参 `lock()`，传了 `leaseTime` 就关闭看门狗：

```java
lock.lock(60, TimeUnit.SECONDS);  // ❌ 看门狗关闭，60s 后强制释放
```

### 2.4 Redis 锁的三个软肋

| 软肋 | 风险场景 |
| --- | --- |
| **主从异步复制** | Master 写完锁后挂掉，从切上来锁丢失 → 多个客户端同时持锁 |
| **GC / 网络暂停** | 客户端卡 GC 30s，锁过期被另一个客户端拿走 → 双持锁 |
| **时钟漂移** | NTP 校时跳变，TTL 算错 → Redlock 的核心争议 |

## 三、ZooKeeper 分布式锁（临时顺序节点）

### 3.1 核心原理

利用 ZK 两个特性：
- **临时节点（Ephemeral Node）**：客户端断开自动删除（解决死锁）
- **顺序节点（Sequential Node）**：自动追加递增序号

```
/locks/order_1001/                   ← 锁路径
├── lock-0000000001 (Client A)        ← A 创建临时顺序节点
├── lock-0000000002 (Client B)
├── lock-0000000003 (Client C)
```

**加锁流程**（公平锁，FIFO）：

```
1. Client X 在 /locks/order_1001/ 下创建临时顺序节点 lock-N
2. 列出该路径下所有子节点
3. 如果 lock-N 是最小的 → 拿锁成功
4. 否则：watch 比 lock-N 小一位的节点（不是 watch 全部，避免羊群）
5. 被 watch 的节点删除时，重试步骤 2
```

**释放锁**：删除自己创建的节点 → 触发下一个 watch → 下一个客户端拿锁。

### 3.2 Curator 实现（标准库）

```java
CuratorFramework client = CuratorFrameworkFactory.newClient(
    "zk1:2181,zk2:2181,zk3:2181",
    new ExponentialBackoffRetry(1000, 3));
client.start();

InterProcessMutex lock = new InterProcessMutex(client, "/locks/order_1001");
if (lock.acquire(10, TimeUnit.SECONDS)) {
    try {
        doBusiness();
    } finally {
        lock.release();
    }
}
```

Curator 还提供：
- `InterProcessReadWriteLock`：读写锁
- `InterProcessSemaphoreV2`：信号量
- `InterProcessMultiLock`：联锁

### 3.3 ZK 锁的优势

✅ **强一致**（CP）：ZAB 协议保证半数以上节点写成功才返回，不会丢锁
✅ **天然解决死锁**：客户端断连，临时节点自动删除
✅ **公平锁**：顺序节点天生 FIFO
✅ **没有羊群效应**：只 watch 前一个节点，不是全部

### 3.4 ZK 锁的代价

❌ **性能差**：所有写都要走 Leader，过半数节点确认 → 单 Leader 瓶颈，QPS 通常 ~10k
❌ **客户端心跳依赖网络**：网络抖动 → ZK 误判客户端死亡 → 锁被释放 → 双持锁（同 Redis 锁过期问题）
❌ **运维复杂**：ZK 集群本身要维护，写入慢，配置复杂

## 四、etcd 分布式锁（Lease + Revision）

### 4.1 核心原理

etcd 用 Raft 协议，类似 ZK 但有几点不同：

- **Lease（租约）**：给 key 绑定 TTL，客户端必须续约（KeepAlive）才能保持 key 存活
- **Revision（全局递增版本号）**：拿到最小 revision 的客户端持锁
- **Watch**：监听前一个 revision 的删除事件

```go
// 简化版（实际 clientv3.Mutex 已封装好）
session, _ := concurrency.NewSession(client, concurrency.WithTTL(30))
mutex := concurrency.NewMutex(session, "/locks/order_1001")

ctx := context.Background()
mutex.Lock(ctx)         // 阻塞等锁
defer mutex.Unlock(ctx)

doBusiness()
```

### 4.2 etcd 锁的优势

✅ **CP 强一致**：Raft 协议
✅ **比 ZK 性能更好**：~20k QPS（Raft 比 ZAB 略优）
✅ **K8s 原生**：K8s 用 etcd 存所有元数据，云原生场景天然契合
✅ **HTTP/gRPC 接口**：客户端开发友好

### 4.3 etcd 锁的代价

❌ 性能仍不如 Redis（CP 协议天花板）
❌ 生态不如 ZK 成熟（Curator 太香）
❌ 仅在云原生（K8s）场景下普及，传统 Java 体系少见

## 五、Redis vs ZK vs etcd 横向对比（核心对比表）

| 维度 | Redis | ZooKeeper | etcd |
| --- | --- | --- | --- |
| **CAP 类型** | AP | CP | CP |
| **一致性协议** | 主从异步 | ZAB（类 Paxos） | Raft |
| **性能（QPS）** | **10w+** | ~10k | ~20k |
| **锁失效检测** | TTL（被动） | 临时节点（心跳，主动） | Lease + KeepAlive |
| **锁可靠性** | 主从切换可能丢锁 | 不丢锁 | 不丢锁 |
| **客户端崩溃** | TTL 兜底（最长等 TTL） | 立即释放（断连即删） | Lease 过期释放 |
| **公平锁** | Redisson 实现复杂 | 顺序节点天然支持 | Revision 天然支持 |
| **可重入** | Redisson 用 Hash 实现 | Curator 实现 | 需要自己实现 |
| **看门狗续约** | Redisson ✅ | 不需要（基于心跳） | Lease KeepAlive |
| **运维复杂度** | 低 | **高** | 中 |
| **客户端生态** | Redisson、Lettuce | Curator | etcdctl、clientv3 |
| **典型场景** | 互联网、高并发 | 强一致、低 QPS | K8s、云原生 |

### 5.1 性能差距的根因

```
Redis 加锁：单次写命令，主节点本地执行，~0.1ms
ZK 加锁：    创建节点 → Leader 写日志 → 同步给过半 Follower → ACK，~5-10ms
etcd 加锁：  类似 ZK，~3-5ms

差距 50-100 倍——这就是 CP 协议的代价（多副本同步）
```

### 5.2 锁可靠性差距的根因

**Redis 主从异步复制**：
```
1. Client → Master: SET lock NX EX 30 → OK
2. Master 准备同步给 Slave，但还没同步就挂了
3. Slave 提升为新 Master（没有锁数据）
4. 另一个 Client 来加锁 → 成功
   → 两个 Client 同时持锁 ❌
```

**ZK / etcd 同步复制**：
```
1. Client → Leader: 创建节点
2. Leader 必须等过半 Follower 确认才返回成功
3. Leader 挂了，Follower 中已有这条记录的接任 Leader
4. 锁不会丢
```

这就是为什么"金融严选 ZK，互联网首选 Redis"。

## 六、Redlock 之争（Martin vs Antirez 辩论）

### 6.1 Redlock 是什么

Redis 作者 Antirez 提出的多 Master 锁算法，针对"主从切换丢锁"问题：

```
1. Client 在 N 个独立 Master（推荐 5 个）上同时尝试加锁，每次都设 TTL
2. 在 (TTL - 网络耗时) 内拿到 ≥ N/2+1 个节点的锁 → 加锁成功
3. 任一步失败 → 释放所有节点的锁
```

### 6.2 Martin Kleppmann 的反对

2016 年分布式系统专家 Martin（《DDIA》作者）发文 `How to do distributed locking` 反对 Redlock，三大论点：

#### 论点 1：依赖物理时钟

Redlock 依赖各节点本地时钟来计算 TTL。**NTP 校时跳变**（管理员手动调时间、闰秒修正）会让时间突变 → TTL 计算错误 → 多个客户端同时持锁。

> 真实事故：2012 年闰秒事件导致 Linux 时钟跳变，全球大量 Java/MySQL 服务出现各种诡异问题。

#### 论点 2：GC 暂停

Java 的 STW GC 可能暂停几秒。客户端 A 拿到锁，开始处理 → GC 30s → 锁过期 → 客户端 B 拿到锁 → A 醒过来还以为自己有锁，写下去 → **数据破坏**。

Redlock 没法解决这个问题——任何基于 TTL 的锁都没法解决。

#### 论点 3：基于 Fencing Token 才是正解

Martin 主张：**锁本身不能保证安全，必须配合 fencing token**。

```
1. 加锁返回一个全局递增的 token（如锁版本号）
2. 客户端访问下游资源时带上 token
3. 下游资源（DB / 文件系统）只接受 token > 已记录最大值 的请求
4. 旧锁的 token 永远写不进去
```

ZK / etcd 的顺序节点 / Revision 天然就是 fencing token，但 Redis Redlock 没有。

### 6.3 Antirez 的回应

Antirez 回怼：
- 时钟跳变在生产里很罕见，Redlock 在合理假设下是安全的
- GC 问题是所有锁服务的通病，跟 Redlock 无关
- Fencing token 需要下游配合，是另一个层次的话题

### 6.4 业界共识

> **结论：Redlock 在大部分场景够用，但不要把它当作"绝对安全"的强一致锁**。
> - 高并发、能容忍极小概率重复执行：用 Redis 单实例锁就够（Redisson 看门狗）
> - 强一致场景（金融、库存核心）：用 ZK / etcd + fencing token
> - **不要用 Redlock 替代 ZK**——它解决不了 Martin 提出的根本问题

阿里、字节内部基本不用 Redlock，强一致用 ZK，普通业务用 Redis 单实例 + Redisson。

## 七、选型决策树

```
要分布式锁
  │
  ├─ 是否高并发（QPS > 1w）？
  │    ├─ 是 → Redis（必选，ZK/etcd 撑不住）
  │    │       │
  │    │       └─ 主从切换丢锁能容忍吗？
  │    │            ├─ 能（业务幂等兜底）→ Redis 单实例 + Redisson ✅
  │    │            └─ 不能 → 业务侧加 fencing token / 二次校验
  │    │
  │    └─ 否（QPS < 1w，强一致优先）
  │         │
  │         ├─ 已用 K8s / 云原生？→ etcd ✅
  │         ├─ Java 体系，已有 ZK？→ ZooKeeper + Curator ✅
  │         └─ 新项目？→ etcd（生态新，代码现代）
  │
  └─ 是否需要 fencing token（绝对安全）？
       └─ 必须用 ZK 顺序节点 / etcd Revision
```

### 7.1 真实场景示例

| 场景 | 锁方案 | 理由 |
| --- | --- | --- |
| 秒杀 / 抢购 | Redis + Redisson | QPS 高，业务幂等性兜底 |
| 订单状态变更 | Redis + 数据库行锁 | Redis 防并发，DB 兜底一致性 |
| 库存扣减（金融级） | DB 行锁 + 唯一约束 | 不需要分布式锁，DB 自带 |
| 选主 / Leader Election | ZK / etcd | 必须强一致，不能脑裂 |
| 配置变更 | ZK / etcd | 强一致 + 通知 |
| K8s Operator 控制器 | etcd（client-go） | 原生支持 |
| 单点定时任务（防多实例执行） | Redis 锁 / xxl-job | Redis 锁简单够用 |

## 八、生产踩过的坑

### 坑 1：Redis 锁误删（真实事故）

> 业务里写 `redis.del(lockKey)` 释放锁，没校验 value → 客户端 A 业务慢了 → A 的锁过期 → B 拿到锁 → A 终于完事，DEL 把 B 的锁删了 → C 又拿到锁，B 和 C 同时操作。
> **修复**：必须用 Lua 脚本校验 UUID 后再删。

### 坑 2：Redisson 看门狗被关闭

```java
// 同事写法
lock.lock(30, TimeUnit.SECONDS);  // 关掉了看门狗
// 业务跑了 35s 后锁过期，被另一个实例拿走 → 双持锁
```

**修复**：业务时间不可预估时，用无参 `lock()` 让看门狗自动续约。

### 坑 3：ZK Session 误判

> ZK 集群网络抖动 30s，客户端 session timeout=30s → 临时节点被删 → 锁被释放 → 另一客户端拿锁 → 原客户端业务还没完。
> **修复**：业务侧加 fencing token 校验，避免双持锁。

### 坑 4：etcd Lease 续约失败

> Go 程序 GC 严重，etcd KeepAlive goroutine 卡住 → Lease 到期 → 锁释放 → 双持锁。
> **修复**：业务里也要做 idempotency / fencing token 兜底。

### 坑 5：Redlock 时钟跳变

> 运维手动校时把服务器时间往前拉了 5 分钟 → Redlock 计算的"剩余 TTL" 错乱 → 部分节点上锁已过期但客户端不知道 → 业务双跑。
> **修复**：禁用手动校时，用 chrony / NTP 平滑校准；关键场景不用 Redlock。

### 坑 6：用分布式锁做"全局唯一性"

```java
// ❌ 错用
lock.lock();
if (!exists(orderId)) {
    create(orderId);
}
lock.unlock();
```

锁释放后，另一个进程拿到锁可能仍 exists 检查失败（DB 主从延迟）→ 重复创建。
**正确**：DB 唯一索引兜底，分布式锁只是减少冲突，不是唯一性保证。

## 九、面试高频追问

### Q1：Redis 锁怎么防止误删？

加锁时 `value = UUID`，删锁前 Lua 脚本判断 UUID 一致才删：

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
```

### Q2：Redisson 看门狗的工作原理？

加锁默认 TTL=30s，启动后台线程每 10s（即 leaseTime/3）检查一次：
- 锁还在自己手里？→ Redis EXPIRE 续到 30s
- 业务释放锁？→ 停止续约线程

底层用 Netty 的 HashedWheelTimer 调度。

### Q3：Redis 锁怎么实现可重入？

Redisson 用 Redis Hash：

```
HSET lock:order:1001 thread_uuid 1   # 第一次加锁，count=1
HINCRBY lock:order:1001 thread_uuid 1  # 同线程重入，count=2
HINCRBY lock:order:1001 thread_uuid -1  # 释放一次
HDEL lock:order:1001 thread_uuid       # count=0 时删除
```

### Q4：Redlock 算法解决了什么、没解决什么？

**解决**：单 Master 主从切换可能丢锁。
**没解决**：① 时钟跳变；② 客户端 GC 暂停。要绝对安全必须配 fencing token。

### Q5：ZK 锁的羊群效应是什么？怎么避免？

**羊群效应**：所有等锁的客户端 watch 锁节点，锁释放时全部被通知 → 雪崩。
**避免**：用顺序节点，每个客户端只 watch **比自己小一位的节点**，锁释放时只通知一个客户端。

### Q6：分布式锁能保证强一致吗？

不能。**任何基于 TTL 的锁都不保证强一致**——客户端 GC 暂停时锁会被错误抢走。
要强一致必须配合 **fencing token**：下游资源拒绝旧 token 的请求。

### Q7：业务里加锁失败怎么办？

| 策略 | 适用 |
| --- | --- |
| 立即返回失败 | 抢购、秒杀（让用户重试） |
| 自旋等待 | 短任务，能很快拿到 |
| 指数退避重试 | 网络抖动场景 |
| 排队（Redisson Fair Lock） | 公平性要求高 |

### Q8：分布式锁和 DB 锁哪个性能高？

```
Redis 锁：    ~0.1ms       （内存操作）
ZK 锁：       ~5ms         （Raft 半同步）
DB 行锁：     ~1-3ms       （索引查找 + 行锁）
DB 表锁：     ~10ms+       （锁等待严重）
```

Redis 最快。但如果业务本来就要查 DB（如 SELECT FOR UPDATE），用 DB 行锁省一次网络。

### Q9：能用 Redis 实现一个公平锁吗？

可以，但代价大：
- Redisson FairLock 用 Sorted Set 维护等锁队列
- 性能比普通锁低 20-30%
- 不如直接用 ZK / etcd（天然公平）

### Q10：分布式锁过期时间怎么定？

| 业务类型 | TTL | 备注 |
| --- | --- | --- |
| 短业务（< 1s） | 5-10s | 留缓冲 |
| 中业务（1-30s） | 30s + 看门狗 | 标准方案 |
| 长业务（> 30s） | 看门狗续约 | 不要硬设很长，万一死锁就锁很久 |
| 极短抢占（计数器） | 100-500ms | 不需要看门狗 |

## 十、答题模板（60 秒话术）

> 分布式锁三选一：**Redis、ZooKeeper、etcd**，本质是 **AP 性能** 和 **CP 可靠性** 的取舍。
>
> **Redis 锁**：`SET NX EX` 加锁，**value=UUID** 防误删，**Lua 脚本删锁**保证原子。生产标配 **Redisson + 看门狗**——业务超期自动续约，无参 `lock()` 才生效。**性能最高，QPS 10w+**，缺点是主从异步可能丢锁。
>
> **ZK 锁**：临时顺序节点 + 监听前一个节点。**强一致 CP**，客户端断连临时节点自动删除，天然公平锁。缺点是性能 ~10k QPS，运维复杂。
>
> **etcd 锁**：Lease + KeepAlive，类似 ZK 但用 Raft，K8s 生态原生。
>
> **Redlock 之争**：Antirez 提出多 Master 投票，Martin Kleppmann 反对——**时钟跳变和 GC 暂停下不安全**，要绝对安全必须配合 **fencing token**（下游拒绝旧 token）。生产里互联网用 Redis + 业务幂等兜底，金融用 ZK。
>
> **选型**：高并发选 Redis，强一致选 ZK / etcd，K8s 场景选 etcd。**不要用 Redlock 替代 ZK**——它解决不了根本问题。
>
> **关键认知**：分布式锁不能保证强一致，只能"减少冲突"——业务侧仍要靠**唯一约束 / 状态机 / fencing token**做最终兜底。
