# 分布式事务

> 跨服务/跨库的"一致性"问题——业务复杂度从单库 ACID 跳到分布式 BASE，是 P6+ 必考。
> 本篇要解决的问题：
> ① 单库事务的 ACID 在分布式下为什么塌陷？
> ② **2PC / 3PC / TCC / 本地消息表 / 事务消息 / Saga / Seata AT** 各自的边界和取舍
> ③ TCC 的三大坑（**幂等 / 空回滚 / 悬挂**）怎么解决
> ④ 互联网业务的**主流方案**和**金融业务**的差异在哪
>
> 面试回答顺序：**先讲为什么需要 → 再讲 CAP/BASE → 再讲方案 → 最后说选型**。

---

## 一、为什么需要分布式事务

单机事务靠数据库 redo/undo log + 锁就能做到。但微服务拆分后：

- 下单 → 订单服务（订单库） + 库存服务（库存库） + 积分服务（积分库）
- 三个库分散在不同实例上，谁都没法一把锁锁住所有人

任何一步成功而其他失败 → 数据不一致：
- 订单成了，库存没扣 → 超卖
- 库存扣了，订单回滚 → 库存丢失

---

## 二、理论基础

### CAP 定理

分布式系统不能同时满足三者：
- **C**onsistency 一致性
- **A**vailability 可用性
- **P**artition tolerance 分区容错性

P 是必选项（网络一定会出问题），所以现实中是在 CP 和 AP 之间二选一。
- **CP**：ZooKeeper、etcd、HBase（Master 挂了不可用，但数据强一致）
- **AP**：Eureka、Cassandra（永远可用，但可能短暂读到旧数据）

### BASE 理论

CAP 的工程化妥协，承认强一致性难达成，追求**最终一致性**：
- **B**asically **A**vailable 基本可用（降级）
- **S**oft state 软状态（中间状态可见）
- **E**ventual consistency 最终一致

> 分布式事务的现代方案绝大多数都是 BASE 思路（最终一致），强一致只在金融核心系统少量使用（如 2PC + XA）。

## 三、方案全景图

| 方案 | 一致性 | 性能 | 复杂度 | 典型场景 |
| --- | --- | --- | --- | --- |
| **2PC（XA）** | 强一致 | 差（阻塞） | 中 | 跨库强一致，传统行业 |
| **3PC** | 强一致 | 差 | 高 | 几乎不用，理论意义大 |
| **TCC** | 强一致 | 中 | 高（侵入业务） | 金融、支付 |
| **本地消息表** | 最终一致 | 高 | 低 | 主流互联网 |
| **可靠消息（事务消息）** | 最终一致 | 高 | 低 | 主流互联网 |
| **Saga** | 最终一致 | 高 | 中 | 长流程业务（订单、旅游） |
| **最大努力通知** | 最终一致 | 高 | 低 | 通知类（短信、第三方回调） |
| **Seata AT** | 最终一致（默认） | 中 | 低（无侵入） | 中小团队微服务首选 |

## 四、方案详解

### 2PC（两阶段提交）

经典的强一致方案，由 **协调者（TC）** 和 **参与者（RM）** 配合完成。

#### 阶段一：准备（Prepare）

```
TC ──[CanCommit?]──> RM1, RM2, RM3
RM 各自执行事务到 prepare（写好 undo/redo log），但不提交
RM ──[Yes/No]──> TC
```

#### 阶段二：提交 / 回滚（Commit/Rollback）

```
全部 Yes      → TC ──[Commit]──> 所有 RM 提交
有一个 No     → TC ──[Rollback]──> 所有 RM 回滚
```

#### 致命问题

1. **同步阻塞**：Prepare 后 RM 必须持有锁等 TC 通知，期间其他事务都阻塞。
2. **协调者单点**：TC 挂了 → RM 卡死，资源永远锁着。
3. **数据不一致**：Commit 阶段部分 RM 收到、部分没收到 → 部分提交部分没提交。
4. **太悲观**：性能差，不适合高并发。

> MySQL XA 协议就是 2PC 的实现，性能损耗 3~5 倍，互联网公司很少用。

### 3PC（三阶段提交）

为了解决 2PC 的阻塞问题，加了一个 CanCommit 阶段 + RM 的超时机制：

```
1. CanCommit  : TC 询问，RM 不锁资源，只判断能不能做
2. PreCommit  : TC 收到全 Yes 后，让 RM 开始 prepare（这一步才锁资源）
3. DoCommit   : TC 通知提交
```

改进：
- RM 有超时：PreCommit 没收到，超时自动回滚；DoCommit 没收到，超时自动提交（赌大概率成功）。
- TC 单点失效不会让 RM 永久阻塞。

但还是没完全解决一致性问题，DoCommit 阶段网络分区还是可能出问题。**工业界几乎不用，面试讲个对比就行**。

### TCC（Try-Confirm-Cancel）

业务层面的 2PC，把每个操作拆成三个接口：

```
Try     : 资源预留（冻结库存、冻结额度）
Confirm : 真正执行（扣库存、扣额度）  —— 幂等
Cancel  : 释放预留（解冻）           —— 幂等
```

**例子**（下单 → 扣库存 + 扣余额）：

| 阶段 | 库存服务 | 账户服务 |
| --- | --- | --- |
| Try | 库存 -1，冻结字段 +1 | 余额 -10，冻结余额 +10 |
| Confirm | 冻结字段 -1（落账） | 冻结余额 -10（落账） |
| Cancel | 库存 +1，冻结 -1 | 余额 +10，冻结 -10 |

#### 关键难点

1. **幂等**：网络抖动会重试，Confirm/Cancel 必须幂等。
2. **空回滚**：Try 还没到，Cancel 先到了 → Cancel 要识别出来，不做实际回滚。
3. **悬挂**：Cancel 比 Try 先执行后，Try 又来了 → Try 要识别出"已经被 Cancel 了"，拒绝执行。
4. **业务侵入大**：每个服务三个接口，改造成本高。

> 适合金融核心：支付、转账、对账。框架：Seata TCC、Hmily、ByteTCC。

### 本地消息表（最经典的最终一致方案）

把"业务操作"和"消息发送"放在**同一个本地事务**里，靠 DB 保证原子性。

```
1. 订单服务在本地事务里：
   - INSERT 订单
   - INSERT 一条"待发送消息"到 message 表
   COMMIT  ← 本地事务原子

2. 后台定时任务扫 message 表：
   - 把状态为"待发送"的消息投递到 MQ
   - 投递成功后更新状态为"已发送"

3. 库存服务消费 MQ：
   - 扣库存
   - 失败重试（消费端幂等）
```

#### 优点
- 不依赖 MQ 的事务消息能力，普通 MQ 就行
- 思路简单，易于排查

#### 缺点
- 业务库要多维护一张消息表
- 需要扫表（可以做成异步、分库分表）

### 可靠消息最终一致性（事务消息）

RocketMQ 提供原生事务消息支持，把上面的"本地消息表"机制内置到了 MQ 中。

```
1. Producer 发送 half message 到 Broker（对消费者不可见）
2. Producer 执行本地事务
3. Producer 根据本地事务结果向 Broker 发 commit / rollback
4. Broker 收到 commit → 投递；收到 rollback → 删除
5. 长时间没收到决议 → Broker 回查 Producer 的本地事务状态
```

→ 详见 [RocketMQ 分布式事务](../MQ/RocketMQ分布式事务.md)、[RocketMQ 事务回查](../MQ/RocketMQ事务回查.md)

### Saga（长流程业务首选）

把长流程拆成多个本地事务 T1, T2, ..., Tn，每个事务都有对应的补偿操作 C1, C2, ..., Cn。

- 正常：T1 → T2 → T3 → ... → Tn
- 失败：执行到 Ti 失败 → 倒序执行 C(i-1) → ... → C1

两种实现：
- **编排式（Choreography）**：服务之间靠事件触发，去中心化，但流程难追踪
- **编制式（Orchestration）**：有一个 Saga 协调器（如 Seata Saga），中心化推进

适用场景：旅游订单（订机票 + 订酒店 + 租车），步骤多、单步处理时间长，不适合用 TCC 锁这么久。

### 最大努力通知

适用于结果对外通知场景（如支付回调）：
- 业务方完成后，多次重试通知接收方
- 配合接收方的查询接口（业务方反查兜底）
- 隔指数退避通知 N 次后人工介入

### Seata AT 模式（无侵入，推荐入门）

Seata 默认模式，对业务**几乎无侵入**，原理：

```
1. 一阶段：解析 SQL，把执行前后的数据存到 undo_log 表，正常提交
2. 全局事务提交：异步删除 undo_log
3. 全局事务回滚：根据 undo_log 反向 SQL 把数据改回去
```

优点：
- 业务代码不改，只加 `@GlobalTransactional` 注解
- 性能好（一阶段就提交了，不锁等）

缺点：
- 不支持复杂 SQL（join、动态 SQL）
- 全局锁（Seata 自己维护的），高并发时是瓶颈
- 二阶段回滚是"脏写"，需要业务能容忍中间态被读到（弱隔离）

## 五、面试高频问答

### Q1：2PC 的"数据不一致"窗口具体在哪一步？

第二阶段，TC 发出 Commit 后：
- TC 发完 Commit 给 RM1 就崩了
- RM1 收到 Commit 提交了，RM2/RM3 没收到
- 新 TC 选举出来时，状态丢失，无法决策
→ 数据不一致

3PC 加超时机制后，RM 会"赌"成功提交，但仍可能赌错。

### Q2：TCC 怎么保证幂等？

每个 Confirm/Cancel 接口入参带**全局事务 ID + 分支 ID**。
执行前先查"事务执行记录表"：
- 已执行 → 直接返回成功（幂等）
- 未执行 → 加锁执行，记录到表中

### Q3：消息事务和本地消息表的区别？

| 维度 | 本地消息表 | 事务消息 |
| --- | --- | --- |
| 依赖 | 任何 MQ 都行 | 需要 MQ 支持事务消息（RocketMQ） |
| 业务库压力 | 多一张消息表 + 定时扫表 | 无 |
| 一致性保障 | DB 本地事务 | half 消息 + 回查 |
| 复杂度 | 简单 | 需要实现回查接口 |

> **大厂选型**：消息基础设施成熟（RocketMQ）→ 事务消息；否则 → 本地消息表。两者本质相同，都是"业务 + 消息"的原子性。

### Q4：怎么选方案？

| 业务特征 | 推荐方案 |
| --- | --- |
| 强一致、金融核心、低并发 | TCC |
| 跨库强一致、可接受性能损失 | XA / 2PC |
| 高并发、互联网业务、可接受秒级最终一致 | 本地消息表 / 事务消息 |
| 长流程、多服务（订单、旅游） | Saga |
| 跨公司通知、回调场景 | 最大努力通知 |
| 中小团队，想低侵入 | Seata AT |

### Q5：为什么不用 XA 直接搞？

性能差 3-5 倍，强阻塞，互联网业务接受不了。
传统行业（银行核心、电信计费）数据极敏感、并发不高，才用 XA。

### Q6：Seata AT 的全局锁怎么理解？

Seata 在自己的 lock_table 里给"被改的行"上一把分布式锁（key = `tableName:pk`），全局事务结束才释放。
作用：避免一阶段提交后、二阶段回滚前，别的事务把这行又改了，导致回滚不掉（脏写）。
副作用：高并发下成为瓶颈，必须避免热点行。

### Q7：本地消息表的消息如果一直发不出去？

补偿机制必须有：
1. 重试次数累加，超过阈值（如 5 次）入"死信队列"
2. 监控告警（消息表中"待发送 + 创建时间 > 5 分钟"的数量）
3. 人工介入或自动补偿任务

### Q8：消费端怎么保证幂等？

→ 详见 [幂等](./幂等.md)、[如何解决重复消费](../MQ/如何解决重复消费.md)

常用：
- DB 唯一约束（业务唯一键 + insert ... on duplicate key）
- 状态机（订单已支付状态下不再处理）
- Redis SETNX（业务 ID 做 key，TTL 兜底）
- Token 表（先发 Token，消费时核销）

## 六、生产踩过的坑

1. **TCC Cancel 写错**：早期 Cancel 没考虑空回滚，Try 还没到 Cancel 先到 → 实际"释放"了一笔从未冻结的库存，导致超卖。
2. **本地消息表扫表慢**：消息表数据上千万后扫表卡死，分库分表 + 状态字段加索引 + 按时间分区。
3. **Seata AT 高并发热点**：秒杀场景全局锁阻塞，最后改成 TCC + Redis 预扣。
4. **事务消息回查接口幂等没做**：Broker 多次回查，每次回查都触发 DB 操作，把库压挂。回查接口必须只读 + 幂等。
5. **Saga 补偿失败**：补偿动作本身也可能失败，需要补偿的补偿，最终方案：补偿失败入告警 + 人工介入。
6. **跨服务调用没传 XID**：用 Seata 但 RPC 没透传 `XID` 上下文，全局事务断链 → 子分支根本没纳入管理 → 部分服务回滚不了。修复：Feign / Dubbo 拦截器统一透传。

## 七、答题模板（60 秒话术）

> **分布式事务的本质**：多服务/多库怎么对外保证一致性——单库 ACID 在分布式下塌陷，必须 CAP 三选二，工程上用 BASE（基本可用 + 软状态 + 最终一致）落地。
>
> **方案七大主流**——按一致性强度排：
> ① **2PC/XA**：强一致但同步阻塞、协调者单点，性能差 3-5 倍，**只在传统行业用**；
> ② **TCC**：业务层 2PC，**Try-Confirm-Cancel** 三接口，强一致但**业务侵入大**，必须解决**幂等/空回滚/悬挂**——金融支付场景标配；
> ③ **本地消息表**：业务和消息一起本地事务提交，定时扫描投递 MQ → 消费端幂等。**互联网最经典最终一致方案**，依赖任意 MQ；
> ④ **事务消息（RocketMQ）**：half message + 本地事务 + 回查，把本地消息表机制内置到 MQ；
> ⑤ **Saga**：长流程拆成 T1...Tn 配补偿 C1...Cn，**编排式 vs 编制式**，适合**订单/旅游**长流程；
> ⑥ **最大努力通知**：第三方回调标准方案，重试 + 反查兜底；
> ⑦ **Seata AT**：基于 undo_log 的逆向 SQL 回滚，**业务零侵入**——中小团队微服务首选，但**全局锁是高并发瓶颈**。
>
> **选型公式**：金融核心 → TCC；互联网高并发 → 本地消息表 / 事务消息；长流程 → Saga；中小团队 → Seata AT；跨公司 → 最大努力通知。
>
> **关键认知**：所有方案都需要**消费端幂等兜底**，因为 MQ / RPC 都是 at-least-once。**强一致和高性能不可兼得**——大部分业务用最终一致换性能。
