# 一致性算法（Paxos / Raft / ZAB / Gossip）

> 分布式系统的"硬核压舱石"——P7+ 必考、阿里 P8 终面常问。
> 本篇要解决的问题：
> ① 为什么分布式必须有共识算法？**两将军问题** / **拜占庭问题** 是什么？
> ② **Paxos** 的 Prepare/Accept 两阶段为什么能达成一致？为什么这么难懂？
> ③ **Raft** 是怎么把 Paxos 简化的？Leader 选举、日志复制、安全性约束怎么工作？
> ④ **ZAB / Multi-Paxos / Raft / Gossip** 的差异和适用场景
> ⑤ **etcd / ZooKeeper / Nacos / TiDB** 各自用什么算法、为什么这么选
>
> 答题策略：**Paxos 讲核心思想 + 难懂原因，Raft 讲三件事（选举/复制/安全），ZAB 讲跟 Raft 的 5 处差异**。死磕公式没意义，工程师要懂"为什么这样设计"。

## 一、共识问题的根源

### 1.1 两将军问题（不可解的反例）

经典思想实验：

```
   [将军 A 山头]                [将军 B 山头]
        │                            │
        │ ────── 信使（可能死）─────▶ │
        │ ◀────── 信使确认 ────────── │
        
A 派信使说"明天 9 点进攻"
B 收到，回复"收到"
A 收到回复，但 B 不知道 A 是否收到回复
B 不放心，让信使再确认 A 收到回复
A 收到二次确认，但 B 还是不知道 A 是否收到二次确认
...
```

**结论**：在**信道不可靠**的前提下，**两个节点无法 100% 达成共识**——任何一方都不能确定对方是否同步。

> 这是数学结论，不是工程问题。共识问题的本质就是"在不可靠网络中如何达成一致"。

### 1.2 FLP 不可能定理

> Fischer-Lynch-Paterson 1985 年证明：**异步网络下，只要有一个节点可能崩溃，就不存在一个确定能达成共识的算法**。

意思是：在最严格的假设下（异步 + 容错），**完美的共识算法不存在**。
所以现实算法都做了**妥协**：要么放宽时间假设（部分同步），要么放宽容错假设。

### 1.3 拜占庭问题（更恶劣的场景）

不仅信道不可靠，**节点本身可能撒谎**（被攻击/Bug）。

- **非拜占庭容错（CFT）**：节点只会"宕机"不会"撒谎"——Paxos / Raft / ZAB
- **拜占庭容错（BFT）**：节点可能撒谎——PBFT / 区块链共识

**99% 互联网公司只需要 CFT**——你的服务器是自己的，不会撒谎。
**区块链需要 BFT**——节点是别人的，不能信。

### 1.4 共识算法要解决什么

**核心问题**：N 个节点对"某个值"达成一致：
1. **一致性**：所有节点最终选定同一个值
2. **可用性**：在多数节点存活时能继续工作
3. **持久性**：选定的值不会丢失

工程上落到三个具体场景：
- **选主**：N 个节点选出一个 Leader（注册中心、DB 主从）
- **状态机复制**：所有节点按相同顺序执行命令（DB、配置中心）
- **原子广播**：消息按相同顺序送达所有节点（消息队列）

## 二、Paxos（最经典，最难懂）

### 2.1 Paxos 的历史地位

- **Lamport 1990 年提出**，2001 年才被业界理解（论文叫 "Paxos Made Simple"，但还是没人看懂）
- Google Chubby、ZooKeeper（基于变种）、各种数据库都用它的思想
- 工程上几乎不用"原版 Paxos"——太难实现，多用 Multi-Paxos / Raft

### 2.2 角色

| 角色 | 职责 |
| --- | --- |
| **Proposer**（提议者） | 发起提案 |
| **Acceptor**（接受者） | 决定是否接受提案 |
| **Learner**（学习者） | 学习被选定的值 |

实际系统里一个节点同时担任多个角色。

### 2.3 两阶段流程

#### 阶段一：Prepare 阶段

```
Proposer ── Prepare(n) ──▶ Acceptors

每个 Acceptor 收到 Prepare(n)：
  if n > 已承诺的最大编号 N
    承诺不再接受 < n 的提案
    返回 Promise(已接受的最大编号 + value 或 null)
  else
    拒绝
```

#### 阶段二：Accept 阶段

```
Proposer 收到多数派 Promise 后：
  if 任何 Promise 包含 value（说明之前有 Acceptor 接受过）
    用编号最大的那个 value（不能改！）
  else
    用自己想提的 value V
  
Proposer ── Accept(n, V) ──▶ Acceptors

Acceptors 收到 Accept(n, V)：
  if n >= 已承诺的最大编号
    接受，记录 (n, V)
    返回 Accepted
  else
    拒绝

Proposer 收到多数派 Accepted → V 被选定
```

### 2.4 ASCII 流程图

```
P                A1            A2            A3
│  Prepare(5)    │             │             │
├───────────────▶│             │             │
├───────────────────────────▶  │             │
├───────────────────────────────────────────▶│
│  Promise(null) │             │             │
│◀───────────────┤             │             │
│  Promise(null) │◀────────────┤             │
│  Promise(3,X)  │◀────────────┴─────────────┤   ← A3 之前接受过(3,X)
│
│  Accept(5, X)  │             │             │   ← Proposer 必须用 X 不能用自己想要的 V
├───────────────▶├────────────▶├────────────▶│
│  Accepted      │             │             │
│◀───────────────┴─────────────┴─────────────┤
│
│  →  X 被选定（多数派接受）
```

### 2.5 Paxos 为什么这么难懂

三个原因：
1. **概念抽象**：Proposer/Acceptor/Learner 名字反人类直觉
2. **两阶段非显然**：第一阶段为什么要"承诺"、第二阶段为什么要带回前面的 value，需要严格证明才知道是必要的
3. **缺少工程指引**：原论文不讲"怎么选 Leader、怎么处理日志、怎么做成员变更"

工程上几乎都用 **Multi-Paxos**（一次选 Leader，连续提案）或 Raft（更易懂的等价物）。

### 2.6 Multi-Paxos

原版 Paxos 一次只决定一个值——做 KV 存储要重复跑 N 轮 Paxos，每轮都要选 Leader。
Multi-Paxos：**第一次跑 Paxos 选出 Leader**，后续提案 Leader 直接用 Accept 阶段（跳过 Prepare）。

→ Google Chubby、Apache BookKeeper 都用 Multi-Paxos。

## 三、Raft（Paxos 的工程化简化版）

### 3.1 设计目标

> Stanford 2014 年提出，目标就一个：**可理解性（Understandability）**。
> 把共识问题拆成三个独立子问题，每个都简单：① Leader 选举；② 日志复制；③ 安全性约束。

### 3.2 三个角色 + 任期

```
┌──────────┐    超时       ┌──────────┐
│ Follower │ ────────────▶ │ Candidate│
└──────────┘               └────┬─────┘
     ▲                          │ 拿到多数票
     │                          ▼
     │                     ┌──────────┐
     └─────发现新 Leader───┤  Leader  │
                           └──────────┘
```

**任期（Term）**：每次选举 Term+1，是个全局逻辑时钟。

| 角色 | 行为 |
| --- | --- |
| **Follower** | 被动接收 Leader 心跳和日志 |
| **Candidate** | Follower 超时后变成 Candidate，发起选举 |
| **Leader** | 处理所有客户端请求，向 Follower 复制日志 |

**关键约束**：同一 Term 最多一个 Leader（多数派投票保证）。

### 3.3 Leader 选举

```
1. Follower 启动随机超时计时器（150~300ms）
2. 超时未收到心跳 → 自己变成 Candidate
3. Candidate：
   - currentTerm++
   - 给自己投一票
   - 向其他节点发 RequestVote(term, lastLogIndex, lastLogTerm)
4. 其他节点投票规则：
   - 当前 Term <= 请求 Term：投赞成
   - Candidate 日志至少跟自己一样新：投赞成
   - 一个 Term 内只能投一票
5. Candidate 拿到多数派投票 → 变成 Leader → 立即广播心跳
6. 没拿到 / 收到更新的心跳 → 变回 Follower
```

**为什么超时随机化（150~300ms）**：
- 避免多个节点同时变 Candidate 互相分票（split vote）
- 谁先超时谁先发起选举，大概率独占多数派

### 3.4 日志复制

```
Client                    Leader                     Follower
  │                         │                            │
  │ ── 写命令 ────────────▶ │                            │
  │                         │ 1. append 到本地日志（未提交）
  │                         │ 2. AppendEntries RPC      
  │                         ├──────────────────────────▶│
  │                         │                            │ 3. append 本地（未提交）
  │                         │                            │    回 success
  │                         │◀───────────────────────────┤
  │                         │ 4. 多数派 success → commit
  │                         │ 5. 应用到状态机
  │ ◀── 返回客户端 ─────────│
  │                         │ 6. 心跳告知 Follower commit
  │                         ├──────────────────────────▶│
  │                         │                            │ 7. 也 commit
```

**日志结构**：每条日志有 `(term, index, command)`。日志只能追加，不能修改。

### 3.5 安全性约束（Raft 最重要的部分）

防止"已 commit 的日志被覆盖"，三条铁律：

#### 选举限制

> Candidate 必须**日志至少跟多数派一样新**才能当 Leader。

判断"新"的规则：
- 比较 lastLogTerm：大的更新
- lastLogTerm 相同则比较 lastLogIndex：大的更新

→ 保证已 commit 的日志肯定在新 Leader 上。

#### 提交限制

> Leader **只能提交当前 Term 的日志**，不能直接提交前任 Term 的日志。

为什么？防止"幽灵复活"——前任 Leader 的日志可能在多数派但还没提交，新 Leader 不能直接 commit 它，必须用一条本任期的日志覆盖确认。

#### 日志匹配

> 如果两个节点的某条日志 (term, index) 相同，那么之前的所有日志都相同。

实现：AppendEntries 带上 `prevLogIndex/prevLogTerm`，Follower 必须先验证前一条匹配才能 append。

### 3.6 脑裂处理

```
[Leader A][F1][F2][F3][F4]   ← 5 节点集群

网络分区：
  少数派：[Leader A][F1]      （2 节点）
  多数派：[F2][F3][F4]         （3 节点）

少数派：A 还是 Leader，但客户端写请求收不到多数派 ACK → 不能 commit
多数派：F2 超时变 Candidate → 拿到 F3、F4 投票（自己 + 2 票 = 3 票，多数派）→ 变成 Leader（Term+1）

分区恢复：
  A 收到新 Leader 的心跳，发现 Term 比自己大 → 变 Follower
  A 上未提交的日志被覆盖（被新 Leader 的日志同步覆盖）
```

**关键**：Raft 通过"多数派"和"Term 比较"自动处理脑裂——少数派的 Leader 写不进去，多数派选出新 Leader。

### 3.7 为什么集群要奇数节点

| 集群规模 | 多数派 | 容忍故障 |
| --- | --- | --- |
| 3 | 2 | 1 |
| 4 | 3 | 1 |
| 5 | 3 | 2 |
| 6 | 4 | 2 |
| 7 | 4 | 3 |

3 节点和 4 节点容忍故障数相同，**多 1 个节点没收益反而增加通信开销** → 选 3。
5 节点比 6 节点容忍数相同，选 5。

> **生产推荐**：3 节点（开发/小集群）、5 节点（生产标准）、7 节点（极高可用）。

## 四、ZAB（ZooKeeper Atomic Broadcast）

### 4.1 跟 Raft 的差异

ZAB 是 ZooKeeper 自己设计的，跟 Raft 思想类似但有差异：

| 维度 | Raft | ZAB |
| --- | --- | --- |
| **设计目标** | 通用共识 | 专为原子广播 |
| **Leader 选举** | 比较 lastLogIndex | 比较 zxid（更精细） |
| **日志复制** | AppendEntries | Proposal + ACK + Commit |
| **任期编号** | term | epoch（高 32 位）+ counter（低 32 位）= zxid |
| **崩溃恢复** | Leader 强制覆盖 Follower | Leader 同步差异（丢/补） |
| **客户端读** | 默认从 Leader（强一致） | 可从 Follower 读（弱一致） |

### 4.2 ZAB 两个核心模式

#### 崩溃恢复模式

```
Leader 挂掉
  ↓
所有节点变 LOOKING（找新 Leader）
  ↓
广播投票（比较 zxid，大的胜）
  ↓
选出新 Leader
  ↓
Leader 同步数据：把自己有的、Follower 没的发过去
  ↓
进入广播模式
```

#### 广播模式（正常工作）

```
Leader 收到写请求
  ↓
Propose（zxid + 数据）→ 所有 Follower
  ↓
Follower ACK
  ↓
Leader 收到多数 ACK → Commit
  ↓
广播 Commit → Follower 应用
```

### 4.3 zxid（ZAB 的关键）

```
zxid = (epoch << 32) | counter

epoch  : 哪一任 Leader（每次选举 +1）
counter: 该 Leader 任内的第几条日志
```

**例子**：
- `zxid = 0x100000001` → 第 1 任 Leader 的第 1 条日志
- `zxid = 0x100000002` → 第 1 任 Leader 的第 2 条日志
- `zxid = 0x200000001` → 第 2 任 Leader 的第 1 条日志（counter 重置）

选举时比较 zxid 而不是简单的日志长度——更精确，能区分"前任的进度"和"本任进度"。

## 五、Gossip 协议（最终一致，不是强一致）

### 5.1 核心思想

不像 Paxos/Raft 那样追求强一致——**节点之间随机传播信息**，最终所有节点收敛到一致状态：

```
1. 节点 A 收到新信息
2. A 随机选 N 个节点 → 把信息推过去
3. 这 N 个节点继续随机选 N 个推过去
4. 类似病毒传播，O(log N) 跳后所有节点都知道
```

### 5.2 Gossip vs Raft 对比

| 维度 | Raft | Gossip |
| --- | --- | --- |
| 一致性 | **强一致**（线性一致） | **最终一致** |
| 性能 | 写延迟高（多数派确认） | 写延迟低（本地写完就完） |
| 可扩展 | 几十节点（多数派开销大） | **数千节点**（O(log N) 收敛） |
| 容错 | 多数派存活 | 单点存活就行 |
| 适用 | 元数据、配置、Leader 选举 | 大规模集群成员管理 |

### 5.3 应用场景

- **Redis Cluster**：节点状态（slot 分布、节点上下线）用 Gossip
- **Cassandra**：节点发现、数据修复
- **Consul**：成员管理（Serf 协议）
- **Nacos**：Distro 协议有 Gossip 思想

> **注意**：Gossip **不能用来做强一致需求**（比如分布式锁、事务）——只适合"最终一致就够"的场景。

## 六、四大算法横向对比

| 维度 | **Paxos** | **Raft** | **ZAB** | **Gossip** |
| --- | --- | --- | --- | --- |
| **一致性** | 强一致 | 强一致 | 强一致 | 最终一致 |
| **角色** | Proposer/Acceptor/Learner | Leader/Follower/Candidate | Leader/Follower | 平等节点 |
| **Leader** | Multi-Paxos 才有 | 必有 | 必有 | 无 |
| **可理解性** | **极难** | **易** | 中 | 易 |
| **可扩展** | 中 | 中 | 中 | **极强**（千节点） |
| **典型实现** | Chubby、Spanner | etcd、TiKV、CockroachDB | ZooKeeper | Redis Cluster、Cassandra |
| **适用场景** | 数据库副本 | 元数据、配置 | 协调服务 | 大规模成员管理 |

## 七、各组件用什么算法

| 组件 | 共识算法 | 用在哪 |
| --- | --- | --- |
| **ZooKeeper** | ZAB | 整体一致性 |
| **etcd** | Raft | 整体一致性 |
| **Consul** | Raft + Gossip | Raft 用于 KV 一致性、Gossip 用于成员管理 |
| **Nacos** | Raft + Distro（自研） | 配置走 Raft、注册走 Distro |
| **Kafka** | KRaft（3.0+） / ZK（旧） | 控制器选举、元数据 |
| **TiDB / TiKV** | Multi-Raft（每个 Region 一组 Raft） | 数据分片副本 |
| **CockroachDB** | Raft | 数据副本 |
| **Spanner** | Multi-Paxos + TrueTime | 全球分布式数据库 |
| **Redis Cluster** | Gossip | 集群拓扑、节点状态 |
| **Cassandra** | Gossip + Quorum | 节点发现、读写一致性 |
| **HBase** | 借助 ZK | Master 选举 |
| **Hadoop HDFS** | 借助 ZK | NameNode 高可用 |

### 7.1 为什么 Kafka 从 ZK 迁到 KRaft

历史：Kafka 之前用 ZK 存元数据（Topic 配置、Broker 列表、ISR 等），但有问题：
- 多一个外部依赖（运维复杂）
- ZK 写性能瓶颈，元数据规模大时 Topic 创建很慢
- Controller 选举依赖 ZK，复杂

KRaft（Kafka 3.0+）：内置 Raft，去掉 ZK 依赖。**部署简化、性能提升、元数据扩展性更好**。

## 八、生产踩过的坑

### 坑 1：奇数节点配置错误

> 公司上线时配 Raft 集群 4 个节点，运维以为"越多越可靠"。
> 实际：4 节点跟 3 节点容错数相同（都是 1）→ **多了一个节点开销，没多容错**。
> **修复**：缩减到 3 节点，或扩到 5 节点。

### 坑 2：选举超时设得太短

> Raft 默认 150-300ms，运维想"更快感知"调成 50-100ms。
> 网络抖动时 Follower 频繁误判 Leader 死亡 → 频繁选举 → 集群震荡。
> **修复**：选举超时至少要比心跳间隔大 5-10 倍，比 RTT 大 100 倍。生产推荐 **500ms-1s**。

### 坑 3：日志压缩没做

> Raft 日志一直追加，几个月后磁盘占满。
> **修复**：定期 snapshot（如 etcd 默认每 10000 条 + 每小时）。

### 坑 4：成员变更两步走未做

> 一次性把 3 节点改成 5 节点，期间出现两个多数派（旧的 [A,B,C] 多数派 = 2，新的 [A,B,C,D,E] 多数派 = 3，A,B 在旧多数派但 D,E 在新多数派）。
> **修复**：用**联合共识（Joint Consensus）**——先到两套都成立的中间态，再切换。Raft 论文有详细方案。

### 坑 5：Gossip 网络风暴

> Redis Cluster 1000 节点 Gossip 互相 ping → 网络带宽打满。
> **修复**：减少节点数（Cluster 不要超过 1000 节点）；调 `cluster-node-timeout` 减少 Gossip 频率。

### 坑 6：ZK 选举依赖 myid

> ZK 集群初始化时 myid 文件配错（重复或缺失）→ 集群起不来或选不出 Leader。
> **修复**：myid 严格 1 到 N，不重复；用 Ansible/Helm 自动化避免人为错。

### 坑 7：跨数据中心 Raft 写延迟

> 跨城（北京-上海）部署 Raft，写延迟从 1ms 飙到 30ms（多数派要跨城 ACK）。
> **修复**：① 不要跨城跑同一组 Raft；② 跨城用最终一致方案；③ Spanner 用 TrueTime + Multi-Paxos 优化。

## 九、面试高频追问

### Q1：Paxos 和 Raft 有什么区别？

| 维度 | Paxos | Raft |
| --- | --- | --- |
| 设计目标 | 通用 | **可理解性** |
| Leader | Multi-Paxos 才有 | 必有 |
| 复杂度 | **极高** | 中 |
| 工程实现 | 极少 | 大量（etcd/TiKV/...） |
| 是否等价 | **是**（数学上等价） | |

工程上几乎都用 Raft 或 Multi-Paxos——纯 Paxos 几乎不用。

### Q2：Raft 能保证强一致性吗？

**能**，但**默认从 Leader 读才行**。
- **写**：必须 Leader 接受 + 多数派 ACK，才回客户端 → 写线性一致
- **读 Leader**：能保证读到最新已提交日志 → 强一致
- **读 Follower**：可能读到旧数据（Follower 还没收到 Leader 的 Commit 通知）→ 不一致

要 Follower 也强一致：用 **ReadIndex** 机制（Follower 先问 Leader "你 commit 到哪了"，等本地追到那个位置再读）。

### Q3：Raft 选举为什么要随机超时？

避免 split vote（多个 Follower 同时变 Candidate 互相分票，没人拿到多数）。
随机化让"谁先超时"是个概率事件 → 大概率独占选举。

### Q4：Raft 5 节点能容忍几个故障？

**2 个**。多数派 = 3，5-3=2。
公式：N 节点容忍 floor((N-1)/2) 故障。

### Q5：网络分区时 Raft 会怎样？

少数派的 Leader：写不进去（拿不到多数 ACK）→ 客户端报错。
多数派：选出新 Leader 继续工作。
分区恢复：旧 Leader 的 Term 比新 Leader 小 → 自动降为 Follower，未提交日志被覆盖。

### Q6：ZAB 和 Raft 哪个好？

工程上差不多——
- ZK 选 ZAB 是历史原因（早于 Raft）
- 新项目（etcd、TiKV）选 Raft 是因为**可理解性更好、社区资源多、实现库成熟（如 etcd-raft）**
- ZAB 在崩溃恢复阶段处理得更精细（同步差异比 Raft 强行覆盖更优雅）

### Q7：为什么 Redis Cluster 用 Gossip 而不是 Raft？

- Cluster 主要管"节点状态、slot 分布"——不需要严格全局一致
- Gossip 可扩展到上百节点（Raft 几十节点就到顶）
- 故障感知容忍秒级延迟（金融才需要毫秒级）

→ 适合 Gossip 的就是这种"规模大 + 一致性要求弱"场景。

### Q8：Multi-Paxos 是怎么减少 RTT 的？

原版 Paxos 每个值都跑两阶段（Prepare + Accept）= 2 RTT。
Multi-Paxos：Leader 一旦选出，**后续值跳过 Prepare 直接 Accept** = 1 RTT。
本质是把"承诺不接受小编号"的承诺**永久化给 Leader**。

### Q9：拜占庭容错（BFT）跟 Raft 有什么区别？

| | Raft（CFT） | PBFT / 区块链共识（BFT） |
| --- | --- | --- |
| 节点会撒谎 | ❌ | ✅ |
| 容忍数 | (N-1)/2 | (N-1)/3 |
| 性能 | 高 | 低（消息复杂度 O(N²)） |
| 适用 | 内部系统 | 区块链、金融跨机构 |

Raft 假设节点崩溃但不会撒谎——所以更高效。区块链不能这么假设。

### Q10：怎么实现一个简版 Raft？

```
1. 三个状态机：Follower / Candidate / Leader
2. 心跳定时器（Leader 每 50-100ms 一次）
3. 选举定时器（Follower 150-300ms 随机）
4. RPC：RequestVote、AppendEntries
5. 日志结构：(term, index, command)
6. 持久化：currentTerm、votedFor、log[]
7. 状态机应用：commitIndex 推进时，apply 日志到业务
```

参考实现：etcd-raft（Go）、SOFAJRaft（Java）、Hashicorp Raft（Go）。

## 十、答题模板（60 秒话术）

> 共识算法解决分布式系统的核心问题——**N 个节点对一个值达成一致**。FLP 不可能定理告诉我们异步网络下完美算法不存在，所有实际算法都做了妥协。
>
> **Paxos** 是 Lamport 的经典方案，**Prepare + Accept 两阶段**保证多数派承诺，但**极难理解**——工程上几乎都用 **Multi-Paxos**（一次选 Leader 后续直接 Accept）。
>
> **Raft** 是 Stanford 2014 的工程化简化版，目标是**可理解性**，把共识拆成三个独立子问题：① **Leader 选举**（随机超时 + 多数票，Term 比较）；② **日志复制**（AppendEntries + 多数派 ACK 后 commit）；③ **安全性**（选举限制、提交限制、日志匹配三条铁律）。**etcd / TiKV / CockroachDB** 都用 Raft。
>
> **ZAB** 是 ZooKeeper 的算法，跟 Raft 类似但用 **zxid（epoch + counter）**做更精细的 Leader 选举。
>
> **Gossip** 是最终一致协议——节点随机传播状态，O(log N) 收敛，可扩展到**千节点**。Redis Cluster、Cassandra 用它管节点状态。
>
> **生产坑**：① 集群必须**奇数节点**（4 节点不如 3 节点）；② 选举超时要够长（500ms+），避免抖动误判；③ 日志要定期 snapshot 防磁盘满；④ **不要跨城跑同一组 Raft**（多数派 RTT 太大）；⑤ Gossip 不能用于强一致场景。
>
> **关键认知**：CFT（Raft/Paxos）够互联网用，BFT（PBFT/区块链）才是节点会撒谎场景；强一致选 Raft，最终一致选 Gossip；Kafka 3.0+ 用 KRaft 替代 ZK 是大趋势。
