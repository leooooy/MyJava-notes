# 一致性哈希

> 一致性哈希是分布式系统的基本功——**Redis Cluster、Memcached、Dubbo、Nginx upstream、CDN**全用它。
>
> 面试要回答 5 件事：
> ① **为什么不用普通 hash + 取模**——节点变动时的雪崩
> ② **哈希环** + **顺时针找节点** 怎么工作
> ③ **虚拟节点** 解决什么问题、为什么是 150 个
> ④ **生产应用场景** —— 为什么 Redis Cluster 不用一致性哈希
> ⑤ **实现关键点** —— 用什么数据结构、用什么 hash 函数

---

## 一、为什么不用普通取模

### 1.1 朴素方案

```
key → hash(key) % N → 选择第 i 号节点
```

例：3 节点，hash("user_1") % 3 = 0 → 落到节点 0。

### 1.2 节点变动的灾难

3 节点 → **加 1 个新节点变 4**：

```
key="user_1" hash=12345
旧：12345 % 3 = 0
新：12345 % 4 = 1     ← 落到不同节点了

key="user_2" hash=67890
旧：67890 % 3 = 0
新：67890 % 4 = 2     ← 也变了
```

→ 几乎**所有 key 的归属节点都变了**——**缓存全部失效**，所有请求**穿透到 DB**，**雪崩**。

**生产场景**：

- 10 节点缩到 9 节点（一台挂了）：**90% key 重新分配**
- 10 节点扩到 11 节点：**91% key 重新分配**

→ 不能这么干。

### 1.3 一致性哈希的目标

**节点变动时，只让"少量" key 重新分配——平均 1/N**。

加 1 个节点：只动 **1/(N+1)** 的 key；删 1 个节点：只动该节点上的 key（约 1/N）。

## 二、一致性哈希 —— 哈希环

### 2.1 核心思想

```
1. 把 hash 空间想象成一个 0 ~ 2^32-1 的环
2. 节点 hash 后落到环上
3. key hash 后落到环上
4. key 顺时针找最近的节点
```

### 2.2 ASCII 图

```
            0/2^32
              ●  ← 节点 A (hash=2)
              │
   2^32 - 1   │
        ●     │
        │     │
      节点 D  │
      (hash) ─┼─── 节点 B (hash=2^31)
        │     │      ●
        │     │
        │     │
        │     │
        ●─────┴──── 节点 C (hash=2^30)
      节点 ?

key K1 hash 落在 节点 A 和 B 之间 → 顺时针找到 → 归 B
key K2 hash 落在 节点 B 和 C 之间 → 顺时针找到 → 归 C
key K3 hash 落在 节点 C 和 D 之间 → 顺时针找到 → 归 D
```

### 2.3 加节点

```
原来：A、B、C、D 在环上
新加：E

E 落在 B 和 C 之间 → 接管"原本归 C 的、现在 hash 落在 B 和 E 之间"的 key
其他节点的 key 不变
```

→ 只有 **E 接管的那段范围内的 key** 受影响——**约 1/N**。

### 2.4 删节点

```
删除 C
原本归 C 的 key → 全部顺时针移交给 D
其他节点不动
```

→ 影响范围 = C 节点上的所有 key。

---

## 三、问题：节点分布不均

### 3.1 现象

哈希环 0~2^32 是**均匀分布**的，但 N 个节点 hash 后**不一定均匀落环**：

```
2^32 - 1                                   0
   ●─────────────────────────────────────●
   │                                     │
   │         A    B  C                   │
   │       ●●●  ●●●●●●●●                 │
   │                                     │
   │                                     D
   │                                     ●
   │                                     │
   ●─────────────────────────────────────●
```

→ A、B、C 挤在一起、D 孤独——**A、B、C 各只接 5% key、D 接 85% key**。

### 3.2 雪上加霜：节点宕机

如果 D 挂了，**它接的 85% key 全部迁到下一个节点 A**——**A 瞬间承担 90% 流量**——**新雪崩**。

---

## 四、虚拟节点

### 4.1 思想

**每个物理节点对应多个虚拟节点**——把"一个大节点"拆成"多个小节点"，散布在环上：

```
物理节点 A → 虚拟节点 A#1, A#2, ..., A#150
物理节点 B → 虚拟节点 B#1, B#2, ..., B#150
...
```

每个虚拟节点 hash 算法不同（如 `hash("A#1")`、`hash("A#2")`）→ 散布均匀。

### 4.2 ASCII 图

```
环：
A#1, B#7, A#23, C#5, B#41, A#88, C#15, B#3, ...   ← 散布得很均匀
```

key 顺时针找虚拟节点 → 知道虚拟节点对应哪个物理节点 → 归到该物理节点。

### 4.3 为什么 150 个

经验值。Ketama（Memcached 的一致性哈希实现）默认每个物理节点 **160 个虚拟节点**——实测**分布偏差 < 5%**。

```
虚拟节点数 vs 分布偏差：
1   节点：偏差 ±50%（极不均）
10  节点：偏差 ±20%
100 节点：偏差 ±5%
150 节点：偏差 ±3%（实用最优）
1000 节点：偏差 ±1%（内存浪费）
```

### 4.4 节点宕机的影响

虚拟节点散布后，挂一个物理节点 → 它的 **150 个虚拟节点都从环上摘除** → 这些虚拟节点接的 key 分摊给**多个物理节点**——**每个其他节点只多接 1/N**。

→ 不再有"挂一个，下一个崩"的问题。

## 五、典型应用场景

### 5.1 Memcached（客户端分片）

Memcached 服务端**不实现集群**，靠客户端做分片。

经典方案：**Ketama 一致性哈希**。

```java
// XMemcached / Spymemcached
MemcachedClient client = new MemcachedClient(
    new ConnectionFactoryBuilder()
        .setLocator(new KetamaConnectionLocator())
        .build(), addrs);
```

虚拟节点 160 个 / 物理节点。

### 5.2 Dubbo

```java
@Reference(loadbalance = "consistenthash")
private UserService userService;
```

Dubbo 的 `ConsistentHashLoadBalance`：

- 默认 160 个虚拟节点
- 用 MD5 哈希
- 选请求参数的 hash 作为 key

适用：**相同参数的请求路由到同一个 provider**——比如带本地缓存的服务。

### 5.3 Nginx upstream

```nginx
upstream backend {
    hash $remote_addr consistent;       # ← consistent 关键字
    server srv1:80;
    server srv2:80;
}
```

按客户端 IP 一致性哈希——同一个 IP 的请求路由到同一台后端，session 保持。

### 5.4 Redis Cluster —— **不用**一致性哈希

Redis Cluster 用的是 **slot 槽位** 方案：

```
固定 16384 个 slot
每个 key → CRC16(key) % 16384 → 确定 slot
slot 分配给某个节点
```

**为什么不用一致性哈希**：

- 一致性哈希是**客户端方案**，节点变动靠客户端感知
- Redis Cluster 要做**服务端动态迁移**——slot 是更可控的逻辑分片
- slot 迁移粒度可控（按 slot 而不是按 hash 范围）

→ 一致性哈希更适合**纯客户端分片**，slot 更适合**服务端协调**。

### 5.5 CDN

按 URL 一致性哈希到边缘节点——**同一个资源永远落到同一节点**，**最大化缓存命中率**。

### 5.6 分布式锁、分布式 ID

也常用一致性哈希分配处理节点（不是必须，但能减少节点变动的影响）。

## 六、实现关键点

### 6.1 数据结构：TreeMap（有序）

```java
public class ConsistentHash<T> {
    private final int virtualNodes;
    private final Function<Object, Long> hashFunction;
    private final SortedMap<Long, T> ring = new TreeMap<>();

    public ConsistentHash(int virtualNodes, Collection<T> nodes) {
        this.virtualNodes = virtualNodes;
        this.hashFunction = key -> {
            // MD5 或 MurmurHash
            byte[] bytes = MessageDigest.getInstance("MD5").digest(key.toString().getBytes());
            return ((long)(bytes[3] & 0xFF) << 24) | ((long)(bytes[2] & 0xFF) << 16)
                 | ((long)(bytes[1] & 0xFF) << 8)  | ((long)(bytes[0] & 0xFF));
        };
        for (T node : nodes) addNode(node);
    }

    public void addNode(T node) {
        for (int i = 0; i < virtualNodes; i++) {
            ring.put(hashFunction.apply(node + "#" + i), node);
        }
    }

    public void removeNode(T node) {
        for (int i = 0; i < virtualNodes; i++) {
            ring.remove(hashFunction.apply(node + "#" + i));
        }
    }

    public T getNode(Object key) {
        if (ring.isEmpty()) return null;
        long hash = hashFunction.apply(key);
        SortedMap<Long, T> tail = ring.tailMap(hash);     // 顺时针找
        return tail.isEmpty() ? ring.get(ring.firstKey()) : tail.get(tail.firstKey());
    }
}
```

**为什么用 TreeMap**：

- `tailMap(hash)` **O(log n)** 找下一个虚拟节点
- 红黑树天然有序

### 6.2 hash 函数选择

| hash 函数 | 速度 | 分布 | 推荐 |
| --- | --- | --- | --- |
| **MD5** | 慢（约 10x slower） | 均匀 | 历史标准（Ketama）|
| **MurmurHash** | **快** | 均匀 | **推荐**（Cassandra / Kafka 用）|
| **CityHash / xxHash** | 极快 | 均匀 | 新一代 |
| `String.hashCode()` | 快 | **不均** | ❌ 不推荐 |

### 6.3 String.hashCode() 不行

```java
"node1".hashCode();   // 一个 int，分布不均匀
"node2".hashCode();
```

**实测**：连续 10 个 nodeN 的 hashCode 在某段集中——分布偏差 50%+。**生产用 MurmurHash 或 MD5**。

## 七、生产踩坑

### 7.1 虚拟节点数过少

**现象**：节点分布不均，某节点接 60% 流量。
**根因**：虚拟节点数 = 1 或 几十——分布偏差大。
**修复**：每节点 **150 ~ 200** 个虚拟节点。

### 7.2 用 String.hashCode() 做哈希

**现象**：节点分布很差。
**根因**：JDK String.hashCode 算法对节点名（短字符串）分布不均。
**修复**：改 MD5 或 MurmurHash。

### 7.3 节点变动后客户端没及时刷新

**现象**：节点宕机后，**部分客户端**仍把 key 路由到挂掉的节点 → 大量超时。
**根因**：客户端缓存了旧的节点列表。
**修复**：注册中心（Nacos / ZooKeeper）推送节点变化 → 客户端实时更新本地 ring。

### 7.4 一致性哈希用 List 实现 O(n)

**现象**：节点找路由 CPU 高。
**根因**：用 List 顺序找，O(n)；应该用 TreeMap O(log n)。
**修复**：改 TreeMap.tailMap。

### 7.5 节点权重不一样不能简单一致性哈希

**现象**：硬件配置不同的节点（旧机器 vs 新机器）流量平均分配——旧机器扛不住。
**修复**：**按权重设虚拟节点数**——大机器 200 个、小机器 100 个。

## 八、答题模板（60 秒话术）

> **普通 hash 取模 `hash % N`** 在节点变动时**几乎所有 key 都要重新分配** → 缓存雪崩。一致性哈希解决这个：
>
> 把 hash 空间做成 0 ~ 2^32 的**环**，节点和 key 都 hash 到环上，**key 顺时针找最近节点**。加 / 删一个节点只影响**该节点相邻的一段 key**——**1/N 量级**。
>
> 节点直接落环会**分布不均**——给每个物理节点配 **150~200 个虚拟节点**散布到环上，分布偏差降到 5% 以内。挂一个节点，它的虚拟节点的负载分摊给**所有其他节点**，避免连锁崩溃。
>
> **数据结构**：用 TreeMap，`tailMap(hash)` 顺时针找 O(log n)。**hash 函数**用 **MurmurHash 或 MD5**——`String.hashCode` 分布太差。
>
> **生产应用**：Memcached 客户端分片、Dubbo 一致性哈希负载均衡、Nginx upstream consistent、CDN 路由。
>
> **Redis Cluster 不用一致性哈希**——它用 **16384 个 slot** 的固定槽位方案，更适合**服务端动态迁移**和**精确分片控制**。一致性哈希更适合**客户端分片**场景。
