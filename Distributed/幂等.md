# 幂等（Idempotency）

> 分布式系统第一性问题之一——**任何会被重试的接口都必须幂等**。
> 本篇要解决的问题：
> ① 幂等到底要解决什么？什么场景**不需要**幂等？
> ② 6 种主流方案的取舍：唯一键 / 乐观锁 / 状态机 / Token / 分布式锁 / 全局请求 ID
> ③ Token 方案的原子性陷阱：先查再删 vs Lua 脚本
> ④ 跟事务、消息消费、接口防重的边界
>
> 跟 [分布式事务](./分布式事务.md) 是配套的——事务保证"做"，幂等保证"重复做不出错"。

---

## 一、为什么需要幂等

### 1.1 一句话定义

**同一操作，无论执行 1 次还是 N 次，结果一致**（DB 状态、外部副作用都一致）。

数学上：`f(x) = f(f(x)) = f(f(f(x)))`。

### 1.2 三大触发场景

```
场景 1：用户重复提交
  下单按钮连点 3 次 → 3 笔订单 → 用户骂街

场景 2：MQ 重复消费
  RocketMQ 至少一次（at-least-once）语义 → 消费者必须幂等
  Kafka 同理（commit offset 失败会重投）

场景 3：RPC / HTTP 超时重试
  调用方 5s 超时 → 实际服务端已执行 → 调用方重试 → 执行两遍
  下游 Feign / Dubbo / 网关 都有重试机制
```

### 1.3 哪些操作天然幂等

| 操作 | 幂等？ | 说明 |
| --- | --- | --- |
| `SELECT` 查询 | ✅ | 读不改变状态 |
| `DELETE WHERE id=1` | ✅ | 第二次删什么也不变 |
| `UPDATE x SET status='paid' WHERE id=1` | ✅ | 状态机幂等（值已经是目标态） |
| `UPDATE x SET count=count+1 WHERE id=1` | ❌ | 累加，每次结果不同 |
| `INSERT INTO log VALUES(...)` | ❌ | 每次产生新行 |
| 调用支付网关扣款 | ❌ | 必须靠 idempotency_key 兜底 |

**RESTful 语义**：GET/PUT/DELETE 天然幂等，POST 不幂等（需要业务侧设计）。

## 二、设计原则：必须先想清楚的 3 件事

### 2.1 选幂等键（Idempotency Key）

幂等的核心是**找到一个能唯一识别"这次操作"的键**。常见来源：

| 来源 | 适用场景 | 例子 |
| --- | --- | --- |
| 业务唯一字段 | 业务有自然唯一键 | 订单号、支付流水号、身份证号 |
| 调用方生成的 token | 通用接口防重 | 客户端 UUID + 时间戳 |
| 服务端预发的 token | 强幂等场景 | 表单提交前先 GET 一个 token |
| MQ 消息 ID | 消费幂等 | RocketMQ 的 msgId / 业务 messageKey |
| 全局请求 ID | 网关层兜底 | TraceId / RequestId |

> **错误示范**：拿"用户 ID + 商品 ID"当幂等键 → 同一用户买同一商品两次都被吃掉。

### 2.2 幂等的"窗口"必须明确

幂等不是永久的，要给一个**TTL**：

- 表单防重：5~30 分钟
- 支付订单号：永久（DB 唯一索引）
- MQ 消费幂等：3~7 天（覆盖最长重试窗口）

### 2.3 幂等的"颗粒度"必须明确

接口级 ≠ 业务级。比如下单接口幂等了，但库存扣减接口没幂等 → 整体仍然会超扣。
**幂等要在每一段会被重试的边界上都做**。

## 三、六种主流方案

### 3.1 数据库唯一键（最朴素，最可靠）

```sql
-- 订单表：业务流水号唯一
CREATE TABLE `order` (
  id BIGINT PRIMARY KEY,
  biz_no VARCHAR(64) NOT NULL,
  amount DECIMAL(10,2),
  ...
  UNIQUE KEY uk_biz_no (biz_no)
);

-- 插入时让 DB 兜底
INSERT INTO `order`(biz_no, amount) VALUES('ORD20260509001', 99.00);
-- 第二次重复插入 → DuplicateKeyException → 业务层捕获并返回成功
```

**Java 写法**：

```java
try {
    orderMapper.insert(order);
} catch (DuplicateKeyException e) {
    // 已存在，视为成功（注意要保证幂等响应也一致）
    Order existing = orderMapper.selectByBizNo(order.getBizNo());
    return convertToResponse(existing);
}
```

**优点**：✅ 最可靠（DB 是最后的真理），✅ 实现简单
**缺点**：❌ 抛异常有性能开销（高并发下不优雅），❌ 仅适合"创建"类操作

> **生产建议**：所有创建类接口都用唯一键兜底，哪怕业务层已经做了别的幂等。

### 3.2 乐观锁（version 号）

适用于**更新**类操作。每行加一个 `version` 字段：

```sql
UPDATE account SET balance = balance - 100, version = version + 1
WHERE id = 1 AND version = 5;
-- 影响行数 = 0 → 已被别人更新 → 拒绝重试
```

**何时用**：
- 状态变更幂等（如订单状态机）
- 余额扣减、库存扣减
- 跟 TCC 的 Confirm/Cancel 配合

**坑**：高并发下 ABA 问题（先 5→6→5，version 看不出来），但 99% 场景不需要管。

### 3.3 状态机（业务幂等的最优雅写法）

最适合"状态流转"类业务：订单、支付、审批。

```
订单状态机：待支付 → 已支付 → 已发货 → 已完成 → 已退款
                  ↓
              已取消（终态）
```

```sql
-- 支付回调：只有"待支付"才能改成"已支付"
UPDATE `order` SET status = 'PAID', pay_time = NOW()
WHERE id = 123 AND status = 'UNPAID';
-- 影响行数 = 0 → 状态已是 PAID（重复回调）→ 直接返回成功
```

**优点**：
- 不用额外存储 idempotency_key
- 业务自带语义，可读性强
- 跟乐观锁是同一类思路（status 当作版本）

**缺点**：仅适用于状态流转类业务，对"插入"无效。

### 3.4 Token 机制（强幂等通用方案）

最通用、面试最高频。流程：

```
[客户端]                       [服务端]                    [Redis]
   │                              │                          │
   │ ① GET /api/token             │                          │
   │ ─────────────────────────► │                          │
   │                              │ SET token:UUID = "1"     │
   │                              │ ──────────────────────► │
   │                              │     EX 1800 NX           │
   │ ◄───────────────────────── │                          │
   │   {token: "abc123"}          │                          │
   │                              │                          │
   │ ② POST /api/order            │                          │
   │   header: X-Token: abc123    │                          │
   │ ─────────────────────────► │                          │
   │                              │ ③ Lua: GET + DEL atomic   │
   │                              │ ──────────────────────► │
   │                              │ ◄────────────────────── │
   │                              │    1 → 业务执行           │
   │                              │    nil → 重复提交，拒绝    │
```

**核心 Lua 脚本（必须用 Lua 保证原子性）**：

```lua
-- KEYS[1] = token key
-- 返回 1 表示成功获取并删除，0 表示 token 不存在（重复提交）
if redis.call('GET', KEYS[1]) then
    redis.call('DEL', KEYS[1])
    return 1
else
    return 0
end
```

**Java 调用**：

```java
String script = "if redis.call('GET', KEYS[1]) then " +
                "  redis.call('DEL', KEYS[1]); return 1 " +
                "else return 0 end";
Long result = redisTemplate.execute(
    new DefaultRedisScript<>(script, Long.class),
    Collections.singletonList("token:" + token));
if (result == null || result == 0L) {
    throw new BizException("请勿重复提交");
}
// 执行业务...
```

**为什么必须用 Lua**：

```java
// ❌ 错误写法：先 GET 再 DEL，非原子
String value = redis.get(token);
if (value == null) throw new RepeatException();
redis.del(token);  // 这两步之间，另一个请求也通过了 GET
// → 两个请求都执行业务 → 幂等失效

// ✅ 用 Lua 把 GET + DEL 合并成原子操作
```

**适用场景**：
- 表单防重提交（订单/付款/评论）
- 一次性操作（领券、签到、抽奖）

**TTL 怎么定**：
- 表单类：30 分钟（够用户填表）
- 强一次性操作：5 分钟（防止 token 被截获重放）

### 3.5 分布式锁

把"操作"作为加锁单位：

```java
String lockKey = "lock:order:" + bizNo;
RLock lock = redisson.getLock(lockKey);
if (lock.tryLock(0, 30, TimeUnit.SECONDS)) {
    try {
        // 检查业务是否已执行（幂等核心）
        if (orderMapper.existsByBizNo(bizNo)) {
            return "已处理过";
        }
        // 执行业务
        doBusiness();
    } finally {
        lock.unlock();
    }
}
```

**注意**：分布式锁本身**不直接做幂等**，它只能"串行化"，配合状态判断才幂等。
真正的幂等还是靠"加锁后查 DB 看是否已执行"。

**何时用**：
- 业务无法用唯一键 / 状态机时的兜底
- 需要把多个动作串成一个"原子段"（事务边界）

→ 详见 [分布式锁](./分布式锁.md)

### 3.6 全局请求 ID + 去重表（消费幂等首选）

MQ 消费场景的标准方案：

```sql
CREATE TABLE `idempotent_record` (
    biz_id VARCHAR(64) PRIMARY KEY,  -- MQ msgId 或业务 ID
    biz_type VARCHAR(32),
    create_time DATETIME,
    INDEX idx_create_time (create_time)
);
```

```java
@Transactional
public void handleMessage(Message msg) {
    String bizId = msg.getKeys();  // RocketMQ 业务唯一键
    try {
        // 先插入去重表（DB 主键约束兜底）
        idempotentRecordMapper.insert(new IdempotentRecord(bizId, "ORDER_PAID"));
    } catch (DuplicateKeyException e) {
        log.info("消息已消费过, bizId={}", bizId);
        return;  // 幂等返回
    }
    // 在同一事务里执行业务
    doBusiness(msg);
}
```

**关键点**：**插入去重表 + 业务操作必须在同一个事务里**——否则插入成功但业务回滚，下次消息重投会被错误丢弃。

**TTL 处理**：
- 去重表会越来越大，按 7 天定期清理（覆盖最长重投窗口）
- 历史数据归档到冷存

## 四、方案对比与选型

| 方案 | 适用场景 | 性能 | 复杂度 | 业务侵入 |
| --- | --- | --- | --- | --- |
| **DB 唯一键** | 创建类（订单/支付/注册） | 中 | 低 | 低 |
| **乐观锁 version** | 更新类（余额/库存） | 高 | 低 | 低 |
| **状态机** | 状态流转（订单/审批） | 高 | 低 | 无 |
| **Token + Lua** | 表单防重、一次性操作 | 高 | 中 | 中 |
| **分布式锁** | 复杂边界、原子段 | 中 | 中 | 中 |
| **去重表** | MQ 消费、外部回调 | 中 | 低 | 低 |

### 4.1 决策树

```
是创建类（INSERT）？
  → 业务有唯一键？  → DB 唯一键（首选）
  → 没有唯一键？    → 全局请求 ID + 去重表

是更新类（UPDATE）？
  → 是状态流转？    → 状态机（status 当版本）
  → 是数值修改？    → 乐观锁 version

是表单防重？
  → 用户操作？      → Token + Lua（标准方案）
  → 一次性操作？    → Token + Lua（缩短 TTL）

是 MQ 消费？        → 去重表（落 DB） + 业务唯一键

跨服务调用？
  → 调用方传 idempotency_key（参考 Stripe API），服务端用 token / 去重表保存
```

### 4.2 多层组合（生产推荐）

**真实生产是组合拳**，不是单选：

```
[网关层]      限流 + 全局请求 ID
    ↓
[业务层]      Token 防表单重复
    ↓
[业务逻辑]    状态机判断
    ↓
[DB 兜底]     唯一键约束
```

举例：支付接口
1. **网关**：拦截 1s 内同 IP 同接口超过 N 次（限流，不算幂等）
2. **入口**：检查 idempotency_key（客户端传）→ Redis Token 拦截重复
3. **业务**：状态机（已支付的订单不再扣款）
4. **DB**：支付流水号唯一索引兜底

## 五、Token 机制深挖（高频追问区）

### 5.1 为什么不能直接 SETNX？

```java
// ❌ 不行：客户端没有这个 token，怎么发起请求？
boolean ok = redis.setnx("token:" + uuid, "1");
```

SETNX 是**服务端来生成 token 防重**——但 token 怎么传给客户端？必须先 GET 拿到。

### 5.2 拿 token 的接口怎么防刷？

`GET /api/token` 本身可能被刷爆 → 配合：
- 用户级限流：每个用户 1 分钟最多 N 个 token
- 客户端签名：只有合法签名才发 token
- **简化方案**：客户端自己生成 UUID 当 token，服务端不预存（牺牲一点严格性，但简单）

### 5.3 Token 删除时机

```
方案 A：业务执行前删除（GET + DEL atomic）
  → 业务失败，token 已删 → 客户端重试拿不回 token，必须重新发起
  → 风险：业务失败后无法重试

方案 B：业务执行后删除
  → 业务执行中，重复请求看到 token 还在 → 全部通过
  → 风险：并发期间幂等失效
```

**生产推荐 A**——失败让客户端走重新发起流程，比重复执行风险小得多。

### 5.4 Token 是先存后用还是先用后删？

强一致 token 流程（推荐）：

```
1. SET token:UUID 1 NX EX 1800   ← 服务端生成
2. 返回 token 给客户端
3. 客户端带 token 发起请求
4. Lua: GET token + DEL atomic    ← 验证 + 消费
5. 业务执行
6. 失败：客户端重新走 1
```

## 六、生产踩过的坑

### 坑 1：幂等键设计错误

```java
// ❌ 错误：用业务字段拼凑当幂等键
String idempotentKey = userId + "_" + productId + "_" + DateUtils.today();
// 同一天同一用户买同一商品两次 → 第二次被错误吃掉
```

**正确**：客户端生成 UUID 或 SnowflakeId 当幂等键，跟业务字段无关。

### 坑 2：Token 用 GET + DEL 两步

```java
// ❌ 错误：非原子
String value = redis.get(token);
if (value == null) throw new RepeatException();
// 这一行和下一行之间发生时间片切换
redis.del(token);
```

**修复**：必须用 Lua 脚本（见 3.4）。

### 坑 3：去重表写入和业务不在同一事务

```java
// ❌ 错误：去重表先提交，业务可能回滚
idempotentMapper.insert(record);  // 自动提交
try {
    doBusiness();
} catch (Exception e) {
    // 业务回滚了，但去重表的记录还在
    // → 下次消息重投会被当成"已处理"丢弃 → 业务永久丢失
}
```

**修复**：去重表插入必须在 `@Transactional` 里，跟业务一起提交/回滚。

### 坑 4：DuplicateKeyException 当成异常上抛

```java
// ❌ 错误
try {
    orderMapper.insert(order);
} catch (Exception e) {
    throw new RuntimeException(e);  // 客户端看到 500，重试无限循环
}

// ✅ 正确
try {
    orderMapper.insert(order);
} catch (DuplicateKeyException e) {
    // 幂等命中，查询已存在数据返回
    Order existing = orderMapper.selectByBizNo(order.getBizNo());
    return Result.success(existing);
}
```

### 坑 5：状态机直接 SET status，不带原状态判断

```sql
-- ❌ 错误：重复回调会反复触发后续动作
UPDATE `order` SET status = 'PAID' WHERE id = 1;

-- ✅ 正确：只在指定原状态才更新
UPDATE `order` SET status = 'PAID', pay_time = NOW()
WHERE id = 1 AND status = 'UNPAID';
-- 影响行数 = 0 → 已是 PAID → 跳过后续业务
```

### 坑 6：Redis 锁 + 状态判断顺序反了

```java
// ❌ 错误：先查后锁
if (orderMapper.existsByBizNo(bizNo)) return;
lock.lock();
doBusiness();
lock.unlock();
// → 检查通过到加锁之间，另一个请求也通过了检查 → 重复执行

// ✅ 正确：先锁后查
lock.lock();
try {
    if (orderMapper.existsByBizNo(bizNo)) return;
    doBusiness();
} finally {
    lock.unlock();
}
```

### 坑 7：不可逆操作（扣款/退款）放在了状态 CAS 之前

**场景**：支付成功回调与"超时兜底定时任务"并发。回调走"成功"分支，定时任务走"失败"分支，两条路径同时操作同一笔订单。

```java
// ❌ 错误：先扣币，再翻状态（先斩后奏）
walletService.consumeFrozen(userId, freezeId);            // 1. 不可逆：币扣了
orderMapper.update(... WHERE status='PENDING' SET 'SHIP'); // 2. 裁决：可能 0 行

// 交错：1 扣币完成 → 兜底抢先把状态翻成 FAILED → 2 命中 0 行
// 结果：币扣了、订单却是 FAILED，且无告警 → 用户付了钱订单显示失败
```

```java
// ✅ 正确：先翻状态（原子裁决），抢到了才扣币
int n = orderMapper.update(... WHERE status='PENDING' SET 'SHIP');
if (n == 1) {                          // 只有本次抢到状态翻转
    walletService.consumeFrozen(userId, freezeId);  // 才做不可逆操作
}
// 没抢到（n==0）→ 已被别人处理 → 不动钱
```

**本质**：扣币 + 改状态是一个**复合操作**，但两步不原子。`UPDATE ... WHERE status=X`（即坑 5 的状态机 CAS）是天然原子的**唯一裁决点**，必须让**所有不可逆副作用都排在裁决点之后**。

**与"加锁顺序统一"的关系**：和 [死锁](../Concurrency/死锁分析.md) 的解法精神一致——都是靠"统一顺序"消除竞态。但这不是死锁（没有互相等待），而是 **TOCTOU / 先斩后奏**：
- 死锁统一的是"拿锁的顺序"；
- 这里统一的是"**先裁决（状态 CAS）、后动钱（不可逆操作）**"的顺序。多条路径只要都遵守这个顺序，谁没抢到裁决就绝不会动钱。

> ⚠️ 排顺序能治本，前提是**已存在一个天然的原子裁决点**（这里是 `UPDATE ... WHERE status=X`）。若没有，得靠锁/事务把多步变原子，光排顺序不够。

## 七、面试高频追问

### Q1：幂等和并发控制是一回事吗？

不是。
- **并发控制**：保证同时请求不冲突（加锁、CAS、MVCC），强调"序列化"。
- **幂等**：保证同一操作多次执行结果一致，强调"重复无害"。

举例：转账接口加锁后并发安全了，但客户端超时重试两次，**还是会扣两次款**——必须再加幂等。

### Q2：Token 方案为什么要用 Lua？分两步不行吗？

不行。`GET → 判断 → DEL` 是三步，期间另一个请求也能 GET 到同一个 value，绕过判断。
Lua 在 Redis 单线程模型下整体原子执行，是 GET+DEL 唯一安全方式。

> 也可以用 `Redis 6.2+` 的 `GETDEL` 命令——同样是原子操作，但 Lua 通用性更高。

### Q3：MQ 消费幂等用 Redis 还是 DB？

| 场景 | 选 |
| --- | --- |
| 消费量小、可容忍少量重复 | Redis（key=bizId, EX 7d） |
| 消费量大、不可重复（金融/库存） | **DB 去重表 + 业务事务** |
| 消费量极大（亿级） | Redis + DB 双层（Redis 过滤 80%，DB 兜底） |

DB 比 Redis 更可靠的关键：能跟业务事务捆绑，避免"去重写成功但业务回滚"的不一致。

### Q4：分布式锁能保证幂等吗？

**单独不行**。锁只保证"一次只有一个执行"，但不能保证"重复请求不再执行"——第一个请求释放锁后，第二个拿到锁还是会执行。
必须 **锁 + 状态判断** 才幂等：

```java
lock.lock();
try {
    if (alreadyProcessed(bizId)) return;  // 关键这一行
    doBusiness();
} finally {
    lock.unlock();
}
```

### Q5：HTTP 接口的 RESTful 语义和幂等的关系？

| 方法 | 语义幂等 | 实际是否幂等 |
| --- | --- | --- |
| GET | ✅ | 通常是 |
| PUT | ✅ | 设计成完全替换，幂等 |
| DELETE | ✅ | 第二次删什么都不发生 |
| POST | ❌ | 创建资源，每次产生新对象 |
| PATCH | ❌ | 部分更新，业务决定 |

**注意**：RESTful 的"幂等"是协议规范，不代表后端实现一定幂等——业务侧仍要主动设计。

### Q6：客户端生成 UUID 当 token，服务端不预存，行不行？

行，但严格性下降：
- 优点：少一次 GET 调用，减一半流量
- 缺点：服务端无法识别"非法 token"——任何 UUID 都会被记一次

**适用**：内部调用、低安全场景。
**不适用**：开放 API、支付场景——必须服务端预发 token，能溯源。

### Q7：怎么处理"业务执行成功但响应丢失"导致的客户端重试？

幂等的标准答案：
1. 第一次：服务端执行成功，响应丢失
2. 客户端超时重试：带同样的 idempotency_key
3. 服务端：根据 key 查到上次结果（缓存 / DB），**返回相同响应**

关键是要 **缓存上次响应**，否则客户端拿不到正确数据。Stripe API、支付宝都是这套：

```
idempotency_key → 缓存 (status, response_body, http_code) → TTL 24h
```

### Q8：幂等需要保留多久？

| 场景 | 保留时长 |
| --- | --- |
| 表单防重（订单提交） | 30 分钟（覆盖网络重试） |
| MQ 消费 | 3-7 天（覆盖最长重投窗口） |
| 第三方回调（支付/物流） | 7-30 天 |
| 关键业务（金融转账） | 永久（DB 唯一索引） |

## 八、答题模板（60 秒话术）

> **幂等是分布式系统的第一性问题——任何会被重试的接口都必须做。**
> 触发场景三个：用户**重复点击**、MQ 的**至少一次消费**、RPC **超时重试**。
>
> 我们做幂等的标准思路是先选**幂等键**（业务唯一键 / 客户端 UUID / MQ msgId），然后选方案：
> ① **创建类**用 **DB 唯一键**兜底，最可靠；② **更新类**用 **乐观锁 version** 或 **状态机**——只在指定原状态才更新，影响行数 0 就直接返回；
> ③ **表单防重**用 **Token 机制**——服务端预发 token 存 Redis，客户端带回，服务端用 **Lua 脚本原子地 GET+DEL**；
> ④ **MQ 消费**用 **去重表 + 业务事务捆绑**，去重写入和业务必须同一个事务；
> ⑤ 复杂边界用**分布式锁 + 状态判断**兜底。
>
> 生产里几乎都是**多层组合**：网关传 idempotency_key → 业务用 Token 拦 → 状态机判断 → DB 唯一索引最终兜底。
>
> 踩过的坑：**Token 必须用 Lua**（GET+DEL 分两步会失效）、**去重表必须跟业务同事务**（否则消息丢失）、**状态机更新必须带 WHERE status='原状态'**（否则反复触发）。
