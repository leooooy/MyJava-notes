# 工作负载（Workload）

> **K8s 不让你直接管 Pod，而是用 Workload 控制器替你管**——6 种各司其职：**Deployment**（无状态主力）、**StatefulSet**（有状态）、**DaemonSet**（每节点一份）、**Job**（一次性任务）、**CronJob**（定时任务）、**ReplicaSet**（Deployment 的下层副本控制器）。每种背后都是一个 Controller 跑控制循环：watch 期望 → diff 实际 → 调整。
>
> 本篇要解决面试官四个连环追问：
>
> ① **6 种 Workload 怎么选？**——Deployment vs StatefulSet 是最经典的对比
> ② **StatefulSet 凭什么"有状态"？**——稳定网络标识 + 稳定存储 + 有序部署
> ③ **DaemonSet 适用场景？**——日志采集 / 监控 / 网络插件为什么离不开它
> ④ **Job 失败重试 / CronJob 错过执行怎么办？**——边界场景生产配置
>
> 跟其它模块的关系：
> - 前置：[Pod 与生命周期](./Pod与生命周期.md)（Workload 都是 Pod 的"管理器"）
> - 联动：[Service 与 kube-proxy](./Service与kube-proxy.md) 中 Headless Service 跟 StatefulSet 强绑定
> - 联动：[发布与弹性伸缩](./发布与弹性伸缩.md) 中滚动更新策略

## 一、为什么不直接管 Pod？

裸 Pod 的问题：节点挂了 → Pod 没了 → 没人重建。**Workload Controller 负责让 Pod 永远存在 / 数量正确**——这是声明式 API 在副本管理上的体现。

```
你写 Deployment：             K8s 控制循环 reconcile：
  replicas: 3                 watch Deployment 状态
  template:                          ↓
    image: nginx              create ReplicaSet（带 OwnerReference）
                              watch ReplicaSet
                                     ↓
                              actual = 0 < desired = 3
                              create 3 个 Pod

节点挂了一个 Pod：              ReplicaSet Controller 立刻发现：
                              actual = 2 < desired = 3
                              create 1 个新 Pod
                              （Scheduler 调度到健康节点）
```

**OwnerReference 链**：Deployment → ReplicaSet → Pod，删 Deployment 会级联删（GarbageCollector）。

## 二、Deployment：无状态主力

最常用——大部分微服务都用它。

### 2.1 三层关系

```
Deployment（你定义的）
   │ creates
   ▼
ReplicaSet（v1, v2, v3——每滚动更新一次产生新的）
   │ creates
   ▼
Pod（无标识，可互换；IP 重启会变）
```

`Deployment` 的真正职责是**管 ReplicaSet 的版本切换**——滚动更新就是逐步把流量从旧 RS 切到新 RS。

### 2.2 滚动更新参数

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%         # 临时多创建 25% 的 Pod
      maxUnavailable: 25%   # 最多 25% Pod 不可用
```

**`replicas: 4` 时的滚动过程**：

```
开始：     旧 RS [P1 P2 P3 P4]   新 RS []
↓ 创建 1 个新 Pod（maxSurge=25%=1）
状态：     旧 RS [P1 P2 P3 P4]   新 RS [N1]   总数 5
↓ N1 ready → 删 1 个旧 Pod
状态：     旧 RS [P1 P2 P3]      新 RS [N1]   总数 4
↓ 再创 N2
状态：     旧 RS [P1 P2 P3]      新 RS [N1 N2]   总数 5
... 循环
最终：     旧 RS []              新 RS [N1 N2 N3 N4]
```

详见 [发布与弹性伸缩](./发布与弹性伸缩.md)。

### 2.3 版本回滚

```bash
kubectl rollout history deployment/myapp           # 看历史 revision
kubectl rollout undo deployment/myapp              # 回上一个版本
kubectl rollout undo deployment/myapp --to-revision=3
kubectl rollout status deployment/myapp            # 看进度
kubectl rollout pause/resume deployment/myapp      # 暂停 / 恢复（金丝雀用）
```

ReplicaSet 历史保留数量：`spec.revisionHistoryLimit`（默认 10）。

## 三、StatefulSet：有状态服务

跑 MySQL / Redis / Kafka / ZK / Etcd 这种"每个实例都有身份"的应用必备。

### 3.1 三大稳定保证

| 维度 | Deployment | **StatefulSet** |
| --- | --- | --- |
| Pod 名字 | random（`myapp-7b8d-xxxx`） | **有序**（`myapp-0`、`myapp-1`、`myapp-2`） |
| Pod IP | 重启变 | 重启变（IP 不稳） |
| **DNS 名** | 没有 | **有**（`myapp-0.headless-svc.ns.svc.cluster.local`） |
| **存储** | 副本共享 PVC 或没有 | **每副本独占 PVC（VolumeClaimTemplate）** |
| **启动顺序** | 并发 | **有序**（0 → 1 → 2） |
| **删除顺序** | 并发 | **逆序**（N → ... → 1 → 0） |

### 3.2 必须配套 Headless Service

```yaml
# 1. Headless Service（clusterIP: None）
apiVersion: v1
kind: Service
metadata:
  name: mysql-headless
spec:
  clusterIP: None        # 关键：无 ClusterIP
  selector:
    app: mysql
  ports:
  - port: 3306

---
# 2. StatefulSet 关联它
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  serviceName: mysql-headless    # 关键：指向 Headless
  replicas: 3
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
      - name: mysql
        image: mysql:8.0
        volumeMounts:
        - name: data
          mountPath: /var/lib/mysql
  volumeClaimTemplates:           # 每个副本独占 PVC
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: ssd
      resources:
        requests:
          storage: 50Gi
```

**部署后**：

```
Pod 名：              DNS 名：                              PVC：
mysql-0    →   mysql-0.mysql-headless.ns.svc.cluster.local   data-mysql-0
mysql-1    →   mysql-1.mysql-headless...                     data-mysql-1
mysql-2    →   mysql-2.mysql-headless...                     data-mysql-2
```

**关键性质**：`mysql-0` 重启重建后，**域名仍是 mysql-0**，PVC `data-mysql-0` 重新挂上——**身份和数据都不变**。

### 3.3 StatefulSet 滚动更新与分区

```yaml
spec:
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 1     # 只滚 N >= 1 的 Pod（mysql-1 / mysql-2 滚，mysql-0 不动）
```

**partition 用途**：金丝雀——只更新部分副本观察效果。

## 四、DaemonSet：每节点一份

### 4.1 适用场景

```
日志采集：fluentd / filebeat / vector   ← 每节点跑一份采集本节点容器日志
监控：node-exporter / cadvisor          ← 暴露节点指标给 Prometheus
网络：calico-node / kube-proxy          ← 节点网络插件 / Service 代理
存储：longhorn-manager / ceph-csi       ← 节点级存储代理
入侵检测：falco                          ← 系统调用层监控
```

**为什么不能用 Deployment**？——Deployment 副本数固定（`replicas: 3`），不会自动覆盖每个节点；新节点加入也不会自动加副本。DaemonSet 的语义是 **"每个匹配的节点一份"**。

### 4.2 实现

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluentd
spec:
  selector:
    matchLabels:
      app: fluentd
  template:
    metadata:
      labels:
        app: fluentd
    spec:
      tolerations:                  # 通常要容忍所有污点（连 Master 都跑）
      - operator: Exists
        effect: NoSchedule
      containers:
      - name: fluentd
        image: fluentd
        volumeMounts:
        - name: varlog
          mountPath: /var/log
      volumes:
      - name: varlog
        hostPath:                   # 挂宿主目录（DaemonSet 常用）
          path: /var/log
```

**节点选择**：通过 `nodeSelector` / `nodeAffinity` 限定在特定节点（如只在 GPU 节点跑驱动）。

## 五、Job 与 CronJob：一次性 / 定时任务

### 5.1 Job：跑完就结束

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: pi-calculation
spec:
  parallelism: 3                  # 同时并发 3 个
  completions: 6                  # 总共要完成 6 次
  backoffLimit: 4                 # 失败重试上限
  activeDeadlineSeconds: 600      # 整个 Job 最多跑 600s
  ttlSecondsAfterFinished: 100    # 完成后 100s 删 Job
  template:
    spec:
      restartPolicy: OnFailure    # Pod 失败重启（不重新调度）
      containers:
      - name: pi
        image: perl
        command: ["perl", "-Mbignum=bpi", "-wle", "print bpi(2000)"]
```

**3 种工作模式**：
- **单次执行**（默认）：`completions=1, parallelism=1`
- **定数完成**：`completions=N, parallelism=M`，跑 N 次 / 同时 M 个
- **工作队列**：`completions` 不设，`parallelism=N`，Pod 自己从队列拿任务，全空了主动 exit 0 → Job 完成

### 5.2 CronJob：定时任务

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: backup
spec:
  schedule: "0 2 * * *"            # 每天凌晨 2 点（cron 语法）
  timeZone: "Asia/Shanghai"        # K8s 1.27 GA，老版本只能 UTC
  concurrencyPolicy: Forbid        # 上次没结束不开新的
  startingDeadlineSeconds: 600     # 错过执行时间 600s 内还能补跑
  successfulJobsHistoryLimit: 3    # 保留 3 次成功 Job
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
          - name: backup
            image: backup-tool
```

**concurrencyPolicy 三选一**：

| 值 | 行为 |
| --- | --- |
| `Allow`（默认） | 上次没结束也开新的（可能重复跑） |
| **`Forbid`** | **上次没结束跳过本次**（推荐生产，避免重复消费） |
| `Replace` | 杀掉上次，开新的 |

## 六、6 种 Workload 对比选型

| 维度 | Deployment | StatefulSet | DaemonSet | Job | CronJob | ReplicaSet |
| --- | --- | --- | --- | --- | --- | --- |
| **副本数** | 任意 | 任意（有序） | 每节点 1 | parallelism | parallelism | 任意 |
| **Pod 标识** | random | 有序+稳定 | 节点名 | random | random | random |
| **网络标识** | 无 | DNS（配 Headless） | 无 | 无 | 无 | 无 |
| **存储** | 共享 PVC | 独占 PVC（VolumeClaimTemplate） | 通常 hostPath | 一般无 | 一般无 | 共享 PVC |
| **启动顺序** | 并发 | **有序 0→N** | 并发 | 并发（受 parallelism 控制） | 并发 | 并发 |
| **更新策略** | 滚动 | 滚动（可分区） | 滚动 | — | — | 直接替换 |
| **典型用途** | **微服务** | DB / 缓存 / 消息队列 | 日志 / 监控 / 网络插件 | ETL / 数据迁移 | 定时备份 / 报表 | 不直接用 |

**选型决策**：

```
要让应用永远跑着？
  ├─ 是
  │   ├─ 节点级守护进程（每节点一份）？→ DaemonSet
  │   ├─ 有状态（DB / Kafka / ZK）？  → StatefulSet
  │   └─ 无状态微服务  → Deployment（99% 业务用这个）
  └─ 否（一次性任务）
      ├─ 定时执行？  → CronJob
      └─ 一次性跑   → Job
```

## 七、生产踩坑

### 坑 1：StatefulSet 缩容不删 PVC

**现象**：`kubectl scale sts mysql --replicas=2`（从 3 缩到 2），mysql-2 删了，但 PVC `data-mysql-2` 还在占磁盘。

**根因**：StatefulSet 缩容**故意保留 PVC**——防数据误删（再扩容会重新挂回）。

**修复**：
- 数据无价值确实要删 → 手动 `kubectl delete pvc data-mysql-2`
- K8s 1.27+ 支持 `persistentVolumeClaimRetentionPolicy: { whenScaled: Delete }` 自动删

### 坑 2：CronJob 时区问题

**现象**：在中国跑的 CronJob `schedule: "0 2 * * *"` 实际在凌晨 10 点跑。

**根因**：K8s 1.27 之前 CronJob 只看 UTC（kube-controller-manager 进程时区）；2 点 UTC = 10 点北京时间。

**修复**：
- K8s 1.27+ 用 `spec.timeZone: "Asia/Shanghai"`
- 老版本：把 cron 表达式按 UTC 反推（`0 18 * * *`）；或修改 controller-manager 时区

### 坑 3：Job backoffLimit 失控

**现象**：Job 配的 backoffLimit=6，结果失败 Pod 累计几十个。

**根因**：`backoffLimit` 是 **整体重试次数上限**，不是每 Pod；但每次重试 Pod 是新的——Pod 累计数 = backoffLimit + 当前还在跑的 parallelism。还有：失败 Pod 默认不删（用于排查），需要 `ttlSecondsAfterFinished` 自动清理。

**修复**：
- 合理设置 `backoffLimit`（一般 3）
- 加 `ttlSecondsAfterFinished` 自动清 Pod
- 加 `activeDeadlineSeconds` 整体超时

### 坑 4：DaemonSet 资源没限制 → 节点 OOM

**现象**：日志收集 fluentd 跑 DaemonSet，某节点上日志暴涨，fluentd 内存飙升 → 节点 OOM → 把业务 Pod 杀了。

**根因**：DaemonSet 没设 `resources.limits.memory`；fluentd 缓存日志在内存里没刷盘。

**修复**：
- 必设 `limits.memory: 500Mi` 等
- DaemonSet 优先级用 `system-cluster-critical` 提高（OOM 时不被先杀）
- 用更高效的采集器（vector / fluent-bit 比 fluentd 内存低）

### 坑 5：Deployment 副本扩缩抖动 → 雪崩

**现象**：HPA 触发扩容到 100 个副本，10 分钟后又缩到 5 个，反复抖动。

**根因**：requests 设太低 → CPU 利用率虚高 → HPA 扩；扩完单副本压力下来 → 又达不到目标利用率 → 缩。

**修复**：
- 合理 requests（看真实压力测试）
- 调大 HPA 缩容冷却（`behavior.scaleDown.stabilizationWindowSeconds: 300`）
- 详见 [发布与弹性伸缩](./发布与弹性伸缩.md)

### 坑 6：StatefulSet 滚动更新卡住

**现象**：StatefulSet rollout 时 mysql-2 一直 NotReady，整个 rollout 不进展。

**根因**：StatefulSet **逆序滚动**（N→0），且**等当前 Pod Ready 才动下一个**——mysql-2 的 Probe 不通过会卡住整个更新。

**修复**：
- 修 mysql-2 的问题（看 logs / describe）
- 用 partition 分区滚动：`partition: 0` 才完整更新
- StatefulSet 1.7+ 支持 `podManagementPolicy: Parallel`（牺牲有序性换并发更新）

## 八、面试高频追问

**Q1：Deployment 和 StatefulSet 区别？**

A：**核心差别在身份和存储**：
- **Deployment**：Pod 无状态（互换）、name 随机、IP 重启变、共享 PVC（或没有）、并发启动
- **StatefulSet**：Pod 有身份——**名字稳定**（`mysql-0/1/2`）、**有 DNS 域名**（`mysql-0.headless-svc.ns`）、**每副本独占 PVC**（VolumeClaimTemplate）、**有序启停**（0→N 启、N→0 停）

**典型用途**：Deployment 跑无状态微服务（99% 业务）；StatefulSet 跑 DB / 缓存 / 消息队列（MySQL / Redis / Kafka / ZK）。

**Q2：StatefulSet 怎么保证稳定的网络标识？**

A：靠 **Headless Service + 有序 Pod 名 + DNS**：① **Headless Service**（`clusterIP: None`）不分配 ClusterIP，DNS 直接解析到 Pod IP；② Pod 名是 `<sts-name>-<index>` 格式，重建后名字不变；③ DNS 自动注册 `<pod-name>.<headless-service>.<namespace>.svc.cluster.local`，副本重启后 IP 变了 DNS 自动跟着变。所以副本之间用域名通信（`mysql-0.mysql-headless`），不用 IP。

**Q3：StatefulSet 必须配 Headless Service 吗？**

A：**强烈推荐**。StatefulSet 的稳定 DNS 名靠 Headless Service 注册——没配也能跑（StatefulSet 不强制校验），但 Pod 之间没法用稳定域名通信，**等于退化成普通 Deployment**。生产 StatefulSet 100% 配 Headless Service，这是设计上不分家的。

**Q4：DaemonSet 适用什么场景？为什么不用 Deployment？**

A：**节点级守护进程**——每节点必须一份的：① 日志采集（fluentd / filebeat）；② 监控代理（node-exporter / cadvisor）；③ 网络插件（calico-node / kube-proxy）；④ 存储 CSI 节点代理。**Deployment 不行的根因**：副本数固定（`replicas: 3`），不会自动覆盖所有节点，新节点加入不会自动加副本——DaemonSet 的语义就是"每节点一份，节点加入自动调度，节点移除自动清理"。

**Q5：Job 失败重试怎么控制？**

A：**3 个关键参数**：① `backoffLimit`（默认 6）—— 整体重试次数上限，超过 Job 标 Failed；② `activeDeadlineSeconds` —— Job 整体超时；③ `restartPolicy: OnFailure / Never` —— OnFailure 是 Pod 失败原地重启（kubelet 拉起），Never 是 Pod 失败保留 + 创新 Pod 重试。**还有**：`ttlSecondsAfterFinished` 完成后 N 秒删 Job 防 etcd 堆积；`parallelism` + `completions` 控制并发 + 总数。

**Q6：CronJob 错过执行时间怎么办？**

A：**两个机制**：① `startingDeadlineSeconds` —— 错过 N 秒内还能补跑（超过就跳过这次）；② `concurrencyPolicy` —— 上次没结束怎么办：`Allow` 允许并发（可能重复消费）、**`Forbid` 跳过本次（推荐生产）**、`Replace` 杀上次开新的。**典型踩坑**：controller-manager 重启 / etcd 慢导致错过 → 加 `startingDeadlineSeconds: 300` 兜底；幂等任务必须配（避免补跑出问题）。

**Q7：CronJob 时区问题怎么解？**

A：**K8s 1.27+ GA `spec.timeZone: "Asia/Shanghai"`**——直接搞定。**老版本只看 UTC**（kube-controller-manager 进程时区），中国凌晨 2 点要写 `0 18 * * *`（前一天 UTC 18 点）。或修改 controller-manager 容器时区——但全局影响、不推荐。CronJob 字段 `schedule` 不接受时区前缀（不是标准 cron）。

**Q8：ReplicaSet 是干什么的？为什么我们不直接用它？**

A：**ReplicaSet 是 Pod 副本控制器**——管"实际副本数 = 期望副本数"，节点挂了重建 Pod。**你不应该直接写 ReplicaSet**——应该写 Deployment：① Deployment 自动创建 / 管理 ReplicaSet；② Deployment 提供**滚动更新和回滚能力**（多版本 RS 切换），ReplicaSet 没有。**RS 历史**：早期叫 ReplicationController，1.2 升级为 RS（支持 set-based selector），但用户接口完全被 Deployment 接管。

**Q9：StatefulSet 缩容时 PVC 会删吗？**

A：**默认不删**——故意保护数据（再扩容能恢复）。`kubectl scale sts --replicas=2` 后 mysql-2 删了，但 PVC `data-mysql-2` 还在。**K8s 1.27+ 支持自动删**：`persistentVolumeClaimRetentionPolicy: { whenScaled: Delete, whenDeleted: Delete }`——明确表示不要数据。**生产建议**：除非是开发环境，否则保持默认（保留 PVC）；要彻底清就 `kubectl delete pvc -l app=mysql`。

**Q10：Deployment 滚动更新参数 maxSurge / maxUnavailable 含义？**

A：**`maxSurge` 是允许临时多出多少 Pod**（突破 replicas 上限），**`maxUnavailable` 是允许同时不可用多少**。例：`replicas: 4, maxSurge: 25%, maxUnavailable: 25%`——滚动期间最多 5 个 Pod、最少 3 个可用。**生产权衡**：① 资源紧张：`maxSurge: 0`（不许多创）；② 可用性敏感：`maxUnavailable: 0`（始终全可用，要先创新再删旧）；③ 两者不能同时为 0（无法滚动）。

**Q11：能让 StatefulSet 的 Pod 并发启动吗？**

A：能——`spec.podManagementPolicy: Parallel`（默认 OrderedReady）。**代价**：失去启动顺序保证；适合**对启动顺序无依赖**的有状态服务（比如分片式 DB，每个分片独立）；不适合主从架构（必须先起主再起从）。也可以滚动更新时用 `partition` 分区，逐步切换。

**Q12：Pod 异常退出后 Workload 怎么处理？**

A：**Pod 重启策略 vs Workload 重建分两层**：
- **Pod 内**（`restartPolicy`）：Always（默认，Deployment 用）/ OnFailure（Job 用）/ Never。控制 kubelet 是否重启容器（同一个 Pod）。
- **Workload 层**：Pod 删了 / 节点挂了 → ReplicaSet Controller 创新 Pod（不同 Pod 名）。

所以 Deployment 默认 `restartPolicy: Always` + ReplicaSet 兜底——容器死了 kubelet 立刻拉，节点挂了 RS 重建。Job 用 `OnFailure` 让 kubelet 拉起避免重新调度（保留环境）。

## 九、答题模板（60 秒话术）

> K8s **不让你直接管 Pod**——用 6 种 Workload Controller 跑控制循环替你管：① **Deployment**（无状态主力，99% 业务）；② **StatefulSet**（有状态，DB/Kafka/Redis/ZK）；③ **DaemonSet**（每节点一份，日志/监控/网络插件）；④ **Job**（一次性任务）；⑤ **CronJob**（定时）；⑥ **ReplicaSet**（不直接用，Deployment 的下层）。
>
> **Deployment 三层关系**：Deployment → ReplicaSet → Pod。Deployment 真正职责是**管 RS 版本切换**——滚动更新就是新 RS 起来 / 旧 RS 缩，靠 maxSurge / maxUnavailable 控制节奏。版本回滚 `kubectl rollout undo`。
>
> **StatefulSet 三大稳定保证**：① **稳定网络标识**——Pod 名 `mysql-0/1/2` + DNS `mysql-0.headless-svc.ns`，重建身份不变；② **稳定存储**——VolumeClaimTemplate 给每副本独占 PVC（`data-mysql-0`），重建挂回；③ **有序启停**——0→N 启、N→0 停。**强烈推荐配 Headless Service**——稳定 DNS 靠它注册；不配等于退化成 Deployment。
>
> **DaemonSet 不能用 Deployment 替代**——Deployment 副本数固定，DaemonSet 语义是"每节点一份，节点加入自动调度"。生产 DaemonSet 必设 limits（防节点 OOM）+ 容忍 NoSchedule 污点。
>
> **Job/CronJob 关键参数**：① `backoffLimit` 失败重试上限；② `parallelism + completions` 并发 + 总数；③ `ttlSecondsAfterFinished` 完成自动清；④ CronJob `concurrencyPolicy: Forbid` 防重复消费；⑤ K8s 1.27+ 用 `timeZone: Asia/Shanghai` 解决时区问题。
>
> **6 大生产坑**：① StatefulSet 缩容默认保留 PVC；② CronJob 老版本只看 UTC；③ Job backoffLimit + 失败 Pod 不删 → etcd 堆积；④ DaemonSet 没限资源 OOM 节点；⑤ Deployment requests 太低 HPA 抖动；⑥ StatefulSet 逆序滚动卡 Pod 不进展。
