# 存储与持久化

> **K8s 把 Docker Volume 抽象成 PV（集群级存储资源）+ PVC（用户申请单）+ StorageClass（动态供应模板）三层**——用户写 PVC 要"5G 块存储"，StorageClass 调 CSI 驱动自动创出 PV，K8s 把 PV 绑到 PVC 上挂进 Pod。**StatefulSet** 通过 VolumeClaimTemplate 给每个副本独占 PVC，做到"Pod 重建数据还在"。
>
> 本篇要解决面试官四个连环追问：
>
> ① **为什么搞 PV/PVC/StorageClass 三层？**——解耦集群管理员与开发者，职责分离
> ② **动态供应怎么工作？CSI 是干嘛的？**——StorageClass + Provisioner + 厂商 CSI 插件
> ③ **回收策略怎么选？Retain vs Delete vs Recycle？**——生产数据安全的关键
> ④ **StatefulSet 怎么独占存储？**——VolumeClaimTemplate 给每副本一份
>
> 跟其它模块的关系：
> - 前置：[Docker 存储与数据卷](./Docker存储与数据卷.md)（单机 Volume 的集群级版本）
> - 配套：[工作负载](./工作负载.md) StatefulSet 强依赖
> - 联动：[ConfigMap 与 Secret](./ConfigMap与Secret.md)（也是 Volume 的一种类型）

## 一、为什么需要 PV/PVC 三层？

单机 Docker Volume 的痛点：

```
1. 跟节点绑定
   节点挂了 → Pod 调度到别节点 → Volume 没了
   
2. 没有统一管理
   100 个节点 / 几百个 Volume → 集群管理员管不过来
   
3. 应用要懂存储细节
   开发要在 yaml 写："挂哪个 NFS / 挂哪个云盘 ID / 多大"
   存储变了所有应用 yaml 都要改
```

**K8s 的解决思路 —— 三层抽象 + 角色分离**：

```
集群管理员（Cluster Admin）
   │
   │ 提供 StorageClass（"我有 ssd / hdd / nfs 三种存储能力"）
   ▼
StorageClass（动态供应模板）
   ↑
   │ PVC 引用 SC，自动创出 PV
   │
开发者（App Developer）
   │
   │ 写 PVC："我要 5G 块存储 + ReadWriteOnce"
   ▼
PersistentVolumeClaim（用户申请单）
   ↓ 自动 Bind
PersistentVolume（实际存储资源）
   ↓ 由 CSI Driver 实际创建（云盘 / Ceph RBD / NFS）
```

**收益**：① 开发只填申请单（PVC），不用懂存储细节；② 集群管理员通过 SC 集中管理；③ 应用 yaml 不依赖具体存储——同一个应用在 AWS（EBS）和私有云（Ceph）都能跑（只是 SC 名字不同）。

## 二、Volume 类型分类

K8s Volume 类型很多，**按持久性 + 来源分**：

| 类型 | 持久性 | 共享性 | 用途 |
| --- | --- | --- | --- |
| **emptyDir** | Pod 同生命周期（Pod 删则没） | 同 Pod 内多容器共享 | 临时缓存 / sidecar 共享数据 |
| **hostPath** | 节点级（节点删 / Pod 调度走则失） | ❌（跟节点绑死） | DaemonSet 挂宿主目录（如 /var/log） |
| **configMap / secret** | 跟 ConfigMap/Secret 同生命周期 | 任意 Pod 挂载 | 配置 / 密钥注入 |
| **persistentVolumeClaim** | **跨 Pod / 跨节点持久化** | 看 accessMode | **生产标准** |
| **nfs / iscsi / cephfs / glusterfs** | 跨节点持久化 | 多读多写 | 共享文件存储 |
| **csi** | 取决于后端 | 取决于后端 | 厂商存储统一接入（推荐） |
| **projected** | 同来源 | — | 多种 Volume（CM+Secret+ServiceAccount）合并到一个目录 |

**生产几乎只用 3 种**：emptyDir（临时）+ configMap/secret（配置）+ PVC（持久化）。

## 三、PV / PVC / StorageClass 详解

### 3.1 PV（PersistentVolume）：集群级存储资源

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-mysql-001
spec:
  capacity:
    storage: 50Gi
  volumeMode: Filesystem        # Filesystem / Block
  accessModes:
  - ReadWriteOnce               # RWO / ROX / RWX / RWOP
  persistentVolumeReclaimPolicy: Retain   # Retain / Delete / Recycle(deprecated)
  storageClassName: ssd
  csi:
    driver: ebs.csi.aws.com
    volumeHandle: vol-0a1b2c3d4
```

**4 种 accessMode**：

| 模式 | 含义 | 典型实现 |
| --- | --- | --- |
| **RWO**（ReadWriteOnce） | 单节点读写 | 块存储（EBS / 云盘 / Ceph RBD） |
| **ROX**（ReadOnlyMany） | 多节点只读 | NFS / 镜像仓 |
| **RWX**（ReadWriteMany） | 多节点读写 | NFS / CephFS / GlusterFS |
| **RWOP**（ReadWriteOncePod） | 单 Pod 读写（K8s 1.22+） | 比 RWO 更严格 |

**关键直觉**：
- RWO ≠ "一次只能一个 Pod 读写" —— 是"一个**节点**"，同节点多 Pod 还能挂
- 块存储天然 RWO（云盘不能多节点同时挂）；要 RWX 必须文件存储

### 3.2 PVC（PersistentVolumeClaim）：用户申请单

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-pvc
spec:
  storageClassName: ssd
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 50Gi
```

**绑定流程**：
1. 用户创建 PVC
2. PV/PVC Controller watch 到，找匹配的 PV（容量 >= 申请 + accessMode 匹配 + storageClassName 匹配）
3. 找到 → Bound（PV.spec.claimRef = PVC，PVC.spec.volumeName = PV）
4. 没找到 → Pending（要么管理员手动创 PV、要么 SC 动态创）

**关键限制**：PVC 一旦 Bound 不能改容量（K8s 1.11+ 支持扩容但不能缩容）；PVC 删了对应 PV 进入 Released 状态（不会自动回到 Available）。

### 3.3 StorageClass：动态供应模板

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: ssd
provisioner: ebs.csi.aws.com    # CSI driver
parameters:
  type: gp3                      # AWS EBS 类型
  iops: "3000"
  throughput: "125"
  encrypted: "true"
reclaimPolicy: Retain            # SC 默认回收策略
allowVolumeExpansion: true       # 允许扩容
volumeBindingMode: WaitForFirstConsumer    # 关键：延迟绑定
```

**volumeBindingMode 两种**：
- **Immediate**：PVC 创建立即创 PV（常见 → 但坑：节点亲和不一致）
- **WaitForFirstConsumer**：等到第一个 Pod 用这个 PVC 时才创 PV（**推荐**——Pod 调度到哪个节点 / 哪个 AZ，PV 就在哪儿创）

**生产示例**：

```yaml
# 场景：跨可用区集群，AZ-A 和 AZ-B
# 错误：Immediate 模式，PV 创在 AZ-A
# Pod 被调到 AZ-B 的节点 → 挂不上（云盘跨 AZ 不能挂）
# 修复：WaitForFirstConsumer，scheduler 选完节点再创 PV
```

## 四、动态供应与 CSI

### 4.1 动态供应流程

```
1. 用户写 PVC（指定 storageClassName: ssd）
2. PV/PVC Controller 找不到匹配 PV
3. 触发 StorageClass 的 Provisioner（ebs.csi.aws.com）
4. CSI Driver 调云 API（AWS EBS API）创建实际云盘 vol-xxx
5. 创建 PV 对象，volumeHandle = vol-xxx
6. PV 跟 PVC Bound
7. Pod 启动，kubelet 调 CSI Node 服务挂载到节点
8. kubelet 把节点目录 bind mount 进容器
```

### 4.2 CSI（Container Storage Interface）

CSI 是 K8s 与存储厂商的契约——**让存储插件跟 K8s 解耦**。CSI Driver 分两个组件：

| 组件 | 角色 | 部署形式 |
| --- | --- | --- |
| **Controller Plugin** | 全局——创建 / 删除 / 扩容卷、Snapshot | Deployment（控制面） |
| **Node Plugin** | 节点级——挂载 / 卸载卷到节点 | DaemonSet（每节点一份） |

**主流 CSI Driver**：

| 类型 | 例子 |
| --- | --- |
| 公有云块存储 | AWS EBS / GCP PD / Azure Disk / 阿里云盘 |
| 公有云文件存储 | AWS EFS / 阿里 NAS |
| 开源分布式 | Ceph CSI / Longhorn / Rook |
| 商业 | Portworx / NetApp Trident |

### 4.3 K8s 与 CSI 的演进

```
in-tree volume（K8s 代码里写死，2018 年前）
   ├─ AWS EBS、GCP PD、Azure Disk 等
   └─ 痛点：每加一个存储要改 K8s 主仓代码

FlexVolume（2017 过渡方案）
   └─ 用 shell 脚本写驱动，能力弱

CSI（K8s 1.13+ GA，目前标准）
   ├─ gRPC 接口，独立部署
   └─ K8s 1.21+ in-tree 全部 CSI Migration
```

## 五、回收策略（Reclaim Policy）

PVC 删除后，PV 怎么处理？

| 策略 | 行为 |
| --- | --- |
| **Retain** | PV 进入 Released 状态，**数据保留**，需管理员手动清理 / 重新绑 |
| **Delete** | PV 跟实际存储（云盘）一起删——**数据没** |
| **Recycle**（已弃用） | 跑 `rm -rf` 清空数据后回到 Available（NFS 可用，已淘汰） |

**生产建议**：
- **生产数据用 Retain**——防误删（PVC 删了至少数据还在）
- **临时 / 开发环境用 Delete**——节省成本
- StorageClass 默认 Delete（坑！），生产 SC 显式 `reclaimPolicy: Retain`

**手动清理 Released PV**：

```bash
kubectl edit pv pv-xxx
# 删除 spec.claimRef
# PV 回到 Available 状态，可重新被 PVC 绑
```

## 六、StatefulSet 存储：VolumeClaimTemplate

StatefulSet 用 `volumeClaimTemplates` 给**每个副本自动创独立 PVC**：

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  replicas: 3
  serviceName: mysql-headless
  template:
    spec:
      containers:
      - name: mysql
        volumeMounts:
        - name: data
          mountPath: /var/lib/mysql
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: [ReadWriteOnce]
      storageClassName: ssd
      resources:
        requests:
          storage: 50Gi
```

**自动展开**：

```
mysql-0 → PVC: data-mysql-0 → PV-001（50G EBS vol-0a）
mysql-1 → PVC: data-mysql-1 → PV-002（50G EBS vol-0b）
mysql-2 → PVC: data-mysql-2 → PV-003（50G EBS vol-0c）
```

**关键性质**：
- 每副本独占 50G——**N 个副本占 N × 50G**
- mysql-0 重建后，PVC `data-mysql-0` 重新挂上，**数据不变**
- StatefulSet 缩容**默认保留 PVC**（防数据误删）

详见 [工作负载](./工作负载.md) StatefulSet 章节。

## 七、生产踩坑

### 坑 1：StorageClass 默认 Delete → PVC 删数据没了

**现象**：测试环境 PVC 删了，发现关联的 50G 云盘也删了，备份都来不及做。

**根因**：StorageClass `reclaimPolicy` 默认 Delete；PVC delete → PV release → CSI 调云 API 删盘。

**修复**：
- 生产 SC 显式 `reclaimPolicy: Retain`
- 重要数据 PV 单独改：`kubectl patch pv pv-xxx -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'`
- 配 Velero 定期备份（包括 PV 快照）

### 坑 2：跨可用区调度但 PV 绑死单 AZ

**现象**：StatefulSet 滚动更新，新 mysql-0 调度到另一个 AZ → 挂载失败 `volume can not be attached`。

**根因**：StorageClass 用 Immediate 模式，PV 创在 AZ-A；scheduler 把新 Pod 调度到 AZ-B 的节点 → 云盘不能跨 AZ 挂。

**修复**：
- StorageClass 改 `volumeBindingMode: WaitForFirstConsumer`——等 Pod 调度完才创 PV
- 节点亲和限制 Pod 只调 AZ-A（topologySpreadConstraints / nodeAffinity）

### 坑 3：ReadWriteOnce 卷被多个 Pod 抢

**现象**：StatefulSet 滚动更新，新 mysql-0 起来时卡住，事件 `Unable to attach or mount volume: volume is already used by pod`。

**根因**：旧 mysql-0 正在 Terminating（kubelet 还没彻底清干净），新 mysql-0 想挂同一个 PVC（RWO 卷只能一个节点挂）。

**修复**：
- 调大 `terminationGracePeriodSeconds`，让旧 Pod 充分清理
- 用 RWX 卷（NFS）—— 但 MySQL 不能在 NFS 上跑（性能差 + 锁问题）
- StatefulSet 反亲和：新旧 Pod 在同节点（旧的解挂后新的能挂）—— 但有单点风险

### 坑 4：PVC 申请的容量改不了

**现象**：上线时 PVC 申请了 50G，半年后存储紧张要扩到 100G——直接改 PVC.resources.requests.storage 不生效。

**根因**：① StorageClass 没开 `allowVolumeExpansion: true`；② 文件系统不支持在线扩容（少数）；③ Pod 还在用着，没重启识别新大小。

**修复**：

```yaml
# StorageClass 必须有
allowVolumeExpansion: true

# 改 PVC
kubectl edit pvc mysql-pvc
# resources.requests.storage: 100Gi

# 等 PV 扩完，重启 Pod 让文件系统扩容
kubectl rollout restart sts mysql
```

**注意**：**只能扩，不能缩**——缩容会丢数据，K8s 直接拒绝。

### 坑 5：节点磁盘满 → Pod 全挂

**现象**：某节点磁盘 95%+，kubelet 触发 evict，所有 Pod 被驱逐。

**根因**：① 容器日志写容器层（详见 [Docker 存储与数据卷](./Docker存储与数据卷.md) 坑 1）；② emptyDir 没限制大小（默认无限）；③ 镜像太多没清理。

**修复**：
- emptyDir 设 `sizeLimit`：`emptyDir: { sizeLimit: 1Gi }`
- 配置 imagefs 阈值（kubelet `--eviction-hard`）
- 节点定期 `crictl rmi --prune`

### 坑 6：snapshot 没设保护

**现象**：误删 PV，云盘也跟着删，备份策略没生效（备份在云盘上）。

**根因**：备份和被备份的存储在同一个故障域。

**修复**：
- 用 **VolumeSnapshot**（CSI 1.20+ GA）—— 通过 K8s API 做存储快照
- 用 **Velero**——备份到对象存储（S3 / OSS），跨故障域
- 重要数据**多重备份**：快照 + Velero + 定期 logical dump

## 八、面试高频追问

**Q1：PV / PVC / StorageClass 三者关系？**

A：**三层抽象 + 角色分离**：① **PV（PersistentVolume）** 是集群级存储资源——实际指向 NFS / 云盘 / Ceph 等存储后端；② **PVC（PersistentVolumeClaim）** 是用户申请单——"我要 5G 块存储 + RWO"；③ **StorageClass** 是动态创建模板——管理员定义"我有 ssd / hdd 两种存储能力"，PVC 引用 SC 自动创 PV。**收益**：开发只填 PVC 不用懂存储细节；管理员通过 SC 集中管理；同一个应用 yaml 在不同存储后端都能跑（换 SC 名）。

**Q2：动态供应是怎么工作的？CSI 是干嘛的？**

A：**动态供应流程**：用户写 PVC（指定 SC）→ PV/PVC Controller 找不到匹配 PV → 触发 SC 的 Provisioner → **CSI Driver 调存储后端 API**（AWS EBS / Ceph）创实际卷 → 创 PV 对象 → Bind 到 PVC → Pod 用 PVC 启动 → kubelet 调 **CSI Node Plugin** 挂载到节点。**CSI**（Container Storage Interface）是 K8s 与存储厂商的契约——存储插件独立部署、用 gRPC 接口；让 K8s 主仓不用为每家存储改代码。CSI Driver 分 Controller Plugin（Deployment）和 Node Plugin（DaemonSet）。

**Q3：accessMode 4 种是什么？怎么选？**

A：① **RWO（ReadWriteOnce）**——单**节点**读写（不是单 Pod！同节点多 Pod 还能挂），块存储（云盘 / EBS / Ceph RBD）的天然能力；② **ROX（ReadOnlyMany）**——多节点只读，NFS / 镜像 ；③ **RWX（ReadWriteMany）**——多节点读写，必须文件存储（NFS / CephFS / GlusterFS），块存储做不到；④ **RWOP（ReadWriteOncePod）** K8s 1.22+——比 RWO 严格，单 Pod 读写。**选型**：MySQL / Kafka 等单实例数据库用 RWO（块存储性能好）；多 Pod 共享数据用 RWX（文件存储）。

**Q4：volumeBindingMode 两种区别？为什么生产用 WaitForFirstConsumer？**

A：**Immediate**——PVC 一创建立刻创 PV（常见但有坑）；**WaitForFirstConsumer**——等到 Pod 真要用这个 PVC 时才创 PV（**推荐生产**）。**经典坑**：跨可用区集群，Immediate 模式 PV 创在 AZ-A，结果 Pod 被调度到 AZ-B 节点 → 云盘不能跨 AZ 挂载 → 失败。**WaitForFirstConsumer 让 scheduler 先选节点 / 选 AZ，PV 跟着在同 AZ 创**——绑得上、挂得上。生产 StorageClass 默认配这个。

**Q5：回收策略 Retain / Delete / Recycle 怎么选？**

A：**Retain**——PVC 删了 PV 进 Released，数据保留，要管理员手动清理（**生产必选**，防误删）；**Delete**——PVC 删了 PV 跟实际存储一起删，数据没（**测试 / 开发用**，省成本）；**Recycle**——已弃用，跑 `rm -rf` 后回 Available（NFS 才支持）。**坑**：StorageClass 默认 Delete——生产 SC 必须显式改 Retain。重要数据加 Velero 备份做双保险。

**Q6：StatefulSet 怎么独占存储？为什么缩容默认不删 PVC？**

A：**StatefulSet 用 `volumeClaimTemplates`** 给每个副本自动创独立 PVC——`mysql-0 → data-mysql-0 → PV-001`，N 个副本 N 个 PVC + N 份存储。**缩容默认保留 PVC** 是设计上的数据安全——`scale --replicas=2` 删了 mysql-2 但 PVC `data-mysql-2` 还在，再扩容会重新挂回。K8s 1.27+ 支持 `persistentVolumeClaimRetentionPolicy: { whenScaled: Delete }` 显式自动删；老版本要手动 `kubectl delete pvc data-mysql-2`。

**Q7：怎么扩容 PVC？**

A：**3 个前提**：① StorageClass 配 `allowVolumeExpansion: true`；② 后端存储支持扩容（块存储一般支持，部分文件存储不支持）；③ 文件系统支持在线扩容（ext4 / xfs 可以）。**操作**：直接改 PVC `resources.requests.storage` → CSI Driver 调云 API 扩盘 → 重启 Pod 让文件系统扩。**关键**：**只能扩不能缩**——K8s 直接拒绝缩容。要缩只能新建 PV + 拷数据 + 切换 PVC。

**Q8：emptyDir / hostPath / PVC 怎么选？**

A：**emptyDir**——Pod 内多容器共享数据 / 临时缓存，**Pod 删则没**；**hostPath**——挂宿主目录，**跟节点绑死**（DaemonSet 挂 /var/log 这种系统目录 OK，业务用慎重）；**PVC**——跨 Pod / 跨节点持久化，**生产标准**。**5 种典型场景**：① 业务数据 → PVC；② sidecar 共享日志 → emptyDir；③ 配置文件 → ConfigMap volume；④ 密钥 → Secret volume；⑤ 节点级日志采集（DaemonSet）→ hostPath。

**Q9：跨可用区怎么处理 PV 调度？**

A：**关键设计**：① **StorageClass 用 WaitForFirstConsumer**——等 Pod 调度完再创 PV（同 AZ）；② **节点 / Pod 亲和限制 AZ**——重要 StatefulSet 用 `topologySpreadConstraints` 散布到多 AZ，但每副本绑定单 AZ；③ **跨 AZ 复制**——业务层做（MySQL 主从 / Kafka 分区跨 AZ）。**坑**：单 AZ 故障 PV 直接不可用 → 必须靠业务层冗余（K8s 的 PV 一般绑死 AZ，跨 AZ 自动迁移做不到）。

**Q10：CSI Migration 是什么？**

A：K8s 1.21+ 把 in-tree 存储插件（aws-ebs / gce-pd / azure-disk 等）**透明迁移到对应 CSI 实现**——你 yaml 还写 `awsElasticBlockStore`，K8s 内部转成调 CSI Driver。目的：① 把存储代码从 K8s 主仓剥离（让 K8s 更轻）；② 厂商自己迭代驱动不依赖 K8s 发版。**对用户透明**——只是底层实现变了，行为不变。K8s 1.27 in-tree 大部分已废弃，强制 CSI。

**Q11：Velero 怎么备份 K8s？**

A：Velero 是 K8s 的**集群级备份恢复工具**——能备份：① **K8s 资源**（YAML 对象）；② **PV 数据**（通过 CSI snapshot 或 Restic 文件级备份）。**架构**：装个 Velero Pod + 备份目标（S3 / OSS / 本地存储）。**典型用途**：① 灾备（跨集群恢复）；② 集群升级前快照；③ 误删恢复；④ 集群迁移。**生产建议**：每天全量 + 重要变更前手动；保留 30 天。Velero CSI 插件可以集成 CSI Snapshot 做快照式备份（比 Restic 快）。

**Q12：节点磁盘满怎么处理？**

A：**3 个层面**：① **预防**：emptyDir 设 sizeLimit；imagefs 配 eviction-hard 阈值；定期清理无用镜像（`crictl rmi --prune`）；② **监控**：Prometheus `node_filesystem_avail_bytes` 告警；③ **应急**：腾空间（删 evicted Pod / 清日志 / docker prune）；驱逐部分 Pod 到其他节点；扩节点磁盘。**根因解决**：业务日志写 stdout（Docker 自动管理）/ 写 PVC（不占节点）；不要写容器层（详见 [Docker 存储与数据卷](./Docker存储与数据卷.md)）。

## 九、答题模板（60 秒话术）

> K8s 把单机 Docker Volume 升级成 **PV / PVC / StorageClass 三层抽象 + 角色分离**：① **PV** 是集群级存储资源（背后是云盘 / NFS / Ceph）；② **PVC** 是开发的申请单（"5G + RWO"）；③ **StorageClass** 是管理员定义的动态创建模板——PVC 引用 SC 自动创 PV。**收益**：开发不用懂存储细节，管理员集中管理，应用 yaml 不绑死存储后端。
>
> **动态供应链路**：PVC → SC → **CSI Driver**（Controller Plugin 调云 API 创盘 + Node Plugin 挂载到节点）→ PV 创建 + Bind PVC → Pod 用上。CSI 是 K8s 与存储厂商的契约（gRPC 接口）——让 K8s 不用为每家存储改主仓代码。
>
> **4 种 accessMode**：RWO（**单节点**读写，块存储）/ ROX / **RWX**（多节点读写，必须文件存储）/ RWOP（K8s 1.22+ 单 Pod 严格）。**MySQL / Kafka 等单实例 DB 用 RWO 块存储，多 Pod 共享数据用 RWX 文件存储**。
>
> **回收策略 Retain vs Delete**：**生产必须 Retain** 防误删（StorageClass 默认 Delete 是大坑）；**volumeBindingMode 必须 WaitForFirstConsumer** 防跨 AZ 挂载失败（Pod 调度到 AZ-B 但 PV 在 AZ-A）。
>
> **StatefulSet 用 volumeClaimTemplates** 给每副本独占 PVC（`data-mysql-0/1/2`）—— Pod 重建数据不变；**缩容默认保留 PVC**（数据安全），K8s 1.27+ 才能配 `whenScaled: Delete` 显式删。
>
> **6 大生产坑**：① SC 默认 Delete 误删数据；② 跨 AZ Immediate 模式调度失败；③ RWO 卷新旧 Pod 抢挂；④ PVC 容量改不了（SC 没开 allowVolumeExpansion）；⑤ 节点磁盘满 evict 全部 Pod；⑥ 备份和数据在同故障域（用 Velero 备份到 S3 跨域）。
