# 调度与资源管理

> **Scheduler 给 Pod 选节点分两步**——**Filter**（按 nodeSelector / 资源 / 亲和 / 污点过滤掉不合规节点）+ **Score**（剩下的打分挑最高分）。资源管理靠 **requests**（调度依据）和 **limits**（运行上限），三者组合决定 **QoS 三档**（Guaranteed / Burstable / BestEffort），节点 OOM 时按 QoS 反向杀 Pod。
>
> 本篇要解决面试官四个连环追问：
>
> ① **Scheduler 怎么挑节点？** ——Filter + Score 两阶段
> ② **怎么把 Pod 调到指定节点 / 强制不调？**——亲和 / 污点 / 容忍
> ③ **requests vs limits 区别？怎么估算？**——一个调度依据一个运行上限
> ④ **节点 OOM 时谁先死？**——QoS 三档决定
>
> 跟其它模块的关系：
> - 前置：[K8s 架构总览](./K8s架构总览.md) Scheduler 章节
> - 联动：[JVM/jvm 参数](../JVM/jvm参数.md)（容器内 JVM 堆大小 vs limits）
> - 联动：[Docker 容器原理](./Docker容器原理.md) Cgroups 是 limits 的内核实现

## 一、调度的目标

K8s 调度**同时优化**多个目标：

```
1. 资源利用率   — 别让某节点闲置 / 某节点爆满
2. 高可用       — 同 Service 副本散布到多节点 / 多 AZ
3. 亲和约束     — 主从应用必须同节点（IO 局部性）/ 必须不同节点（容灾）
4. 业务隔离     — DB 跑在专属节点 / GPU 应用只到 GPU 节点
5. 优先级       — 在线业务挤掉离线任务（资源紧张时）
```

**Scheduler 通过 Filter + Score 两阶段** 在这些目标间平衡。

## 二、Scheduler 两阶段算法

```
Pod 待调度（nodeName="")
   │
   ▼
   ┌──────────────────────────┐
   │  Filter（预选 / Predicate） │
   │  把不合规的节点过滤掉        │
   │  - NodeName/NodeAffinity   │
   │  - PodFitsResources        │
   │  - Taint/Toleration        │
   │  - VolumeBinding           │
   │  - 节点状态（NotReady 排除） │
   └──────────────────────────┘
   │  剩 N 个候选节点
   ▼
   ┌──────────────────────────┐
   │  Score（优选 / Priority）   │
   │  给每个节点打分（0~100）    │
   │  - LeastRequested（资源少占）│
   │  - BalancedResource（均衡） │
   │  - ImageLocality（本地有镜像）│
   │  - InterPodAffinity        │
   │  - TaintTolerationPriority │
   └──────────────────────────┘
   │  最高分节点
   ▼
Bind：Pod.spec.nodeName = "node-X"
   │
   ▼
目标节点 kubelet watch 到 → 启 Pod
```

**为什么两阶段？**——上千节点先 Filter 过滤到几十个，再打分性能可控；如果直接全部打分，O(n) × O(m 个 Priority 函数) 算不动。

## 三、亲和性（Affinity）

### 3.1 Node Affinity（节点亲和）

让 Pod **倾向 / 必须**调度到带特定 Label 的节点。

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:    # 必须满足（硬约束）
        nodeSelectorTerms:
        - matchExpressions:
          - key: gpu
            operator: In
            values: ["nvidia-a100"]
      preferredDuringSchedulingIgnoredDuringExecution:   # 倾向（软约束）
      - weight: 100
        preference:
          matchExpressions:
          - key: instance-type
            operator: In
            values: ["large"]
```

**两个层次**：
- `required` —— 硬约束（不满足不调度）
- `preferred` —— 软约束（评分加权，不满足也能调）

**典型场景**：
- GPU Pod 只调到 GPU 节点
- 数据库只调到 SSD 节点
- 跨 AZ 散布

### 3.2 Pod Affinity / AntiAffinity（Pod 间亲和反亲和）

让 Pod **跟特定 Pod 同节点 / 不同节点**：

```yaml
# Pod 反亲和：副本散到不同节点（容灾）
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchExpressions:
        - key: app
          operator: In
          values: ["myapp"]
      topologyKey: kubernetes.io/hostname    # 关键：拓扑域

# Pod 亲和：缓存跟应用同节点（局部性）
affinity:
  podAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels:
          app: redis
      topologyKey: kubernetes.io/hostname
```

**`topologyKey` 含义**：
- `kubernetes.io/hostname`——同节点 / 不同节点
- `topology.kubernetes.io/zone`——同 AZ / 不同 AZ
- `topology.kubernetes.io/region`——同 region / 不同 region

**生产经典模式**：

```yaml
# 重要 Service 的副本必须散到不同节点 + 倾向不同 AZ
podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
  - labelSelector: { matchLabels: { app: api } }
    topologyKey: kubernetes.io/hostname        # 必须不同节点
  preferredDuringSchedulingIgnoredDuringExecution:
  - weight: 100
    podAffinityTerm:
      labelSelector: { matchLabels: { app: api } }
      topologyKey: topology.kubernetes.io/zone  # 倾向不同 AZ
```

### 3.3 topologySpreadConstraints（更现代）

亲和反亲和写法繁琐——K8s 1.18+ 提供更简洁的 `topologySpreadConstraints`：

```yaml
spec:
  topologySpreadConstraints:
  - maxSkew: 1                                    # 最多偏差 1 个
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule              # 或 ScheduleAnyway
    labelSelector:
      matchLabels:
        app: api
```

**含义**：把 Pod 在 zone 维度均匀散布，最大偏差不超过 1 个。比 podAntiAffinity 简洁、更适合大集群。

## 四、污点（Taint）与容忍（Toleration）

亲和是"Pod 主动要求节点"；污点反过来——**节点拒绝 Pod**，除非 Pod 显式容忍。

```bash
# 给节点加污点
kubectl taint nodes node-1 dedicated=mysql:NoSchedule
# 含义：除非 Pod 容忍这个污点，否则不能调来

# 删除污点
kubectl taint nodes node-1 dedicated-
```

**3 种 Effect**：

| Effect | 行为 |
| --- | --- |
| **NoSchedule** | 不容忍则不调度（已在节点上的 Pod 不动） |
| **PreferNoSchedule** | 软约束（优先不调，但实在没节点也行） |
| **NoExecute** | 不容忍则不调 + **驱逐已在节点上的 Pod**（最强） |

Pod 容忍：

```yaml
spec:
  tolerations:
  - key: dedicated
    operator: Equal
    value: mysql
    effect: NoSchedule
  # 容忍 NoExecute 时还可加 tolerationSeconds
  - key: node.kubernetes.io/not-ready
    operator: Exists
    effect: NoExecute
    tolerationSeconds: 300         # 节点 NotReady 5min 后才被驱逐
```

### 4.1 Master 节点为什么不调度业务 Pod？

K8s 给 Master 节点（控制面节点）打了污点：

```bash
$ kubectl describe node master-1 | grep Taints
Taints: node-role.kubernetes.io/control-plane:NoSchedule
```

业务 Pod 没容忍 → 调不上 Master。**这是设计**——保护控制面不被业务挤垮。**单节点测试集群**（k3s / kind）可以删污点：

```bash
kubectl taint nodes master-1 node-role.kubernetes.io/control-plane:NoSchedule-
```

### 4.2 节点故障的 NoExecute

K8s 内置自动给故障节点打污点：

```
node.kubernetes.io/not-ready:NoExecute    # NotReady 节点
node.kubernetes.io/unreachable:NoExecute  # 失联节点
node.kubernetes.io/disk-pressure:NoSchedule
node.kubernetes.io/memory-pressure:NoSchedule
node.kubernetes.io/pid-pressure:NoSchedule
node.kubernetes.io/network-unavailable:NoSchedule
```

**Pod 默认容忍** `not-ready` / `unreachable` 5 分钟（300 秒），超过驱逐——所以**节点挂了 5 分钟后** Pod 才被赶到别节点。生产可调小 tolerationSeconds 加快故障切换。

## 五、资源管理：requests vs limits

### 5.1 两个核心字段

```yaml
resources:
  requests:           # 调度依据
    cpu: 500m         # 0.5 核
    memory: 512Mi
  limits:             # 运行上限
    cpu: 1000m        # 1 核
    memory: 1Gi
```

**职责完全不同**：

| | requests | limits |
| --- | --- | --- |
| **用途** | **调度依据**（节点 allocatable - sum(requests) >= 这个值才调来） | **运行时上限**（cgroup 限额） |
| **超了怎样** | 调度时不满足就不调 | CPU → throttle 限速；memory → OOMKill |
| **保证什么** | 节点至少给这么多资源（不被其他 Pod 抢） | Pod 最多用这么多 |

**关键直觉**：requests 是"承诺给"，limits 是"最多用"。

### 5.2 节点 allocatable

```
节点总资源 4 核 8Gi
  - kube-reserved 0.5 核 / 0.5Gi（kubelet/runtime 自身）
  - system-reserved 0.5 核 / 0.5Gi（OS 自身）
  - eviction-threshold 100Mi（kubelet 触发 evict 阈值）
  = allocatable 3 核 7.4Gi（给 Pod 用的）

调度算法：sum(节点上 Pod 的 requests) <= allocatable
不是 sum(实际用量)！
```

**所以**：requests 设太高 → 节点装得下的 Pod 少（资源浪费）；设太低 → 突发流量时所有 Pod 实际用量超 allocatable → 节点 OOM。

### 5.3 CPU vs 内存的根本不同

| | CPU | 内存 |
| --- | --- | --- |
| **超 limits 行为** | **限速（throttle）** —— 进程暂停等下个调度周期 | **OOMKill** —— 内核杀进程（exit 137） |
| **可压缩资源** | ✅（限速不死人） | ❌（杀进程才能回收） |
| **超的影响** | 应用变慢 | 应用突死 |
| **设置建议** | limits 可以略宽 | limits 必须给足 |

**生产经验**：宁可 CPU 限速（应用变慢但不死），也别让内存 OOM（突死无日志）。

## 六、QoS 三档与 OOMKill 优先级

K8s 不让你直接配置"OOM 优先级"——根据 requests / limits 配置自动归类**三档 QoS**：

| QoS | 条件 | OOM 优先级 |
| --- | --- | --- |
| **Guaranteed**（最高保护） | 所有容器**所有资源**（CPU + 内存）都设了 requests==limits | 最低（最后被杀） |
| **Burstable** | 至少一个容器设了 requests 或 limits（但不满足 Guaranteed） | 中等 |
| **BestEffort**（无保护） | 完全不设（都没 requests 也没 limits） | 最高（最先被杀） |

```bash
kubectl get pod xxx -o jsonpath='{.status.qosClass}'
# Guaranteed / Burstable / BestEffort
```

### 6.1 OOMKill 顺序

节点内存压力 → kubelet 触发 evict（按 QoS 顺序）：

```
1. 先杀 BestEffort（不重要的）
2. 再杀 Burstable 中超 requests 最多的
3. 最后才动 Guaranteed
```

**生产建议**：核心业务**必须 Guaranteed**——`limits == requests`，确保资源一旦给就不被回收。

### 6.2 oom_score_adj

具体落实在内核 `/proc/<pid>/oom_score_adj`：

```
QoS Guaranteed → oom_score_adj = -997（最低）
QoS Burstable  → oom_score_adj = 2 ~ 999（按超 requests 比例）
QoS BestEffort → oom_score_adj = 1000（最高）
```

OOM 时内核选 `oom_score_adj + memory_usage` 最大的进程杀。

## 七、抢占（Preemption）与 PriorityClass

资源不够时，**高优先级 Pod 可以抢占低优先级 Pod 的资源**——驱逐低优先级 Pod 给自己腾位置。

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 10000
globalDefault: false
description: "在线业务高优"

---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: low-priority
value: 100
description: "离线任务低优"

---
# Pod 引用
spec:
  priorityClassName: high-priority
```

**抢占流程**：① 高优 Pod Pending 找不到节点；② Scheduler 找：哪个节点驱逐若干低优 Pod 后能容下我？③ 驱逐这些低优 Pod；④ 调度高优 Pod 上去。

**内置高优**：
- `system-cluster-critical` (2000000000)
- `system-node-critical` (2000001000)——更高，给 kube-system 关键 Pod 用（kube-proxy / kube-apiserver）

**生产用法**：在线业务用 `system-cluster-critical` 等高 PriorityClass + Guaranteed QoS 双重保护；离线 Job / 批处理用低 PriorityClass，资源紧张被抢占也无所谓。

## 八、容器化 JVM 必坑

### 8.1 必配 `-XX:+UseContainerSupport`

JDK 8u131 之前 / 默认设置下，JVM 通过 `/proc/meminfo` 看总内存——**容器内 /proc 是宿主视图**（不是 Cgroup 限额）。结果：

```
节点 64G 内存
Pod limits.memory: 2Gi
JVM 默认堆 = 总内存 / 4 = 16Gi（按宿主 64G 算）
JVM 实际用到 2.1Gi → OOMKill (exit 137)，没堆栈、无日志
```

**修复**：

```bash
java \
  -XX:+UseContainerSupport \           # JDK 8u191+ / 10+ 默认开启
  -XX:MaxRAMPercentage=75 \            # 用 cgroup 限额的 75% 作堆
  -XX:InitialRAMPercentage=75 \
  -jar app.jar

# ✅ 不写 -Xmx 写死值（容器扩缩跟不上）
# ✅ 留 25% 给非堆（Metaspace / DirectByteBuffer / JIT codecache / 线程栈）
```

### 8.2 Go 必加 `automaxprocs`

Go runtime 默认按 `/proc/cpuinfo` 看 CPU 数——容器内还是宿主视图。

```
容器 limits.cpu: 2
节点 64 核
Go 默认 GOMAXPROCS = 64 → 起 64 个 P → 频繁上下文切换
单线程性能反而比 4 核还差
```

**修复**：`import _ "go.uber.org/automaxprocs"` 自动按 cgroup CPU 限额设 GOMAXPROCS。

## 九、生产踩坑

### 坑 1：JVM 不识别 cgroup → 反复 OOMKill

**现象**：Java Pod CrashLoopBackOff，`describe` 显示 `OOMKilled exit 137`，logs 里看不到任何异常。

**根因**：JDK 8u131 之前默认按宿主内存设默认堆 → 远超 limits → 内核 OOMKill。

**修复**：升 JDK 到 8u191+ + `UseContainerSupport` + `MaxRAMPercentage=75`。**还要给 limits 留出非堆**（25%）—— `MaxRAMPercentage=75` 意味着堆占 cgroup 的 75%，剩下 25% 给 Metaspace / DirectByteBuffer / JIT。

### 坑 2：requests 太低 → HPA 抖动

**现象**：HPA 配 CPU 50% 触发扩容，结果反复扩 100 个又缩 5 个。

**根因**：`requests.cpu: 100m`（0.1 核），实际单 Pod 跑 0.3 核——CPU 使用率 = 0.3 / 0.1 = 300% → HPA 立刻扩容；扩完每 Pod 压力降低 → 又达不到目标 → 缩容。

**修复**：合理的 requests（接近实际平均用量），让 HPA 算的百分比有意义。详见 [发布与弹性伸缩](./发布与弹性伸缩.md)。

### 坑 3：DaemonSet 不容忍污点

**现象**：日志采集 fluentd DaemonSet 在某些节点没跑（包括 Master）。

**根因**：DaemonSet 默认 ServiceAccount 容忍少量内置污点，但不容忍业务自定义污点（如 Master 的 control-plane）。

**修复**：

```yaml
spec:
  template:
    spec:
      tolerations:
      - operator: Exists                    # 容忍所有污点（DaemonSet 通常这么配）
        effect: NoSchedule
      - operator: Exists
        effect: NoExecute
```

### 坑 4：Pod 反亲和卡住调度

**现象**：3 副本 Deployment + `requiredDuringScheduling podAntiAffinity` (hostname)，但集群只有 2 个节点 → 第 3 个 Pod 永远 Pending。

**根因**：硬约束要求每副本独占一节点，节点不够就调不上。

**修复**：
- `preferred` 替代 `required`（软约束，节点不够也能调）
- 用 `topologySpreadConstraints` 配 `whenUnsatisfiable: ScheduleAnyway`
- 增加节点

### 坑 5：CPU limits 太严 → 应用尖峰被限速

**现象**：服务平均 CPU 30% requests 100m / limits 200m，但 P99 延迟从 50ms 飙到 500ms。

**根因**：业务有突发尖峰（处理大对象 / GC），瞬时需要 800m CPU，被 cgroup limits 200m 限速 → 大量 throttle → P99 延迟恶化。

**修复**：
- 调高 limits（或不设 limits，让 Burstable Pod 用空闲资源）
- 监控 `container_cpu_cfs_throttled_seconds_total` 指标（限速时长）
- 关键服务**不设 CPU limits**（K8s 1.27+ 推荐做法，降 throttle 风险）

### 坑 6：抢占链式驱逐

**现象**：高优 Pod 调度，驱逐了 5 个低优 Pod；这些低优 Pod 又抢占别的更低优——一连串驱逐，集群抖动。

**根因**：抢占级联无限制。

**修复**：
- PriorityClass 层级设清楚（在线 = 10000、批处理 = 100、抢占只跨级）
- 监控 `kube_pod_status_phase{phase="Pending"}` 看积压量
- 用 PreemptionPolicy: Never 关闭抢占（特定 PriorityClass）

## 十、面试高频追问

**Q1：Scheduler 怎么挑节点？**

A：**Filter + Score 两阶段**：① **Filter（预选）**——把不合规的节点过滤掉：NodeAffinity / 资源够不够（PodFitsResources）/ 污点容忍 / VolumeBinding（PVC 能不能挂）/ 节点状态（NotReady 排除）；② **Score（优选）**——剩下的打分排序：LeastRequested（资源占用低）/ BalancedResource（CPU 内存均衡）/ ImageLocality（节点本地有镜像优先）/ InterPodAffinity 等几十个 Priority 函数。最高分节点 Bind。**两阶段**是性能优化——上千节点先 Filter 到几十再打分。

**Q2：requests 和 limits 区别？**

A：**职责完全不同**：① **requests 是调度依据**——Scheduler 算 `节点 allocatable - sum(其他 Pod 的 requests) >= 我的 requests` 才能调过来；运行时**保证至少有这么多**资源（不被其他 Pod 抢）。② **limits 是运行时上限**——cgroup 限额：CPU 超了 throttle 限速，**内存超了 OOMKill**（exit 137）。**估算原则**：requests 接近实际平均用量（让 HPA 百分比准）；limits 给 25%~50% buffer 应对尖峰；**核心业务设 requests==limits 走 Guaranteed QoS**。

**Q3：QoS 三档怎么决定？OOM 时谁先死？**

A：**根据 requests / limits 配置自动归类**：① **Guaranteed**——所有容器所有资源（CPU + 内存）都设且 requests==limits，**最高保护，最后被 OOMKill**；② **Burstable**——至少一个容器设了 requests 或 limits 但不满足 Guaranteed，中等保护；③ **BestEffort**——完全不设，**最先被杀**。**OOM 顺序**：先杀 BestEffort → 再杀 Burstable 中超 requests 最多的 → 最后才动 Guaranteed。**核心业务必须 Guaranteed**。

**Q4：Master 节点为什么不调度业务 Pod？**

A：**Master 默认带污点** `node-role.kubernetes.io/control-plane:NoSchedule`——业务 Pod 没显式容忍就调不上。**目的**：保护控制面（apiserver / etcd / scheduler / controller-manager）不被业务挤垮。**单节点测试集群**（k3s / kind / minikube）需要业务也跑 Master，`kubectl taint nodes master node-role.kubernetes.io/control-plane:NoSchedule-` 删掉污点。**生产 Master 节点**专门跑控制面 + DaemonSet（监控 / 日志），业务严禁上去。

**Q5：节点亲和、Pod 亲和反亲和分别怎么用？**

A：**Node Affinity**——Pod 倾向 / 必须调到带某 Label 的节点（GPU Pod 只到 GPU 节点 / DB 只到 SSD 节点）。**Pod Affinity**——跟特定 Pod 同一拓扑域（缓存跟应用同节点 → IO 局部性）。**Pod AntiAffinity**——跟特定 Pod 不同拓扑域（**副本散到不同节点 → 容灾**，最常用）。**topologyKey** 决定拓扑域（hostname / zone / region）。**现代写法**：用 `topologySpreadConstraints` 替代繁琐的 podAntiAffinity——`maxSkew` 控制最大偏差，更适合大集群。

**Q6：污点容忍跟亲和有什么区别？**

A：**亲和是 Pod 主动选节点（吸引）**；**污点是节点主动拒绝 Pod（排斥）**。① 亲和：Pod 写 nodeSelector / nodeAffinity，无 Label 节点跟它无关；② 污点：节点打 Taint，**所有 Pod 默认调不上去**，除非容忍。**典型用法**：① **专属节点**：DB 节点打 `dedicated=mysql:NoSchedule` 污点 + Pod 容忍——既排斥业务，DB Pod 又能调上去（污点排他 + 配合 nodeSelector 把 DB 选过去）；② **故障转移**：节点挂了 K8s 自动打 `not-ready:NoExecute` 污点，5 分钟后驱逐 Pod。

**Q7：抢占（Preemption）怎么工作？**

A：**资源不够时高优 Pod 抢占低优**：① 高优 Pod Pending 找不到节点；② Scheduler 找"驱逐哪些低优 Pod 后能容下我"的方案；③ 驱逐这些低优 Pod（发 Eviction → 给优雅停机时间 → 强杀）；④ 调度高优 Pod。**PriorityClass** 决定优先级——用户可以建自己的（在线 10000 / 离线 100），内置 `system-cluster-critical`（2000000000）和 `system-node-critical`（2000001000）给 kube-system。**坑**：抢占级联（被驱逐的 Pod 又去抢更低优的），生产监控 Pending 积压。

**Q8：为什么核心服务推荐"不设 CPU limits"？**

A：**K8s 1.27+ 越来越多人推荐核心服务不设 CPU limits**：① **CPU 是可压缩资源**——超 limits 是 throttle（限速）不是 kill，应用变慢但不死；② **CFS throttle 在内核 100ms 周期里限制配额**——业务突发尖峰被限速 → 平均用量看似低但 P99 延迟飙；③ **不设 limits 时 Burstable Pod 能用节点空闲 CPU**——更高效。**前提**：① **必须设 requests**（否则 BestEffort）；② **节点 allocatable 已经被 requests 总和限制**（不会过载到节点崩）。**仍然推荐设内存 limits**——内存超了直接 OOMKill 不可逆。

**Q9：JVM 容器化必配什么？**

A：**3 个**：① `-XX:+UseContainerSupport`（JDK 8u191+ / 10+ 默认开）—— JVM 按 cgroup 限额设默认堆而不是宿主内存；② `-XX:MaxRAMPercentage=75`—— 用 cgroup 限额的 75% 作堆，**留 25% 给 Metaspace / DirectByteBuffer / JIT codecache / 线程栈**；③ **不要写死 `-Xmx`**——容器 limits 调整后 -Xmx 跟不上。**还有**：JDK 17 ZGC 容器化更好；监控 `container_memory_working_set_bytes`（K8s OOMKill 真正参考的指标）；时区基础镜像默认 UTC，要 `TZ=Asia/Shanghai`。

**Q10：Go 容器化必加什么？**

A：`import _ "go.uber.org/automaxprocs"`—— Go runtime 默认按 `/proc/cpuinfo` 设 GOMAXPROCS，容器内 /proc 是宿主视图（64 核节点 limits 2 核 → Go 起 64 个 P → 频繁上下文切换 → 单线程性能反而差）。automaxprocs 自动读 cgroup CPU 限额设 GOMAXPROCS。**注意**：要写 `_ "..."` 让 init 生效，不能只 import。还要监控 `runtime.GOMAXPROCS(-1)` 验证生效。

**Q11：节点 NotReady 时 Pod 怎么处理？**

A：① kubelet 心跳超时（默认 40s）→ Node Controller 标记节点 NotReady；② **5 分钟后**（Pod 默认容忍 `not-ready:NoExecute` 300 秒）→ Pod 被驱逐 → 调度到其他节点重建。**生产调优**：① 调小 `tolerationSeconds`（如 60s）加快故障切换，但抖动风险增加；② 用 PDB 防一次性驱逐过多副本；③ 监控 `kube_node_status_condition` 节点状态。**关键**：StatefulSet 用 RWO 卷的 Pod 故障切换有大坑——旧 Pod 还没彻底清理新 Pod 不能挂同一卷。

**Q12：requests 怎么估算？**

A：**3 步**：① **压测**——单 Pod 在生产负载下跑 1 小时，看 P50 / P99 CPU、内存；② **设 requests 接近 P50 平均用量**（让 HPA 百分比准）；③ **设 limits 给 30%~50% buffer 应对尖峰**（核心服务可不设 CPU limits）。**经验值**：Java 微服务 `requests: 500m/1Gi, limits: 1000m/2Gi`；Go 微服务 `requests: 200m/256Mi, limits: 500m/512Mi`。**最坏做法**：requests 设很低（觉得"省资源"）→ HPA 抖动 + 节点超卖被打挂。

## 十一、答题模板（60 秒话术）

> **Scheduler 给 Pod 选节点分两步**：① **Filter（预选）**——按 nodeAffinity / 资源 / 污点 / VolumeBinding / 节点状态过滤掉不合规节点；② **Score（优选）**——剩下的打分（LeastRequested / BalancedResource / ImageLocality 等几十个 Priority）—— 选最高分 Bind。
>
> **怎么调度去指定节点**：① **节点 Label + nodeAffinity**（required 硬 / preferred 软）；② **nodeSelector**（简化版 nodeAffinity）；③ **污点容忍**（节点打 Taint 拒绝 Pod，特定 Pod 容忍才能调过来——专属节点池常用）；④ **podAntiAffinity / topologySpreadConstraints**（副本散到不同节点 / AZ）。
>
> **资源管理**：requests 是**调度依据**（节点 allocatable - sum(requests) >= 我才调过来），limits 是**运行时上限**（cgroup 限额）。**CPU 超 limits 是 throttle**（限速变慢），**内存超 limits 是 OOMKill**（exit 137 突死）。**核心服务推荐：不设 CPU limits**（K8s 1.27+ 趋势，避免尖峰被限速）+ **必设内存 limits**（防 OOM 全节点崩）。
>
> **QoS 三档**——不直接配，根据 requests/limits 配置自动归类：**Guaranteed**（CPU+内存都设且 requests==limits / 最后被杀）/ **Burstable**（部分设 / 中等保护）/ **BestEffort**（都不设 / 最先被杀）。**OOM 时按 QoS 反向杀**——核心业务必须 Guaranteed。
>
> **JVM 容器化必配**：① `-XX:+UseContainerSupport`（JDK 8u191+/10+ 默认开）；② `-XX:MaxRAMPercentage=75`（堆占 cgroup 的 75% 留 25% 给非堆）；③ 不要写死 `-Xmx`。**Go 必加** `automaxprocs` 让 GOMAXPROCS 跟 cgroup CPU 限额。
>
> **6 大生产坑**：① JVM 不识别 cgroup OOMKill；② requests 太低 HPA 抖动；③ DaemonSet 不容忍污点漏调；④ Pod 反亲和硬约束节点不够卡 Pending；⑤ CPU limits 太严尖峰被 throttle 高 P99；⑥ 抢占链式驱逐集群抖动。
