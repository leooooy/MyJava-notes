# 发布与弹性伸缩

> **发布靠 Deployment 滚动更新（maxSurge / maxUnavailable）+ Probe 把控**；高级策略（蓝绿 / 金丝雀）靠 Service 切换 + 多 Deployment / Ingress 流量比例。**弹性靠三层**：HPA（横向 Pod，按 CPU / 自定义指标）、VPA（纵向，调 requests）、Cluster Autoscaler（节点级，加机器）。**优雅停机** = preStop + terminationGracePeriodSeconds + 业务 hook，缺一会断流。
>
> 本篇要解决面试官四个连环追问：
>
> ① **Deployment 滚动更新参数 maxSurge / maxUnavailable 怎么取？**——可用性 vs 资源紧张的取舍
> ② **蓝绿 / 金丝雀 / 滚动 怎么选？**——3 种发布的不同代价
> ③ **HPA 触发条件 / 冷却时间？**——抖动是经典坑
> ④ **怎么不丢请求停机？**——优雅停机三件套必须配齐
>
> 跟其它模块的关系：
> - 前置：[工作负载](./工作负载.md) Deployment / StatefulSet 滚动机制
> - 前置：[Pod 与生命周期](./Pod与生命周期.md) preStop / Probe
> - 配套：[调度与资源管理](./调度与资源管理.md) HPA 跟 requests 强相关
> - 联动：[Microservice/服务治理](../Microservice/服务治理.md) 重试 / 熔断与发布配合

## 一、为什么要发布与弹性？

```
不停机发布：用户感知不到、业务不中断
弹性伸缩：流量大时多开实例，流量小时缩回省钱
优雅停机：缩 Pod 时已建立的请求要处理完，新请求不打过来
```

K8s 通过 Deployment / HPA / preStop 这套机制把这些做成"声明式"——配好策略，平台自动执行。

## 二、Deployment 滚动更新机制

### 2.1 滚动更新参数

```yaml
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%              # 临时超出 replicas 的上限
      maxUnavailable: 25%        # 最多多少 Pod 不可用
  minReadySeconds: 30            # Pod Ready 后等 30s 才算"真就绪"
  progressDeadlineSeconds: 600   # 滚动 10min 没进展标记 Failed
  revisionHistoryLimit: 10       # 保留 10 个历史 RS
  template:
    spec:
      containers:
      - name: app
        image: myapp:v2          # 改 image 触发滚动
```

**`maxSurge` 和 `maxUnavailable` 含义**：
- `maxSurge: 25%, replicas: 4` → 滚动期间最多 5 个 Pod（超出 1 个）
- `maxUnavailable: 25%` → 最多 1 个不可用，至少 3 个可用

**滚动过程**（详细 8 步）：

```
开始：旧 RS [P1 P2 P3 P4]   新 RS []   总数 4
Step1：创 1 个新 Pod（maxSurge=1）
       旧 RS [P1 P2 P3 P4]   新 RS [N1] 总数 5
Step2：N1 ready 30s（minReadySeconds）→ 删 1 个旧 Pod
       旧 RS [P1 P2 P3]      新 RS [N1] 总数 4
Step3：再创 N2
       旧 RS [P1 P2 P3]      新 RS [N1 N2] 总数 5
Step4：N2 ready → 删 P3
       旧 RS [P1 P2]         新 RS [N1 N2] 总数 4
... 重复
最终：旧 RS [] 缩到 0，新 RS [N1 N2 N3 N4]
```

### 2.2 参数取舍

| 场景 | 配置 | 取舍 |
| --- | --- | --- |
| **可用性敏感**（金融 / 实时） | `maxSurge: 25% / maxUnavailable: 0` | 始终全可用，要先创新再删旧；**资源消耗大** |
| **资源紧张** | `maxSurge: 0 / maxUnavailable: 25%` | 先删旧再创新，节省资源；**滚动期间能力下降** |
| **平衡（默认）** | `maxSurge: 25% / maxUnavailable: 25%` | 中庸 |

**两者不能同时为 0**——无法滚动。

### 2.3 minReadySeconds 重要性

```
Pod Probe Ready ≠ 真的就绪
  - JVM 刚 warmup，第一个请求可能慢 10 倍
  - 缓存预热没做完
  - 连接池初始化中

minReadySeconds 让 Pod 在 ready 后多观察 30s 没崩才算"真就绪"
→ 滚动更新会等这 30s 才删下一个旧 Pod
→ 防止"看似 ready 但实际刚启崩"的雪崩
```

### 2.4 版本回滚

```bash
kubectl rollout history deployment/myapp
# REVISION  CHANGE-CAUSE
# 1         <none>
# 2         Update to v1.5.0
# 3         Update to v1.5.1

kubectl rollout undo deployment/myapp                  # 回上一版（v1.5.0）
kubectl rollout undo deployment/myapp --to-revision=1  # 回指定版

kubectl rollout status deployment/myapp                # 看滚动进度
kubectl rollout pause deployment/myapp                 # 暂停（金丝雀手动控制）
kubectl rollout resume deployment/myapp                # 恢复
```

**回滚原理**：每次镜像变化创新 RS，老 RS 保留（受 `revisionHistoryLimit` 限制）；回滚 = 新建 RS 用老镜像。

## 三、3 种发布策略

### 3.1 滚动更新（Rolling，默认）

```
v1: [P1 P2 P3 P4]
逐步替换：
[P1 P2 P3 P4 N1] → [P1 P2 P3 N1] → [P1 P2 P3 N1 N2] → ... → [N1 N2 N3 N4]
```

**优点**：自动、零停机、占用资源少。
**缺点**：v1 v2 同时在线（不兼容数据库变更场景有坑）；回滚慢（要再滚一次）。

### 3.2 蓝绿（Blue-Green）

```
旧 Deployment（蓝）4 个 Pod    新 Deployment（绿）4 个 Pod
              ↑                            ↑
              │                            │
        Service 指向蓝     ───切换───→  Service 指向绿
```

**做法**：跑两套完整 Deployment（v1 + v2），Service.selector 切换 label 一刀切流量。

**优点**：瞬时切换、回滚秒级（改 selector 切回去）；新版本完全隔离测试。
**缺点**：**资源翻倍**（两套同时跑）；切换瞬间客户端连接重置；不适合渐进。

```yaml
# blue: app: myapp, version: v1, replicas: 4
# green: app: myapp, version: v2, replicas: 4

# Service 切换：
spec:
  selector:
    app: myapp
    version: v1     # 改成 v2 → 流量瞬切
```

### 3.3 金丝雀（Canary）

```
v1: 8 个 Pod    v2: 2 个 Pod   ← 总 10 个，v2 占 20%
               ↑
       通过同一 Service / Ingress 按比例分流
```

**做法**：v1 和 v2 都接到同一 Service / Ingress，按比例 / 按 Header 分流；逐步加大 v2 比例直到 100%。

**优点**：**渐进式**（5% → 20% → 50% → 100%），出问题影响小；可按用户 / Header 灰度精准放量。
**缺点**：实施复杂（要 Ingress / Service Mesh 支持）；监控要跟得上（v2 出问题要快速发现）。

**Nginx Ingress 实施**（详见 [Ingress 与网关](./Ingress与网关.md)）：

```yaml
# 主 Ingress：100% → v1
metadata:
  name: api
spec:
  rules:
  - http:
      paths:
      - backend: { service: { name: api-v1, port: { number: 80 } } }

---
# Canary Ingress：按比例
metadata:
  name: api-canary
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "20"
spec:
  rules:
  - http:
      paths:
      - backend: { service: { name: api-v2, port: { number: 80 } } }
```

### 3.4 三种策略对比选型

| 维度 | 滚动 | 蓝绿 | 金丝雀 |
| --- | --- | --- | --- |
| **资源占用** | 略多（maxSurge） | **2 倍** | 略多 |
| **切换时间** | 渐进（几分钟） | **瞬间** | 渐进（按比例） |
| **回滚** | 慢（再滚一次） | **秒级** | 调比例瞬时 |
| **新旧共存** | ✅ | ❌（要么蓝要么绿） | ✅ |
| **实施复杂度** | 简单（K8s 原生） | 中（要管两套） | **复杂**（Ingress / Mesh 支持） |
| **风险** | 中（旧版本逐步退） | 高（瞬切影响大） | **低**（按比例） |
| **适用** | 日常迭代 | 大版本 / 不兼容变更 | 高风险变更 |

**生产经验**：
- **小变更**用滚动（K8s 原生最简单）
- **大版本 + 不兼容数据库变更**用蓝绿（避免 v1 v2 同时跑）
- **核心业务关键变更**用金丝雀（按 Header 精准灰度内部 / VIP 用户先验证）

## 四、HPA / VPA / Cluster Autoscaler 三层弹性

### 4.1 三层关系

```
[HPA] 横向：Pod 副本数变化       — autoscaling/v2 内置
   - 按 CPU / 内存利用率
   - 按自定义指标（QPS / 延迟）

[VPA] 纵向：Pod requests/limits 变化  — Operator 装
   - 按历史用量推荐 / 自动调整 requests
   - 不能跟 HPA 同时管 CPU（冲突）

[Cluster Autoscaler] 节点级：节点数变化  — 云厂商集成
   - 节点资源不够调度 → 加节点
   - 节点利用率低 → 缩节点
```

### 4.2 HPA 详解

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  minReplicas: 3
  maxReplicas: 50
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60       # 平均 CPU 利用率 60% 触发
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 70
  behavior:                           # K8s 1.23+ 控制扩缩节奏
    scaleUp:
      stabilizationWindowSeconds: 0   # 扩容 0s 冷却（响应快）
      policies:
      - type: Percent
        value: 100                    # 一次最多扩 100%
        periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 300 # 缩容 5min 冷却（防抖）
      policies:
      - type: Percent
        value: 50
        periodSeconds: 60
```

**HPA 算法**：

```
desiredReplicas = ceil(currentReplicas × (currentMetric / desiredMetric))

例：currentReplicas=4, CPU 平均 80%, target 60%
desired = ceil(4 × (80/60)) = ceil(5.33) = 6
```

**关键参数**：
- `stabilizationWindowSeconds`——冷却时间，防抖动（缩容 5 分钟，扩容 0 秒）
- `behavior.policies`——单次扩缩比例 / 数量上限
- HPA Controller 周期：默认 15s 算一次

**HPA 抖动经典坑**：
- **requests 设太低** → CPU 利用率虚高 → 频繁扩
- **缩容冷却太短** → 上下抖动
- 修复：合理 requests + 缩容冷却 5min+ + behavior.policies 限速

### 4.3 自定义指标 HPA

```yaml
metrics:
- type: Pods
  pods:
    metric:
      name: http_requests_per_second
    target:
      type: AverageValue
      averageValue: 1000             # 平均 QPS 1000
```

需要装 **Prometheus Adapter** 或 **KEDA**（事件驱动伸缩，支持 Kafka 队列长度 / RabbitMQ / Redis 等）。

### 4.4 VPA（Vertical Pod Autoscaler）

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api
  updatePolicy:
    updateMode: "Auto"                # Off / Initial / Auto
  resourcePolicy:
    containerPolicies:
    - containerName: '*'
      minAllowed: { cpu: 100m, memory: 128Mi }
      maxAllowed: { cpu: 4, memory: 8Gi }
```

**3 种 updateMode**：
- `Off`——只推荐不修改（看 VPA Recommender 给出建议）
- `Initial`——只在 Pod 创建时设置（重启后才生效）
- `Auto`——自动重启 Pod 应用新 requests（**有侵入性，慎用**）

**VPA 跟 HPA 不能共存管 CPU**——HPA 横向扩缩，VPA 纵向调 requests，互相打架。**生产用法**：HPA 管 CPU 横向；VPA `Off` 模式给推荐值，人工确认后改 yaml。

### 4.5 Cluster Autoscaler

```
HPA 想扩到 50 个 Pod → 节点资源不够 → CA 介入
CA 调云厂商 API（AWS ASG / GCP MIG）扩节点
新节点 Ready → kubelet 注册 → Scheduler 调 Pending Pod 上去
```

**节点缩容条件**（Pod 全部能迁走）：
- 节点利用率 < 50%（默认）
- 节点上 Pod 都能调度到其他节点
- 节点空闲 10+ 分钟

**典型配合**：HPA 横向扩 Pod → CA 加节点（节点不够时）→ 流量回落 → HPA 缩 Pod → CA 缩节点。

## 五、优雅停机：preStop 三件套

### 5.1 K8s 终止 Pod 的完整流程

```
1. apiserver 标 Pod 为 Terminating（Pod.metadata.deletionTimestamp 设值）
2. Endpoint Controller 把 Pod 从 EndpointSlice 摘除（开始）
3. kubelet 调 preStop hook（同步阻塞）
4. preStop 完 → 发 SIGTERM 给容器主进程（PID 1）
5. 等 terminationGracePeriodSeconds（默认 30s）
6. 还没退 → 发 SIGKILL 强杀
```

**关键陷阱**：步骤 2 和步骤 3 是**并行执行**——
- Endpoint 摘除是异步的（要传到所有节点的 kube-proxy，**最多几秒延迟**）
- preStop 一开始就执行
- 如果 preStop 不 sleep，业务进程立刻 SIGTERM 退出，但流量还在打过来 → 客户端报 502

### 5.2 标准三件套

```yaml
spec:
  terminationGracePeriodSeconds: 60          # 总超时（>= preStop sleep + 业务收尾 + 余量）
  containers:
  - name: app
    lifecycle:
      preStop:
        exec:
          command:
          - sh
          - -c
          - |
            sleep 15                          # 让 Endpoint 传播
            curl -X POST localhost:8080/admin/shutdown   # 业务收尾
            sleep 5                           # 等收尾完成
```

**为什么 sleep 15**：
- Endpoint 摘除 → kube-proxy 同步 iptables/IPVS（几秒）
- Ingress Controller / 客户端 LB 也要发现这个变化（比如 Nginx Ingress watch Endpoint）
- 总和约 5~10 秒，**留 15 秒余量保底**

### 5.3 应用层配合

**Spring Boot 2.3+**：

```yaml
server:
  shutdown: graceful                          # 启用优雅关闭
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s           # 每阶段最多 30s

# K8s preStop:
preStop:
  exec:
    command: ["sh", "-c", "sleep 15"]         # Spring 自己处理 SIGTERM
```

**Go 应用**：

```go
ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, syscall.SIGINT)
defer stop()

server.ListenAndServe()

<-ctx.Done()
shutdownCtx, _ := context.WithTimeout(context.Background(), 30*time.Second)
server.Shutdown(shutdownCtx)
```

### 5.4 Dockerfile 必坑

```dockerfile
# ❌ 反例：sh 是 PID 1，java 收不到 SIGTERM
CMD java -jar app.jar

# ✅ 正例：java 直接是 PID 1
CMD ["java", "-jar", "app.jar"]

# 或装 tini 作 init：
ENTRYPOINT ["/tini", "--"]
CMD ["java", "-jar", "app.jar"]
```

详见 [Dockerfile 与镜像优化](./Dockerfile与镜像优化.md) 坑 5。

## 六、PodDisruptionBudget（PDB）

防止"voluntary disruption"（节点 drain / 维护 / 升级）一次性把所有副本 evict 掉。

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-pdb
spec:
  minAvailable: 2                # 最少保留 2 个可用
  # 或 maxUnavailable: 1          # 最多 1 个不可用
  selector:
    matchLabels:
      app: api
```

**生效场景**：
- `kubectl drain node-X` → 节点上的 Pod 要被驱逐 → PDB 检查：驱逐后是否还满足 PDB？满足才放行
- 集群升级、节点下线、Cluster Autoscaler 缩节点

**不生效场景**：
- 节点突然挂了（**involuntary disruption**）
- Pod 被 Liveness Probe 杀

**生产建议**：
- 重要 Service 必配 PDB（`minAvailable: replicas / 2 + 1` 半数 + 1）
- StatefulSet（如 etcd）配 `maxUnavailable: 1`（一次只允许挂一个）

## 七、生产踩坑

### 坑 1：Probe 太松 → 流量打到没启好的 Pod

**现象**：滚动更新期间客户端报 502。

**根因**：Readiness Probe `initialDelaySeconds: 5` 太短，Pod 刚启动就 ready，但应用还没真就绪（warmup 没完）→ Endpoint 加进去 → 流量打过来 → 应用响应慢 / 报错。

**修复**：
- Readiness 改严（看深度健康检查接口）
- 加 `minReadySeconds: 30`（K8s 层面再等 30s 才认）
- 用 Startup Probe 兜底（详见 [Pod 与生命周期](./Pod与生命周期.md) 第 5 章）

### 坑 2：preStop 没等连接释放 → 502

**现象**：滚动更新时偶发 connection reset。

**根因**：preStop 没 sleep / sleep 太短；或 sleep 了但 Endpoint 还没传播完（Nginx Ingress watch 慢）。

**修复**：preStop sleep 至少 15s + terminationGracePeriodSeconds: 60s。

### 坑 3：HPA 抖动

**现象**：HPA 反复扩到 50 个又缩到 5 个。

**根因**：① requests 设太低 CPU 利用率虚高；② 缩容冷却太短；③ 业务波动大但 HPA 配置激进。

**修复**：
- requests 接近实际平均用量（让百分比有意义）
- `behavior.scaleDown.stabilizationWindowSeconds: 300`（缩容 5min 冷却）
- `behavior.scaleDown.policies` 限速（一次最多缩 25%）

### 坑 4：节点 drain evict 全副本

**现象**：节点维护 drain 时，业务 5 个副本全在这台 → 一次性 evict → 业务挂。

**根因**：Pod 反亲和没配（5 个副本在一节点）+ PDB 没配（drain 没限制）。

**修复**：
- 副本反亲和：`podAntiAffinity` 散到不同节点
- 配 PDB `minAvailable: 3`（5 个副本至少留 3 个）

### 坑 5：Spring Boot 优雅停机配错

**现象**：preStop 配了 60s，业务还是被强杀。

**根因**：① 没设 `server.shutdown: graceful`；② Dockerfile CMD 用 shell 形式 sh 是 PID 1 收不到 SIGTERM；③ Spring Boot 1.x / 2.2 不支持优雅关闭（要装 spring-boot-actuator 处理 /shutdown）。

**修复**：升 Spring Boot 2.3+ + `server.shutdown: graceful` + Dockerfile exec 形式 + tini 作 init。

### 坑 6：滚动更新期间数据库迁移冲突

**现象**：v1 v2 同时在线（滚动期间），v2 跑了 schema 迁移加新字段，v1 不认这个字段开始报错。

**根因**：滚动更新本质是**v1 v2 同时跑几分钟**——破坏性的 DB 变更（删字段 / 改类型）在这期间出问题。

**修复**：
- **三步迁移**：① 加新字段（v1 仍能跑）；② 部署 v2 用新字段；③ 后续删旧字段
- 大版本不兼容变更用蓝绿（v1 v2 不同时跑）
- 数据库变更走专门的 migration job（initContainer）

## 八、面试高频追问

**Q1：maxSurge 和 maxUnavailable 含义？怎么取？**

A：**`maxSurge` 是滚动期间允许临时多出多少 Pod**（突破 replicas 上限），**`maxUnavailable` 是允许同时不可用多少**。例 `replicas: 4, maxSurge: 25%, maxUnavailable: 25%` —— 滚动期间最多 5 个 Pod / 最少 3 个可用。**3 种典型配置**：① **可用性敏感**：`maxSurge: 25% / maxUnavailable: 0`（始终全可用，资源消耗大）；② **资源紧张**：`maxSurge: 0 / maxUnavailable: 25%`（先删旧再创新）；③ **平衡**：默认。**两者不能同时为 0**——无法滚动。

**Q2：滚动 / 蓝绿 / 金丝雀 怎么选？**

A：**滚动**——K8s 原生、零停机、资源占用少；新旧共存几分钟；**回滚慢**（要再滚一次）。**蓝绿**——跑两套完整副本，Service 切 selector 一刀切；**回滚秒级**；**资源翻倍**；适合大版本 / 不兼容数据库变更。**金丝雀**——v1 + v2 同时接同 Ingress 按比例分流（5%→20%→100%），**渐进 + 风险最低**；实施最复杂（要 Ingress / Mesh 支持）；适合高风险变更。**生产经验**：日常迭代用滚动；大版本用蓝绿；核心业务关键变更用金丝雀（按 Header 内部用户先灰度）。

**Q3：HPA 触发条件 / 算法 / 冷却时间？**

A：**算法**：`desired = ceil(current × (currentMetric / targetMetric))`——例 4 个副本 CPU 80% / 目标 60% → ceil(4 × 80/60) = 6。**触发条件**：默认每 15s 计算一次；**冷却时间**：扩容 0s（快速响应），**缩容 5min**（防抖动）；K8s 1.23+ 用 `behavior` 字段精细控制（`stabilizationWindowSeconds` + `policies`）。**自定义指标**：装 Prometheus Adapter 或 KEDA（事件驱动，支持 Kafka 队列长度 / Redis 等）。

**Q4：HPA 抖动怎么解？**

A：**3 个根因 + 3 个修复**：① **requests 太低** → CPU 利用率虚高 → 频繁扩 / 修复：合理 requests（接近平均用量）；② **缩容冷却太短** → 上下抖 / 修复：`scaleDown.stabilizationWindowSeconds: 300`（5 分钟）；③ **业务波动大但配置激进** / 修复：`behavior.scaleDown.policies` 限速（一次最多缩 25%）。**经验**：缩容冷却 5 分钟起步，扩容快（0~30 秒）；监控 `kube_horizontalpodautoscaler_status_current_replicas` 看历史抖动情况。

**Q5：Pod 怎么优雅停机？详细步骤？**

A：**完整链路**：① apiserver 标 Pod 为 Terminating；② **Endpoint Controller 摘除**（异步，传播延迟几秒）；③ kubelet **调 preStop hook**（同步阻塞）；④ preStop 完发 SIGTERM；⑤ 等 `terminationGracePeriodSeconds`（默认 30s）；⑥ 还没退发 SIGKILL。**关键**：步骤 2 和 3 **并行执行**——必须在 preStop **sleep 15s** 让 Endpoint 真正传播完 + 业务收尾 + 余量。`terminationGracePeriodSeconds` >= preStop sleep + 业务收尾 + 余量（建议 60s）。

**Q6：Spring Boot 怎么配优雅停机？**

A：**4 件事**：① Spring Boot 2.3+ 配 `server.shutdown: graceful` + `spring.lifecycle.timeout-per-shutdown-phase: 30s`；② Dockerfile **CMD 用 exec 形式**（`CMD ["java", ...]`），shell 形式 sh 成 PID 1 收不到 SIGTERM；③ K8s preStop `sleep 15`（让 Endpoint 摘干净再开始关闭）；④ `terminationGracePeriodSeconds: 60`。**Dubbo / Spring Cloud** 还要主动从注册中心摘除（preStop 调 `/actuator/shutdown` 或 unregister 接口）。

**Q7：什么是 PDB？什么场景必须配？**

A：**PodDisruptionBudget**——防止 voluntary disruption（节点 drain / 维护 / 升级 / Cluster Autoscaler 缩节点）一次性 evict 太多副本。配 `minAvailable: 2` 或 `maxUnavailable: 1`，节点 drain 时 K8s 检查：驱逐这个 Pod 后是否还满足 PDB？不满足就**等待**（不强行驱逐）。**必配场景**：① 重要 Service（`minAvailable: replicas / 2 + 1` 半数+1）；② StatefulSet（如 etcd / Kafka，`maxUnavailable: 1`）。**注意**：PDB 不防 involuntary disruption（节点突挂 / Liveness 杀）。

**Q8：HPA / VPA / CA 三层关系？**

A：**三层互补，按粒度分**：
- **HPA**（横向 Pod 数）—— 按 CPU / 自定义指标算 Pod 数 = `current × (currentMetric / target)`；最常用。
- **VPA**（纵向 requests）—— 调 Pod 的 requests / limits；**不能跟 HPA 同时管 CPU**（冲突）；生产常用 `Off` 模式只看推荐值。
- **Cluster Autoscaler**（节点级）—— Pod Pending 找不到节点 → 调云 API 加节点；节点利用率低 → 缩节点。

**典型配合**：HPA 横向扩 Pod → 节点不够 CA 加节点 → 流量回落 HPA 缩 Pod → CA 缩节点。

**Q9：CMD 用 shell vs exec 形式有什么区别？**

A：**shell 形式** `CMD java -jar app.jar` → 实际跑 `/bin/sh -c "java -jar app.jar"` → **sh 成 PID 1**，java 是子进程；K8s 发 SIGTERM 给 PID 1（sh），sh 不转发，java 永远收不到 → **优雅停机失效**，30s 后被 SIGKILL。**exec 形式** `CMD ["java", "-jar", "app.jar"]` → java 直接是 PID 1，能收 SIGTERM。**正确做法**：① 总是用 exec 形式；② 或装 `tini` 作 init 转发信号（`ENTRYPOINT ["/tini", "--"]`）。

**Q10：金丝雀发布怎么实施？**

A：**核心**：v1 + v2 都在跑，通过 Service / Ingress 控制流量比例。**Nginx Ingress 实施**：主 Ingress 100% 到 v1，再建一个 Canary Ingress（同 host）配 `nginx.ingress.kubernetes.io/canary: "true"` + `canary-weight: "20"` 把 20% 流量分到 v2。**渐进**：5% → 20% → 50% → 100%，每个台阶停 1 小时观察指标（错误率 / 延迟 / 业务指标）。**精准灰度**：用 `canary-by-header` 按 Header 路由——内部测试 / VIP 用户先灰度。**工具**：Flagger / Argo Rollouts 自动化（按指标自动晋升或回滚）。

**Q11：minReadySeconds 是干什么的？**

A：**Pod Probe Ready 之后再等 N 秒才算"真就绪"**——防止"看似 ready 但实际刚启动会崩"。**典型场景**：① JVM 刚 warmup，第一个请求慢 10 倍；② 缓存预热没完；③ 连接池初始化中。**滚动更新会等这 N 秒才删下一个旧 Pod**——给新 Pod 充分稳定的窗口。**生产建议**：30s 起步，JVM 大堆应用 60s+；HPA 也用这个值算副本（防止刚扩容的副本立刻被算进利用率分母）。

**Q12：节点维护怎么不丢业务？**

A：**安全 drain 流程**：① 配 PDB（`minAvailable`）防一次驱逐过多；② 配 podAntiAffinity（副本不在同节点）；③ `kubectl drain node-X --ignore-daemonsets --delete-emptydir-data` 优雅驱逐 Pod（K8s 调 preStop + 等 graceful period）；④ 节点维护完 `kubectl uncordon node-X`。**关键**：① **业务必须配 preStop 三件套**（否则 drain 时也丢请求）；② DaemonSet 用 `--ignore-daemonsets` 跳过；③ 监控 drain 期间 PDB 是否阻塞（不阻塞才能继续）。

## 九、答题模板（60 秒话术）

> **Deployment 滚动更新**靠 maxSurge（临时多出）+ maxUnavailable（最多不可用）控制节奏；典型配置 25% / 25%。**3 种发布**：① **滚动**（K8s 原生 / 渐进 / 资源少 / 回滚慢，日常迭代）；② **蓝绿**（两套副本切 Service / 秒级回滚 / 资源翻倍，大版本 + 不兼容 DB 变更）；③ **金丝雀**（按比例分流 + 按 Header 灰度 / 风险最低 / 实施复杂，关键变更）。
>
> **三层弹性**：① **HPA**（横向 Pod 数，公式 `desired = ceil(current × currentMetric/target)`，扩 0s 缩 5min 防抖）；② **VPA**（纵向 requests，跟 HPA 不能同时管 CPU，生产用 Off 模式只看推荐值）；③ **Cluster Autoscaler**（节点级，Pod Pending 加节点 / 利用率低缩节点）。**HPA 抖动**根因 90% 是 requests 设太低 + 缩容冷却太短。
>
> **优雅停机三件套**（**滚动期间不丢请求的核心**）：① **preStop sleep 15s**（让 Endpoint 真正传播 + 业务收尾）；② **terminationGracePeriodSeconds: 60s**（>= preStop + 业务收尾 + 余量）；③ **CMD 用 exec 形式数组**（shell 形式 sh 是 PID 1 收不到 SIGTERM，优雅停机失效）。
>
> **Spring Boot** 加 `server.shutdown: graceful` + `lifecycle.timeout-per-shutdown-phase: 30s`；**Dubbo / Spring Cloud** 在 preStop 主动从注册中心摘除。
>
> **PDB 防 voluntary disruption**——节点 drain / 升级时一次性 evict 副本太多 → 业务挂。重要 Service 必配（`minAvailable: replicas/2+1`）；StatefulSet 用 `maxUnavailable: 1`（如 etcd）。
>
> **6 大生产坑**：① Probe 太松流量打到没起好的 Pod；② preStop sleep 太短 502；③ HPA requests 设太低抖动；④ 节点 drain 副本全在一节点全 evict；⑤ Dockerfile shell 形式 CMD 优雅停机失效；⑥ 滚动更新期间 v1/v2 同时跑 + 数据库不兼容变更冲突（用三步迁移或蓝绿）。
